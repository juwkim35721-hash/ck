# 문제 정의·완료 기준

## 역할
실제 과제의 제공 자료를 읽기 전용으로 분석하여 검증 가능한 완료 조건을 만든다.
구현 순서, 설계 선택, 코드 수정, 제출 실행은 이 스킬의 범위에서 제외한다.
공식 안내가 제공되면 가장 높은 우선순위의 근거로 사용한다.

## 입력
- 실제 과제 루트와 남은 시간을 확인한다.
- 요청문, README, 제공 파일, 담당자 답변의 원문과 출처를 받는다.
- 알려진 제출 형식·경로와 이미 실행한 검증 결과만 받는다.
- 입력이 없으면 내용을 발명하지 말고 읽기 전용 확인 또는 필요한 정보 한 가지를 요청한다.

## 절차
1. 준비 도구 저장소와 실제 과제 루트를 구분하고 제공 자료만 읽는다.
2. 사용자·목표·성공 결과를 한 문장으로 정리한다.
3. 독립 요구사항마다 R1, R2처럼 ID를 부여하고 원문 근거와 해석을 분리한다.
4. 각 R에 입력, 기대 출력, 제약, 보존 조건을 연결한다.
5. 각 R에 정상 사례와 경계 또는 실패 사례를 포함한 수용 기준을 쓴다.
6. 모호한 형용사는 측정값, 출력 형식, 비교 사례처럼 판정 가능한 조건으로 바꾼다.
7. 확인된 제출 파일·형식·경로·필수 내용을 별도로 기록한다.
8. 명시되지 않은 기능, 통합, 성능 약속, 배포를 비목표로 기록한다.
9. 결과를 바꾸는 미확인 사항만 영향도 순으로 표시한다.

## 분기와 중단
- 공식 안내나 담당자 답변이 기존 해석과 충돌하면 안내 원문을 우선하고 충돌을 기록한다.
- 수용 기준을 정할 근거가 없으면 “미확인”으로 남기고 임의 기본값을 정하지 않는다.
- 높은 영향도 미확인이 있으면 구현으로 진행하지 말고 질문 또는 보류 항목으로 넘긴다.
- AI 허용 여부가 불명확하면 공식 안내를 확인할 때까지 분석을 중단한다.
- 후속 AI 금지 서술형이 시작되면 프롬프트·스킬·암기자료 사용을 즉시 중단한다.

## 출력 형식
다음 순서로 짧고 증거 중심으로 출력한다.
1. 사용자 문제 한 문장
2. `R-ID | 원문 근거 | 해석 | 입력/행동 | 기대 출력 | 제약` 요구사항 목록
3. `R-ID | 정상 | 경계/실패 | 판정 방법` 수용 기준 목록
4. 확인된 필수 제출물
5. 미확인 가정과 영향도
6. 비목표
7. 다음 단계 게이트 판정과 부족한 정보

## 완료 기준
- 모든 독립 요구에 R-ID와 원문 근거가 있다.
- 각 R의 수용 기준이 관찰 가능하거나 미확인으로 명시되어 있다.
- 필수 제출물과 비목표가 요구사항 본문과 분리되어 있다.
- 높은 영향도 미확인이 질문 또는 보류로 처리되어 있다.

## 금지 행동
근거 없는 채점 방식, 일정, 모델, 금지 규정, 문항, 만점 보장을 주장하지 않는다.
없는 답변, 테스트 결과, 제출 규칙을 만들지 않는다.
이 단계에서 파일을 수정하거나 테스트를 실행·삭제·숨기지 않는다.
외부 제출, 배포, push, 민감정보 전송을 수행하지 않는다.
전체 사고과정을 요구하지 말고 판단 근거와 확인된 사실만 보고한다.
