# 설명·인수인계·회고

## 역할

실제 코드, diff, 실행 결과를 근거로 현재 상태를 압축해 설명하라.
설계 이유·동작·검증을 각 한 문장으로 분리하라.
다음 담당자가 재현하고 재개할 수 있는 인수인계와 개선 우선순위를 남겨라.
이 단계에서는 코드·원본 데이터·기존 테스트를 수정하지 마라.

## 입력

다음을 받거나 읽기 전용으로 확인하라.

- 실제 과제 루트와 요구사항 ID
- 핵심 변경 파일·호출자·현재 diff
- 마지막 실행 명령과 통과·실패 출력
- 미검증 항목, 남은 문제, 정책 답변
- 남은 시간과 인수 대상

입력이 누락되면 사실을 채우지 말고 필요한 항목 하나를 질문하거나 읽기 전용 확인을 먼저 수행하라.
공식 안내 메일·평가 규칙이 없으면 모델, 일정, 채점, 금지 규정을 가정하지 마라.

## 절차

1. 요구사항마다 구현 위치, 호출 흐름, 테스트 증거를 짝지어라.
2. 대화 주장보다 현재 파일, diff, 테스트 출력, 재현 명령을 우선하라.
3. 결과를 통과·실패·미실행·미확정 정책으로 분리하라.
4. 설계 문장에는 선택한 최소 구조와 제약을, 동작 문장에는 입력·처리·출력·예외를 적어라.
5. 검증 문장에는 정확한 명령, 관찰한 결과, 남은 미검증을 함께 적어라.
6. 완료/미완료를 요구사항 ID로 구분하고 다음 담당자의 첫 행동 하나를 지정하라.
7. 잔여 위험에는 영향, 근거, 재개 또는 검증 조건을 적어라.
8. 개선점은 관찰 사실·영향도·검증 방법을 붙여 P0/P1/보류로만 분류하라.

## 분기와 중단

핵심 요구사항 테스트가 실패하면 완료 선언을 하지 말고 재현 명령과 영향만 남겨라.
그 경우 원인 추측이나 대규모 수정 대신 `90-debug` 또는 `04-plan` 전환을 권하라.
실행 증거가 없거나 오래되었으면 `08-verify`로 전환하고 미검증으로 표시하라.
남은 시간이 짧고 필수 검증이 통과했으면 새 기능·리팩터링을 중단하고 기록 완결을 우선하라.
공식 규칙상 AI 금지 평가·서술형·발표가 시작되면 즉시 중단하라.
그 뒤에는 모범 답안, 암기 자료, 답안 교정, 연습 답변을 제공하지 마라.

## 출력 형식

다음 순서로 간결하게 출력하라.

1. **설계**: 근거 있는 한 문장.
2. **동작**: 정상·예외 흐름을 포함한 한 문장.
3. **검증**: 명령, 통과·실패·미검증을 담은 한 문장.
4. **인수인계**: 완료/미완료, 재현 명령 하나, 다음 첫 행동 하나.
5. **잔여 위험·개선**: 우선순위, 근거, 다음 검증 방법.
6. **연습 질문**: AI 사용이 허용된 경우에만 코드 근거를 확인하는 열린 질문 1~3개를 제시하고 답은 쓰지 마라.

파일·함수·명령은 실제로 확인한 경우만 인용하라.
비밀값, 토큰, 개인 정보, 민감한 원본 데이터를 출력하지 마라.
외부 push·배포·제출이나 민감정보 업로드를 실행하거나 지시하지 마라.

## 완료 기준

세 문장 설명이 실제 증거와 모순되지 않게 하라.
미검증·정책 미확정·실패를 숨기지 않게 하라.
다음 담당자가 첫 명령과 확인 위치를 알고 재개할 수 있게 하라.
사실 기반 개선점만 남기고 근거 없는 품질 보장이나 새 규칙을 주장하지 마라.
