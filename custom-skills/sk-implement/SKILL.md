# 수직 슬라이스 구현

## 역할

한 번에 요구사항 ID 하나만 구현하라.
실제 과제 루트에서 기존 계약을 보존하며 최소 변경을 적용하라.
준비 도구 저장소를 과제 루트로 가정하지 마라.

## 입력

다음을 확인하라.

- 실제 과제 루트와 남은 시간
- 구현할 요구사항 ID와 검증 가능한 수용 기준
- 수정 허용 범위와 사용자의 기존 관련 없는 변경
- 입력·출력·오류 계약 및 선택된 최소 설계
- 기준선 실행 명령과 실제 결과
- 제공된 공식 안내와 AI 사용 가능 범위

입력이 없으면 수정하지 말고 부족한 정보를 질문하거나 읽기 전용으로 확인하라.
공식 안내가 있으면 우선 적용하라.
AI 금지 서술형이 시작되면 즉시 사용을 중단하라.

## 절차

1. 실제 과제 루트, 현재 diff, 호출자, 관련 테스트를 확인하라.
2. 변경 전 가장 좁은 관련 테스트 또는 실행 명령을 실행하고 결과를 기록하라.
3. 기준선 실패를 미구현 요구사항의 예상 실패, 기존 기능 결함, 환경 오류로 구분하라. 담당 슬라이스의 예상 실패는 테스트를 보존하고 구현하되, 무관한 결함·실행 불가 환경은 먼저 보고하고 작업을 분리하라.
4. 입력 → 처리 → 출력이 닫히는 P0 슬라이스 하나와 수정할 파일·함수를 선언하라.
5. 공개 API, 필수 키, 단위, 순서, 오류 형식을 바꿀 근거가 있는지 확인하라.
6. 허용 범위 안에서 선언한 슬라이스만 최소 수정하라.
7. 같은 재현 명령을 실행하고 정상 경로를 실제 assert로 확인하라.
8. 가장 가까운 경계 또는 오류 경로 하나를 assert로 확인하라.
9. 실패하면 실패 위치를 좁힌 뒤 최소 수정하고 같은 명령을 다시 실행하라.
10. 실행 증거와 미검증 항목을 구분해 보고하라.

## 분기와 중단

계약이 모호하여 출력·오류 정책을 정할 수 없으면 추정 구현하지 말고 질문과 되돌릴 지점을 제시하라.
수정이 다수 모듈 재설계, 의존성 교체, 새 기능으로 번지면 현재 슬라이스를 중단하고 범위 축소를 제안하라.
시간이 검증 버퍼를 침범하면 새 슬라이스를 시작하지 말고 현재 변경의 실행 증거를 확보하라.
실행 환경이 없거나 테스트가 실행되지 않으면 통과라고 쓰지 말고 정확한 차단 원인을 보고하라.

## 출력 형식

다음 항목만 사실과 실행 증거로 보고하라.

- 구현한 요구사항 ID와 충족한 수용 기준
- 변경 파일과 함수, 변경 이유
- 실행한 정확한 명령과 통과·실패 실제 결과
- 확인한 정상 경로와 경계/오류 경로
- 남은 작업, 미검증 항목, 정책 또는 환경 한계

## 완료 기준

요구사항 하나가 입력부터 관찰 가능한 출력까지 실제로 실행되어야 한다.
정상 경로와 관련 경계 또는 오류 경로에 assert가 있어야 한다.
기존 API·스키마·원본 데이터·사용자의 관련 없는 변경을 보존해야 한다.

## 금지 행동

기존 테스트나 원본 데이터를 삭제·약화·덮어쓰지 마라.
실패를 건너뛰거나 미실행 결과를 성공으로 기록하지 마라.
전면 리팩터링, 파괴적 reset·rm·재작성, 범위 밖 수정을 하지 마라.
외부 push·배포·제출·민감정보 업로드를 자동 실행하지 마라.
