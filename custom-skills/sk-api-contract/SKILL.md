# API 계약·상태 전이 검증

## 역할

기존 API 표면을 근거로 계약을 추출하고, 상태 코드·본문·부작용을 함께 검증하라.
새 엔드포인트 설계, 인증 정책 재설계, 전면 리팩터링은 이 스킬의 역할로 취급하지 말라.
공식 안내와 과제 규칙을 우선하고, AI 사용이 허용된 단계에서만 실행하라.
AI 금지 서술형이 시작되면 즉시 사용을 중단하라.

## 입력

실제 과제 루트, 남은 시간, 관련 요구사항 또는 명세를 받으라.
라우트·핸들러·스키마·상태 저장소·호출자·기존 테스트의 위치를 확인하라.
서버 또는 테스트 실행 명령과 제공된 인증 주체의 범위를 확인하라.
입력이 없으면 준비 도구 저장소를 과제로 가정하지 말고, 실제 루트를 질문하거나 읽기 전용으로 탐색하라.

## 절차

1. 변경 전 작업 트리와 기존 테스트 방식을 확인하고, 관련 파일을 읽어 계약 증거를 수집하라.
2. 메서드와 경로별로 전제조건, 요청, 성공 응답, 오류 응답, 관찰 가능한 부작용을 정리하라.
3. 각 항목에 근거가 된 파일·함수·명세 위치를 붙이고, 근거 없는 기대값은 미확인으로 표시하라.
4. 상태가 있는 자원은 시작 상태, 허용 전이, 금지 전이, 종결 상태를 분리하라.
5. 정상 요청, 잘못된 입력, 없는 ID, 중복 요청, 적용 가능한 권한 사례를 계약별 테스트로 매핑하라.
6. 기존 테스트 러너 또는 격리된 실제 요청으로 사례를 실행하라.
7. 상태 코드뿐 아니라 응답 본문의 필수 필드·값·오류 구조를 assert하라.
8. 부작용이 있으면 후속 조회, 저장 결과 또는 관찰 가능한 출력으로 실제 결과를 확인하라.
9. 중복 요청은 같은 요청을 두 번 실행하여 생성 수, 최종 상태, 응답 의미를 비교하라.
10. 멱등 키·재시도 규칙은 코드나 명세에 존재할 때만 검사하라.

## 분기와 중단

명세와 현재 코드가 충돌하면 어느 쪽이 계약인지 임의로 결정하지 말고, 각각의 증거와 영향 질문을 보고하라.
실행 환경, 인증 주체, 상태 초기화 방법이 없어 사례를 재현할 수 없으면 요청을 만들거나 결과를 추정하지 말라.
남은 시간이 부족하면 P0 경로의 정상·오류·상태 전이를 우선 실행하고, 나머지는 미검증 사유와 함께 중단하라.
테스트 실패 시 삭제·무시·완화하지 말고 재현 명령, 기대 근거, 실제 본문, 영향 계약을 보존하라.
수정이 필요하면 최소 수정 후보만 제안하고, 승인된 범위에서만 수정·재실행하라.

## 권한과 안전

기존 인증·인가 정책을 편의상 추가, 제거, 우회하지 말라.
제공된 테스트 계정·토큰만 사용하고 자격증명은 출력에 노출하지 말라.
원본 데이터, 기존 테스트, 사용자와 무관한 변경을 삭제·되돌리거나 덮어쓰지 말라.
외부 배포, push, 제출, 실제 운영 데이터 변경을 수행하지 말라.

## 출력 형식

아래 순서로 간결하게 보고하라.

1. `계약 테스트`: 메서드/경로, 입력, 기대 근거, 상태 코드·본문 assert 결과.
2. `상태 전이·멱등성`: 시작/종료 상태, 허용·거부 전이, 중복 요청 비교 결과.
3. `실행 증거`: 정확한 명령, 통과/실패, 실패 재현 정보.
4. `미검증`: 확인하지 못한 계약, 이유, 필요한 입력 또는 다음 검증.

## 완료 기준

각 확인 가능한 API 계약에 실제 실행 또는 명확한 실행 불가 사유를 연결하라.
성공 판정에는 상태 코드와 본문 검증을 포함하고, 상태 변경에는 전후 상태 증거를 포함하라.
미확인 정책·권한·환경을 사실처럼 쓰지 말고 다음 단계가 확인할 수 있게 남기고 종료하라.
