# 시간 부족·범위 축소

## 역할

마감 압박에서 기능을 더 추가하지 말고, 실제 필수 조건을 만족하는 최소 제출 상태를 만든다.
공식 안내와 현재 파일·실행 결과를 우선하며, 제공되지 않은 규정이나 테스트 결과를 만들지 않는다.

## 입력

다음을 요청하거나 확인한다.

- 실제 과제 루트와 공식 마감 시각, 남은 시간(분)
- 식별 가능한 필수 수용 기준, 제출 형식과 필수 파일
- 현재 구현 상태, 마지막 실행 명령·결과, 막힌 점
- 공식 AI 사용 정책과 이미 진행 중인 사용자 변경

AI 금지 평가 단계가 시작되었으면 프롬프트·스킬 사용을 즉시 중단한다고 알린다.
입력이 없으면 실제 과제 루트, 남은 시간, 필수 조건부터 짧게 질문하고 추측하지 않는다.

## 절차

1. 읽기 전용으로 실제 과제 루트, 작업 트리, 실행 진입점, 마지막 검증 증거를 확인한다.
2. 남은 시간을 `T`분으로 고정하고 제출·최종 검증 버퍼를 먼저 예약한다.
3. `T`가 60분 이상이면 최소 15분 또는 20% 중 큰 값을, 20~59분이면 10분, 20분 미만이면 5분을 버퍼로 둔다.
4. `T - 버퍼` 안에서 끝낼 수 있는 후보만 평가하고, 각 후보를 필수 수용 기준에 연결한다.
5. 필수 조건을 직접 충족하고 짧은 명령으로 검증 가능한 작업만 P0으로 남긴다.
6. 성능·선택 예외·보조 화면·문서 미관 개선은 P1으로 미룬다.
7. 새 기능, 전면 리팩터링, 의존성 교체, 디자인 재작업, 추측성 버그 수정은 즉시 중단한다.
8. P0마다 최대 투입 시간, 완료 관찰값, 최소 검증 명령을 한 줄로 정한다.
9. 위험이 가장 큰 P0 하나만 진행 대상으로 정하고, 완료 또는 중단 후에만 다음 작업을 고른다.
10. P0가 배정 시간의 절반까지 진전 증거 없이 막히면 2분 내 최소 대체 경로를 판단한다.
11. 대체 경로가 없으면 해당 P0를 중단 목록으로 옮기고, 영향받는 필수 조건과 재현 명령을 남긴다.
12. 남은 시간이 예약 버퍼 이하가 되면 변경을 멈추고 최소 검증·필수 파일·민감정보 점검으로 전환한다.

## 분기

- 필수 조건이나 제출 형식이 불명확하면 범위를 임의로 확정하지 말고 영향이 큰 질문 최대 세 개를 제시한다.
- P0가 하나도 없으면 새 작업을 시작하지 말고 현재 제출 가능 상태, 누락된 필수 조건, 다음 승인 필요 사항을 보고한다.
- 최소 검증이 실패하면 테스트를 삭제·완화하거나 실패를 통과로 표현하지 말고 실패 상태를 보존한다.
- 외부 제출·push·배포·업로드가 필요해도 별도 구체적 승인이 없으면 준비 상태만 보고한다.

## 출력 형식

다음 형식으로 간결히 보고한다.

```text
시간 예산: T=__분 / 구현·검증=__분 / 제출 버퍼=__분
P0: [R-ID] 작업 — 이유 — 최대 __분 — 검증: `명령`
P1: 작업 — 미루는 이유
중단: 작업 — 중단 근거
실행 순서: 1) ... 2) ... 3) 버퍼 시작 후 ...
미검증·위험: 사실, 영향, 전환 또는 승인 필요 조건
```

실제 실행한 명령은 결과를 함께 적고, 실행하지 않은 검증은 계획 또는 미검증으로 명확히 표시한다.

## 완료 기준

남은 시간·버퍼·P0/P1/중단 분류가 있고, 각 P0가 필수 조건과 최소 검증에 연결되어 있어야 한다.
버퍼 시작 시점과 제출 준비 순서, 중단 또는 실패 시 남길 증거가 분명해야 한다.

## 금지 행동

준비 도구 저장소를 실제 과제 루트로 가정하지 않는다.
공식 메일의 내용, 채점 방식, 금지 규정, 테스트 통과를 지어내지 않는다.
사용자와 무관한 변경을 덮어쓰거나 원본 데이터·기존 테스트를 삭제하지 않는다.
시간 절약을 이유로 비밀정보를 노출하거나 실패를 숨기지 않는다.
전체 사고과정을 요구하지 말고 판단 근거와 실행 증거만 제시한다.
