# 수용 기준과 테스트 케이스 표

## 목적

요구사항의 모호한 완료 문장을 실제 입력과 기대 출력으로 바꾸고 `SPEC.md`의 테스트 기준을 채워라.
이 스킬은 `## 11. 수용 테스트 표 T`만 갱신한다.
테스트 코드 작성은 4.1의 책임이므로 여기서는 구현 파일·테스트 파일을 수정하거나 실행하지 않는다.

## 언제 쓰나 / 쓰지 않나

- 2.1에서 R/AC/P가 통합되고, 가능하면 2.2에서 입출력 계약을 쓴 뒤 사용한다.
- P0/P1의 완성 정의가 추상적이거나 담당자 정책을 코드 테스트로 옮기기 전일 때 사용한다.
- 실제 실패 테스트를 과제 프레임워크에 추가할 때는 → 4.1 test-first (`$sk-test-first`)로 넘긴다.
- 전체 요구사항의 실행 증거를 연결할 때는 → 5.1 verify (`$sk-verify`)를 쓴다.
- 새로운 정책·기대값을 발명하거나 코드 구현 방법을 정할 때는 사용하지 않는다.

## 입력과 사전 확인

1. `sk/work/SPEC.md`의 `## 3. 요구사항 R`, `## 5. 확정 정책 P`, `## 6. 가정 A`, `## 7. 열린 모호성 G`, `## 10. 입출력·데이터 계약`을 읽어라.
2. 각 R의 `AC-R#-n`이 입력→출력 또는 Given/When/Then인지 확인하고, 아니라면 2.1 (`$sk-spec`)으로 돌려보내라.
3. `sk/work/BRIEF.md`의 `## 코드 지도`에서 기존 테스트 프레임워크·픽스처 위치를 읽기만 하여 제공 테스트 여부를 식별하라.
4. 과제 문서와 DM_LOG의 P# 근거를 다시 대조해, 테스트의 기대값이 공식 문서나 확정 답변에 뿌리내리는지 확인하라.
5. 기존 11절이 있으면 이미 할당한 T#를 유지하고, 중복 테스트인지 먼저 확인하라.

## 절차

1. P0 R부터, 그 다음 P1 R 순으로 각각의 AC-R#-n을 한 개 이상 T# 후보로 분해하라.
2. 모든 P#가 적어도 하나의 T#에 연결되는지 별도 점검하라.
3. 각 테스트에 `정상`, `경계`, `실패`, `회귀` 중 하나의 유형을 붙여라.
4. 정상은 대표 입력으로 결과·스키마를 확인하고, 경계는 등호·빈 값·최대/최소·동점 같은 정책 경계 하나를 고르라.
5. 실패는 계약이 정의한 잘못된 입력의 오류 상태·본문·데이터 불변을 검증하고, 오류 정책이 미확정이면 G#로 돌려라.
6. 회귀는 기존 동작·공개 인터페이스·이미 해결한 결함이 변하지 않아야 할 때만 작성하라.
7. 입력 칸에는 재현 가능한 구체값, 요청 본문, 파일 행 또는 사전조건을 적어 모호한 `유효한 입력`을 피하라.
8. 기대 출력 칸에는 정확한 값, 상태, 정렬 순서, 오류 구조 또는 불변 조건을 적어 `정상 처리` 같은 표현을 피하라.
9. 기대값 근거는 손계산 식, 문서 절, P#, 제공 픽스처 중 하나 이상을 적어라.
10. 집계·금액·날짜 계산은 구현 예정 함수의 결과를 기대값 근거로 쓰지 말고 손계산을 보이거나 별도 최소 계산으로 독립 검산하라.
11. 출력 전체가 불필요하게 변할 수 있으면 안정적인 필드·순서·개수·불변 조건만 assert할 수 있게 범위를 명확히 하라.
12. 제공 테스트는 테스트명·파일과 검증하는 R/P를 찾아 `제공 테스트 여부`에 `예: 제공: tests/x`로 표시하라.
13. 제공 테스트가 있어도 특정 AC를 실제로 검증하는지 확인할 수 없다면 `제공됨(범위 미확인)`으로 표시하고 새 T#를 생략하지 마라.
14. T# 표는 `ID | 관련 R/P | 유형 | 입력 | 기대 출력 | 기대값 근거 | 확인 방법 | 제공 테스트 여부` 열을 정확히 사용하라.
15. 확인 방법에는 나중에 실행할 테스트명·명령 또는 수동 관찰 절차를 쓰되, 아직 실행하지 않았다고 명시하라.
16. 가정 A#에 의존하는 T#는 관련 R/P에 A#도 병기하고 기대값이 바뀔 조건을 적어라.
17. H 영향 G#가 기대값을 둘 이상으로 갈라놓으면 임의로 한 경우를 고르지 말고, 1.3 질문 또는 A#의 되돌릴 계획을 요구하라.
18. 표 마지막에 `### 커버리지 점검`을 두어 P0 R, P1 R, P#, 정상/경계/실패/회귀별 누락을 수로 요약하라.
19. 테스트가 많은 경우에도 P0과 모든 P#의 연결 표를 먼저 완성하고 P2는 시간·위험에 따라 표시하라.
20. 11절만 갱신하고 12절 추적표에는 구현·증거 상태를 쓰지 마라.

## 판단 기준·분기

- 한 T#가 여러 R을 다루더라도 관련 R/P에 모두 적되, 실패 시 원인을 구분할 수 없으면 분리하라.
- 한 AC가 여러 결과를 요구하면 값·스키마·정렬·오류를 각각 T#로 나눠 진단 가능하게 하라.
- 정책 P#가 조건→동작으로 충분히 구체적이면 정상 또는 경계 T#를 반드시 하나 만든다.
- P#가 범위만 말하고 기대 결과가 없으면 P#를 고치지 말고 2.1 또는 1.4에 반환하라.
- 기존 제공 테스트와 같은 입력·assert면 제공 테스트를 재사용 표시하되, 근거 없는 포괄 주장으로 커버리지를 채우지 마라.
- 테스트 프레임워크가 불명확하면 확인 방법을 `4.1에서 기존 프레임워크 확인 후 구현`으로 쓰고 명령을 지어내지 마라.
- 시간이 부족하면 각 P0 R당 정상 1개와 핵심 경계/실패 1개, 각 P#당 최소 1개를 우선해 2.4로 넘겨라.

## 작업 노트 기록

`sk/work/SPEC.md`의 `## 11. 수용 테스트 표 T`만 갱신하라.

| 열 | 작성 규칙 |
| --- | --- |
| `ID` | 기존 번호 뒤의 고유 `T#`를 사용 |
| `관련 R/P` | R#, P#, 필요 시 A#를 모두 기입 |
| `유형` | 정상 / 경계 / 실패 / 회귀 중 하나 |
| `입력` | 구체값·사전조건·요청 또는 파일 행 |
| `기대 출력` | 값·상태·스키마·순서·불변 중 관찰값 |
| `기대값 근거` | 손계산·문서·P#·픽스처를 명시 |
| `확인 방법` | 향후 테스트명·명령 또는 수동 절차 |
| `제공 테스트 여부` | 없음 / 제공: 경로 / 제공됨(범위 미확인) |

예: `T4 | R3,P2 | 경계 | requestId=7 재전송 | 200, 이전 결과와 동일, 잔액 변화 0 | P2 및 첫 요청 금액 1000의 손계산 | 4.1에서 API 테스트 추가 | 없음`처럼 쓴다.
손계산 예: `1,000 - 120 = 880`을 근거에 쓰되, 금액 단위·반올림은 10절 계약 또는 P#에 있는 경우만 적용하라.
`### 커버리지 점검`에는 `P0 R 4/4, P1 R 2/3, P# 5/5, 정상 4, 경계 3, 실패 2, 회귀 1`처럼 현재 수치를 기록하라.

## 채팅 출력 형식

다음 순서로 보고하라.

1. 새로 만든 T# 수와 P0/P1/P# 커버리지
2. 독립 기대값 근거가 있는 대표 정상·경계·실패 사례
3. 제공 테스트 재사용 여부와 아직 작성하지 않은 테스트
4. 기대값을 막는 G#/A# 또는 DM 필요 사항
5. 다음 단계: → 2.4 spec-gate (`$sk-spec-gate`), 구현 시 → 4.1 test-first (`$sk-test-first`)

## 완료 기준

- P0/P1 R의 각 AC가 하나 이상 T#에 연결되고 모든 P#가 하나 이상의 T#에 연결돼 있다.
- 모든 T#가 정확한 표 열, 구체 입력, 관찰 가능한 기대 출력, 독립된 기대값 근거를 가진다.
- 정상·경계·실패가 필요한 계약에 대해 구분돼 있으며 회귀가 필요한 기존 동작도 식별됐다.
- 제공 테스트는 존재 여부와 실제 범위가 구분돼 있고, 테스트는 아직 미실행임을 숨기지 않았다.
- 11절 외 SPEC 절과 과제 파일을 바꾸지 않았으며 2.4가 판정할 수 있다.

## 금지

- 테스트 파일, 과제 코드, 원본 데이터, 기존 테스트를 작성·수정·삭제·실행하지 마라.
- 구현 예정 코드의 출력이나 AI의 직감을 기대값 근거로 쓰지 마라.
- 문서·P#에 없는 오류 코드, 정렬, 반올림, 기본값을 테스트에 박아 넣지 마라.
- 제공 테스트가 있다는 사실만으로 R/P가 검증됐다고 주장하지 마라.
- 실패·미확정 기대값을 통과로 표시하거나 G#를 T#로 숨기지 마라.
- 외부 제출·배포·push·업로드 또는 민감정보 출력을 하지 마라.
