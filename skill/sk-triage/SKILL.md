# 과제 유형 판별·공략 경로 선택

## 목적
환경·문서·코드의 초기 관찰을 A~E 유형으로 분류하고, 필수 다음 단계와 시간 배분 초안을 정한다.
복합 과제의 주·보조 유형을 명확히 해 데이터·API·UI·기존 기능 위험을 놓치지 않는다.
이 스킬은 코드를 바꾸지 않으며 `sk/work/BRIEF.md`의 `## 과제 유형·전략`만 갱신한다.

## 언제 쓰나 / 쓰지 않나
- → 0.1 context (`$sk-context`) 직후, 구현 방향을 정하기 전에 사용한다.
- README·디렉터리·테스트에서 과제 형태가 여러 개로 보일 때 사용한다.
- 요구사항 R/C를 원문 인용으로 전부 뽑는 일은 → 1.1 requirements (`$sk-requirements`)의 책임이다.
- 파일·함수·호출 흐름을 상세 지도화하는 일은 → 0.3 code-map (`$sk-code-map`)으로 넘긴다.
- 실제 설계, 구현 순서, 코드 수정, 테스트 작성은 여기서 하지 않는다.

## 입력과 사전 확인
- `sk/work/BRIEF.md#환경`의 실행 환경, 기준선, 금지 조건을 먼저 읽는다.
- 과제 README, 명세, 샘플 입출력, 디렉터리 이름, 실행 스크립트, 기존 테스트를 읽기 전용으로 본다.
- 공식 안내가 있는 경우 그 안내의 과제 범위와 제출물을 가장 높은 근거로 둔다.
- 관찰과 추측을 분리한다. 파일명만으로 기능을 단정하지 않는다.
- 시간이 남은 정도와 담당자에게 첫 DM을 보낼 수 있는 시점을 입력으로 받는다.

## 절차
1. 과제의 한 문장 목표를 문서의 동사를 유지해 적는다.
   예: “CSV를 읽어 집계한다”는 A 후보, “기존 엔드포인트의 규칙을 고친다”는 B·D 후보가 된다.
2. 아래 유형별 관찰 증거를 표로 수집한다.
   - A 데이터 처리·집계: CSV/JSON, 변환·집계, 배치 출력, 통계·정합성 요구.
   - B API·백엔드 규칙: 라우트, HTTP 상태, 요청·응답 스키마, 서비스·저장소 계층.
   - C 풀스택·UI: 화면 컴포넌트, 폼, 사용자 흐름, 브라우저·클라이언트 상태.
   - D 버그 수정·기존 기능 유지·리팩터링: 실패 테스트, 결함 재현, 기존 공개 인터페이스 보존.
   - E CLI·알고리즘: 표준입출력, 명령 옵션, 시간·공간 복잡도, 결정적 출력.
3. 주 유형 1개와 보조 유형 0~2개를 선택한다.
   선택하지 않은 유형도 반증 증거가 있으면 기록해 과잉 분류를 막는다.
4. 유형별 위험을 목표·제약과 연결한다.
   A는 결측·중복·단위·반올림·원본/결과 대사, B는 상태 코드·오류 스키마·호환성, C는 정상/빈/오류 흐름, D는 회귀·변경 범위, E는 경계·복잡도·정렬 결정성을 우선 확인한다.
5. 유형별 필수 프롬프트 ID를 고른다.
   공통으로 → 1.1 requirements (`$sk-requirements`), → 1.2 ambiguity (`$sk-ambiguity`), → 2.1 spec (`$sk-spec`), → 2.3 acceptance (`$sk-acceptance`)를 연결한다.
6. 유형 전용 필수 경로를 추가한다.
   A면 → 2.2 io-contract (`$sk-data-contract`)와 → 5.3 data-validation (`$sk-data-validation`)을 필수로 표시한다.
   B면 → 2.2 io-contract (`$sk-data-contract`)와 → 5.4 api-contract (`$sk-api-contract`)를 필수로 표시한다.
   C면 → 0.3 code-map (`$sk-code-map`), → 5.5 ui-smoke (`$sk-ui-smoke`)를 필수로 표시하고 API가 있으면 5.4도 추가한다.
   D면 → 0.3 code-map (`$sk-code-map`), → 4.1 test-first (`$sk-test-first`), → 5.1 verify (`$sk-verify`)를 필수로 표시한다.
   E면 → 2.3 acceptance (`$sk-acceptance`), → 4.1 test-first (`$sk-test-first`), → 5.1 verify (`$sk-verify`)를 필수로 표시한다.
7. 첫 DM 시점을 정한다.
   출력 형식, 결측·오류 규칙, 충돌 우선순위처럼 구현 결과를 바꾸는 H 영향 모호성이 보이면 요구사항·모호성 추출 직후 → 1.3 dm-questions (`$sk-dm-questions`)를 제안한다.
   문서로 답이 명확하거나 질문이 평가 방식만 묻는 경우에는 DM을 제안하지 않는다.
8. 남은 시간 기준의 초안 예산을 작성한다.
   전체 시간의 약 20%는 발견·명세, 40%는 P0 구현, 15%는 검증, 15%는 보고서·QA 준비, 최소 10분은 제출 버퍼로 둔다.
   실제 남은 시간이 적으면 P0·필수 제출물·검증 증거·버퍼를 먼저 고정한다.
9. `sk/work/BRIEF.md`의 `## 과제 유형·전략`만 생성 또는 갱신한다.
   주 유형의 근거가 바뀌기 전에는 결론을 자주 바꾸지 않고, 새 사실이 나오면 변경 이유를 남긴다.
10. 최우선 경로를 한 줄로 제시한다.
    보통은 → 1.1 requirements (`$sk-requirements`)이며, 기존 코드가 있으면 그 전에 또는 병렬로 → 0.3 code-map (`$sk-code-map`)을 권한다.

## 판단 기준·분기
- if 데이터 파일과 API가 함께 있으면 then A와 B를 모두 쓰되, 채점·제출물에 더 직접적인 것을 주 유형으로 둔다.
- if 화면만 보이고 API 호출이 있으면 then C 주 유형, B 보조 유형으로 두고 UI와 계약 모두를 경로에 넣는다.
- if “수정”, “회귀”, 기존 테스트 실패가 중심이면 then D를 반드시 포함하고 공개 인터페이스 보존을 위험으로 적는다.
- if 입력 크기·제한·정렬·표준입출력이 명시되면 then E를 포함하고 최악 복잡도와 동점 처리를 위험으로 적는다.
- if 근거가 부족하면 then `판정 보류`로 쓰고 1.1의 문서 추출 후 재판정한다.
- if H 영향 모호성이 하나라도 있으면 then 구현 시작 전에 1.2와 필요 시 1.3을 우선한다.
- if 남은 시간이 30분 이하이면 then 주 유형의 P0 최소 경로와 검증 1종을 고정하고 보조 유형의 확장 기능은 보류 후보로 둔다.
- if 공식 문서와 기존 코드가 달라 보이면 then 어느 쪽도 조용히 선택하지 말고 → 1.2 ambiguity (`$sk-ambiguity`)에서 G로 등록한다.

## 작업 노트 기록
`sk/work/BRIEF.md`에서 정확히 `## 과제 유형·전략` 섹션만 쓴다.
유형 판단은 다음 표를 사용한다.

| 유형 | 판정 | 근거(문서·파일:줄) | 주요 위험 | 필수 다음 ID | 최소 경로 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| A 데이터 처리·집계 | 주/보조/해당 없음/보류 | 관찰 사실 | 결측·대사 등 | 2.2, 5.3 등 | P0 우선 행동 |
| B API·백엔드 규칙 | 주/보조/해당 없음/보류 | 관찰 사실 | 계약·상태 코드 등 | 2.2, 5.4 등 | P0 우선 행동 |
| C 풀스택·UI | 주/보조/해당 없음/보류 | 관찰 사실 | 사용자 흐름 등 | 0.3, 5.5 등 | P0 우선 행동 |
| D 기존 기능 유지 | 주/보조/해당 없음/보류 | 관찰 사실 | 회귀·호환성 등 | 0.3, 4.1, 5.1 등 | P0 우선 행동 |
| E CLI·알고리즘 | 주/보조/해당 없음/보류 | 관찰 사실 | 경계·복잡도 등 | 2.3, 4.1, 5.1 등 | P0 우선 행동 |

이어 아래 표를 쓴다.

| 구간 | 목표 | 시간 상한 | 중단·축소 기준 |
| :--- | :--- | :--- | :--- |
| 발견·명세 | R/C/G와 명세 게이트 | 전체의 약 20% | H G는 가정·DM으로 관리 |
| P0 구현 | 가장 작은 수직 슬라이스 | 전체의 약 40% | P1/P2는 보류 후보 |
| 검증 | 유형별 독립 근거 | 전체의 약 15% | 미검증을 통과로 쓰지 않음 |
| 보고·QA | 보고서 근거와 이해 자료 | 전체의 약 15% | 증거 없는 문장 제외 |
| 제출 버퍼 | 파일·형식·최종 확인 | 최소 10분 | 새 기능 금지 |

마지막에 `첫 DM 시점: <시점 또는 불필요 이유>`와 `다음 행동: <ID + 스킬>` 한 줄을 둔다.

## 채팅 출력 형식
1. **한 줄 판정**: 주 유형과 보조 유형, 확신도, 가장 강한 근거를 말한다.
2. **유형 표**: A~E의 판정·근거·위험을 짧은 표로 낸다.
3. **필수 공략 경로**: 공통과 유형 전용 ID를 순서대로 말한다.
4. **시간·축소안**: 남은 시간 기준 예산과 가장 먼저 뺄 범위를 말한다.
5. **첫 DM**: 질문이 필요한 H 영향 모호성과 보낼 시점, 또는 불필요 이유를 말한다.
6. **기록·다음 단계**: `sk/work/BRIEF.md#과제 유형·전략` 갱신과 다음 ID를 말한다.

## 완료 기준
- A~E를 관찰 근거로 판정했고 주·보조 유형을 구분했다.
- 유형별 위험과 필수 프롬프트 ID·스킬 이름을 연결했다.
- 첫 DM 시점과 시간을 초과했을 때의 축소 기준을 정했다.
- `sk/work/BRIEF.md#과제 유형·전략`만 갱신했다.
- 구현 지시나 코드 변경 없이 1-discover로 넘길 준비가 되었다.

## 금지
- 파일명·프레임워크 이름만으로 과제 정책이나 채점 기준을 사실처럼 단정하지 않는다.
- 요구사항을 새로 발명하거나 H 영향 모호성을 임의 정책으로 확정하지 않는다.
- 평가·채점 방식을 묻는 DM을 만들거나 Codex가 담당자에게 DM을 보냈다고 주장하지 않는다.
- 과제 코드, 테스트, 설정, 데이터, 의존성 파일을 수정하지 않는다.
- `sk/` 폴더를 과제 분석·테스트 대상으로 포함하지 않는다.
- 시간이 부족하다는 이유로 검증·제출 버퍼를 0으로 계획하지 않는다.
