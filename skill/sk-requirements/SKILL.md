# 요구사항·제약·제출물 추출

## 목적

과제 문서, 코드, 테스트, 설정에 흩어진 사실을 구현 가능한 후보 요구사항으로 분해한다.
명시 문장과 관찰된 동작을 섞지 않고, 각 항목에 재검증 가능한 출처를 붙인다.
이 스킬은 정책을 결정하지 않는다. 해석이 갈리는 부분은 `G#` 후보로 넘긴다.

## 언제 쓰나 / 쓰지 않나

- 착수 단계의 환경 확인 뒤, 담당자에게 첫 DM을 보내기 전에 사용한다.
- README, API 명세, 샘플 파일, 기존 테스트, TODO, 설정 중 하나라도 있을 때 사용한다.
- 새 과제 문서가 도착하거나 범위가 바뀌면 해당 출처만 다시 훑어 갱신한다.
- 코드 구현, 테스트 작성, 데이터 이상치의 상세 판정에는 사용하지 않는다.
- 담당자 답변을 정책으로 바꾸는 일은 `→ 1.4 dm-answers ($sk-dm-log)`에 맡긴다.

## 입력과 사전 확인

- 과제 루트와 `sk/`의 경계를 확인한다. `sk/`는 도구이므로 과제 분석 대상이 아니다.
- `sk/work/BRIEF.md`의 `## 환경`, `## 과제 유형·전략`, `## 코드 지도`가 있으면 먼저 읽는다.
- 과제 README, 안내 문서, API 스펙, 예제 입출력, 설정 파일, 테스트 파일의 경로를 모은다.
- 파일은 읽기만 한다. 이 단계에서 과제 코드·테스트·설정을 수정하지 않는다.
- 공식 안내가 따로 있으면 문서 이름과 문단·파일:줄을 출처로 기록할 준비를 한다.
- 실행이 안전하고 이미 허용됐더라도 여기서는 관찰 목적의 명령만 사용하며 결과를 추정하지 않는다.

## 절차

1. **증거 목록을 만든다.** 문서 → 샘플 → 테스트 → 코드 → 설정 순으로 읽고, 각 파일의 역할을 한 줄로 적는다.
2. **제출물을 먼저 찾는다.** “제출”, “산출물”, “실행”, “포트”, “파일명”, “형식”을 찾아 파일·경로·형식을 분리한다.
3. **명시 요구를 문장 단위로 쪼갠다.** 한 문장에 행동과 조건이 둘 이상이면 각각 별도 `R#` 후보로 만든다.
4. **입력·처리·출력으로 재배열한다.** 입력값, 검증, 계산·상태 전이, 오류, 출력 스키마, 실행 조건을 구분한다.
5. **암묵 요구를 관찰한다.** 테스트의 기대값, 함수 시그니처, 라우트, 픽스처 이름, 기존 호출자가 유지해야 할 인터페이스를 찾는다.
6. **암묵 요구에는 관찰 꼬리표를 붙인다.** “테스트 관찰”, “코드 관찰”로 쓰며 공식 요구처럼 승격하지 않는다.
7. **제약을 별도 `C#`로 뽑는다.** 수정 금지 파일, API 호환성, 허용 라이브러리, 포트·호스트, 성능·규모, 데이터 보안 제약을 요구와 분리한다.
8. **우선순위를 잠정 배정한다.** 제출·실행 불가·핵심 결과 오류는 P0, 요구된 부가 동작은 P1, 있으면 좋은 개선은 P2 후보로 둔다.
9. **모호한 표현을 표시한다.** “적절히”, “유효한”, “빠르게”, “정렬”, “오류 처리”처럼 결과가 여러 개인 문장은 즉시 `G#` 후보로 만든다.
10. **출처를 검산한다.** 각 R/C/제출물 행이 실제 파일과 줄 또는 문단을 가리키는지 확인한다.
11. **발견 노트만 갱신한다.** 기존 ID와 다른 스킬 섹션을 보존하고, 새 행에만 다음 번호를 부여한다.
12. **다음 행동을 연결한다.** G 후보가 있으면 `→ 1.2 ambiguity ($sk-ambiguity)`, 없으면 `→ 2.1 spec ($sk-spec)`을 권한다.

### 증거 읽기 순서와 질문

| 출처 | 먼저 찾을 것 | 기록할 사실 |
| :--- | :--- | :--- |
| README·과제 문서 | 목표, 입력, 제출 형식, 금지 | 원문 인용과 문단·줄 |
| API 스펙·샘플 | 메서드, 필드, 상태 코드, 예시 | 필수/선택·타입·정렬 |
| 기존 테스트 | 기대값, 오류, 회귀 인터페이스 | 테스트명·입력·assert |
| 코드·TODO | 현재 동작, 호출자, 미구현 흔적 | 파일:줄·관찰 여부 |
| 설정·스크립트 | 실행 명령, 포트, 환경 변수 | 값이 아닌 키·경로 |

### R과 C의 구분 예시

- `R#`: “CSV의 유효 레코드별로 점수를 계산해 JSON 배열을 반환한다.”처럼 제품이 해야 할 동작이다.
- `C#`: “기존 `/api/summary` 경로와 응답 필드명은 유지한다.”처럼 구현 선택을 제한한다.
- “결과를 점수 내림차순으로 정렬한다”는 R이지만, 동점의 2차 키가 없으면 별도 G다.
- “음수는 무효”라는 문장이 없고 데이터에 음수가 보인다는 사실만으로 필터링 R을 만들지 않는다.

## 판단 기준·분기

- 공식 문서에 명시되면 `R#` 또는 `C#`로 기록하고 출처를 “공식 문서”로 쓴다.
- 테스트가 문서와 다르면 둘 다 인용하고 독자적으로 고르지 말고 `G#` 후보로 보낸다.
- 코드가 문서와 다르게 동작하면 현재 코드의 관찰일 뿐이다. 문서 요구를 덮어쓰지 않는다.
- 제출 경로가 없으면 “미지정”으로 기록하고, 추측한 경로를 필수 제출물로 단정하지 않는다.
- 필수인지 불명확한 기능은 P1 후보와 G 후보를 함께 만들고 담당자 확인 대상으로 둔다.
- 데이터·로그에 비밀값이나 개인정보가 보이면 값 자체 대신 필드명·패턴·건수만 기록한다.
- 문서에 평가·채점 방식이 없으면 질문 후보에 넣지 않는다. 평가 방식 질문은 금지다.
- 10분밖에 없으면 README, 제출 안내, 테스트 이름·assert, 실행 설정만 읽어 P0와 C만 기록한다.

## 작업 노트 기록

`sk/work/DISCOVERY.md`가 없으면 만들되, 아래 정확한 제목만 추가한다. 다른 섹션은 바꾸지 않는다.

### `## 필수 제출물`

| ID | 항목 | 경로·파일명 | 형식 | 출처 | 상태 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| D1 | 실행 결과 | 문서에 명시된 경로 또는 미지정 | 예: JSON | README:12 | 확인 필요 |

제출물이 불확실하면 상태를 `확인 필요`로 두고 `G#`로 연결한다.

### `## 요구사항 후보 R`

| ID | 내용 | 우선순위 후보 | 수용 기준 초안 | 출처 | 성격 | 상태 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| R1 | 조건과 동작을 한 문장으로 | P0 | 입력 → 기대 결과 | 파일:줄 | 명시/관찰 | 후보 |

`수용 기준 초안`은 구현 방법이 아니라 관찰 가능한 결과로 쓴다.

### `## 제약 C`

| ID | 제약 | 종류 | 출처 | 영향 R | 상태 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| C1 | 기존 응답 필드 유지 | 인터페이스 | 테스트:24 | R1 | 확인 |

종류는 인터페이스, 실행환경, 수정범위, 의존성, 성능, 보안, 제출형식 중 하나로 통일한다.

## 채팅 출력 형식

다음 순서로 짧게 보고한다.

1. 읽은 출처와 아직 읽지 못한 출처
2. 필수 제출물 표 요약과 미지정 항목
3. P0/P1/P2 후보 R 목록과 근거
4. C 목록과 구현에 미치는 제한
5. 해석이 갈리는 문장 또는 충돌의 `G#` 후보
6. 다음 행동: `→ 1.2 ambiguity ($sk-ambiguity)` 또는 `→ 2.1 spec ($sk-spec)`

각 주장에는 파일:줄, 문단, 테스트명 중 하나를 붙인다. 추정은 “가정”이라고 분리한다.

## 완료 기준

- 제출물마다 항목·경로 또는 미지정·형식·출처가 기록돼 있다.
- 모든 P0 후보 R과 모든 C에 관찰 가능한 출처가 있다.
- 명시 요구와 코드·테스트 관찰이 구분돼 있다.
- 해석이 갈리는 사항이 R 속에 숨지 않고 G 후보로 분리돼 있다.
- 다음 단계가 명확하고, 과제 파일을 수정하지 않았다.

## 금지

- 담당자 답변이나 공식 문서에 없는 정책을 확정 사실로 쓰지 않는다.
- 기존 테스트의 기대값만 보고 비즈니스 의도를 지어내지 않는다.
- 과제 코드, 테스트, 설정, 원본 데이터 또는 `sk/` 도구 파일을 수정하지 않는다.
- 비밀값·개인정보·원본 민감 데이터를 노트나 채팅에 복사하지 않는다.
- 평가·채점 방식, 내부 ID만 나열한 DM 질문, 구현 해법 자체를 담당자에게 묻는 일을 하지 않는다.
