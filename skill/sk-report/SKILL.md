# 제출 보고서 작성

## 목적

- 공식 제출물이 요구하는 보고서를 `sk/templates/SUBMISSION_DOC_TEMPLATE.md`의 5개 절 구조 그대로 작성한다.
- 주장마다 실제 작업 노트의 ID, 파일·함수 위치 또는 실행 증거를 연결해 과장 없는 제출 문서를 만든다.
- 과제 지정 경로가 있으면 그 경로·파일명에 저장하고, 미지정이면 `sk/work/REPORT_DRAFT.md`에만 초안을 남긴다.
- 코드나 원본 데이터를 수정하지 않는다. 이 스킬의 산출물은 보고서와 저장 위치 확인 요청이다.

## 언제 쓰나 / 쓰지 않나

- 7.2 준수 감사 뒤, 제출 전에 구현 근거를 제출 문서로 정리할 때 쓴다.
- 6.5 범위 축소 뒤에는 실제 완성 범위와 한계를 투명하게 문서화할 때 쓴다.
- `SPEC.md` 2절에 보고서의 경로·파일명·형식이 확정됐을 때 공식 경로에 쓴다.
- 제출 경로가 비어 있거나 “문서 제출”만 적혀 있으면 공식 경로를 추정하지 말고 초안만 쓴다.
- 요구사항 분석, 코드 설계, 새 테스트 작성, 코드 수정이 목적이면 이 스킬을 쓰지 않는다.
- 아직 의미 있는 실행 증거가 없다면 보고서를 완성으로 선언하지 말고 → 5.1 verify (`$sk-verify`)로 넘긴다.

## 입력과 사전 확인

1. `sk/work/SPEC.md`에서 `## 2. 필수 제출물`, `## 3. 요구사항 R`, `## 4. 제약 C`, `## 5. 확정 정책 P`, `## 11. 수용 테스트 표 T`, `## 12. 추적표`를 읽는다.
2. `sk/work/DM_LOG.md`에서 실제로 받은 `## M<n>` 블록과 `## 정책 목록 P`를 읽는다. 답변이 없는 DM을 확인된 정책처럼 쓰지 않는다.
3. `sk/work/DECISIONS.md`에서 관련 `## DD<n>`와 `## AI 교정 기록`을 읽는다.
4. `sk/work/EVIDENCE.md`의 `## 실행 기록`에서 현재 코드 기준 PASS, FAIL, 미검증, STALE을 구분한다.
5. 있으면 `sk/work/UNDERSTANDING.md`에서 실제 파일·함수 흐름과 한계·개선안을 교차 확인한다.
6. `sk/work/REVIEW.md`가 있으면 차단·높음 발견과 `## 준수 감사`의 미충족 항목을 읽는다.
7. `sk/templates/SUBMISSION_DOC_TEMPLATE.md`를 원문으로 읽고, 제목과 1~5절의 순서·절 제목을 바꾸지 않는다.
8. `SPEC.md` 2절에서 보고서 대상이 과제 제출물인지, 단순 실행 로그인지, 경로가 무엇인지 확인한다.
9. 비밀값, 개인식별정보, 원본 데이터의 민감한 값이 노트·출력에 있는지 확인하고 요약·가명·건수로 대체한다.

## 절차

1. 보고서의 저장 위치를 먼저 결정한다.
   - `SPEC.md` 2절에 명시된 경로·파일명이 있으면 그 위치가 공식 경로다.
   - 제출 경로가 확정되지 않았으면 `sk/work/REPORT_DRAFT.md`에만 작성하고, 사용자에게 공식 경로 확인을 요청한다.
   - 보고서 경로가 필수 제출물 표의 경로와 다르면 임의로 둘 중 하나를 고르지 말고 불일치를 알린다.
2. 템플릿을 복사해 작성 기반을 만든다. 공식 경로가 확정된 경우에만 다음처럼 대상 경로를 채운다.

```bash
cp sk/templates/SUBMISSION_DOC_TEMPLATE.md <과제 지정 보고서 경로>
```

3. 템플릿의 예시 문구와 대괄호 플레이스홀더를 남기지 않는다. 근거가 없으면 그 문장을 지우거나 “미검증”과 사유를 적는다.
4. 1절에는 `SPEC.md`의 목표·제약·필수 인터페이스를 압축한다.
   - 핵심 해결 목표는 R#와 연결된 한두 문장으로 쓴다.
   - 제약은 실제 적용한 C#만 적고, 바인딩·출력 스키마 같은 항목은 과제 문서에 있을 때만 적는다.
   - DM 항목은 실제 M# 질문과 답변에서 확정된 P#를 “문의 → 반영 결과”로 쓴다.
5. 2절 표는 관련 DD#마다 한 행을 쓴다.
   - `의사결정 항목`에는 결정 대상, `채택한 방식`에는 현재 구조, `비교 대안`에는 실제 검토한 대안만 쓴다.
   - `채택 이유 및 트레이드오프`에는 R#/P#/C# 근거와 포기한 이점을 함께 쓴다.
   - 대안을 검토한 기록이 없으면 만들어 내지 말고, 한 행으로 현재 선택과 제한을 투명하게 적는다.
6. 3절에는 실제 수정·핵심 파일과 함수만 2~5개로 추린다.
   - 각 항목을 `` `경로` (`함수 또는 모듈`) `` 표기로 시작한다.
   - 입력 경계 → 규칙 적용 → 출력/오류의 흐름을 실제 호출 순서로 설명한다.
   - 함수명이나 흐름이 불확실하면 `UNDERSTANDING.md`와 코드를 읽어 확인한 뒤 적는다.
7. 4절에는 T#와 E#의 현재성 있는 결과만 쓴다.
   - 정상 경로는 입력 범주, 기대값 근거, 실제 명령 또는 테스트, E# 판정을 한 문장으로 묶는다.
   - 엣지 케이스는 템플릿에 적힌 세 범주를 포함해 실제로 처리·검증한 항목만 번호 목록으로 적는다.
   - 제목의 “7대 엣지 케이스”라는 표현 때문에 일곱 항목을 채우지 않는다. 처리하지 않은 범주는 적지 않는다.
   - 실패 또는 미검증 T#는 숨기지 말고 항목과 사유, 다음 행동을 짧게 적는다.
   - AI 교정은 `AI#`가 있을 때만 초기 제안의 문제, 발견 방법, 수정 지시, E# 검증 순으로 적는다.
8. 5절에는 현재 구조에서 실제로 가능한 실패 조건과 구체적 후속 개선을 쓴다.
   - 시간·범위 때문에 생긴 제한은 `PLAN.md`의 축소 결정 및 검증 범위와 대조한다.
   - “성능 개선” 같은 일반론 대신 어느 경계·모듈을 어떤 방식으로 바꾸고 무엇으로 검증할지 쓴다.
   - 이미 확인된 결함은 한계가 아니라 미해결 이슈로 명확히 구분한다.
9. 작성 후 아래 근거 표로 문장마다 역추적한다. 표는 보고서에 반드시 넣을 필요는 없고 작업 중 점검용으로 쓴다.

| 보고서 절 | 주장 요약 | 근거 ID/위치 | 상태 | 조치 |
| :--- | :--- | :--- | :--- | :--- |
| 1절 | 정책 반영 | P# / M# | 확인 | 표현 유지 |
| 2절 | 설계 선택 | DD# / R# | 확인 | 표 행 작성 |
| 3절 | 구현 흐름 | 파일:함수 | 확인 필요 | 코드 재확인 |
| 4절 | 검증 통과 | T# / E# | 현재/STALE | 재실행 또는 미검증 |
| 5절 | 한계·개선 | PLAN / REVIEW | 확인 | 구체화 |

10. 템플릿 구조 점검을 한다.
    - 제목 `# 과제 수행 계획 및 기술 의사결정·검증 보고서`를 유지한다.
    - 1~5절 제목과 순서를 유지한다.
    - 2절의 4열 표를 유지한다.
    - 플레이스홀더 `[` `]`의 예시 문구, 사실이 아닌 수치, “모두 통과” 같은 포괄 표현이 없는지 확인한다.
11. 저장 후 파일 경로와 미검증·열린 이슈를 채팅에 분명히 보고한다.

## 판단 기준·분기

- if `SPEC.md` 2절에 보고서 경로·형식이 명시됨 → then 그 경로에 템플릿 기반 보고서를 저장한다.
- if 경로만 있고 형식이 불명확함 → then 과제 안내를 다시 확인하고, 충돌이 없으면 Markdown 템플릿을 사용하되 확인 필요를 보고한다.
- if 제출 경로가 없음 → then `sk/work/REPORT_DRAFT.md`만 작성하고 공식 위치를 사용자에게 질문한다.
- if E#가 STALE임 → then 해당 결과를 현재 통과 증거로 쓰지 말고 → 5.1 verify (`$sk-verify`) 재실행을 권한다.
- if T#가 FAIL임 → then “통과”로 서술하지 말고 실패 사실과 영향 범위를 적고 → 6.1 debug (`$sk-debug`)로 넘긴다.
- if P#가 없고 담당자 답변도 없음 → then 정책 확정처럼 쓰지 말고 A# 또는 G# 상태로 표현한다.
- if 보고서의 예시가 실제 과제와 다름 → then 예시를 그대로 남기지 말고 실제 구현으로 교체한다.
- if 민감정보가 근거에 포함됨 → then 원문 값은 제거하고 행 수·범주·마스킹된 식별자 등 안전한 요약으로 바꾼다.
- if 시간이 10분 미만임 → then 1절 목표·제약, 3절 실제 파일·흐름, 4절 최신 E#, 5절 미검증만 우선 채우고 장황한 배경 설명을 줄인다.

## 작업 노트 기록

- 이 스킬은 보고서 제출물이 공식 경로로 확정되기 전까지만 `sk/work/REPORT_DRAFT.md`를 작성한다.
- `REPORT_DRAFT.md`에는 템플릿의 5절 구조를 유지하고, 첫 줄 아래에 `- 상태: 초안 | 공식 제출 경로: 미확정`을 적는다.
- 공식 경로가 확정되면 `REPORT_DRAFT.md`에는 이동 사실만 간단히 남기고, 과제 지정 보고서 파일을 최신으로 유지한다.
- `SPEC.md`, `DM_LOG.md`, `DECISIONS.md`, `EVIDENCE.md`, `UNDERSTANDING.md`의 기존 섹션은 이 스킬이 덮어쓰지 않는다.
- 보고서에서 참조한 ID는 원문을 바꾸지 않고 인용·연결만 한다.

## 채팅 출력 형식

1. **저장 위치**: 공식 경로 또는 `sk/work/REPORT_DRAFT.md`, 그리고 공식 경로 확정 여부
2. **근거 요약**: 1절 R#/C#/P#, 2절 DD#, 4절 T#/E#의 사용 범위
3. **미검증·제외**: 쓰지 않은 주장, STALE/FAIL/미검증 항목과 사유
4. **템플릿 점검**: 5절 구조·4열 표 유지, 플레이스홀더 제거 여부
5. **다음 행동**: → 8.2 deliver (`$sk-deliver`) 또는 필요한 검증/수정 스킬

## 완료 기준

- 보고서가 과제 지정 경로에 저장됐거나, 미지정이면 `sk/work/REPORT_DRAFT.md`에만 저장됐다.
- `SUBMISSION_DOC_TEMPLATE.md`의 제목과 1~5절 구조·순서, 2절 4열 표가 보존됐다.
- 모든 핵심 주장이 실제 R#/C#/P#/DD#/T#/E#/AI# 또는 파일·함수 위치로 추적된다.
- 예시 문구·대괄호 플레이스홀더·만들어 낸 DM 답변·만들어 낸 테스트 결과가 없다.
- PASS, FAIL, 미검증, STALE가 실제 증거와 일치하며 민감정보가 없다.
- 다음 단계가 → 8.2 deliver (`$sk-deliver`)로 명시됐다.

## 금지

- 제출 경로를 추측해 과제 파일의 임의 위치에 보고서를 만들지 않는다.
- 템플릿의 5개 절을 재구성하거나 예시 플레이스홀더를 그대로 제출하지 않는다.
- 실행하지 않은 테스트, 담당자가 답하지 않은 정책, 존재하지 않는 AI 교정 기록을 사실처럼 쓰지 않는다.
- 실제 처리하지 않은 엣지 케이스를 개수 맞추기 위해 추가하지 않는다.
- 코드·테스트·원본 데이터·제출 설정을 수정하거나 외부 제출·업로드·push를 실행하지 않는다.
- 비밀값, 토큰, 개인정보, 민감한 원본 데이터 값이나 전체 실행 로그를 보고서에 넣지 않는다.
