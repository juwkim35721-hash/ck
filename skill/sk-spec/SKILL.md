# 명세 통합과 동결

## 목적

흩어진 과제 문서, 코드 관찰, 담당자 답변, 가정을 `sk/work/SPEC.md` 한 곳의 구현 기준으로 통합하라.
구현을 제안하거나 과제 파일을 고치지 말고, 무엇이 확정·가정·미해결인지 추적 가능하게 분리하라.
이 스킬은 SPEC의 1~9절과 13절을 책임진다.
0절·14절은 `sk-spec-gate`, 10절은 `sk-data-contract`, 11절은 `sk-acceptance`, 12절은 구현·검증 스킬의 소유다.

## 언제 쓰나 / 쓰지 않나

- 1.1~1.4가 만든 발견 노트와 DM 답변을 구현 전에 한 문서로 묶을 때 쓴다.
- 담당자 답변, 과제 문서 또는 관찰이 새로 들어와 명세의 근거가 바뀌었을 때 다시 쓴다.
- 2.2·2.3보다 먼저 쓰고, 2.4 게이트 직전에 최신화한다.
- 단순히 질문을 만들 때는 → 1.3 dm-questions (`$sk-dm-questions`)를 쓴다.
- 답변 원문을 정책으로 해석할 때는 → 1.4 dm-answers (`$sk-dm-log`)를 쓴다.
- 코드·테스트·원본 데이터를 수정하거나 수용 테스트를 실제 파일에 작성할 때는 쓰지 않는다.

## 입력과 사전 확인

1. `sk/work/BRIEF.md`의 `## 환경`, `## 과제 유형·전략`, `## 코드 지도`를 읽어 실행 환경과 관찰 근거를 확인하라.
2. `sk/work/DISCOVERY.md`의 `## 필수 제출물`, `## 요구사항 후보 R`, `## 제약 C`, `## 모호성 G`를 읽어라.
3. `sk/work/DM_LOG.md`의 모든 `## M<n> …` 블록과 `## 정책 목록 P`를 읽어 원문과 해석을 대조하라.
4. 과제의 공식 문서·README·테스트·코드는 읽기만 하고, 인용은 파일:줄 또는 문서 절로 남겨라.
5. 기존 `sk/work/SPEC.md`가 있으면 먼저 0~14절, 특히 10~12절과 14절을 읽어 다른 스킬의 내용을 보존할 준비를 하라.
6. 자료가 없으면 없는 사실을 요구사항으로 만들지 말고 G 또는 A 후보로 분류하라.

## 절차

1. `SPEC.md`가 없으면 표준 0~14절 제목을 모두 만든 뒤, 이 스킬 소유 절만 채우고 다른 소유 절에는 대기 표지만 둬라.
2. 파일이 있으면 다른 스킬 소유 절을 덮어쓰지 말고 1~9절과 13절만 갱신하라.
3. 근거를 공식 과제 문서·대회 안내, P#, 관찰된 테스트·코드, A# 순으로 정렬하라.
4. 공식 문서와 P#가 상충하면 어느 쪽도 조용히 선택하지 말고 G#로 등록하고 1.3용 확인 질문 초안을 남겨라.
5. `## 한 장 요약`을 10줄 이내로 써서 목표, 입력, 출력, 핵심 규칙, 제출물을 한눈에 보이게 하라.
6. `## 구현 시 반드시 지킬 규칙 Top 5`에는 출력 계약, 확정 정책, 제약, 금지 변경, 검증 기준 중 실패 비용이 큰 다섯 개만 넣어라.
7. `## 1. 목표`는 사용자의 결과와 범위를 한 문단으로 쓰고, 해결 수단이나 추측을 목표로 쓰지 마라.
8. `## 2. 필수 제출물`은 `항목 | 경로·파일명 | 형식 | 출처` 표로 작성하고, 경로가 미정이면 미정 사유와 G#를 남겨라.
9. `## 3. 요구사항 R`은 `ID | 내용 | 우선순위 P0/P1/P2 | 수용 기준 AC | 출처 | 상태` 표로 작성하라.
10. R은 검증 가능한 한 문장으로 쪼개고, 하나의 R에 독립 동작과 제약을 섞지 마라.
11. 모든 R마다 `AC-R#-n`을 부여하고 `입력 → 기대 출력` 또는 Given/When/Then으로 관찰 가능하게 써라.
12. P0는 제출·핵심 기능·호환성에 필수인 최소 집합만 지정하고, 근거 없는 P0 확대를 피하라.
13. `## 4. 제약 C`는 `ID | 제약 | 종류 | 출처` 표로 작성하고 인터페이스, 실행 환경, 수정 금지, 성능, 보안 제약을 구분하라.
14. `## 5. 확정 정책 P`는 `ID | 규칙 "조건 → 동작" | 예시 | 근거 M#/문서 | 영향 R` 표로 작성하라.
15. P#의 예시는 실제 작은 입력과 결과를 적고, 담당자 답변의 범위를 넘어 일반화하지 마라.
16. `## 6. 가정 A`는 `ID | 가정(기본값) | 근거 | 위험 | 되돌릴 지점 | 확인 계획` 표로 작성하라.
17. A#는 답이 없어서 임시로 선택한 것만 기록하고, 기본값처럼 보이게 P#로 위장하지 마라.
18. `## 7. 열린 모호성 G`에는 미해결 항목만 남기고 `영향 | 현재 선택지 | 처리 방식 | 결정 필요 시점`을 함께 써라.
19. 해결된 G#는 삭제하지 말고 상태를 해결로 옮겨 13절 변경 기록과 연결하거나 발견 노트에 보존하라.
20. `## 8. 비목표`에는 이번 구현에서 하지 않을 기능·호환 범위·운영 작업을 명확히 적어 범위 팽창을 막아라.
21. `## 9. 용어집`에는 문서마다 뜻이 흔들릴 수 있는 도메인 용어, 상태, 단위를 `용어 | 뜻 | 근거`로 정의하라.
22. `## 13. 변경 기록`은 `시각 | 변경 | 이유·근거 | 영향` 표로 시작하고, 이번 통합·수정도 한 행으로 기록하라.
23. 동결 전에는 빠진 R, P의 출처, G와 A의 구분, 제출물 경로를 다시 대조하라.
24. 2.2와 2.3이 뒤에 채울 10~11절의 입력으로 필요한 R/P/AC를 명확히 남겨라.

## 판단 기준·분기

- 공식 문서와 P#가 일치하면 공식 문서를 출처로 우선 적고 P#를 보강 근거로 연결하라.
- P#와 코드 관찰이 다르면 P#를 정책으로 우선하되, 기존 호환성 위험을 C# 또는 G#로 명시하라.
- 코드가 문서와 다른 동작을 보여도 관찰 사실만 쓰고, 변경 요구인지 예외인지 G#로 확인하라.
- 담당자 답이 `적절히`처럼 모호하면 원문 범위를 넘지 말고 A#에 기본안과 되돌릴 지점을 기록하라.
- H 영향 G#가 남으면 1.3 (`$sk-dm-questions`)로 질문을 만들고, 답을 기다리는 동안만 되돌릴 수 있는 A#로 진행하라.
- P0 R에 AC가 없으면 명세는 아직 게이트에 낼 수 없으므로 AC부터 완성하라.
- 시간이 부족하면 한 장 요약, Top 5, P0 R·AC, C, P, H G, A, 제출물부터 채우고 P1/P2의 세부화를 나중에 표시하라.

## 작업 노트 기록

`sk/work/SPEC.md`의 다음 정확한 제목을 사용하라.

| 절 | 기록 내용 | 형식 |
| --- | --- | --- |
| `## 한 장 요약` | 목표·입력·출력·규칙·제출물 | 10줄 이내 |
| `## 구현 시 반드시 지킬 규칙 Top 5` | 실패 비용이 큰 다섯 규칙 | 번호 목록 |
| `## 1. 목표`~`## 9. 용어집` | 통합된 명세 | 위 절차의 표 |
| `## 13. 변경 기록` | 근거 있는 명세 변화 | 시각·변경·이유·영향 |

다른 스킬이 쓴 0, 10, 11, 12, 14절은 읽되 수정하지 마라.
예: `R3 | 중복 주문은 한 번만 반영 | P0 | AC-R3-1: 같은 requestId 두 번 입력 → 잔액 1회 변화 | README 32행 | 확정`처럼 쓴다.
예: `P2 | requestId가 기존이면 → 기존 결과를 반환하고 잔액을 다시 바꾸지 않음 | id=7 재요청 → 동일 응답 | M2-1 | R3`처럼 쓴다.

## 채팅 출력 형식

다음 순서로 짧게 보고하라.

1. SPEC 반영 범위와 읽은 근거 수
2. P0 R와 핵심 P# 요약
3. 새로 등록·해결·승격한 G#/A#/P# 목록
4. 남은 충돌 또는 H 영향 위험과 필요한 사용자 행동
5. 다음 단계: → 2.2 io-contract (`$sk-data-contract`) 및 → 2.3 acceptance (`$sk-acceptance`)

## 완료 기준

- `SPEC.md`에 표준 0~14절 제목이 있고, 이 스킬 소유 절 1~9와 13이 현재 근거로 채워져 있다.
- 한 장 요약은 10줄 이하이며 Top 5가 R/C/P와 모순되지 않는다.
- 모든 R에 우선순위·출처·상태와 하나 이상의 AC-R#-n이 있다.
- P#에는 조건→동작, 예시, M#/문서 근거, 영향 R이 있다.
- A#에는 위험·되돌릴 지점·확인 계획이 있고 미해결 G#와 혼동되지 않는다.
- 다른 스킬 소유 절을 덮어쓰지 않았으며 이번 변경이 13절에 기록돼 있다.

## 금지

- 과제 코드, 기존 테스트, 원본 데이터, 설정을 수정·삭제·생성하지 마라.
- 공식 안내에 없는 모델, 일정, 채점 방식, 금지 규정, 담당자 답변을 사실처럼 만들지 마라.
- DM을 직접 보내거나 답변을 지어내지 마라. 복붙용 문안은 1.3에 넘긴다.
- 근거가 없는 정책·기대값·기본값을 P#로 확정하지 마라.
- 동결 뒤 13절 기록 없이 조용히 명세를 바꾸지 마라.
- 외부 제출·배포·push·업로드·자격증명 전송을 하지 마라.
- 비밀값·개인정보·민감한 원본 데이터 값을 노트나 채팅에 쓰지 마라.
