# 질의 루프 — 전체 스캔·DM·후속 질문 반복

## 목적

- 과제 루트 전체(도구 폴더 `sk/` 제외)를 빠짐없이 스캔해 요구사항 R·제약 C·필수 제출물·모호성 G를 뽑는다.
- 담당자 DM 질문 → 사용자가 붙여 넣은 답변 반영 → 답변이 만든 파생 질문을 **라운드** 단위로 반복해, 구현 전에 "무엇을 만들어야 하는지"를 닫힌 목록으로 만든다.
- 라운드마다 상태판으로 남은 모호성을 숫자로 보여 주고 `계속` / `확인` / `종료` / `차단`을 판정한다.
- 이 스킬은 1.1~1.5의 진행자다. 세부 형식은 아래 원본 스킬의 해당 절을 읽어 그대로 따른다.
  - R·C·제출물 추출: `sk/skill/sk-requirements/SKILL.md`
  - 14개 범주 G 탐지: `sk/skill/sk-ambiguity/SKILL.md`
  - DM 문구 규칙: `sk/skill/sk-dm-questions/SKILL.md` (템플릿 `sk/templates/DM_QUESTION_TEMPLATES.txt`)
  - 답변 해석·P 변환: `sk/skill/sk-dm-log/SKILL.md`
  - 재진술 확인 DM: `sk/skill/sk-dm-confirm/SKILL.md`

## 언제 쓰나 / 쓰지 않나

- 0.1 context(필요하면 0.2·0.3) 직후, 발굴부터 DM 수렴까지 한 흐름으로 진행하고 싶을 때 쓴다.
- 담당자 답변을 붙여 넣고 해석·영향 재스캔·후속 질문까지 한 번에 받고 싶을 때 쓴다.
- 명세 동결 뒤에도 남은 가정과 구현 중 생긴 새 모호성을 병행 라운드로 계속 확인할 때 쓴다.
- DM 문구 하나만 다듬을 때는 `→ 1.3 dm-questions ($sk-dm-questions)`, 답변 하나만 기록할 때는 `→ 1.4 dm-answers ($sk-dm-log)`를 쓴다.
- `SPEC.md` 통합·수용 테스트·동결 판정은 하지 않는다. 루프가 닫히면 `→ 2.1 spec ($sk-spec)`으로 넘긴다.
- 코드 구현·테스트 작성에는 쓰지 않는다. 루프 중에는 읽기와 `sk/work/` 기록만 한다.

## 루프 개요

```text
R0 전체 스캔 → R·C·G 목록 → R1 질문(최대 3개) → [사용자가 DM 전송] → 답변 원문 붙여넣기
        ▲                                                                   │
        │            ┌──── 영향 재스캔 · 파생 G 추출 · 자체 해결 ◀─────────────┘
        │            ▼
        └── 판정: 계속(R2 질문) / 확인(재진술 DM 1회) / 종료(→ 2.1 spec)
                  / 병행 전환(동결 시각 도달 → 구현하며 계속 질문) / 차단(긴급 단일 질문)
```

## 입력과 사전 확인

- `sk/work/DM_LOG.md`에 `## 질의 루프 상태판`이 있으면 먼저 읽고, 마지막 라운드부터 이어 간다. 없으면 R0부터 시작한다.
- `sk/work/BRIEF.md`(환경·과제 유형·코드 지도), 기존 `sk/work/DISCOVERY.md`, `sk/work/DM_LOG.md`를 읽는다.
- 현재 시각과 남은 시간을 확인한다. 모르면 사용자에게 한 줄로 묻고, 답이 없으면 MASTER_GUIDE 3절 시간표(첫 DM 10:22, 동결 10:40)를 기준으로 한다.
- 과제 루트 `AGENTS.md`는 `SK-KIT:BEGIN`~`SK-KIT:END` 관리 구역 밖의 내용만 과제 지시로 본다.
- 과제 코드·테스트·데이터·설정은 읽기만 한다. 쓰는 파일은 `sk/work/DISCOVERY.md`, `sk/work/DM_LOG.md`뿐이다.
- 사용자가 붙여 넣은 답변이 있으면 어느 M#에 대한 답인지 먼저 확인한다. 불명확하면 가장 최근 `발송됨` M#으로 보되 그 가정을 출력에 밝힌다.

## 절차

### 라운드 0 — 전체 스캔 (DM 없음, 10분 이내)

1. **파일 인벤토리를 만든다.** 추적 파일과 미추적 파일을 모두 본다.

```bash
find . \( -path ./sk -o -path ./.git -o -path ./.agents -o -path ./.codex -o -path ./node_modules -o -path ./.venv -o -path ./venv -o -name __pycache__ \) -prune -o -type f -print | sort | head -500
git ls-files 2>/dev/null | grep -v '^sk/' | wc -l
```

2. **역할과 읽기 깊이를 정한다.** 파일(또는 같은 종류 묶음)마다 역할(문서·명세 / 샘플·데이터 / 테스트 / 코드-진입점 / 코드-핵심 / 코드-보조 / 설정 / 스크립트 / 기타)과 깊이(정독 / 훑음 / 목록만 / 제외+사유)를 붙인다.
   - 반드시 정독: 모든 문서·명세, 모든 테스트, 진입점, 미구현 흔적이 있는 파일, 실행 설정.
   - 데이터: 헤더와 앞 몇 줄만 보고, CSV·JSON·JSONL이면 `python3 sk/snippets/data_audit.py <파일>`로 결측·음수·중복 수치를 얻는다.
   - `.env` 등 비밀이 있을 수 있는 파일은 키 이름만 기록하고 값은 출력하지 않는다.
   - 바이너리·대용량·생성물·벤더 코드는 `제외`로 두되 사유를 적는다.
3. **신호를 검색한다.** `rg`가 없으면 `grep -rn`으로 같은 패턴을 쓴다.

```bash
rg -n -i "TODO|FIXME|XXX|NotImplemented|not implemented|구현하세요|구현 필요" --glob '!sk/**' --glob '!AGENTS.md'
rg -n -i "반드시|해야|금지|must|should|required|제출|submit|형식|format|포트|port|정렬|sort|반올림|round|null|empty|빈 값|오류|error|status|timezone|UTC|KST" --glob '!sk/**' --glob '!AGENTS.md' --glob '!*.csv' --glob '!*.jsonl'
rg -n "assert|expect\(|toEqual|status_code|pytest.raises" --glob '!sk/**'
```

4. **R·C·제출물을 뽑는다.** `sk-requirements`의 절차·표 형식으로, 모든 행에 `파일:줄` 출처를 단다. 테스트·코드에서 관찰한 암묵 요구에는 `테스트 관찰`·`코드 관찰` 꼬리표를 붙인다.
5. **G를 뽑는다.** `sk-ambiguity`의 14개 범주를 한 번씩 통과한다. G마다 결과가 달라지는 구체 예시와 영향도 H/M/L을 적는다.
6. **자체 해결을 먼저 시도한다.** 공식 문서 → 최신 샘플 → 제공 테스트 → 관찰된 코드 순으로 확인하고, 답이 있으면 `자체 해결`로 닫는다.
7. **질문 가능성 필터를 적용한다.** 결과가 달라지고, 문서로 답이 없고, 담당자 업무 정책에 속하는 G만 DM 후보로 둔다. 내부 설계 선택은 `→ 3.2 design ($sk-design)`으로 넘긴다.
8. **상태판을 만들고 R1 질문 묶음을 고른다.** H 먼저, 최대 3문항, 하나의 답이 여러 G를 닫는 질문을 우선한다.
9. **R1 DM을 만든다.** `sk-dm-questions` 규칙(상황 1줄 · 실제 값 예시 · A/B(/C) · 기본 제안과 이유 · 다른 기준 허용 · `1-A, 2-B` 안내 · 12줄 이내)을 지킨다. `DM_LOG.md`에 `## M<n>` 블록과 `M<n>-k → G#` 매핑을 남기고, 해당 G 상태를 `질문 중(M<n>-k)`로 바꾼다.

### 라운드 n — 답변 반영 (사용자가 원문을 붙여 넣었을 때)

1. **원문을 보존한다.** 해당 M 블록의 `답변 원문`에 그대로 붙인다. 요약으로 대체하지 않는다.
2. **질문별로 분류한다.** 명시 / 조건부 / 사례 / 위임("알아서") / 무응답 / 선택지 밖 새 정책 / 문서·테스트와 충돌 중 하나로 나눈다.
3. **변환한다.** 명시·조건부는 `P#`("조건 → 동작" + 마스킹 예시 + 근거 M#), 위임은 기본안이 있는 `가정 전환` 후보, 부분 답·충돌은 G 재오픈으로 처리한다(`sk-dm-log` 해석 규칙).
4. **영향 재스캔을 한다.** 새 P마다 그 규칙의 키워드(필드명·상태값·경로·함수명·용어)로 과제 전체를 다시 검색한다.

```bash
rg -n -i "<필드명>|<상태값>|<엔드포인트>|<용어>" --glob '!sk/**' --glob '!AGENTS.md'
```

   - 같은 규칙이 적용돼야 하는 다른 위치(다른 엔드포인트·집계·화면·출력 파일)
   - 기대값이 반대인 기존 테스트·샘플 출력·문서 문장 → 충돌 G
   - 규칙이 바꾸는 출력 필드·건수·정렬·상태 코드 → 영향 R/C/T 후보
5. **파생 질문 7점검을 한다.** 답변 하나마다 아래를 확인하고, 결과가 달라지며 문서에 답이 없는 것만 새 G로 등록한다(출처: `파생 M<n>-k`).

| 점검 | 확인 질문 | 예: "음수 수량은 제외" 답변 뒤 |
| :--- | :--- | :--- |
| 경계 | 등호·0·빈 문자열은 같은 규칙인가? | 수량 0은 제외인가 포함인가 |
| 적용 범위 | 다른 필드·엔드포인트·데이터셋에도 적용되나? | 금액 음수에도 같은 규칙인가 |
| 출력 표현 | 제외·오류 사실을 응답이나 로그에 드러내나? | 제외 건수를 응답에 넣는가 |
| 집계 영향 | 분모·건수·평균·순위가 바뀌나? | 평균의 분모에서 빠지는가 |
| 규칙 순서 | 기존 P와 동시에 적용될 때 순서는? | 중복 제거 전인가 후인가 |
| 예외 | 이 규칙이 적용되지 않는 조건이 있나? | 반품 레코드는 예외인가 |
| 시점 | 기존·과거 데이터에도 소급하나? | 이미 저장된 결과도 다시 계산하나 |

6. **자체 해결을 다시 시도한다.** 파생 G도 문서·테스트·데이터에서 답을 찾으면 바로 닫는다. 데이터에 해당 사례가 0건이고 문서가 침묵하면 영향도를 한 단계 낮춘다(단, 외부 인터페이스·금액·데이터 손실은 낮추지 않는다).
7. **상태판을 갱신하고 판정한다.** 아래 판정표를 적용한다.
8. **다음 행동을 만든다.** `계속`이면 다음 묶음 DM, `확인`이면 재진술 DM, `종료`면 구현 기준 요약과 인계, `차단`이면 긴급 단일 질문을 만든다.

## 판단 기준·분기

### 판정표

| 판정 | 조건 | 행동 |
| :--- | :--- | :--- |
| 계속 | 질문 가치가 있는 열린 H, 또는 P0 결과를 바꾸는 열린 M이 1개 이상 | 다음 묶음 DM(최대 3문항, H 먼저) |
| 확인 | 열린 H 0개, P0 결과를 바꾸는 열린 M 0개 | `sk-dm-confirm` 형식 재진술 DM 1회 |
| 종료 | 확인 DM에 동의·수정 반영 완료, 또는 남은 G가 모두 L·범위 밖 | 남은 G를 `가정 전환`·`보류`로 정리하고 `→ 2.1 spec ($sk-spec)` |
| 병행 전환 | 열린 H·M이 남았지만 동결 목표 시각이 지남 | 남은 G를 되돌릴 지점이 있는 `가정 전환`으로 두고 `→ 2.1 spec ($sk-spec)`·2.4로 진행, 질문은 병행 라운드로 계속 |
| 차단 | 필수 제출물·P0 출력 형식 자체가 미정이고 문서·답변 모두 없음 | 긴급 단일 질문 + 사용자에게 위험 고지, 2.4에서 BLOCKED 예상 |

### "모호성이 닫혔다"의 정의

- 모든 G의 상태가 `자체 해결` / `해결(P#)` / `가정 전환(기본안·되돌릴 지점 기록)` / `범위 밖` / `보류(L)` 중 하나다.
- `열림`·`질문 중`·`충돌` 상태의 H G가 0개다.
- 모든 P#에 "조건 → 동작", 예시, 근거 M#/문서가 있다.
- 공식 문서와 P# 사이의 충돌이 0개다.
- 모든 P0 R에 대해 입력 하나를 주면 기대 출력을 손으로 계산할 수 있다.

### 질문 수와 멈추는 기준

- 총 질문 수와 라운드 수에는 상한을 두지 않는다. 루프는 "닫힘 정의"를 충족할 때까지 계속한다.
- 줄이는 대상은 질문 개수가 아니라 **가치 없는 질문**이다. 매 라운드 질문 가능성 필터(결과가 달라짐 · 문서·테스트·데이터로 답이 없음 · 담당자 정책 영역)를 다시 적용한다.
- 한 메시지는 최대 3문항이다. 물을 것이 더 있으면 라운드를 늘린다. 담당자가 한 번에 정확히 답할 수 있는 양을 지키기 위해서다.
- 앞 메시지의 답이 오기 전에는 다음 묶음을 보내지 않는다. 예외는 구현을 막는 긴급 단일 질문뿐이다. 재촉 DM은 만들지 않는다.
- 질문 순서는 H → P0 결과를 바꾸는 M → 나머지 M이다. L은 묻지 않고 `가정 전환`·`보류`로 둔다.
- 같은 G를 두 번 물었는데도 불명확하면 "이 예시의 결과가 X인가요?" 사례 확인을 1회 하고, 그래도 불명확하면 `가정 전환`한다. 한 항목에서 끝없이 반복하지 않기 위해서다.
- **수렴 점검**(멈춤이 아니라 보고): 라운드 5회 또는 누적 질문 15개를 넘길 때마다, 그리고 2라운드 연속으로 새로 열린 H가 닫힌 H보다 많을 때 아래를 보고하고 계속할지 사용자에게 묻는다.
  - 남은 열린 G 수(H/M/L)와 최근 2라운드의 열림·닫힘 추세
  - 질문이 과제 범위 밖으로 넓어지는지. 그렇다면 "이번 과제 범위에 X가 포함되나요?" 같은 범위 확인 질문 1개로 여러 G를 한꺼번에 정리할 수 있는지
  - 지금 멈추면 가정으로 남는 항목과 그 위험
- 답을 10분 넘게 기다리면 답에 의존하지 않는 작업(2.2 io-contract, 0.3 code-map 보강, 기본안 기록)을 제안한다.

### 동결 시각과 병행 라운드

- 동결 목표(시작 후 약 40분, 예시 10:40)는 질문을 멈추는 시각이 아니라 **구현을 시작하는 시각**이다.
- 그 시각에 열린 H·M이 남아 있으면 각 G를 기본안·근거·위험·되돌릴 지점이 있는 `가정 전환`으로 바꾸고 `병행 전환`으로 판정한다. 2.1 → 2.4는 READY-WITH-ASSUMPTIONS로 진행한다. 단, 필수 제출물·P0 출력 형식이 비어 있으면 `차단`이다.
- 병행 라운드에서는 구현과 동시에 남은 G를 계속 묻는다. 상태판 모드를 `병행`으로 바꾸고 라운드 번호를 이어 `R<n>(병행)`으로 기록한다.
- 되돌리는 비용이 큰 가정(출력 형식·API·집계 규칙)부터 묻는다.
- 답이 가정과 같으면 그 G를 `해결(P#)`로 바꾼다. 다르면 P를 만들고 `SPEC.md` 13절 변경 기록이 필요하다고 표시한 뒤, 되돌릴 지점과 영향받는 T#부터 고치도록 `→ 2.1 spec ($sk-spec)`에 넘긴다.
- 구현 중 새로 생긴 G도 같은 방식으로 병행 라운드에 넣는다. 문서·기존 P로 답이 있으면 묻지 않는다.
- 질문 마감: 리뷰 단계(예시 12:00) 이후에는 H만 묻고, 제출 점검(예시 12:35) 이후에는 새 질문을 보내지 않는다. 늦게 온 답은 반영할 시간이 없거나 바꾸는 위험이 더 크기 때문이다. 그때 남은 가정은 보고서 5절과 Q6 한계로 넘긴다.

## 작업 노트 기록

- `sk/work/DISCOVERY.md`: `## 필수 제출물`, `## 요구사항 후보 R`, `## 제약 C`, `## 모호성 G`는 1.1·1.2 형식 그대로 쓴다. 루프가 소유하는 `## 스캔 커버리지` 절을 추가한다.

```markdown
## 스캔 커버리지
- 기준: sk/ · .git · .agents · 의존성 폴더 제외, 파일 N개

| 경로·묶음 | 역할 | 깊이 | 사유·메모 |
| :--- | :--- | :--- | :--- |
| README.md | 문서 | 정독 | 제출 형식 3절 |
| tests/ (4개) | 테스트 | 정독 | 동점 기대값 test_rank.py:41 |
| data/raw.csv | 데이터 | 훑음 + data_audit | 결측 12, 음수 3 |
| vendor/ | 기타 | 제외 | 외부 라이브러리 |
```

- G 상태값은 `열림` / `질문 중(M<n>-k)` / `부분 해결` / `충돌` / `해결(P#)` / `자체 해결` / `가정 전환` / `범위 밖` / `보류`를 쓴다. 해결된 행은 지우지 않는다.
- `sk/work/DM_LOG.md`: M 블록과 `## 정책 목록 P`는 1.3·1.4 형식 그대로 쓴다. 루프가 소유하는 `## 질의 루프 상태판`을 파일 맨 위에 둔다.

```markdown
## 질의 루프 상태판
- 현재: R2 답변 대기 | 판정: 계속 | 갱신: 10:31
- 누적: 라운드 2 · 질문 5개 · 모드: 동결 전 · 동결 목표 10:40

| 라운드 | 메시지 | 질문 | 새 P | 가정 전환 | 신규·재오픈 G | 열린 H | 판정 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| R0 | — | — | — | — | G1–G9 | 4 | 질문 |
| R1 | M1 | 3 | P1, P2 | — | G10(파생), G11(충돌) | 3 | 계속 |

### 현재 구현 기준
- R2(P0) 유효 레코드 합계 → P1 음수 제외, P2 빈 결과 `[]`
- 미정: G10 수량 0 처리(H, M2-1 질문 중)
```

- `현재 구현 기준`은 라운드마다 다시 쓴다. P0 R마다 적용되는 P·가정과 아직 열린 G를 한 줄씩 적는다.

## 채팅 출력 형식

1. **라운드·판정**: 예) `R1 답변 반영 완료 → 판정: 계속`
2. **상태판 요약**: 열린 H/M/L 수, 질문 중, 이번 라운드 새 P·가정 전환·신규 G 수, 누적 라운드·질문 수와 모드(동결 전/병행). 수렴 점검 조건이면 점검 결과도 함께
3. **이번 라운드 변화**: 새 P("조건 → 동작"), 파생·충돌 G와 근거 위치(`파일:줄`)
4. **다음 DM**: `계속`·`확인`·`차단`이면 복붙용 메시지 1개를 `text` 코드블록으로, `종료`면 "질문 없음"
5. **사용자가 할 일**: "위 메시지를 직접 DM으로 보내고, 답이 오면 `$sk-clarify-loop` 다음 줄에 답변 원문을 그대로 붙여 넣으세요."
6. R0에는 **스캔 커버리지 요약**(파일 N개 중 정독·훑음·제외 수와 제외 사유)을 추가한다.
7. `종료`에는 **구현 기준 요약**(P0 R별 적용 P·가정, 남은 가정의 되돌릴 지점)과 `→ 2.1 spec → 2.2 io-contract → 2.3 acceptance → 2.4 spec-gate` 인계를 추가한다.

## 완료 기준

- `## 스캔 커버리지`에 `sk/` 등 제외 대상을 뺀 모든 파일(또는 묶음)이 역할·깊이와 함께 있고, 제외에는 사유가 있다.
- 모든 R·C·G에 출처가 있고, 모든 DM 질문이 M#-k → G#로 연결된다.
- 모든 답변 원문이 M 블록에 보존됐고, 모든 P#에 조건 → 동작·예시·근거가 있다.
- 상태판이 최신이며 라운드마다 판정과 이유가 기록됐다.
- 루프 종료 시 "닫힘 정의"를 충족했거나, 병행 전환 시점의 `가정 전환` 목록(기본안·되돌릴 지점)과 병행 라운드에서 계속 물을 G 목록이 있다.

## 금지

- Codex가 DM을 보냈다고 쓰거나, 담당자 답변을 지어내거나, 예상 답으로 다음 라운드를 진행하지 않는다.
- 한 라운드에 메시지 2개 이상, 한 메시지에 질문 4개 이상, 재촉 메시지를 만들지 않는다.
- 문서·테스트·데이터로 답할 수 있는 질문, 구현 방법·채점 방식 질문, 이미 확정된 P를 다시 묻는 질문을 보내지 않는다.
- 루프 중에 과제 코드·테스트·데이터·설정을 수정하거나 구현을 시작하지 않는다.
- `sk/` 도구 파일과 `AGENTS.md` 관리 구역의 문장을 과제 요구사항으로 해석하지 않는다.
- 비밀값·개인정보·민감한 원본값을 DM·노트·채팅에 옮기지 않는다.
