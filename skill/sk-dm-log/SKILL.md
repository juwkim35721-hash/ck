# 담당자 답변 기록·해석·후속 질문

## 목적

사용자가 붙여넣은 담당자 답변을 왜곡 없이 보존하고, 코드와 테스트에 적용할 수 있는 `P#` 정책으로 변환한다.
답변의 범위를 넘어 일반화하지 않으며, 모호한 위임은 `A#` 가정으로 남겨 추적 가능하게 한다.
문서·기존 답변과 충돌하는 경우 조용히 고르지 않고 `G#`를 다시 연다.

## 언제 쓰나 / 쓰지 않나

- 사용자가 담당자 DM 답변 원문을 붙여 넣은 직후 사용한다.
- `→ 1.3 dm-questions ($sk-dm-questions)`의 M# 질문에 대한 회신을 해석할 때 사용한다.
- 구현 중 정책 변경 회신, 범위 변경 회신, 확인 메시지 답변에도 사용한다.
- 답이 오기 전에는 사용하지 않는다. 예상 답이나 가공된 요약만으로 P를 만들지 않는다.
- 완전한 명세 통합은 `→ 2.1 spec ($sk-spec)`가 담당한다.

## 입력과 사전 확인

- 사용자가 제공한 답변 원문과 관련 `M#` 블록을 `sk/work/DM_LOG.md`에서 찾는다.
- 해당 M의 질문 문구, G 매핑, 발송 전 기본안을 읽는다.
- `sk/work/DISCOVERY.md`의 관련 R/C/G와 공식 문서·테스트 근거를 함께 확인한다.
- 답변의 시간, 발신자 역할, 인용·이모지·줄바꿈을 과도하게 정리하지 않고 보존한다.
- 담당자 답변이 아니거나 출처가 불명확하면 P로 승격하지 않고 출처 확인을 요청한다.

## 절차

1. **원문을 먼저 붙인다.** M 블록의 `답변 원문` 아래에 사용자가 준 텍스트를 그대로 넣는다.
2. **질문별 답을 분리한다.** `M2-1`, `M2-2`와 연결하되, 한 답이 여러 질문을 덮는지 표시한다.
3. **명시 답·조건부 답·위임·무응답을 구분한다.** “A”, “A이지만 B면…”, “알아서”, 답 없음은 서로 다르게 처리한다.
4. **P 후보를 조건 → 동작으로 바꾼다.** 주체·입력 조건·결과·오류/출력까지 있어야 한다.
5. **예시를 하나 붙인다.** 실제 민감값 대신 작은 마스킹 예시로 P가 테스트 가능한지 확인한다.
6. **일반화 범위를 제한한다.** 담당자가 “이 케이스는 제외”라고만 했으면 모든 음수·모든 데이터셋으로 확장하지 않는다.
7. **불명확한 표현을 A로 기록한다.** “적절히”, “알아서”, “보통”은 담당자 위임을 근거로 기본안 A를 만든다.
8. **충돌을 대조한다.** 공식 문서, 이전 P, 테스트 관찰, 새 답변이 다른 결과를 말하는지 확인한다.
9. **충돌·부분 답은 G로 재등록한다.** 어느 근거와 충돌하는지, 결과 차이, 후속 질문 초안을 적는다.
10. **영향을 연결한다.** 영향을 받는 R/C/T 후보, 예상 코드 위치는 “확인 필요”로 표시하되 코드를 수정하지 않는다.
11. **G 상태를 갱신한다.** 해결, 부분 해결, 신규, 충돌로 명확히 쓰고 근거 M#를 붙인다.
12. **후속 DM 필요성을 판정한다.** H 영향이 남고 문서로 해소되지 않을 때만 `→ 1.3 dm-questions ($sk-dm-questions)`을 제안한다.
13. **명세 반영을 인계한다.** P/A/G가 정리되면 `→ 2.1 spec ($sk-spec)`으로 연결한다.

### 답변 해석 규칙

| 답변 형태 | 기록 방법 | 예 |
| :--- | :--- | :--- |
| 선택지 확정 | 정확한 선택의 P | “1-A” → 조건과 A 동작 |
| 조건부 확정 | 조건을 나눠 P 또는 P+G | “음수만 오류, 빈 값은 제외” |
| 사례 답변 | 사례 범위 P, 일반화 G | “이 파일의 -2는 제외” |
| 위임 | 되돌릴 수 있는 A | “알아서 처리하세요” |
| 무응답·읽음 | G 유지, A 가능 | “답변 대기” |
| 문서와 충돌 | G 재등록, 확인 DM | 문서는 `[]`, 답변은 `null` |

### 정책 문장 품질

좋은 P는 “**조건** → **동작**”과 예시를 포함한다.

| 불충분한 기록 | 테스트 가능한 기록 |
| :--- | :--- |
| “음수는 처리하지 않음” | “`quantity < 0`인 레코드 → 요청을 400으로 종료하고 결과를 만들지 않음” |
| “동점은 ID 기준” | “점수가 같음 → `id` 오름차순으로 정렬” |
| “빈 결과 처리” | “유효 레코드가 0개 → 200과 빈 배열 `[]` 반환” |

출력 상태 코드·필드가 답변에 없으면 지어내지 않는다. 관련 G를 남긴다.

## 판단 기준·분기

- 담당자가 “A”라고 답했으면 M 질문의 A 문구 범위에서만 P를 만든다.
- 담당자가 선택지 밖 답을 했으면 선택지를 억지로 매핑하지 말고 답변 원문대로 P를 쓴다.
- 답변이 두 가지 조건을 한 문장에 포함하면 조건별 P로 분리하고 같은 M# 근거를 붙인다.
- 한 답이 H G를 해결하지만 출력 스키마를 비워 두면 `부분 해결`로 둔다.
- 공식 문서와 담당자 확정 답변이 충돌하면 우선순위 규칙을 적용해 조용히 선택하지 말고 G와 확인 DM을 만든다.
- 담당자의 “알아서”가 외부 API·데이터 손실에 영향을 주면 안전한 A만 두고 확인을 다시 요청한다.
- 시간이 부족하면 원문 보존 → H P/A → 영향 R/G만 우선 기록하고, P2 해석은 보류한다.

## 작업 노트 기록

`sk/work/DM_LOG.md`에서 기존 `## M<n> …` 블록에만 답변·해석을 추가하고, 아래 정확한 제목의 정책 목록을 유지한다.

### 메시지별 블록

```markdown
## M1 2026-..-.. 첫 질문 배치 — 답변 수신
- 관련 G: G1, G3
- 질문 매핑: M1-1 → G1, M1-2 → G3
- 답변 원문:
  > 사용자가 붙여넣은 텍스트를 원문 그대로 보존
- 해석:
  - M1-1: P1 후보 — `quantity < 0` → 레코드 제외
  - M1-2: 부분 해결 — 1차 정렬만 답변됨, 2차 키는 G4
- 영향: R2, C1, T 후보, 구현 위치는 명세화 후 확인
- 상태: 해석 완료 / 후속 확인 필요
```

### `## 정책 목록 P`

| ID | 규칙 “조건 → 동작” | 예시 | 근거 M#/문서 | 영향 R/C/T | 상태 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| P1 | `quantity < 0` → 해당 레코드 제외 | `-2`는 합계 미포함 | M1-1 | R2, T 후보 | 확정 |

- P ID는 기존 최대 번호 다음을 쓴다. 답변 원문을 P 표에 요약만으로 대체하지 않는다.
- “알아서” 답변은 P가 아니라 `DISCOVERY.md`의 해당 G 기본안과 이후 `SPEC.md`의 A 후보로 연결한다.
- 답변 수신만으로 SPEC을 임의로 새로 만들지 않는다. 2.1에서 정식 통합한다.

## 채팅 출력 형식

1. 원문이 연결된 M#과 질문별 해석
2. 새·갱신 P 표: 조건 → 동작, 예시, M# 근거
3. 범위가 불명확한 A 또는 열린·충돌 G
4. 영향을 받는 R/C/T 후보와 확인이 필요한 코드 위치
5. 후속 DM 필요 여부와 이유
6. 다음 행동: `→ 2.1 spec ($sk-spec)` 또는 `→ 1.3 dm-questions ($sk-dm-questions)`

## 완료 기준

- 사용자 제공 답변 원문이 M 블록에 보존돼 있다.
- 확정 답은 조건 → 동작·예시·M# 근거를 갖는 P로 변환됐다.
- 사례 답변의 일반화 범위가 제한됐고, 위임은 A로 분리됐다.
- 충돌·부분 답·신규 모호성이 G로 남아 있다.
- R/C/T 영향과 다음 단계가 명확하며 과제 파일을 수정하지 않았다.

## 금지

- 담당자 답변을 요약본만 남기고 원문을 삭제·왜곡하지 않는다.
- 한 사례나 “알아서”를 전체 정책 P로 일반화하지 않는다.
- 공식 문서와 P의 충돌을 숨기거나 임의로 우선순위를 정하지 않는다.
- 아직 실행하지 않은 테스트·코드 변경을 완료된 사실처럼 기록하지 않는다.
- DM 답변, 원본 데이터, 개인 정보 속 민감값을 불필요하게 노출하지 않는다.
