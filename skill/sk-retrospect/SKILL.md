# 한계·개선안 정리

## 목적
- 실제 코드 구조, 검증 범위, 제한 시간에 따른 선택에서 나온 한계와 실패 조건을 정리한다.
- 막연한 '추후 고도화' 대신 어느 파일·함수·계약을 어떻게 바꾸고 무엇으로 검증할지 우선순위화한다.
- Q6과 보고서 5절에서 정직하고 구체적으로 말할 수 있는 근거를 만든다.

## 언제 쓰나 / 쓰지 않나
- `9.1 understand ($sk-understand)`로 흐름과 테스트 범위를 정리한 뒤, 제출 전 AI 사용 허용 시간에 사용한다.
- 범위 축소·가정·미검증이 남았거나, Q6에서 현재 구현의 한계를 현실적으로 설명해야 할 때 사용한다.
- `8.1 report ($sk-report)` 전에 사용하면 보고서 5절의 근거를 정리하기 좋다.
- AI·복붙 금지 서술형 단계가 시작되면 즉시 사용을 중단한다.
- 버그를 찾아 수정하는 단계가 아니다. 현재 요구사항을 충족하지 못한 결함은 한계가 아니라 `6.1 debug ($sk-debug)` 또는 `7.2 compliance ($sk-compliance)`의 이슈로 처리한다.
- 정책을 새로 정하거나 업무 영향을 추정하는 스킬이 아니다. 정책 공백은 `1.3 dm-questions ($sk-dm-questions)`에 넘긴다.

## 입력과 사전 확인
- 다음을 읽고 근거마다 출처 ID를 확인한다.
  - `sk/work/UNDERSTANDING.md`의 테스트가 증명하지 못한 것, 엣지 케이스, 결정 요약
  - `sk/work/SPEC.md`의 A#, G#, 비목표, T#, 추적표 상태
  - `sk/work/PLAN.md`의 S#, 축소 결정, 시간 예산
  - `sk/work/DECISIONS.md`의 DD#와 포기한 대안
  - `sk/work/EVIDENCE.md`의 FAIL/미검증/STALE E#
  - `sk/work/REVIEW.md`의 미해결 F#과 준수 감사 상태
- 현재 코드에서 확장 시 병목·상태·입력 형식·외부 의존 경계를 읽기 전용으로 확인한다.
- 한계는 '현재 P0를 충족하나 조건이 바뀌면 실패할 수 있음'과 '현재도 미충족인 결함'을 구분한다.
- 외부 규모, 트래픽, SLA, 사용자 수는 공식 문서나 관찰 근거가 없으면 임의 숫자로 쓰지 않는다.

## 절차
1. AI 사용 허용 여부와 남은 시간을 확인한다. 금지 단계이면 즉시 멈춘다.
2. 현재 구현의 범위와 비목표를 한 줄로 적는다. 이 범위 안에서 PASS인 P0와 미검증 항목을 구분한다.
3. 실패 조건 후보를 코드·E#·F#·A#·S#에서 수집한다. 예: 전체 파일 메모리 적재, 순차 처리, 고정 열거값, 인증 부재, 단일 실패가 전체 요청을 중단하는 구조처럼 실제로 확인된 것만 쓴다.
4. 각 후보를 재현 조건, 사용자/결과 영향, 현재 방어 유무, 근거 ID로 분해한다.
5. 후보가 현재 R#/P# 위반이면 '수정 필요 결함'으로 분류해 디버그/리뷰에 넘긴다. 정상 범위를 벗어날 때만 한계로 유지한다.
6. 개선안을 현재 파일·함수·데이터 계약과 연결한다. 바꿀 위치, 변경 내용, 예상 트레이드오프, 새 T#/E# 검증을 한 항목씩 적는다.
7. 개선을 P0(제출 전 필수 결함), P1(다음 구현 우선), 보류(근거/시간 부족)로 분류한다. P0는 개선안이 아니라 즉시 복구할 이슈다.
8. 기존 인터페이스·P#·C#와 충돌하는 개선이면 먼저 가정/질문으로 표시한다. 마음대로 구조를 확장하지 않는다.
9. `UNDERSTANDING.md`의 `## 한계·실패 조건·개선안`만 갱신하고, QA 카드·보고서는 다음 스킬이 이 근거를 사용할 수 있게 남긴다.
10. 한계 2~4개와 가장 현실적인 P1 개선 1~2개를 골라 `9.2 qa-card ($sk-qa-card)` 및 `8.1 report ($sk-report)`로 넘긴다.

```text
근거 대조 예시
sed -n '1,260p' sk/work/UNDERSTANDING.md
sed -n '1,260p' sk/work/PLAN.md
sed -n '1,320p' sk/work/EVIDENCE.md
sed -n '1,260p' sk/work/REVIEW.md
git diff --stat
```

## 판단 기준·분기
- if 구현이 전체 입력을 메모리에 읽는 것이 코드로 확인되면 → 입력 규모가 커질 때 메모리 한계 가능성을 적고, 스트리밍/청크 처리의 위치와 검증을 제시한다.
- if 성능 시험 E#가 없으면 → '성능 미검증'으로 적고 느리다고 단정하거나 임의 임계치를 말하지 않는다.
- if 동시성·재시도·권한 경계가 과제 범위 밖이면 → 비목표/미검증으로 적되, 현재 오류라고 표현하지 않는다.
- if 고정 규칙이 P#로 확정돼 있으면 → 설정화는 개선 후보일 수 있으나 현재 규칙 위반으로 쓰지 않는다.
- if 검증되지 않은 데이터 형식이 있다면 → 지원하지 않는 형식, 실패 방식, 계약 확장 위치를 구체화한다.
- if 개선이 새 패키지·외부 서비스·배포를 요구하면 → 대회 규칙과 사용자 확인이 필요하다고 표시하며 실행하지 않는다.
- if 남은 시간이 5분 미만이면 → 실제 한계 두 개, 근거 ID, 다음 검증 한 개만 먼저 적고 Q6 카드로 넘긴다.

## 작업 노트 기록
- 파일은 `sk/work/UNDERSTANDING.md`이며 이 스킬은 `## 한계·실패 조건·개선안` 절만 갱신한다.
- 먼저 `### 현재 범위와 전제`에 P0 충족 범위·A#·비목표·미검증을 4줄 이내로 쓴다.
- 이어서 아래 표를 작성한다.

| 항목 | 분류 | 실패 조건 또는 제약 | 코드·노트 근거 | 현재 영향·방어 | 개선 위치·방법 | 검증 T#/E# 계획 | 우선순위 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |

- 항목은 시간순으로 구분하되 새 ID 체계를 만들지 않는다. R/P/T/E/DD 등의 기존 근거 ID는 해당 열에서만 인용한다.
- `분류`는 `구조 한계`, `미검증`, `가정 의존`, `범위 축소`, `수정 필요 결함` 중 하나로 쓴다.
- `코드·노트 근거`에는 파일:함수, A#/S#/DD#/E#/F# 중 적어도 하나를 적는다.
- `수정 필요 결함`은 표에 남기되 상태와 `6.1 debug ($sk-debug)` 또는 `7.1 review ($sk-review)`의 인수인계를 명시한다.
- 보고서용 요약은 한계마다 `현재 선택 → 실패 조건 → 구체 개선 → 검증` 순서의 두 문장 이내로 적는다.

## 채팅 출력 형식
1. **범위 판정**: 현재 P0 충족, 미검증, 가정, 범위 밖을 분리한다.
2. **한계 표**: `분류 | 실패 조건 | 근거 | 현재 영향 | 개선·검증 | 우선순위`로 낸다.
3. **즉시 수정 필요**: 한계가 아닌 결함만 별도 목록으로 내고 다음 스킬 ID를 붙인다.
4. **Q6 말하기 뼈대**: 현재 선택, 조건부 한계, 한 가지 현실적 개선, 검증 방법을 네 조각으로 제시한다.
5. **인수인계**: `9.2 qa-card ($sk-qa-card)`과 `8.1 report ($sk-report)`에 사용할 한계·개선안 항목 목록을 알린다.

## 완료 기준
- 각 한계가 실제 코드·노트·실행 증거 중 하나 이상의 근거와 연결된다.
- 현재 요구사항 결함과 조건부 한계/미검증이 구분된다.
- 개선안은 현재 구조의 특정 위치, 트레이드오프, 검증 방법을 포함한다.
- 우선순위 P0/P1/보류가 시간·위험·근거에 따라 배정된다.
- `UNDERSTANDING.md`의 지정 절만 갱신하고 다른 절 또는 과제 파일을 수정하지 않는다.
- Q6와 보고서 5절로 이어질 수 있는 짧은 사실 기반 요약이 있다.

## 금지
- AI·복붙 금지 서술형 단계에서 한계 분석·답안 생성·카드 보완을 하지 않는다.
- 현재 코드·노트에 근거 없는 대규모 트래픽, 보안 취약점, 비용, 사용자 영향 수치를 지어내지 않는다.
- 실제 요구사항 미충족 결함을 '향후 개선'으로 포장해 제출 전 수정을 피하지 않는다.
- 현재 과제와 무관한 캐싱, 큐, 머신러닝, 분산 시스템을 만능 개선안으로 나열하지 않는다.
- 코드·테스트·설정·외부 서비스·제출물을 변경·배포·업로드하지 않는다.
- 민감한 입력값·비밀값·개인정보를 실패 사례나 증거로 기록하지 않는다.
