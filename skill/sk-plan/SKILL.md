# 슬라이스·시간 예산 계획

## 목적

확정된 명세를 작은 수직 슬라이스 S#로 나누고, 남은 시간 안에 P0와 검증·제출 준비를 지키는 실행 순서를 만든다.

이 스킬은 구현 계획만 기록한다. 과제 코드, 기존 테스트, 원본 데이터, 설정은 수정하지 않는다.

## 언제 쓰나 / 쓰지 않나

- `2.4 spec-gate`가 READY 또는 READY-WITH-ASSUMPTIONS로 판정된 직후 사용한다.
- 남은 시간이 변했거나 새 G#/P#가 계획 순서를 바꾸면 30분 체크포인트에서 다시 사용한다.
- 첫 구현 전, 구현이 막혔을 때, 6.5 범위 축소 전에 사용한다.
- 요구사항·입출력 계약이 아직 없으면 계획을 추측하지 말고 → `2.1 spec ($sk-spec)` 또는 `2.2 io-contract ($sk-data-contract)`로 돌아간다.
- H 영향 G#가 가역적 A#로도 처리 불가하면 → `1.3 dm-questions ($sk-dm-questions)`을 먼저 제안한다.
- 코드를 작성·수정해야 하는 요청은 이 스킬의 범위가 아니다. → `4.1 test-first ($sk-test-first)` 또는 `4.2 implement ($sk-implement)`로 넘긴다.

## 입력과 사전 확인

1. `sk/work/SPEC.md`의 0절 상태, 한 장 요약, Top 5, R/C/P/A/G, 11절 T, 14절 게이트 결과를 읽는다.
2. `sk/work/BRIEF.md`에서 실행·테스트 기준선과 과제 유형을 확인한다.
3. `sk/work/DM_LOG.md`의 최근 P#와 미확정 질문을 확인한다.
4. 남은 실제 시간(분), 마감 전 제출 버퍼, 이미 실행한 기준선의 E# 여부를 확인한다.
5. 읽기 전용으로 현재 변경 범위만 확인해야 하면 다음을 사용한다.

```bash
git status --short
git diff --stat
```

6. `sk/`은 도구 폴더이므로 과제 분석·테스트·변경 대상에서 제외한다.
7. 시간이 없거나 입력이 비면 임의의 마감·채점·정책을 만들지 말고, 확인할 사실을 첫 S# 또는 G#로 명시한다.

## 절차

1. 먼저 보호 시간을 고정한다.
   - 전체 남은 시간의 검증은 최소 15%로 잡는다.
   - 보고서와 6문항 카드 준비는 합산 최소 15%로 잡는다.
   - 최종 제출 전 버퍼는 최소 10분으로 잡고, 공식 안내가 더 크면 그 값을 우선한다.
2. 남은 시간을 조사·위험 실험·P0 구현·검증·문서/QA·버퍼로 합계가 맞게 배분한다.
3. SPEC 3절의 P0 R#마다 입력부터 출력까지 관찰 가능한 한 흐름으로 쪼갠다.
4. 한 S#에는 대상 R#/AC/P#/T#, 건드릴 후보 파일, 선행조건, 완료 증거를 모두 연결한다.
5. "모델 추가", "리팩터링"처럼 결과가 보이지 않는 작업은 S#가 아니다. 동작과 증거가 보이는 단위로 다시 나눈다.
6. 영향이 크고 불확실하며 되돌리기 어려운 항목을 위험 후보로 모은다.
7. 각 위험에는 전체 구현보다 작은 판별 실험 1개, 시간 상한, 통과·실패 뒤 행동을 둔다.
8. 가장 큰 위험 실험을 첫 S#보다 먼저 두되, P0 경로와 무관한 탐색은 하지 않는다.
9. 순서는 "위험 확인 → S# 하나 → 해당 T# 실행 → 증거 기록"의 반복으로 만든다.
10. 의존성 때문에 막힌 S#에는 기다리는 대신 할 수 있는 독립 S# 또는 A# 기반 가역 경로를 적는다.
11. P2 전체, P1 일부, 품질 개선 순으로 명시적인 축소 후보를 둔다.
12. 30분마다 실제 경과·완료 S#·실패 E#·남은 시간을 비교하는 재계획 시점을 표시한다.
13. 첫 착수는 → `3.2 design ($sk-design)`에서 첫 S#의 최소 구조를 정하도록 인계한다. 설계가 끝나면 슬라이스마다 → `4.0 build-loop ($sk-build-loop)`로 한 바퀴씩 진행한다.

### 최소 경로 — 시간이 없을 때

1. P0 R#를 최대 3개 S#로 묶고 각 S#에 T# 하나 이상을 연결한다.
2. 결과를 뒤집을 위험 1개만 골라 10분 이내 실험으로 둔다.
3. 검증 15%, 문서·QA 15%, 제출 버퍼 10분을 먼저 빼고 나머지만 구현에 배정한다.
4. P2와 비필수 다듬기를 `보류`로 기록한 뒤 → `3.2 design ($sk-design)`으로 간다.

## 판단 기준·분기

- **if** SPEC 0절이 BLOCKED **then** 구현 S#를 만들지 말고, BLOCKED 원인 G#와 → `1.3 dm-questions ($sk-dm-questions)`을 최우선 행동으로 둔다.
- **if** READY-WITH-ASSUMPTIONS이고 A#가 H 영향 **then** 가정을 되돌릴 파일·함수 경계와 확인 시점을 위험 실험에 적고 → `1.5 dm-confirm ($sk-dm-confirm)`을 권장한다.
- **if** P0 R#에 AC 또는 T#가 없다 **then** 해당 S#은 시작 금지로 표시하고 → `2.3 acceptance ($sk-acceptance)`로 넘긴다.
- **if** 위험 실험이 시간 상한을 넘긴다 **then** 더 큰 탐색을 하지 말고 A# 기반 가역안, 질문, 또는 축소 중 하나를 고른다.
- **if** 예상보다 남은 시간이 줄었다 **then** 새 P1 시작을 멈추고 → `6.5 timebox ($sk-timebox)`에 축소 근거를 넘긴다.
- **if** 기존 테스트 기준선이 이미 실패한다 **then** 새 실패와 구분할 수 있도록 첫 S#에 최소 재현·E# 기록을 넣고 → `6.1 debug ($sk-debug)`을 제안한다.
- **if** 공식 안내·P#·관찰 동작이 충돌한다 **then** 임의 우선순위를 정하지 말고 G#와 DM 초안을 만든다.

## 작업 노트 기록

`sk/work/PLAN.md`가 없으면 만들되, 다른 스킬의 섹션은 덮어쓰지 않는다.

### `## 시간 예산`

| 구간 | 시작 조건 | 시간(분) | 종료 조건 | 보호 여부 |
| :--- | :--- | ---: | :--- | :--- |
| 위험 실험 | 가장 큰 불확실성 | 10 | 판별 E# 또는 시간 상한 | 아니오 |
| P0 슬라이스 | S#별 | 0 | 관련 T# 실행 | 아니오 |
| 검증 | P0 종료 뒤 | 0 | 5.1 근거 확보 | 예 |
| 보고서·QA | 검증 뒤 | 0 | 8.1·9.2 준비 | 예 |
| 제출 버퍼 | 마지막 | 10 이상 | 최종 점검 | 예 |

실제 숫자로 바꾸고 합계가 남은 시간과 일치하는지 적는다.

### `## 슬라이스 S`

| ID | 목표·대상 R/AC/P | 선행조건 | 최소 변경 경계 | 검증 T | 완료 증거 | 상태 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| S1 | R1 / AC-R1-1 / P1 | SPEC READY | 파일·함수 후보 | T1 | E# 또는 미검증 | 대기 |

상태는 `대기`, `진행`, `완료`, `막힘`, `보류`, `축소` 중 하나만 사용한다. 이 표의 열은 구현·루프·축소 스킬이 모두 그대로 쓰는 공통 형식이다. 다른 스킬은 열을 바꾸지 않고 `완료 증거`와 `상태` 칸만 갱신한다.

### `## 위험 실험`

| 위험 | 관련 G/A/R | 영향 | 가장 작은 실험 | 상한(분) | 통과 시 | 실패·시간초과 시 |
| :--- | :--- | :--- | :--- | ---: | :--- | :--- |

실험 결과가 나오면 E#를 연결하고, 실행 전에는 통과라고 쓰지 않는다.

### `## 축소 결정`

| 시각 | 트리거 | 제외·축소할 범위 | 지킬 P0/제출물 | 영향·한계 | 다음 행동 |
| :--- | :--- | :--- | :--- | :--- | :--- |

## 채팅 출력 형식

다음 순서로만 간결히 보고한다.

1. 현재 판정: SPEC 상태, 남은 시간, 구현 시작 가능 여부.
2. 시간 예산 표: 합계와 보호 시간을 포함한다.
3. S# 실행 순서: 대상 R#/T#, 완료 증거, 선행조건을 포함한다.
4. 위험 실험: 가장 먼저 할 판별과 실패 시 행동을 포함한다.
5. 축소·중단 규칙: P2 → P1 일부 → 품질 개선 순서를 명시한다.
6. 다음 행동: `3.2 design ($sk-design)` 또는 막힌 정확한 프롬프트 ID를 1개 제시한다.

## 완료 기준

- 모든 P0 R#가 적어도 한 S#와 T#에 연결된다.
- S#마다 관찰 가능한 완료 증거와 상태가 있다.
- 가장 큰 불확실성에 시간 상한이 있는 작은 위험 실험이 있다.
- 시간 예산 합계가 맞고 검증 15%, 문서·QA 15%, 버퍼 10분 이상이 보호된다.
- 축소 순서와 30분 재계획 조건이 `PLAN.md`에 기록된다.
- 과제 코드는 수정하지 않았고 미실행 결과를 성공으로 쓰지 않았다.

## 금지

- 계획 단계에서 과제 코드·테스트·원본 데이터·설정을 수정하지 않는다.
- 공식 안내에 없는 마감, 채점 방식, 성능 수치, 정책을 사실처럼 채우지 않는다.
- P0 수용 기준이나 검증 시간을 편의상 삭제하지 않는다.
- 가정 A#를 P#처럼 확정해 기록하지 않는다.
- 외부 제출, 배포, push, 업로드, 자격증명 전송을 실행하지 않는다.
- `git reset --hard`, `git clean`, `git stash`, 강제 체크아웃을 제안하거나 실행하지 않는다.
- 비밀값·개인정보·민감 원본값을 채팅이나 작업 노트에 적지 않는다.
