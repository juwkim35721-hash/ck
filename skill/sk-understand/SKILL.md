# 내 구현 이해 지도

## 목적
- 내가 작성하거나 승인한 구현을 남에게 가르치듯 설명할 수 있는 근거 지도를 만든다.
- 코드의 실제 흐름, 정책, 결정, 테스트 증거를 하나의 `sk/work/UNDERSTANDING.md`에 연결한다.
- Q1~Q6 카드의 원천 사실을 만들되, 대신 답안을 암기시키거나 추측을 사실로 만들지 않는다.

## 언제 쓰나 / 쓰지 않나
- 제출 직전, 구현·검증·리뷰가 어느 정도 끝난 뒤 AI 사용이 허용된 시간에 사용한다.
- 코드 위치를 잊었거나 Q1 Why와 Q2 How를 연결해 말하기 어려울 때 사용한다.
- `8.1 report ($sk-report)` 전에 사용하면 보고서 3절과 5절의 근거를 정리하기 좋다.
- AI·복붙 금지인 후속 서술형 단계가 시작되면 즉시 사용을 중단한다.
- 요구사항이 아직 불명확하면 이 스킬로 해석을 발명하지 말고 `1.2 ambiguity ($sk-ambiguity)` 또는 `2.1 spec ($sk-spec)`으로 돌아간다.
- 구현을 고치거나 새 테스트를 추가하는 스킬이 아니다. 발견한 결함은 `6.1 debug ($sk-debug)` 또는 승인된 `7.1 review ($sk-review)`에 넘긴다.

## 입력과 사전 확인
- 과제 루트에서 실행 중이며 `sk/`는 분석·테스트 대상이 아닌 도구 폴더임을 확인한다.
- 다음 자료의 존재와 최신성을 읽기 전용으로 확인한다.
  - `sk/work/SPEC.md`의 한 장 요약, Top 5, 5. 확정 정책 P, 11. 수용 테스트 표 T, 12. 추적표
  - `sk/work/PLAN.md`의 완료 슬라이스 S와 축소 결정
  - `sk/work/DECISIONS.md`의 DD# 및 AI 교정 기록 AI#
  - `sk/work/EVIDENCE.md`의 최신 PASS/FAIL/미검증 E#
  - `sk/work/REVIEW.md`의 미해결 F#와 준수 감사
  - `sk/work/DM_LOG.md`의 P# 근거가 되는 M# 답변
- 현재 변경 범위를 읽기 전용으로 확인한다. 예: `git status --short`, `git diff --stat`.
- 실제 코드와 테스트 파일을 읽고, 노트의 파일명·함수명·테스트 수를 코드/실행 근거와 대조한다.
- 비밀값, 원본 민감 데이터, 담당자 답변을 넘어선 추정은 노트에 적지 않는다.

## 절차
1. AI 사용 가능 여부와 남은 시간을 먼저 확인한다. 금지 단계라면 노트를 만들거나 읽는 작업을 즉시 멈춘다.
2. `SPEC.md`에서 목표, P0 요구사항 R#, 확정 정책 P#, 가정 A#, 수용 테스트 T#를 목록으로 뽑는다.
3. 최신 `EVIDENCE.md`를 읽어 실제로 실행된 검증과 미검증 항목을 분리한다. 오래된 증거는 현재 코드 증거처럼 쓰지 않는다.
4. 현재 diff와 진입점에서 시작해 입력 → 검증 Guard → 핵심 규칙 → 출력/오류의 호출 경로를 실제 파일·함수명으로 추적한다.
5. 대표 사례 하나를 고른다. 공개 가능한 작은 입력만 사용해 값이 각 함수에서 어떻게 바뀌는지, 어떤 P#가 적용되는지 순서대로 적는다.
6. null·빈 값·경계·잘못된 타입·중복·빈 결과 중 실제 구현과 관련된 항목만 골라 Guard 위치와 결과를 코드 근거로 기록한다.
7. 각 DD#에 대해 당시 문제, 대안, 선택, 포기한 대안, 영향 파일을 1~2줄로 압축한다. 근거 없는 '더 좋다'는 표현은 삭제한다.
8. 테스트가 증명한 입력·기대결과와, 표본·성능·동시성·미실행 경로처럼 증명하지 못한 범위를 분리한다.
9. `UNDERSTANDING.md`에서 이 스킬 담당 절만 만들거나 갱신한다. 다른 스킬의 절을 덮어쓰지 않는다.
10. 코드와 노트가 어긋나면 어느 쪽이 최신인지 확인하고, 해석으로 덮지 않는다. 정책 누락은 G 후보와 근거를 적어 `1.4 dm-answers ($sk-dm-log)` 또는 `2.1 spec ($sk-spec)`으로 넘긴다.

```text
읽기 전용 확인 예시
sed -n '1,240p' sk/work/SPEC.md
sed -n '1,240p' sk/work/DECISIONS.md
sed -n '1,260p' sk/work/EVIDENCE.md
git status --short
git diff --stat
```

## 판단 기준·분기
- if 최신 E#가 현재 코드 변경 전이면 → 해당 증거를 STALE 또는 미검증으로 취급하고 `5.1 verify ($sk-verify)`에서 재실행을 요청한다.
- if 함수 이름은 노트에 있으나 코드에 없으면 → 삭제/이동 여부를 확인하고 현재 경로로 고친다. 추정하지 않는다.
- if P#가 구현 분기에 보이지 않으면 → 정책 미반영 가능성으로 표시하고 `7.2 compliance ($sk-compliance)`에 감사 근거를 넘긴다.
- if 엣지 케이스의 동작이 A#에만 의존하면 → 확정 정책처럼 말하지 말고 '가정'과 되돌릴 지점을 함께 적는다.
- if 대표 사례가 민감한 실제 값을 요구하면 → 익명화한 최소 예시를 쓰고, 값 대신 흐름만 기록한다.
- if 남은 시간이 10분 이하면 → 한 문단 요약, 전체 흐름, 핵심 사실 10개만 먼저 완성하고 카드 작성 `9.2 qa-card ($sk-qa-card)`으로 넘긴다.
- if 결함을 발견하면 → 이 스킬에서 수정하지 말고 재현·위치·관련 R/P/T만 적어 `6.1 debug ($sk-debug)`으로 넘긴다.

## 작업 노트 기록
- 파일은 `sk/work/UNDERSTANDING.md`이며, 없으면 아래 정확한 제목으로 만든다.
- `## 한 문단 요약`: 목표·입력·핵심 규칙·출력을 5~7문장 이내로 쓴다.
- `## 전체 흐름`: `입력 → 함수/Guard → 규칙(P#) → 출력/오류` ASCII 흐름도와 진입점을 쓴다.
- `## 파일·함수 지도`: `파일 | 함수·컴포넌트 | 역할 | 입력 → 출력 | 근거 R/P/DD` 표를 쓴다.
- `## 예시 1건 추적`: `단계 | 파일·함수 | 예시 값/상태 | 적용 규칙 | 다음 값/결과` 표로 한 건만 추적한다.
- `## 정책이 강제되는 위치`: `P# 또는 A# | 코드 위치 | 조건 → 동작 | 관련 T#/E# | 확정/가정` 표를 쓴다.
- `## 엣지 케이스와 방어 위치`: `사례 | Guard 위치 | 실제 동작 | 정책 근거 | 검증 T#/E# | 미검증 위험` 표를 쓴다.
- `## 핵심 결정 요약`: `DD# | 문제 | 선택·대안 | 선택 근거 | 트레이드오프` 표를 쓴다.
- `## 테스트가 증명하는 것과 못하는 것`: `T#/E# | 증명한 범위 | 증명하지 못한 범위 | 다음 검증` 표를 쓴다.
- `## 핵심 사실 10개`: 번호 목록으로 파일명·함수명·정책·수치·제약을 사실 단위로 적는다.
- `## 한계·실패 조건·개선안`: 실제 관찰 또는 코드 구조 근거만 요약하고, 자세한 우선순위는 `9.4 retrospect ($sk-retrospect)`로 넘긴다.

## 채팅 출력 형식
1. **상태**: AI 사용 가능 여부, 읽은 노트, 코드 기준 시점.
2. **한 문단 이해**: 목표·입력·출력·핵심 규칙을 7문장 이내로 쓴다.
3. **흐름과 지도**: 진입점, 핵심 함수 3~6개, 대표 사례의 경로를 표로 낸다.
4. **말할 근거**: Q1~Q6에 재사용할 DD#/P#/T#/E#/AI#를 축별로 나열한다.
5. **불확실성**: 미검증, 가정 A#, 미해결 F#/G#만 별도 표기한다.
6. **다음 단계**: `9.2 qa-card ($sk-qa-card)` 또는 필요한 복구 스킬 ID를 한 개 제안한다.

## 완료 기준
- 목표부터 출력까지 실제 코드 경로가 파일·함수명으로 이어진다.
- 대표 사례 1건이 입력값, 적용 P#/A#, 중간 상태, 결과까지 추적된다.
- 실제 관련 엣지 케이스의 Guard 위치와 정책 근거가 연결된다.
- DD#, T#, E#, AI#가 있는 경우 각각 사실에 맞게 연결되며 없는 번호를 만들지 않는다.
- 테스트가 증명한 것과 못한 것이 분리되고 미검증을 통과처럼 쓰지 않는다.
- `sk/work/UNDERSTANDING.md`의 정확한 열 개 절이 다른 노트를 훼손하지 않고 갱신된다.

## 금지
- AI·복붙 금지인 후속 서술형 단계에서 이 스킬을 사용하거나 답안을 생성하지 않는다.
- 과제 코드, 테스트, 설정, 제출물을 수정하지 않는다.
- 공식 문서·P#·관찰된 코드·E#보다 약한 추측을 사실 또는 정책으로 선언하지 않는다.
- 담당자 답변, 테스트 결과, DD#, AI#를 지어내거나 실행하지 않은 검증을 PASS로 적지 않는다.
- 민감한 원본 데이터 값·토큰·개인정보를 노트나 채팅에 복사하지 않는다.
- `sk/` 도구 폴더를 과제 코드로 분석하거나 변경 대상으로 포함하지 않는다.
