# UI 핵심 흐름·접근성 점검

## 역할

실제 관찰 가능한 UI만 근거로 핵심 사용자 흐름과 기본 접근성을 점검하라.
디자인 전면 변경, 새 기능 제안, 코드 수정은 이 스킬의 범위에서 수행하지 마라.
공식 안내와 허용된 AI 사용 단계가 있으면 우선 따르고, AI 금지 서술형이 시작되면 즉시 중단하라.

## 입력

다음 정보를 확인하라.

- 실제 과제 루트와 앱 실행 명령 또는 대상 URL
- 남은 시간, 변경 허용 범위, 핵심 요구사항 또는 P0 사용자 흐름
- 테스트 계정·데모 데이터·알려진 장애와 공식 사용 제약

입력이 없으면 과제 루트와 실행 방법을 먼저 질문하거나 읽기 전용으로 확인하라.
준비 도구 저장소를 실제 과제로 간주하지 마라.

## 절차

1. Browser 도구의 가용성, 앱 기동 성공 여부, 접속 URL을 먼저 확인하라.
2. 브라우저 또는 앱에 접근하지 못하면 원인, 시도한 명령/URL, 미검증 범위를 기록하고 통과 판정을 중단하라.
3. 요구사항에서 사용자 가치가 큰 흐름을 최대 세 개 선정하라. 각 흐름을 진입→핵심 조작→결과 확인으로 작게 정의하라.
4. 흐름별로 시작 상태, 행동, 기대 결과, 실제 관찰, 증거를 분리해 기록하라.
5. 화면과 API 또는 저장 데이터가 연결되는 흐름은 화면 변화와 재조회·네트워크 등 연동 증거를 구분해 확인하라.
6. 적용 가능한 로딩, 빈 데이터, 오류, 긴 값 또는 중복 클릭 상태를 흐름마다 최소 하나 확인하라.
7. Tab, Shift+Tab, Enter, Space, Escape로 핵심 버튼·링크·입력·모달의 포커스 표시, 순서, 실행, 닫기를 점검하라.
8. 반응이 없거나 포커스가 보이지 않거나 오류 뒤 복구할 수 없으면 재현 단계를 보존하고 사용자 영향을 평가하라.
9. 테스트 데이터·원본 데이터·코드·기존 테스트를 수정하거나 삭제하지 마라.
10. 남은 시간이 부족하면 P0 정상 흐름과 키보드 진입/실행/결과 확인을 우선하고 나머지는 미검증으로 남겨라.

## 분기와 중단

UI가 없거나 대상이 API/CLI뿐이면 UI 해당 없음과 근거를 보고하고 점검을 종료하라.
로그인, 권한, 네트워크, 브라우저 부재로 막히면 우회 계정 생성·민감정보 요청·환경 변경을 하지 마라.
P0 흐름이 차단되면 추가 화면 탐색을 줄이고 재현 정보와 P0 판정을 보고한 뒤 90-debug 또는 승인된 구현 단계로 넘겨라.
P0가 통과하더라도 확인하지 못한 브라우저, 화면 크기, 보조기기, 실패 상태는 통과로 일반화하지 마라.

## 출력 형식

다음 순서로 간결하게 출력하라.

1. 점검 환경: Browser 가용성, URL, 실행/접속 결과, 제한
2. 흐름 표: 흐름 | 기대 | 실제 | 판정 | 화면·연동 증거
3. 상태·접근성: 로딩/빈/오류/긴 값과 키보드 점검 결과
4. 발견 사항: P0/P1/P2 | 위치 | 재현 | 사용자 영향 | 근거
5. 미검증 목록과 다음 한 작업

관찰하지 않은 결과, API 응답, 접근성 준수 여부를 만들어 내지 마라.
발견이 없으면 점검한 범위와 한계를 함께 명시하라.

## 완료 기준

Browser 및 앱 접근 가능 여부가 기록되어 있어야 한다.
P0 흐름별 기대와 실제 관찰, 적용 가능한 실패 상태, 키보드 결과가 구분되어 있어야 한다.
수정 없이도 재현 가능한 발견 사항 또는 명시적인 미검증 목록이 있어야 한다.
외부 제출·배포·계정 조작은 별도 구체적 승인 없이는 수행하지 마라.
