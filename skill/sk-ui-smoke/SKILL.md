# UI 핵심 흐름 확인

## 목적

제한된 시간에 사용자 관점의 핵심 흐름 세 개 이내를 실제로 확인한다.
먼저 HTTP 도달성을 확인하고, 가능하면 브라우저로 입력·결과·오류·로딩·빈 상태와 콘솔 오류를 대조한다.
브라우저가 없으면 검증 범위를 정직하게 HTTP 수준과 사용자의 수동 체크리스트로 낮춘다.

## 언제 쓰나 / 쓰지 않나

- 웹·풀스택·데스크톱 UI가 있고 화면 요구사항 또는 사용자 흐름 T#가 있을 때 쓴다.
- 4.2 구현 후, 화면 변경이 포함된 P0 슬라이스마다, 제출 직전 쓴다.
- API의 메서드·응답 계약 자체는 → 5.4 api-contract ($sk-api-contract)에서 검증한다.
- 시각 디자인 전면 개편, 스냅샷 이미지 비교, 접근성 감사 전체는 이 시간 제한 스모크의 범위가 아니다.
- 이 스킬은 화면 문구·스타일·코드·테스트를 수정하지 않는다.

## 입력과 사전 확인

1. `sk/work/SPEC.md`의 1절 목표, 5절 P, 10절 UI·API 계약, 11절 T를 읽는다.
2. `sk/work/BRIEF.md`의 `## 환경`에서 공식 UI 시작 명령, 포트·호스트, 브라우저 접근 방법을 확인한다.
3. `sk/work/PLAN.md`에서 P0 사용자 흐름과 현재 S#를 확인한다.
4. 실제 계정·민감 데이터·유료 동작이 필요한지 확인하고 안전한 테스트 입력만 준비한다.
5. 브라우저 도구의 사용 가능 여부를 확인한다. 없으면 처음부터 수동 체크리스트 모드임을 선언한다.

## 절차

1. 핵심 흐름을 최대 세 개로 고른다.
   우선순위는 `정상 입력 → 기대 결과`, `빈 값 또는 잘못된 입력 → 검증 메시지`, `서버 오류 또는 빈 결과 → 안내·복구`다.
   각 흐름에 T#, R#, P#, 시작 화면, 입력, 기대 화면 상태를 적는다.
2. 공식 명령으로 앱을 시작하거나 이미 실행된 앱의 URL을 확인한다.
   웹 UI는 내장 Browser 미리보기를 위해 지정 포트로 `0.0.0.0`에 바인딩되어야 한다(과제 문서가 다르게 정하면 그 요구를 따른다). 포트는 바꾸지 않는다.
   Browser 미리보기가 연결되지 않으면 ① 서버 프로세스가 살아 있는지 ② `0.0.0.0` 바인딩인지 ③ Browser의 PORT가 실제 포트와 같은지 순서로 확인한다.
3. HTTP 도달성을 먼저 확인한다.
```bash
python3 sk/snippets/smoke_test.py http://127.0.0.1:<포트>/<페이지_또는_건강경로>
```
   이 스니펫은 GET 1건에서 2xx인지 보는 1차 확인이며, 5초 제한·본문 120자 출력·실패 시 종료 코드 1이라는 한계를 기록한다.
4. 브라우저가 있으면 정상 흐름을 수행한다.
   시작 URL, 클릭·입력 순서, 제출 동작, 결과 값·문구·목록·화면 전환을 T# 기대와 대조한다.
   스크린샷은 필요할 때만 최소 1장 저장하고 민감 값이 보이면 저장하지 않는다.
5. 빈 값 또는 잘못된 입력 흐름을 수행한다.
   필수값 비움, 형식 오류, 범위 밖 값 중 SPEC·T#가 정의한 한 가지를 입력한다.
   폼이 무반응인지, 명확한 검증 메시지가 있는지, 잘못된 API 호출을 막는지 확인한다.
6. 오류 또는 빈 상태 흐름을 수행한다.
   안전하게 재현 가능한 빈 검색 결과·빈 목록·공식 오류 테스트 경로를 쓴다.
   로딩 표시, 빈 상태 안내, API 오류 표시, 재시도·복귀 가능성을 실제 화면에서 확인한다.
7. 콘솔·네트워크 신호를 확인한다.
   브라우저 도구가 가능하면 현재 흐름 중 콘솔 오류와 실패 요청을 보되, 무관한 기존 경고와 새 오류를 분리한다.
   브라우저가 없으면 API 응답 수준 확인으로 제한하고 콘솔은 미검증으로 기록한다.
8. 화면 계약을 대조한다.
   문구의 정확한 어조가 아니라 요구된 필드·오류·빈 상태·로딩·정렬·결정적 결과가 보이는지 P#/T# 근거로 판단한다.
9. 각 흐름의 실제 결과를 E#로 남긴다.
   URL, 안전한 입력 유형, 관찰한 결과·콘솔 요약, 종료 코드, 코드 상태를 → 5.2 evidence ($sk-evidence) 형식에 쓴다.
10. 차이를 분류한다.
    기능 실패, API 실패, 검증 메시지 누락, 빈 상태 누락, 시각적 사소한 차이, 브라우저 부재로 분류한다.
11. 다음 행동을 고른다.
    재현 가능한 기능 실패는 → 6.1 debug ($sk-debug), API 응답 차이는 → 5.4 api-contract ($sk-api-contract), 요구가 불명확한 문구·상태는 → 1.3 dm-questions ($sk-dm-questions)로 넘긴다.
12. 이 세션에서 시작한 앱의 종료 책임을 확인한다.
    더 이상 필요 없으면 공식 방법으로만 종료하고, 기존 프로세스는 종료하지 않는다.

## 판단 기준·분기

- if 스모크 GET이 2xx다 → 페이지·건강 경로 도달성 PASS일 뿐 UI 흐름 PASS는 아니다.
- if 브라우저 도구가 있다 → HTTP만으로 화면 검증을 끝내지 말고 적어도 정상 흐름 하나는 직접 수행한다.
- if 브라우저 도구가 없다 → `UI PASS`로 쓰지 말고 `HTTP 확인 PASS / 화면 수동 확인 필요`로 분리한다.
- if 서버 오류를 안전하게 재현할 수 없다 → 고의로 서버를 망가뜨리지 말고 오류 표시는 미검증과 수동 체크로 둔다.
- if 콘솔에 오류가 있다 → 현재 흐름의 새 오류인지 기준선·무관한 경고인지 E# 근거로 분류한다.
- if 화면은 보이나 P#가 정한 필수 문구·결과·빈 상태가 없다 → FAIL이다.
- if 시간이 부족하다 → 정상 1개, 잘못된 입력 1개, 빈 상태 1개만 확인하고 나머지는 미검증으로 둔다.

## 작업 노트 기록

`sk/work/EVIDENCE.md`의 `## 실행 기록`에 서버 도달성 및 각 UI 흐름의 실제 실행을 E#로 추가한다.
표 열은 `E# | 시각 | 명령·작업 디렉터리 | 대상 R/T | 기대 | 실제 결과 요약 | 판정 | 코드 상태`다.

실제 결과 요약 예시는 `빈 검색어 제출 → 인라인 필수 메시지, 요청 없음` 또는
`결과 0건 → 빈 상태 안내 표시, 콘솔 새 오류 없음`처럼 입력 유형·관찰·콘솔 여부만 적는다.
실제 계정명, 고객 데이터, 비밀 URL 파라미터, 개인 정보가 보이는 스크린샷·출력은 기록하지 않는다.

수용 테스트가 확인되면 `sk/work/SPEC.md`의 `## 12. 추적표`에서
`R | AC | T | 구현 위치 | 증거 E | 상태` 행의 증거 E와 상태를 실제 E#로 갱신한다.

## 채팅 출력 형식

1. `환경·범위`: URL, 서버 상태, 브라우저 가능 여부, 선택한 최대 3개 흐름.
2. `도달성`: 스모크 명령·종료 코드·HTTP 상태와 한계.
3. `흐름별 결과`: T#, 입력 유형, 기대 화면, 실제 화면, 콘솔·API 관찰, 판정 표.
4. `미검증`: 브라우저 부재·안전상 미재현 등 구체 사유.
5. `증거·종료`: E#, 코드 상태, 이 세션이 시작한 프로세스의 종료 상태.
6. `다음 행동`: 디버그·API·DM 중 하나의 ID와 스킬.

## 완료 기준

- 공식 URL에서 실제 도달성 결과가 있으며 스니펫의 한계를 구분했다.
- 최대 세 개의 P0 핵심 흐름이 R/T/P 기반으로 선택됐다.
- 가능하면 정상·잘못된 입력·오류/빈 상태를 실제 UI에서 각각 확인했다.
- 브라우저가 없으면 HTTP 결과와 수동 체크가 명확히 분리돼 있다.
- 콘솔·실패 요청은 실제 관찰 여부와 함께 기록됐다.
- 모든 판정이 E#와 현재 코드 상태에 연결된다.

## 금지

- 도달성 2xx만으로 UI의 입력·결과·오류 처리가 통과했다고 주장하지 않는다.
- 대규모 문구·스타일·레이아웃 변경이나 과제 코드 수정으로 발견을 해결하지 않는다.
- 실제 사용자 계정, 개인정보, 결제·외부 시스템 동작을 허가 없이 시험하지 않는다.
- 오류 상태를 보기 위해 서버를 강제 종료·변조하거나 포트·호스트를 임의 변경하지 않는다.
- 브라우저가 없을 때 직접 본 것처럼 화면·콘솔 결과를 기록하지 않는다.
- 실패·미검증을 PASS로 바꾸거나 스크린샷에 민감 정보를 남기지 않는다.
