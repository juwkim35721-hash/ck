# 기존 코드 지도 작성

## 목적
기존 코드의 진입점, 모듈 역할, 데이터 흐름, 설정, 테스트 위치를 짧고 검증 가능한 지도로 만든다.
구현 전에 변경 예상 지점과 손대면 위험한 공개 인터페이스·공용 유틸을 드러낸다.
과제 파일을 읽기만 하고 `sk/work/BRIEF.md`의 `## 코드 지도`만 갱신한다.

## 언제 쓰나 / 쓰지 않나
- 기존 소스가 있고 → 0.1 context (`$sk-context`)에서 과제 루트가 확인된 뒤 사용한다.
- B·C·D 유형이거나, A·E라도 제공 코드·테스트를 보존해야 할 때 사용한다.
- 새 과제를 빈 프로젝트로 시작하고 기존 코드가 전혀 없으면 최소 지도만 남기고 → 1.1 requirements (`$sk-requirements`)로 간다.
- 요구사항을 R/C로 확정하는 일은 → 1.1 requirements (`$sk-requirements`)에 맡긴다.
- 실제 수정 후보의 설계 비교는 → 3.2 design (`$sk-design`)에 맡기며 이 단계에서 변경하지 않는다.

## 입력과 사전 확인
- `sk/work/BRIEF.md#환경`에서 루트, 언어·런타임, 명령 후보, 보호 파일을 읽는다.
- `sk/work/BRIEF.md#과제 유형·전략`이 있으면 주 유형과 위험을 읽고 탐색 우선순위를 맞춘다.
- README의 실행 명령, 라우팅·엔트리 설정, 테스트 설정을 읽기 전용 단서로 쓴다.
- `sk/`는 도구이므로 탐색·린트·테스트 대상에서 반드시 제외한다.
- 대용량 의존성 폴더와 생성물은 먼저 제외하고, 필요할 때만 특정 파일을 연다.

## 절차
1. 소스·테스트·설정의 상위 구조를 읽기 전용으로 나열한다.
   ```bash
   find . -path './sk' -prune -o -path './.git' -prune -o -path './node_modules' -prune -o -path './venv' -prune -o -maxdepth 3 -type f -print | sort
   ```
   언어별 생성물 디렉터리가 더 있으면 목록에서 제외하되, 제외한 사실을 노트에 적는다.
2. 진입점 후보를 찾는다.
   ```bash
   find . -path './sk' -prune -o -type f \( -name 'main.*' -o -name 'app.*' -o -name 'server.*' -o -name 'index.*' -o -name 'manage.py' \) -print | sort
   rg -n --glob '!sk/**' --glob '!node_modules/**' --glob '!venv/**' 'listen\(|create_app|FastAPI\(|Flask\(|main\(|if __name__' .
   ```
   결과는 후보일 뿐이므로 실제 import·호출 위치를 열어 확인한 뒤 진입점으로 기록한다.
3. 모듈과 파일의 역할을 한 줄씩 적는다.
   디렉터리 구조가 아니라 실제 함수·클래스·라우트·명령 등록을 근거로 역할을 기술한다.
4. 핵심 요구사항 후보 또는 README의 대표 사용자 흐름 1건을 고른다.
   아직 R#이 없으면 `대표 흐름 후보`로 부르고 요구사항 ID를 임의로 만들지 않는다.
5. 그 흐름을 진입 → 검증 → 핵심 로직 → 저장/외부 연동 → 출력 순서로 추적한다.
   ```bash
   rg -n --glob '!sk/**' --glob '!node_modules/**' '<라우트명|함수명|명령어|데이터 필드>' .
   ```
   각 연결은 함수 호출, import, 라우팅 등록, 테스트 호출 중 실제로 확인된 방식만 화살표로 잇는다.
6. 데이터 모델과 입출력 경계를 찾는다.
   요청 DTO, 스키마, 타입, CSV 헤더, ORM 모델, 상태 객체, 직렬화 코드 중 확인된 것을 기록한다.
   미확인 필드는 추정으로 채우지 말고 → 1.1 requirements 또는 → 1.2 ambiguity (`$sk-ambiguity`)의 확인 대상으로 표시한다.
7. 설정과 실행 경계를 찾는다.
   포트·호스트·환경 변수·기본 경로·설정 파일을 찾아 값 자체가 민감하면 키 이름과 위치만 기록한다.
8. 기존 테스트와 픽스처를 찾는다.
   ```bash
   find . -path './sk' -prune -o -type f \( -path '*/test/*' -o -path '*/tests/*' -o -name '*test*.*' -o -name '*spec*.*' -o -path '*/fixtures/*' \) -print | sort
   ```
   테스트가 무엇을 검증하는지 한 줄로 적고, 통과 여부는 실제 실행하지 않았다면 `미실행`으로 둔다.
9. 변경 예상 지점과 위험 경계를 분리한다.
   변경 예상은 목표를 충족하기 위해 읽어 본 후보일 뿐이며, 실제 변경 승인은 3.2 설계와 4.2 구현에서 한다.
   공개 라우트, CLI 옵션, 공용 유틸, 공유 모델, 테스트 픽스처, 설정 기본값은 위험 경계로 표시한다.
10. ASCII 흐름도를 만든다.
    ```text
    [입력/사용자] -> [진입점: 파일:심볼] -> [검증] -> [핵심 로직] -> [출력/저장]
    ```
    미확인 연결은 `?`로 표시하고 사실처럼 이어 붙이지 않는다.
11. `sk/work/BRIEF.md`의 `## 코드 지도`만 생성 또는 갱신한다.
    다른 섹션, 과제 소스, 테스트, 설정에는 쓰지 않는다.
12. 지도에서 정책·출력·경계의 빈칸이 보이면 → 1.1 requirements (`$sk-requirements`)와 → 1.2 ambiguity (`$sk-ambiguity`)로 넘긴다.

## 판단 기준·분기
- if 명확한 실행 진입점이 여러 개면 then API·CLI·배치 등 실행 단위별로 나열하고 주 흐름과의 관계를 적는다.
- if 프레임워크 자동 탐색 때문에 호출이 보이지 않으면 then 등록 파일과 설정 근거를 적고 `간접 연결`이라고 표시한다.
- if 핵심 흐름이 외부 서비스에서 끊기면 then 외부 경계를 기록하되 인증값·엔드포인트 비밀값은 적지 않는다.
- if 대표 흐름이 문서와 코드에서 다르면 then 어느 것을 정답으로 고르지 말고 차이를 1.2에 넘긴다.
- if 테스트가 없으면 then `테스트 부재`를 위험으로 기록하고, 나중에 2.3 acceptance (`$sk-acceptance`)와 4.1 test-first (`$sk-test-first`)를 연결한다.
- if 공용 유틸이 여러 모듈에서 import되면 then 변경 예상 지점과 분리해 위험 경계로 표시한다.
- if 파일이 너무 많으면 then 진입점→대표 흐름→직접 의존 모듈→테스트 순으로 좁히고 모든 파일을 요약하려 하지 않는다.
- if 시간이 10분 미만이면 then 진입점, 대표 흐름, 테스트 위치, 위험 경계만 표로 기록한다.

## 작업 노트 기록
`sk/work/BRIEF.md`에서 정확히 `## 코드 지도` 섹션만 쓴다.
섹션의 파일·모듈 지도 표는 다음 열을 그대로 사용한다.

| 영역 | 경로 | 역할 | 진입점·호출자 | 입력→출력·부작용 | 근거 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 예: API 라우팅 | `src/routes.py` | 요청을 서비스로 전달 | `src/app.py:create_app` | JSON → 서비스 호출 | 파일:줄 |

대표 흐름 표는 다음 열을 사용한다.

| 흐름 | 단계 | 파일:심볼 | 입력→출력 | 정책·검증 위치 | 확인 상태 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 대표 흐름 후보 | 1 | `경로:심볼` | 값 변화 | 확인됨/미확인 | 관찰 근거 |

설정·테스트·위험 경계 표는 다음 열을 사용한다.

| 구분 | 경로·심볼 | 현재 역할·값 | 변경 예상 여부 | 위험·보존 이유 | 근거 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 설정/테스트/공개 인터페이스 | `경로:심볼` | 관찰 사실 | 예/아니오/미정 | 호환성·공유 범위 | 파일:줄 |

마지막에 ASCII 흐름도와 `미확인·다음 확인: <질문 또는 다음 ID>`를 둔다.
파일·행은 사실만 쓰고, 대표 흐름 후보는 1.1에서 R#이 확정되면 그 ID로 갱신한다.

## 채팅 출력 형식
1. **진입점**: 실제 확인한 실행 진입점과 근거를 말한다.
2. **지도 요약**: 핵심 모듈·데이터 모델·설정·테스트 위치를 표로 말한다.
3. **대표 흐름**: ASCII 흐름도와 확인되지 않은 연결을 구분해 말한다.
4. **변경 예상·위험**: 후보 지점과 절대 조심할 공개·공용 경계를 나눠 말한다.
5. **기록**: `sk/work/BRIEF.md#코드 지도` 갱신 여부를 말한다.
6. **다음 행동**: → 1.1 requirements (`$sk-requirements`), 빈칸은 → 1.2 ambiguity (`$sk-ambiguity`)를 제안한다.

## 완료 기준
- 진입점, 모듈 역할, 대표 흐름 1건을 관찰 근거로 기록했다.
- 데이터 모델·설정·테스트·픽스처의 위치 또는 부재를 구분했다.
- 변경 예상 지점과 위험 경계를 분리했고 ASCII 흐름도를 남겼다.
- `sk/work/BRIEF.md#코드 지도`만 갱신했다.
- 코드 수정, 테스트 실행, 의존성 설치 없이 발견 단계로 넘길 수 있다.

## 금지
- 과제 코드, 테스트, 설정, 데이터, 잠금 파일을 수정하지 않는다.
- 테스트·빌드·서버를 실행하지 않는다. 실행 기준선은 → 0.1 context (`$sk-context`)의 안전성 판단을 따른다.
- `sk/` 폴더를 탐색 대상에 포함하거나 그 파일을 과제 코드로 기록하지 않는다.
- 함수명·파일명만 보고 호출 관계·정책·데이터 스키마를 단정하지 않는다.
- 민감한 환경 변수 값, 토큰, 개인정보, 원본 데이터의 민감한 값을 노트나 채팅에 쓰지 않는다.
- 모든 파일을 읽으려 하거나 무관한 리팩터링 제안을 하지 않는다.
