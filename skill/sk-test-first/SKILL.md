# 실패하는 수용 테스트 먼저 작성

## 목적

현재 구현 슬라이스의 수용 테스트 T#를 코드보다 먼저 작성하고, 실패가 실제 미구현 동작 때문임을 확인한다.
테스트가 요구사항 R#, 확정 정책 P#, 수용 기준 AC를 고정하므로 구현 범위가 넓어지는 것을 막는다.

## 언제 쓰나 / 쓰지 않나

- 2.4가 READY 또는 READY-WITH-ASSUMPTIONS이고 3.1의 현재 S#를 시작할 때 사용한다.
- 슬라이스 전체를 한 번에 돌릴 때는 `→ 4.0 build-loop ($sk-build-loop)`가 이 규칙으로 단계 1(RED)을 진행한다.
- 기존 기능을 고치거나 새 기능을 추가하기 전에, 그 변경을 증명할 T#가 있을 때 사용한다.
- 테스트 실패가 보였지만 원인이 아직 불명확할 때도 사용한다. 먼저 실패 종류를 분류한다.
- 명세가 BLOCKED이거나 P0 규칙에 H 영향 G#가 남아 있으면 코드를 추측해 테스트로 고정하지 말고 1.3 dm-questions으로 넘긴다.
- 테스트만 작성하지 않고 구현까지 하려면 이 작업을 끝낸 뒤 4.2 implement로 넘긴다.

## 입력과 사전 확인

1. `sk/work/SPEC.md`에서 `## 0. 상태`, `## 3. 요구사항 R`, `## 5. 확정 정책 P`, `## 6. 가정 A`, `## 11. 수용 테스트 표 T`를 읽는다.
2. `sk/work/PLAN.md`의 `## 슬라이스 S`에서 현재 S#와 대상 R#/T#를 확인한다. 없으면 3.1 plan으로 돌아간다.
3. `sk/work/BRIEF.md`의 `## 환경`, `## 코드 지도`와 기존 테스트 설정을 읽어 프레임워크, 명령, 테스트 위치, 명명 규칙을 확인한다.
4. 현재 작업 트리와 변경 파일을 읽기 전용으로 확인한다. 남의 변경이나 기존 실패를 내 실패로 기록하지 않는다.
5. 테스트에 쓸 입력과 기대값은 SPEC의 AC/P에서 가져오고, 애매하면 손계산 근거를 메모한다. 구현 코드를 기대값 계산기로 쓰지 않는다.

## 절차

1. 현재 S# 하나만 선언하고, 이 회차에 검증할 T#를 P0 우선으로 한두 개 고른다.
2. 각 T#에 대해 `입력 → 호출 경로 → 기대 출력/오류 → 관련 R#/P#/AC`를 한 줄씩 적는다.
3. 기존 테스트 디렉터리, 파일명, fixture와 assertion 관례를 찾아 가장 가까운 사례를 읽는다.
4. 새 패키지를 추가하지 말고 기존 프레임워크와 표준 라이브러리만 사용해 테스트를 작성한다.
5. 테스트 이름에 행위와 조건을 드러낸다. 예: `빈_항목이면_정책_P2에_따라_빈_결과를_반환한다`처럼 작성한다.
6. Arrange-Act-Assert가 구분되도록 최소 입력을 만들고, 결과 전체 또는 필수 필드를 구체적으로 비교한다.
7. 정책 P#를 확인하는 테스트는 정책의 결과를 명시적으로 assert한다. 단지 예외가 나지 않는지만 확인하지 않는다.
8. 기존 테스트 파일의 수정·삭제가 아니라 추가가 가능한지 확인한다. 기존 실패 테스트를 약화하거나 skip 처리하지 않는다.
9. 추가한 테스트만 먼저 실행한다. 명령, 작업 디렉터리, 종료 코드, 통과·실패 수를 보존한다.
10. 실패가 미구현 동작에서 왔는지 아래 분류 기준으로 판정한다.
11. 판정이 맞으면 실패하는 테스트를 그대로 두고 4.2 implement에 구현 지시를 넘긴다.
12. 이 단계에서 실제로 실행한 결과만 `sk/work/EVIDENCE.md`에 E#으로 기록한다.

## 판단 기준·분기

- if 테스트가 기대한 값 불일치, 미구현 분기, `NotImplemented`처럼 기능 부재를 보인다 → `기대된 RED`로 판정하고 구현한다.
- if 문법 오류, import 오류, 테스트 탐색 오류, fixture 누락, 서버 미기동, 환경 변수 누락이다 → 기능 RED가 아니다. 환경/테스트 설정을 고친 뒤 다시 실행하고 E#에는 별도 원인으로 기록한다.
- if 이미 통과한다 → 기존 구현이 T#를 충족하는지 assertion의 약함·잘못된 fixture·잘못된 대상 호출을 먼저 점검한다. 통과를 억지로 실패시키지 않는다.
- if T#의 기대값을 P#/A#/AC 어디에서도 정할 수 없다 → 새 동작을 발명하지 말고 G 후보와 두 선택지를 정리해 1.3 dm-questions($sk-dm-questions)로 넘긴다.
- if 과제 규칙이 테스트 파일 추가를 금지하거나 프레임워크가 없다 → `sk/work/` 아래에 T# 이름의 임시 검증 스크립트를 만들 수 있는지 규칙을 확인한다. 허용될 때만 만들고, 제출물에 포함하지 않는다는 사실을 E#에 기록한다.
- if 현재 테스트가 기존 기능의 회귀 실패를 드러낸다 → 실패 출력과 최소 재현을 보존하고 6.1 debug($sk-debug)로 넘긴다. 기대값을 바꾸지 않는다.
- 시간이 부족하면 P0의 정상 1건과 가장 위험한 경계/실패 1건만 RED로 확인하고, 나머지 T#는 미실행으로 남긴다.

## 작업 노트 기록

`sk/work/SPEC.md`의 `## 11. 수용 테스트 표 T`는 읽기 기준이다. T#가 누락되었거나 기대값 근거가 없으면 임의로 확정하지 말고 2.3 acceptance($sk-acceptance)에 보완을 요청한다.

`sk/work/EVIDENCE.md`의 `## 실행 기록`에 기존 표가 없으면 아래 열로 만든다. 기존 표가 있으면 열과 다른 스킬의 행을 보존하고 E# 행만 추가한다.

| E# | 시각 | 명령·작업 디렉터리 | 대상 R/T | 기대 | 실제 결과 요약 | 판정 | 코드 상태 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |

- 기대된 RED는 판정에 `RED-미구현`으로, 환경·문법 실패는 `FAIL-설정`으로 명시한다.
- 실제 결과에는 종료 코드, 실패한 테스트명, 핵심 assertion 차이를 짧게 적는다. 비밀값·개인정보·긴 원본 출력은 쓰지 않는다.
- 코드 상태에는 현재 변경 파일 또는 확인 가능한 짧은 식별자를 적고, 실행하지 않은 결과는 기록하지 않는다.

## 채팅 출력 형식

다음 순서의 번호 목록으로 보고한다.

1. `대상`: S#, R#, AC, P#, T#.
2. `작성 위치`: 새 테스트/임시 검증 파일과 테스트 이름.
3. `기대값 근거`: SPEC의 정확한 R#/P#/A# 또는 손계산 요약.
4. `실행`: 실제 명령, 종료 코드, RED/통과 수.
5. `분류`: 기대된 RED인지 설정·문법·기존 회귀 문제인지.
6. `증거`: 추가한 E#.
7. `다음`: 4.2 implement 또는 막힌 이유와 1.3/6.1 핸드오프.

## 완료 기준

- 현재 S#의 우선 T#가 기존 관례에 맞는 위치와 이름으로 작성되었다.
- 입력, 기대값, 관련 R#/P#/AC가 테스트 또는 보고에서 추적 가능하다.
- 최소 한 번 실행했고, 실패 원인이 미구현인지 다른 문제인지 구분했다.
- 실제 실행 결과가 E#에 기록되었다.
- 구현 대상과 보존할 인터페이스를 4.2 implement에 넘길 수 있다.

## 금지

- 기존 테스트를 수정·삭제·skip 처리하거나 assertion을 약화해 통과시키지 않는다.
- 새 테스트 도구·패키지를 사용자 확인 없이 설치하지 않는다.
- 명세에 없는 정책, 정렬, 오류 메시지를 테스트 기대값으로 발명하지 않는다.
- `sk/` 도구 폴더를 과제 코드나 테스트 대상으로 넣거나 그 안의 파일을 수정하지 않는다.
- 테스트 실행 결과를 추정해 PASS/RED로 쓰지 않는다.
- push, 배포, 제출, 업로드를 실행하지 않는다.
