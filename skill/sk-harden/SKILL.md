# 관련 엣지 케이스 방어

## 목적

방금 구현한 기능에 실제로 닿는 입력·상태 경계를 좁게 점검하고, P#/A# 근거가 있는 경우에만 입구 Guard와 회귀 테스트를 추가한다.
모든 예외를 상상해 과잉 설계하는 대신, 재현 가능한 실패와 정책 연결을 남겨 품질과 속도를 함께 지킨다.

## 언제 쓰나 / 쓰지 않나

- 4.2 implement가 S#의 정상 경로를 통과시킨 직후, 다음 슬라이스 전에 사용한다.
- 수용 테스트 표의 경계·실패 T# 또는 현재 변경이 연 입력·상태 규칙을 확인할 때 사용한다.
- 전체 데이터 품질 감사는 5.3 data-validation, API 계약 전체 검증은 5.4 api-contract, UI 흐름 검증은 5.5 ui-smoke로 넘긴다.
- 새 비즈니스 규칙을 결정하거나 모든 파일을 전면 리팩터링하려면 사용하지 않는다. 불명확한 정책은 1.3 dm-questions로 보낸다.

## 입력과 사전 확인

1. `sk/work/SPEC.md`에서 `## 3. 요구사항 R`, `## 4. 제약 C`, `## 5. 확정 정책 P`, `## 6. 가정 A`, `## 10. 입출력·데이터 계약`, `## 11. 수용 테스트 표 T`를 읽는다.
2. `sk/work/PLAN.md`의 `## 슬라이스 S`에서 방금 끝낸 S#와 변경 범위를 확인한다.
3. `sk/work/EVIDENCE.md`의 최신 E#와 4.2 결과를 읽어 정상 경로가 실제로 GREEN인지 확인한다.
4. 변경 diff와 호출 경로를 읽어 입력 경계, 상태 전이, 출력 직전 중 어느 위치에 위험이 생기는지 확인한다.
5. 정책 근거가 P#인지 A#인지 구분한다. A#는 불확실성·확인 계획을 존중하며 영구 규칙처럼 과장하지 않는다.

## 절차

1. 현재 S#에 관련된 위험만 1~3개 고른다. 각 위험에 `재현 입력/상태`, `영향`, `근거 P#/A#/C#`, `방어 위치`를 적는다.
2. 아래 범주에서 해당하는 것만 선택한다: null·빈 값, 숫자 문자열·잘못된 타입·손상 레코드, 경계값·이상치, 중복·멱등성, 동점의 결정적 정렬, 빈 결과, 권한·상태 전이, 문서화된 웹 경계의 호스트/CORS.
3. 각 선택 항목을 현재 코드 또는 기존 테스트로 최소 재현한다. 추측한 위험을 사실처럼 쓰지 않는다.
4. 현재 동작과 기대 동작을 비교하고 기대가 P#/A#와 계약에 의해 결정되는지 확인한다.
5. 입력을 받는 가장 이른 경계에 최소 Guard를 둔다. 하위 계층마다 같은 검사를 중복하지 않는다.
6. 오류가 허용된 계약이면 예외 유형·상태 코드·빈 결과 형식을 계약에 맞춘다. 오류를 조용히 삼키지 않는다.
7. 방어마다 회귀 테스트를 T#로 추가하거나 기존 T#와 연결한다. 정상 테스트와 오류/경계 테스트를 혼동하지 않는다.
8. 방어 테스트와 관련 기존 테스트를 실행한다. 출력 스키마·정렬·기존 인터페이스가 보존되는지 확인한다.
9. 새 T#가 생겼다면 SPEC 11절에 근거와 기대값을 기록하고, 실행 결과는 E#으로 남긴다.
10. 정책 근거가 없거나 더 넓은 변경이 필요하면 코드를 억지로 막지 말고 G 후보와 최소 재현을 다음 단계에 넘긴다.

## 판단 기준·분기

- if null/빈 값의 결과가 P#에 명시되어 있다 → 해당 입력에서 Guard와 정확한 출력/오류를 테스트한다.
- if 숫자·타입 오류의 처리 규칙이 없다 → 임의로 0 변환, 무시, 제외하지 않는다. G 후보를 1.3 dm-questions($sk-dm-questions)로 보낸다.
- if 경계값이 `이상/초과`, `이하/미만` 중 불명확하다 → 동등 경계 입력을 만들되 기대값을 확정하지 않는다. 2.3 acceptance 또는 1.3에서 확인한다.
- if 중복 처리·멱등성 요구가 있다 → 같은 입력을 두 번 적용한 결과와 키 기준을 명시해 테스트한다. 기준이 없으면 정책을 만들지 않는다.
- if 동점 정렬이 출력 계약에 있다 → 2차 키 P#를 assert한다. 계약에 없으면 우연한 현재 순서를 고정하지 않는다.
- if 빈 결과가 가능하다 → 빈 배열/객체/상태 코드 등 SPEC 10절 형식을 확인한다. `null`로 바꾸거나 404로 바꾸지 않는다.
- if 권한·상태 전이가 실제 과제 범위다 → 허용되지 않은 상태의 거부와 성공 상태의 전이를 각각 확인한다. 인증 체계를 새로 만들지 않는다.
- if 웹 서버·UI 과제다 → 지정 포트 유지와 내장 Browser 미리보기용 `0.0.0.0` 바인딩만 확인한다(과제 문서가 다르게 정하면 과제 문서 우선). CORS·헤더는 문서화된 요구만 확인하고 와일드카드 CORS나 인증 해제는 추가하지 않는다.
- 시간이 부족하면 장애 영향이 큰 P0 경계 1개와 입력 오류 1개만 실제 실행하고, 나머지는 미검증으로 남겨 5.1 verify에 알린다.

## 작업 노트 기록

`sk/work/SPEC.md`의 `## 11. 수용 테스트 표 T`에 새 회귀 테스트가 꼭 필요할 때만 다음 열을 유지해 다음 미사용 T# 행으로 추가한다. 기존 T#의 ID와 행을 덮어쓰지 않는다.

| ID | 관련 R/P | 유형 | 입력 | 기대 출력 | 기대값 근거 | 확인 방법 | 제공 테스트 여부 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |

- 유형은 `정상`, `경계`, `실패`, `회귀` 중 하나로 쓰며, `관련 R/P`에 P# 또는 A#을 명시한다.
- A#가 근거이면 `기대값 근거`에 가정임과 되돌릴 지점을 적는다.
- 정책이 미확정인 항목은 T#로 확정하지 말고 G 후보로 보고한다.

`sk/work/EVIDENCE.md`의 `## 실행 기록`에 아래 열로 E# 행을 추가한다.

| E# | 시각 | 작업 디렉터리 | 명령 | 대상 R/T | 기대 | 실제 결과 요약 | 판정 | 코드 상태 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |

- 실제 결과에는 재현 입력의 민감하지 않은 요약, 종료 코드, 통과·실패 수, 핵심 출력만 적는다.
- 방어 추가 후 기존 E#이 현재 코드에 더 이상 맞지 않으면 `STALE`로 표시하고 필요 시 재실행한다.
- G 후보는 이 스킬의 정책으로 확정하지 않는다. R#/P#/A# 영향과 재현을 채팅에서 1.3에 넘긴다.

## 채팅 출력 형식

다음 순서의 번호 목록으로 보고한다.

1. `범위`: S#, 변경 파일·함수, 이번에 고른 위험 범주.
2. `위험 매트릭스`: 재현 입력/상태, 현재 동작, 기대 근거 P#/A#/C#, 영향.
3. `방어`: Guard 위치, 동작, 보존한 출력·인터페이스.
4. `테스트`: T#와 실행 명령, 종료 코드, 실제 결과, E#.
5. `미확정`: 정책 없는 G 후보와 코드로 정하지 않은 이유.
6. `다음`: 5.1 verify 또는 관련 전문 검증(5.3/5.4/5.5), 필요 시 1.3.

## 완료 기준

- 정상 경로가 이미 통과한 S#에 한정해 관련 위험만 조사했다.
- 각 방어에는 재현 입력과 P#/A#/C# 근거가 있다.
- 방어 위치가 입구 Guard 또는 계약 경계로 최소화되었다.
- 추가·갱신한 T#와 실제 실행 E#이 연결되었다.
- 미확정 정책은 코드가 아니라 G 후보·핸드오프로 남겼다.

## 금지

- 근거 없이 모든 null, 음수, 중복, 동점을 같은 방식으로 처리하지 않는다.
- 데이터 행을 삭제·정규화하거나 기존 출력 스키마를 바꾸지 않는다.
- 내부 오류를 빈 성공 결과로 숨기거나 무조건 예외를 무시하지 않는다.
- 보안 요구가 없는 인증·권한·CORS·호스트 정책을 새로 만들지 않는다.
- `sk/`의 도구 파일과 원본 데이터·기존 테스트를 수정하거나 삭제하지 않는다.
- 새 패키지 설치, 네트워크 사용, 배포·제출·push를 사용자 확인 없이 실행하지 않는다.
