# 가설 기반 디버깅

## 목적
실제 실패를 추측성 수정이 아닌 관찰 가능한 가설과 작은 실험으로 원인까지 좁힌다.
수정 범위를 현재 문제와 직접 관련된 파일·함수·정책으로 제한하고, 실패 사례를 회귀 테스트와 실행 증거로 남긴다.

## 언제 쓰나 / 쓰지 않나
- 테스트, 빌드, 실행, 데이터 대사, API·UI 확인에서 실제 FAIL 또는 예상과 다른 출력이 생기면 쓴다.
- `5.1 verify`, `5.3 data-validation`, `5.4 api-contract`, `5.5 ui-smoke`가 남긴 E# 실패를 시작점으로 삼는다.
- 같은 오류 문구를 두 번 이상 고쳤는데 재발하거나 원인이 불명확하면 먼저 이 스킬을 쓴다.
- 요구사항 자체가 모호하거나 정책이 충돌하는 경우에는 원인을 코드로 단정하지 말고 `1.3 dm-questions ($sk-dm-questions)`로 넘긴다.
- 구현 전 기능 설계, 단순 정적 리뷰, 시간 부족에 따른 범위 선택만을 위한 스킬은 아니다. 각각 `3.2 design`, `7.1 review`, `6.5 timebox`를 쓴다.

## 입력과 사전 확인
1. 실패한 명령 전체, 작업 디렉터리, 종료 코드, 오류 전문, 입력 또는 요청값을 확보한다.
2. `sk/work/SPEC.md`의 `## 3. 요구사항 R`, `## 5. 확정 정책 P`, `## 10. 입출력·데이터 계약`, `## 11. 수용 테스트 표 T`에서 관련 R#/P#/T#를 찾는다.
3. `sk/work/EVIDENCE.md`의 `## 실행 기록`에서 마지막 PASS E#와 처음 FAIL E#를 비교한다.
4. 읽기 전용으로 변경 범위를 본다. 예: `git status --short`, `git diff -- <관련 파일>`.
5. 재현 입력에 비밀값·개인정보가 있으면 값을 마스킹하고, 노트에는 형태·길이·식별 불가능한 요약만 기록한다.

## 절차
1. 오류를 한 문장으로 재진술한다: “입력 X에서 기대 Y 대신 실제 Z가 나오며, R#/P#를 위반한다.”
2. 오류 전문을 축약하지 말고 확보하되, 채팅·노트에는 필요한 스택 프레임과 핵심 값만 발췌한다.
3. 최소 재현을 만든다. 실패한 전체 흐름에서 입력 1건, 명령 1개, 가능한 한 작은 실행 경로만 남긴다.
4. 최소 재현을 수정 전 상태에서 한 번 실행해 같은 실패인지 확인한다. 재현되지 않으면 환경·시간·상태 의존 가설을 세우고 수정하지 않는다.
5. 서로 다른 계층의 가설을 2~3개만 적는다. 예: 입력 파싱, 정책 분기, 호출 순서·상태, 테스트 기대값 오류.
6. 각 가설에 관찰 근거와 반증 방법을 붙인다. “P3의 빈 값 규칙을 무시하는 분기”처럼 검증 가능한 문장으로 쓴다.
7. 가장 싸고 비파괴적인 판별 실험 하나를 고른다. 단위 함수 호출, 중간값 임시 출력, 단일 테스트, 응답 본문 확인을 우선한다.
8. 실험마다 한 변수만 바꾸고 결과를 읽는다. 로그를 추가했다면 민감값을 출력하지 않고 원인 확정 뒤 제거하거나 과제 규칙에 맞는 진단으로 정리한다.
9. 반증된 가설은 버리고, 관찰로 지지된 가설만 남긴다. 두 가설을 한 수정으로 동시에 시험하지 않는다.
10. 원인을 “어느 입력이 어느 조건에서 어떤 규칙을 누락·왜곡했는가”로 확정한다. 확정되지 않으면 다음 작은 실험으로 돌아간다.
11. 관련 P#/A#와 공개 인터페이스를 다시 읽고, 원인을 고치는 최소 변경만 구현한다. 새 정책이 필요하면 구현하지 말고 G#로 등록한다.
12. 실패 재현 케이스를 기존 프레임워크의 회귀 테스트로 추가한다. 테스트 위치·의존성 규칙상 추가할 수 없으면 `sk/work/`의 일회성 검증 스크립트로 대체하고 이유를 E#에 쓴다.
13. 새 회귀 테스트를 먼저 실행하고, 관련 테스트, 마지막으로 가능한 전체 테스트를 실행한다. 각 결과가 같은 코드 상태인지 확인한다.
14. 관련 R→AC→T→E 연결을 `5.1 verify ($sk-verify)`에 넘길 수 있게 정리한다.
15. 최소 경로(시간 10분 이하)는 오류 전문 확보 → 최소 재현 1회 → 가설 2개 → 판별 실험 1개 → 최소 수정 → 재현 테스트 1회 → E# 기록이다.

```bash
# 읽기 전용 범위 확인 예시: 과제 루트에서 실행한다.
git status --short
git diff -- <관련-파일>

# 최소 재현 테스트 예시: 실제 프로젝트의 테스트 명령으로 바꾼다.
<프로젝트-테스트-명령> <실패-테스트-선택자>
```

## 판단 기준·분기
- 최소 재현이 PASS이면 → 캐시, 환경 변수, 실행 순서, 외부 상태를 후보로 두고 현재 값을 비교한다. 코드 수정은 보류한다.
- 가설의 판별 실험이 원인을 배제하면 → 해당 가설을 폐기하고 다음 가설 하나만 시험한다.
- 오류가 P#/문서와 테스트 기대값의 충돌이면 → G#로 남기고 `1.3 dm-questions ($sk-dm-questions)`를 준비한다. 조용히 한쪽을 고르지 않는다.
- 코드가 아닌 데이터 불일치이면 → 원본을 수정하지 말고 `5.3 data-validation ($sk-data-validation)`의 독립 대사를 다시 수행한다.
- API 도달성·상태 코드 문제면 → 서버 실행 요구를 확인한 뒤 `5.4 api-contract ($sk-api-contract)`로 계약을 대조한다.
- 수정 시도 두 번 뒤에도 원인이 불명확하거나 diff가 커지면 → 편집을 멈추고 `6.2 unstuck ($sk-unstuck)`으로 전환한다.
- 현재 변경이 마지막 PASS 상태보다 위험하거나 회복이 불명확하면 → `6.3 rollback ($sk-rollback)`에서 백업·사용자 승인 절차를 따른다.
- AI가 만든 코드가 원인이라면 → 원인·교정 지시·확인 E#를 AI#로 기록한다. AI 탓이라고 추측만 기록하지 않는다.

## 작업 노트 기록
`sk/work/EVIDENCE.md`의 `## 실행 기록`에 실제 실행 직후 새 행을 추가한다. 기존 행은 덮어쓰지 않는다.

| E# | 시각 | 명령·작업 디렉터리 | 대상 R/T | 기대 | 실제 결과 요약 | 판정 | 코드 상태 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| E12 | 14:18 | `<명령>` / `<경로>` | R3, T7 | 빈 값은 400 | 500, TypeError | FAIL | `<짧은 해시·변경 파일>` |

- 판별 실험도 결과가 의사결정에 쓰였다면 E#으로 남긴다. 변경 후 기존 PASS 증거는 STALE 여부를 표시한다.
- AI 생성 코드의 결함을 실제로 확인한 경우에만 `sk/work/DECISIONS.md`의 `## AI 교정 기록`에 다음 블록을 더한다.

```markdown
### AI3
- 문제: `<실제 누락·불일치>`
- 발견 방법: `E12`의 `<테스트·오류>`
- 내가 지시한 수정: `<최소 수정의 요지>`
- 확인: `T7`, `E13` PASS; `<미검증 범위가 있으면 명시>`
```

- 설계 선택 자체가 바뀌면 `## DD<n> 제목` 블록을 갱신하되, 단순 버그 수정에 새 DD#를 남발하지 않는다.

## 채팅 출력 형식
1. **실패 정의**: 관련 R#/P#/T#, 실제 오류 요약, 재현 명령.
2. **가설 표**: 번호 | 근거 | 가장 싼 판별 실험 | 결과 | 채택/폐기.
3. **확정 원인**: 파일·함수·조건과 근거 E#.
4. **최소 수정**: 변경 파일, 보존한 인터페이스, 회귀 테스트.
5. **검증**: 재현/관련/전체 테스트의 실제 PASS·FAIL·미검증과 E#.
6. **다음 행동**: `5.1 verify ($sk-verify)` 또는 남은 차단 요인 1개.

## 완료 기준
- 실패가 수정 전 최소 재현으로 확인되었거나, 재현 불가 사유와 다음 관찰 방법이 명확하다.
- 채택·폐기된 가설과 판별 결과가 구분되어 있다.
- 원인이 확정된 경우 최소 수정과 실패 사례 회귀 테스트가 존재한다.
- 관련 테스트와 가능한 전체 테스트의 실제 결과가 E#으로 기록되어 있다.
- 관련 P#/A#를 임의로 바꾸지 않았고, 새 정책 필요성은 G# 또는 DM으로 넘겼다.

## 금지
- 오류 전문 없이 “아마 null 문제”처럼 추측 수정 연타를 하지 않는다.
- 한 실험에서 코드·입력·환경·기대값을 함께 바꾸지 않는다.
- 기존 테스트·원본 데이터·제출물을 삭제하거나 실패를 PASS로 표현하지 않는다.
- `sk/` 도구 폴더를 과제 코드처럼 분석·테스트·수정하지 않는다. 작업 노트는 `sk/work/`에만 쓴다.
- 패키지 설치·네트워크 사용·외부 제출을 과제 규칙과 사용자 확인 없이 하지 않는다.
- 위험한 전체 되돌리기 명령, 강제 체크아웃, 임의 포트·호스트 변경을 하지 않는다.
