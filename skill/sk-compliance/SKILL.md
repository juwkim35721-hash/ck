# 명세·DM 반영 준수 감사

## 목적

SPEC의 요구사항·제약·확정 정책·가정이 코드, 테스트, 실행 증거에 실제로 연결됐는지 행 단위로 감사한다.
“테스트가 통과했다”는 한 문장으로 준수를 추정하지 않고 R#/C#/P#/A#마다 구현 위치·T#·E#·상태를 남긴다.
감사 결과는 제출 가능 판정과 영향도순 수정 목록, 그리고 정직하게 남길 한계 목록이다.

## 언제 쓰나 / 쓰지 않나

- `7.1 review`($sk-review) 뒤, 전체 검증 후, 보고서·제출 직전에 명세 반영을 확인할 때 사용한다.
- 담당자 DM 답변이 코드·테스트에 반영됐는지 별도로 보장해야 할 때 특히 사용한다.
- 특정 실패의 원인을 찾는 작업은 `6.1 debug`($sk-debug), 변경 자체의 결함 탐색은 `7.1 review`($sk-review)가 먼저다.
- SPEC가 DRAFT 또는 BLOCKED면 감사 결과를 “준수”로 판정하지 말고 `2.4 spec-gate`($sk-spec-gate)로 되돌린다.
- 본 스킬은 기본적으로 읽기·감사만 한다. 수정은 사용자가 승인한 항목을 해당 구현·디버그 흐름으로 넘긴다.

## 입력과 사전 확인

1. `sk/work/SPEC.md`의 `## 0. 상태`, `## 2. 필수 제출물`, `## 3. 요구사항 R`, `## 4. 제약 C`, `## 5. 확정 정책 P`, `## 6. 가정 A`, `## 10. 입출력·데이터 계약`, `## 11. 수용 테스트 표 T`, `## 12. 추적표`, `## 13. 변경 기록`을 읽는다.
2. `sk/work/DM_LOG.md`에서 M# 원문과 `## 정책 목록 P`를 대조한다. P#가 어떤 답변에서 왔는지 잃지 않는다.
3. `sk/work/PLAN.md`의 완료·축소 S#, `sk/work/EVIDENCE.md`의 E#, `sk/work/REVIEW.md`의 열려 있는 F#를 읽는다.
4. 과제 루트에서 `git status --short`, `git diff --stat`, `git diff --name-only`로 현재 변경 범위를 확인한다. `sk/`는 도구이므로 과제 산출물·검증 범위에서 제외한다.
5. 최신 E#의 코드 상태와 현재 변경 파일을 비교한다. 다르면 이전 PASS는 STALE이므로 다시 검증이 필요하다.
6. 공식 과제 문서가 접근 가능하면 SPEC 출처와 대조하되, 문서에 없는 평가 방식·규칙은 사실처럼 추가하지 않는다.

## 절차

1. **감사 기준선을 선언한다.** SPEC 상태, 감사 시각, 현재 변경 범위, 최신 코드 상태, 남은 시간을 기록한다. 상태가 READY-WITH-ASSUMPTIONS면 A#를 별도 우선 대상으로 표시한다.
2. **대상을 전부 수집한다.** P0/P1 R#, 모든 C#, 모든 P#, 구현에 영향을 주는 A#, 필수 제출물을 각각 한 행으로 만든다. P2는 시간 부족 시 “미감사”로 남길 수 있으나 행을 생략하지 않는다.
3. **각 R#을 AC까지 추적한다.** R# → AC-R#-n → T# → 구현 파일·함수/라우트 → E# 순으로 연결한다. 하나라도 비어 있으면 “충족”으로 쓰지 않는다.
4. **각 C#를 독립 점검한다.** 인터페이스 유지, 지정 호스트·포트, 금지 의존성, 성능 제한, 수정 금지 파일, 제출 형식처럼 유형에 맞는 관찰 근거를 찾는다. 단순히 코드가 있어 보인다는 근거는 충분하지 않다.
5. **DM 정책 P#를 역추적한다.** M#의 답변 범위를 다시 읽고 P#의 “조건 → 동작”과 실제 분기·기본값·오류·정렬·테스트를 대조한다. 답변을 과도하게 일반화한 구현은 부분 또는 미충족이다.
6. **가정 A#를 노출한다.** 가정의 근거, 되돌릴 지점, 확인 계획이 남아 있는지 확인한다. 확인되지 않은 A#가 P0 동작을 좌우하면 “조건부”가 아니라 수정 또는 담당자 확인이 필요함을 표시한다.
7. **입출력과 제출물을 점검한다.** SPEC 10절의 필드·타입·정렬·반올림·오류 계약을 코드와 T#에 대조한다. SPEC 2절의 파일명·경로·형식·필수 문서 존재도 실제 파일 기준으로 확인한다.
8. **증거의 신선도를 판정한다.** E#에 명령·작업 디렉터리·대상 R/T·실제 결과·코드 상태가 있는지 보고, 변경 이후 실행되지 않은 E#는 STALE로 표시한다. 증거가 없으면 미검증이다.
9. **상태를 보수적으로 부여한다.** `충족`, `부분`, `미충족`, `미검증`, `해당 없음`만 사용한다. “부분”에는 빠진 조건, “미검증”에는 필요한 실행을 반드시 쓴다.
10. **불일치를 원인별로 분류한다.** 코드 결함은 F#와 연결해 `7.1 review`($sk-review) 또는 `6.1 debug`($sk-debug)로, 명세·DM 충돌은 G#와 함께 `1.3 dm-questions`($sk-dm-questions)로, 추적표 누락은 `5.1 verify`($sk-verify)로 보낸다.
11. **수정 순서를 제시한다.** `차단`(필수 제출물·P0·C# 위반), `높음`(P#·인터페이스·신선한 증거 부재), `중간`, `낮음` 순서로 최소 조치를 쓴다. 수정은 승인 전 수행하지 않는다.
12. **감사 결론을 제한한다.** 모든 필수 행이 충족이고 최신 E#가 있으면 준수 확인, 부분·미충족·미검증이 있으면 조건과 남은 행동을 포함한 조건부 또는 보류로 보고한다.

## 판단 기준·분기

| 상황 | 상태·행동 |
| :--- | :--- |
| R#에는 구현이 있으나 AC/T/E 중 하나가 없음 | `부분` 또는 `미검증`; `5.1 verify`($sk-verify)로 빈 연결을 채운다. |
| P#는 코드에 반영됐으나 답변의 조건보다 넓게 적용됨 | `부분`; M# 원문, 영향 예시, G# 후보를 남기고 `1.3 dm-questions`($sk-dm-questions)로 확인한다. |
| C#의 금지 의존성 또는 수정 금지 파일을 위반함 | `미충족`, 차단으로 분류한다. 사용자 승인 후 최소 복구와 재검증이 필요하다. |
| 필수 제출물 경로·이름·형식을 실제로 확인하지 못함 | `미검증`; 추정으로 존재한다고 쓰지 않는다. |
| 최신 E#보다 코드가 바뀜 | 이전 증거를 STALE로 취급하고 필요한 테스트를 다시 실행하도록 `5.1 verify`($sk-verify)에 넘긴다. |
| 공식 문서와 P#가 충돌함 | 어느 쪽을 임의 채택하지 말고 `G#`와 확인 질문을 만든다. 정보 우선순위는 공식 문서가 높다. |
| A#가 남았지만 되돌릴 지점·확인 계획이 있음 | 영향이 P0가 아니면 `부분` 및 한계 목록에 남긴다. |
| 시간 10분 이하 | P0 R, 모든 C#, P#, 필수 제출물, 최신 E#만 우선 감사하고 나머지는 `미감사`가 아니라 `미검증`으로 명시한다. |

`충족`은 구현 위치, 적절한 T#, 현재 코드에 대응하는 E#가 모두 있고 관찰 결과가 AC/P/C와 맞을 때만 쓴다.

## 작업 노트 기록

`sk/work/REVIEW.md`의 정확한 `## 준수 감사` 제목 아래에 감사 기준선과 표를 추가·갱신한다. `## 리뷰 발견 F`는 덮어쓰지 않는다.

```markdown
## 준수 감사

- 감사 기준: SPEC 상태 `READY`, 코드 상태 `<짧은 해시 또는 변경 파일 목록>`, 감사 시각 `<시각>`

| 대상 | 요구·제약·정책/가정 요약 | 출처 | 구현 위치 | 테스트 T | 증거 E | 상태 | 빈칸·다음 행동 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| P3 | 동점이면 이름 오름차순으로 정렬 | M2-1 | `src/rank.py:42` | T8 | E14 | 충족 | - |
| C2 | 기존 `/items` 응답 키 유지 | README:18 | `api/items.py:20` | T11 | E15 | 부분 | 오류 응답 키는 미검증; 5.4로 확인 |
| A1 | 빈 입력은 빈 목록 반환 | A1 | `src/rank.py:12` | T9 | E14 | 미검증 | 담당자 확인 또는 경계 테스트 실행 |
```

- 대상은 `R#`, `C#`, `P#`, `A#`, `DEL-<제출물 번호>` 형식으로 쓰고 중복 행을 만들지 않는다.
- 코드·테스트 실행이 필요해 실제 실행했으면 `sk/work/EVIDENCE.md`의 `## 실행 기록`에 E#으로 남긴다.
- 감사 중 발견한 구현 결함은 F#를 새로 만들거나 기존 F#와 연결한다. AI 산출물 결함이면 `sk/work/DECISIONS.md`의 `## AI 교정 기록`에 AI#도 남긴다.
- SPEC의 사실을 감사 도중 고치지 않는다. 변경 근거가 있으면 `2.1 spec`($sk-spec) 또는 `1.4 dm-answers`($sk-dm-log)로 인계한다.

## 채팅 출력 형식

아래 순서로 보고한다.

1. **감사 기준선:** SPEC 상태, 현재 변경 범위, 최신/STALE E# 여부.
2. **결론:** `준수 확인` / `조건부 준수` / `준수 보류` 중 하나와 행 수 요약.
3. **상태 집계:** 충족·부분·미충족·미검증 개수.
4. **차단·높음 목록:** 대상 ID | 상태 | 근거 | 최소 다음 행동 | 관련 F#/G# 순서.
5. **남길 한계:** 승인 없이 고치지 않을 부분·미검증 범위·A#를 구분.
6. **인계:** 수정이면 `6.1 debug`($sk-debug), 증거면 `5.1 verify`($sk-verify), 질문이면 `1.3 dm-questions`($sk-dm-questions), 다음이면 `8.1 report`($sk-report).

## 완료 기준

- 모든 R#/C#/P#/영향 A#/필수 제출물이 표에 있고, 누락 행을 숨기지 않았다.
- 각 행에 출처, 구현 위치, T#, E#, 상태, 다음 행동 또는 공백 사유가 있다.
- M# 원문과 P#의 범위를 실제 코드·테스트에 역추적했다.
- 최신 코드와 E#의 코드 상태를 비교해 STALE 증거를 분리했다.
- 차단·높음 수정은 영향도순으로 제시했지만 사용자 승인 없이 과제 파일을 고치지 않았다.

## 금지

- 테스트 통과 하나만으로 모든 R#/C#/P#가 충족됐다고 선언하지 않는다.
- 담당자 답변을 지어내거나 M#의 짧은 답변을 더 넓은 정책으로 일반화하지 않는다.
- 공식 문서와 P#의 충돌을 임의로 해소하지 않는다. G#와 확인 질문으로 남긴다.
- 실행하지 않은 검증, 보지 않은 제출물, 추정한 코드 위치를 E# 또는 충족 근거로 쓰지 않는다.
- 사용자 승인 없이 감사 발견을 이유로 과제 코드·테스트·설정·문서를 수정하지 않는다.
- 외부 제출·업로드·push·배포를 실행하거나 비밀값·토큰·개인정보를 기록하지 않는다.
- `sk/` 도구 폴더 자체를 과제 산출물·수정 금지 파일 감사의 대상이라고 오인하지 않는다.
