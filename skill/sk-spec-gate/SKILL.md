# 구현 착수 게이트와 명세 동결

## 목적

완성된 척하는 명세를 막고, 구현을 시작해도 되는지 실제 노트 근거로 판정하라.
`sk/work/SPEC.md`의 `## 0. 상태`와 `## 14. 게이트 결과`만 갱신하며, 판정 이후 변경은 13절을 통한 통제 절차로 안내하라.
READY는 낙관적 표현이 아니라 P0·정책·계약·T#가 서로 연결된 실제 상태여야 한다.

## 언제 쓰나 / 쓰지 않나

- 2.1 명세 통합, 2.2 데이터 계약, 2.3 수용 테스트 표를 마친 뒤 구현 직전에 쓴다.
- 담당자 답변·범위·입출력 계약이 변해 동결을 다시 판단해야 할 때 쓴다.
- R/P/AC 자체를 새로 작성할 때는 → 2.1 spec (`$sk-spec`)으로 돌아간다.
- 데이터 계약이 비어 있을 때는 → 2.2 io-contract (`$sk-data-contract`)을 먼저 쓴다.
- T#가 없거나 약할 때는 → 2.3 acceptance (`$sk-acceptance`)를 먼저 쓴다.
- 구현 계획·코드 변경·테스트 실행은 이 스킬의 일이 아니다.

## 입력과 사전 확인

1. `sk/work/SPEC.md` 전체를 읽고 특히 0~14절 제목 누락, 표의 빈칸, 오래된 상태 문구를 찾는다.
2. `## 한 장 요약`, `## 구현 시 반드시 지킬 규칙 Top 5`, `## 2. 필수 제출물`이 서로 일치하는지 확인한다.
3. P0 R의 AC-R#-n, P#, A#, G#, 10절 계약, 11절 T#와 각 T#의 관련 R/P를 대조한다.
4. `sk/work/BRIEF.md`의 `## 환경`에서 기준선 실행 기록·실행 제약을 확인한다.
5. `sk/work/DISCOVERY.md`와 `sk/work/DM_LOG.md`를 다시 읽어 P# 출처와 열린 G#가 최신인지 확인한다.
6. 기준선이 실행되지 않았다면 이유와 미검증 상태를 확인하고, 실행하지 않은 통과 기록을 찾으면 수정 요구로 표시한다.
7. 현재 시각과 과제 시작 이후 경과 시간을 확인해 약 40분 상한에 도달했는지 판단한다.

## 절차

1. `## 0. 상태`를 먼저 `DRAFT, <판정 시각>`으로 두고 실제 점검이 끝난 뒤 최종 상태로 바꿔라.
2. 목표가 한 문장으로 명확하고 구현 범위·비목표와 모순 없는지 확인하라.
3. 필수 제출물마다 경로·파일명·형식·출처가 있는지 확인하라.
4. 모든 P0 R에 우선순위, 출처, 하나 이상의 AC-R#-n, 하나 이상의 T#가 있는지 행 단위로 대조하라.
5. 모든 P#에 `조건 → 동작`, 예시, M#/문서 근거, 영향 R, 하나 이상의 T#가 있는지 확인하라.
6. C#가 인터페이스, 실행 환경, 수정 범위, 보안과 충돌하지 않는지 확인하라.
7. 입력·출력·오류·키·정렬·빈 결과가 필요한 과제에서 10절 계약이 존재하는지 확인하라.
8. H 영향 G#가 열려 있으면 담당자 질문 여부, A# 전환 여부, 되돌릴 지점, 확인 계획을 각각 확인하라.
9. A#가 있으면 근거·위험·되돌릴 지점·확인 계획 네 칸이 모두 있고 P#로 위장되지 않았는지 확인하라.
10. 11절 T#에 구체 입력·기대 출력·독립 근거·확인 방법이 있는지, P0/P1/P# 커버리지 수치가 맞는지 확인하라.
11. 비목표와 용어집이 범위·용어 충돌을 막을 만큼 기록됐는지 확인하라.
12. 충돌이 공식 문서와 P# 사이인지, P#와 코드 관찰 사이인지, 단순 누락인지 분류하라.
13. 실제 근거로 아래 체크리스트 표를 14절에 작성하라.
14. `항목 | 판정 | 근거 위치 | 부족하면 필요한 최소 행동` 열을 사용하고 예/아니오/조건부를 사실대로 적어라.
15. 모든 필수 항목이 예이고 실질 가정이 없으면 `READY`로 판정하라.
16. P0·T#·계약이 있으나 되돌릴 수 있는 A# 또는 H G#의 임시 처리만 남으면 `READY-WITH-ASSUMPTIONS`로 판정하라.
17. P0의 AC/T 누락, 필수 제출물 미정, 해결되지 않은 문서↔P# 충돌, 되돌릴 수 없는 H G#, 필수 계약 부재 중 하나가 있으면 `BLOCKED`로 판정하라.
18. 답을 기다리느라 시작 뒤 약 40분을 넘겼고 P0·AC·T·계약은 갖췄다면 H G#를 A#로 전환할 수 있는지 확인한 뒤 `READY-WITH-ASSUMPTIONS`로 진행하라.
19. 40분 규칙은 핵심 제출물·P0·오류 계약 자체가 비어 있는 BLOCKED를 READY로 바꾸는 면허가 아니다.
20. `## 0. 상태`에 최종 상태와 판정 시각을, `## 14. 게이트 결과`에 이유·위험·최소 다음 행동을 기록하라.
21. READY 계열이면 명세 동결 시각과 변경 절차를 14절에 명시하고 → 3.1 plan (`$sk-plan`)으로 인계하라.
22. BLOCKED면 가장 작은 해소 행동 하나만 우선순위로 제시하고, DM이 필요하면 → 1.3 dm-questions (`$sk-dm-questions`) 또는 → 1.5 dm-confirm (`$sk-dm-confirm`)으로 연결하라.

## 판단 기준·분기

- `기준선 기록`은 실제 명령·결과가 있거나 실행 불가 사유가 명시된 경우에만 예로 표시하라.
- 비핵심 P1/P2의 T# 누락은 READY-WITH-ASSUMPTIONS 또는 위험으로 기록할 수 있으나 P0 누락을 가리지 못한다.
- H 영향 G#가 A#가 되었더라도 되돌릴 지점·확인 계획이 없으면 BLOCKED로 처리하라.
- 공식 문서와 P#가 충돌하면 담당자 답변이 더 최신이어도 독단으로 선택하지 말고 BLOCKED 또는 확인 대기로 남겨라.
- 유효한 10절이 필요 없는 순수 알고리즘 과제라면 `해당 없음`의 근거를 14절에 적고 계약 누락으로 막지 마라.
- T#가 전부 계획일 뿐 아직 실행되지 않은 것은 정상이며, 이를 테스트 통과라고 쓰지 마라.
- 시간이 10분 이하이면 새 범위를 추가하지 말고 최소 P0·필수 제출물·게이트와 → 3.1의 축소 계획을 우선하라.

## 작업 노트 기록

`sk/work/SPEC.md`의 다음 정확한 제목만 수정하라.

| 절 | 필수 형식 |
| --- | --- |
| `## 0. 상태` | `READY | <판정 시각>`처럼 상태와 시각; 필요 시 이유 한 줄 |
| `## 14. 게이트 결과` | 체크리스트 표, 최종 판정, 이유, 위험, 최소 다음 행동, 동결 규칙 |

14절 체크리스트 예시는 다음 의미를 빠뜨리지 마라.

| 항목 | 판정 | 근거 위치 | 부족하면 필요한 최소 행동 |
| --- | --- | --- | --- |
| 모든 P0 R에 AC와 T | 예/아니오 | R 표, T 표 | 누락 AC/T를 2.1/2.3에서 추가 |
| 모든 P에 출처와 T | 예/아니오 | P 표, T 표 | 근거 또는 T를 추가 |
| H G의 A·되돌릴 지점 | 예/아니오 | G/A 표 | 질문 또는 A 보완 |
| 입출력 계약 | 예/아니오/해당 없음 | 10절 | 2.2 수행 또는 해당 없음 근거 |
| 기준선 기록 | 예/아니오/실행 불가 | BRIEF 환경 | 실제 결과 또는 사유 기록 |

동결 후 변경은 13절에 `시각 | 변경 | 이유·근거 | 영향` 행을 먼저 추가한 뒤, 영향받는 R/AC/P/A/G/T를 갱신하고 필요하면 2.4를 재실행하는 절차로 기록하라.

## 채팅 출력 형식

다음 순서로 보고하라.

1. 최종 상태: READY / READY-WITH-ASSUMPTIONS / BLOCKED와 판정 시각
2. 충족·미충족 체크리스트 수와 가장 큰 근거
3. 남은 A#/G#와 구현에 미치는 위험
4. 최소 다음 행동 1개와 담당자에게 필요한 확인 여부
5. READY 계열일 때 다음 단계: → 3.1 plan (`$sk-plan`)

## 완료 기준

- 0절에 허용된 상태 중 하나와 실제 판정 시각이 있다.
- 14절에 모든 핵심 체크 항목의 근거 위치와 최소 보완 행동이 있다.
- 상태가 실제 P0·P#·A/G·10절·11절·제출물·기준선 기록과 일치한다.
- READY-WITH-ASSUMPTIONS의 각 가정에는 되돌릴 지점·확인 계획이 있고, BLOCKED 원인은 숨기지 않았다.
- 동결 후 13절 변경 기록과 재게이트 조건이 명확하다.
- 다른 SPEC 절, 과제 코드, 테스트, 원본 데이터는 수정하지 않았다.

## 금지

- 체크하지 않은 항목을 예·통과·READY로 표시하지 마라.
- 시간 압박을 이유로 P0 AC/T, 필수 제출물, 되돌릴 수 없는 H 충돌을 무시하지 마라.
- 담당자에게 DM을 직접 보내거나 답변·공식 규칙을 만들어 내지 마라.
- 게이트 통과를 근거로 테스트가 실행됐거나 구현이 정확하다고 주장하지 마라.
- 과제 파일, 테스트, 데이터, 설정을 수정·삭제·실행하거나 외부 제출·배포·push·업로드를 하지 마라.
- 비밀값·개인정보·민감한 원본 데이터 값을 기록하지 마라.
