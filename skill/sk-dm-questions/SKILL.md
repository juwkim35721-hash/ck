# 담당자 DM 질문 설계
## 목적
구현 전에 고영향 정책을 업무 담당자에게 짧고 답하기 쉽게 확인한다.
담당자의 시간을 아끼면서도, 답변이 코드·테스트로 옮겨질 만큼 구체적인 선택지와 사례를 제공한다.
Codex는 DM을 보내지 않는다. 사용자가 복사해 우측 메신저에 보내고, 답변 원문을 다시 붙여 넣는다.

## 언제 쓰나 / 쓰지 않나
- `→ 1.2 ambiguity ($sk-ambiguity)`에서 `DM 질문`으로 분류된 H 또는 중요한 M `G#`가 있을 때 사용한다.
- 첫 질문 배치, 후속 질문, 구현 중 긴급 단일 질문, 예시 확인·충돌 확인·범위 확인 질문을 만들 때 사용한다(템플릿 4절 M01~M10).
- 문서·테스트에서 답을 찾을 수 없는 정책 공백에만 사용한다.
- 구현 방법, 라이브러리 선택, 평가·채점 방식, 내부 ID 자체를 묻는 용도로는 사용하지 않는다.
- 받은 답변의 보존·정책화는 `→ 1.4 dm-answers ($sk-dm-log)`가 담당한다.
- 스캔부터 후속 질문까지 라운드로 반복할 때는 `→ 1.0 clarify-loop ($sk-clarify-loop)`가 이 문구 규칙으로 DM을 만든다.

## 입력과 사전 확인
- `sk/work/DISCOVERY.md`의 `## 모호성 G`와 관련 R/C/제출물 후보를 읽는다.
- G마다 문서·샘플·테스트를 다시 확인해 이미 답이 있으면 질문 후보에서 뺀다.
- 담당자가 읽을 때 필요한 실제 조건·마스킹된 예시·선택지를 준비한다.
- `sk/templates/DM_QUESTION_TEMPLATES.txt`를 읽는다. 1절 공통 규칙 R1~R12, 2절 뼈대 S1·S2, 3절 범주별 패턴 P01~P14, 4절 상황별 형식 M01~M11, 6절 완성 예시 E1~E6, 9절 체크리스트를 쓴다.
- 3절 패턴 번호는 `sk-ambiguity`의 14개 범주와 같은 순서다. G에 적힌 범주(또는 `DM 질문(P07)` 같은 패턴 번호)로 바로 고른다.
- 템플릿 문장을 그대로 붙이지 말고, '채울 칸'을 현재 G의 대상·값·건수·선택지별 결과로 바꾼다.
- 사용자에게 DM 발송 권한이 있음을 전제하지 않는다. 복붙용 메시지까지만 만든다.

## 절차
1. **열린 G를 영향도순으로 정렬한다.** H 우선, 그다음 P0 결과를 바꾸는 M만 고려한다.
2. **자체 해결 여부를 재확인한다.** 공식 문서·최신 샘플·테스트에서 답을 찾았으면 질문을 제거하고 G 상태를 갱신한다.
3. **질문 효용을 평가한다.** 답이 구현·출력·데이터 손실·제출에 영향을 주고, 답변에 따라 행동이 달라질 때만 채택한다. 템플릿 1절 R10의 '묻지 않음'에 걸리면 버린다.
4. **형식을 고른다.** 템플릿 4절에서 지금 상황의 형식을 고른다: 첫 묶음 M01, 단일 M02, 부분 답 뒤 후속 M03, "상황에 따라" 뒤 M04, 예시 확인 M05, 문서 충돌 M06, 위임 뒤 기본안 알림 M07, 범위 확인 M08, 긴급 단일 M09, 동결 후 가정 확인 M10. 재진술(M11)은 `→ 1.5 dm-confirm ($sk-dm-confirm)`이 맡는다.
5. **G마다 패턴을 고른다.** G의 범주와 같은 번호의 3절 패턴(P01~P14)을 고르고, 문구 a/b/c 중 실제 빈칸에 맞는 것을 쓴다. 과제 유형이 비슷한 6절 완성 예시(E1~E6)를 참고한다.
6. **'채울 칸'을 실제 사실로 채운다.** 대상 이름, 값·건수(`data_audit.py` 수치 등), 선택지별 결과를 넣는다. 실제 값이 민감하면 `수량=-2`, `customerId=…`처럼 마스킹한다.
7. **한 묶음에 최대 세 질문만 넣는다.** 서로 독립적으로 `1-A, 2-B`로 답할 수 있게 한다.
8. **질문별로 한 정책만 묻는다.** 결측 처리와 정렬 기준을 한 번호에 섞지 않는다.
9. **상황을 한 줄로 쓴다.** 업무 목적을 짧게 말하되 내부 R/G/P ID나 파일 경로를 노출하지 않는다.
10. **서로 배타적인 선택지를 만든다.** A/B(/C)는 결과가 다르고 구현 가능한 동작이어야 한다.
11. **기본 제안과 이유를 한 줄로 쓴다.** 답이 없을 때 가장 안전하고 되돌리기 쉬운 안을 명시하고, 이유는 템플릿 8절 목록에서 한 가지만 고른다.
12. **열린 탈출구를 둔다.** “다른 기준이 있으면 알려주세요”를 질문마다, 또는 묶음 마지막 줄에 한 번 넣는다.
13. **답변 형식을 안내한다.** 끝에 “`1-A, 2-B`처럼 답해주셔도 됩니다.”를 넣는다.
14. **템플릿 9절 체크리스트를 통과시킨다.** 줄 수(인사 포함 12줄, 단일·긴급 6줄), 존댓말, 마스킹을 포함해 항목별로 확인하고, 걸리는 항목은 고친 뒤 다시 점검한다.
15. **DM_LOG에 먼저 기록한다.** M 번호, 사용한 패턴·형식 번호, 복붙용 최종 메시지, 질문 매핑을 남긴다.
16. **사용자에게 발송 행동을 분리해 안내한다.** “아래를 직접 DM으로 보내고 답변 원문을 붙여 주세요”라고 말한다.

### 질문 선별 규칙

| 우선 | 보내는 조건 | 예 |
| :--- | :--- | :--- |
| 즉시 H | 답에 따라 합계·상태·API·제출물이 달라짐 | 음수 수량 포함/제외/오류 |
| 먼저 H | 서로 충돌한 규칙의 우선순위가 필요함 | 승인 상태와 취소 상태 동시 |
| 선택 M | P0는 가능하지만 사용자 결과가 달라짐 | 동점 2차 정렬 키 |
| 보내지 않음 | 문서·테스트에 명확한 답이 있음 | README가 빈 배열을 명시 |
| 보내지 않음 | 내부 구현 선택 또는 평가 관련 질문 | 캐시 방식·채점 비중 |

### 메시지 해부도 (템플릿 2절 S1·S2)

1. 인사와 확인 목적 한 줄
2. 질문 번호와 현재 상황 한 줄
3. 실제 데이터·조건 예시 한 줄
4. A/B(/C) 선택지: 각각 관찰 가능한 동작
5. 기본 제안과 선택 이유 한 줄
6. “다른 기준이 있으면 알려주세요.” — 질문마다, 또는 묶음 마지막 줄에 한 번
7. 여러 질문이면 마지막 답변 형식 한 줄

선택지에는 “적절히 처리”처럼 해석이 갈리는 말을 쓰지 않는다.

### 현실적 질문 예시

과제 유형별 완성 예시는 템플릿 6절에 있다: E1 데이터 집계, E2 API·서버, E3 규칙 판정, E4 기존 기능 수정, E5 화면(UI), E6 답변 뒤 후속 라운드. 아래는 P02·P03을 단일 질문(M02)으로 쓴 예다.

```text
안녕하세요. 집계 결과의 입력 처리 기준을 확인 부탁드립니다.
수량이 비어 있거나 `-2`처럼 음수인 주문이 15건 있습니다. 어떻게 처리할까요?
A) 해당 주문을 제외하고 계속 집계  B) 요청 전체를 오류로 반환  C) 별도 상태로 결과에 포함
저는 잘못된 합계가 섞이지 않도록 A를 제안드립니다. 다른 기준이 있으면 알려주세요.
`A`처럼 답해주셔도 됩니다.
```

### 상황별 형식 (템플릿 4절)

| 형식 | 사용할 때 | 핵심 |
| :--- | :--- | :--- |
| M01 첫 질문 묶음 | 구현 전 H G가 2~3개 | 2~3문항, 답변 형식 포함 |
| M02 단일 | 의문이 하나이거나 시간이 5분 이내 | 1문항, 6줄 이내 |
| M03 후속 | 답변이 일부만 해결 | 이전 답 인용 1줄 + 남은 정책 하나 |
| M04 조건 묻기 | “상황에 따라”라는 답 | 문서에 있는 구분 중 나누는 조건만 |
| M05 예시 확인 | 규칙은 알지만 경계가 불명확 | “이 예시의 결과가 X인가요?” |
| M06 충돌 확인 | 문서와 답변이 다름 | 양쪽 인용 + 사례 + 확인 전 기본안 |
| M07 위임 알림 | “알아서 해 주세요” | 기본안 알림, 답을 요구하지 않음, A로 기록 |
| M08 범위 확인 | 질문이 넓어짐 | 영역 포함 여부 하나로 여러 G 정리 |
| M09 긴급 단일 | P0 구현이 막힘 | 선택지 + 결정 시점 + 되돌리기 쉬운 기본안 |
| M10 가정 확인 | 동결 후 가정으로 구현 중 | 현재 가정 + 맞음/아님 |
| M11 재진술 | 구현 직전 | `→ 1.5 dm-confirm ($sk-dm-confirm)`의 10줄 틀 |

## 판단 기준·분기

- H G가 4개 이상이면 답 하나로 함께 해소되는 것을 묶되, 세 문항을 넘기면 M2 등 다음 배치로 나눈다.
- 담당자가 선택지만 고르게 만들고 싶을 때도 “다른 기준” 문장을 남긴다.
- 답이 “상황에 따라”일 가능성이 크면 A/B보다 판단에 필요한 추가 필드·우선순위를 묻는다.
- 예시 하나의 답을 전체 정책으로 일반화하지 않는다. 일반화 범위를 확인할 후속 질문을 준비한다.
- H 가정이 남아도 대기만 하지 않는다. 되돌리기 쉬운 A로 문서화한 뒤 독립 작업을 한다.
- 답변이 오기 전 코드 구현은 하지 않는다. 이 단계에서는 분석·명세 준비만 한다.
- 5분밖에 없으면 H 한 건만 단일 DM으로 보내고, 나머지는 G/A로 보류한다.

### 답변을 기다리는 동안

- 공식 문서에서 질문과 독립적인 R/C를 더 추출한다: `→ 1.1 requirements ($sk-requirements)`.
- 데이터의 결측·범위·중복 사실을 읽기 전용으로 확인한다: `→ 1.2 ambiguity ($sk-ambiguity)`.
- 답변에 의존하지 않는 제출물 목록과 용어집 초안을 정리한다.
- 각 H G의 기본안, 위험, 되돌릴 지점을 A 후보로만 적는다. P로 승격하지 않는다.
- 답을 재촉하는 연속 DM을 보내지 말고, 새 H 충돌이 생긴 경우에만 후속 묶음을 만든다.

## 작업 노트 기록

`sk/work/DM_LOG.md`에 기존 기록을 보존하며 새 `## M<n> …` 블록을 추가한다. 예시는 다음과 같다.

```markdown
## M1 2026-..-.. 첫 질문 배치 — 발송 대기
- 목적: 구현 전 데이터·정렬 정책 확인
- 관련 G: G1, G3
- 선택 이유: H이며 P0 결과와 API 출력이 달라짐
- 사용 패턴·형식: P02, P05 / M01
- 발송자: 사용자 직접 DM 예정
- 메시지:
  [복붙용 최종 문구]
- 질문 매핑: M1-1 → G1, M1-2 → G3
- 답변 원문: (수신 후 원문 그대로 추가)
- 상태: 발송 대기
```

- `M<n>`은 기존 최대 번호 다음을 쓴다. 질문은 `M1-1`, `M1-2`처럼 식별한다.
- 발송 완료 시 사용자가 알려 준 사실만 `발송됨`으로 바꾼다. 보내지 않았으면 보냈다고 쓰지 않는다.
- 정책 목록은 여기서 만들지 않는다. 답변 수신 뒤 `sk-dm-log`가 `## 정책 목록 P`를 갱신한다.

## 채팅 출력 형식

1. DM 대상 G, 보내는 이유(H/M, 결과 영향), 사용한 템플릿 패턴·형식 번호
2. 복붙용 최종 메시지 1개를 `text` 코드블록으로 제시
3. 사용자가 직접 보내야 한다는 한 줄 안내
4. DM_LOG에 기록한 M 번호와 질문 매핑
5. 기다리는 동안 할 독립 작업 2~3개
6. 다음 행동: 답변 수신 시 `→ 1.4 dm-answers ($sk-dm-log)`

## 완료 기준

- 질문마다 상황, 실제 조건 예시, A/B(/C), 기본 제안·이유가 있고, 열린 대안 문장이 질문마다 또는 묶음 끝에 있다.
- 템플릿 9절 체크리스트를 모두 통과했고, 사용한 P·M 번호가 M 블록에 기록됐다.
- 한 메시지는 최대 3문항·12줄 이내이며 `1-A`식 답변 형식이 있다.
- 문서에 답이 있는 질문과 평가·채점 질문이 제거됐다.
- M 블록과 M#-n 매핑이 기록됐으며 사용자 발송과 Codex의 역할이 분리됐다.
- 답변 의존 작업과 독립 작업이 구분됐다.

## 금지

- Codex가 DM을 보냈다고 주장하거나 담당자 답변을 지어내지 않는다.
- 담당자에게 내부 R/G/P ID, 과도한 코드 용어, 여러 정책이 섞인 질문을 보내지 않는다.
- “어떻게 구현할까요?”, “채점은 어떻게 하나요?”를 묻지 않는다.
- 문서에 명확히 쓰인 내용, 이미 확정된 P, 같은 질문을 반복하지 않는다.
- 민감한 원본값·개인정보·비밀값을 메시지나 노트에 넣지 않는다.
