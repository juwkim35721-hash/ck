# API 계약 검증

## 목적

SPEC 10절의 메서드·경로·상태 코드·요청·응답·오류 계약을 실제 HTTP 호출로 대조한다.
먼저 제공 스니펫으로 한 URL의 도달성을 확인하고, 이어 정상·오류·기존 인터페이스 경로를 계약 기준으로 검증한다.
서버를 임의로 재구성하지 않고 실행 근거와 종료 절차를 E#에 남긴다.

## 언제 쓰나 / 쓰지 않나

- API, 백엔드, 웹 서버, CLI의 HTTP 엔드포인트가 P0 요구사항에 있을 때 쓴다.
- 4.2 구현 후, 5.1 요구사항 추적 전, 제출 직전 최신 서버 상태 확인에 쓴다.
- 데이터 파일의 집계 정합성은 → 5.3 data-validation ($sk-data-validation)이 맡는다.
- 화면 상호작용·문구·상태 표시는 → 5.5 ui-smoke ($sk-ui-smoke)로 넘긴다.
- 이 스킬은 API 구현·라우팅·서버 설정을 수정하거나 포트·호스트를 임의 변경하지 않는다.

## 입력과 사전 확인

1. `sk/work/SPEC.md`의 10절 API 계약, 5절 P, 11절 T를 읽는다.
2. `sk/work/BRIEF.md`의 `## 환경`에서 공식 서버 시작 명령, 지정 포트·호스트, 종료 방법을 확인한다.
3. 기존 API·헬스 경로와 변경 전 인터페이스가 있으면 `sk/work/BRIEF.md`의 코드 지도와 테스트를 확인한다.
4. 인증·외부 네트워크·실제 데이터가 필요한지 확인하고 규칙·사용자 허가 없이는 호출하지 않는다.
5. 요청 본문·응답에 민감 값이 들어갈 수 있으면 안전한 테스트 값과 마스킹 방법을 정한다.

## 절차

1. 계약 체크 표를 준비한다.
   `T# | 메서드 | 경로 | 요청 조건 | 기대 상태 | 필수 응답 필드·타입 | 오류 규칙 | P# 근거` 열로 P0 엔드포인트를 적는다.
2. 서버 시작 명령을 확인한다.
   과제 안내와 `BRIEF.md`에 있는 명령만 사용한다.
   웹 서버는 내장 Browser 미리보기를 위해 지정 포트로 `0.0.0.0`에 바인딩해 띄운다(과제 문서가 다르게 정하면 그 요구를 따른다). 요청은 같은 환경의 `127.0.0.1`로 보내고, 포트는 바꾸지 않는다.
3. 서버를 한 번 시작하고 준비 상태를 확인한다.
   콘솔의 실제 시작 메시지와 프로세스 식별 정보를 짧게 기록한다.
   서버가 이미 실행 중이면 중복 시작하지 말고 소유자·포트·현재 URL을 확인한다.
4. 도달성 1차 확인을 실행한다.
```bash
python3 sk/snippets/smoke_test.py http://127.0.0.1:<포트>/<경로>
```
   이 스니펫은 인자로 받은 URL에 GET 한 번만 보내고, 2xx면 성공으로 판단한다.
   타임아웃은 5초이고 본문은 120자만 출력하며 실패 시 종료 코드 1이므로 계약 완전 검증으로 오해하지 않는다.
5. 도달성 실패를 분리한다.
   연결 실패면 서버 로그·포트·공식 시작 명령을 확인하고, HTTP 4xx/5xx면 응답 본문·상태를 실제 결과로 보존한다.
   임의 재시작·포트 변경·방화벽 변경은 하지 않는다.
6. 정상 경로를 계약별로 호출한다.
   과제 테스트 클라이언트가 있으면 우선 사용하고, 없으면 `curl` 또는 언어 표준 HTTP 도구로 메서드·경로·헤더·본문을 명시한다.
```bash
curl -i -X <메서드> http://127.0.0.1:<포트>/<경로> \
  -H 'Content-Type: application/json' \
  --data '<안전한_JSON_본문>'
```
   HTTP 상태, 필수 필드 존재, 타입 표현, 값, 정렬, null·빈 결과 표현을 SPEC 10절과 대조한다.
7. 오류 경로를 계약별로 호출한다.
   누락 필수 필드, 잘못된 타입, 존재하지 않는 리소스 중 T#에 정의된 입력만 쓴다.
   기대한 상태 코드와 오류 본문의 키·메시지 범위를 확인하고 500을 정상 오류로 해석하지 않는다.
8. 기존 인터페이스 유지 여부를 확인한다.
   기존 테스트·문서에 있던 메서드·경로·필수 필드가 현재도 동작하는지 최소 한 건 확인한다.
   의도된 호환성 변경이 문서화되지 않았다면 FAIL 또는 G# 후보로 둔다.
9. 응답 스키마를 독립적으로 읽는다.
   성공·오류 응답에서 필드 누락, 추가 필드, 타입 변화, 날짜·숫자 형식, 순서에 의존하는 클라이언트 위험을 확인한다.
10. 모든 호출을 E#로 기록한다.
    URL의 민감 쿼리·토큰은 마스킹하고 → 5.2 evidence ($sk-evidence) 표에 T#, 기대, 실제 상태·핵심 필드, 판정, 코드 상태를 남긴다.
11. 서버 종료 책임을 확인한다.
    이 세션에서 시작했고 더 이상 필요 없으면 과제 안내의 정상 종료 방법으로 정리한다.
    다른 세션이 시작한 서버는 종료하지 않고 상태만 보고한다.
12. 다음 행동을 고른다.
    계약 불일치는 요청·응답·E#를 붙여 → 6.1 debug ($sk-debug)로, 계약 모호성은 → 2.2 io-contract ($sk-data-contract) 또는 → 1.3 dm-questions ($sk-dm-questions)로 넘긴다.

## 판단 기준·분기

- if smoke_test.py가 2xx다 → 도달성 PASS일 뿐 메서드·스키마·오류 계약 PASS는 아니다.
- if smoke_test.py가 비0이다 → 출력의 연결 실패인지 HTTP 상태 불일치인지 분리해 기록한다.
- if endpoint가 POST/PUT/PATCH/DELETE만 지원한다 → GET 스모크 대상은 건강 확인 URL 또는 공식 GET 경로로 잡고, 해당 메서드는 별도 호출한다.
- if 인증이 필요하다 → 실제 비밀 토큰을 출력·기록하지 않고 공식 테스트 자격·허가가 없으면 미검증으로 둔다.
- if 서버 시작 실패다 → 실패 출력과 명령을 E#로 기록하고 코드 수정 대신 → 6.1 debug ($sk-debug)로 넘긴다.
- if 응답 상태는 맞지만 필드 타입·빈 결과·오류 형식이 다르다 → FAIL이다.
- if 시간이 부족하다 → P0의 건강 확인 1건, 정상 1건, 오류 1건, 기존 인터페이스 1건을 최소 경로로 실행한다.

## 작업 노트 기록

`sk/work/EVIDENCE.md`의 `## 실행 기록`에 서버 시작과 의미 있는 HTTP 검증마다 E# 행을 추가한다.
표 열은 `E# | 시각 | 명령·작업 디렉터리 | 대상 R/T | 기대 | 실제 결과 요약 | 판정 | 코드 상태`다.

실제 결과 요약에는 `GET /health → 200, body에 status 문자열`, `POST /items → 400, error 키 존재`처럼 상태·필수 필드만 적는다.
URL의 토큰, 인증 헤더, 전체 본문, 실제 개인정보는 기록하지 않는다.

R/T가 확인되면 `sk/work/SPEC.md`의 `## 12. 추적표`에서
`R | AC | T | 구현 위치 | 증거 E | 상태` 중 증거 E·상태를 실제 결과로 갱신한다.

## 채팅 출력 형식

1. `서버 조건`: 실제 시작 명령, 호스트·포트, 이미 실행 중 여부와 종료 책임.
2. `도달성`: 스모크 URL, 종료 코드, HTTP 상태, 스니펫의 제한.
3. `계약 대조`: T#별 메서드·경로·기대/실제 상태·스키마·오류 형식 표.
4. `호환성`: 기존 인터페이스 확인 결과 또는 미검증 사유.
5. `증거·판정`: E#, PASS·FAIL·미검증과 코드 상태.
6. `다음 행동`: 디버그 또는 명세·DM 인계 ID와 스킬.

## 완료 기준

- 공식 실행 조건으로 서버를 확인했고, 도달성 스모크 결과가 있다.
- P0 API마다 정상 경로와 적용되는 오류 경로가 계약과 대조됐다.
- 메서드·경로·상태 코드·필수 응답 필드·오류 형식을 따로 확인했다.
- 기존 API가 있으면 최소 하나의 호환성 경로를 실제로 확인했다.
- E#에 실제 명령·결과·코드 상태와 서버 종료 책임이 남아 있다.
- 실패와 실행 불가는 FAIL 또는 미검증으로 투명하게 남겼다.

## 금지

- 2xx GET 한 번을 API 전체 계약 통과로 선언하지 않는다.
- 과제 요구 없이 호스트·포트·CORS·환경변수·라우팅을 바꾸지 않는다.
- 실제 사용자 데이터, 토큰, 인증 헤더, 비밀값을 요청·응답·EVIDENCE에 기록하지 않는다.
- 과제 규칙·사용자 허가 없이 네트워크 서비스나 외부 API를 호출하지 않는다.
- 다른 사람이 시작한 서버를 종료하거나 서버·코드를 이 스킬에서 수정하지 않는다.
- 실패를 숨기려고 요청·응답 검사를 약화하거나 테스트를 삭제하지 않는다.
