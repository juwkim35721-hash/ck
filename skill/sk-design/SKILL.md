# 최소 설계·대안 비교

## 목적

첫 구현 슬라이스에 필요한 최소 구조를 선택하고, 선택하지 않은 대안과 근거를 DD#으로 남긴다.

입력 → 검증 Guard → 핵심 도메인 로직 → 출력·오류 스키마의 흐름을 실제 코드 기준으로 그린다.

이 스킬은 설계와 읽기 전용 분석만 한다. 과제 코드, 테스트, 데이터, 설정은 수정하지 않는다.

## 언제 쓰나 / 쓰지 않나

- `3.1 plan ($sk-plan)`에서 첫 S#와 시간 상한이 정해진 뒤 사용한다.
- 새 기능의 경계, 기존 인터페이스 보존, 오류 처리 위치, 호출자 영향이 불명확할 때 사용한다.
- 구현 중 설계 선택이 바뀌면 → `3.3 decision-log ($sk-decision-log)`으로 짧게 기록하고 필요 시 이 스킬로 돌아온다.
- SPEC에 P0·AC·T가 없거나 입출력 계약이 비면 → `2.1 spec ($sk-spec)`, `2.2 io-contract ($sk-data-contract)`, `2.3 acceptance ($sk-acceptance)`을 먼저 쓴다.
- 단순히 정해진 S#을 코딩하는 일은 → `4.1 test-first ($sk-test-first)`와 `4.2 implement ($sk-implement)`의 책임이다.
- 광범위한 재설계, 신규 프레임워크 도입, 새 패키지 설치는 이 해커톤의 최소 설계 범위가 아니다.

## 입력과 사전 확인

1. `sk/work/SPEC.md`의 1~12절에서 대상 R#/AC/P#/A#/C#/T#만 추린다.
2. `sk/work/PLAN.md`의 `## 슬라이스 S`, `## 위험 실험`, `## 시간 예산`에서 현재 S#의 범위를 확인한다.
3. `sk/work/BRIEF.md`의 코드 지도와 실행 기준선을 읽는다.
4. `sk/work/DM_LOG.md`의 P# 원문 근거와 열려 있는 G#를 확인한다.
5. 실제 과제에서 관련 진입점·호출자·테스트를 읽기 전용으로 찾는다.

```bash
rg -n "<함수명>|<경로>|<응답 필드>" --glob '!sk/**' .
find . -path './sk' -prune -o -type f -print | sort
```

6. 필요하면 다음으로 변경 범위만 관찰한다. 출력에는 민감값을 포함하지 않는다.

```bash
git status --short
git diff --stat
```

7. `sk/`은 과제 코드가 아니므로 설계 대상, 테스트 대상, 변경 후보에서 제외한다.

## 절차

1. 현재 흐름을 한 줄씩 적는다: 입력 출처 → 현재 검증 → 변환·상태 변경 → 출력 또는 오류 → 호출자.
2. 각 화살표에 실제 파일·함수·관찰 근거를 붙이고, 모르면 `미확인`으로 남긴다.
3. 보존할 공개 인터페이스를 정한다: 함수 시그니처, API 메서드·경로·상태 코드, 출력 스키마, 설정 키, 기존 테스트 기대값이다.
4. 변경해야 하는 곳을 한 S#에 필요한 최소 파일·함수로 제한한다.
5. 대안 A는 기존 흐름과 호출자를 가장 많이 보존하는 최소 변경안으로 만든다.
6. 대안 B는 A가 R#/P#/C# 또는 오류 계약을 충족하지 못할 때만 필요한 국소 확장안으로 만든다.
7. 두 대안을 같은 기준으로 비교한다: 요구 충족, 변경 범위, 호출자 영향, 테스트 용이성, 실패 처리, 위험, 시간, 되돌림이다.
8. 증거 없는 비교 칸은 추측으로 채우지 않고 `미확인`과 확인 방법을 적는다.
9. 선택안에서 Guard 위치, 핵심 도메인 로직 위치, 출력·오류 변환 위치를 분리한다.
10. Guard는 입력 경계에 두고, 근거 없는 업무 정책은 넣지 않는다. 새 정책 필요 시 G#로 등록한다.
11. 영향을 받는 호출자와 기존 테스트를 열거하고, 호환이 깨질 가능성이 있으면 즉시 위험으로 표시한다.
12. 선택을 DD#으로 기록하고, 첫 구현 순서를 `테스트 → 최소 구현 → 관련 검증`으로 정한다.
13. 설계 산출물을 → `4.1 test-first ($sk-test-first)`에 대상 T#와 보존 인터페이스로 인계한다.

### 최소 경로 — 시간이 없을 때

1. S# 하나만 고르고, 현재 입력→출력 흐름 4칸을 파일·함수 이름과 함께 적는다.
2. 최소 변경안 A와 필요한 경우의 B를 표의 5개 기준으로 비교한다.
3. Guard·도메인·출력의 위치와 보존할 인터페이스를 한 줄씩 적는다.
4. DD# 하나를 기록하고 → `4.1 test-first ($sk-test-first)`로 넘긴다.

## 판단 기준·분기

- **if** A가 모든 대상 R#/P#/C#를 충족하고 공개 계약을 보존한다 **then** A를 선택한다. 더 일반적인 구조를 추가하지 않는다.
- **if** A가 특정 요구를 충족하지 못한다 **then** 그 요구와 실패 모드를 명시한 B만 비교한다.
- **if** B가 새 패키지·새 프레임워크·다수 호출자 변경을 요구한다 **then** 시간·규칙 허용 여부를 확인하고, 대개 A 또는 범위 축소를 우선한다.
- **if** 출력 스키마나 오류 상태가 바뀐다 **then** 모든 호출자·T#·SPEC 10절을 확인한다. 호환 방안이 없으면 구현을 멈추고 G#로 남긴다.
- **if** P#와 현재 코드 관찰이 충돌한다 **then** P#를 임의로 무시하지 말고 G#와 → `1.4 dm-answers ($sk-dm-log)` 또는 `1.3 dm-questions ($sk-dm-questions)`을 제안한다.
- **if** A#가 설계 선택을 바꾼다 **then** 되돌릴 파일·함수 경계와 확인 시점을 DD#에 포함한다.
- **if** 코드 지도가 오래되었거나 호출자를 찾지 못한다 **then** → `0.3 code-map ($sk-code-map)`으로 읽기 전용 지도를 보완한다.
- **if** 설계 중 새로운 위험이 10분 이상 걸린다 **then** `PLAN.md` 위험 실험으로 되돌려 시간 상한을 정한다.

## 작업 노트 기록

`sk/work/DECISIONS.md`에서 기존 결정과 `## AI 교정 기록`을 보존한다. 새 결정은 다음 형식의 독립 블록으로 추가한다.

```markdown
## DD<n> <짧은 결정 제목>
- 시각·대상 S#: <시각> · S<n>
- 상황: <어떤 R/P/C 또는 인터페이스 문제가 있었는가>
- 선택지: A) <최소 변경안> / B) <국소 확장안>
- 선택: <A 또는 B>
- 근거: <R#/P#/C#/T#, 코드 파일:함수, 시간 근거>
- 포기한 것·트레이드오프: <채택하지 않은 범위와 이유>
- 영향: <수정 후보 파일·함수, 보존할 호출자·인터페이스>
- 되돌림·검증: <되돌릴 경계, T# 또는 E# 계획>
```

- `DD<n>`은 기존 번호보다 큰 새 번호를 사용한다. 삭제·번호 재사용을 하지 않는다.
- 설계 근거는 관찰 사실과 A#를 구분한다. 미실행 테스트를 E#로 쓰지 않는다.
- `## AI 교정 기록`은 이 스킬의 주 기록 대상이 아니다. 구현 중 교정은 → `3.3 decision-log ($sk-decision-log)`에 맡긴다.

## 채팅 출력 형식

다음 순서로 보고한다.

1. 대상: S#, R#/P#/C#/T#, 남은 시간, 설계 전제.
2. 현재 흐름: 입력 → Guard → 도메인 → 출력/오류를 파일·함수와 함께 제시한다.
3. 보존 경계: 공개 인터페이스·호출자·테스트 기대값을 적는다.
4. 대안 비교 표: A/B의 요구 충족·변경 범위·테스트·위험·시간·되돌림을 같은 열로 비교한다.
5. 선택 DD#: 선택 이유, 포기한 것, 최소 구현 순서를 적는다.
6. 위험·중단 게이트: G#/A#와 확인 행동을 적는다.
7. 다음 단계: → `4.1 test-first ($sk-test-first)`를 한 줄로 제안한다.

## 완료 기준

- 대상 S#의 입력부터 출력·오류까지 실제 파일·함수 근거가 있다.
- A/B가 같은 비교 기준으로 제시되고 선택이 R#/P#/C#/시간에 연결된다.
- Guard, 핵심 로직, 출력·오류 경계와 보존 인터페이스가 분명하다.
- 영향 호출자, 관련 T#, 되돌릴 경계가 빠지지 않았다.
- `DECISIONS.md`에 DD#이 추가되었고 다음 구현 순서가 작다.
- 과제 코드·테스트·데이터·설정은 수정하지 않았다.

## 금지

- 설계 단계에서 과제 파일을 수정하거나 테스트를 새로 작성하지 않는다.
- 과잉 추상화, 전면 재작성, 새 의존성, 근거 없는 성능 최적화를 기본안으로 삼지 않는다.
- 공식 문서·P#·관찰 코드보다 A#를 우선하지 않는다.
- 확인되지 않은 업무 규칙을 Guard·기본값·오류 메시지로 고정하지 않는다.
- 기존 API·스키마·설정·공용 유틸의 변경 영향을 숨기지 않는다.
- 외부 push, 배포, 제출, 업로드, 자격증명 전송을 실행하지 않는다.
- 민감 원본값이나 비밀값을 결정 기록에 남기지 않는다.
