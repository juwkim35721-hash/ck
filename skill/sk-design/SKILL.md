# 최소 설계 비교

## 역할

구현하지 말고 실제 코드와 확인된 요구사항을 근거로 최소 변경 설계를 결정하라.
실제 과제 루트와 공식 안내를 먼저 확인하고 AI 사용 허용 여부를 지켜라.

## 입력

다음 입력을 확보하라.

- 실제 과제 루트·남은 시간·요구사항 ID·정책 답변·입출력 계약·허용 수정 범위
- 관련 진입점, 호출자, 테스트, 데이터 원본의 경로

입력이 없으면 읽기 전용으로 확인하라.
선택을 바꾸는 정보만 짧게 질문하고, 미응답 정책을 확정하지 말라.

## 절차

1. 관련 진입점과 호출자를 읽고 현재 입력→변환→출력 흐름을 요약하라.
2. 선택안의 흐름을 `입력 → 검증 Guard → 핵심 도메인 로직 → 출력/오류 스키마`로 명시하되, 현재 코드와 제안 구조를 구분하라.
3. 기존 공개 인터페이스, 데이터 원본, 수정 금지 영역을 목록화하라.
4. A안을 기존 구조와 호출자를 유지하는 최소 변경안으로 정의하라.
5. B안을 A안이 확인된 요구사항을 충족하지 못할 때만 필요한 국소 확장안으로 정의하라.
6. 전면 재작성, 새 프레임워크, 불필요한 추상화는 후보에서 제외하라.
7. 두 안을 요구사항 충족, 수정 파일, 인터페이스 영향, 실패 처리, 복잡도, 시간, 테스트, 롤백으로 비교하라.
8. 증거가 없으면 사실처럼 쓰지 말고 ‘미확인’과 확인 방법을 함께 적어라.
9. 기존 API나 스키마 변경이 불가피하면 영향 호출자와 호환·되돌림 방법을 명시하라.
10. 입력 처리→핵심 변환→출력 연결→관련 테스트의 최소 수직 순서를 제시하라.

## 분기와 중단

정책 답변 또는 데이터 계약이 선택을 바꾸면 구현으로 진행하지 말고 확인 단계로 되돌려라.
A안이 요구사항을 충족하면 B안을 선택하지 말라.
B안의 추가 경계·상태·의존성이 필수임을 증명하지 못하면 A안을 유지하라.
남은 시간 안에 검증 가능한 수직 흐름을 만들 수 없으면 범위 축소를 요청하라.
공식 지침이 없거나 후속 AI 금지 서술형이 시작되면 즉시 사용을 중단하라.

## 출력 형식

다음 제목으로 간결히 보고하라.

- 현재 흐름: 근거가 된 파일·함수, 데이터 방향, 검증 경계
- 대안 비교: A/B별 장점·제약·영향·검증·롤백
- 선택: 선택안과 요구사항·호출자에 연결한 근거
- 최소 구현 순서: 파일별 책임과 첫 수직 슬라이스
- 위험과 게이트: 미확인 사항, 확인 방법, 중단·되돌림 조건

## 완료 기준

두 대안이 동일 기준으로 비교되고 하나가 근거와 함께 선택되어야 한다.
수정 파일·보존 인터페이스·실패 경로·롤백 지점이 명시되어야 한다.
구현 전 확인할 검증과 선택을 뒤집을 조건이 남아 있어야 한다.

## 금지 행동

이 단계에서 파일을 수정하거나 테스트 결과를 만들지 말라.
제공되지 않은 공식 규칙, 채점 방식, 데이터 의미를 추정하지 말라.
기존 호출자·API·스키마를 편의상 깨거나 원본 데이터·테스트를 삭제하지 말라.
실패를 기본값으로 숨기거나 근거 없는 완료 선언을 하지 말라.
