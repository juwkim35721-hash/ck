# 구현 루프 — 슬라이스 하나를 RED→GREEN→방어→검증까지

## 목적

- `sk/work/PLAN.md`의 슬라이스 S# 하나를 **착수 점검 → RED → GREEN → 방어 → 검증·증거 → 판정**까지 한 번의 호출로 진행한다.
- 단계마다 게이트(다음 단계로 넘어가는 조건)를 확인하고, 멈춤 조건이면 진행하지 않고 원인과 다음 행동을 보고한다.
- `## 구현 루프 상태판`에 슬라이스별 진행·증거·소요 시간을 남겨, 세션이 바뀌어도 이어 가고 30분 재계획에 쓸 수 있게 한다.
- 이 스킬은 4.1~5.5의 진행자다. 각 단계의 세부 규칙은 아래 원본 스킬의 해당 절을 읽어 그대로 따른다.
  - 실패하는 테스트 작성·RED 분류: `sk/skill/sk-test-first/SKILL.md`
  - 최소 구현·인터페이스 보존: `sk/skill/sk-implement/SKILL.md`
  - 관련 엣지 케이스 방어: `sk/skill/sk-harden/SKILL.md`
  - 정상·경계·실패 경로 검증: `sk/skill/sk-verify/SKILL.md`, 증거 형식: `sk/skill/sk-evidence/SKILL.md`
  - 과제 유형별 검증: `sk/skill/sk-data-validation/SKILL.md`, `sk/skill/sk-api-contract/SKILL.md`, `sk/skill/sk-ui-smoke/SKILL.md`

## 언제 쓰나 / 쓰지 않나

- 2.4 spec-gate가 `READY` 또는 `READY-WITH-ASSUMPTIONS`이고, 3.1 plan이 슬라이스 표를 만든 뒤 쓴다.
- "S2 진행", "다음 슬라이스"처럼 슬라이스 하나를 끝까지 돌리고 싶을 때 쓴다. 연속 모드에서는 P0 슬라이스를 순서대로 이어 간다.
- 멈춘 슬라이스를 디버그·되돌림 뒤 다시 이어 갈 때, 담당자 답이 가정과 달라 슬라이스를 다시 돌릴 때 쓴다.
- 한 단계만 다시 할 때는 해당 스킬을 직접 쓴다: `→ 4.1 test-first ($sk-test-first)`, `→ 4.2 implement ($sk-implement)`, `→ 4.3 harden ($sk-harden)`, `→ 5.1 verify ($sk-verify)`.
- 원인 모를 실패의 분석은 `→ 6.1 debug ($sk-debug)`, 슬라이스 분할·재계획은 `→ 3.1 plan ($sk-plan)`, 명세 수정은 `→ 2.1 spec ($sk-spec)`이 맡는다. 이 루프는 하지 않는다.

## 입력과 사전 확인

- 대상: 사용자가 준 S#. 없으면 `## 슬라이스 S`에서 상태가 `진행`인 행, 없으면 P0 중 첫 `대기` 행을 고르고 그 선택을 출력에 밝힌다.
- 모드: `자동`(기본) / `확인` / `빠른` / `연속`. 아래 "진행 모드" 표를 따른다.
- 읽을 노트: `sk/work/PLAN.md`(`## 구현 루프 상태판`, `## 슬라이스 S`, `## 시간 예산`), `sk/work/SPEC.md`(0절, Top 5, 3~6절, 10~12절), `sk/work/BRIEF.md`(`## 환경`의 실행·테스트 명령, 기준선), `sk/work/DECISIONS.md`, `sk/work/EVIDENCE.md`.
- 상태판에 이 S#의 기록이 있으면 마지막으로 끝난 단계 다음부터 이어 간다. 이미 `완료`면 다시 돌리지 않고 이유를 묻는다.
- 현재 시각과 남은 시간을 확인한다. 모르면 한 줄로 묻고, 답이 없으면 MASTER_GUIDE 3절 시간표(구현 10:50–12:00, 리뷰 12:00)를 기준으로 한다.
- 과제 루트 `AGENTS.md`는 `SK-KIT:BEGIN`~`SK-KIT:END` 관리 구역 밖만 과제 지시로 본다.

## 진행 모드

| 모드 | 멈추는 곳 | 쓰는 때 |
| :--- | :--- | :--- |
| 자동 (기본) | 멈춤 조건에서만 | 일반 슬라이스 |
| 확인 | 단계 0 선언 뒤, 단계 1 RED 뒤에 사용자 승인 대기 + 멈춤 조건 | 담당자 정책·가정이 얽힌 슬라이스, 처음 보는 코드, 설명할 수 있어야 하는 핵심 로직 |
| 빠른 | 멈춤 조건에서만 | 남은 시간 부족. 단계 1은 P0 정상 1건 + 가장 위험한 경계 1건, 단계 3은 장애 영향이 큰 1건, 단계 4는 P0 정상 경로 + 전체 스위트만 |
| 연속 | 슬라이스 판정마다 한 줄 보고, `완료`가 아니면 즉시 중단 | P0 슬라이스를 순서대로 진행. 사용자가 정한 개수(기본 2개)까지만 |

- 확인 모드에서 사용자가 테스트 기대값·설계를 고치게 하면, 그 지적이 AI 초안의 실제 오류일 때 `## AI 교정 기록`에 AI#로 남긴다.

## 절차

### 단계 0 — 착수 점검 (읽기만, 3분 이내)

1. 아래 6개를 확인한다. 하나라도 아니면 멈추고 해당 단계로 넘긴다.

| 점검 | 통과 조건 | 아니면 |
| :--- | :--- | :--- |
| 명세 상태 | SPEC 0절이 `READY` 또는 `READY-WITH-ASSUMPTIONS` | `→ 2.4 spec-gate ($sk-spec-gate)` |
| 슬라이스 행 | S#에 대상 R/AC/P, 최소 변경 경계, 검증 T가 있고 선행 S#가 `완료` | `→ 3.1 plan ($sk-plan)` |
| 테스트 기준 | 대상 T#마다 입력·기대 출력·기대값 근거가 SPEC 11절에 있음 | `→ 2.3 acceptance ($sk-acceptance)` |
| 실행 명령 | BRIEF `## 환경`에 테스트 명령과 기준선(기존 실패 목록 포함)이 있음 | `→ 0.1 context ($sk-context)` |
| 설계 | 공개 인터페이스·여러 파일을 건드리면 이 S#의 DD#가 있음 | `→ 3.2 design ($sk-design)` 최소 경로 후 재개 |
| 시간 | 상한 = PLAN 배정 시간, 없으면 20분. 리뷰 시작 전 끝낼 수 있음 | `→ 6.5 timebox ($sk-timebox)` |

2. 슬라이스를 선언한다: `S# / R# / AC / T# / 적용 P#·A# / 후보 파일 / 보존 인터페이스 / 상한(분)`.
3. 시작 상태를 남긴다. 이후 변경이 이 슬라이스의 것인지 구분하는 기준이다.

```bash
git rev-parse --short HEAD 2>/dev/null; git status --short; git diff --stat
```

4. 상태판에 S# 행을 만들고 `단계: 착수`로 둔다. PLAN 슬라이스 표의 상태를 `진행`으로 바꾼다.

### 단계 1 — RED (sk-test-first 규칙)

1. 대상 T#를 P0부터 1~3개 골라 기존 테스트 프레임워크·위치·명명 관례로 작성한다. 기대값은 SPEC 11절의 손계산 값을 쓴다. 구현을 실행해서 기대값을 만들지 않는다.
2. 추가한 테스트만 실행하고 E#로 기록한다. 결과를 `RED-미구현` / `FAIL-설정` / `이미 통과`로 분류한다.
3. `FAIL-설정`(import·탐색·fixture·환경 오류)은 테스트 쪽 설정만 고쳐 1회 재실행한다. 그래도 실패하면 멈춘다.
4. `이미 통과`면 assertion이 약하거나 대상 호출이 틀렸는지 먼저 본다. 정말 충족되면 해당 T#를 `기존 충족`으로 적고 단계 3으로 간다.
- **게이트 R**: 모든 대상 T#가 `RED-미구현` E# 또는 근거 있는 `기존 충족`을 가진다.

### 단계 2 — GREEN (sk-implement 규칙)

1. 입력 경계·핵심 규칙·출력 변환 중 가장 작은 수정 지점을 고른다. P#의 "조건 → 동작"이 코드 조건과 한눈에 대응되게 쓴다. A#를 적용한 위치는 되돌릴 지점으로 상태판 메모에 적는다.
2. 대상 테스트 → 영향받는 기존 테스트 순으로 실행하고 E#로 기록한다.
3. 실패하면 원인 가설 하나를 세우고 고친다. **같은 실패에 수정 2회**가 넘으면 멈춘다.
4. 변경 파일이 단계 0의 후보 파일 밖으로 나가면 멈추고 이유를 보고한다.
- **게이트 G**: 대상 T# GREEN, 기준선에 없던 실패 0건, 보존 인터페이스(서명·경로·상태 코드·출력 스키마) 유지.

### 단계 3 — 방어 (sk-harden 규칙)

1. 이 슬라이스에 해당하는 위험만 1~3개 고른다(빠른 모드는 1개). 범주는 결측·빈 값, 타입 오염, 경계·0, 중복·멱등, 동점 정렬, 빈 결과, 권한·상태 전이, 바인딩·경로다.
2. 각 위험을 최소 재현으로 확인한다. 기대 동작의 근거가 P#/A#/C#에 있을 때만 방어하고 회귀 T#를 추가한다.
3. 근거가 없으면 막지 않는다. G 후보(상황 · 결과가 달라지는 예시 · 영향 R)로 적고 계속한다.
- **게이트 H**: 추가한 방어 테스트와 관련 기존 테스트가 통과하고, 출력 스키마·정렬이 바뀌지 않았다.

### 단계 4 — 검증과 증거 (sk-verify · sk-evidence 규칙)

1. 대상 R의 정상 → 경계 → 실패 경로를 T# 입력으로 실행한다.
2. BRIEF의 전체 테스트 명령을 한 번 실행하고 통과·실패·건너뜀 수를 기준선과 비교한다.
3. 과제 유형별 검증을 덧붙인다(세부는 5.3 · 5.4 · 5.5 스킬).

```bash
python3 sk/snippets/data_audit.py <결과_파일>                    # 데이터 과제: 결과 건수·결측을 원본과 대조
python3 sk/snippets/smoke_test.py http://127.0.0.1:<포트>/<경로>  # API·UI 과제: 서버를 띄운 상태에서
```

4. 이 슬라이스 때문에 바뀐 코드에 걸린 이전 E#는 `STALE — `를 붙이고 다시 실행한다.
5. SPEC 12절 추적표의 대상 R 행을 실제 근거로만 `PASS` / `FAIL` / `미검증`으로 갱신한다.
- **게이트 V**: 대상 R이 독립 기대값 근거와 함께 `PASS`이고, 전체 스위트에 기준선 대비 새 실패가 없다.

### 단계 5 — 판정과 인계

1. 아래 판정표로 슬라이스를 판정하고 PLAN 슬라이스 표의 `완료 증거`·`상태`를 갱신한다.
2. 결정이 있었으면 DD#, AI 초안의 오류를 사람이 교정했으면 AI#를 `sk/work/DECISIONS.md`에 남긴다.
3. **슬라이스 설명 3문장**을 쓴다: ① 입력 → 적용 규칙(P#/A#) → 출력, ② 왜 이 위치(파일·함수)를 고쳤는가, ③ 무엇으로 검증했는가(T#·E#). 9.1 understand와 후속 6문항 대비의 재료다.
4. 이번 루프에서 생긴 G 후보와 가정에 의존한 항목을 모아 `→ 1.0 clarify-loop ($sk-clarify-loop)` 병행 라운드 입력으로 넘긴다.
5. 다음 행동을 하나로 정한다: 다음 S#, 멈춘 원인의 해당 단계, 또는 모든 P0 완료 시 `→ 7.1 review ($sk-review)`.

## 판단 기준·분기

### 슬라이스 판정표

| 판정 | 조건 | PLAN 상태 | 다음 |
| :--- | :--- | :--- | :--- |
| 완료 | 게이트 R·G·H·V 모두 통과 | 완료 | 다음 S# |
| 완료-가정 | 완료와 같으나 결과가 H 영향 A#에 의존 | 완료 | 다음 S# + 그 A#를 병행 라운드 우선 질문으로 |
| 부분 | P0 정상 경로는 PASS, 경계·방어 일부가 시간·정책 때문에 미검증 | 진행 | 남은 T#와 이유를 적고 사용자 선택(계속 / 다음 S#) |
| 막힘 | 멈춤 조건 발생 | 막힘 | 아래 멈춤 조건의 해당 단계 |
| 분할 | 상한 초과, 후보 파일 밖으로 확장, T# 4개 이상 필요 | 보류 | `→ 3.1 plan ($sk-plan)`으로 S#a·S#b 분할 |
| 재작업 | 담당자 답이 가정과 달라 P#가 바뀜 | 진행 | 변경된 T#부터 단계 1로 다시 |

### 멈춤 조건 (이 중 하나면 즉시 멈추고 보고한다)

1. 단계 0 점검 중 하나라도 통과하지 못했다.
2. P#/A#/계약으로 기대 동작을 정할 수 없다. 새 정책을 코드에 넣지 말고 G 후보를 `→ 1.0 clarify-loop` 병행 라운드로 넘긴다. 다른 T#가 독립적이면 그 T#만 계속할지 묻는다.
3. 같은 실패에 수정 2회를 넘겼다 → `→ 6.2 unstuck ($sk-unstuck)` 또는 `→ 6.1 debug ($sk-debug)`.
4. 공개 인터페이스·출력 스키마·기존 테스트 기대값을 바꿔야 한다 → `→ 3.2 design ($sk-design)` 또는 G로.
5. 기존 테스트를 고치거나 지우거나 건너뛰어야 통과한다 → 사용자 확인 없이는 진행하지 않는다.
6. 기준선에 없던 실패가 생겼고 이 슬라이스와의 관련성을 판별할 수 없다 → `→ 6.1 debug ($sk-debug)`.
7. 새 패키지 설치·네트워크·외부 서비스가 필요하다 → 과제 규칙 확인과 사용자 승인을 받는다.
8. 상한을 넘겼다 → 분할 판정. 리뷰 시작 시각(예시 12:00)이 지났으면 새 슬라이스를 시작하지 않고 `→ 6.5 timebox ($sk-timebox)`.
9. 변경을 되돌려야 한다 → `→ 6.3 rollback ($sk-rollback)`. 파괴적 git 명령은 쓰지 않는다.
10. 서버·외부 시스템이 없어 검증을 실행할 수 없다 → 사유를 E#에 적고 `미검증`으로 판정한다.

### 시간 규칙

- 슬라이스 시작·종료 시각과 소요 분을 상태판에 남긴다. 연속 모드는 30분마다 PLAN 대비 진행을 한 줄로 보고한다.
- 남은 시간이 PLAN의 보호 시간(검증·문서·버퍼)을 침범하기 시작하면 다음 슬라이스를 시작하지 말고 `→ 6.5 timebox ($sk-timebox)`를 제안한다.
- 기준선부터 실패하던 테스트는 이 루프에서 고치지 않는다. 판정에서 `기존 실패`로 구분한다.

## 작업 노트 기록

- `sk/work/PLAN.md`의 `## 구현 루프 상태판`은 이 스킬이 소유한다. 파일 맨 위(제목 바로 아래)에 둔다.

```markdown
## 구현 루프 상태판
```
