# 요구사항 추적 검증

## 목적

명세의 요구사항 R, 수용 기준 AC, 수용 테스트 T, 실행 명령, 증거 E를 한 줄로 연결한다.
전체 테스트와 핵심 정상·경계·실패 경로를 실제로 다시 실행해 PASS, FAIL, 미검증만 판정한다.
코드를 고치지 않고 검증의 빈칸과 오래된 근거를 드러내 다음 행동을 결정한다.

## 언제 쓰나 / 쓰지 않나

- 4-build의 P0 슬라이스 구현 직후, 제출 문서 전, 또는 코드 변경 후 재검증할 때 쓴다.
- 2.3 수용 테스트 표와 4.1 테스트가 준비된 뒤에 가장 효과적이다.
- 실패의 원인을 고치려는 때는 이 절차를 멈추고 → 6.1 debug ($sk-debug)로 넘긴다.
- 테스트가 아직 없다면 먼저 → 2.3 acceptance ($sk-acceptance)와 → 4.1 test-first ($sk-test-first)로 보낸다.
- 이 스킬은 과제 코드·테스트·설정을 수정하거나 실패를 우회하지 않는다.

## 입력과 사전 확인

1. `sk/work/SPEC.md`에서 3절 R, 5절 P, 11절 T, 12절 추적표를 읽는다.
2. `sk/work/BRIEF.md`의 `## 환경`에서 실제 테스트·빌드 명령과 안전 조건을 확인한다.
3. `sk/work/PLAN.md`의 현재 S#와 `sk/work/EVIDENCE.md`의 최신 E#를 확인한다.
4. 작업 디렉터리는 과제 루트인지 확인하고 `sk/`는 테스트·린트·분석 대상에서 제외한다.
5. 비밀값, 개인정보, 원본 데이터 값이 출력될 수 있으면 마스킹 방법을 정한 뒤 실행한다.
6. 새 패키지 설치, 네트워크 호출, 포트 변경이 필요하면 공식 규칙과 사용자 허가가 있는지 먼저 확인한다.

## 절차

1. 검증 범위를 고정한다.
   현재 S#에 연결된 P0 R부터 시작하고, 검증 대상 R#/AC#/T# 목록을 표로 적는다.
   P1·P2는 남은 시간과 계획의 축소 결정을 보고 별도 열에 보류 이유를 남긴다.
2. 추적표의 빈칸을 찾는다.
   각 R에 AC가 있는지, 각 AC에 T가 있는지, 각 T에 실행 명령과 E#가 있는지 대조한다.
   P#마다 적어도 하나의 T#가 있는지, C#가 시험 또는 점검으로 확인됐는지도 표시한다.
3. 기대값의 독립성을 점검한다.
   기대 결과가 구현 함수의 결과를 다시 호출해 만든 값이면 독립 근거가 아니다.
   SPEC의 손계산, 담당자 답변 P#, 샘플 출력, 별도 최소 계산 중 근거 하나를 `기대값 근거`에 적는다.
4. 가장 작은 P0 테스트를 먼저 실행한다.
   실패하면 종료 코드·핵심 오류·대상 T#를 캡처하고, 같은 실행을 반복하지 않는다.
   통과해도 전체 검증 전에는 해당 R 전체를 PASS로 올리지 않는다.
5. 정상 경로를 실행한다.
   대표 입력 하나가 AC의 출력 값·형식·정렬·파일 또는 응답 위치를 만족하는지 확인한다.
6. 경계 경로를 실행한다.
   T 표에 있는 빈 입력, 최솟값·최댓값, 동점, 0, 한 건 등 해당 기능의 경계를 실제 입력으로 실행한다.
7. 실패 경로를 실행한다.
   잘못된 타입, 누락 필수값, 존재하지 않는 리소스 등 T#에 정의된 오류가 계약한 오류 형식·상태로 나오는지 확인한다.
   근거 없는 새 입력 규칙은 만들지 말고 G#로 등록할 후보라고 표시한다.
8. 전체 테스트 스위트를 한 번 실행한다.
   `sk/work/BRIEF.md`에 기록된 명령만 사용하며, 출력에서 통과·실패·건너뜀 수와 종료 코드를 기록한다.
   기존 실패가 기준선에 있었는지는 E#와 환경 기록으로 구분하고, 근거가 없으면 새 실패로 취급한다.
9. 빌드·정적 검사 요구가 명세나 과제에 있을 때만 실행한다.
   테스트와 별개로 빌드 성공 여부, 경고와 실패를 분리해 기록한다.
10. 변경 범위를 읽기 전용으로 확인한다.
```bash
git status --short
git diff --stat
```
   미추적 파일과 의도 밖 변경을 목록화할 뿐 삭제·되돌리기·정리는 하지 않는다.
11. 증거의 신선도를 판정한다.
   E# 이후 관련 코드·테스트·설정이 바뀌었으면 그 E#는 `STALE`로 표시하고 해당 명령을 재실행한다.
   비교 기준은 E#의 코드 상태와 현재 짧은 해시·변경 파일 목록이다.
12. 결과를 추적표에 반영한다.
   실제 실행 근거가 있는 행만 `PASS`, 실패한 행은 `FAIL`, 실행·근거가 없으면 `미검증`으로 쓴다.
13. 실행 직후 증거 행을 기록한다.
   → 5.2 evidence ($sk-evidence)의 E# 형식을 따라 명령, 종료 코드, 실제 결과, 코드 상태를 남긴다.
14. 다음 행동을 하나로 좁힌다.
   FAIL이면 재현 입력과 E#를 붙여 → 6.1 debug ($sk-debug)로 넘긴다.
   미검증이면 필요한 T# 작성은 → 2.3 acceptance ($sk-acceptance), 테스트 구현은 → 4.1 test-first ($sk-test-first)로 넘긴다.

## 판단 기준·분기

- if R에 AC 또는 T가 없다 → `미검증`으로 두고 누락 위치를 보고한다. 추측으로 PASS로 바꾸지 않는다.
- if 테스트는 통과하지만 기대값이 구현에 의존한다 → 독립 근거가 확보될 때까지 `미검증`이다.
- if 전체 스위트가 실패한다 → 관련성 미확정이면 FAIL로 숨기지 말고 `실패·원인 미분류`로 E#에 기록한다.
- if 기준선부터 실패한 테스트다 → 기준선 E#가 있을 때만 `기존 실패`로 구분하고, 현재 요구사항 판정은 미검증으로 둔다.
- if 명세와 관찰된 동작이 충돌한다 → 공식 문서·P#와 대조하고 G# 후보를 만든다. 임의로 코드를 고치지 않는다.
- if 남은 시간이 적다 → 모든 P0의 정상 경로, 전체 스위트, 변경 범위 확인을 최소 경로로 끝낸다.
- if 서버나 외부 시스템이 없어 실행 못 한다 → 명령·차단 사유·수동 확인 필요를 기록하고 `미검증`으로 판정한다.

## 작업 노트 기록

`sk/work/SPEC.md`의 `## 12. 추적표`에서 기존 표의 열을 유지하고 각 R 행을 갱신한다.
표준 열은 `R | AC | T | 구현 위치 | 증거 E | 상태`이며, 상태는 `PASS | FAIL | 미검증`만 쓴다.
예시는 `R3 | AC-R3-1 | T7,T8 | src/rank.py:42 | E21,E22 | PASS`처럼 쓴다.

`sk/work/EVIDENCE.md`의 `## 실행 기록`에는 의미 있는 실행마다 다음 열로 E# 행을 추가한다.
`E# | 시각 | 명령·작업 디렉터리 | 대상 R/T | 기대 | 실제 결과 요약 | 판정 | 코드 상태`.
실행 뒤 관련 코드가 바뀌면 이전 행의 판정 앞에 `STALE —`를 붙이고 새 E#를 추가한다.
추적표에는 실행하지 않은 E# 번호를 예약하지 않는다.

## 채팅 출력 형식

1. `검증 범위`: S#, R#/AC#/T# 개수와 제외·보류 항목.
2. `추적 결과`: `PASS / FAIL / 미검증` 수를 포함한 R별 표.
3. `실행 근거`: E#, 실행 명령, 종료 코드, 통과·실패 수, 핵심 실제 결과.
4. `빈칸·오래된 증거`: 누락 AC/T/E 또는 STALE E#와 영향.
5. `변경 범위`: `git status --short`, `git diff --stat`의 요약과 의도 밖 항목.
6. `다음 행동`: 정확히 한 단계와 프롬프트 ID·스킬 이름.

## 완료 기준

- P0 R마다 AC, T, 실제 실행 E#가 추적표에서 연결되어 있다.
- 전체 테스트 스위트가 현재 코드 상태에서 실제로 한 번 실행됐다.
- 해당되는 정상·경계·실패 경로의 판정과 기대값 근거가 있다.
- 오래된 증거가 재실행되었거나 STALE·미검증으로 명확히 표시됐다.
- PASS, FAIL, 미검증 외의 모호한 완료 표현을 쓰지 않았다.
- 실패·미검증의 다음 행동이 1개 이상 정해졌다.

## 금지

- 테스트를 삭제·약화·건너뛰어 통과 수를 만들지 않는다.
- 과제 코드, 테스트, 설정, 원본 데이터를 이 스킬에서 수정하지 않는다.
- 실행하지 않은 명령·결과를 E#나 채팅에 통과로 적지 않는다.
- `git reset --hard`, `git clean`, `git stash`, 강제 체크아웃으로 작업 상태를 정리하지 않는다.
- 비밀값·개인정보·민감한 원본 값을 출력하거나 작업 노트에 기록하지 않는다.
- 공식 규칙·담당자 답변 없이 새 의존성, 네트워크, 서버 설정을 도입하지 않는다.
