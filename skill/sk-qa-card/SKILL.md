# 6문항 암기 카드

## 목적
- 실제 구현을 내 말로 설명할 수 있도록 Q1~Q6별 짧고 정확한 암기 카드를 만든다.
- `sk/templates/POST_QA_6_TEMPLATE.md`의 축과 3문장 형식을 유지하되, 예시 문구를 사실처럼 복사하지 않는다.
- 설계·동작·예외·검증·업무 맥락·한계의 근거를 파일·함수·ID로 바로 되짚을 수 있게 한다.

## 언제 쓰나 / 쓰지 않나
- `9.1 understand ($sk-understand)`로 코드 흐름을 정리한 뒤, 제출 전 AI 사용 허용 시간에 사용한다.
- 제출 전 최종 점검 `8.2 deliver ($sk-deliver)`에서 6문항 준비 여부를 확인하기 전에 사용한다.
- AI·복붙 금지 서술형 단계가 시작되면 즉시 중단한다. 그 단계에서 카드 읽기, 생성, 보완, 답안 작성에 사용하지 않는다.
- 구현 근거가 비어 있으면 그럴듯한 문장을 만들지 말고 `5.1 verify ($sk-verify)` 또는 `9.1 understand ($sk-understand)`로 되돌아간다.
- 이 스킬은 보고서·코드·테스트를 수정하지 않는다. 발견한 사실 오류는 해당 원천 노트의 담당 스킬에 넘긴다.

## 입력과 사전 확인
- `sk/templates/POST_QA_6_TEMPLATE.md`를 읽고 Q1~Q6의 축과 문항당 3문장이라는 형식을 확인한다.
- 다음 원천을 우선순위대로 읽는다.
  - `sk/work/UNDERSTANDING.md`: 파일·함수 지도, 대표 사례, Guard, 사실 10개, 한계
  - `sk/work/SPEC.md`: R#, C#, P#, A#, T# 및 추적표
  - `sk/work/DECISIONS.md`: DD#와 AI 교정 기록 AI#
  - `sk/work/EVIDENCE.md`: 실제 실행 E#와 PASS/FAIL/미검증
  - `sk/work/DM_LOG.md`: M#에서 나온 정책 P#의 범위
- 숫자(테스트 수, 행 수, 상태 코드, 포트, 시간)는 최신 E# 또는 코드에서 직접 확인한 것만 후보로 쓴다.
- AI#가 없으면 AI가 교정된 것처럼 쓰지 않는다. 대신 'AI 교정 기록 없음' 또는 해당 항목이 없음을 표기한다.
- 제출 전 AI 사용 허용 상태인지 먼저 확인한다.

## 절차
1. 템플릿을 열고 각 Q가 요구하는 축을 적는다: Q1 Why, Q2 How, Q3 Edge Cases, Q4 Verification and AI correction, Q5 Business Fit, Q6 Limitations.
2. Q1에 R#/C# 또는 DD#를 붙여 문제와 선택지를 말한다. '안정적' 같은 결과만 쓰지 말고 대안과 트레이드오프를 포함한다.
3. Q2에 실제 진입 파일·핵심 함수·입력 검증·도메인 규칙·출력의 순서를 붙인다. 존재하지 않는 계층을 만들지 않는다.
4. Q3에 실제 구현한 Guard 2~3개와 그 위치, 결과, P#/A# 근거를 붙인다. 처리하지 않은 사례는 한계로 넘긴다.
5. Q4에 T#/E#가 증명한 정상·경계·실패 경로를 붙인다. AI#가 있을 때만 초기 제안의 문제, 발견 방법, 수정 지시, 재검증을 쓴다.
6. Q5에 README·공식 문서·M# 답변에서 확인된 업무 정책 P#가 코드에 강제된 지점을 붙인다. 조직 효과를 추측하지 않는다.
7. Q6에 현재 구조에서 실제로 가능한 실패 조건, 제한 시간에 택한 단순화, 우선순위 있는 개선과 검증 방법을 붙인다.
8. 각 Q를 정확히 3문장으로 압축한다: 결론 1문장, 코드/증거 1문장, 효과·한계 또는 근거 1문장.
9. 각 Q 아래에 암기 키워드 정확히 5개, 반드시 말할 숫자·이름, 예상 꼬리질문 1개와 답의 방향, 근거 위치를 넣는다.
10. `sk/work/QA_CARD.md`의 정확한 Q1~Q6 절을 갱신하고, AI 금지 시작 시 사용할 수 없다는 경고를 상단에 적는다.

```text
원천 읽기 예시
sed -n '1,260p' sk/templates/POST_QA_6_TEMPLATE.md
sed -n '1,300p' sk/work/UNDERSTANDING.md
sed -n '1,280p' sk/work/DECISIONS.md
sed -n '1,320p' sk/work/EVIDENCE.md
```

## 판단 기준·분기
- if Q1에 대안 DD#가 없으면 → 코드에서 실제 비교한 범위만 쓰고 '대안 비교 미기록'을 표시한다. 대안을 지어내지 않는다.
- if Q2 함수명이 바뀌었으면 → 현재 코드를 읽어 카드의 옛 이름을 고친 뒤, 링크된 UNDERSTANDING 지도도 갱신하도록 알린다.
- if Q3에 근거 P#가 없고 A#만 있으면 → '가정 A#'로 명확히 말하고 정책 확정처럼 표현하지 않는다.
- if Q4의 테스트가 실패했거나 오래되었으면 → PASS가 아니라 FAIL/미검증을 쓰고 `5.1 verify ($sk-verify)`로 넘긴다.
- if 실제 업무 정책이 문서에 없다면 → 업무 효과를 일반화하지 말고 해당 구현의 기술적 목적만 말한다. 필요하면 `1.3 dm-questions ($sk-dm-questions)`으로 확인한다.
- if 개선안이 현재 구조와 무관하면 → 삭제한다. 예를 들어 실제 비동기 작업이 없으면 비동기 큐를 관성적으로 쓰지 않는다.
- if 시간이 8분 미만이면 → Q1·Q2·Q3·Q4 먼저 3문장으로 채우고, Q5·Q6은 근거 ID와 미검증 표시를 우선 남긴다.

## 작업 노트 기록
- 파일은 `sk/work/QA_CARD.md`이며, 템플릿의 Q1~Q6 축을 다음 정확한 절 제목으로 쓴다.
- `## Q1 설계 의도 (Why)`부터 `## Q6 한계점 및 개선안 (Limitations)`까지 여섯 절을 만든다.
- 각 절의 고정 서식은 다음과 같다.
  - `### 3문장 답변`: 실제 근거가 있는 세 문장.
  - `### 암기 키워드 5개`: 쉼표 목록이 아니라 번호 1~5로 쓴다.
  - `### 반드시 말할 숫자·이름`: `항목 | 값·이름 | 근거 위치 | 검증 상태` 표를 쓴다.
  - `### 예상 꼬리질문과 답의 방향`: 질문 1개와 사실을 말할 방향 1줄.
  - `### 근거 위치`: `R/C/P/A/DD/T/E/AI/M | 위치 | 이 답에서 쓰는 사실 | 상태` 표를 쓴다.
- `## 연습 기록`은 `9.3 qa-drill ($sk-qa-drill)`이 갱신한다. 카드를 만들 때 연습 결과를 덮어쓰지 않는다.
- Q4의 AI 관련 사실은 `AI# | 초기 문제 | 발견 방법 | 내 수정 지시 | 재검증 E#` 형태로만 기록한다.

## 채팅 출력 형식
1. **사용 가능 확인**: AI 허용 시간인지와 읽은 템플릿·노트 목록.
2. **카드 요약표**: `문항 | 3문장 근거 ID | 말할 파일·함수 | 검증 상태`.
3. **숫자·이름 체크**: 실제로 말할 값과 근거 E#/코드 위치.
4. **금지할 표현**: 증거 없음, 가정, 미검증이라서 말하면 안 되는 주장.
5. **다음 단계**: `9.3 qa-drill ($sk-qa-drill)`로 무참조 연습을 제안하거나 부족한 원천 스킬을 하나 제안한다.

## 완료 기준
- Q1~Q6가 각각 정확히 3문장 답변, 키워드 5개, 숫자·이름, 꼬리질문, 근거 위치를 가진다.
- 모든 파일명·함수명·DD#/P#/T#/E#/AI#는 실제 원천과 일치한다.
- Q4는 실제 검증 범위와 미검증 범위를 함께 말하며, AI#가 없으면 AI 교정 사실을 만들지 않는다.
- Q5는 확인된 문서·M#·P#에 근거하고, Q6은 현재 구현의 구조적 한계에 근거한다.
- 템플릿의 대괄호와 예시 도메인 문구가 남지 않으며, 카드가 `sk/work/QA_CARD.md`에 저장된다.

## 금지
- AI·복붙 금지 서술형 단계에서 카드 생성, 열람, 해설, 답안 작성, 연습을 하지 않는다.
- 카드에 없는 수치·테스트·정책·담당자 답변·AI 수정 내역을 꾸며 넣지 않는다.
- 템플릿의 비동기 큐, 센서 오류, 특정 예시를 실제와 무관하게 재사용하지 않는다.
- 과제 코드·테스트·설정·제출 문서를 수정하거나 제출·업로드를 실행하지 않는다.
- '검증했다'처럼 실행 증거 없는 완료 표현을 사용하지 않는다.
- 민감 데이터, 토큰, 개인정보를 카드의 예시·숫자·근거로 쓰지 않는다.
