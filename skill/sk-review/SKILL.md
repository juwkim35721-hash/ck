# 반증 중심 코드 리뷰

## 목적

변경된 코드가 요구사항을 만족한다는 주장보다 먼저, 그 주장이 깨지는 입력과 경로를 찾는다.
`git diff`를 리뷰 범위의 출발점으로 삼고 정확성, 정책, 인터페이스, 테스트, 보안, 성능을 짧고 재현 가능하게 점검한다.
리뷰의 산출물은 수정 자체가 아니라 `sk/work/REVIEW.md`의 발견 F#과 승인 요청용 우선순위다.

## 언제 쓰나 / 쓰지 않나

- 구현 슬라이스가 끝난 뒤, 전체 검증 직후, 제출 전 변경 범위를 독립적으로 검토할 때 사용한다.
- `7.2 compliance`($sk-compliance) 전에 사용해 코드 수준의 결함 후보를 먼저 찾는다.
- 실패 출력의 원인을 좁히는 일이면 `6.1 debug`($sk-debug)를 우선 사용한다.
- 요구사항·정책 자체가 불명확하면 새 규칙을 만들지 말고 `1.2 ambiguity`($sk-ambiguity)로 G#를 만든다.
- 아직 구현이 전혀 없거나 명세가 동결되지 않았으면 리뷰 결론을 내리지 말고 `2.4 spec-gate`($sk-spec-gate)로 보낸다.
- 기본 모드에서는 과제 파일을 수정하지 않는다. 발견을 고치는 일은 사용자 승인 뒤에만 수행한다.

## 입력과 사전 확인

1. `sk/work/SPEC.md`에서 `## 구현 시 반드시 지킬 규칙 Top 5`, `## 3. 요구사항 R`, `## 4. 제약 C`, `## 5. 확정 정책 P`, `## 10. 입출력·데이터 계약`, `## 11. 수용 테스트 표 T`, `## 12. 추적표`를 읽는다.
2. `sk/work/DM_LOG.md`의 최신 `## 정책 목록 P`와 `sk/work/DECISIONS.md`의 관련 DD#를 읽는다.
3. `sk/work/EVIDENCE.md`의 최신 E#가 현재 변경 이후인지 확인한다. 코드가 바뀐 뒤의 증거는 STALE일 수 있다.
4. 과제 루트에서 작업 중인지 확인하고 `sk/`는 도구이므로 과제 코드·테스트·diff 범위에서 제외한다.
5. 읽기 전용으로 변경 범위와 상태를 확보한다. 비밀값이 보이면 값은 출력·기록하지 말고 위치와 유형만 남긴다.

```bash
git status --short
git diff --stat
git diff --check
git diff --name-only
```

6. Git 저장소가 아니면 사용자가 지정한 변경 파일 목록, 파일 수정 시각, 직전 E#를 범위 근거로 쓴다.
7. 리뷰 시작 시점의 HEAD 또는 현재 변경 파일 목록을 메모해, 리뷰 중 새 변경과 구분한다.

## 절차

1. **리뷰 계약을 고정한다.** 대상 슬라이스 S#, 관련 R#/P#/C#, 변경 파일, 최신 E#, 남은 시간을 한 줄씩 적는다. 범위 밖 파일은 발견하지 않으면 검토하지 않았다고 명시한다.
2. **diff를 작은 단위로 읽는다.** 파일마다 추가·삭제·이름 변경을 구분하고, 공개 함수·라우트·CLI·데이터 스키마·설정의 변화에 표시한다. 포맷만 바뀐 대규모 diff는 기능 변경과 분리한다.
3. **정상 주장에 반대되는 입력을 만든다.** 각 핵심 분기마다 빈 값, 누락 필드, 잘못된 타입, 경계값, 0·음수, 중복, 동점, 빈 결과, 예상 밖 오류를 먼저 대입한다. 해당 범주가 SPEC에 없으면 정책을 추정하지 말고 G# 후보로 적는다.
4. **정확성을 추적한다.** 입력이 Guard, 핵심 로직, 출력 또는 오류 경로를 거쳐 어떤 값이 되는지 R#의 AC와 T#의 기대값에 대조한다. 산술·필터·정렬·반올림은 작은 예시로 손계산한다.
5. **P#와 C#를 대조한다.** P#의 “조건 → 동작”이 코드의 조건문·기본값·오류 처리·테스트에 모두 있는지 확인한다. 인터페이스 유지, 지정 바인딩·포트, 금지 의존성, 수정 금지 파일도 C#별로 살핀다.
6. **오류 계약을 점검한다.** 오류를 삼키거나 성공처럼 반환하지 않는지, 오류 상태·본문·null/빈 목록 표현이 SPEC 10절과 같은지, 실패 뒤 부분 결과가 남지 않는지 본다.
7. **호환성과 변경 범위를 점검한다.** 함수 서명, JSON 키·타입, 정렬, CLI 출력, 환경변수 이름, 기존 호출자를 비교한다. 무관한 리팩터링·생성물·대용량 파일은 별도 발견으로 남긴다.
8. **테스트의 실효성을 읽는다.** 테스트가 함수 호출만 하고 결과를 assert하지 않는지, 새 분기·P#·실패 경로를 실제로 검증하는지, 구현 내부를 과도하게 모방하지 않는지 확인한다. 필요한 경우 가장 작은 재현 테스트를 제안하되 승인 전에는 과제 파일에 추가하지 않는다.
9. **보안·민감정보·성능 위험을 훑는다.** 키·토큰·개인정보·원본 데이터가 하드코딩·로그·오류 메시지에 없는지, 입력 크기마다 중첩 반복·전체 메모리 적재·무제한 재시도가 새로 생기지 않았는지 확인한다. 추측성 성능 수치는 쓰지 않는다.
10. **재현 근거를 확보한다.** 안전한 기존 테스트나 최소 명령을 실제 실행했을 때만 E#에 결과를 기록한다. 실행하지 못한 항목은 “미검증”이고 통과가 아니다.
11. **발견을 F#로 분류한다.** 위치, 깨지는 구체 입력 또는 정적 근거, 관련 R#/P#/C#, 영향, 최소 제안을 한 행으로 만든다. 같은 원인의 증상은 한 F# 아래에 묶되 서로 다른 수정이 필요하면 분리한다.
12. **수정 승인을 구한다.** 차단·높음 발견은 영향과 최소 수정안을 먼저 보여 주고 사용자의 승인을 기다린다. 승인된 항목만 `6.1 debug`($sk-debug) 또는 구현 흐름으로 넘겨 수정·재검증한다.

## 판단 기준·분기

| 상황 | 판정과 다음 행동 |
| :--- | :--- |
| P0 R 또는 P#를 깨는 재현이 있음 | `차단` 또는 `높음` F#로 기록하고, 제출·보고서보다 수정과 재검증을 우선한다. |
| 공개 인터페이스·출력 스키마가 명세 없이 변함 | 호출자 영향이 없어도 `높음`으로 기록하고 `C#` 및 SPEC 10절과 대조한다. |
| 명세가 두 해석을 허용함 | 코드 결함이라고 단정하지 말고 G# 후보, 기본안, 결정 필요 시점을 `1.2 ambiguity`($sk-ambiguity)에 넘긴다. |
| 테스트가 실패하지만 현 변경과 관련이 불명확함 | 실제 출력과 직전 E#를 붙여 `6.1 debug`($sk-debug)로 넘긴다. 리뷰에서 추측 수정하지 않는다. |
| 테스트가 구현과 같은 상수·분기를 복제함 | 결과 검증이 약한 `중간` F#로 기록하고 독립 기대값·입출력 assert를 제안한다. |
| 문제는 스타일만이고 요구·동작에 영향 없음 | 시간 여유가 있으면 `낮음`, 남은 시간이 적으면 한계 목록으로 이월한다. |
| 민감정보 노출 가능성이 보임 | 값은 복사하지 않고 즉시 `차단`으로 위치·유형·노출 경로만 기록한다. |
| 시간 10분 이하 | P0/P#·제출물·공개 인터페이스·민감정보 네 축만 점검하고 미점검 범위를 명시한다. |

심각도는 `차단`(제출 불가·보안·데이터 훼손), `높음`(P0/P# 또는 호환성 실패), `중간`(중요 엣지·테스트 공백), `낮음`(영향 작은 유지보수)만 사용한다.

## 작업 노트 기록

`sk/work/REVIEW.md`가 없으면 만들되 다른 스킬의 섹션은 건드리지 않는다. 다음 정확한 제목 아래에 행을 추가한다.

```markdown
## 리뷰 발견 F

| F# | 심각도 | 위치 | 근거·재현 입력 | 관련 R/P/C | 영향 | 제안 | 상태 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| F1 | 높음 | `src/rank.py:42` | 동점 `A=10,B=10`에서 입력 순서에 따라 결과가 달라짐 | P3, T8 | 결과 비결정적 | 보조 키 오름차순 정렬과 회귀 T 추가 | 승인 대기 |
```

- 상태는 `열림`, `승인 대기`, `수정 중`, `수정 후 재검증`, `종료`, `수용된 한계` 중 하나로 쓴다.
- 테스트나 재현 명령을 실제 실행했으면 `sk/work/EVIDENCE.md`의 `## 실행 기록`에 E#을 추가하고 F#와 연결한다.
- AI가 만든 코드·제안의 결함이면 `sk/work/DECISIONS.md`의 `## AI 교정 기록`에 AI#을 추가한다. 최초 제안 문제, 발견 방법, 사용자가 지시한 수정, 확인 E#만 사실로 적는다.
- 승인 후 수정으로 P#/R#/AC가 바뀌면 리뷰에서 임의 갱신하지 말고 `1.4 dm-answers`($sk-dm-log) 또는 `2.1 spec`($sk-spec)으로 인계한다.

## 채팅 출력 형식

아래 순서로 짧고 사실만 보고한다.

1. **범위:** 검토한 변경 파일, 관련 S#/R#/P#, 검토하지 못한 범위.
2. **판정:** `수정 필요` / `조건부 통과` / `발견 없음(검토 범위 내)` 중 하나와 근거 한 줄.
3. **발견 표:** F# | 심각도 | 위치 | 깨지는 조건 | 최소 제안 | 상태 순서.
4. **실행 근거:** 실제 실행한 E#과 요약, 또는 미실행 이유.
5. **승인 요청:** 차단·높음 항목의 수정 범위와 사용자 승인 필요 여부.
6. **다음 단계:** `7.2 compliance`($sk-compliance) 또는 승인된 항목의 `6.1 debug`($sk-debug).

## 완료 기준

- 변경 범위와 최신 코드 상태를 실제 `git diff` 또는 동등 근거로 확인했다.
- P0 R, P#, C#, 공개 인터페이스, 오류 경로, 테스트 실효성, 민감정보를 리뷰 범위에서 점검했다.
- 각 실질 발견은 F#·심각도·위치·근거·관련 ID·상태를 갖는다.
- 실행 결과는 실제 E#로만 주장했고, 미검증·미점검 범위를 숨기지 않았다.
- 승인 없이 과제 파일을 수정하지 않았고, 다음 담당 스킬을 ID와 이름으로 제시했다.

## 금지

- 리뷰를 이유로 과제 코드·테스트·설정·제출물을 자동 수정하지 않는다. 사용자가 승인한 항목만 수정 흐름으로 넘긴다.
- 실행하지 않은 테스트나 추측한 성능·보안 결과를 통과로 기록하지 않는다.
- 담당자 답변이나 명세에 없는 정책을 코드 결함의 확정 근거로 만들지 않는다.
- 기존 테스트, 원본 데이터, 과제 파일을 삭제하거나 되돌리기 위한 위험한 Git 명령을 사용하지 않는다.
- 외부 제출·업로드·push·배포·자격증명 전송을 하지 않는다.
- 비밀값·토큰·개인정보·민감 원본값을 채팅, diff 발췌, 작업 노트에 기록하지 않는다.
- `sk/` 도구 폴더를 과제 구현물처럼 분석·수정·테스트 대상으로 포함하지 않는다.
