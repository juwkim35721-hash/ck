# 시간 부족 시 범위 축소

## 목적
남은 시간을 기능 욕심이 아니라 제출 가능한 P0 동작, 필수 제출물, 실제 검증 증거, 보고서·설명 준비, 제출 버퍼에 배분한다.
무엇을 자를지 명시적으로 결정하고 영향과 한계를 기록해, 마감 직전 무계획 수정·미검증 기능 추가·사실과 다른 보고를 막는다.

## 언제 쓰나 / 쓰지 않나
- 계획의 체크포인트를 넘겼거나, 남은 시간으로 열린 S#를 모두 끝낼 수 없을 때 쓴다.
- 디버깅·복구가 길어져 제출물 완성 위험이 생겼을 때 쓴다.
- 남은 시간이 15분 이하가 되었을 때는 반드시 쓴다.
- 기능이 충분히 끝났고 정상적인 테스트 순서만 정리하면 되는 경우에는 `5.1 verify ($sk-verify)`와 `8.2 deliver ($sk-deliver)`를 쓴다.
- 요구사항의 우선순위·정책 자체가 모호한 경우에는 임의로 P0를 정하지 말고 `2.1 spec ($sk-spec)` 또는 `1.3 dm-questions ($sk-dm-questions)`로 근거를 확인한다.
- 같은 오류를 분석하는 절차는 `6.1 debug ($sk-debug)`, 반복 루프 정지는 `6.2 unstuck ($sk-unstuck)`이 담당한다.

## 입력과 사전 확인
1. 마감 시각과 현재 시각에서 실제 남은 분을 계산한다. 공식 안내가 불명확하면 추정 마감 시각을 사실처럼 쓰지 않고 사용자에게 확인한다.
2. `sk/work/SPEC.md`의 `## 2. 필수 제출물`, P0 R#, AC, P#, A#, `## 11. 수용 테스트 표 T`, `## 8. 비목표`를 읽는다.
3. `sk/work/PLAN.md`의 `## 시간 예산`, `## 슬라이스 S`, `## 위험 실험`, 기존 `## 축소 결정`, `## 상태 캡슐`을 읽는다.
4. `sk/work/EVIDENCE.md`의 최신 E#으로 P0별 PASS/FAIL/미검증을 구분한다. 실행하지 않은 결과를 통과로 채우지 않는다.
5. 보고서·제출·설명 준비 상태를 점검한다: `8.1 report ($sk-report)`, `8.2 deliver ($sk-deliver)`, AI 허용 시간 내의 `9.2 qa-card ($sk-qa-card)`.
6. 현재 diff와 미추적 파일을 읽기 전용으로 확인한다. `git status --short`, `git diff --stat`을 사용하고 정리·삭제는 하지 않는다.

## 절차
1. 남은 시간을 3구간으로 잠근다: 구현·수정, 검증·증거, 문서·제출 버퍼. 제출 버퍼는 최소 10분을 먼저 떼어 둔다.
2. 다음 필수 목록을 고정한다: P0 동작, SPEC 2절의 필수 제출물, 각 P0의 최소 T#/E#, 지정 보고서, 제출 전 6문항 카드 준비 여부, 제출 버퍼.
3. 열린 작업을 하나씩 표에 적어 R#/S#/P0·P1·P2, 제출 차단 여부, 남은 시간, 이미 있는 E#, 잘랐을 때 영향으로 평가한다.
4. 축소 순서는 P2 전체 → P1의 독립 부가 기능 → 품질 개선·리팩터링·화면 다듬기다. P0와 필수 제출물·최소 검증은 원칙적으로 자르지 않는다.
5. 각 작업을 `완료`, `최소 구현`, `보류`, `cut` 중 하나로 결정한다. `최소 구현`은 R#/AC/P#를 만족하는 가장 작은 수직 슬라이스여야 하며, 보기 좋은 데모만 만드는 것이 아니다.
6. 현재 진행 중인 S#가 P0가 아니거나 10분 안에 테스트 가능한 단위로 끝나지 않으면 즉시 멈춘다. 안전한 중단점과 현재 테스트 상태를 기록한다.
7. P0에 실패가 있으면 원인 분석을 최대 10분으로 제한해 `6.1 debug ($sk-debug)`에 맡긴다. 해결되지 않으면 사용자에게 사실을 알리고, 남은 필수물·보고서로 이동한다.
8. cut·보류 항목마다 사용자가 이해할 수 있는 한계 문구를 만든다. 실제 미구현·미검증 범위만 쓰며, 원인을 핑계로 과장하지 않는다.
9. `PLAN.md`의 시간 예산·슬라이스·축소 결정·상태 캡슐을 같은 시각 기준으로 갱신한다.
10. 구현 시간이 끝나면 추가 기능·리팩터링을 중단하고 `5.1 verify ($sk-verify)`로 최신 코드의 P0 증거를 채운다.
11. 그 뒤 `8.1 report ($sk-report)`로 증거 기반 보고서를 작성하고 `8.2 deliver ($sk-deliver)`로 GO/CONDITIONAL/NO-GO를 점검한다.
12. AI 사용이 허용된 제출 전 시간에만 `9.2 qa-card ($sk-qa-card)`로 Q1~Q6 근거를 준비한다. 금지 단계가 시작되면 즉시 사용을 멈춘다.
13. 남은 15분 이하면 새 기능·새 의존성·리팩터링을 시작하지 않는다. 필수 제출물 존재, P0의 최신 E#, 보고서, 제출 버퍼만 처리한다.
14. 최소 경로는 남은 시간 계산 → P0/필수물 고정 → P2/P1 cut → P0 테스트 1회 → E# → 보고서·제출 점검이다.

```bash
# 과제 루트에서 현재 범위만 읽기 전용으로 확인한다.
git status --short
git diff --stat

# 새 기능보다 기존 P0 테스트를 먼저 한 번 실행한다.
<P0-핵심-테스트-명령>
```

## 판단 기준·분기
- 남은 시간 45분 이상이지만 계획이 2개 체크포인트 지연 → P2를 보류하고, 가장 위험한 P0 하나만 10분 실험으로 확인한다.
- 남은 시간 16~45분 → P0·필수 제출물·검증·보고서 시간을 표로 고정하고 P1은 증거가 이미 있는 경우에만 유지한다.
- 남은 시간 15분 이하 → 새 기능·리팩터링·대규모 UI 변경을 금지하고 제출 점검 모드로 전환한다.
- P0 구현이 끝났지만 최신 전체 테스트가 없음 → 기능 추가 대신 `5.1 verify ($sk-verify)`와 `5.2 evidence ($sk-evidence)`를 우선한다.
- P0가 아직 FAIL이고 고칠 후보가 한 가지임 → `6.1 debug ($sk-debug)`에 10분만 배정한다. 두 번째 전략은 시간표를 새로 승인하지 않으면 시작하지 않는다.
- P0가 아직 FAIL이고 원인이 정책 모호성임 → G#와 영향만 기록하고 긴급 DM을 제안한다. 답변을 가정해 기능을 만들지 않는다.
- 제출물 경로나 형식이 불명확함 → SPEC 2절 기준을 확인하고, 미확정이면 `8.2 deliver ($sk-deliver)`에서 CONDITIONAL/NO-GO로 정직하게 표시한다.
- 보류 기능이 P0에 간접 영향 → cut하지 말고 최소 구현으로 재분류하거나 영향·위험을 사용자에게 알린다.

## 작업 노트 기록
`sk/work/PLAN.md`에서 다음 정확한 섹션만 갱신하고, 다른 스킬의 기록은 덮어쓰지 않는다.

`## 시간 예산`에는 기준 시각과 남은 시간을 붙여 적는다.

| 기준 시각 | 남은 시간 | 구현·수정 | 검증·증거 | 보고서·제출 | 버퍼 | 재점검 시각 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 14:30 | 35분 | 10분 | 8분 | 7분 | 10분 | 14:40 |

`## 슬라이스 S`에는 각 열린 S#의 최종 상태를 남긴다.

| S# | 관련 R/T | 상태 | 종료 조건 | 다음 행동 |
| :--- | :--- | :--- | :--- | :--- |
| S4 | R3, T8 | 최소 구현 | T8 실제 PASS | 5.1 검증 |

`## 축소 결정`에는 다음 표를 추가한다.

| 결정 시각 | 항목 R/S | 결정 완료/최소 구현/보류/cut | 이유·시간 근거 | 사용자 영향 | 보고서 한계 문구 | 재개 조건 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 14:30 | S6/R8 | cut | P2, 남은 35분 | 고급 정렬 없음 | “고급 정렬은 시간 제약으로 구현하지 않았다.” | P0 PASS 후 |

- 최신 P0 테스트 실행은 `sk/work/EVIDENCE.md`의 `## 실행 기록`에 E#으로 기록한다.
- 상태 전환의 요약은 `## 상태 캡슐`에도 남긴다. A#/P#·R#의 내용을 이 스킬에서 임의 변경하지 않는다.

## 채팅 출력 형식
1. **시간 사실**: 기준 시각, 공식 또는 확인된 마감, 남은 시간, 확보한 버퍼.
2. **필수 고정 목록**: P0 R#, 필수 제출물, 최소 T#/E#, 보고서·제출·Q1~Q6 준비.
3. **우선순위 표**: S#/R# | 예상 분 | 증거 상태 | 결정 | 자르면 생기는 영향.
4. **축소 결정**: cut·보류·최소 구현 항목과 정직한 한계 문구.
5. **마감 순서**: 지금부터의 단일 순서와 각 종료 시각.
6. **다음 인계**: `5.1 verify`, `8.1 report`, `8.2 deliver` 중 즉시 실행할 하나.

## 완료 기준
- 남은 시간과 제출 버퍼가 숫자로 기록되어 있다.
- P0·필수 제출물·최소 증거가 다른 작업보다 먼저 고정되어 있다.
- 모든 열린 S#가 완료·최소 구현·보류·cut 중 하나로 분류되고 이유·영향이 있다.
- P0 최신 테스트의 실제 결과가 E#에 있거나 미검증 사유가 명시되어 있다.
- 보고서·제출·AI 허용 시간의 QA 준비로 이어지는 순서가 있으며, 한계는 사실만 반영한다.

## 금지
- 마감 압박을 이유로 P0 실패·미검증·필수 제출물 누락을 숨기거나 PASS로 쓰지 않는다.
- 사용자 승인 없이 요구사항을 P0에서 P2로 임의 강등하거나, 담당자 답변을 무시하지 않는다.
- 남은 15분 이하에 새 기능, 새 패키지, 대규모 리팩터링, 미승인 포트·호스트 변경을 시작하지 않는다.
- 시간을 절약한다며 기존 테스트·원본 데이터·사용자 변경을 삭제하거나 위험한 복구 명령을 쓰지 않는다.
- 외부 제출·push·배포·업로드를 실행하지 않는다. 제출 버튼은 사용자가 결정한다.
- `sk/` 도구 파일을 과제 범위로 수정하지 않으며, 기록은 `sk/work/`에만 쓴다.
