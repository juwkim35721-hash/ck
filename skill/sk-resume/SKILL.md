# 맥락 복구·작업 인수인계

## 역할

현재 상태를 읽기 전용으로 재구성하고, 다음 원자 작업 하나를 결정하라.
대화 속 완료 주장이나 오래된 요약을 사실로 확정하지 마라.
공식 안내와 현재 과제 규칙을 이 절차보다 우선하라.
AI 사용 금지 평가가 시작되었으면 즉시 보조 사용을 중단하라.

## 입력 확인

실제 과제 루트, 남은 시간, 적용 요구사항과 허용 실행 범위를 확인하라.
준비 도구 저장소를 실제 과제 루트로 간주하지 마라.
공식 안내나 담당자 답변이 없으면 정책·요구사항을 추정하지 말고 `미확인`으로 남겨라.
토큰, 자격증명, 개인정보, 원본 민감 데이터는 읽더라도 요약에 값 자체를 쓰지 마라.

## 복구 절차

1. 과제 루트와 적용 규칙을 확인하고, AI 사용 가능 여부가 불명확하면 그 사실을 먼저 보고하라.
2. 요구사항 원문, 현재 파일 구조, `git status`, `git diff`, 관련 호출 지점, 기존 테스트·실행 설정을 읽어라.
3. 각 항목을 `사실`, `주장`, `미확인`으로 분류하라.
4. 요구사항 ID 또는 수용 기준이 있으면 완료·진행 중·미검증·불명 상태를 연결하라.
5. 기존에 문서화된 실행 명령과 최근 출력에서 마지막 검증을 확인하라.
6. 검증 결과가 현재 diff보다 이전이면 현재 상태의 증거가 아니라는 한계를 표시하라.
7. 실행이 허용되고 안전한 기존 명령이 명확할 때만 가장 관련된 검증 하나를 실행하라.
8. 실행 실패, 명령 불명확, 환경 차단이 있으면 핵심 오류와 재현 명령을 기록하고 반복 실행을 멈춰라.
9. 가장 위험한 미확인 또는 막힌 필수 항목을 줄일 다음 원자 작업 하나를 고르라.

## 분기

공식 규칙이 AI 사용을 금지하면 상태 복구 결과도 만들지 말고 중단 이유만 알리라.
실제 과제 루트를 확인하지 못하면 파일 상태를 단정하지 말고 루트 확인을 다음 작업으로 지정하라.
요구사항이 없으면 완료 여부를 판정하지 말고 요구사항 원문 또는 담당자 답변 확보를 다음 작업으로 지정하라.
기존 검증 명령이 없으면 테스트를 새로 만들지 말고 검증 명령 확인을 미검증으로 남겨라.
남은 시간이 짧으면 새 분석을 넓히지 말고 필수 요구사항에 직접 연결된 한 작업만 고르라.

## 출력 형식

12줄 이내 상태 캡슐을 작성하라.
`과제 루트/규칙`, `확인된 사실`, `변경·진행 상태`, `미재확인 주장`, `미확인·차단 요인`을 포함하라.
`마지막 검증`에는 명령, 실행 여부, 결과, 현재 diff와의 관계를 적어라.
`다음 한 작업`에는 목적, 예상 5~30분, 완료 판정을 적어라.
근거는 파일 경로·명령·출력 요약처럼 재확인 가능한 형태로만 적어라.

## 완료 기준

과제 루트와 적용 규칙의 확인 수준이 드러나야 한다.
사실·주장·미확인이 섞이지 않아야 한다.
검증을 실행하지 않았거나 실행할 수 없었으면 그 이유를 숨기지 않아야 한다.
다음 작업은 정확히 하나여야 하며, 완료 판정이 가능해야 한다.

## 금지 행동

파일을 수정, 삭제, 정리하거나 테스트를 추가·제거하지 마라.
근거 없는 테스트 통과, 공식 정책, 제출 상태를 만들지 마라.
사용자와 무관한 변경을 되돌리거나 민감정보를 인수인계에 복사하지 마라.
사용자의 별도 구체적 승인 없이 제출, push, 배포, 외부 업로드를 실행하지 마라.
