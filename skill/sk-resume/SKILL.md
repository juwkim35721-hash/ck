# 맥락 복구·작업 재개

## 목적
새 세션, 컨텍스트 압축, 장시간 중단 뒤에 대화 기억 대신 작업 노트·현재 diff·실제 실행으로 작업 상태를 복구한다.
현재 코드가 기록된 상태와 다르면 차이를 먼저 해결하고, 다음 행동 하나만 확정한 짧은 상태 캡슐을 남겨 또 다른 전환에도 이어갈 수 있게 한다.

## 언제 쓰나 / 쓰지 않나
- 이전 대화가 보이지 않거나, Codex가 요구사항·현재 슬라이스·테스트 상태를 자신 있게 말할 수 없을 때 쓴다.
- 휴식·담당자 답변 대기·다른 작업 후 과제에 돌아왔을 때 쓴다.
- `git status` 또는 최신 E#가 PLAN의 기억과 다를 가능성이 있을 때 쓴다.
- 실제 오류가 이미 최소 재현되고 원인만 좁히면 되는 경우는 `6.1 debug ($sk-debug)`를 쓴다.
- 같은 시도 반복으로 전략을 잃은 경우는 `6.2 unstuck ($sk-unstuck)`을 쓴다.
- 마감 때문에 기능을 포기할 우선순위를 정하는 경우는 `6.5 timebox ($sk-timebox)`를 쓴다.

## 입력과 사전 확인
1. 과제 루트에서 시작한다. 모든 도구 경로는 `sk/`로 시작하며, `sk/` 자체는 과제 코드가 아니다.
2. `sk/work/SPEC.md`의 `## 한 장 요약`, `## 구현 시 반드시 지킬 규칙 Top 5`, `## 0. 상태`, 관련 R#/P#/A#/G#/T#를 읽는다.
3. `sk/work/PLAN.md`의 `## 시간 예산`, `## 슬라이스 S`, `## 위험 실험`, `## 축소 결정`, 기존 `## 상태 캡슐`을 읽는다.
4. `sk/work/EVIDENCE.md`의 `## 실행 기록`에서 최신 코드 상태의 PASS/FAIL/STALE E#를 찾는다.
5. `sk/work/REVIEW.md`에 있다면 `## 리뷰 발견 F`, `## 준수 감사`의 미해결 항목을 확인한다.
6. `sk/work/DM_LOG.md`에 있다면 최근 M# 답변과 `## 정책 목록 P`를 확인한다. 답변 원문을 새 정책으로 과장하지 않는다.
7. `git status --short`, `git diff --stat`, 필요한 경우 `git diff -- <파일>`로 노트 밖의 실제 변경을 읽기 전용으로 확인한다.

## 절차
1. 작업 노트가 없거나 섹션이 비어 있으면 없는 사실을 추정하지 않는다. `0.1 context ($sk-context)` 또는 `2.1 spec ($sk-spec)`으로 필요한 기준을 다시 만든다.
2. SPEC에서 목표 1줄, P0 요구, 필수 제출물 경로, 금지·제약 Top 5를 5줄 이내로 추린다.
3. PLAN에서 마지막 완료 S#, 진행 중 S#, 멈춘 이유, 남은 시간, 축소 확정 항목을 추린다.
4. EVIDENCE에서 마지막 PASS E#, 최근 FAIL E#, 그때의 명령·코드 상태를 찾는다. PASS라도 현재 코드가 달라졌으면 STALE 후보로 표시한다.
5. REVIEW와 DM_LOG에서 현재 구현에 아직 반영하지 않은 F#/P#가 있는지 대조한다.
6. 읽기 전용 diff를 통해 실제 변경 파일을 나열하고, 현재 S# 범위·기록된 파일과 다르면 “기록-현실 불일치”로 표시한다.
7. 현재 상태를 검증할 가장 작은 기존 테스트 또는 명령 하나를 고른다. 기존 실행 명령을 우선하고, 새 의존성·새 서버·새 패키지를 임의로 도입하지 않는다.
8. 선택한 명령을 한 번 실행하고 종료 코드·통과/실패 수·핵심 출력·코드 상태를 E#으로 기록한다. 실행하지 못하면 이유와 미검증 범위를 기록한다.
9. 실행 결과가 마지막 PASS E#와 같으면 다음 미완료 S# 하나를 선택한다. 다르면 구현을 재개하지 말고 `6.1 debug ($sk-debug)`로 차이를 최소 재현한다.
10. 사용자·기존 변경이 내 변경과 섞여 있거나 현재 diff가 위험하면 복구하지 말고 `6.3 rollback ($sk-rollback)`에서 백업·승인 절차를 따른다.
11. 정확히 10줄 이내의 상태 캡슐을 `PLAN.md`에 갱신한다. 최신 E#와 다음 행동 하나를 반드시 넣는다.
12. 최소 경로는 SPEC Top 5 읽기 → PLAN/EVIDENCE 최신 상태 읽기 → git 상태 확인 → 핵심 테스트 1회 → 상태 캡슐 → 다음 행동 하나다.

```bash
# 과제 루트에서 실제 상태를 읽기 전용으로 확인한다.
git status --short
git diff --stat
git diff -- <현재-S번호와-관련된-파일>

# 마지막 PASS 증거와 같은 기존 명령을 우선 사용한다.
<기존-핵심-테스트-명령>
```

## 판단 기준·분기
- SPEC 상태가 `BLOCKED`이고 H 영향 G#가 남음 → 코딩을 재개하지 말고 `1.3 dm-questions ($sk-dm-questions)` 또는 `1.5 dm-confirm ($sk-dm-confirm)`으로 넘긴다.
- SPEC 상태가 `READY-WITH-ASSUMPTIONS` → A#와 되돌릴 지점을 상태 캡슐에 명시하고, 독립적인 S#만 진행한다.
- 현재 diff가 기록한 파일과 다름 → 누가·왜 바꿨는지 단정하지 말고, 사용자에게 범위를 확인하거나 `6.3 rollback ($sk-rollback)`으로 안전하게 분리한다.
- 핵심 테스트가 PASS이고 최신 E#보다 코드가 변하지 않음 → PLAN의 다음 P0 S#를 `4.2 implement ($sk-implement)`로 진행한다.
- 핵심 테스트가 FAIL → 새 기능을 시작하지 말고 `6.1 debug ($sk-debug)`로 원인을 좁힌다.
- 검증 명령이 환경·서버 부재로 실행 불가 → E#에 미검증을 남기고, 필요한 환경 조건을 확인한다. 결과를 추정 PASS로 바꾸지 않는다.
- 남은 시간이 15분 이하 → 재개한 기능이 P0가 아니면 `6.5 timebox ($sk-timebox)`으로 먼저 전환한다.

## 작업 노트 기록
`sk/work/PLAN.md`의 `## 상태 캡슐`만 갱신하며 다른 스킬의 섹션은 덮어쓰지 않는다. 다음 10줄 형식을 쓴다.

```markdown
## 상태 캡슐
- 시각: `<시각>` / 남은 시간: `<분>`
- 목표: `<과제 목표 1줄>`
- 완료: `<완료 S#·P0 또는 필수 제출물>`
- 진행 중: `<현재 S#·파일·함수>`
- 최신 검증: `E# — <명령>, PASS/FAIL/미검증`
- 현재 코드 상태: `<짧은 해시 또는 변경 파일 요약>`
- 실패·차단: `<E# 또는 없음>`
- 미해결 정책: `<G#/A#/P# 또는 없음>`
- 결정된 축소: `<cut 항목 또는 없음>`
- 다음 행동 1개: `<스킬 ID + 명령 또는 확인>`
```

- 핵심 명령을 실행했다면 `sk/work/EVIDENCE.md`의 `## 실행 기록`에 E#을 추가한다. 표 열은 `E# | 시각 | 명령·작업 디렉터리 | 대상 R/T | 기대 | 실제 결과 요약 | 판정 | 코드 상태`를 지킨다.
- 계획이 바뀌면 `## 슬라이스 S`와 `## 시간 예산`도 사실에 맞게 갱신한다. 정책·요구 자체는 이 스킬에서 고치지 않는다.

## 채팅 출력 형식
1. **복구한 사실**: 목표, 현재 S#, 남은 시간, SPEC 상태.
2. **노트 근거**: 마지막 PASS/FAIL E#, 최근 P#/A#/G#, 미해결 F#.
3. **실제 상태**: git 변경 파일과 기록-현실 일치/불일치.
4. **핵심 실행**: 명령, 실제 결과, 새 E# 또는 미실행 이유.
5. **10줄 상태 캡슐**: PLAN에 기록한 내용.
6. **다음 행동 하나**: `4.2 implement`, `6.1 debug`, `6.3 rollback`, `6.5 timebox` 중 실제 근거가 있는 경로.

## 완료 기준
- SPEC·PLAN·EVIDENCE·DM_LOG·REVIEW의 최신 사실을 읽고, 대화 기억보다 우선했다.
- 마지막 증거와 현재 코드 상태의 일치 여부가 확인되었다.
- 핵심 테스트 또는 명령을 실제 실행했거나 실행 불가 이유가 E#에 있다.
- PLAN의 상태 캡슐이 10줄 이내이며 다음 행동은 하나다.
- 정책 차단, 테스트 실패, 위험한 diff, 시간 부족을 각각 적절한 스킬로 인계했다.

## 금지
- 노트나 실행 결과를 읽지 않고 이전 대화의 설명만으로 코드를 수정하지 않는다.
- 현재 diff를 모두 내 변경이라고 가정하거나, 사용자 승인 없이 되돌리지 않는다.
- 실행하지 않은 테스트를 PASS라고 기록하지 않고, 오래된 E#를 현재 증거처럼 쓰지 않는다.
- 새 세션이라는 이유로 기존 테스트·원본 데이터·제출물을 삭제하거나 대규모 리팩터링하지 않는다.
- 비밀값·개인정보를 상태 캡슐에 쓰지 않으며, 네트워크·패키지 설치·외부 제출을 임의로 하지 않는다.
- `sk/` 도구 폴더를 과제 구현 대상으로 취급하지 않는다.
