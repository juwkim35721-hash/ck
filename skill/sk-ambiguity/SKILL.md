# 모호성·충돌·누락 탐지

## 목적

요구사항을 “알아서 처리”로 넘기지 않도록, 결과를 바꾸는 빈칸과 충돌을 `G#`로 드러낸다.
문서·테스트·데이터로 먼저 스스로 해결할 수 있는지를 확인한 뒤에만 담당자 질문을 추천한다.
이 스킬은 정답을 발명하지 않고, 기본안과 그 위험을 분리해 기록한다.

## 언제 쓰나 / 쓰지 않나

- `→ 1.1 requirements ($sk-requirements)` 뒤, 첫 DM 묶음을 만들기 전에 사용한다.
- CSV, JSON, JSONL의 실제 데이터, 샘플 입출력, 경계 조건이 있는 테스트가 있으면 우선 사용한다.
- 문서·테스트·담당자 답변 사이가 충돌하거나 출력 스키마가 불완전할 때 사용한다.
- 이미 담당자가 확정한 `P#`를 재논의하거나 구현 상세 설계를 정하는 용도는 아니다.
- 답변을 확정 정책으로 전환하는 일은 `→ 1.4 dm-answers ($sk-dm-log)`에 맡긴다.

## 입력과 사전 확인

- `sk/work/DISCOVERY.md`의 `## 필수 제출물`, `## 요구사항 후보 R`, `## 제약 C`를 읽는다.
- README·명세·샘플·기존 테스트·관련 설정에서 근거를 다시 확인한다.
- 데이터 파일은 과제 규칙상 읽을 수 있는 경우에만 경로·형식을 확인한다.
- 민감한 값은 출력하지 않는다. 필드명, 개수, 범위, 마스킹한 예시만 사용한다.
- 모든 모호성을 DM으로 보내지 않는다. 영향도와 자체 해결 가능성을 먼저 판정한다.

## 절차

1. **R/C별 결정 지점을 표시한다.** 입력, 경계, 우선순위, 출력, 오류, 범위마다 “누가·무엇을·언제·어떻게”가 빠졌는지 본다.
2. **14개 범주를 한 번씩 통과한다.** 아래 표에서 해당 없음도 확인하되, 억지로 G를 만들지 않는다.
3. **문서 내부 충돌을 찾는다.** 같은 용어·필드·정렬·오류 규칙이 문서마다 다르면 원문과 위치를 나란히 적는다.
4. **테스트와 문서를 대조한다.** 기대값이 다른 경우 현재 테스트를 우선시하지 말고 충돌 G로 등록한다.
5. **데이터가 있으면 실제 분포를 확인한다.** 허용될 때만 아래 명령을 실행한다.

```bash
python3 sk/snippets/data_audit.py <파일>
```

6. **감사 결과를 해석한다.** 결측·음수·0·중복·상위 범주가 발견됐다는 사실은 정책이 아니라 질문의 근거다.
7. **각 빈칸의 결과 차이를 예시로 쓴다.** 예: `quantity=-2`를 제외하면 합계 10, 오류면 요청 실패처럼 결과가 달라지는 형태로 적는다.
8. **자체 해결 순서를 적용한다.** 공식 문서 → 최신 샘플 → 제공 테스트 → 관찰된 코드 순으로 확인하고, 해소됐으면 G를 만들지 않는다.
9. **처리 방식을 정한다.** `DM 질문`, `가정`, `자체 해결`, `보류` 중 하나와 결정 필요 시점을 기록한다.
10. **영향도를 매긴다.** 제출 실패·금액/집계·API 호환성·데이터 손실은 H, 제한된 화면·P1 기능은 M, 문구·비핵심은 L로 둔다.
11. **기본안을 제한적으로 제안한다.** 담당자 답 전 진행에 필요한 경우에만 되돌릴 지점과 위험을 적는다.
12. **DM 후보를 선별한다.** H 우선, 질문 하나의 답이 여러 G를 해소하면 묶어 `→ 1.3 dm-questions ($sk-dm-questions)`으로 넘긴다.

### 14개 점검 범주

| 범주 | 확인 질문 | 실제 차이를 적을 예 |
| :--- | :--- | :--- |
| 용어 정의 | “유효”, “완료”, “최신”의 뜻은? | 상태값 포함/제외 |
| 결측·빈 값·타입 오류 | null·빈 문자열·숫자 문자열은? | 행 제외/오류/기본값 |
| 이상치·경계 등호 | 음수, 0, 임계값과 같은 값은? | `>=`/`>` 결과 차이 |
| 중복·멱등성 | 같은 ID가 두 번 오면? | 합산/최신/거절 |
| 정렬·동점 | 1차·2차 키와 방향은? | ID 오름/입력순 |
| 수치 형식·반올림·단위 | 소수 자리·반올림 시점은? | 1.005 처리 차이 |
| 시간대·기간 경계 | 기준 시간대·끝 시각 포함은? | 자정 레코드 포함 |
| 규칙 충돌 우선순위 | A와 B가 동시에 참이면? | 차단/예외 중 무엇 우선 |
| 오류 처리 방식 | 한 행 오류가 전체 실패인가? | 400/부분 성공 |
| 출력 스키마·빈 결과 | 빈 배열·null·누락 필드는? | `[]` vs `null` |
| 성능·규모 | 행 수·응답 시간 한계는? | 전량 메모리 가능 여부 |
| 범위·비목표·수정 파일 | 어디까지 구현·수정 가능한가? | UI 포함 여부 |
| 권한·보안 | 접근 불가·민감 필드 처리? | 마스킹/거절 |
| 제출 형식 | 파일명·경로·실행 방식은? | 경로 오답 방지 |

### `data_audit.py`의 한계

- CSV, JSON, JSONL만 대상이며 TSV·Excel·Parquet는 지원하지 않는다.
- 숫자 판정은 값의 50% 초과가 파싱될 때의 휴리스틱이며, 정책 판정이 아니다.
- 결측 토큰은 고정 목록이고, 파일 전체를 메모리에 읽는다.
- 손상된 JSONL 줄에서는 중단할 수 있다. 실패하면 오류 사실을 남기고 다른 읽기 전용 방법을 택한다.
- 상위값 출력에 민감정보가 있으면 해당 값을 노트·DM에 옮기지 않는다.

## 판단 기준·분기

- 공식 문서가 한 가지 결과를 분명히 말하면 `자체 해결`로 기록하고 G를 닫는다.
- 공식 문서와 담당자 답변 또는 테스트가 충돌하면 H로 올리고 DM 확인 후보로 둔다.
- 기본안이 외부 인터페이스·금액·데이터 삭제에 영향을 주면 담당자 답 전 확정하지 않는다.
- 결과 차이가 없거나 구현 내부 선택일 뿐이면 G가 아니라 설계 판단으로 `→ 3.2 design ($sk-design)`에 넘긴다.
- 데이터 감사에서 음수·null이 0건이어도 미래 입력 정책이 불명확하면 문서·테스트 근거를 더 확인한다.
- H G가 없고 P0에 필요한 빈칸이 없으면 DM을 위한 지연보다 `→ 2.1 spec ($sk-spec)`을 진행한다.
- 시간이 부족하면 출력 스키마, 오류, 경계값, 충돌 우선순위, 제출 형식 다섯 범주만 우선 점검한다.

## 작업 노트 기록

`sk/work/DISCOVERY.md`의 기존 섹션을 보존하고 `## 모호성 G`만 생성·갱신한다.

| ID | 모호성·충돌·누락 | 결과가 달라지는 구체 예시 | 영향도 | 확인 근거·자체 확인 결과 | 기본안 | 처리 | 결정 필요 시점 | 상태 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| G1 | 음수 수량 처리 미정 | `-2` 제외/오류/합산 | H | 샘플에 음수 3건, 문서 무언급 | 오류로 격리 | DM 질문 | 구현 전 | 열림 |

- ID는 기존 최대 번호 다음으로 부여하며, 해결된 행을 삭제하지 않고 상태·근거만 갱신한다.
- `처리`는 `DM 질문`, `가정`, `자체 해결`, `보류` 중 하나로 쓴다.
- `기본안`은 결정이 아니라 답이 없을 때의 임시 기준임을 분명히 한다.
- 담당자에게 물을 G에는 질문 하나당 하나 이상의 결과 예시를 남긴다.

## 채팅 출력 형식

1. 점검한 14개 범주와 특히 문제가 된 범주
2. H → M → L 순서의 열린 G 표 요약
3. 데이터 감사 실행 여부, 핵심 수치 또는 실행 실패 사실과 한계
4. 문서·테스트 충돌과 스스로 해소한 항목
5. DM으로 보낼 후보 1~3개와 각 질문의 결정 필요 이유
6. 다음 행동: `→ 1.3 dm-questions ($sk-dm-questions)` 또는 `→ 2.1 spec ($sk-spec)`

## 완료 기준

- 14개 범주를 실제 과제에 맞게 훑었고, 관련 G마다 결과 차이 예시가 있다.
- H/M/L, 근거, 기본안, 처리 방식, 결정 시점이 기록돼 있다.
- 데이터 감사는 실행 결과 또는 미실행 이유와 한계를 남겼다.
- 문서로 답할 수 있는 질문을 DM 후보에 남기지 않았다.
- 구현·정책 확정을 하지 않고 다음 담당 스킬로 넘겼다.

## 금지

- 관찰된 null·음수·중복만으로 제외·합산·오류 정책을 정하지 않는다.
- 감사 스크립트의 통계를 전체 데이터 품질 보증 또는 정책 근거로 과장하지 않는다.
- 원본 데이터, 테스트, 코드, 설정을 수정하거나 민감값을 출력하지 않는다.
- 평가·채점 방식이나 문서에 명시된 답을 담당자에게 다시 묻지 않는다.
- 단순한 스타일 선호를 H 모호성으로 부풀리거나, 구현 가능한 내부 설계를 DM으로 넘기지 않는다.
