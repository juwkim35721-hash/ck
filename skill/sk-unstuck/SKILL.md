# AI 반복 루프 탈출

## 목적
AI와의 작업이 같은 오류·큰 diff·맥락 혼동을 반복할 때 즉시 편집을 멈추고, 사실 기반의 짧은 상태로 문제를 재정의한다.
마지막 통과 상태와 현재 상태의 차이를 분리해, 더 작은 슬라이스·판별 실험·복구·범위 축소 중 한 가지 안전한 다음 행동을 고른다.

## 언제 쓰나 / 쓰지 않나
- 같은 오류 또는 같은 테스트 FAIL이 수정 후 2회 이상 반복되면 쓴다.
- 한 곳을 고치면 다른 곳이 깨지고, 같은 파일을 여러 차례 왕복 수정하거나 `git diff`가 의도보다 계속 커지면 쓴다.
- AI가 R#/P#·파일 역할·현재 코드 상태를 앞선 대화 기억과 혼동하면 쓴다.
- 새 세션에서 단지 작업을 재개하는 경우는 `6.4 resume ($sk-resume)`를 먼저 쓴다.
- 원인이 이미 한 가지로 확정된 단발 오류는 `6.1 debug ($sk-debug)`에서 바로 고친다.
- 시간이 절대적으로 부족해 우선순위를 끊어야 하는 경우는 `6.5 timebox ($sk-timebox)`를 쓴다.

## 입력과 사전 확인
1. 실패한 시도 2회 이상에 대한 명령, 오류 요약, 바꾼 파일·함수, 결과 E#를 모은다.
2. `sk/work/SPEC.md`의 한 장 요약, Top 5, 관련 R#/P#/A#/T#를 읽는다. 대화에서 기억한 요구보다 이 문서를 우선한다.
3. `sk/work/PLAN.md`의 `## 시간 예산`, `## 슬라이스 S`, `## 위험 실험`, `## 축소 결정`, `## 상태 캡슐`을 읽는다.
4. `sk/work/EVIDENCE.md`의 마지막 PASS E#와 최근 FAIL E#를 찾는다.
5. 읽기 전용으로 현재 상태를 확인한다: `git status --short`, `git diff --stat`, 필요 시 `git diff -- <파일>`.
6. 남은 시간, 제출 필수물, 지금 작업 중인 S# 하나를 명확히 한다. 모르면 코드 편집을 시작하지 않는다.

## 절차
1. 즉시 편집·자동 수정·새 패키지 탐색을 중단한다. 현재 파일을 더 바꾸기 전에 상태를 고정한다.
2. 시도 목록을 작성한다: 시도 번호, 의도, 변경, 실행한 명령, 실제 결과, 배운 사실. “수정했다” 같은 모호한 표현을 쓰지 않는다.
3. 마지막 PASS E#의 코드 상태와 현재 diff를 대조한다. 그 사이에 추가된 파일·변경 덩어리·미추적 파일을 구분한다.
4. 현재 문제를 SPEC 언어로 한 문장으로 다시 쓴다: “S#에서 R#과 P#를 만족하려 했으나 T#가 X로 FAIL한다.”
5. 문제를 한 층으로 축소한다. 입력, 순수 함수, 저장·상태, API 계약, UI 표시 중 하나만 다음 실험 대상으로 고른다.
6. 다음 전략을 하나만 선택한다: 실제 중간값 관찰, 최소 재현, 가정 A 검증, 더 작은 독립 함수, 다른 알고리즘, 정책 질문, 안전 복구.
7. 선택 전략에 10분 타임박스를 건다. 시작 시각·끝 시각·성공 판정(예: T7의 원인 확정)을 `## 시간 예산`에 적는다.
8. 리셋 지시문을 사용해 AI에 현재 사실·금지·단일 목표를 재주입한다. 이전 대화의 넓은 요청을 반복하지 않는다.
9. 10분 안에 원인 확정 또는 회귀 테스트 PASS가 나오면 `6.1 debug ($sk-debug)` 또는 `4.2 implement ($sk-implement)`로 한 슬라이스만 진행한다.
10. 10분 후에도 차단되면 현재 diff의 회복 가능성을 평가한다. 위험하면 `6.3 rollback ($sk-rollback)`을, 기능 가치가 낮거나 시간이 부족하면 `6.5 timebox ($sk-timebox)`을 선택한다.
11. 정책이 차단 요인이면 답을 지어내지 말고 `1.3 dm-questions ($sk-dm-questions)`의 긴급 단일 질문을 만든다. 답을 기다리는 동안 독립 작업만 한다.
12. 최소 경로는 편집 중단 → 마지막 PASS/현재 diff 확인 → 문제 한 문장 → 10분 실험 하나 → 결과에 따라 debug·rollback·timebox 중 하나 선택이다.

```bash
# 과제 루트에서 읽기 전용으로 상태를 분리한다.
git status --short
git diff --stat
git diff -- <반복-수정한-파일>
```

## 판단 기준·분기
- 같은 실패가 2회 반복 → 코드 변경을 세 번째로 시도하지 말고 최소 재현과 가설 표로 전환한다.
- diff가 현재 S# 밖 파일까지 번짐 → 무관한 변경을 추가하지 말고 `6.3 rollback ($sk-rollback)`의 범위 식별·백업을 요청한다.
- 마지막 PASS E#가 없거나 코드 상태를 알 수 없음 → `6.4 resume ($sk-resume)`의 상태 검증부터 수행한다.
- 실제 중간값이 명세 기대값과 다름 → `6.1 debug ($sk-debug)`에서 입력·정책 분기를 판별한다.
- 실제 값은 맞는데 테스트 기대가 P#/문서와 다름 → G#로 남기고 `1.3 dm-questions ($sk-dm-questions)`로 확인한다.
- 남은 시간이 15분 이하 → 새 접근·리팩터링을 중단하고 `6.5 timebox ($sk-timebox)`으로 전환한다.
- 복구 없이도 작은 독립 함수·T# 하나로 범위를 줄일 수 있음 → `4.1 test-first ($sk-test-first)`와 `4.2 implement ($sk-implement)`으로 한 번만 진행한다.

## 작업 노트 기록
`sk/work/PLAN.md`에서 다른 섹션을 덮어쓰지 않고 다음을 갱신한다.

- `## 슬라이스 S`: 현재 S# 상태를 `중단`, `10분 재시도`, `복구 검토`, `축소 후보` 중 하나와 근거 E#로 표시한다.
- `## 위험 실험`: 실험 ID, 가설, 종료 시각, 성공 판정, 실제 결과를 한 행으로 추가한다.
- `## 시간 예산`: 소요·남은 시간과 10분 타임박스의 종료 시각을 갱신한다.
- `## 축소 결정`: 차단이 계속될 때 포기 가능한 P1/P2 후보와 영향만 미리 적고, 실제 cut은 `6.5`에서 확정한다.
- `## 상태 캡슐`: 아래처럼 10줄 이내로 현재 사실을 기록한다.

```markdown
## 상태 캡슐
- 시각: `<시각>` / 남은 시간: `<분>`
- 목표: `S3 / R2`
- 마지막 PASS: `E9 — <명령>`
- 현재 FAIL: `E11 — T7, <짧은 오류>`
- 반복 시도: `2회, <파일·함수>`
- 확정 사실: `<관찰된 값 또는 원인>`
- 미해결: `G2 또는 가설 H2`
- 다음 10분 행동: `<명령·관찰>`
- 중단 조건: `<언제 rollback/timebox로 갈지>`
- 다음 인계: `6.1 debug` 또는 `6.3 rollback`
```

- 실행한 실험의 명령·결과는 `sk/work/EVIDENCE.md`의 `## 실행 기록`에 E#으로도 남긴다.

## 채팅 출력 형식
1. **루프 발동 근거**: 반복 횟수, E#, 변경 파일, 남은 시간.
2. **시도 표**: 시도 | 변경 | 명령 | 실제 결과 | 배운 사실.
3. **상태 차이**: 마지막 PASS와 현재 diff의 핵심 차이.
4. **재진술**: S#/R#/P#/T#를 포함한 한 문장 문제 정의.
5. **10분 계획**: 선택 전략 1개, 성공 판정, 중단 조건.
6. **리셋 지시문**: 아래 형식의 복붙용 text 블록.
7. **인계**: debug·rollback·timebox 중 선택한 하나와 이유.

```text
현재는 반복 수정 루프를 중단한 상태다.
과제 루트의 sk/work/SPEC.md에서 R#·P#·T#만 사실로 사용하라.
마지막 통과 증거는 <E#>, 현재 실패는 <E#>이며 오류는 <요약>이다.
현재 변경 범위는 <파일·함수>이고, 이 밖의 파일은 수정하지 마라.
목표는 <단일 판별 질문 또는 T#> 하나다.
코드를 바로 고치지 말고 가설 2개와 각각의 가장 싼 판별 실험을 제시하라.
한 번에 한 변수만 바꾸고, 실제 출력으로 채택·폐기하라.
10분 안에 원인이 확정되지 않으면 더 수정하지 말고 rollback 또는 timebox를 권고하라.
실행 결과는 E#으로, 상태는 PLAN.md의 상태 캡슐로 기록하라.
```

## 완료 기준
- 편집 중단 시점의 실제 상태, 마지막 PASS, 최근 FAIL, 현재 S#가 구분되어 있다.
- 반복 시도에서 배운 사실과 아직 검증하지 않은 가설이 분리되어 있다.
- 다음 행동은 10분 안의 단일 실험이며 성공·중단 조건이 있다.
- PLAN의 상태 캡슐과 시간 예산이 갱신되고, 실행한 실험은 E#으로 남아 있다.
- 복구·DM·범위 축소가 필요한 경우 해당 스킬과 이유가 명시되어 있다.

## 금지
- “한 번만 더”라는 이유로 같은 유형의 수정 세 번째 시도를 하지 않는다.
- 현재 diff를 확인하지 않은 채 파일을 덮어쓰거나 여러 파일을 한꺼번에 리팩터링하지 않는다.
- 담당자 답변·SPEC·실행 결과 대신 대화 기억이나 AI 추측을 사실로 쓰지 않는다.
- 사용자의 승인 없이 코드 복구를 실행하지 않는다. 복구는 `6.3 rollback` 절차를 따른다.
- 실패·미검증을 PASS로 기록하거나, 비밀값·개인정보를 상태 캡슐에 적지 않는다.
- `sk/` 도구 파일을 수정하거나 외부 제출·배포·패키지 설치를 임의로 하지 않는다.
