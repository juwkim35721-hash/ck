# 슬라이스 하나 최소 변경 구현

## 목적

실패가 확인된 수용 테스트를 통과시키는 데 필요한 한 개 S#만 구현한다.
명세의 R#/P#/A#를 코드 위치, 테스트 T#, 실행 증거 E#와 연결해 시간이 지나도 변경 이유를 설명할 수 있게 한다.

## 언제 쓰나 / 쓰지 않나

- 4.1 test-first가 현재 T#의 기대된 RED 또는 명확한 구현 목표를 확인한 뒤 사용한다.
- 슬라이스 전체를 한 번에 돌릴 때는 `→ 4.0 build-loop ($sk-build-loop)`가 이 규칙으로 단계 2(GREEN)를 진행한다.
- S# 하나의 범위, 영향 파일, 보존할 인터페이스를 설명할 수 있을 때 사용한다.
- 설계를 처음 정하거나 대안 비교가 필요한 큰 구조 변경이면 먼저 3.2 design으로 보낸다.
- 실제 실패의 원인을 모르는 상태에서 수정 연타를 하지 않는다. 6.1 debug을 사용한다.
- 명세 상태가 BLOCKED이거나 핵심 P0 정책이 불명확하면 1.3 dm-questions 또는 2.4 spec-gate로 되돌린다.

## 입력과 사전 확인

1. `sk/work/SPEC.md`의 `## 0. 상태`, `## 구현 시 반드시 지킬 규칙 Top 5`, `## 3. 요구사항 R`, `## 4. 제약 C`, `## 5. 확정 정책 P`, `## 6. 가정 A`, `## 10. 입출력·데이터 계약`, `## 11. 수용 테스트 표 T`, `## 12. 추적표`를 읽는다.
2. `sk/work/PLAN.md`의 `## 슬라이스 S`, `## 위험 실험`, `## 축소 결정`에서 지금 할 S# 하나와 시간 한도를 확인한다.
3. `sk/work/BRIEF.md`의 코드 지도와 `sk/work/DECISIONS.md`의 관련 DD#를 읽고, 호출자·공개 인터페이스·수정 금지 파일을 확인한다.
4. 4.1의 E#에서 RED가 실제 미구현임을 확인한다. 없으면 먼저 4.1 test-first($sk-test-first)를 수행한다.
5. 수정 전 읽기 전용으로 현재 변경 범위와 기존 테스트 명령을 확인한다. 다른 사람의 변경을 되돌리거나 섞지 않는다.

## 절차

1. 시작 선언을 만든다: `S# / R# / T# / 적용 P#·A# / 변경 후보 파일 / 보존 인터페이스`.
2. 대상 함수의 호출자와 반환값·오류 경로를 읽어 영향 범위를 좁힌다. 필요한 파일만 연다.
3. 입력 경계, 핵심 규칙, 출력 변환 중 어느 층을 고칠지 정하고, 현재 공개 API·CLI·스키마를 유지할 방법을 정한다.
4. 정책 P#는 코드의 조건과 결과가 한눈에 대응되도록 구현한다. A#를 적용하면 되돌릴 위치를 명확히 한다.
5. 가장 작은 변경을 한다. 무관한 이름 변경, 포맷 정리, 모듈 이동, 성능 튜닝을 함께 넣지 않는다.
6. 컴파일·정적 검사·대상 테스트를 해당 과제 명령으로 실행한다. 실제 출력에서 T#가 GREEN인지 확인한다.
7. 영향을 받는 기존 테스트를 실행한다. 실패 시 변경과의 관련성을 먼저 판별하고, 추측 수정 대신 6.1 debug으로 분리한다.
8. 새 결정이 있었으면 `sk/work/DECISIONS.md`에 DD#을, AI 초안의 오류를 사람이 교정했으면 AI#을 사실만 기록한다.
9. `sk/work/PLAN.md`에서 S# 상태와 다음 행동을 갱신하고, `sk/work/SPEC.md`의 추적표에 구현 위치와 E#를 연결한다.
10. 의미 있는 명령마다 `sk/work/EVIDENCE.md`에 E#을 남긴 뒤, 다음 S# 또는 4.3 harden으로 넘긴다.

## 판단 기준·분기

- if 대상 테스트가 GREEN이고 관련 회귀 테스트도 통과한다 → S#을 `완료` 후보로 표시하고 4.3 harden($sk-harden)으로 관련 경계만 점검한다.
- if 대상 테스트가 GREEN이지만 기존 공개 인터페이스나 출력 스키마가 바뀌었다 → 완료가 아니다. 3.2 design 또는 6.1 debug으로 영향과 호환 방법을 다시 정한다.
- if 구현 중 P#/A#로 정할 수 없는 동작을 만난다 → 새 정책을 코드에 숨기지 않는다. 조건·선택지·영향 R#을 G 후보로 정리하여 1.3 dm-questions($sk-dm-questions)에 넘긴다.
- if 문서와 담당자 답변 P#가 충돌한다 → 조용히 하나를 선택하지 않는다. 1.4 dm-answers($sk-dm-log)와 2.1 spec($sk-spec)에 충돌을 남긴다.
- if 한 S#가 여러 파일·규칙으로 커져 20분 안에 검증할 수 없다 → 계획을 멈추고 3.1 plan($sk-plan)으로 더 작은 수직 슬라이스로 나눈다.
- if 같은 실패에 두 번 이상 추측 수정했다 → 편집을 중단하고 6.2 unstuck($sk-unstuck) 또는 6.1 debug($sk-debug)으로 전환한다.
- 시간이 부족하면 P0의 이미 RED인 T#를 통과시키는 최소 경로만 완성하고, P1/P2·리팩터링은 6.5 timebox에 축소 후보로 넘긴다.

## 작업 노트 기록

`sk/work/PLAN.md`의 `## 슬라이스 S`는 3.1 plan이 만든 표 열(`ID | 목표·대상 R/AC/P | 선행조건 | 최소 변경 경계 | 검증 T | 완료 증거 | 상태`)을 그대로 유지한다. 현재 S# 행의 `완료 증거`와 `상태` 칸만 갱신하고, 행이 없으면 같은 열로 추가한다.

상태는 `대기`, `진행`, `완료`, `막힘`, `보류`, `축소` 중 하나로 쓰고, 완료는 GREEN 증거 E#가 있을 때만 쓴다. 다음 행동은 채팅 보고에 쓴다.

`sk/work/SPEC.md`의 `## 12. 추적표`에는 구현된 요구사항 행만 갱신한다. 표 열은 반드시 다음 의미를 유지한다.

| R | AC | T | 구현 위치 | 증거 E | 상태 |
| :--- | :--- | :--- | :--- | :--- | :--- |

`구현 위치`에는 실제 상대 파일 경로와 함수·클래스명을 쓴다. 상태는 5.1 verify와 같은 `PASS`, `FAIL`, `미검증`만 쓴다. 구현 직후에는 대상 T가 GREEN이어도 `미검증`으로 둔다. `PASS`는 5.1이 정상·경계·실패 경로와 전체 스위트를 확인한 뒤 올린다.

`sk/work/DECISIONS.md`에는 필요할 때만 다음 형식의 `## DD<n> 제목` 블록을 추가한다.

- 상황과 선택지 A/B
- 선택과 근거 R#/P#/C#
- 포기한 것, 영향 파일·함수, 되돌리는 방법

AI가 처음 제안한 코드의 문제를 고쳤다면 `## AI 교정 기록` 아래에 `AI# | 문제 | 발견 방법 | 내가 지시한 수정 | 확인 E#`를 추가한다. AI 사용 사실만으로 AI#을 만들지 않는다.

`sk/work/EVIDENCE.md`의 `## 실행 기록`에는 5.2 evidence와 같은 `E# | 시각 | 명령·작업 디렉터리 | 대상 R/T | 기대 | 실제 결과 요약 | 판정 | 코드 상태` 열을 사용한다. 코드 변경 뒤 과거 E#은 현재 코드의 증거가 아니므로 필요하면 `STALE`로 표시한다.

## 채팅 출력 형식

다음 순서의 번호 목록으로 보고한다.

1. `슬라이스 선언`: S#, R#, T#, P#/A#, 보존한 인터페이스.
2. `변경`: 실제 수정 파일·함수와 각 변경의 목적.
3. `의도적 비변경`: 이번 S#에서 하지 않은 리팩터링·기능.
4. `검증`: 실행한 명령, 종료 코드, 대상/회귀 테스트 결과와 E#.
5. `추적 갱신`: PLAN 상태, SPEC 추적표, DD#/AI# 여부.
6. `판정`: 완료·부분완료·막힘과 근거.
7. `다음`: 4.3 harden, 다음 4.1 test-first, 또는 6.1 debug.

## 완료 기준

- S# 하나만 다뤘고, 변경 범위가 R#/P#/A#와 연결된다.
- 4.1에서 정한 대상 T#가 실제 실행에서 통과한다.
- 관련 회귀 테스트를 실행했거나 미실행 사유를 명시했다.
- PLAN, SPEC 추적표, EVIDENCE가 실제 결과에 맞게 갱신되었다.
- 새 설계 판단과 AI 교정이 있었다면 DD#/AI#으로 남았다.

## 금지

- 한 번에 여러 S#를 구현하거나 요구사항과 무관한 리팩터링을 섞지 않는다.
- P#/A# 없는 예외 정책, 정렬 규칙, 기본값을 발명하지 않는다.
- 기존 공개 인터페이스, 출력 스키마, 테스트를 조용히 변경하지 않는다.
- 새 의존성을 설치하거나 네트워크를 사용하지 않는다. 필요하면 대회 규칙과 사용자 확인을 먼저 받는다.
- `sk/` 도구 파일을 과제 코드처럼 수정·테스트·린트하지 않는다.
- `git reset --hard`, `git clean`, `git stash`, 강제 체크아웃, push·배포·제출을 실행하지 않는다.
