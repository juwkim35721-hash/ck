# 제출 전 최종 점검·도구 정리

## 목적

- 실제 파일·최신 실행 증거·제출 규칙을 대조해 GO, CONDITIONAL, NO-GO 판정을 내린다.
- 제출물의 이름·경로·형식, 보고서, 전체 테스트, 서버 요구, 민감정보, 변경 범위를 짧은 체크리스트로 확인한다.
- 도구 정리는 공식 제출 규칙과 사용자의 명시적 결정에 따라 안내만 하며, 제출·업로드·push·삭제를 실행하지 않는다.
- 모든 새 실행 결과를 `sk/work/EVIDENCE.md`의 `## 실행 기록`에 E#으로 남기게 한다.

## 언제 쓰나 / 쓰지 않나

- 보고서가 작성된 뒤, 실제 제출 버튼을 누르기 직전에 쓴다.
- 6.5 시간 부족 판단 뒤 최소 제출물을 고정하고 위험을 투명하게 표시할 때 쓴다.
- 테스트 실패·리뷰 차단 이슈·필수물 누락이 발견되면 제출 판정 대신 복구 우선순위를 정할 때 쓴다.
- 기능 구현, 대규모 코드 리뷰, 새 기능 추가가 목적이면 이 스킬을 쓰지 않는다.
- 남은 시간이 15분 이하일 때 새 기능이나 리팩터링을 시작하게 하지 않는다.
- 후속 서술형 단계가 AI·복붙 금지 시간에 들어갔다면 9-qa 자료를 열거나 생성하지 않는다.

## 입력과 사전 확인

1. `sk/work/SPEC.md`의 `## 0. 상태`, `## 2. 필수 제출물`, `## 4. 제약 C`, `## 11. 수용 테스트 표 T`, `## 12. 추적표`, `## 14. 게이트 결과`를 읽는다.
2. `sk/work/EVIDENCE.md`의 `## 실행 기록`에서 최신 코드 기준 E#인지, 종료 코드·통과 수·작업 디렉터리가 적혔는지 확인한다.
3. `sk/work/REVIEW.md`의 `## 리뷰 발견 F`, `## 준수 감사`에서 차단·높음·미충족·미검증을 확인한다.
4. `sk/work/PLAN.md`의 `## 축소 결정`, `## 상태 캡슐`로 남은 시간과 제외 기능을 확인한다.
5. 보고서 경로가 `SPEC.md` 2절의 필수 제출물 표와 일치하는지, 파일이 실제 존재하는지 확인한다.
6. AI 허용 시간이라면 `sk/work/QA_CARD.md`의 존재·완성 여부만 준비 상태로 확인한다. AI 금지 시간이라면 접근·생성을 즉시 중단한다.
7. 과제 안내에서 제출 방법, 허용 파일, 서버 호스트·포트, 도구 흔적 제거 요구를 다시 확인한다. 안내에 없는 규칙을 만들지 않는다.
8. 실행 명령과 결과를 주장하려면 실제로 실행할 시간·환경이 있는지 먼저 확인한다.

## 절차

1. 현재 상태를 읽기 전용으로 확인한다.

```bash
git status --short
git diff --stat
```

2. `SPEC.md` 2절의 필수 제출물 표를 기준으로 아래 표를 채운다. 파일의 존재만으로 내용이 충족됐다고 판정하지 않는다.

| 제출물 | 지정 경로·파일명 | 실제 존재 | 형식·이름 | 내용/근거 | 상태 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 구현물 | SPEC 2절 기준 | 예/아니오 | 일치/불일치 | R#/T# | PASS/FAIL |
| 보고서 | SPEC 2절 기준 | 예/아니오 | 일치/불일치 | 8.1 산출물 | PASS/FAIL |
| 기타 필수물 | SPEC 2절 기준 | 예/아니오 | 일치/불일치 | 과제 안내 | PASS/FAIL |

3. 최신 코드 기준 전체 테스트를 한 번 새로 실행한다.
   - 0.1에서 확인한 표준 명령 또는 과제 문서의 명령만 쓴다.
   - 명령, 작업 디렉터리, 대상 R#/T#, 기대 결과, 종료 코드, 통과/실패 수, 핵심 출력, 판정을 E#으로 기록한다.
   - 시간이 없어 재실행하지 못하면 “이전 E#만 존재, 현재 코드 미검증”으로 기록한다.
4. 서버 제출물인 경우 과제의 호스트·포트 요구를 정확히 대조한다.
   - 지정 포트를 바꾸지 않는다. 웹 과제는 내장 Browser 미리보기용 `0.0.0.0` 바인딩인지 확인하고(과제 문서 우선), `localhost`·`127.0.0.1` 바인딩이면 수정 여부를 사용자에게 확인한다.
   - 필요한 경우 과제 안내의 실행 명령으로 서버를 시작한다.
   - 도달성 1차 확인은 다음 형식으로 한다. 이 도구는 GET 1건을 5초 제한으로 확인하고 2xx가 아니면 실패를 알리므로, 계약 검증을 대체하지 않는다.

```bash
python3 sk/snippets/smoke_test.py http://127.0.0.1:<포트>/<경로>
```

   - 종료 코드가 0이 아니면 도달성을 통과로 쓰지 않는다.
   - 이어서 SPEC 10절 계약의 메서드·상태 코드·응답 스키마·오류 경로를 기존 테스트 또는 명시된 클라이언트로 대조한다.
   - 서버를 시작했다면 과제에 안전한 종료 방법으로 정리하고, 종료 여부를 E#에 적는다.
5. 보고서를 최종 대조한다.
   - 보고서가 지정된 경로·이름·형식으로 존재하는지 확인한다.
   - 1~5절, 2절 4열 표, 실제 T#/E#/DD#/P# 근거, 미검증 표기가 유지되는지 확인한다.
   - 보고서에 테스트가 모두 통과했다고 적었다면 새 E#이 이를 뒷받침하는지 확인한다.
6. 민감정보·제출 잡음·변경 범위를 점검한다.
   - 비밀값, 액세스 토큰, 비밀번호, 개인식별정보, 민감 원본값을 `git diff`와 제출 파일에서 찾는다.
   - 자동 생성 캐시·디버그 출력·대용량 로그·의도하지 않은 파일은 사용자에게 보여주고, 삭제·변경은 승인된 범위에서만 한다.
   - `sk/` 폴더는 도구이므로 과제 코드 검사·테스트 대상에 넣지 않는다.
7. QA 준비 상태를 확인한다.
   - 제출 전 AI 사용이 허용된 시간에만 `9.2 qa-card` 결과의 준비 여부를 확인한다.
   - 카드가 없다면 제출 차단으로 단정하지 말고 과제 안내·남은 시간과 함께 “준비 권장” 또는 “규칙상 불필요”로 표시한다.
   - AI 금지 서술형 단계가 시작된 후에는 자료를 생성·열람·복사하지 않는다.
8. 도구 흔적 처리 필요 여부를 분기한다.
   - 과제 공식 규칙에 제거 요구가 없으면 `sk/`, `AGENTS.md` 관리 구역, `.agents/skills/sk-*`를 임의로 삭제하지 않는다.
   - 제거 요구가 있으면 먼저 사용자에게 다음을 확인받는다: 보존할 `sk/work/` 노트, 정확한 제출 범위, 제거 승인.
   - 필요한 노트는 과제 루트 밖의 사용자가 지정한 안전한 위치로 복사한 뒤에만 정리 절차를 안내한다.
   - 사용자가 명시 승인하고 공식 규칙이 요구할 때만 아래 명령을 제안한다. 이 스킬은 직접 실행하지 않는다.

```bash
python3 sk/scripts/install.py --uninstall
```

   - 위 명령은 관리 구역·설치된 스킬·git 제외 설정에 영향을 줄 수 있으므로 결과를 확인한 뒤에만 `sk/` 폴더 제거 여부를 사용자가 결정하게 한다.
9. 발견을 GO, CONDITIONAL, NO-GO로 판정한다.
   - GO: 필수 제출물 존재·형식 일치, 최신 전체 테스트 PASS, 차단 이슈 없음, 보고서 존재, 민감정보 없음, 제출 규칙 충족.
   - CONDITIONAL: 제출은 가능하나 미검증·낮은 위험·사용자 확인·도구 정리 결정 같은 조건이 남아 있고 이를 명확히 적을 수 있다.
   - NO-GO: 필수물 누락, 최신 테스트 FAIL, 차단/높음 미해결, 서버 계약 위반, 민감정보 노출, 공식 규칙 위반이 있다.
10. 제출·업로드·push는 실행하지 않고, 사용자가 실행할 마지막 행동과 남은 위험을 채팅으로 보고한다.

## 판단 기준·분기

- if 필수 제출물의 경로·이름·형식 중 하나라도 불일치 → then NO-GO, → 8.1 report (`$sk-report`) 또는 해당 제출물 보완을 우선한다.
- if 최신 전체 테스트 E#가 PASS이고 코드 변경 뒤 재실행됨 → then 검증 항목 PASS로 표시한다.
- if 이전 PASS 뒤 코드가 바뀌었거나 E#가 STALE임 → then CONDITIONAL이며 → 5.1 verify (`$sk-verify`) 재실행을 우선한다.
- if 테스트가 FAIL 또는 실행 오류임 → then NO-GO, 원인 분석은 → 6.1 debug (`$sk-debug`)로 넘긴다.
- if 리뷰에서 차단·높음 F#가 미해결 → then NO-GO 또는 공식 기한·영향을 포함해 사용자에게 에스컬레이션한다.
- if 서버 요구가 있으나 도달성 확인이 실패함 → then 통과로 쓰지 않고 → 5.4 api-contract (`$sk-api-contract`) 또는 → 5.5 ui-smoke (`$sk-ui-smoke`)로 넘긴다.
- if `QA_CARD.md`가 없고 AI 허용 시간이 남음 → then 제출을 막지 말고 → 9.2 qa-card (`$sk-qa-card`)를 권장한다.
- if AI 금지 서술형 시간이 시작됨 → then QA 관련 스킬·카드 사용을 중단하고 제출 규칙을 우선한다.
- if 도구 제거 요구가 불명확함 → then 현 상태를 보존하고 공식 안내 확인 및 사용자 결정을 기다린다.
- if 남은 시간이 15분 이하 → then 새 기능·리팩터링을 금지하고 필수물, 최신 증거, 보고서, 제출 버퍼만 유지한다.

## 작업 노트 기록

- 실제로 실행한 최종 테스트·서버 확인·파일 검사만 `sk/work/EVIDENCE.md`의 `## 실행 기록` 표에 새 E#으로 적는다.
- E# 행에는 `시각 | 명령과 작업 디렉터리 | 대상 R/T | 기대 | 실제 결과 요약 | 판정 | 코드 상태`를 빠뜨리지 않는다.
- 명령을 실행하지 않은 제출물 존재 점검은 E#으로 꾸미지 말고 채팅 체크리스트에서 “미실행 점검”으로 구분한다.
- 기존 E#의 결과가 코드 변경으로 오래됐으면 원문을 고치지 말고 STALE임을 표시한다.
- 이 스킬은 `SPEC.md`, `PLAN.md`, `REVIEW.md`의 기존 섹션을 덮어쓰지 않는다.
- 도구 정리의 사용자 승인·공식 규칙 근거는 실행 기록과 별도로 채팅에 명시하고, 확인 전에는 변경하지 않는다.

## 채팅 출력 형식

1. **제출 판정**: `GO` / `CONDITIONAL` / `NO-GO`와 한 줄 이유
2. **필수 제출물 표**: 경로·존재·형식·근거·상태를 한 표로 제시
3. **최신 검증**: 새 E# 목록, 전체 테스트·서버 확인 결과, 미검증 항목
4. **차단/조건**: F#, FAIL, STALE, 사용자 확인이 필요한 항목과 다음 행동
5. **도구 흔적**: 공식 규칙 확인 결과, 보존할 노트, 사용자 승인 필요 여부
6. **사용자 실행 행동**: 제출 버튼·업로드·push는 사용자가 수행한다고 명시

## 완료 기준

- `SPEC.md` 2절의 모든 필수 제출물이 실제 경로·이름·형식과 대조됐다.
- 최신 코드 기준 전체 테스트가 실제 실행돼 E#에 기록됐거나, 미실행 사유와 위험이 분명히 표시됐다.
- 서버 요구·보고서·민감정보·git 변경 범위가 해당되는 경우 점검됐다.
- GO, CONDITIONAL, NO-GO 중 하나와 근거·차단 조건이 명확하다.
- QA 준비 여부가 대회 시간 규칙을 침해하지 않도록 확인됐다.
- 도구 정리는 공식 규칙과 사용자의 명시적 승인 전에는 실행되지 않았다.
- 외부 제출·업로드·push·삭제·강제 복구가 실행되지 않았다.

## 금지

- 최신 실행 근거 없이 “제출 가능”, “전체 통과”, “서버 정상”이라고 단정하지 않는다.
- 필수 제출물 누락, 실패 테스트, 차단 리뷰 발견, 민감정보를 숨겨 GO로 바꾸지 않는다.
- `git reset --hard`, `git clean`, `git stash`, 강제 체크아웃, 원본 데이터·기존 테스트 삭제를 하지 않는다.
- 공식 규칙과 사용자 승인 없이 도구 파일·관리 구역·설치된 스킬·작업 노트를 제거하지 않는다.
- `sk/work/`의 노트를 보존 확인 없이 정리하지 않는다.
- 서버 호스트·포트·제출 형식·채점 방식을 추측하거나 임의로 바꾸지 않는다.
- 제출 버튼, 업로드, 외부 push, 자격증명 전송을 실행하지 않는다.
