# 내 변경만 안전하게 되돌리기

## 목적
실패한 구현·디버깅 변경을 과제 원본이나 사용자의 작업에 손대지 않고 안전하게 되돌린다.
먼저 현재 상태를 복구 가능한 형태로 보관하고, 되돌릴 정확한 범위를 사용자에게 보여 준 뒤, 명시 승인을 받은 파일·덩어리만 복구하고 테스트로 확인한다.

## 언제 쓰나 / 쓰지 않나
- 마지막 통과 증거 이후 내 변경 때문에 회귀가 생겼고, 원인 분리가 더 위험하거나 시간이 부족할 때 쓴다.
- `6.2 unstuck ($sk-unstuck)`이 현재 diff가 커졌거나 회복 불명확하다고 판정했을 때 쓴다.
- 잘못된 수정 하나를 제거해야 하지만 과제 원본·사용자 변경과 섞여 있을 가능성이 있을 때 쓴다.
- 원인이 이미 확정되어 한 줄만 고치면 되는 경우에는 `6.1 debug ($sk-debug)`를 쓴다.
- 단순히 코드 스타일을 이전으로 바꾸거나, 사용자 승인 없이 작업 전체를 버리기 위한 스킬이 아니다.

## 입력과 사전 확인
1. 되돌릴 이유, 관련 S#/R#/T#, 마지막 PASS E#와 현재 FAIL E#를 적는다.
2. `sk/work/PLAN.md`의 `## 슬라이스 S`에서 현재 슬라이스·소유 범위를 확인한다.
3. 읽기 전용으로 `git status --short`, `git diff --name-only`, `git diff -- <파일>`을 실행한다.
4. 파일마다 변경을 `내 변경`, `사용자·기존 변경`, `소유 불명`으로 나눈다. 소유 불명은 복구 대상에서 제외한다.
5. 저장소 여부를 확인한다. Git이 아니면 현재 파일을 복사해 보관할 수 있는지, 마지막 정상 복사본이 어디인지 확인한다.
6. 원본 데이터·기존 테스트·사용자 작성물·수정 금지 파일은 어떤 경우에도 되돌릴 대상으로 넣지 않는다.

## 절차
1. 복구 단위를 파일 또는 확인 가능한 patch hunk로 결정한다. “전체 작업”처럼 넓은 단위는 허용하지 않는다.
2. 현재 상태를 먼저 `sk/work/rollback/<시각>.patch`에 저장한다. 시각은 정렬 가능한 형식으로 쓴다.
3. Git 환경에서는 추적 파일 diff를 patch로 저장하고, 내 미추적 파일은 `sk/work/rollback/<시각>/` 아래에 원래 상대 경로를 보존해 복사한다.
4. Git이 아닌 환경에서는 복구 대상 파일의 현재 사본과 복구 기준 사본을 각각 `sk/work/rollback/<시각>/`에 보관하고 출처를 적는다.
5. 백업 파일 존재·크기·대상 목록을 확인한다. patch를 만들었다고 복구가 완료된 것이 아니며, 비밀값이 들어간 파일은 복사·노트 기록 전에 안전 규칙을 확인한다.
6. 사용자에게 복구 계획을 보여 준다: 복구 이유, 대상 파일·hunk, 보존할 사용자 변경, 백업 경로, 복구 후 실행할 테스트, 되돌리지 않을 항목.
7. **명시적인 사용자 승인**을 기다린다. 승인 전에는 backup·분석·계획만 하고 과제 파일을 복구하지 않는다.
8. 승인된 파일 하나씩에만 파일 단위 복구 또는 특정 patch hunk의 역적용을 수행한다. 각 파일 뒤에 diff로 예상 범위인지 확인한다.
9. 복구 후 `git status --short`와 `git diff --stat`으로 실제 변경 범위를 다시 확인한다.
10. 마지막 PASS 재현 명령, 복구 대상의 회귀 테스트, 가능한 관련 전체 테스트를 실행한다. 실행하지 못한 것은 미검증으로 남긴다.
11. 복구 결과·테스트 결과를 E#으로 기록하고 PLAN의 S# 상태를 `복구됨`, `부분 복구`, `복구 실패` 중 실제 상태로 갱신한다.
12. 최소 경로는 범위 식별 → patch/복사 백업 → 사용자 승인 → 파일 하나 복구 → 테스트 1회 → E# 기록이다.

```bash
# 과제 루트에서: 복구 전 읽기 전용 범위 확인
git status --short
git diff --name-only
git diff -- <복구-후보-파일>

# 백업 예시: patch에는 현재 추적 파일의 변경만 담긴다.
mkdir -p sk/work/rollback
git diff -- <복구-후보-파일> > sk/work/rollback/<YYYYMMDD-HHMMSS>-<S번호>.patch

# 미추적 파일은 내 파일임이 확인된 경우에만 상대 경로를 보존해 복사한다.
mkdir -p sk/work/rollback/<YYYYMMDD-HHMMSS>-<S번호>
cp --parents <내-미추적-파일> sk/work/rollback/<YYYYMMDD-HHMMSS>-<S번호>/
```

## 판단 기준·분기
- 파일에 사용자·기존 변경과 내 변경이 섞임 → 파일 전체 복구를 하지 않는다. hunk를 분리할 수 없으면 사용자에게 기준 버전을 확인받는다.
- 내 변경의 시작점이 마지막 PASS E# 이후로 확실함 → 그 파일·hunk만 복구 후보로 제시한다.
- 백업 저장에 실패하거나 대상 파일을 읽을 수 없음 → 복구를 중단하고 실패 사실을 E#으로 기록한다.
- 사용자 승인이 없음 또는 범위가 모호함 → 과제 파일은 변경하지 않고 질문한다.
- Git 명령을 쓸 수 없음 → 정상 사본으로의 교체 전·후 파일 해시와 사본 경로를 제시하고 동일하게 승인받는다.
- patch 역적용이 깨끗하게 적용되지 않음 → 강제로 적용하지 않는다. 현재 diff를 다시 보여 주고 부분 복구 계획을 새로 승인받는다.
- 복구 후 마지막 PASS 테스트도 FAIL → 복구 성공으로 단정하지 말고 `6.1 debug ($sk-debug)` 또는 `6.2 unstuck ($sk-unstuck)`으로 넘긴다.
- 남은 시간이 15분 이하 → 복구 후 새 기능을 시작하지 말고 `6.5 timebox ($sk-timebox)`의 제출 우선순위를 따른다.

## 작업 노트 기록
`sk/work/PLAN.md`의 `## 슬라이스 S`에서 해당 S# 행 또는 블록에 다음을 추가한다.

| S# | 상태 | 복구 범위 | 백업 | 승인 | 복구 후 다음 행동 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| S3 | 부분 복구 | `src/a.py`의 내 분기 | `rollback/20261031-1415-S3.patch` | `<시각·승인 요약>` | T7 재실행 |

`sk/work/EVIDENCE.md`의 `## 실행 기록`에는 실제 백업 확인·복구 후 검증 명령을 E#으로 추가한다.

| E# | 시각 | 명령·작업 디렉터리 | 대상 R/T | 기대 | 실제 결과 요약 | 판정 | 코드 상태 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| E18 | 14:22 | `<테스트 명령>` / `<경로>` | T7 | 마지막 PASS와 동일 | 12 passed | PASS | `<상태>` |

- `sk/work/rollback/`에는 patch 또는 복사본만 둔다. 복구 사유·승인·결과는 PLAN/EVIDENCE에 남겨 재개 시 알 수 있게 한다.

## 채팅 출력 형식
1. **복구 필요성**: S#/R#/T#, 마지막 PASS E#, 현재 FAIL E#.
2. **범위 표**: 파일 또는 hunk | 소유 판정 | 복구 여부 | 이유.
3. **백업 확인**: 상대 경로, 포함 범위, 미추적 파일 처리 여부.
4. **복구 계획**: 승인 후 수행할 단일 파일 순서와 보존할 변경.
5. **승인 질문**: “위 범위만 되돌리고 T#를 재실행해도 될까요?”를 명시한다.
6. **승인 후 결과**: 실제 복구 범위, 테스트 PASS/FAIL/미검증, E#, 다음 인계.

## 완료 기준
- 되돌릴 변경이 파일·hunk 수준으로 식별되고 사용자·기존 변경과 구분되어 있다.
- 현재 상태가 `sk/work/rollback/` 아래 복구 가능한 형태로 보관되었다.
- 과제 파일 복구 전 사용자 승인을 받았고, 승인 범위를 넘지 않았다.
- 복구 후 상태 확인과 관련 테스트 결과가 E#에 실제로 기록되었다.
- PLAN에 복구 상태와 다음 행동이 남아 있으며, 미검증을 숨기지 않았다.

## 금지
- `git reset --hard`, `git clean`, `git stash`, 강제 체크아웃, 대량 삭제를 사용하지 않는다.
- 승인 없이 `git restore`, 파일 교체, patch 역적용 등 과제 파일을 바꾸는 행동을 하지 않는다.
- 원본 데이터·기존 테스트·사용자 변경·소유 불명 파일을 내 변경으로 간주하지 않는다.
- backup만 만든 뒤 검증 없이 “복구 완료”라고 말하지 않는다.
- 외부 push·배포·제출·업로드를 실행하지 않으며, 비밀값을 patch·채팅·노트에 노출하지 않는다.
- `sk/`의 도구 파일을 복구 대상으로 다루지 않는다. 작업 기록과 백업은 `sk/work/`에만 둔다.
