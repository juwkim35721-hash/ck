# 실행 증거 기록

## 목적

의미 있는 실행의 사실을 짧고 재현 가능하게 `E#`로 기록한다.
명령, 작업 디렉터리, 대상 R/T, 기대, 실제 결과, 판정, 코드 상태를 연결한다.
실행 뒤 코드가 바뀌었을 때 이전 근거를 STALE로 표시해 낡은 통과의 재사용을 막는다.

## 언제 쓰나 / 쓰지 않나

- 테스트, 빌드, 데이터 대사, API 호출, UI 핵심 흐름을 실행한 직후 쓴다.
- 4-build, 5-verify, 6-debug, 7-review, 8-submit의 의미 있는 실행에 적용한다.
- 계획·추정·코드 읽기만 한 일은 E#가 아니라 해당 작업 노트에만 기록한다.
- 실패의 원인을 고치려는 일은 → 6.1 debug ($sk-debug), 요구사항 완결성 판정은 → 5.1 verify ($sk-verify) 책임이다.

## 입력과 사전 확인

1. 실행 전에 대상 R#, P#, T#, S#와 기대 결과를 `sk/work/SPEC.md`에서 찾는다.
2. `sk/work/EVIDENCE.md`의 `## 실행 기록`에서 마지막 E#와 현재 코드 상태를 확인한다.
3. `sk/work/BRIEF.md`의 `## 환경`에서 허용된 명령·작업 디렉터리·서버 조건을 확인한다.
4. 명령에 토큰·개인정보·민감 데이터가 출력될 가능성이 있으면 출력 축소 또는 마스킹을 준비한다.
5. 실제로 실행할 수 없는 경우에는 실행한 것처럼 E#를 만들지 말고 차단 사유를 채팅에만 알린다.

## 절차

1. E# 번호를 정한다.
   기존 최대 번호 다음만 쓰고 실패·미검증 실행도 번호를 건너뛰지 않는다.
2. 실행 목적을 한 문장으로 고정한다.
   예: `T8에서 빈 입력이 P3의 오류 응답 규칙을 따르는지 확인`처럼 R/T/P와 연결한다.
3. 기대 결과를 실행 전 기록한다.
   SPEC의 AC, T, P 또는 독립 손계산을 근거로 `종료 코드 0`, `HTTP 400`, `총합 17`처럼 쓴다.
4. 현재 코드 상태를 수집한다.
```bash
git rev-parse --short HEAD
git status --short
```
   Git이 아닌 과제면 실제로 수정된 파일 목록만 적고 없는 해시를 만들지 않는다.
5. 명령을 과제 루트 또는 실제 작업 디렉터리에서 한 번 실행한다.
   표에는 인자까지 충분히 써 재현 가능하게 하되 비밀값은 `[REDACTED]`로 대체한다.
6. 종료 코드와 핵심 결과를 확인한다.
   테스트는 통과·실패·건너뜀 수, API는 메서드·상태·핵심 필드, 데이터는 행 수·합계 같은 최소 사실을 잡는다.
7. 전체 출력을 복사하지 말고 판정에 필요한 1~3개 줄만 발췌한다.
   스택 트레이스, 민감 값, 수천 행 출력은 보관하지 않고 오류 종류·위치만 요약한다.
8. EVIDENCE 표에 E# 행을 즉시 추가한다.
   시간은 실행을 마친 시각과 시간대를 포함해 쓰고 실제 결과는 기대와 분리한다.
9. 판정을 붙인다.
   기대와 실제가 일치하면 `PASS`, 다르면 `FAIL`, 실행·판정 근거가 없으면 `미검증`으로 쓴다.
10. 관련 코드 변경 뒤 기존 행을 점검한다.
    E#의 코드 상태와 현재 변경 파일을 비교하고 영향 가능성이 있으면 기존 판정 앞에 `STALE —`를 붙인다.
11. 같은 명령을 새 E#로 재실행한다.
    STALE 행을 덮어써 과거 사실을 숨기지 않고 새 결과를 추가한다.
12. 연결을 갱신한다.
    T#가 확인됐으면 `sk/work/SPEC.md`의 `## 12. 추적표`에 실제 E#를 연결한다.
13. 다음 행동을 분기한다.
    FAIL은 재현 정보와 E#를 보존해 → 6.1 debug ($sk-debug)로 넘긴다.
    PASS라도 코드가 바뀌면 제출 전 → 5.1 verify ($sk-verify)에서 최신 전체 검증을 한다.

## 판단 기준·분기

- if 명령의 종료 코드는 0이지만 기대한 값·스키마가 다르다 → `FAIL`이다.
- if 종료 코드는 비0이지만 명세가 의도한 오류를 기대했고 실제 오류가 일치한다 → 기대 충족 여부로 판정한다.
- if 연결·권한·환경 문제로 실행되지 않는다 → 실제 오류를 적고 `미검증`으로 쓴다.
- if 한 실행이 여러 T#를 검증한다 → 모든 T#와 기대값을 명확히 쓸 수 있을 때만 한 E#로 묶는다.
- if 이전 E#와 코드 상태가 다르지만 무관함을 확실히 증명할 수 없다 → STALE로 표시하고 재실행한다.
- if 출력에 민감정보가 있다 → 값 대신 개수·형식·마스킹 표시만 기록한다.
- if 시간이 부족하다 → P0 전체 테스트와 필수 제출물 검증부터 기록하고, 미실행은 미검증으로 남긴다.

## 작업 노트 기록

`sk/work/EVIDENCE.md`에 파일이 없으면 `## 실행 기록` 제목만 만들고 기존 행을 덮어쓰지 않는다.
다음 표 열을 정확히 사용한다.

`E# | 시각 | 명령·작업 디렉터리 | 대상 R/T | 기대 | 실제 결과 요약 | 판정 | 코드 상태`

행 예시는 다음과 같다.
`E14 | 2026-10-31 14:20 KST | pytest -q (과제 루트) | R2/T4,T5 | 2개 통과·종료 0 | 2 passed, 종료 0 | PASS | a1b2c3d; src/score.py 수정`

관련 변경 후에는 기존 행의 판정을 `STALE — PASS`처럼 바꾸고 새 실행은 새 E#로 추가한다.
추적표 갱신이 필요하면 `sk/work/SPEC.md`의 `## 12. 추적표`에 E#만 연결한다.

## 채팅 출력 형식

1. `E#와 목적`: 대상 R/T/P와 검증하려던 한 문장.
2. `재현 명령`: 작업 디렉터리와 민감값을 제거한 명령.
3. `기대 / 실제`: 종료 코드, 통과·실패 수 또는 핵심 수치를 나란히 제시.
4. `판정`: PASS, FAIL, 미검증 중 하나와 짧은 이유.
5. `코드 상태`: 짧은 해시·변경 파일 또는 비Git 파일 목록.
6. `신선도·다음 행동`: STALE E# 또는 다음 프롬프트 ID·스킬.

## 완료 기준

- 실행이 실제로 끝난 뒤에만 새 E#가 있다.
- 모든 E#에 재현 가능한 명령·작업 디렉터리·대상 R/T가 있다.
- 기대와 실제가 분리되어 있고 종료 코드 또는 동등한 관찰 근거가 있다.
- 코드 상태가 기록되어 나중에 신선도를 판정할 수 있다.
- 관련 변경으로 낡은 증거는 STALE 처리되거나 재실행됐다.
- 민감 값 없이 보고서와 추적표에서 인용할 수 있다.

## 금지

- 실행하지 않은 테스트, 브라우저 확인, 담당자 답변을 E#로 기록하지 않는다.
- PASS를 먼저 정하고 실제 결과를 맞춰 쓰지 않는다.
- 전체 콘솔 로그·토큰·비밀번호·개인정보·원본 행을 작업 노트에 복사하지 않는다.
- 기존 E#를 삭제하거나 번호를 재사용해 실패 이력을 감추지 않는다.
- 과제 코드·테스트·설정·원본 데이터를 증거 기록 과정에서 수정하지 않는다.
- `git reset --hard`, `git clean`, `git stash`, 강제 체크아웃을 실행하지 않는다.
