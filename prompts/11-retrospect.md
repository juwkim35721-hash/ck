# 설명·인수인계·회고

## 사용 시점

구현·검증·제출 준비가 끝났거나 인수인계가 필요할 때 사용한다.
실제 과제 루트의 코드, diff, 실행 로그, 테스트 결과만 근거로 상태를 설명한다.
공식 안내와 현장 규칙을 우선하며, AI 사용이 허용된 단계에서만 사용한다.
후속 AI 금지 서술형·발표·평가 단계가 시작되면 이 문서와 프롬프트 사용을 즉시 중단한다.

## 필요 입력

- [과제 루트]
- [남은 시간: 분]
- [요구사항/파일/답변]: 요구사항 ID, 핵심 파일, 실제 변경 범위
- [실행 명령과 결과]: 마지막 테스트·빌드·수동 확인의 정확한 결과
- [남은 문제/정책]: 미해결 오류, 미검증 항목, 업무 규칙 또는 담당자 답변
- [인수 대상]: 다음 작업자, 심사 준비자 또는 유지보수 담당자

입력이 없거나 오래되었으면 추측하지 말고 읽기 전용으로 파일·diff·테스트 명령을 확인한다.
테스트를 실행할 수 없으면 이유와 마지막 알려진 결과를 분리해 기록한다.
공식 안내 메일의 내용, 채점 기준, 금지 규정은 제공되지 않았으므로 새로 가정하지 않는다.

## 전략

### 1. 증거를 고정한다

요구사항 ID별로 구현 위치, 호출 경로, 실행한 검증과 결과를 한 줄씩 연결한다.
대화 속 주장보다 현재 파일, 버전 관리 diff, 테스트 출력, 재현 명령을 우선한다.
성공·실패·미실행을 섞지 말고, 명령·관찰값·날짜 또는 시점을 그대로 남긴다.
비밀값, 개인 정보, 접근 토큰, 원본 민감 데이터는 인수인계에 복사하지 않는다.

### 2. 세 문장으로 설명한다

설계 문장은 문제와 제약 때문에 선택한 최소 구조 및 대안을 말한다.
동작 문장은 입력에서 핵심 처리·출력·오류 또는 예외 흐름을 실제 코드 기준으로 말한다.
검증 문장은 실행한 명령, 확인한 요구사항, 통과·실패·미검증을 구분해 말한다.
이 세 문장에는 보지 못한 코드, 수행하지 않은 테스트, 보장할 수 없는 성능을 넣지 않는다.

### 3. 인수인계의 다음 행동을 하나로 좁힌다

완료 항목과 미완료 항목을 요구사항 ID로 분리한다.
다음 담당자가 처음 실행할 명령 하나와 확인할 파일 또는 로그 하나를 지정한다.
미검증·재현 불가·정책 미확정은 영향, 현재 상태, 재개 조건을 적는다.
수정이 필요한 경우에도 이 단계에서는 원인 주장이나 변경안을 확정하지 말고 증거와 질문만 남긴다.

### 4. 개선을 우선순위화한다

개선점은 관찰된 실패, 테스트 공백, 반복 수작업, 불명확한 정책처럼 확인 가능한 사실에서만 뽑는다.
각 항목에 영향도, 근거, 예상 검증 방법을 붙이고 P0/P1/보류 중 하나로 표시한다.
P0은 필수 요구사항 위반·데이터 손상·제출 불가처럼 현재 결과를 막는 경우에만 쓴다.
근거 없는 리팩터링, 기능 추가, 모델 교체는 개선 목록에 넣지 않거나 보류로 분류한다.

### 5. 중단·전환을 결정한다

[남은 시간: 분]이 짧고 마지막 검증이 통과했으면 새 변경을 멈추고 인수인계와 제출 전 기록을 완성한다.
테스트 실패가 핵심 요구사항을 막으면 실패를 숨기지 말고 재현 명령과 영향 범위를 전달한 뒤 계획·디버깅 단계로 전환한다.
증거가 부족하면 완료 선언을 중단하고 읽기 전용 확인 또는 필요한 한 가지 질문만 수행한다.
AI 금지 평가가 시작되면 연습 질문의 모범 답안 작성, 암기 자료, 답안 교정을 하지 않고 사용을 종료한다.

## 기본 프롬프트

```text
$sk-retrospect
[과제 루트]의 현재 코드와 실제 테스트 증거만 읽기 전용으로 확인해 설명·인수인계·회고를 작성하라.
입력: [요구사항/파일/답변], [실행 명령과 결과], [남은 문제/정책], [남은 시간: 분], [인수 대상].
공식 안내에 없는 규칙이나 수행하지 않은 테스트 결과를 만들지 말고, 민감정보는 노출하지 마라.
먼저 요구사항 ID별로 구현 위치와 검증 증거를 연결한 뒤 다음을 짧게 출력하라.
1) 설계 이유 1문장, 2) 실제 동작과 예외 1문장, 3) 검증 명령·결과·미검증을 담은 1문장.
그 다음 완료/미완료, 재현 명령 하나, 다음 담당자의 첫 행동 하나, 정책 미확정 또는 잔여 위험을 표로 정리하라.
개선점은 관찰 사실·영향도·검증 방법을 붙여 P0/P1/보류로만 정하고, 근거 없는 개선은 제외하라.
핵심 실패 또는 증거 부족이면 완료 선언 대신 중단 이유와 plan/debug 단계로 전환할 조건을 명시하라.
후속 AI 금지 평가 단계라면 답안·연습·교정을 제공하지 말고 사용 중단 사실만 알리라.
```

## 심화/반증 프롬프트

```text
$sk-retrospect
다음 인수인계 초안을 반증 중심으로 감사하라: [인수인계 초안].
[과제 루트]의 코드, diff, 테스트 출력, 요구사항 ID와 대조하되 파일을 수정하지 마라.
각 주장에 대해 증거 있음/증거 없음/상충을 표시하고, 증거가 있으면 파일·함수 또는 정확한 실행 명령을, 없으면 필요한 읽기 전용 확인 한 가지를 제시하라.
특히 입력 경계, 오류 흐름, 정책 가정, 테스트가 다루지 않은 요구사항, 성공이라고 과장한 표현을 찾는다.
검증 결과는 통과·실패·미실행으로 분리하고 추측한 원인이나 새 정책을 사실처럼 쓰지 마라.
마지막에는 인수인계가 가능한지 판정하고, 가능하면 다음 담당자의 첫 행동 하나를, 불가하면 중단 조건과 필요한 질문 하나를 제시하라.
AI 금지 평가 단계이면 감사나 답안 개선을 수행하지 말고 즉시 중단하라.
```

## 완료 기준

- 설계·동작·검증의 세 문장이 실제 코드와 실행 증거로 뒷받침된다.
- 요구사항별 완료·미완료·미검증과 재현 명령이 구분되어 있다.
- 잔여 위험과 개선점에 사실 근거, 우선순위, 다음 검증 방법이 있다.
- 다음 담당자가 첫 행동을 바로 실행할 수 있고 민감정보가 없다.
- 공식 안내 밖의 사실이나 실제로 하지 않은 검증을 주장하지 않는다.

## 다음 단계

검증 실패가 핵심 요구사항을 막으면 `90-debug` 또는 `04-plan`으로 돌아간다.
실행·테스트 증거가 오래되었거나 누락됐으면 `08-verify`로 돌아간다.
제출 준비 기록이 아직 없으면 `10-deliver`를 수행한다.
모든 기준을 만족하고 외부 제출 권한이 별도로 주어졌을 때만 사용자가 제출 행동을 결정한다.

## 주의

이 단계는 회고와 인수인계이며 코드 수정, 외부 push·배포·제출, 원본 데이터 변경을 수행하지 않는다.
읽지 않은 파일, 확인하지 않은 정책, 실행하지 않은 테스트를 기억이나 대화만으로 확정하지 않는다.
AI 금지 서술형·발표·평가가 시작된 뒤에는 답안 제공으로 전환하지 않는다.
