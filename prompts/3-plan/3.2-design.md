# 3.2 최소 설계·대안 비교

> 스킬: `$sk-design` · 단계: 계획·설계 · 작업 노트: `sk/work/DECISIONS.md` · 사용 자료: `없음`

## 언제 쓰나

- `3.1 plan`에서 첫 S#과 시간 상한이 정해졌고, 구현 전 가장 작은 변경 경로를 골라야 할 때 사용한다.
- API·함수 시그니처·출력 스키마·오류 처리를 보존하면서 P0를 충족할 위치가 불명확할 때 사용한다.
- 기존 호출자와 테스트가 있는 과제에서 "어디에 Guard를 둘지"와 "무엇을 바꾸지 않을지"를 명시할 때 사용한다.
- 이 단계는 읽기·설계·기록만 한다. 과제 코드, 테스트, 데이터, 설정을 수정하지 않는다.
- R#/P#/T# 또는 입출력 계약이 없는 경우에는 설계를 추측하지 않고 명세 단계로 되돌아간다.

## 준비할 입력

- `sk/work/SPEC.md`: 대상 R#/AC/P#/A#/C#/T#, 특히 10절 입출력 계약과 12절 추적표.
- `sk/work/PLAN.md`: 현재 S#, 위험 실험, 시간 예산, 보류 범위.
- `sk/work/BRIEF.md`: 코드 지도·기준선·수정 금지 파일.
- `sk/work/DM_LOG.md`: 구현에 영향을 주는 최근 확정 P#과 미해결 G#.
- 실제 과제의 관련 진입점·호출자·기존 테스트 파일 위치와 남은 시간.

근거가 없는 데이터 의미·성능 목표·에러 규칙은 만들지 않는다. 모르는 것은 `미확인`과 확인 방법으로 표시한다.

## 전략 — 왜 이렇게 하나

시간 제한 과제에서 좋은 설계는 가장 많은 추상화를 만드는 것이 아니라, R#/P#/C#를 충족하면서 기존 계약과 변경 범위를 가장 작게 유지하는 것이다.

입력 → Guard → 도메인 로직 → 출력/오류 경계를 분리하면 검증 가능한 위치와 호출자 영향을 숨기지 않는다. Guard에는 입출력 계약에 있는 검증만 넣고, 업무 정책이 비면 G#로 다시 올린다.

대안은 A(기존 경계를 보존한 최소 변경)와 B(A가 부족할 때만 필요한 국소 확장)로 제한한다. 전면 재작성·새 프레임워크는 비교를 부풀리고 구현 시간을 위험하게 만든다.

## 기본 프롬프트

```text
$sk-design
너는 최소 변경 설계자다. 대상 S#의 설계를 읽기 전용으로 분석하고 과제 파일은 수정하지 마라.

대상 S#: <S#>
남은 시간: <분>
관련 명세: <R#/AC/P#/A#/C#/T#>
허용·금지 변경 범위: <파일/인터페이스/규칙>
현재 구조 단서: <진입점, 호출자, 테스트, 또는 BRIEF 참조>

sk/work/SPEC.md, sk/work/PLAN.md, sk/work/BRIEF.md, sk/work/DM_LOG.md를 먼저 읽고 실제 코드의
입력 → 현재 검증 → 핵심 처리/상태 → 출력·오류 → 호출자 흐름을 파일·함수 근거로 정리하라.
보존할 공개 인터페이스, 출력 스키마, 기존 테스트 기대값, 수정 금지 영역을 분리하라.

A=기존 흐름·호출자를 최대한 보존하는 최소 변경안, B=A가 R#/P#/C#를 충족하지 못할 때만 필요한
국소 확장안을 같은 기준(요구 충족, 변경 범위, 호출자 영향, 테스트, 위험, 시간, 되돌림)으로 비교하라.
선택안에는 Guard 위치, 도메인 로직 위치, 출력/오류 변환 위치, 영향받는 호출자, 최소 구현 순서를 넣어라.

선택의 근거·포기한 것·되돌릴 경계·검증 T#을 DD#으로 sk/work/DECISIONS.md에 기록하라.
새 정책이 필요하거나 계약 충돌이 보이면 G#로 표시하고 구현 중단·확인 행동을 제시하라.
마지막에는 첫 테스트 우선 행동과 → 4.1 test-first ($sk-test-first) 인계 내용을 보고하라.
```

## 심화 프롬프트 — 선택안의 계약 파손·과설계 반증

```text
$sk-design
아래 선택안을 실제 코드와 명세만 근거로 반증하라. 수정은 하지 말고, 과설계 또는 계약 파손을 찾는 데 집중하라.

대상 S#: <S#>
선택안/기존 DD#: <붙여넣기>
관련 R/P/C/T: <ID 목록>
현재 호출자·테스트·인터페이스: <파일/함수/관찰 결과>
남은 시간: <분>

1) A 최소 변경안이 충족하지 못하는 R#/P#/C#가 있는지 파일·함수·계약 근거로 확인하라.
2) B가 A보다 추가하는 파일, 상태, 의존성, 호출자 변경을 열거하고 각각의 필수성을 판정하라.
3) 빈 입력, 잘못된 타입, 기존 호출자, 오류 응답, 빈 결과에서 깨질 수 있는 공개 계약을 찾고 T#으로 검증할 방법을 적어라.
4) Guard가 업무 정책을 발명하거나 핵심 로직이 출력 형식을 마음대로 바꾸는 부분이 있는지 확인하라.
5) 되돌릴 파일·함수 경계가 실제로 국소적인지, 시간이 허용하는지 점검하라.

출력은 반증 결과, 유지할 최소 경계, 수정 전 확인할 사항, 중단/질문 조건 순서로 써라.
발견이 없으면 "발견 못함"과 확인한 근거를 적고, 추정으로 결함을 만들지 마라.
필요한 수정은 DD# 보완만 기록하고, 구현은 → 4.1 test-first ($sk-test-first)에서 시작하게 하라.
```

## 변형 — API·기존 호출자 호환성 우선

```text
$sk-design
대상 S#은 기존 API 또는 공개 함수의 동작을 바꿀 위험이 있다. 코드는 수정하지 말고 호환성 중심 설계를 하라.

SPEC 10절의 메서드·경로·상태 코드·본문 스키마와 실제 호출자·기존 테스트를 대조하라.
입력, 성공 출력, 오류 출력, 빈 결과 각각에서 보존할 필드·타입·정렬·null 표현·오류 상태를 표로 만들라.

A는 기존 시그니처와 응답 형태를 유지하는 변경, B는 호환 계층이 꼭 필요할 때의 국소 확장으로 제한하라.
새 필드, 기본값, 상태 코드, 예외 삼키기가 호출자에 미칠 영향을 명시하고, 증거 없는 호환성 주장은 미확인으로 두어라.

선택을 DD#으로 기록하고, 계약 검증에 필요한 T#과 이후 → 5.4 api-contract ($sk-api-contract) 인계 항목을 제시하라.
```

## 변형 — 데이터 처리 Guard 위치 결정

```text
$sk-design
대상 S#의 문제는 입력 데이터의 결측·잘못된 타입·중복·경계값 처리 위치다. 새 정책을 만들지 말고 설계만 하라.

SPEC 10절 계약, P#, A#, G#, 데이터 감사 결과와 현재 데이터 흐름을 대조해 각 이상 입력이
입구 Guard, 도메인 로직, 출력 변환 중 어디에서 처리되어야 하는지 근거와 함께 정하라.

A=입구 Guard에서 계약 위반을 격리하는 안과 B=도메인 단계에서만 처리해야 하는 불가피한 안을 비교하라.
레코드 제외, 오류 반환, null 유지, 정렬·동점은 P# 또는 A# 근거가 있을 때만 선택하라.
근거가 없으면 G#와 → 1.3 dm-questions ($sk-dm-questions) 인계로 남겨라.

DECISIONS.md에 DD#을 남기고, 정상·경계·실패 T#을 어떤 입력으로 만들지 제시한 뒤 → 4.1 test-first ($sk-test-first)로 넘겨라.
```

## 결과물 확인

- 대상 S#의 흐름이 입력 → Guard → 도메인 → 출력/오류 순으로 실제 파일·함수와 연결된다.
- 보존할 공개 인터페이스, 호출자, 기존 테스트 기대값, 수정 금지 영역이 구분된다.
- 대안 A/B가 같은 기준으로 비교되고, A가 기본·B가 필요한 경우만 남는다.
- 선택 DD#에 상황·선택지·근거·포기·영향·되돌림·T#/E# 계획이 있다.
- 새 정책, P# 충돌, 계약 공백을 억지 설계로 처리하지 않고 G#와 다음 확인 행동으로 남겼다.

## 주의

- 설계 편의로 기존 API, 출력 스키마, 공용 유틸, 설정 키를 바꾸지 않는다.
- 새 패키지 설치·네트워크 사용은 공식 규칙이 허용하고 사용자가 확인한 경우 외에는 계획하지 않는다.
- `sk/`은 도구 폴더이므로 과제 코드 지도·테스트·변경 후보에 포함하지 않는다.
- 실행하지 않은 테스트나 성능 측정 결과를 DD#의 근거로 쓰지 않는다.
- 외부 제출, 배포, push, 업로드, 자격증명 전송을 실행하지 않는다.
