# 3.1 슬라이스·시간 예산 계획

> 스킬: `$sk-plan` · 단계: 계획·설계 · 작업 노트: `sk/work/PLAN.md` · 사용 자료: `없음`

## 언제 쓰나

- `SPEC.md`가 READY 또는 READY-WITH-ASSUMPTIONS가 된 뒤, 코드·테스트를 고치기 전에 사용한다.
- P0 구현 순서가 불분명하거나 남은 시간이 줄어 우선순위·축소 기준을 다시 정할 때 사용한다.
- 위험한 데이터 계약, 호출 방식, 기존 인터페이스 문제가 전체 구현 전에 판별되어야 할 때 사용한다.
- 이 프롬프트는 계획만 만든다. 과제 코드, 기존 테스트, 원본 데이터, 설정은 수정하지 않는다.
- SPEC가 BLOCKED이거나 P0에 AC/T가 없으면 구현 계획을 억지로 만들지 말고 원인을 다음 단계로 돌린다.

## 준비할 입력

- `sk/work/SPEC.md`: 0절 상태, 한 장 요약, R/C/P/A/G, 11절 T, 14절 게이트 결과.
- `sk/work/BRIEF.md`: 실행·테스트 기준선, 코드 지도, 과제 유형.
- `sk/work/DM_LOG.md`: 최근 확정 P#와 아직 답을 기다리는 질문.
- 실제 남은 시간(분), 공식 안내상 마감·필수 제출물, 현재 기준선 E# 여부.
- 이미 시작했다면 `sk/work/PLAN.md`의 기존 슬라이스 상태와 가장 최근 E#.

입력이 없으면 없는 사실을 추정하지 말고, 읽기 전용 확인 항목 또는 가장 영향 큰 질문을 첫 행동으로 둔다.

## 전략 — 왜 이렇게 하나

P0를 기능 목록이 아니라 입력부터 출력까지 검증되는 수직 슬라이스로 나누면, 가장 작은 변경을 실제 T#로 증명할 수 있다.

시간이 촉박할수록 구현 시간을 먼저 채우지 않는다. 검증 15%, 보고서·QA 15%, 제출 버퍼 최소 10분을 먼저 보호해야 막판에 통과 여부를 모르는 제출을 막는다.

영향이 크고 불확실하며 되돌리기 어려운 가정은 전체를 만들기 전에 작은 위험 실험으로 판별한다. 실험이 상한을 넘으면 더 파지 않고 질문·가역안·범위 축소를 고른다.

## 기본 프롬프트

```text
$sk-plan
너는 해커톤 실행 계획 담당자다. 구현하거나 과제 파일을 수정하지 말고 계획만 세워라.

먼저 sk/work/SPEC.md의 상태, P0 R#/AC/P#/A#/G#, T#와 sk/work/BRIEF.md의 기준선을 읽어라.
남은 실제 시간은 <남은 시간: 분>이고, 공식 안내상 마감·제출 조건은 <공식 안내 또는 미확인>이다.
현재 기준선 또는 최근 E#은 <기준선 결과 또는 미실행>이다.

P0부터 입력→처리→출력 한 흐름으로 S# 수직 슬라이스를 만들고, 각 S#에 대상 R#/AC/P#, 선행조건,
최소 변경 경계, 검증 T#, 완료 증거, 상태를 연결하라. 가장 불확실한 고영향 항목은 전체 구현 대신
시간 상한이 있는 작은 위험 실험으로 먼저 둬라. 통과·실패·시간초과 후 행동도 각각 적어라.

검증 15%, 보고서·6문항 카드 15%, 제출 버퍼 최소 10분을 먼저 보호한 시간 예산을 만들고 합계를 확인하라.
P2 → P1 일부 → 품질 개선 순서의 축소 규칙과 30분 재계획 체크포인트도 정하라.

sk/work/PLAN.md의 ## 시간 예산, ## 슬라이스 S, ## 위험 실험, ## 축소 결정만 갱신하라.
각 표에는 실제 ID와 미검증 상태를 쓰고, 실행하지 않은 결과를 성공으로 쓰지 마라.
마지막에는 구현 시작 가능 여부, 가장 먼저 할 행동 1개, 다음 프롬프트 1개를 보고하라.
```

## 심화 프롬프트 — 기존 계획 반증·재계획

```text
$sk-plan
아래의 기존 계획을 반증 중심으로 감사한 뒤, 필요한 부분만 갱신하라. 코드·테스트·데이터는 수정하지 마라.

남은 시간: <남은 시간: 분>
기존 PLAN 상태: <sk/work/PLAN.md의 관련 표 또는 요약>
최신 SPEC/DM 변경: <새 R#/P#/A#/G# 또는 없음>
실제 실행 증거: <최근 E# 결과 또는 미실행>

다음을 순서대로 확인하라.
1) 각 P0 R#가 AC와 T#가 있는 S#에 연결되는가.
2) 위험 실험이 가장 작은 판별인지, 시간 상한과 실패 후 행동이 있는가.
3) 막힌 정책·의존성을 가능한 작업처럼 표시하지 않았는가.
4) S# 완료 증거가 E# 또는 명확한 T# 실행으로 관찰 가능한가.
5) 시간 합계가 맞고 검증 15%, 보고서·QA 15%, 버퍼 10분이 실제로 보호되는가.
6) 새 P1을 멈출 시점과 P2 → P1 일부 → 품질 개선의 축소 순서가 있는가.

문제마다 근거 ID와 영향만 짧게 제시하고, 수정된 시간 예산·S# 순서·위험 실험·축소 결정을 제시하라.
미확인 정책은 G# 또는 A#로 구분하고, H 영향이면 질문 또는 가역 경계를 다음 행동으로 적어라.
PLAN.md의 내 섹션만 갱신한 뒤 가장 먼저 해야 할 행동을 하나만 보고하라.
```

## 변형 — 시작 후 40분을 넘어도 담당자 답이 없는 경우

```text
$sk-plan
구현 시작 후 40분이 지났고 H 영향 질문 <G# 목록>에 아직 답이 없다. SPEC 상태와 A#를 읽어
답을 기다리지 않는 READY-WITH-ASSUMPTIONS 계획으로 재구성하라. 과제 파일은 수정하지 마라.

각 영향을 받는 S#에 가정 ID, 되돌릴 파일·함수 경계, 확인 시점, 잘못됐을 때 재검증할 T#를 붙여라.
답이 없어도 진행 가능한 P0와 답 없이는 시작 금지인 P0를 분리하라. 진행 가능한 P0만 시간 예산에 넣고,
위험 실험 또는 DM 확인이 해소 조건인 작업은 막힘으로 표시하라.

검증·보고서·QA·제출 버퍼는 줄이지 말고, 먼저 보류할 P2/P1과 사용자에게 보일 한계 문구를 ## 축소 결정에 기록하라.
마지막에 → 1.5 dm-confirm ($sk-dm-confirm)과 → 3.2 design ($sk-design) 중 먼저 갈 하나를 근거와 함께 제시하라.
```

## 변형 — 남은 30분 이하의 범위 축소

```text
$sk-plan
남은 시간이 <30분 이하 실제 값>이다. 새 기능을 늘리지 말고 최소 제출 가능 경로만 계획하라.

SPEC의 P0 동작, 필수 제출물, 최소 검증 E#, 보고서, QA 카드, 제출 버퍼를 고정 목록으로 두고,
각 항목의 최소 시간과 담당 S#를 배정하라. P2, P1 일부, 시각적 다듬기, 일반화, 리팩터링은
어떤 순서로 보류할지와 사용자 영향·보고서 한계 문구를 ## 축소 결정에 기록하라.

남은 15분 이하가 되는 정확한 중단 트리거를 적고, 그 뒤에는 새 기능·리팩터링을 시작하지 않도록 하라.
현재 S#의 다음 행동은 테스트 실행, 증거 기록, 필수 파일 확인 중 하나만 선택해 보고하라.
```

## 결과물 확인

- `PLAN.md`에 `## 시간 예산`, `## 슬라이스 S`, `## 위험 실험`, `## 축소 결정`이 있고 기존 타 스킬 섹션을 덮지 않았다.
- 모든 P0가 적어도 하나의 S#와 T#에 연결되고, S#마다 완료 증거가 있다.
- 시간 합계가 맞고 검증 15%, 보고서·QA 15%, 제출 버퍼 10분 이상이 보호된다.
- 위험 실험에는 상한·통과·실패/시간초과 뒤 행동이 있다.
- 미확인 답변, 미실행 테스트, 가정 A#를 확정 사실처럼 쓰지 않았다.

## 주의

- 공식 안내·담당자 확정 P#·관찰된 코드보다 가정 A#를 앞세우지 않는다.
- `sk/`은 도구 폴더이므로 과제 구현·테스트·변경 대상에 넣지 않는다.
- 외부 제출, 배포, push, 업로드, 자격증명 전송은 계획하거나 실행하지 않는다.
- `git reset --hard`, `git clean`, `git stash`, 강제 체크아웃으로 시간을 아끼려 하지 않는다.
- 민감 원본값, 토큰, 개인정보는 노트·채팅·계획 표에 적지 않는다.
