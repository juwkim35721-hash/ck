# 3.3 설계 결정·AI 교정 즉시 기록

> 스킬: `$sk-decision-log` · 단계: 계획·설계 · 작업 노트: `sk/work/DECISIONS.md` · 사용 자료: `없음`

## 언제 쓰나

- 구현 중 두 경로 중 하나를 택해 영향 파일·호출자·테스트가 달라졌을 때 DD#을 남긴다.
- AI가 제안하거나 생성한 코드에서 실제 결함·누락·과잉 변경을 발견하고 수정 지시했을 때 AI#을 남긴다.
- 디버깅에서 원인과 최소 수정이 확정됐거나, 시간 부족으로 기능·개선안을 포기했을 때 근거를 보존한다.
- 기록은 짧게 즉시 한다. 다음 세션의 기억이나 보고서 작성 때 다시 추측하지 않기 위한 것이다.
- 아직 발생하지 않은 선택, 실행하지 않은 테스트, 단순 포맷 변경은 이 프롬프트의 기록 대상이 아니다.

## 준비할 입력

- 현재 S#, 관련 R#/AC/P#/A#/C#/T#, 이미 실행한 E# 또는 `미검증` 상태.
- `sk/work/DECISIONS.md`의 마지막 DD#·AI# 번호와 기존 `## AI 교정 기록` 섹션.
- `sk/work/SPEC.md`의 정책·가정·추적표와 `sk/work/PLAN.md`의 S# 상태.
- 실제로 보았던 AI 최초 제안, 발견한 문제, 발견 방법, 내가 내린 수정 지시, 실행한 확인 결과.

AI의 긴 원문·전체 diff는 입력으로 붙이지 않는다. 문제를 특정할 파일·함수·ID·오류 요약만 준비한다.

## 전략 — 왜 이렇게 하나

설계 의도는 나중에 꾸미면 사실과 다르기 쉽다. 선택 직후에 R#/P#/C#와 파일·함수·되돌림 경계를 연결하면 Q1과 보고서의 근거가 된다.

AI 교정 기록은 AI 사용 사실이 아니라, 내가 무엇이 틀렸음을 어떻게 발견하고 어떻게 고치도록 했는지의 증거다. 테스트가 아직 없으면 `미검증`으로 남겨서 성공을 꾸며내지 않는다.

DD#과 AI#을 분리하면 설계의 트레이드오프와 AI 산출물의 품질 교정을 혼동하지 않는다. 기존 번호를 재사용하지 않아 시간 순서도 지킨다.

## 기본 프롬프트

```text
$sk-decision-log
너는 사실 기반 결정 기록 담당자다. 과제 코드·테스트·설정·데이터는 수정하지 말고 sk/work/DECISIONS.md만 갱신하라.

현재 S#: <S#>
관련 근거: <R#/AC/P#/A#/C#/T#/E# 또는 미검증>
발생한 선택 또는 AI 교정: <실제 사실>
영향 파일·함수·호출자: <목록 또는 미확인>

먼저 기존 DD#과 AI#의 최대 번호를 확인하라. 기록 대상이 설계 선택이면 새 ## DD<n> 블록을 만들어
상황, 실제 선택지 A/B와 선택, R#/P#/C#/A#·코드 관찰·시간 근거, 포기한 것과 영향, 되돌림·T#/E# 확인을 적어라.

AI 제안의 실제 문제를 교정한 일이면 정확한 ## AI 교정 기록 아래 새 ### AI<n>을 만들고,
최초 제안·문제, 발견 방법, 내가 지시한 수정, 실행한 T#/E# 결과 또는 미검증을 적어라.

각 새 기록은 2~6줄로 짧게 쓰고, 기존 기록을 지우거나 번호를 재사용하지 마라.
담당자 답변과 충돌하거나 근거 없는 정책이 필요하면 확정 기록 대신 G#와 질문 필요를 보고하라.
마지막에는 새 ID, 사실 상태, 다음에 갱신할 노트 또는 다음 프롬프트를 보고하라.
```

## 심화 프롬프트 — AI 제안의 결함을 교정한 뒤 증거까지 연결

```text
$sk-decision-log
아래 AI 산출물 교정 사건을 사실만으로 기록하고, 검증 상태를 명확히 하라. 파일 자체는 수정하지 마라.

대상 S#/R/P/T: <ID>
AI 최초 제안 또는 생성 코드의 문제: <구체 문제>
발견 방법: <T# 실패/오류 출력/호출자 대조/P# 재확인>
내 수정 지시: <지시 내용>
실제 확인: <명령·T#·E# 결과 또는 아직 미실행>
영향 파일·함수: <목록>

문제는 "AI가 틀림"처럼 쓰지 말고, 예를 들어 "빈 배열에서 첫 요소를 읽어 R3의 빈 결과 계약을 위반"처럼
입력·동작·계약을 연결해 써라. 발견 방법은 실제 실행 또는 읽기 근거만 쓰고, 실행하지 않았다면 미검증이라 적어라.

sk/work/DECISIONS.md의 ## AI 교정 기록 아래에 새 ### AI<n>을 4개 항목으로 추가하라.
설계 선택도 바뀌었다면 별도의 DD#을 추가하되, 없는 선택지를 꾸며내지 마라.
T#가 실패했거나 결과가 불명확하면 성공으로 포장하지 말고 → 6.1 debug ($sk-debug) 또는 → 5.2 evidence ($sk-evidence)를 다음 행동으로 제시하라.
보고 시 AI# 번호, 관련 ID, 확인 상태, 영향, 다음 행동을 순서대로 제시하라.
```

## 변형 — 빠른 구현 중 60초 결정 기록

```text
$sk-decision-log
지금은 S# <S#> 구현 중이며 60초 안에 결정 기록만 남겨야 한다. 코드 수정은 하지 마라.

선택 사실: <무엇을 골랐는가>
근거: <R#/P#/C#/A# 또는 코드 관찰>
영향: <파일·함수·호출자>
확인: <T#/E# 또는 미검증>

새 ## DD<n>을 정확히 5개 불릿으로 작성하라: 상황, 선택지·선택, 근거, 포기·영향, 되돌림·확인.
불확실한 정보는 미확인/미검증으로 적고, 이미 있는 DD#은 건드리지 마라.
마지막 한 줄에는 구현으로 돌아갈 때 유지할 인터페이스 또는 다음 T#을 적어라.
```

## 변형 — 디버깅 원인 확정 후 기록

```text
$sk-decision-log
디버깅으로 원인이 확정됐다. 과제 파일은 수정하지 말고 발생한 설계 선택과 AI 교정 여부만 기록하라.

최소 재현과 실제 오류: <명령/입력/오류 요약>
원인: <파일·함수·조건>
최소 수정 선택: <선택>
대안과 포기 이유: <있으면 작성, 없으면 없음>
재실행 결과: <T#/E# 또는 미검증>
AI 관여: <AI 최초 제안이 원인인지, 교정했는지, 아니면 없음>

원인으로 선택지가 달라졌다면 DD#에 근거·영향·되돌림·검증을 기록하라.
AI 최초 제안의 결함을 내가 발견해 수정 지시한 사실이 있을 때만 AI#을 별도로 기록하라.
실패가 남아 있으면 실패 사실과 다음 → 6.1 debug ($sk-debug) 행동을 적고, 통과했다면 실제 E#만 연결하라.
```

## 결과물 확인

- DD#은 `## DD<n> 제목`이고 상황·선택지/선택·근거·포기/영향·되돌림/확인이 있다.
- AI#은 정확한 `## AI 교정 기록` 아래 `### AI<n> 제목`이며 최초 문제·발견·내 수정 지시·확인이 있다.
- 번호가 기존 최대 번호보다 크고, 기존 기록을 수정·삭제·재번호하지 않았다.
- 근거에 실제 R#/P#/C#/A#/T#/E# 또는 코드 파일·함수가 연결된다.
- 실행하지 않은 확인은 `미검증`이고, 실패는 실패로 남았다.
- 민감값·토큰·개인정보·AI 긴 원문·전체 diff를 기록하지 않았다.

## 주의

- AI가 제안한 내용을 사실·근거·검증 없이 기록하지 않는다. AI 사용 사실 자체는 AI# 대상이 아니다.
- 담당자 답변의 범위를 넓혀 P#처럼 적거나, 가정 A#를 확정 정책으로 승격하지 않는다.
- 실패한 테스트를 지우거나 수정해 좋은 결과처럼 만들지 않는다.
- 결정 기록을 이유로 과제 코드·테스트·데이터·설정을 수정하지 않는다.
- `sk/`은 도구 폴더이므로 과제 구현 대상으로 다루지 않는다.
- 외부 제출, 배포, push, 업로드, 자격증명 전송을 실행하지 않는다.
