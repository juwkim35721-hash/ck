# 예외·경계·불변식 방어

## 사용 시점

수직 슬라이스가 동작한 뒤, 요구사항을 넓히기 전에 입력 경계·상태 전이·오류 처리의 실패를 재현하고 막을 때 사용한다.
공식 안내와 과제 규칙이 최우선이며, AI 사용이 허용된 단계에서만 사용한다.
후속 AI 금지 서술형이 시작되면 이 문서·스킬·암기자료 사용을 즉시 중단한다.

## 필요 입력

- [과제 루트]와 실제 실행/테스트 명령
- [남은 시간: 분], 승인된 수정 범위, 변경된 요구사항 ID
- [요구사항/파일/답변]의 입력·출력 계약, 호출자, 현재 실패 또는 의심 사례
- 권한·시간 제한·중복 처리·상태 규칙이 있다면 그 원문; 없으면 없다고 명시

입력이 없으면 파일을 바꾸지 말고 과제 루트와 재현 명령부터 확인한다.
답변, 규칙, 테스트 결과를 추정하거나 만들어 내지 않는다.

## 전략

목표는 모든 나쁜 입력을 막는 것이 아니라, 실제 계약을 깨거나 데이터·권한·상태를 손상시키는 경계를 증거로 방어하는 것이다.
먼저 기존 테스트와 최소 정상 흐름을 실행해 기준선을 기록한다. 기준선이 실패하면 새 방어 코드보다 원인 분리를 우선한다.
함수·API·배치 경계마다 입력, 출력, 변경되는 상태, 실패 전달 경로를 한 줄로 적는다.

다음 위험을 과제에 적용 가능한 것만 높은 순서로 고른다.

1. 권한 우회, 데이터 손실, 잘못된 상태 확정처럼 되돌리기 어려운 실패
2. 중복 요청·재시도·경합으로 불변식이나 멱등성이 깨지는 실패
3. 필수 키 누락, 타입/단위 오류, 최솟값·최댓값 직전/직후의 계약 위반
4. timeout·외부 실패·없는 대상에서 오류가 숨겨지거나 성공처럼 보이는 실패
5. 빈 값·0·음수·긴 값·정렬 순서처럼 정상일 수 있는 경계의 의미 훼손

각 위험은 한 번에 하나만 최소 입력으로 재현한다. 기대 동작은 계약 또는 호출자 근거로 쓴다.
빈 배열, 빈 문자열, 0, 음수는 업무상 유효할 수 있으므로 falsy 검사로 묶어 거절하지 않는다.
검증하지 않은 값으로 대체하지 말고, 계약이 정한 오류를 호출자까지 보존하거나 명시적으로 변환한다.
예외를 무조건 잡아 무시하거나 로그만 남긴 뒤 성공을 반환하지 않는다.

수정 전에는 재현 테스트가 실제로 실패하는지 확인한다. 수정은 실패 원인 한 가지와 가장 가까운 경계에서 최소화한다.
수정 후에는 새 회귀 테스트, 기존 관련 테스트, 정상 흐름을 다시 실행한다.
테스트가 불안정하면 통과로 처리하지 말고 입력·시간·외부 의존성을 분리하거나 미검증으로 남긴다.

## 기본 프롬프트

```text
$sk-harden
[과제 루트]에서 07-harden만 수행하라. 먼저 공식 규칙과 AI 허용 여부, 승인된 수정 범위, [남은 시간: 분]을 확인하라. 규칙이나 입력이 없으면 추정하지 말고 필요한 항목만 질문하라. AI 금지 서술형이 시작되면 즉시 중단하라.

변경된 요구사항 ID와 실제 호출자·테스트를 읽고, 현재 최소 정상 흐름을 실행해 기준선을 기록하라. 경계별로 입력 / 변경 상태 / 기대 출력 또는 오류 전달을 정리하라. 권한·데이터 손실·상태 불변식·중복/재시도·범위/형식·시간/외부 실패·빈 값 의미 중 적용 가능한 항목만 위험 순으로 최대 [검사 수: 3~5]개 선택하라.

각 항목은 최소 재현 입력 하나를 먼저 실행하고, 실제 실패 증거가 있을 때만 원인에 가장 가까운 최소 수정과 회귀 assert를 추가하라. 0·음수·빈 값의 업무 의미를 보존하고, 검증되지 않은 기본값·무조건 예외 무시·원본 데이터 변경·기존 실패 삭제는 하지 마라.

각 검사에 대해 `재현 입력 | 기대 동작의 근거 | 수정 또는 해당 없음 이유 | 실행 명령과 결과 | 회귀 테스트`를 보고하라. 실패하거나 실행할 수 없는 검증은 숨기지 말고 잔여 위험으로 남겨라. 외부 제출·배포·push는 수행하지 마라.
```

## 심화/반증 프롬프트

```text
$sk-harden
[과제 루트]의 현재 구현이 “정상 입력에서만 통과”한다는 가설을 반증하라. 코드 설명을 믿지 말고 계약, 호출자, 상태 변경 지점, 오류 처리 경로를 근거로 보라. [남은 시간: 분] 안에 영향이 큰 반례부터 한 번에 하나씩 재현하라.

특히 (a) 같은 요청을 두 번 보냈을 때, (b) 대상이 없거나 이미 처리된 상태일 때, (c) 필수 값이 빠졌지만 0/빈 값/음수는 유효할 수 있을 때, (d) 의존 호출이 늦거나 실패할 때, (e) 권한 없는 주체가 접근할 때를 과제 계약에 맞는 경우에만 검사하라. 각각에 대해 기대 상태와 오류가 호출자에 어떻게 보여야 하는지 명시하라.

재현된 결함만 최소로 수정하고 정상 경로·새 반례·관련 기존 테스트를 실행하라. 계약 근거가 없어 정책 선택이 필요한 경우 수정하지 말고 질문과 되돌릴 지점을 제시하라. 적용 불가 항목은 검사하지 않은 이유와 남은 위험을 표로 보고하라.
```

## 완료 기준

- 기준선과 선택한 위험의 실제 실행 명령·결과가 남아 있다.
- 각 수정은 재현 입력, 계약 근거, 최소 변경, 회귀 assert와 연결된다.
- 정상 입력뿐 아니라 적용 가능한 경계 또는 실패 경로가 검증되었다.
- 0·음수·빈 값의 의미와 기존 API/오류 계약을 임의로 바꾸지 않았다.
- 적용 불가·실행 불가·미확인 항목은 근거와 잔여 위험으로 분리했다.

## 다음 단계

완료 기준을 충족하면 `08-verify`로 넘겨 요구사항 ID별 정상·경계·실패 검증의 독립성을 점검한다.
권한 정책이나 업무 의미가 확정되지 않아 방어 동작을 선택할 수 없으면 `02-clarify`로 되돌린다.
새 결함의 원인이 불명확하면 재현 입력을 유지한 채 `90-debug`로 전환한다.

## 주의

모든 입력을 거절하는 과잉 검증, 전면 리팩터링, 인증의 임의 추가·제거를 하지 않는다.
원본 데이터·기존 테스트·사용자 관련 없는 변경을 삭제하거나 덮어쓰지 않는다.
시간이 부족하면 새 기능과 저위험 미관 작업을 중단하고, P0 방어와 회귀 실행·잔여 위험 보고를 우선한다.
정책 근거 없이 HTTP 상태, 재시도 횟수, timeout 값, 기본값을 새로 정하지 않는다.
