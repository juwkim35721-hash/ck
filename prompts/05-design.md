# 대안 비교·최소 설계

## 사용 시점

요구사항과 입출력 계약, 우선순위가 어느 정도 확인되었고 구현 직전에
기존 구조를 보존하는 가장 작은 변경 경로를 결정할 때 사용한다.
이 단계는 설계 판단을 기록하는 읽기 전용 단계이며 코드를 수정하지 않는다.
공식 안내가 있다면 그것을 최우선으로 하고, AI 사용이 허용된 단계에서만 사용한다.

## 필요 입력

- [과제 루트]: 실제 과제 디렉터리. 준비 도구 저장소를 과제로 간주하지 않는다.
- [남은 시간: 분]: 설계·구현·검증·제출 버퍼를 포함한 실시간 예산이다.
- [요구사항/파일/답변]: 요구사항 ID, 정책 답변, 샘플, 오류 사례, 기존 테스트다.
- [허용 수정 범위]: 수정 가능한 파일·공개 API·금지 영역이다.
- [현재 구조]: 관련 진입점, 호출자, 데이터 원본, 기존 인터페이스다.

입력이 비어 있으면 파일을 읽기 전용으로 확인한 뒤, 선택을 바꾸는 정보만
정확히 질문한다. 제공되지 않은 공식 규칙, 채점 방식, 데이터 의미는 추정하지 않는다.

## 전략

먼저 실제 과제 루트에서 관련 진입점과 호출자를 찾고, 현재 입력→변환→출력
흐름을 한 줄씩 요약한다. 변경 대상 밖의 리팩터링 요구는 후보에서 제외한다.

대안은 정확히 두 개를 둔다. A는 기존 경계와 호출 방식을 유지하는 최소 변경안으로
둔다. B는 A가 요구사항·계약·복구 가능성을 충족하지 못할 때에만 필요한 국소 확장안으로
둔다. 전면 재작성, 새 프레임워크, 추상 계층 추가를 대안처럼 부풀리지 않는다.

각 대안은 요구사항 충족, 변경 파일 수, 호출자 영향, 데이터 이동, 실패 처리,
테스트 가능성, 시간·복잡도, 되돌리기 지점을 같은 기준으로 비교한다. 증거가 없는
항목은 ‘미확인’으로 남기고 확인 명령 또는 질문을 붙인다.

선택안에는 입력 검증 위치, 도메인 변환 위치, 출력·오류 전달 방식, 상태를 만들거나
바꾸는 지점을 명시한다. 기존 API·스키마·데이터 원본을 보존할 수 없는 경우에는
호환 전략과 영향을 받는 호출자를 먼저 드러낸다.

실패 전략은 오류를 숨기는 기본값보다 호출자가 해석 가능한 기존 오류 계약의 보존을
우선한다. 외부 의존 실패, 빈값, 불완전 입력, 재시도 가능 여부를 실제 계약 범위에서만
표기한다. 확인되지 않은 업무 정책을 설계로 고정하지 않는다.

롤백은 작은 커밋이나 교체 가능한 함수 경계가 아니라, 되돌릴 수 있는 파일·인터페이스
변경 지점으로 적는다. B가 선택되면 A로 되돌릴 조건과 비용도 함께 적는다.

구현 순서는 하나의 수직 흐름으로 제한한다: 계약을 지키는 입력 처리, 핵심 변환,
출력 연결, 관련 테스트 순으로 둔다. 설계 중 새로운 불확실성이 핵심 선택을 바꾸면
구현으로 넘어가지 말고 02-clarify 또는 03-data-contract로 되돌린다.

## 기본 프롬프트

```text
$sk-design
너는 최소 변경 설계자다. 구현하거나 파일을 수정하지 말고 읽기 전용으로 설계하라.

[과제 루트]: [과제 루트]
[남은 시간: 분]: [남은 시간: 분]
[요구사항/파일/답변]: [요구사항/파일/답변]
[허용 수정 범위]: [허용 수정 범위]

1. 실제 과제 루트에서 관련 진입점·호출자·테스트를 확인하고 현재 데이터 흐름을 요약하라.
2. A=기존 구조·호출자를 보존하는 최소 변경안, B=A가 불충분할 때의 국소 확장안만 제시하라.
3. 두 안을 요구사항 ID, 수정 파일/인터페이스, 호출자 영향, 실패 처리, 복잡도, 검증 방법,
   롤백 지점, 남은 시간으로 비교하라. 증거 없는 내용은 미확인으로 표시하라.
4. 하나를 선택하고 선택 근거와 수정 파일별 책임, 입력→변환→출력 경계,
   최소 구현 순서, 위험을 작성하라.
5. 선택을 뒤집을 사실, 먼저 확인할 읽기 전용 명령 또는 질문, 구현 중단 조건을 명시하라.

출력 순서는 ‘현재 흐름’, ‘대안 비교’, ‘선택’, ‘최소 구현 순서’, ‘위험·롤백’,
‘검증/중단 게이트’로 한다. 공식 안내가 없거나 AI 사용이 금지된 상황에서는 추정·작성·사용을 중단하라.
```

## 심화/반증 프롬프트

```text
$sk-design
아래 선택안이 과설계 또는 계약 파손인지 반증하라. 파일을 수정하지 말고 실제 코드와 호출자만 근거로 삼아라.

[선택안]: [선택안]
[과제 루트]: [과제 루트]
[요구사항/파일/답변]: [요구사항/파일/답변]
[남은 시간: 분]: [남은 시간: 분]

- A 최소 변경안이 충족하지 못하는 요구사항을 파일·함수·계약 근거와 함께 찾거나 ‘발견 못함’으로 적어라.
- B가 A보다 추가하는 파일, 상태, 의존성, 호출자 변경을 열거하고 각각의 필수성을 판정하라.
- 입력 누락·기존 호출자·오류 경로·되돌리기 상황에서 깨질 인터페이스를 찾고 재현 가능한 확인 방법을 적어라.
- 더 작은 설계가 가능하면 제안하고, 불가능하면 그 제약의 실제 근거를 적어라.
- 확인되지 않은 정책이 선택을 바꾸면 구현 중단 및 질문으로 분류하라.

‘반증 결과’, ‘유지할 최소 경계’, ‘수정 전 확인’, ‘중단/되돌림 조건’만 간결히 출력하라.
```

## 완료 기준

- 두 대안이 같은 비교 기준으로 제시되고, 최소 변경안이 분명하다.
- 선택 근거가 실제 호출자·계약·시간 제약에 연결되고 추정은 표시된다.
- 수정 파일과 보존할 인터페이스, 데이터 흐름, 실패·롤백 지점이 구체적이다.
- 최소 구현 순서와 독립적으로 확인할 검증 항목, 중단 게이트가 있다.

## 다음 단계

선택이 계약과 시간 예산을 통과하면 06-implement에서 첫 수직 슬라이스만 구현한다.
정책·데이터 계약이 선택을 바꾸면 02-clarify 또는 03-data-contract로 돌아간다.
시간이 부족하면 92-timebox에서 필수 흐름 이외의 설계를 중단한다.

## 주의

실제 공식 메일·정책이 제공되지 않았으므로 존재하지 않는 규칙을 만들지 않는다.
후속 AI 금지 서술형이 시작되면 이 문서, 프롬프트, 스킬의 사용을 즉시 중단한다.
기존 파일, 원본 데이터, 테스트를 설계 편의상 삭제·재작성하거나 실패를 숨기지 않는다.
