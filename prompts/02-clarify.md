# 정책·모호성 확인

## 사용 시점

요구사항을 초안 수준으로 분해한 뒤, 구현 착수 전에 호출한다.
이 단계는 답을 추측해 확정하는 시간이 아니라 구현 결과를 바꾸는 정책을 확인하는 시간이다.
공식 안내 메일·공고·담당자 답변이 있으면 그것을 최우선 근거로 사용한다.
공식 안내가 제공되지 않은 상태에서는 존재하지 않는 규정이나 채점 기준을 만들지 않는다.
AI 사용이 허용된 준비 단계에서만 사용하고, AI 금지 서술형 평가가 시작되면 즉시 중단한다.

## 필요 입력
- [과제 루트]: 실제 과제 경로. 준비 도구 저장소와 혼동하지 않는다.
- [남은 시간: 분]: 답변 대기와 구현 버퍼를 판단할 시간.
- [요구사항/파일/답변]: 현재 요구사항 ID, 관련 파일·샘플, 공식 원문 또는 담당자 답변.
- [이미 확정된 사항]: 출처와 함께 기록한 결정.
- [연락 가능 여부/결정권자]: 질문을 보낼 수 있는지와 답변 기한.

입력이 없으면 파일·공식 원문을 읽기 전용으로 먼저 확인하거나, 정확히 부족한 항목 하나를 질문한다.
담당자에게 실제로 메시지를 보내거나 외부 시스템을 조작하지 말고 질문 초안만 제시한다.

## 전략
먼저 사실, 해석, 미결정을 분리한다.
사실에는 원문 인용과 출처를 붙이고, 해석에는 해당 문장이 의미하는 범위만 쓴다.
미결정에는 어떤 구현·검증·제출 결과가 달라지는지 한 문장으로 적는다.

각 미결정을 영향도 순으로 평가한다.
수용 기준·입출력·데이터 처리·권한·제출 형식·필수 우선순위를 바꾸면 높은 영향이다.
되돌리기 어려움, 잘못 구현했을 때의 재작업량, 답변을 기다릴 수 있는 시간을 함께 고려한다.
용어 정의, 취향, 코드 스타일처럼 결과를 바꾸지 않거나 코드에서 확인 가능한 것은 질문 후보에서 제외한다.

질문은 최대 3개만 남긴다.
각 질문은 하나의 정책만 묻고, 맥락·선택지·답변이 없을 때 막히는 작업을 짧게 포함한다.
답변 가능한 선택지가 명확하면 A/B 같은 선택지와 각 영향만 제시하되, 선택지를 정답처럼 강요하지 않는다.
질문이 4개 이상이면 동일한 상위 정책 아래로 묶거나 영향이 낮은 항목을 보류한다.

답변이 오면 원문, 해석, 적용 규칙을 반드시 따로 기록한다.
원문에 없는 예외나 기본값을 해석에 끼워 넣지 않는다.
서로 충돌하거나 범위가 불명확한 답변이면 충돌한 문구를 인용하고 하나의 후속 확인 질문으로 되돌린다.

답변이 없으면 미응답을 확정 정책으로 바꾸지 않는다.
일을 진행해야 하면 가장 되돌리기 쉬운 가정만 `가정(미확정)`으로 표시하고, 코드·설계에서 교체 지점과 재확인 시점을 정한다.
가정으로도 안전하게 진행할 수 없거나 높은 영향의 필수 수용 기준이 막히면 구현을 중단하고 답변 대기로 보고한다.

## 기본 프롬프트
```text
$sk-clarify
[과제 루트]와 [요구사항/파일/답변]을 읽기 전용으로 검토해 정책·모호성만 정리하라.
공식 안내가 제공되지 않았으면 그 사실을 명시하고 규정·채점·마감·AI 허용 범위를 추정하지 마라.
먼저 아래 세 구역으로 분리하라.
1) 확인된 사실: 요구사항 ID 또는 원문 근거와 출처를 함께 쓴다.
2) 해석: 사실에서 직접 따라오는 적용 범위만 쓴다.
3) 미결정: 구현 결과·검증·제출물 중 무엇이 달라지는지 쓴다.

미결정마다 영향도(높음/중간/낮음), 되돌리기 어려움, 지금 확인하지 않을 때의 손실을 판단하라.
코드·파일에서 읽어 확인할 수 있는 내용, 구현 취향, 결과를 바꾸지 않는 용어는 질문하지 마라.
높은 영향 순으로 담당자에게 보낼 질문을 최대 3개만 작성하라.
각 질문은 질문 ID, 필요한 맥락, 단일 정책 질문, 가능하면 중립적 선택지, 답변 지연 시 막히는 작업을 포함하라.
질문 초안은 작성만 하고 외부 전송은 하지 마라.

[담당자 답변]이 있으면 질문별로 원문 / 해석 / 적용 규칙을 분리해 기록하라.
원문에 없는 기본값·예외를 추가하지 말고, 충돌·불명확성은 후속 질문 하나로 표시하라.
답변이 없으면 미응답을 결정으로 바꾸지 마라.
진행이 꼭 필요할 때만 가역적인 `가정(미확정)`을 제시하고, 교체 지점·재확인 시점·영향을 적어라.
높은 영향의 필수 항목이 가정으로 안전하게 처리되지 않으면 `중단: 답변 대기`를 선언하라.

출력 순서는 다음으로 고정하라.
- 영향도 높은 질문(0~3개)
- 정책 결정 기록: ID | 근거 원문 | 해석 | 적용 규칙 | 상태
- 미응답 항목: 가정 여부 | 되돌릴 지점 | 재확인 시점
- 다음 게이트: 진행 가능 조건 또는 중단 이유
[남은 시간: 분]을 고려하되, 시간이 부족하다는 이유로 미응답 정책을 확정하지 마라.
```

## 심화/반증 프롬프트
```text
$sk-clarify
아래의 정책 결정 기록과 질문 초안을 반증 관점에서 감사하라.
입력: [요구사항/파일/답변], [이미 확정된 사항], [남은 시간: 분]

각 결정에 대해 다음을 확인하라.
- 근거가 실제 원문인지, 해석이나 추측을 사실처럼 적지 않았는가?
- 답변 하나가 입출력, 데이터 범위, 예외 처리, 제출 형식, 우선순위를 바꾸는가?
- 한 질문에 서로 독립인 정책을 두 개 이상 묶지 않았는가?
- 질문이 구현 파일에서 확인 가능한 사실이나 취향을 묻고 있지 않은가?
- 선택지가 누락된 제3의 정책을 배제하거나 답변자를 유도하지 않는가?
- 미응답 항목을 사실상 확정한 문장, 숨은 기본값, 되돌리기 어려운 선행 작업이 있는가?
- 공식 원문과 담당자 답변이 충돌할 때 어느 쪽이 무엇을 우선하는지 확인이 필요한가?

문제마다 `유지`, `질문으로 승격`, `질문에서 제외`, `중단` 중 하나를 판정하고 근거를 한 줄로 쓴다.
질문은 최대 3개를 넘기지 말고, 더 중요한 질문이 생기면 낮은 영향 질문을 제거하라.
미응답 상태에서 허용할 최소 진행안은 인터페이스를 고정하지 않는 가역 작업으로만 제안하라.
필수 수용 기준 또는 제출 형식이 불명확해 안전한 가정이 불가능하면 구현·제출 준비를 멈추고 필요한 답변을 명시하라.
최종 출력은 `수정된 질문`, `결정 기록의 수정`, `가정과 되돌릴 지점`, `진행/중단 게이트` 네 항목만 사용하라.
```

## 완료 기준
확인된 사실·해석·미결정이 섞이지 않았고, 영향도 높은 질문이 3개 이하이다.
각 담당자 답변은 원문·해석·적용 규칙으로 분리되어 있다.
미응답 항목에는 확정이 아니라 가정 여부, 되돌릴 지점, 재확인 시점이 있다.
높은 영향의 미확정 항목에 대해 진행 또는 답변 대기 게이트가 명시되어 있다.

## 다음 단계
게이트를 통과하면 확정된 정책과 명시적 가정만 03-data-contract에 전달한다.
질문 답변을 기다려야 하면 현재 기록을 보존하고 구현·제출 판단으로 넘어가지 않는다.
새 답변이 오면 이 단계를 다시 실행해 기록을 갱신한다.

## 주의

이 단계는 기본 읽기 전용이며 과제 파일·원본 데이터·기존 테스트를 수정하지 않는다.
실제 공식 메일, 시험 날짜, 모델명, 금지 규정, 채점 방식, 출제 내용은 입력 근거 없이는 주장하지 않는다.
전체 사고과정을 요구하지 말고 질문의 영향과 판단 근거만 제시한다.
외부 전송·제출·배포·push는 별도 구체적 승인 없이는 실행하지 않는다.
