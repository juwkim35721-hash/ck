# 우선순위·위험 기반 실행 계획

## 사용 시점
요구사항·정책·입출력 계약을 확인한 뒤, 구현 전에 무엇을 먼저 할지 정할 때 사용한다.
실제 과제 루트를 읽기 전용으로 확인해 계획만 만들며, 준비 도구 저장소를 과제로 취급하지 않는다.
공식 안내가 있으면 우선 적용하고 AI 허용 준비 단계에서만 사용한다. AI 금지 서술형이 시작되면 즉시 중단한다.

## 필요 입력
- [과제 루트]: 실제 과제 경로
- [남은 시간: 분]: 검증·제출 준비를 포함한 실제 시간
- [요구사항/파일/답변]: R1 등 요구사항 ID, 정책 답변, 관찰 파일
- [현재 기준선]: 실행·테스트 명령과 통과/실패/미실행 결과
- [제출 조건]: 알려진 필수 파일·형식·마감; 모르면 ‘미확인’
과제 루트 또는 남은 시간이 없으면 먼저 질문한다.
요구사항·기준선이 없으면 구현 순서를 추측하지 말고 읽기 전용 확인 작업을 첫 작업으로 둔다.

## 전략
### 1. 사실과 가정을 분리
관찰한 사실, 미확인 가정, 구현 결과를 바꾸는 질문을 분리한다.
공식 규칙·담당자 답변·기존 계약이 충돌하면 임의로 해결하지 말고 영향이 큰 질문으로 남긴다.

### 2. P0를 수용 기준에서 역산
각 요구사항을 입력부터 출력까지의 얇은 수직 슬라이스로 나눈다.
슬라이스마다 요구사항 ID, 기대 동작, 의존성, 최소 검증, 완료 증거를 연결한다.
P0는 필수 수용 기준, 선행 의존성, 실패 영향이 큰 항목만 둔다. P1은 P0 이후 품질 개선, 보류는 직접 연결되지 않은 작업이다.

### 3. 위험한 가정을 먼저 판별
영향이 크고 불확실하며 되돌리기 어려운 가정을 위험 상단에 둔다.
위험마다 가정, 영향, 가장 작은 실험, 통과/실패 증거, 시간 상한, 다음 결정을 적는다.
예를 들어 호출 형식이 불명확하면 전체 구현 대신 실제 호출자·샘플 한 건으로 계약을 확인한다.
시간 상한 내 증거가 없으면 사실처럼 기본값을 채우지 말고 질문, 가역적 선택, 범위 축소 중 하나를 선택한다.

### 4. 의존성·완료 게이트를 드러냄
정책·환경·입출력 계약처럼 앞 단계가 막힌 작업은 해소 조건과 대체 경로를 적는다.
막힌 작업을 병렬로 가능한 것처럼 표시하지 않는다.
실행은 ‘위험 확인 → P0 한 슬라이스 → 해당 검증’의 반복으로 배치한다.

### 5. 시간과 범위를 보호
[남은 시간: 분]을 조사, 위험 실험, P0, 독립 검증, 제출 준비에 합계가 맞게 배분한다.
독립 검증과 제출 준비에는 전체의 최소 25% 또는 현실적인 보호 버퍼를 먼저 남긴다.
새 P1 시작 금지 시점과 각 작업의 시간 상한을 적는다.
시간 부족 시 선택 기능, 다듬기, 일반화, 리팩터링 순으로 미룬다. P0 수용 기준이나 검증은 삭제하지 않는다.
정책 미확인으로 결과가 달라지는 경우, 원본 보존이 불가능한 작업, AI 금지 평가 시작은 중단·질문 조건이다.
외부 제출·배포·전송은 ‘사용자 승인 필요’로만 기록하고 실행하지 않는다.

## 기본 프롬프트
```text
$sk-plan
너는 우선순위·위험 기반 실행 계획 담당자다. 구현하거나 파일을 수정하지 말고 계획만 작성하라.

입력:
- 실제 과제 루트: [과제 루트]
- 남은 시간: [남은 시간: 분]
- 요구사항/정책/답변: [요구사항/파일/답변]
- 현재 기준선: [현재 기준선]
- 제출 조건: [제출 조건]

확인된 사실, 미확인 가정, 결과를 바꾸는 질문을 분리하라. 입력이 부족하면 읽기 전용 확인 항목 또는 가장 영향 큰 질문을 제시하라. 제공되지 않은 공식 규칙·채점·마감은 만들지 마라.

R1 등 요구사항 ID별 P0/P1/보류 백로그를 만들고, 각 P0에 얇은 수직 슬라이스·의존성·최소 검증·완료 증거를 연결하라. 영향·불확실성·되돌리기 어려움을 기준으로 위험 가정을 정렬하고, 각각에 작은 판별 실험·시간 상한·통과/실패 후 결정을 적어라.

[남은 시간: 분]과 합계가 맞는 시간 예산을 제시하되 독립 검증·제출 준비 버퍼를 먼저 보호하라. 위험 확인 → P0 한 슬라이스 → 검증 순서, 단계별 완료 기준, 별도 ‘축소/중단 규칙’을 출력하라.
```

## 심화/반증 프롬프트
```text
$sk-plan
아래 실행 계획을 반증 중심으로 감사하고 수정된 계획만 제시하라. 코드를 수정하거나 없는 테스트 결과를 만들지 마라.

계획: [기존 계획]
증거/요구사항/기준선: [요구사항/파일/답변]
남은 시간: [남은 시간: 분]

다음을 점검하라: (1) P0가 수용 기준이 아니라 구현 편의성에 끌리지 않았는가? (2) 가장 위험한 가정이 가장 작은 실험으로 먼저 판별되는가? (3) 막힌 의존성을 가능한 작업으로 표시하지 않았는가? (4) 완료 기준에 관찰 가능한 증거와 최소 검증이 있는가? (5) 시간 합계와 검증·제출 버퍼가 맞는가? (6) 실험 실패·정책 미확인·시간 초과 시 질문·가역적 대안·범위 축소가 있는가?

발견마다 영향·근거·바꿀 우선순위를 짧게 적고, P0/P1/보류·위험 실험·시간 상한·게이트·축소/중단 조건을 다시 제시하라. 공식 안내에 없는 규칙이나 결과는 추정하지 마라.
```

## 완료 기준
- P0/P1/보류가 요구사항 ID와 최소 검증에 연결된다.
- 위험 가정마다 작은 실험, 증거, 시간 상한, 실패 후 결정이 있다.
- 시간 예산 합계와 검증·제출 준비 버퍼가 명시된다.
- 의존성, 완료 게이트, 축소·중단 조건이 관찰 가능한 표현이다.
- 미확인 정책·테스트 결과·공식 규칙을 사실처럼 쓰지 않는다.

## 다음 단계
P0 첫 슬라이스와 위험 실험 결과를 입력으로 최소 설계 단계로 이동한다.
정책 또는 데이터 계약이 계획을 바꿀 만큼 미확인이면 설계 전에 해당 확인 단계로 되돌아간다.

## 주의
계획은 제출·배포 권한이 아니다. 외부 push, 제출, 배포, 민감정보 전송은 구체적 사용자 승인 없이는 실행하지 않는다.
원본 데이터·기존 테스트·관련 없는 사용자 수정은 보존한다.
