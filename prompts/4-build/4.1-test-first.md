# 4.1 실패하는 수용 테스트 먼저 작성

> 스킬: `$sk-test-first` · 단계: 구현 · 작업 노트: `sk/work/SPEC.md#11. 수용 테스트 표 T`, `sk/work/EVIDENCE.md#실행 기록` · 사용 자료: `없음`

## 언제 쓰나

- 2.4 구현 착수 게이트가 READY 또는 READY-WITH-ASSUMPTIONS이고, 3.1에서 현재 S#를 정한 직후에 쓴다.
- 새 기능·버그 수정의 구현 코드를 쓰기 전에 T# 하나 이상을 실제 실패로 확인하고 싶을 때 쓴다.
- 기존 테스트가 있어도 현재 요구사항 R#/P#를 직접 증명하는 assertion이 없는지 확인할 때 쓴다.
- 명세가 BLOCKED이거나 H 영향 G#가 남은 경우에는 테스트로 정책을 확정하지 말고 1.3으로 되돌린다.

## 준비할 입력

- `sk/work/SPEC.md`의 상태, R#, P#, A#, AC, 그리고 `## 11. 수용 테스트 표 T`.
- `sk/work/PLAN.md`의 `## 슬라이스 S`에서 현재 S#과 대상 R#/T#.
- `sk/work/BRIEF.md`의 실행·테스트 명령, 코드 지도, 수정 금지 파일.
- 과제의 기존 테스트 설정 파일, 가까운 테스트 사례, fixture·mock 관례.
- 가능하면 최근 기준선 결과와 현재 변경 목록. 다른 사람의 기존 실패를 새 실패로 오인하지 않는다.

## 전략 — 왜 이렇게 하나

수용 테스트는 구현의 설계도가 아니라 명세의 실행 가능한 증거다. 따라서 기대값은 구현 코드가 아니라 R#/P#/AC와 손계산에서 얻는다.
먼저 RED를 확인하면 "테스트 자체가 틀린지", "환경이 망가졌는지", "정말 기능이 없는지"를 구현 전에 분리할 수 있다.
한 번에 S# 하나와 T# 한두 개만 다뤄야 실패 출력이 다음 4.2의 최소 변경 범위를 정확히 가리킨다.
기존 테스트를 고치거나 약화해 통과시키는 것은 회귀 보호를 없애므로 금지한다.

## 기본 프롬프트

```text
$sk-test-first
현재 구현 슬라이스를 시작한다. 과제 루트 기준으로 작업하고 sk/는 도구이므로 분석·수정·테스트 대상에서 제외하라.
먼저 sk/work/SPEC.md의 0절, R/P/A, 11절과 sk/work/PLAN.md의 현재 S#을 읽어라.
현재 S#에서 P0 우선 T# 한두 개를 고르고, 각각의 R#, AC, P#/A#, 최소 입력, 기대값 근거를 표로 정리하라.
기대값은 구현 코드를 참고해 계산하지 말고 명세·정책·손계산만 근거로 하라.
기존 테스트 프레임워크·파일 위치·명명·fixture 관례를 읽고, 새 의존성 없이 그 관례에 맞는 테스트를 추가하라.
기존 테스트를 수정·삭제·skip 처리하거나 assertion을 약화하지 마라.
추가한 테스트만 실제 명령으로 실행하고 종료 코드와 실패 원인을 확인하라.
실패를 RED-미구현, FAIL-설정, 기존 회귀, 이미 통과로 분류하라. RED-미구현이 아니면 구현을 시작하지 마라.
실제 실행만 sk/work/EVIDENCE.md의 ## 실행 기록에 다음 미사용 E#으로 기록하라.
기록 열은 E#, 시각, 작업 디렉터리, 명령, 대상 R/T, 기대, 실제 결과 요약, 판정, 코드 상태를 유지하라.
마지막에 대상·작성 위치·기대값 근거·실행 결과·E#·다음 행동을 번호 목록으로 보고하고, RED면 4.2 implement로 넘겨라.
```

## 심화 프롬프트 — 정책과 회귀가 얽힌 슬라이스

```text
$sk-test-first
현재 S#의 실패하는 수용 테스트를 작성하되, 먼저 SPEC에서 관련 R#, AC-R#-n, P#, A#, C#와 T#를 추출해 추적표를 만들어라.
각 T#마다 Given/When/Then을 만들고, 입력 값·호출 경로·기대 출력 또는 오류·기대값 근거를 분리해 제시하라.
기대값이 문서와 DM 정책 P#에서 충분히 결정되는지 먼저 판정하라. 부족하면 테스트를 확정하지 말고 G 후보, 선택지, 영향 R#을 적어 1.3 dm-questions을 제안하라.
과제의 기존 테스트 파일과 fixture를 읽어 같은 레이어에서 테스트하라. 단위·통합·API 테스트 중 가장 작은 범위를 택한 이유도 써라.
정상 1건과 이번 변경이 실제로 여는 경계 또는 실패 1건을 고르되, 새 S#나 무관한 기능을 섞지 마라.
테스트 이름이 조건과 결과를 설명하게 하고, 출력 전체 또는 계약상 필수 필드를 assert하라. 단지 예외가 없음을 확인하는 테스트는 충분하지 않다.
테스트 파일을 추가할 수 없다는 공식 규칙이 있을 때만 sk/work/ 아래 임시 검증 스크립트를 제안하고, 허용 근거와 제출 제외 사실을 E#에 남겨라.
테스트를 실제 실행한 뒤 종료 코드, 통과·실패 수, 실패 assertion, 현재 코드 상태를 수집하라.
문법·import·테스트 탐색·fixture·환경 오류는 FAIL-설정으로 분리하고, 미구현 분기나 값 불일치만 RED-미구현으로 판정하라.
기존에 이미 통과하면 assertion 약함, 잘못된 fixture, 잘못된 호출 대상을 점검하되 통과를 억지로 실패시키지 마라.
EVIDENCE의 ## 실행 기록에 실제 결과만 E# 행으로 남기고, 비밀값과 긴 원본 출력은 기록하지 마라.
최종 보고는 1) S#/R#/T#/P# 2) 테스트 설계 3) 실행·분류 4) E# 5) 4.2에 넘길 최소 구현 목표 순으로 작성하라.
```

## 변형 — 테스트 프레임워크가 없거나 테스트 파일 추가가 제한된 상황

```text
$sk-test-first
과제 규칙과 기존 파일을 먼저 읽어 테스트 파일 추가가 허용되는지, 프레임워크와 실행 명령이 있는지 확인하라.
허용되는 경우에는 기존 관례의 테스트를 작성하고 기본 절차를 따르라.
허용되지 않거나 프레임워크가 없다면, 구현 코드와 제출물은 바꾸지 말고 sk/work/ 아래에 T# 이름의 최소 임시 검증 스크립트를 만들 수 있는지 규칙 근거를 먼저 확인하라.
임시 스크립트에는 명세 입력, 독립 기대값, 실제 호출, 명시적 비교, 종료 상태를 넣어라.
그 스크립트가 과제 제출물이 아님과 삭제·보존 판단이 필요한 임시 검증임을 E#에 적어라.
실제 실행 전에는 PASS라고 쓰지 말고, 실패를 RED-미구현과 FAIL-설정으로 분리하라.
SPEC 11절의 T#를 읽기 기준으로 사용하고, 기대값이 불명확하면 구현 대신 1.3 dm-questions으로 넘겨라.
최종 보고에는 규칙상 선택한 검증 방식, 파일 경로, 명령, 종료 코드, E#, 다음 4.2 또는 1.3 행동을 포함하라.
```

## 변형 — 새 테스트가 이미 통과한 상황

```text
$sk-test-first
새로 작성한 T#가 첫 실행에서 통과했다. 이를 실패로 만들지 말고, 먼저 기존 구현이 정말 R#/P#/AC를 충족했는지 검증하라.
테스트 대상 함수·엔드포인트가 맞는지, fixture가 실제 경계 조건을 포함하는지, assertion이 값·스키마·오류를 충분히 비교하는지 확인하라.
테스트가 약하면 명세 근거를 유지한 채 assertion 또는 입력을 보강하고 다시 실제 실행하라.
이미 구현된 동작이 충분히 증명되면 E#에 GREEN-기존충족으로 기록하고, 불필요한 구현은 하지 마라.
현재 S#의 다른 미충족 T#가 있으면 그 하나만 선택해 기본 절차를 반복하라.
모든 대상이 이미 충족되면 PLAN의 S# 상태를 임의로 완료로 바꾸지 말고 4.2 또는 4.3이 확인할 사항을 명시해 넘겨라.
최종 보고에는 통과 이유의 근거, 보강한 assertion, 실제 명령·결과, E#, 변경하지 않은 이유를 포함하라.
```

## 결과물 확인

- [ ] 대상 S# 하나와 T# 한두 개가 R#/AC/P#/A#에 연결되어 있다.
- [ ] 기대값이 구현이 아니라 명세·정책·손계산에 근거한다.
- [ ] 기존 관례에 맞는 테스트 또는 규칙상 허용된 임시 검증이 있다.
- [ ] 실제 실행으로 RED-미구현과 환경·기존 회귀 실패를 구분했다.
- [ ] `sk/work/EVIDENCE.md#실행 기록`에 실제 결과 E#이 있다.
- [ ] 기존 테스트를 약화·삭제·skip 처리하지 않았다.

## 다음 단계

- 기대된 RED면 [4.2 implement](../4-build/4.2-implement.md)의 `$sk-implement`로 최소 구현을 시작한다.
- 실패 원인이 구현이 아니라 실제 오류라면 6.1 debug($sk-debug)으로 최소 재현과 가설을 분리한다.
- 기대값을 정할 P#/A#/AC가 없으면 1.3 dm-questions($sk-dm-questions)으로 질문 초안을 만든다.
- 대상 T#가 이미 충분히 GREEN이면 4.3 harden($sk-harden)으로 현재 변경과 관련된 경계만 점검한다.

## 주의

- 과제 파일 수정이 허용되는 구현 단계라도, 테스트 외의 구현 코드를 이 작업에서 먼저 쓰지 않는다.
- `sk/work/` 외의 `sk/` 파일은 수정하지 않는다.
- 새 패키지 설치·네트워크 사용은 공식 규칙이 허용하고 사용자가 확인한 경우만 한다.
- 실행하지 않은 결과, 통과 수, 코드 상태를 E#에 추정해 기록하지 않는다.
- 담당자에게 DM을 직접 보내지 않는다. 필요한 메시지는 1.3이 복붙용으로 만들고 사용자가 전송한다.
