# 4.3 관련 엣지 케이스 방어

> 스킬: `$sk-harden` · 단계: 구현 · 작업 노트: `sk/work/SPEC.md#11. 수용 테스트 표 T`, `sk/work/EVIDENCE.md#실행 기록` · 사용 자료: `없음`

## 언제 쓰나

- 4.2에서 현재 S#의 정상 경로가 실제로 GREEN이 된 직후, 다음 슬라이스 전에 쓴다.
- 새 변경이 입력 검증·상태 전이·정렬·빈 결과·오류 계약에 영향을 주어 관련 경계를 좁게 확인할 때 쓴다.
- 현재 기능과 관련된 회귀를 방어할 때 쓴다. 모든 가능한 예외를 한꺼번에 다루는 보안 감사나 전면 리팩터링에는 쓰지 않는다.
- 데이터 전체 검산은 5.3, API 전체 계약은 5.4, UI 핵심 흐름은 5.5로 넘긴다.

## 준비할 입력

- `sk/work/SPEC.md`의 R#/C#/P#/A#, 10절 입출력 계약, 11절 T# 표.
- `sk/work/PLAN.md#슬라이스 S`의 방금 구현한 S#과 실제 변경 파일·함수.
- `sk/work/EVIDENCE.md`의 최신 GREEN E#과 대상 테스트 결과.
- 변경 diff, 호출 흐름, 기존 오류 처리와 가까운 경계 테스트.
- 정책이 확정 P#인지 가정 A#인지 구분할 수 있는 근거. 근거 없는 기본값은 만들지 않는다.

## 전략 — 왜 이렇게 하나

엣지 케이스 방어의 목적은 더 많은 코드를 쓰는 것이 아니라, 실제 입력 경계에서 잘못된 결과와 크래시가 하위 로직으로 전파되는 것을 막는 것이다.
현재 S#와 연결된 위험만 1~3개 선택하면 시간 내에 재현·근거·Guard·회귀 테스트·증거를 모두 남길 수 있다.
Guard는 가능한 한 입력을 받는 경계에 한 번만 둔다. 같은 검증을 여러 계층에 반복하면 정책이 분산되고 수정이 어려워진다.
정책 P#/A#가 없으면 선택 자체가 요구사항 판단이다. 코드를 추정으로 고정하지 않고 G 후보와 DM 핸드오프로 남긴다.

## 기본 프롬프트

```text
$sk-harden
방금 구현한 S#의 정상 경로가 GREEN인지 최신 E#으로 먼저 확인하라. GREEN 근거가 없으면 방어를 시작하지 말고 4.2 implement로 되돌려라.
과제 루트에서 작업하고 sk/는 도구이므로 sk/work/ 외에는 수정하지 마라.
SPEC의 R/C/P/A, 10절 계약, 11절 T#와 PLAN의 S#을 읽어 이번 변경에 실제로 관련된 위험만 1~3개 고르라.
각 위험을 재현 입력 또는 상태, 현재 동작, 기대 근거 P#/A#/C#, 영향, 방어 위치로 표로 정리하라.
null·빈 값, 타입 오류, 경계값, 중복·멱등성, 동점 정렬, 빈 결과, 권한·상태 전이, 문서화된 웹 경계 중 관련 범주만 검사하라.
먼저 최소 재현을 실제로 실행하고, 기대값이 확정 정책 또는 가정으로 정해지는지 확인하라.
근거가 있는 경우에만 가장 이른 입력 경계에 최소 Guard를 구현하고, 기존 출력 스키마·인터페이스를 보존하라.
방어마다 회귀 T#를 추가하거나 기존 T#와 연결하고, 실제로 방어 테스트와 관련 회귀 테스트를 실행하라.
새 T#가 필요하면 SPEC 11절에 다음 미사용 ID로 입력·기대값·근거·확인 방법을 기록하라.
실행 결과는 EVIDENCE.md의 ## 실행 기록에 다음 미사용 E#으로 남기고, 이전 증거가 오래되면 STALE 여부를 표시하라.
근거 없는 동작은 구현하지 말고 G 후보, 최소 재현, 선택지, 영향 R#을 정리해 1.3 dm-questions으로 넘겨라.
마지막에 위험 매트릭스, Guard, T#/E#, 미확정 사항, 5.1 verify 또는 전문 검증 핸드오프를 번호 목록으로 보고하라.
```

## 심화 프롬프트 — 데이터·정렬·오류 계약을 함께 건드린 상황

```text
$sk-harden
현재 S#의 정상 경로 GREEN E#과 변경 diff를 읽고, 어느 입력 필드와 출력 필드가 실제로 바뀌었는지 먼저 확정하라.
SPEC 10절의 필드 타입·필수 여부·범위·결측 표현·정렬·null 표현·오류 계약과 P#/A#을 대조해 위험 후보를 만들라.
후보 중 사용자 결과나 채점 결과를 바꿀 수 있는 것만 1~3개 선정하고, null/빈 값, 숫자 문자열·손상 타입, 경계 등호, 중복 키, 동점 2차 정렬, 빈 결과를 관련성 기준으로 분류하라.
각 항목에 최소 재현 입력, 현재 출력, 기대 출력, P#/A#/C# 근거, Guard 위치, 회귀 T#를 작성하라.
정렬·반올림·빈 결과처럼 계약에 없는 세부 정책은 현재 우연한 구현을 고정하지 말고 G 후보로 분리하라.
입력 검증은 호출 초입 또는 계약 경계에 한 번만 배치하고, 하위 함수에 무관한 웹·보안 정책을 추가하지 마라.
계약상 오류여야 하면 명시된 오류 타입·상태 코드·본문 형식을 확인하고, 내부 예외를 성공 빈 결과로 숨기지 마라.
새 방어 테스트는 SPEC 11절의 ID | 관련 R/P | 유형 | 입력 | 기대 출력 | 기대값 근거 | 확인 방법 | 제공 테스트 여부 열을 지켜 기록하라.
정상·경계·실패·회귀를 구분해 실제 명령을 실행하고, 종료 코드·통과 수·핵심 출력만 E#에 남겨라.
방어 뒤 대상 GREEN E#이 현재 코드와 맞지 않으면 STALE로 표시하고 필요한 테스트를 재실행하라.
최종 보고에는 하지 않은 범주와 그 이유도 밝혀 과잉 방어가 없음을 보여 주고, 전체 추적 검증은 5.1 verify로 넘겨라.
```

## 변형 — 정책 근거 없이 오류 입력을 발견한 상황

```text
$sk-harden
현재 기능에서 오류 입력을 재현했지만 SPEC의 P#/A#/입출력 계약으로 결과를 결정할 수 없다. 임의의 0 변환, 레코드 제외, 빈 성공 응답을 구현하지 마라.
최소 입력과 현재 동작을 실제로 확인하고, 선택지 A/B의 출력·호환성·영향 R#을 짧게 비교하라.
문서·기존 테스트·DM_LOG에 이미 답이 있는지 읽기 전용으로 확인하되, 발견하지 못했다고 정책 공백을 자동 확정하지 마라.
G 후보에 영향도, 결정 필요 시점, 기본 제안, 되돌릴 지점, 확인할 질문을 정리하라.
1.3 dm-questions($sk-dm-questions)으로 복붙용 질문을 만들고, 사용자가 답을 붙여 넣으면 1.4 dm-answers($sk-dm-log)와 2.1 spec($sk-spec)으로 정책을 반영하도록 안내하라.
이미 만든 테스트는 미확정 기대값을 assert하지 말고, 재현 스크립트·현재 결과·미검증 상태만 E#에 기록하라.
최종 보고에는 코드로 방어하지 않은 이유, G 후보, 실제 재현 E#, 다음 확인 경로를 포함하라.
```

## 변형 — API 또는 UI 경계가 관련된 상황

```text
$sk-harden
현재 S#이 API 또는 UI 입력 경계를 포함하는지 먼저 확인하고, 문서화된 계약 안에서만 방어하라.
API면 메서드·경로·필수 필드·오류 상태·응답 스키마를 SPEC 10절과 대조하고, UI면 정상 입력·빈/잘못된 입력·오류 또는 빈 상태 중 관련 흐름만 고르라.
웹 과제라면 지정 포트와 내장 Browser 미리보기용 `0.0.0.0` 바인딩만 확인하고(과제 문서 우선), CORS·인증은 공식 요구나 P#가 있을 때만 검사하라. 와일드카드 CORS나 인증 해제를 추가하지 마라.
입력 오류의 Guard와 사용자·클라이언트가 받는 결과를 테스트하고, 화면 문구·스타일의 대규모 변경은 하지 마라.
도달성·계약 전체 확인은 아직 완료로 주장하지 말고 5.4 api-contract($sk-api-contract) 또는 5.5 ui-smoke($sk-ui-smoke)로 넘겨라.
실제 실행한 테스트의 종료 코드·응답 요약·E#과, 아직 전문 검증이 필요한 항목을 구분해 보고하라.
```

## 결과물 확인

- [ ] 최신 E#로 정상 경로 GREEN을 확인한 뒤에만 방어를 시작했다.
- [ ] S#와 관련된 위험 1~3개마다 재현·현재 동작·P#/A#/C# 근거가 있다.
- [ ] Guard가 가장 이른 계약 경계에 최소한으로 배치되었다.
- [ ] 새 회귀 T#는 SPEC 11절의 정확한 표 열과 다음 미사용 ID를 사용한다.
- [ ] 실제 방어 실행이 `sk/work/EVIDENCE.md#실행 기록`의 E#으로 남아 있다.
- [ ] 정책 공백은 코드가 아니라 G 후보·1.3 핸드오프로 남겼다.

## 다음 단계

- 구현된 요구사항 전체를 R→AC→T→E로 대조하려면 5.1 verify($sk-verify)를 사용한다.
- 원본·결과 데이터의 행 수·합계·제외 사유를 독립 검산해야 하면 5.3 data-validation($sk-data-validation)으로 넘긴다.
- API 경계는 5.4 api-contract($sk-api-contract), UI 핵심 흐름은 5.5 ui-smoke($sk-ui-smoke)로 실제 검증한다.
- 방어 테스트가 실제 실패했지만 원인이 불명확하면 6.1 debug($sk-debug)으로 최소 재현과 가설을 만든다.

## 주의

- 모든 null·음수·중복을 같은 방식으로 처리하는 일반화를 하지 않는다.
- 원본 데이터·기존 테스트·기존 출력 스키마를 수정하거나 삭제하지 않는다.
- 민감한 원본 값, 토큰, 개인정보를 재현 입력이나 E#에 기록하지 않는다.
- 새 패키지 설치·네트워크 사용·배포·제출·push는 하지 않는다.
- 실행하지 않은 결과는 PASS, 안전, 방어 완료로 표현하지 않는다.
