# 4.2 슬라이스 하나 최소 변경 구현

> 스킬: `$sk-implement` · 단계: 구현 · 작업 노트: `sk/work/PLAN.md#슬라이스 S`, `sk/work/SPEC.md#12. 추적표`, `sk/work/DECISIONS.md`, `sk/work/EVIDENCE.md#실행 기록` · 사용 자료: `없음`

## 언제 쓰나

- 4.1에서 현재 S#의 테스트가 RED-미구현으로 확인되고, 변경할 R#/T#/P#를 설명할 수 있을 때 쓴다.
- 기존 기능을 고치거나 새 기능을 한 개의 수직 슬라이스로 추가할 때 쓴다.
- 구현 완료 뒤 다음 기능으로 넘어가기 전, 한 S#의 추적과 실제 실행 결과를 남길 때 쓴다.
- 큰 구조 선택이 아직 필요하면 3.2 design, 실제 원인이 불명확한 실패면 6.1 debug을 먼저 쓴다.

## 준비할 입력

- `sk/work/SPEC.md`의 상태, Top 5, R#/C#/P#/A#, 데이터·입출력 계약, T#, 추적표.
- `sk/work/PLAN.md`의 현재 S#, 시간 예산, 위험 실험, 축소 결정.
- `sk/work/BRIEF.md#코드 지도`, 관련 소스·호출자, 기존 테스트 명령과 수정 금지 파일.
- 4.1에서 남긴 RED-미구현 E# 및 작성한 테스트 위치·실패 assertion.
- `sk/work/DECISIONS.md`의 영향을 받는 DD#과 AI 교정 기록. 대화 기억보다 노트와 실제 코드가 우선이다.

## 전략 — 왜 이렇게 하나

슬라이스는 "한 요구사항의 입력부터 사용자에게 보이는 출력까지"를 작게 완성하는 단위다. 파일 수가 아니라 검증 가능한 동작으로 나눈다.
각 변경을 R#/P#/T#와 연결하면 AI가 제안한 편의 구현이나 무관한 리팩터링이 요구사항을 덮는 일을 막을 수 있다.
대상 테스트 GREEN만으로는 부족하다. 영향받는 기존 테스트와 출력 계약을 확인해야 기존 인터페이스를 조용히 깨지 않는다.
정책이 비어 있으면 코드의 기본값이 정책이 된다. 그래서 새 정책은 구현하지 않고 G 후보로 되돌린다.

## 기본 프롬프트

```text
$sk-implement
과제 루트에서 현재 S# 하나만 구현하라. sk/는 도구이므로 sk/work/ 외에는 수정하지 말고, 무관한 리팩터링·포맷 변경을 섞지 마라.
먼저 sk/work/SPEC.md의 상태, Top 5, R/C/P/A, 10~12절과 sk/work/PLAN.md의 현재 S#을 읽어라.
4.1의 E#에서 대상 T#가 RED-미구현인지 확인하고, S#/R#/T#/P#/A#/후보 파일/보존 인터페이스를 먼저 선언하라.
대상 함수의 호출자·반환값·오류 경로를 읽고, 입력 경계·핵심 규칙·출력 변환 중 가장 작은 수정 지점을 정하라.
P#의 조건→동작을 그대로 구현하고, A#를 적용하면 되돌릴 위치를 명확히 하라. 명세 밖 정책은 만들지 마라.
변경 후 과제의 컴파일·정적 검사·대상 테스트를 실제 실행하고, T# GREEN과 출력 스키마 보존을 확인하라.
영향받는 기존 테스트도 실제 실행하라. 실패하면 추측 수정하지 말고 변경 관련성을 분리하라.
실행마다 sk/work/EVIDENCE.md의 ## 실행 기록에 다음 미사용 E#을 남겨라.
PLAN의 ## 슬라이스 S 상태와 SPEC의 ## 12. 추적표에 실제 구현 위치·E#·검증 수준을 갱신하라.
새 설계 판단은 DECISIONS.md에 DD#, AI 초안의 실제 오류를 교정했다면 ## AI 교정 기록에 AI#으로 적어라.
마지막에 슬라이스 선언, 변경, 의도적 비변경, 실행 결과/E#, 추적 갱신, 판정, 다음 행동을 번호 목록으로 보고하라.
```

## 심화 프롬프트 — 인터페이스 보존과 정책 반영을 엄격히 확인하는 상황

```text
$sk-implement
현재 S#을 최소 변경으로 구현하기 전에 SPEC에서 R#, AC-R#-n, C#, P#, A#, T#를 표로 추출하고 우선순위를 확인하라.
4.1의 RED E#을 읽어 실패 assertion이 기능 미구현 때문인지 다시 확인하라. 설정·import·fixture 문제면 구현을 시작하지 말고 6.1 debug을 제안하라.
현재 공개 API, CLI 인자, 데이터 스키마, 호출자를 탐색해 보존 목록과 변경 후보 파일을 분리하라.
구현 전에는 S#/R#/T#/P#/A#/변경 파일/보존 인터페이스/시간 상한을 선언하고, 다른 S#은 범위 밖으로 표시하라.
정책마다 코드의 조건과 결과를 대응시켜 구현하라. P#와 충돌하거나 A#로도 결정할 수 없는 동작은 G 후보·선택지·영향 R#로 기록하고 1.3 dm-questions으로 넘겨라.
가장 이른 경계 또는 기존 도메인 함수 한 곳을 고쳐 중복을 피하고, 대규모 구조 변경·새 의존성·디렉터리 이동은 하지 마라.
대상 테스트, 영향을 받는 회귀 테스트, 가능한 컴파일/린트를 실제 순서대로 실행하라. 각 명령의 작업 디렉터리, 종료 코드, 통과·실패 수를 확보하라.
T#가 GREEN이어도 출력 필드·타입·정렬·오류 계약과 기존 호출자를 비교해 호환성을 확인하라.
PLAN의 S# 행은 대기/진행/완료/막힘/축소 중 실제 상태로 갱신하고, 완료는 GREEN E#이 있을 때만 쓰라.
SPEC 12절에는 R | AC | T | 구현 위치 | 증거 E | 상태 열로 실제 파일·함수와 증거를 연결하라.
대안 선택이 새로 있었으면 DECISIONS.md의 ## DD<n> 제목 블록에 상황·선택지·선택·R/P/C 근거·포기한 것·되돌리는 방법을 기록하라.
AI가 낸 초안의 구체 오류를 내가 교정한 사실이 있을 때만 AI#에 문제·발견법·수정·E#을 남겨라.
마지막 보고에는 미검증 항목을 PASS로 쓰지 말고 부분검증 또는 막힘으로 표시하며, 다음 4.3 또는 6.1 행동을 명시하라.
```

## 변형 — 명세에 없는 동작을 구현 중 발견한 상황

```text
$sk-implement
구현 중 명세로 결정할 수 없는 동작을 발견했다. 편의상 기본값이나 오류 처리를 코드에 추가하지 말고 즉시 범위를 멈춰라.
SPEC의 R#, P#, A#, C#, T#와 현재 코드의 관찰된 동작을 분리해 읽고, 어떤 조건에서 선택지가 갈리는지 최소 입력으로 제시하라.
각 선택지가 출력·인터페이스·테스트에 미치는 영향과 기본 제안을 적되, 제안을 확정 정책처럼 구현하지 마라.
G 후보의 제목, 영향도, 결정 필요 시점, 관련 R#/T#을 정리하고 1.3 dm-questions($sk-dm-questions)으로 보낼 질문 초안을 요청하라.
현재까지 바꾼 코드가 있다면 범위를 넓히지 말고 대상 테스트·git diff를 읽기 전용으로 확인해 실제 상태를 E#에 기록하라.
담당자 답변이 오면 1.4 dm-answers($sk-dm-log)와 2.1 spec($sk-spec) 반영 후 다시 이 S#으로 돌아오도록 안내하라.
최종 보고에는 구현하지 않은 이유, 정책 공백, 최소 재현, 영향, E#, 다음 의사결정 경로를 명시하라.
```

## 변형 — 한 슬라이스가 예상보다 커진 상황

```text
$sk-implement
현재 S#이 여러 모듈·규칙·호출자를 건드려 짧은 시간에 검증하기 어렵다. 더 많은 코드를 쓰기 전에 편집을 멈춰라.
현재 요구사항과 이미 GREEN인 T#, 아직 RED인 T#, 변경 파일, 미확정 사항을 사실만 기준으로 목록화하라.
S#을 사용자에게 보이는 최소 동작 단위로 나누고, 각 하위 슬라이스의 R#/T#/완료 증거 E#을 제안하라.
P0이며 이미 RED인 테스트를 통과시키는 첫 조각을 우선으로 하고, P1/P2·성능·정리는 축소 후보로 표시하라.
sk/work/PLAN.md의 ## 슬라이스 S와 ## 축소 결정에 실제 상태를 기록할 내용을 제시하고 3.1 plan($sk-plan)으로 재계획을 넘겨라.
수정한 코드가 있으면 되돌리기 명령을 실행하지 말고, 변경 범위와 마지막 통과 E#만 기록하라. 복구가 필요하면 6.3 rollback을 제안하라.
최종 보고에는 중단 시점, 분할 근거, 우선순위, 남은 위험, 다음 S#을 포함하라.
```

## 결과물 확인

- [ ] 한 개 S#만 다루며 R#/AC/T#/P#/A#와 수정 파일·함수가 연결된다.
- [ ] 기존 공개 인터페이스·출력 스키마·수정 금지 파일의 보존 여부를 확인했다.
- [ ] 대상 T#와 관련 회귀 테스트를 실제 실행했거나 미실행 사유가 있다.
- [ ] PLAN의 상태와 SPEC 12절의 구현 위치·E#이 실제 결과와 맞다.
- [ ] 새 판단은 DD#, 실제 AI 교정은 AI#으로만 기록했다.
- [ ] `EVIDENCE.md#실행 기록`의 판정은 실행 출력에 근거한다.

## 주의

- 담당자 답변·공식 문서·관찰된 테스트보다 가정 A#을 우선하지 않는다.
- 기존 테스트를 고치거나 출력 계약을 바꿔 GREEN을 만들지 않는다.
- 새 패키지 설치, 네트워크 사용, 지정 포트 변경은 규칙 허용과 사용자 확인 없이는 하지 않는다. 웹 과제는 내장 Browser 미리보기용 `0.0.0.0` 바인딩을 유지한다.
- `git reset --hard`, `git clean`, `git stash`, 강제 체크아웃은 사용하지 않는다.
- push·배포·제출·업로드와 비밀값 출력은 하지 않는다.
