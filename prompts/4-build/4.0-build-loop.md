# 4.0 구현 루프 — 슬라이스 하나를 RED→GREEN→방어→검증까지

> 스킬: `$sk-build-loop` · 단계: 구현 · 작업 노트: `sk/work/PLAN.md#구현 루프 상태판`, `sk/work/EVIDENCE.md#실행 기록`, `sk/work/SPEC.md#12. 추적표` · 사용 자료: `sk/snippets/data_audit.py`, `sk/snippets/smoke_test.py`

## 언제 쓰나

- 2.4 spec-gate가 READY 계열이고 3.1 plan으로 슬라이스 표가 생긴 뒤, 슬라이스마다 쓴다. 4.1 → 4.2 → 4.3 → 5.1/5.2를 네 번 부르는 대신 이 프롬프트 하나로 한 바퀴를 돈다.
- 슬라이스가 멈춘 뒤(디버그·되돌림·세션 교체) 이어 갈 때, 담당자 답이 가정과 달라 다시 돌릴 때도 쓴다.
- 한 단계만 다시 하고 싶으면 [4.1](../4-build/4.1-test-first.md) · [4.2](../4-build/4.2-implement.md) · [4.3](../4-build/4.3-harden.md) · [5.1](../5-verify/5.1-verify.md)을 직접 쓴다.

## 준비할 입력

- 현재 시각 (구현 구간 10:50–12:00, 리뷰 12:00은 예시)
- 진행할 슬라이스 번호 S# (없으면 Codex가 PLAN에서 다음 P0 슬라이스를 고른다)
- 모드: 자동(기본) / 확인 / 빠른 / 연속
- `sk/work/BRIEF.md`에 테스트 명령과 기준선이 있어야 한다. 없으면 [0.1 context](../0-start/0.1-context.md)부터.

## 전략 — 왜 이렇게 하나

슬라이스 하나를 끝까지 닫는 것이 진행의 단위다. 테스트를 먼저 실패시키고(RED), 그 테스트만 통과시키는 최소 변경을 하고(GREEN), 관련 경계만 막고, 실제 실행으로 검증해야 "됐다"고 말할 수 있다. 단계마다 게이트가 있어서 앞 단계가 닫히지 않으면 다음으로 가지 않는다.

루프가 스스로 멈추는 조건도 정해 두었다. 명세에 없는 정책, 같은 실패에 수정 2회 초과, 인터페이스·기존 테스트를 바꿔야 하는 상황, 시간 상한 초과다. 이때 억지로 진행하지 않고 원인과 갈 곳(6.1 debug, 3.1 plan, 1.0 병행 라운드 등)을 알려 준다. 사람이 판단할 지점에서 멈추는 것이 자동 진행보다 시간을 덜 쓴다.

슬라이스가 끝날 때마다 **설명 3문장**(입력 → 규칙 → 출력, 왜 이 위치, 무엇으로 검증)을 남긴다. 보고서 3·4절과 후속 6문항 대비에서 그대로 쓰는 재료다.

## 기본 프롬프트 — 슬라이스 하나 (자동 모드)

```text
$sk-build-loop
<S#>를 자동 모드로 한 바퀴 돌려줘. 현재 시각은 <시각>이야.
단계 0: SPEC 0절 상태, PLAN의 슬라이스 행, SPEC 11절 T#의 기대값 근거, BRIEF의 테스트 명령·기준선, 이 슬라이스의 DD#, 시간 상한을 점검해. 하나라도 빠지면 멈추고 어디로 가야 하는지 말해.
통과하면 S#/R#/AC/T#/P#·A#/후보 파일/보존 인터페이스/상한을 선언하고 git 상태를 기록해.
단계 1: T#를 기존 테스트 관례로 작성하고 그것만 실행해서 RED-미구현인지 확인해. 기대값은 SPEC 11절 손계산 값만 써.
단계 2: 가장 작은 수정으로 GREEN을 만들고, 대상 테스트와 영향받는 기존 테스트를 실행해. 같은 실패에 수정 2회를 넘기면 멈춰.
단계 3: 이 슬라이스와 관련된 경계 1~3개만 P#/A#/C# 근거가 있을 때 방어하고 회귀 T#를 추가해. 근거가 없으면 G 후보로만 적어.
단계 4: 정상·경계·실패 경로와 전체 스위트를 실행하고 기준선과 비교해. STALE E#는 다시 실행하고 SPEC 12절을 실제 근거로만 갱신해.
단계 5: 판정(완료/완료-가정/부분/막힘/분할/재작업), 슬라이스 설명 3문장, 병행 질문 후보, 다음 행동 1개를 줘.
모든 실행은 EVIDENCE의 E#로, 진행은 PLAN 맨 위 구현 루프 상태판에 기록해. 기존 테스트 수정·삭제·skip, 기대값 바꾸기, 무관한 리팩터링, 파괴적 git 명령은 하지 마.
```

## 짧은 프롬프트 — 슬라이스 번호만 줄 때

스킬이 위 절차를 모두 담고 있으므로 시험 중에는 이렇게만 입력해도 같은 한 바퀴가 진행된다.

```text
$sk-build-loop
S2 진행
```

## 심화 프롬프트 — 확인 모드: 정책·가정이 얽힌 핵심 슬라이스

```text
$sk-build-loop
<S#>를 확인 모드로 진행해줘. 현재 시각은 <시각>이야. 이 슬라이스는 담당자 정책 <P#>와 가정 <A#>가 결과를 정하는 핵심 로직이라, 내가 설명할 수 있어야 해.
단계 0 선언 뒤 한 번 멈춰: 고칠 파일·함수, 보존할 인터페이스, P#의 "조건 → 동작"이 코드 어디에 들어갈지, A#가 틀렸을 때 되돌릴 지점을 보여 줘.
단계 1 RED 뒤 한 번 더 멈춰: 각 테스트의 입력, 기대값, 그 기대값의 근거(SPEC 11절 손계산·P#)를 표로 보여 주고 내 승인을 기다려.
내가 기대값이나 설계를 고치라고 하면, 그게 AI 초안의 실제 오류였는지 판단해서 맞으면 DECISIONS.md의 AI 교정 기록에 AI#로 남겨.
승인 뒤에는 단계 2~5를 자동으로 진행하되, 멈춤 조건이면 즉시 멈춰.
마지막 보고에는 슬라이스 설명 3문장과 함께, 이 슬라이스에서 후속 질문으로 나올 만한 "왜 이렇게 했나" 1개와 "무엇으로 검증했나" 1개의 답을 내 말로 쓸 수 있게 근거 위치(파일:줄, T#, E#)를 붙여 줘.
```

## 변형 — 빠른 모드: 남은 시간이 부족할 때

```text
$sk-build-loop
<S#>를 빠른 모드로 진행해줘. 현재 시각은 <시각>, 이 슬라이스에 쓸 수 있는 시간은 <분>분이야.
RED는 P0 정상 1건과 가장 위험한 경계 1건만, 방어는 장애 영향이 가장 큰 1건만, 검증은 P0 정상 경로와 전체 스위트만 실행해.
생략한 T#와 경계는 판정에 "미검증 + 사유"로 남기고, 보고서 5절 한계 후보로 표시해.
상한을 넘길 것 같으면 그 시점에서 멈추고 6.5 timebox로 넘길지 물어봐.
```

## 변형 — 연속 모드: P0 슬라이스를 이어서 진행할 때

```text
$sk-build-loop
P0 슬라이스를 연속 모드로 진행해줘. 현재 시각은 <시각>이고 최대 <개수>개까지만 해.
PLAN 순서대로 한 슬라이스씩 단계 0~5를 끝내고, 판정이 완료 또는 완료-가정일 때만 다음 슬라이스로 넘어가.
판정이 부분·막힘·분할·재작업이면 그 자리에서 멈추고 전체 보고를 해.
슬라이스마다 "S# → 판정 · 소요 분 · 다음" 한 줄만 보고하고, 30분마다 PLAN 시간 예산 대비 진행을 한 줄로 알려 줘.
리뷰 시작 시각(<시각>)이 되면 새 슬라이스를 시작하지 마.
```

## 변형 — 멈춘 슬라이스 재개: 디버그·되돌림·세션 교체 뒤

```text
$sk-build-loop
<S#>를 이어서 진행해줘. 현재 시각은 <시각>이야. 멈춘 이유는 <이유: 6.1 debug로 원인 수정 / 6.3 rollback으로 되돌림 / 세션 교체>야.
PLAN 맨 위 구현 루프 상태판, 슬라이스 표, EVIDENCE의 최근 E#, git 상태를 읽고 이 슬라이스가 어느 단계까지 닫혔는지 복원해.
그 뒤 바뀐 코드에 걸린 E#는 STALE로 표시하고, 마지막으로 닫힌 단계의 게이트부터 다시 확인한 뒤 이어서 진행해.
상태판과 실제 기록이 어긋나면 기록을 기준으로 상태판을 고치고 무엇을 고쳤는지 알려 줘.
```

## 변형 — 재작업: 담당자 답이 가정과 달랐을 때

```text
$sk-build-loop
담당자 답이 가정 <A#>와 달라서 정책이 <새 P#: 조건 → 동작>으로 확정됐어. SPEC.md 13절 변경 기록과 11절 T# 수정은 2.1·2.3에서 끝냈어.
이 정책이 걸린 슬라이스(<S# 목록>)를 재작업 판정으로 다시 돌려줘.
바뀐 T#부터 단계 1로 시작해서 RED를 다시 확인하고, A#의 되돌릴 지점(<파일·함수>)을 고쳐 GREEN을 만든 다음, 이 정책이 영향을 주는 다른 슬라이스의 테스트도 전체 스위트로 확인해.
이전 E# 중 이 변경과 관련된 것은 모두 STALE로 표시하고 새 E#로 대체해.
```

## 결과물 확인

- `PLAN.md` 맨 위 `## 구현 루프 상태판`에 슬라이스별 RED·GREEN·방어·검증 E#, 판정, 소요 분이 있다.
- `## 슬라이스 S` 표의 상태와 완료 증거, `SPEC.md` 12절 추적표가 상태판의 판정과 일치한다.
- `EVIDENCE.md`에 실제로 실행한 명령만 8열 형식으로 있고, 바뀐 코드에 걸린 이전 E#는 STALE로 표시됐다.
- 상태판 `### 슬라이스 설명`에 슬라이스마다 3문장이 있다.
- 데이터 과제는 `python3 sk/snippets/data_audit.py`로, API·UI 과제는 `python3 sk/snippets/smoke_test.py`로 확인한 E#가 있다.

## 다음 단계

판정이 완료면 다음 S#를 같은 프롬프트로 진행한다. 막힘이면 보고된 곳으로 간다: 원인 모를 실패는 [6.1 debug](../6-debug/6.1-debug.md), 같은 실패 반복은 [6.2 unstuck](../6-debug/6.2-unstuck.md), 분할은 [3.1 plan](../3-plan/3.1-plan.md), 시간 부족은 [6.5 timebox](../6-debug/6.5-timebox.md). 병행 질문 후보가 있으면 [1.0 질의 루프](../1-discover/1.0-clarify-loop.md)의 병행 라운드로 넘긴다. 모든 P0 슬라이스가 완료되면 [7.1 review](../7-review/7.1-review.md)로 간다.

## 주의

- 한 번에 슬라이스 하나만 구현한다. 연속 모드도 하나씩 판정한 뒤 다음으로 간다.
- 테스트 기대값을 구현 결과에 맞춰 바꾸거나 기존 테스트를 고치·지우·건너뛰지 않는다. 그래야 통과한다면 루프가 멈춰야 정상이다.
- 담당자 정책이 없는 동작은 코드에 넣지 않고 질문 후보로 넘긴다. Codex는 DM을 보낼 수 없다.
- 확인 모드는 시간이 더 들지만, 6문항에서 설명해야 할 핵심 슬라이스에는 쓰는 편이 낫다.
