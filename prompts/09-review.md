# 반증 중심 코드 리뷰

## 사용 시점

구현 또는 독립 검증 뒤, 제출·릴리스 준비 전에 변경 코드가 요구사항과 기존 계약을 깨뜨리지 않는지 읽기 전용으로 점검할 때 사용한다.
작성자의 설명이나 테스트 통과만으로 정답을 가정하지 말고, 실제 diff·호출자·테스트·실행 결과에서 반례를 찾는다.
공식 안내가 제공되면 그 규칙을 우선한다. AI 사용이 금지된 평가·서술형이 시작되면 즉시 이 문서와 모든 AI 보조 사용을 중단한다.

## 필요 입력

- [과제 루트]: 준비 도구 저장소가 아닌 실제 과제 경로
- [남은 시간: 분]: 검토 범위와 중단 우선순위 판단용
- [요구사항/파일/답변]: 요구사항 ID, 변경 목적, 알려진 한계 또는 관련 답변
- [기준선/비교 범위]: base 커밋·브랜치·파일 목록 중 확인 가능한 것
- [검증 명령과 결과]: 이미 실행한 테스트 및 실패 로그; 없으면 없다고 명시

입력이 비어 있으면 코드를 추측하지 말고, 먼저 현재 경로·비교 기준·요구사항 중 빠진 항목을 정확히 질문한다.
비교 기준이 없으면 현재 변경 파일만 검토하며 범위 한계로 기록한다.

## 전략

1. **권한과 범위를 고정한다.** 이 단계의 기본 동작은 읽기 전용이다. `git status`, `git diff --check`, 기준선 대비 diff, 관련 파일 읽기처럼 상태를 바꾸지 않는 확인부터 한다.
2. **변경 의도를 코드로 역추적한다.** 각 변경 hunk마다 어떤 요구사항을 만족하려는지, 실제 호출자가 무엇을 전달·기대하는지, 오류가 어디로 전파되는지 확인한다. 설명과 코드가 다르면 코드를 증거로 삼는다.
3. **가장 큰 손실부터 반증한다.** 데이터 손실·권한 우회·비밀 노출·필수 흐름 중단 가능성을 먼저 검토한다. 다음으로 계약 불일치, 경계값, 빈 값, 실패 경로, 순서·상태 전이, 단위·시간대, 중복·재시도를 변경 맥락에 맞게 선택한다.
4. **반례는 실행 가능한 형태로 만든다.** 발견마다 파일·라인, 전제, 최소 입력 또는 호출 순서, 기대 동작과 실제/추론된 동작, 근거를 연결한다. 테스트를 실행할 수 있으면 기존 명령 또는 비파괴적 임시 검증으로 확인하되 결과를 꾸미지 않는다.
5. **심각도를 일관되게 판정한다.** Critical은 보안·데이터 손실·핵심 기능의 광범위한 실패, High는 필수 요구사항 위반 또는 일반 입력에서의 명확한 실패, Medium은 특정 경계·회복·호환성 문제, Low는 제한적 유지보수 위험으로 둔다. 증거 없는 개선 제안은 발견 사항과 분리한다.
6. **리뷰와 수정을 분리한다.** 버그를 보고한 뒤에도 파일을 고치지 않는다. 수정은 사용자의 별도 요청·승인과 범위가 있을 때만 다음 단계에서 한다.

## 기본 프롬프트

```text
$sk-review
실제 과제 루트는 [과제 루트]이고, 검토 가능 시간은 [남은 시간: 분]분이다.
검토 대상은 [기준선/비교 범위]이며 요구사항·변경 목적은 [요구사항/파일/답변]이다.
이미 실행한 검증과 결과는 [검증 명령과 결과]이다.

반증 중심의 읽기 전용 코드 리뷰를 수행하라. 먼저 실제 과제 루트인지, 비교 기준과 변경 파일이 무엇인지 확인하고 git diff --check 및 diff를 읽어라. 각 변경이 실제 호출자·데이터 계약·오류 경로·요구사항과 맞는지 역추적하라. 작성자 설명이나 통과한 테스트를 정답으로 가정하지 말고, 변경과 관련된 가장 작은 반례를 찾아라.

발견은 Critical/High/Medium/Low 순으로만 보고하고, 각 항목에 (1) 파일:라인, (2) 재현 입력 또는 호출 순서, (3) 기대와 실제/예상 결과, (4) 코드·테스트·실행 근거, (5) 회귀 영향을 써라. 실행하지 못한 검증은 미검증이라고 명시하라. 근거 없는 스타일 의견과 가상의 테스트 결과는 제외하라. 변경하지 말고, 발견 없음이면 검토한 범위와 남은 한계를 분명히 보고하라.
```

## 심화/반증 프롬프트

```text
$sk-review
[과제 루트]의 [변경 파일/함수]를 [요구사항 ID 또는 계약] 기준으로 반증하라. 남은 시간은 [남은 시간: 분]분이며, 기준선은 [기준선/비교 범위]이다.

각 변경 hunk에 대해 "이 코드가 틀리려면 어떤 입력·상태·호출 순서가 필요한가?"를 질문하고, 실제 호출자와 기존 테스트에서 그 전제가 가능한지 확인하라. 다음 중 변경에 관련된 항목만 우선순위로 검사하라: 누락·빈 값, 0/최대/경계값, 타입·키·순서·단위 불일치, 오류 반환·예외 전파, 중복 요청·재시도·상태 전이, 시간대·기간 경계, 기존 API 호환성, 권한·민감정보 노출.

주장마다 파일:라인과 근거를 붙이고, 가능한 최소 재현 명령 또는 테스트 입력을 제시하라. 실제로 실행한 명령은 출력의 핵심 결과를, 실행하지 못한 것은 이유를 기록하라. Critical/High를 먼저 확정하고 시간이 부족하면 Low 탐색을 중단한 뒤 미검토 범위를 적어라. 코드 수정, 테스트 삭제, 실패 숨기기, 외부 제출·push는 하지 마라.
```

## 완료 기준

- 실제 과제 루트와 검토 범위 또는 그 부재가 기록되어 있다.
- 변경 hunk와 관련 호출자·요구사항·테스트를 읽고, 위험 우선순위로 반례를 탐색했다.
- 모든 발견은 심각도, 파일·라인, 재현, 근거, 회귀 영향으로 추적 가능하다.
- 실행 결과·미실행 이유·발견 없음 여부와 검토 한계가 구분되어 있다.
- 코드·데이터·테스트·외부 시스템을 변경하지 않았다.

## 다음 단계

Critical 또는 High가 있으면 발견 목록과 최소 재현을 공유하고, 수정할 파일·범위에 대한 별도 승인을 받은 뒤 구현 또는 디버깅 단계로 이동한다.
발견이 없고 필수 요구사항 추적과 독립 검증이 남아 있으면 08-verify로 돌아간다.
근거 있는 발견과 검증 증거가 충분하면 10-deliver의 제출 준비 점검으로 넘긴다.

## 주의

리뷰는 결함이 없음을 증명하지 않는다. diff가 없거나 요구사항·기준선·실행 환경이 없으면 "발견 없음"이 아니라 검토 불가 범위와 남은 위험을 보고한다.
원본 데이터, 기존 테스트, 사용자의 관련 없는 수정은 삭제·덮어쓰기·되돌리지 않는다.
공식 메일의 내용, 모델·일정·채점 기준·금지 규정을 추정해 만들지 않는다.
