# 9.4 한계·개선안 정리

> 스킬: `$sk-retrospect` · 단계: 후속 서술형 6문항 대비 · 작업 노트: `sk/work/UNDERSTANDING.md#한계·실패 조건·개선안` · 사용 자료: 없음

## 언제 쓰나

제출 전 AI 사용이 허용된 상태에서 Q6를 일반론 없이 설명하거나 보고서 5절에 현재 구현의 한계와 다음 개선을 적어야 할 때 쓴다. 범위 축소, 가정, 미검증, 코드 구조에서 나온 조건부 실패를 실제 근거로 정리한다.

현재 요구사항을 만족하지 않는 버그는 한계가 아니라 수정·검증할 이슈다. 그런 경우 이 프롬프트로 포장하지 말고 `6.1 debug` 또는 `7.2 compliance`로 넘긴다. AI·복붙 금지 단계가 시작되면 사용을 즉시 중단한다.

## 준비할 입력

- AI 사용 허용 여부와 남은 시간
- `sk/work/UNDERSTANDING.md`, 특히 테스트가 증명하지 못한 것과 엣지 케이스
- `sk/work/SPEC.md`의 A#/G#/비목표/T#/추적표
- `sk/work/PLAN.md`의 S#·축소 결정, `DECISIONS.md`의 DD#, `EVIDENCE.md`의 미검증/FAIL/STALE E#
- 있으면 `sk/work/REVIEW.md`의 미해결 F#과 실제 변경 코드
- 공식 문서나 관찰 근거가 없을 때 수치를 단정하지 않겠다는 원칙

## 전략 — 왜 이렇게 하나

좋은 한계 설명은 “시간이 부족했다”로 끝나지 않는다. 현재 선택이 어느 조건에서 실패할 수 있는지, 그 조건이 코드의 어느 경계에서 생기는지, 현재 방어는 무엇인지, 다음에 무엇을 바꾸고 어떻게 검증할지를 말해야 한다.

구조 한계·미검증·가정 의존·범위 축소와 현재 P0 결함을 구분하면 정직하면서도 제출 직전 우선순위를 잃지 않는다. 개선안은 실제 파일·함수·계약에 닿아야 하며, 현재 과제와 무관한 기술 나열은 제외한다.

## 기본 프롬프트

```text
$sk-retrospect
지금은 제출 전이며 AI 사용이 허용된 시간이다. 과제 파일은 수정하지 말고 읽기만 하라.
`sk/work/UNDERSTANDING.md`, `SPEC.md`, `PLAN.md`, `DECISIONS.md`, `EVIDENCE.md`와 실제 변경 코드를 읽어
현재 구현의 한계·실패 조건·개선안을 사실 기반으로 정리하라.

각 항목을 구조 한계, 미검증, 가정 의존, 범위 축소, 수정 필요 결함 중 하나로 분류하라.
현재 R#/P# 위반은 한계로 포장하지 말고 별도 수정 필요 결함으로 분리하라.
한계마다 코드·노트 근거, 조건부 영향, 현재 방어, 바꿀 위치·방법, 검증 T#/E# 계획, P0/P1/보류를 적어라.

`sk/work/UNDERSTANDING.md`의 `## 한계·실패 조건·개선안`만 갱신하라.
근거 없는 성능·보안·트래픽 수치, 무관한 기술, 실행하지 않은 검증을 쓰지 마라.
완료 후 Q6와 보고서 5절에 쓸 2문장 요약과 `9.2 qa-card ($sk-qa-card)` 인수인계를 보고하라.
```

## 심화 프롬프트 — 한계와 현재 결함을 엄격히 분리하는 상황

```text
$sk-retrospect
AI 사용 허용 시간에 다음 자료를 대조하여 Q6용 한계 분석을 작성하라.
- `sk/work/UNDERSTANDING.md`, `SPEC.md`, `PLAN.md`, `DECISIONS.md`, `EVIDENCE.md`, `REVIEW.md`
- 현재 변경 파일과 관련 테스트

먼저 현재 P0 R#, P#, 통과 E#, 미검증 E#, A#, G#, S#, F#를 표로 추려라.
그 후 각 실패 후보에 대해 '현재 요구사항 위반인가, 조건이 바뀌면 드러나는 한계인가, 아직 검증하지 않은 범위인가'를 판정하라.
현재 위반이면 수정 필요 결함으로 두고 `6.1 debug ($sk-debug)` 또는 `7.2 compliance ($sk-compliance)`에 넘겨라.

조건부 한계에는 실제 파일:함수 또는 데이터 계약 위치, 재현 조건, 현재 방어, 예상 결과, 개선의 트레이드오프를 써라.
개선마다 변경 위치, 변경 방법, 새 T# 또는 E# 검증 계획, P0/P1/보류 우선순위를 붙여라.
예를 들어 스트리밍·캐싱·재시도는 현재 구조에서 해당 문제가 확인될 때만 제안하라.

`sk/work/UNDERSTANDING.md`의 `## 한계·실패 조건·개선안`만 갱신하고 다른 작업 노트·코드·테스트는 수정하지 마라.
출력은 1) 범위 판정 2) 한계 표 3) 즉시 수정 필요 4) Q6 뼈대 5) 보고서/카드 인수인계 순서로 작성하라.
```

## 변형 — 성능·규모를 검증하지 못한 상황

```text
$sk-retrospect
AI 사용 허용 시간이다. 성능 또는 대용량 검증 E#가 없는 현재 구현의 한계를 정직하게 정리하라.
실제 코드에서 전체 입력 적재, 반복 횟수, 상태 보관, 외부 호출처럼 확인 가능한 구조만 읽기 전용으로 찾으라.
성능 저하를 단정하거나 처리량·사용자 수·메모리 수치를 지어내지 말고 '성능 미검증'과 조건부 위험을 분리하라.

`sk/work/UNDERSTANDING.md`의 지정 절에 현재 구조, 실패할 수 있는 조건, 검증 계획, 실제로 관련 있을 때만 개선 위치를 기록하라.
현재 R#/P# 위반이 발견되면 한계로 쓰지 말고 디버그 인수인계로 분리하라.
Q6에서 말할 한계 한 개와 다음 검증 한 개를 보고하라.
```

## 변형 — 남은 시간이 5분 이하인 상황

```text
$sk-retrospect
AI 사용 허용 시간이 5분 이하이다. 과제 파일은 수정하지 말고 최소 Q6 근거만 작성하라.
`sk/work/UNDERSTANDING.md`, `PLAN.md`, `EVIDENCE.md`와 현재 코드에서 실제 한계 두 개만 고르라.
각 한계에 코드/노트 근거 ID, 조건부 실패, 현실적인 개선 한 가지, 검증 한 가지를 적어라.
미검증과 현재 결함을 구분하고, 근거 없는 기술 제안은 제외하라.
`sk/work/UNDERSTANDING.md`의 `## 한계·실패 조건·개선안`만 갱신한 뒤
`9.2 qa-card ($sk-qa-card)`과 `8.1 report ($sk-report)`에 넘길 한계·개선안 항목 목록을 보고하라.
```

## 결과물 확인

- 한계마다 실제 파일·함수 또는 A#/S#/DD#/E#/F# 근거가 있다.
- P0/P# 위반인 현재 결함과 조건부 한계·미검증이 분리됐다.
- 개선안은 바꿀 위치·방법·트레이드오프·검증 계획을 포함하며 무관한 기술 나열이 아니다.
- 공식 근거 없는 규모·비용·보안·트래픽 수치를 쓰지 않았다.
- `UNDERSTANDING.md`의 `## 한계·실패 조건·개선안`만 갱신했고 과제 파일은 수정하지 않았다.

## 다음 단계

정리된 한계·개선안 항목을 [9.2 QA 카드](../9-qa/9.2-qa-card.md)의 `$sk-qa-card` Q6와 [8.1 보고서](../8-submit/8.1-report.md)의 `$sk-report` 5절에 반영한다. 현재 요구사항 미충족이 발견되면 즉시 `6.1 debug ($sk-debug)` 또는 `7.2 compliance ($sk-compliance)`으로 돌아간다.

## 주의

이 프롬프트는 AI가 허용된 제출 전 학습 시간에만 쓴다. AI·복붙 금지 단계에서는 분석·카드 보완·답안 생성을 중단한다. 코드·테스트·설정·외부 서비스·제출물을 변경하거나 배포·업로드하지 않으며, 민감한 입력값과 비밀값을 사례로 기록하지 않는다.
