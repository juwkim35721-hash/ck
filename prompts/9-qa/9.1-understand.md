# 9.1 내 구현 이해 지도

> 스킬: `$sk-understand` · 단계: 후속 서술형 6문항 대비 · 작업 노트: `sk/work/UNDERSTANDING.md` · 사용 자료: 없음

## 언제 쓰나

구현·검증·리뷰가 끝나 가고, 제출 전 AI 사용이 허용된 시간에 내 코드가 실제로 어떻게 동작하는지 되짚을 때 쓴다. Q1의 선택 이유와 Q2의 호출 흐름, Q3의 방어, Q4의 증거, Q5의 정책, Q6의 한계를 모두 실제 파일과 ID로 연결하는 준비 단계다.

AI·복붙 금지인 후속 서술형 단계가 시작된 뒤에는 절대 쓰지 않는다. 요구사항이나 정책이 아직 불명확하다면 이해 자료로 추측을 메우지 말고 1단계 또는 2단계의 원천 문서로 돌아간다.

## 준비할 입력

- AI 사용이 아직 허용된다는 확인과 남은 시간
- `sk/work/SPEC.md`, `sk/work/PLAN.md`, `sk/work/DECISIONS.md`, `sk/work/EVIDENCE.md`
- 있으면 `sk/work/REVIEW.md`, `sk/work/DM_LOG.md`, 실제 과제 코드와 테스트
- 대표 입력 1건. 민감한 실제 값 대신 익명화한 작은 값으로 준비한다.
- 현재 변경 범위를 확인할 수 있는 읽기 전용 git 상태

## 전략 — 왜 이렇게 하나

후속 문항에서 중요한 것은 포괄적인 설명이 아니라 “어느 파일의 어느 함수가, 어떤 정책을, 어떤 증거로”라는 연결이다. 먼저 명세·결정·증거를 읽고 그 다음 코드 흐름을 추적하면 AI가 그럴듯한 구조를 상상하는 일을 막을 수 있다.

대표 사례 1건을 값의 흐름으로 따라가면 Q2를, 실제 Guard와 정책 근거를 붙이면 Q3·Q5를, 테스트가 증명하지 못한 범위를 남기면 Q4·Q6를 정직하게 설명할 수 있다. 이 단계는 분석만 하며 과제 파일을 수정하지 않는다.

## 기본 프롬프트

```text
$sk-understand
지금은 제출 전이며 AI 사용이 허용된 시간이다. 과제 코드는 수정하지 말고 읽기만 하라.
`sk/work/SPEC.md`, `sk/work/DECISIONS.md`, `sk/work/EVIDENCE.md`와 실제 변경 파일·테스트를 읽어
내 구현을 가르치듯 설명할 수 있는 지도를 만들어라.

`sk/work/UNDERSTANDING.md`의 정확한 열 개 절만 만들거나 갱신하라.
특히 목표, 입력→Guard→핵심 규칙→출력 흐름, 파일·함수 지도, 익명화한 예시 1건 추적을 실제 코드로 확인하라.
P#/A#가 강제되는 코드 위치, 실제 엣지 케이스와 Guard 위치, DD# 선택 근거, T#/E# 검증 범위를 연결하라.

실행하지 않은 검증·없는 정책·없는 AI 교정은 만들지 말고 미검증 또는 근거 없음으로 표시하라.
`sk/`은 도구이므로 과제 코드 분석 대상에서 제외하라.
완료 후 Q1~Q6별로 재사용할 근거 ID를 표로 보고하고, 다음에 할 한 가지 행동을 제안하라.
```

## 심화 프롬프트 — 코드와 노트가 어긋나거나 설명 근거가 부족한 상황

```text
$sk-understand
AI 사용 허용 시간에 다음 자료를 대조해 내 구현의 사실 기반 이해 지도를 작성하라.
- 명세: `sk/work/SPEC.md`
- 계획·결정: `sk/work/PLAN.md`, `sk/work/DECISIONS.md`
- 실행 증거·리뷰: `sk/work/EVIDENCE.md`, `sk/work/REVIEW.md`
- 정책 원문: `sk/work/DM_LOG.md`
- 현재 코드·테스트: `<변경 파일 또는 진입점>`

먼저 각 원천의 기준 시점과 현재 git 변경 범위를 읽기 전용으로 확인하라.
그 다음 P0 R#, P#, A#, DD#, T#, E#, AI#, F#를 파일·함수·테스트 위치에 연결하는 표를 만들어라.
대표 입력 `<익명화한 입력>` 하나를 선택해 입력값, 각 함수의 중간 상태, 적용 조건, 출력 또는 오류를 순서대로 추적하라.

노트의 함수명이 코드에 없거나 E#가 현재 코드보다 오래됐으면 어느 것이 어긋났는지 명시하고 PASS로 포장하지 마라.
정책 분기가 코드에 보이지 않으면 구현 누락 가능성으로 표시하고 관련 R/P/T와 함께 인수인계하라.
`sk/work/UNDERSTANDING.md`의 지정 절만 갱신하며 과제·테스트·설정 파일은 수정하지 마라.

출력은 1) 한 문단 요약 2) 흐름도 3) Q1~Q6 근거표 4) 미검증/가정/결함 가능성 5) 다음 단계 순서로 작성하라.
발견한 결함은 수정하지 말고 `6.1 debug ($sk-debug)` 또는 `7.2 compliance ($sk-compliance)` 중 맞는 하나로 넘겨라.
```

## 변형 — 남은 시간이 10분 이하인 상황

```text
$sk-understand
AI 사용 허용 시간이 10분 이하이다. 과제 파일은 수정하지 말고 최소 이해 지도를 만들어라.
`sk/work/SPEC.md`, `sk/work/EVIDENCE.md`, 현재 변경 파일만 우선 읽어라.
`sk/work/UNDERSTANDING.md`에 한 문단 요약, 전체 흐름, 핵심 사실 10개를 먼저 완성하라.
각 사실은 실제 파일·함수명 또는 R#/P#/T#/E# 하나와 연결하라.

대표 사례는 하나만, 엣지 케이스는 실제 Guard가 있는 것만 적어라.
미검증·가정은 숨기지 말고 별도 표시하라. 실행·수정·제출은 하지 마라.
마지막에 `9.2 qa-card ($sk-qa-card)`에 넘길 Q1~Q6 근거를 축별로 한 줄씩 보고하라.
```

## 변형 — 대표 사례를 말로 따라가기 어려운 상황

```text
$sk-understand
AI 사용 허용 시간이다. Q2 설명을 위해 대표 사례 하나의 코드 경로만 깊게 추적하라.
진입점 `<파일·함수>`에서 시작해 `<익명화한 입력>`이 출력까지 가는 실제 호출을 읽기 전용으로 확인하라.
각 단계에 파일·함수, 입력값/중간 상태, 적용한 P#/A#, 다음 상태를 표로 기록하라.
Guard에서 중단되는 대안 경로 하나도 실제 코드에 있을 때만 덧붙여라.

`sk/work/UNDERSTANDING.md`의 `## 예시 1건 추적`과 `## 전체 흐름`만 갱신하라.
추정한 상태나 실행하지 않은 결과를 쓰지 말고, Q2에서 반드시 말할 함수명 세 개와 근거를 보고하라.
```

## 결과물 확인

- `UNDERSTANDING.md`에 정확한 열 개 절 제목이 있고, 다른 스킬의 절을 덮어쓰지 않았다.
- 흐름도와 사례 추적이 실제 진입점·파일·함수·정책 P#/A#와 일치한다.
- 엣지 케이스는 실제 Guard 위치 및 T#/E# 또는 미검증 상태와 연결된다.
- DD#, AI#, 테스트 수, 실행 결과에 근거가 없으면 지어내지 않고 표시했다.
- 현재 요구사항 위반 가능성은 한계로 포장하지 않고 디버그/감사에 인계했다.

## 주의

이 프롬프트는 제출 전 학습 자료를 만드는 용도다. AI·복붙 금지 단계가 시작되면 사용·열람·보완을 즉시 중단한다. Codex는 담당자 DM을 보내지 않으며, 코드·테스트·설정·제출물을 수정하지 않는다. 민감 데이터·토큰·개인정보는 사례 값이나 노트에 적지 않는다.
