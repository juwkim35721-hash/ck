# 2.3 수용 기준·테스트 케이스 표

> 스킬: `$sk-acceptance` · 단계: 구현 전 명세 정리·동결 · 작업 노트: `sk/work/SPEC.md#11. 수용 테스트 표 T` · 사용 자료: `없음`

## 언제 쓰나

2.1에서 P0/P1 요구사항과 AC를 정리하고, 가능하면 2.2에서 입출력 계약을 확정한 뒤 사용한다.
구현 전 "완료"를 정상·경계·실패·회귀 입력과 독립 기대값으로 바꿀 때 쓴다.
이 단계는 표를 작성하는 단계이며 실제 테스트 파일 추가·실행은 4.1에서 한다.

## 준비할 입력

- 현재 기준: `sk/work/SPEC.md`의 R, P, A, G, 10절 계약
- 기존 테스트 정보: `<테스트 프레임워크·테스트 경로 또는 불명>`
- 제공 테스트: `<파일·테스트명 또는 없음>`
- 정산·집계 등 독립 계산 필요 여부: `<있음/없음과 대상 R>`
- 시간 상황: `<남은 시간: 분>`
- 특별히 불확정인 기대값: `<G# 또는 A# 목록 또는 없음>`

## 전략 — 왜 이렇게 하나

테스트 표는 구현 방식 목록이 아니라 "이 입력에서 이 결과여야 한다"는 판정 기준이다.
기대값을 구현 예정 함수의 결과에 기대면 코드와 테스트가 같이 틀릴 수 있으므로 손계산·문서·P#·픽스처로 독립 근거를 남긴다.
제공 테스트의 존재는 범위 충족 증거가 아니다. 실제로 어떤 R/P/AC를 assert하는지 따로 표시한다.

## 기본 프롬프트

```text
$sk-acceptance
sk/work/SPEC.md의 R, AC, P, A, G, 10절 입출력 계약과 <테스트 프레임워크·테스트 경로 또는 불명>을 읽어라.
P0/P1 R과 모든 P#를 구현 전 수용 테스트 T# 표로 바꾸되, 코드·테스트 파일은 수정하거나 실행하지 마라.

각 T#는 ID | 관련 R/P | 유형 | 입력 | 기대 출력 | 기대값 근거 | 확인 방법 | 제공 테스트 여부 열을 정확히 사용하라.
P0/P1의 각 AC에는 하나 이상의 T#를, 모든 P#에는 최소 하나의 T#를 연결하라.
유형은 정상·경계·실패·회귀로 구분하고 입력에는 실제 값·사전조건·요청을 적어라.
기대 출력에는 정확한 값·상태·스키마·정렬·불변을 쓰고 '정상 처리'처럼 모호하게 쓰지 마라.
기대값 근거는 손계산, 공식 문서, P#, 제공 픽스처 중 하나 이상으로 독립시켜라.
제공 테스트는 파일·테스트명과 실제 검증 범위를 확인할 수 있을 때만 표시하라.
A# 또는 G# 때문에 값이 갈리면 임의 기대값을 만들지 말고 관련 ID와 확인 필요성을 적어라.
SPEC 11절만 갱신하고 커버리지 점검에 P0/P1/P#와 유형별 수를 기록하라.
끝나면 누락된 AC/P 커버리지, 대표 경계·실패 사례, 2.4 게이트 전 막힌 항목을 보고하라.
```

## 심화 프롬프트 — 기대값의 독립성과 제공 테스트의 빈틈을 반증할 때

```text
$sk-acceptance
sk/work/SPEC.md 전체와 <기존 테스트 경로>를 읽기 전용으로 대조해 11절의 T# 표를 작성 또는 강화하라.
특히 다음 R/P는 오류가 나기 쉬우므로 우선 검증하라: <R#/P# 목록 또는 전체 P0>.
테스트 파일은 만들거나 실행하지 마라.

먼저 P0/P1의 AC-R#-n과 P#를 행으로 펴고, 각 행에 연결된 T#가 있는지 빈칸을 표시하라.
각 P#의 조건→동작이 정상·경계 중 어느 입력으로 가장 잘 깨지는지 고르고 최소 하나의 T#를 배정하라.
집계·금액·기간·정렬 값은 구현 예정 함수가 아닌 손계산 식, 문서 절, P# 또는 별도 픽스처로 근거를 적어라.
예를 들어 합계라면 구성값과 계산식을, 정렬이라면 비교 키·동점 규칙·기대 순서를 명시하라.
실패 유형은 계약에 있는 오류 상태·본문·불변 조건만 기대하고, 미확정 오류 규칙은 G#로 반환하라.
기존 제공 테스트마다 테스트명·입력·assert를 읽어 관련 R/P를 표시하되, 범위를 확인할 수 없으면 제공됨(범위 미확인)으로 써라.
한 T#가 너무 많은 동작을 가려 실패 원인을 분리할 수 없으면 값·스키마·정렬·오류를 나눠라.
A# 의존 T#에는 A#와 가정이 바뀔 때 바뀌는 기대값을 병기하라.
11절 표의 열 순서를 유지하고, `### 커버리지 점검`에 P0·P1·P#·정상·경계·실패·회귀의 실제 수를 기록하라.
12절 추적표·테스트 코드·과제 파일은 건드리지 마라.
끝나면 테스트로 아직 증명하지 못하는 영역과 2.4에서 BLOCKED가 될 수 있는 누락을 명확히 보고하라.
```

## 변형 — AC가 모호해서 테스트 표가 막혔을 때

```text
$sk-acceptance
sk/work/SPEC.md의 <R#/AC 목록>은 '빠르게', '적절히', '정상적으로'처럼 기대 결과가 모호하다.
11절에 근거 없는 T#를 채우지 말고, R·AC·P·10절 계약·DM 원문을 읽어 구체화 가능한 근거를 먼저 찾아라.
문서나 P#로 확정되는 값·상태·정렬·오류 조건만 T# 후보로 작성하라.
근거가 없어서 결과가 둘 이상으로 갈리면 G#와 결과 예시를 정리하고 필요한 담당자 질문을 최대 3개 제시하라.
질문 없이도 임시 진행이 필요하면 A#의 기본안·위험·되돌릴 지점이 있는지 확인하고, T#의 관련 R/P에 A#를 병기하라.
AC 자체가 부족하면 2.1에서 고칠 정확한 AC-R#-n 문안을 제안하되 SPEC의 3절은 수정하지 마라.
11절은 이미 근거가 있는 T#만 갱신하고, P0 커버리지의 빈칸을 숨기지 마라.
끝나면 2.1·1.3·2.4 중 먼저 가야 할 단계와 이유를 보고하라.
```

## 변형 — 시간이 부족해 최소 P0 테스트 기준을 만들 때

```text
$sk-acceptance
남은 시간은 <남은 시간: 분>이다. sk/work/SPEC.md를 읽고 11절에 최소 구현 착수용 T# 표를 만들어라.
범위는 모든 P0 R의 AC와 모든 P#이며, P1/P2는 누락 상태를 명시하고 확장하지 마라.
각 P0 R에는 대표 정상 1개와 가장 위험한 경계 또는 실패 1개를 먼저 배정하라.
각 P#에는 조건→동작을 직접 깨는 T#를 최소 하나 배정하라.
구체 입력·기대 출력·독립 근거가 없는 테스트는 만들지 말고, 필요한 G#/A#를 표시하라.
확인 방법은 4.1에서 기존 프레임워크에 옮길 수 있도록 테스트 대상·assert 요점을 써라.
기존 테스트를 실행하거나 추가하지 말고 11절만 갱신하라.
커버리지 점검에 P0/P1/P#와 유형별 실제 수를 기록하고, 2.4에서 READY-WITH-ASSUMPTIONS 또는 BLOCKED가 될 위험을 보고하라.
```

## 결과물 확인

- 모든 P0/P1 AC와 P#가 하나 이상의 T#에 연결됐는가?
- T# 표의 여덟 열, 구체 입력, 관찰 가능한 기대 출력, 독립 근거가 모두 있는가?
- 정상·경계·실패가 구분되고 필요한 기존 동작은 회귀로 표시됐는가?
- 제공 테스트의 실제 경로·범위와 "제공됨(범위 미확인)"을 구분했는가?
- 테스트 코드나 12절 추적표를 바꾸지 않았는가?

## 주의

테스트 표를 통과 결과로 쓰지 않는다. 이 단계에서는 어떤 테스트도 실행하지 않는다.
AI가 예상한 결과나 구현 예정 함수의 결과를 기대값 근거로 삼지 않는다.
문서·P#에 없는 오류 코드·기본값·반올림·정렬을 억지로 T#에 넣지 않는다.
과제 코드, 테스트, 데이터, 설정을 수정·삭제하거나 외부 제출·배포·push·업로드하지 않는다.
