# 2.4 구현 착수 게이트·명세 동결

> 스킬: `$sk-spec-gate` · 단계: 구현 전 명세 정리·동결 · 작업 노트: `sk/work/SPEC.md#0. 상태, #14. 게이트 결과` · 사용 자료: `없음`

## 언제 쓰나

2.1의 통합 명세, 2.2의 입출력 계약, 2.3의 T# 표를 준비한 뒤 코드 작성 직전에 쓴다.
목적은 "대체로 알겠다"를 READY/READY-WITH-ASSUMPTIONS/BLOCKED라는 재현 가능한 판정으로 바꾸는 것이다.
새 정책·AC·계약을 만드는 단계가 아니라, 빈칸과 충돌을 찾아 최소 보완 행동으로 되돌리는 단계다.

## 준비할 입력

- 단일 기준 문서: `sk/work/SPEC.md` 전체
- 발견·답변 근거: `sk/work/BRIEF.md`, `sk/work/DISCOVERY.md`, `sk/work/DM_LOG.md`
- 시간: `<현재 시각과 과제 시작 후 경과 시간>`
- 기준선 정보: `<실행 명령·결과 또는 실행 불가 사유>`
- 특히 불안한 항목: `<P0 R#/P#/A#/G# 또는 없음>`
- 제출물 요구: `<확정 경로·형식 또는 미정>`

## 전략 — 왜 이렇게 하나

게이트는 구현 품질을 보장하는 테스트가 아니라 구현해도 되는 명세 상태를 판정한다.
P0 R의 AC와 T, 모든 P의 출처와 T, H 영향 가정의 되돌릴 지점이 연결돼야 코드가 추측을 굳히지 않는다.
40분이 지났다고 필수 제출물·P0·계약의 빈칸이 사라지지 않는다. 되돌릴 수 있는 가정만 READY-WITH-ASSUMPTIONS로 관리한다.

## 기본 프롬프트

```text
$sk-spec-gate
sk/work/SPEC.md 전체와 sk/work/BRIEF.md, sk/work/DISCOVERY.md, sk/work/DM_LOG.md를 읽고 구현 착수 게이트를 수행하라.
현재는 <현재 시각과 과제 시작 후 경과 시간>이고, 기준선 정보는 <실행 명령·결과 또는 실행 불가 사유>이다.
과제 코드·테스트·데이터를 수정·실행하지 말고 SPEC의 0절과 14절만 갱신하라.

목표·필수 제출물, 모든 P0 R의 AC와 T, 모든 P의 조건→동작·출처·T, C, 10절 계약, A/G, 비목표, 기준선을 실제 표로 대조하라.
14절에 항목 | 판정 | 근거 위치 | 부족하면 필요한 최소 행동 체크리스트를 작성하라.
공식 문서와 P의 충돌, P0 AC/T 누락, 필수 제출물 미정, 되돌릴 수 없는 H G, 필수 계약 부재는 BLOCKED로 판정하라.
P0·T·계약은 있으나 되돌릴 수 있는 A 또는 H G의 임시 처리만 남으면 READY-WITH-ASSUMPTIONS로 판정하라.
모든 필수 항목이 근거로 충족되고 실질 가정이 없을 때만 READY로 판정하라.
시작 후 약 40분을 넘겼다면 기다리던 답을 A로 안전하게 전환할 수 있는지 검토하되, 핵심 누락은 READY로 바꾸지 마라.
0절에 최종 상태와 판정 시각을 쓰고, 14절에 이유·위험·최소 다음 행동·동결 후 변경 절차를 남겨라.
끝나면 최종 상태, 가장 큰 위험, 사용자가 지금 할 행동 1개, READY 계열일 때 3.1 인계를 보고하라.
```

## 심화 프롬프트 — READY 판정을 반증하며 누락·충돌을 감사할 때

```text
$sk-spec-gate
아래처럼 READY라고 주장된 sk/work/SPEC.md를 반증하는 관점에서 게이트를 다시 수행하라.
함께 읽을 자료는 sk/work/BRIEF.md, sk/work/DISCOVERY.md, sk/work/DM_LOG.md이고 현재 시간은 <현재 시각·시작 후 경과 시간>이다.
과제 파일과 0절·14절 밖의 SPEC 내용은 수정하지 마라.

R 표에서 모든 P0를 꺼내 각각 AC-R#-n, T#, 출처, 제출물 또는 계약 연결이 있는지 행 단위로 검사하라.
P 표에서 모든 P#를 꺼내 조건→동작, 예시, M#/문서 근거, 영향 R, T#를 모두 찾을 수 있는지 검사하라.
A 표에서 근거·위험·되돌릴 지점·확인 계획이 모두 있는지, G 표에서 H 영향 항목이 A로 안전하게 관리되는지 검사하라.
10절에서 필요한 입력·출력·오류·키·정렬·빈 결과 계약이 있는지, 11절에서 구체 입력·기대 출력·독립 근거가 있는지 검사하라.
공식 문서↔P, P↔코드 관찰, 제출물 경로↔과제 안내의 충돌을 찾아도 독단으로 해결하지 마라.
기준선은 실제 명령·결과 또는 실행 불가 사유가 있는 경우만 충족으로 처리하라.
14절 체크리스트에 각 판정의 정확한 근거 위치와 최소 보완 행동을 적어라.
READY, READY-WITH-ASSUMPTIONS, BLOCKED 중 하나를 정의에 맞춰 고르고 0절에 상태·시각을 적어라.
READY-WITH-ASSUMPTIONS이면 A#/G#, 위험, 되돌릴 지점, 확인 계획을 요약하고 40분 경과 규칙 적용 여부를 밝혀라.
동결 시각과 13절 변경 기록 → 영향 R/AC/P/A/G/T 갱신 → 재게이트 절차를 14절에 명시하라.
끝나면 판정 근거, BLOCKED를 해소하는 최소 행동 1개, 3.1 또는 1.3/1.5로 갈 다음 단계를 보고하라.
```

## 변형 — 담당자 답변을 기다리다 40분 상한에 도달했을 때

```text
$sk-spec-gate
과제 시작 후 약 40분이 지났고 <질문 내용>에 대한 담당자 답변이 아직 없다.
sk/work/SPEC.md, sk/work/BRIEF.md, sk/work/DISCOVERY.md, sk/work/DM_LOG.md를 읽고 0절과 14절의 게이트를 실제 상태로 갱신하라.
우선 모든 P0 R의 AC·T, 필수 제출물, 10절 계약, P# 출처가 이미 갖춰졌는지 점검하라.
미응답 항목이 결과를 바꾸면 A#에 기본안·위험·되돌릴 지점·확인 계획이 있는지 확인하라.
되돌릴 수 있는 A로 관리 가능하고 나머지 P0 기준이 갖춰졌을 때만 READY-WITH-ASSUMPTIONS로 판정하라.
필수 제출물 미정, P0 AC/T 누락, 문서↔P 충돌, 되돌릴 수 없는 H G, 필수 계약 부재라면 시간과 무관하게 BLOCKED로 판정하라.
14절 표에 기다리지 않고 할 최소 안전 행동과 담당자 답이 왔을 때 재게이트할 조건을 기록하라.
코드·테스트·데이터는 건드리지 말고, 상태·시각·가정·위험을 숨기지 않은 채 결과를 보고하라.
```

## 변형 — 공식 문서와 DM 정책이 정면 충돌할 때

```text
$sk-spec-gate
sk/work/SPEC.md에서 <R#/P#/G#>에 대해 공식 문서와 담당자 정책이 충돌한다.
공식 문서 경로는 <문서 경로>이고, 담당자 답변 원문은 sk/work/DM_LOG.md의 <M#>이다.
0절과 14절만 수정하면서 이 충돌이 READY를 막는지 판정하라.
각 근거의 위치, 결과가 달라지는 입력 예시, 영향을 받는 R/AC/P/T/제출물, 확인해야 할 담당자 질문을 표로 정리하라.
어느 근거도 임의로 선택하거나 P#를 삭제하지 말고 G#로 보존하라.
문서와 P가 동일 동작을 다르게 요구하면 BLOCKED로 판정하고, 1.3 또는 1.5에서 보낼 최소 확인 행동을 제시하라.
충돌과 무관한 P0는 진행 가능하더라도 전체 게이트 상태와 부분 진행 가능 범위를 분리해 보고하라.
동결하지 말아야 하는 이유와 답변 뒤 재게이트 순서를 14절에 적어라.
```

## 결과물 확인

- 0절에 DRAFT/READY/READY-WITH-ASSUMPTIONS/BLOCKED 중 하나와 실제 판정 시각이 있는가?
- 14절에 P0 AC/T, P 출처/T, A/G, 계약, 제출물, 기준선, 비목표를 대조한 표가 있는가?
- READY 계열의 가정은 되돌릴 지점·확인 계획을 가지고, BLOCKED 원인은 감춰지지 않았는가?
- 40분 규칙을 핵심 누락 면제가 아니라 가정 관리 규칙으로 적용했는가?
- 13절 변경 기록·재게이트 절차가 동결 규칙으로 적혔는가?

## 주의

게이트 통과는 테스트 통과나 구현 정확성을 뜻하지 않는다. 실제 실행 근거가 없는 기준선·테스트를 통과로 적지 않는다.
DM을 직접 보내거나 담당자 답변·공식 규칙을 만들어 내지 않는다.
과제 코드·테스트·데이터·설정을 수정·삭제·실행하지 않고, 외부 제출·배포·push·업로드도 하지 않는다.
동결 뒤 변경은 13절 기록과 영향 R/AC/P/A/G/T 갱신, 필요 시 재게이트 없이는 진행하지 않는다.
