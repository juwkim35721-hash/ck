# 2.1 명세 통합 (SPEC.md)

> 스킬: `$sk-spec` · 단계: 구현 전 명세 정리·동결 · 작업 노트: `sk/work/SPEC.md` · 사용 자료: `없음`

## 언제 쓰나

1.1 요구사항 추출과 1.2 모호성 탐지가 끝난 뒤, 1.4에서 해석한 담당자 답변까지 한 기준 문서로 합칠 때 쓴다.
코드를 쓰기 전에 P0 범위, 정책, 가정, 열린 질문, 제출물을 한 번에 보이게 해야 할 때 사용한다.
담당자 답변이나 공식 문서가 새로 들어왔으면 같은 프롬프트로 근거와 변경 기록을 갱신한다.

## 준비할 입력

- 읽을 자료: `<과제 README·공식 문서 경로>`, `sk/work/BRIEF.md`, `sk/work/DISCOVERY.md`, `sk/work/DM_LOG.md`
- 기존 명세: `sk/work/SPEC.md`가 있으면 그대로 보존하면서 갱신
- 시간 상황: `<남은 시간 또는 시작 후 경과 시간>`
- 새로 받은 자료: `<붙여넣은 담당자 답변 또는 없음>`
- 특히 확인할 충돌: `<문서·답변·기존 테스트가 서로 다른 부분 또는 없음>`

## 전략 — 왜 이렇게 하나

SPEC은 구현 중 다시 해석할 메모가 아니라, 무엇을 만들고 어떻게 완료를 증명할지 정한 단일 기준 문서다.
따라서 관찰 사실, 확정 정책, 임시 가정, 미해결 질문을 섞지 않고 ID와 출처로 연결해야 한다.
우선순위는 공식 과제 문서·대회 안내, 담당자 확정 답변 P#, 관찰된 코드·테스트, 가정 A# 순이다.
공식 문서와 P#가 충돌하면 구현 편의로 고르지 말고 G#와 확인 문안으로 남긴다.

## 기본 프롬프트

```text
$sk-spec
<과제 README·공식 문서 경로>, sk/work/BRIEF.md, sk/work/DISCOVERY.md,
sk/work/DM_LOG.md와 기존 sk/work/SPEC.md를 읽고 구현 전 단일 기준 명세를 정리하라.
현재 시간 상황은 <남은 시간 또는 시작 후 경과 시간>이며, 새 담당자 답변은 <붙여넣은 담당자 답변 또는 없음>이다.
과제 코드·테스트·데이터는 읽기만 하고 수정하지 마라.

SPEC.md 표준 0~14절 제목이 없으면 모두 만들되, 이번에는 1~9절과 13절만 채워라.
0·14절은 게이트, 10절은 데이터 계약, 11절은 수용 테스트, 12절은 구현·검증의 소유이므로 덮어쓰지 마라.
한 장 요약은 10줄 이내, 구현 Top 5는 실패 비용이 큰 규칙만 써라.
모든 R에 P0/P1/P2, 출처, 상태, AC-R#-n을 입력→기대 출력 또는 Given/When/Then으로 붙여라.
P는 조건→동작·작은 예시·M#/문서 근거·영향 R을, A는 위험·되돌릴 지점·확인 계획을 갖게 하라.
공식 문서와 P가 충돌하면 G로 남기고 확인 문안을 제안하되 임의로 해결하지 마라.
이번 갱신을 13절 변경 기록에 남겨라.
끝나면 P0·핵심 P·남은 G/A·다음 단계 2.2와 2.3을 순서대로 보고하라.
```

## 심화 프롬프트 — 상충 자료를 반증하며 명세를 동결 직전까지 정리할 때

```text
$sk-spec
아래 자료를 근거 우선순위대로 대조해 sk/work/SPEC.md의 1~9절과 13절을 재구성하라.
공식 자료: <과제 README·공식 문서 경로>
발견 노트: sk/work/BRIEF.md, sk/work/DISCOVERY.md
DM 원문·정책: sk/work/DM_LOG.md
현재 SPEC: sk/work/SPEC.md
새 답변: <붙여넣은 담당자 답변 또는 없음>

먼저 출처별 주장 목록을 만들고 같은 R에 영향을 주는 문장끼리 묶어라.
공식 문서 > P# > 관찰된 테스트·코드 > A# 순으로 판단하되, 문서와 P# 충돌은 G#로만 남겨라.
R은 하나의 검증 가능한 동작씩으로 쪼개고 모든 P0에는 최소 하나의 AC-R#-n을 넣어라.
AC는 입력·사전조건·동작·기대값이 보여야 하며, '정상 동작' 같은 표현을 제거하라.
제약 C와 정책 P를 분리하고, P의 적용 조건·결과·예시·근거·영향 R을 표에 빠짐없이 기록하라.
답변이 모호하면 P로 일반화하지 말고 A#의 기본안·위험·되돌릴 지점·확인 계획으로 제한하라.
열린 G에는 영향, 갈리는 결과 예시, 처리 방식, 결정 필요 시점을 기록하라.
필수 제출물은 경로·파일명·형식·출처로 확정 여부를 보이고, 미정이면 G로 연결하라.
한 장 요약 10줄과 Top 5가 세부 표와 모순되지 않는지 역검토하라.
13절에는 이번 정리의 시각, 변경, 근거, 영향 R/P/T를 남겨라.
다른 소유 절 0·10·11·12·14는 읽기만 하고 변경하지 마라.
마지막에 충돌별 확인 질문 초안, P0 커버리지 누락, 2.2/2.3에 넘길 입력을 표로 보고하라.
```

## 변형 — 담당자 답변을 기다리며 최소 명세만 확정할 때

```text
$sk-spec
현재 남은 시간은 <남은 시간: 분>이며 담당자 답변은 아직 없다.
sk/work/BRIEF.md와 sk/work/DISCOVERY.md, 과제 문서를 읽고 sk/work/SPEC.md의 1~9절과 13절을 작성하라.
특히 P0 최소 범위, 필수 제출물, 인터페이스·수정 범위 제약, H 영향 G를 우선 확정하라.
문서로 확정된 규칙만 P로 쓰고, 답변이 필요한 기본값은 A로 분리하라.
A마다 어떤 구현 경계에서 되돌릴지와 언제 확인할지를 써라.
H 영향 G는 결과가 어떻게 갈리는지 작은 입력 예시로 적고, 1.3에서 보낼 질문 후보를 최대 3개로 제한하라.
AC가 없는 P0는 즉시 보완하고, P1/P2 세부화는 시간 부족으로 남겼다면 상태를 숨기지 마라.
0·10·11·12·14절은 수정하지 말고 이번 갱신만 13절에 기록하라.
끝나면 READY를 주장하지 말고, 2.2·2.3·2.4 전에 반드시 보완할 빈칸을 우선순위로 보고하라.
```

## 변형 — 공식 문서와 담당자 답변이 충돌할 때

```text
$sk-spec
<공식 문서 경로>의 문장과 아래 담당자 답변이 같은 동작에 대해 충돌하는지 분석하라.
담당자 답변: <붙여넣은 담당자 답변>
sk/work/BRIEF.md, sk/work/DISCOVERY.md, sk/work/DM_LOG.md, sk/work/SPEC.md도 함께 읽어라.
두 근거의 정확한 문장·위치, 영향을 받는 R/C/P/AC, 결과가 달라지는 입력 예시를 표로 분리하라.
어느 쪽을 구현할지 임의로 선택하거나 P를 덮어쓰지 마라.
충돌마다 G#를 만들고 영향도·결정 필요 시점·기본안·되돌릴 지점을 기록하라.
사용자가 보내야 할 짧은 확인 질문을 1.3 형식에 맞게 초안으로 제시하라.
기존 명세의 1~9절과 13절만 필요한 범위에서 갱신하고 다른 소유 절은 보존하라.
마지막에 이 상태에서 2.2·2.3을 진행 가능한 항목과 게이트를 막는 항목을 구분해 보고하라.
```

## 결과물 확인

- `sk/work/SPEC.md`에 표준 0~14절 제목이 있고, 1~9절과 13절이 현재 근거로 갱신됐는가?
- 한 장 요약은 10줄 이하이며, 모든 R에는 우선순위·AC·출처·상태가 있는가?
- 모든 P에는 조건→동작, 예시, 근거, 영향 R이 있고 A/G와 섞이지 않았는가?
- 공식 문서↔P 충돌을 조용히 선택하지 않고 G와 질문 초안으로 남겼는가?
- 다른 스킬 소유 절을 바꾸지 않았는가?

## 다음 단계

입출력 또는 데이터 경계가 있으면 [2.2 입출력·데이터 계약](../2-spec/2.2-io-contract.md)으로 이어간다.
P0와 정책을 구체 입력·기대값으로 바꾸려면 [2.3 수용 기준·테스트 케이스 표](../2-spec/2.3-acceptance.md)를 사용한다.

## 주의

과제 코드·테스트·데이터·설정을 수정하거나 DM을 직접 보내지 않는다.
공식 안내에 없는 일정·채점·금지 규정, 받지 않은 담당자 답변, 실행하지 않은 결과를 사실처럼 기록하지 않는다.
민감한 데이터 값·토큰·개인정보는 명세와 채팅에 남기지 않는다.
동결 이후에는 13절 변경 기록 없이 명세를 조용히 바꾸지 않는다.
