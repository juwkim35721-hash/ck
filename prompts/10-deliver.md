# 제출·릴리스 준비

## 사용 시점
구현, 방어, 독립 검증, 리뷰가 끝났거나 마감 직전에 제출 가능 상태를 판단할 때 사용한다.
이 단계는 해커톤 결과물의 제출·릴리스 **준비**만 다루며, 외부 제출이나 배포를 실행하지 않는다.
앞 단계의 주장 대신 현재 파일, 실제 실행 결과, 공식 안내를 근거로 최종 상태를 확인한다.

## 필요 입력
- [과제 루트]: `~/sk` 같은 준비 도구 경로가 아닌 실제 과제 저장소의 절대 경로로 바꾼다.
- [남은 시간: 분]: 필수 점검을 우선순위화할 실제 분 단위 시간으로 바꾼다.
- [공식 제출 안내/요구사항]: 제출 경로, 필수 파일명, 형식, 마감, 허용 도구 규칙의 원문 또는 링크를 넣는다.
- [요구사항 ID와 수용 기준]: 예: R1, R2와 각각의 검증 기준을 넣는다.
- [최종 검증 명령과 결과]: 실제로 실행한 명령, 종료 코드, 통과·실패·미실행을 넣는다.
- [제출 예정 파일/산출물]: 이름, 상대 경로, 형식, 생성 방법을 넣는다.
- [알려진 문제·사용자 승인 범위]: 남은 결함, 제한, 외부 동작 승인 여부를 넣는다.
공식 안내나 테스트 결과가 없으면 추정으로 채우지 말고, 먼저 필요한 원문이나 실행 결과를 요청한다.

## 전략
1. 먼저 AI 사용 가능 여부와 제출 규칙의 출처를 확인한다. 후속 AI 금지 서술형 평가가 시작되면 즉시 프롬프트·스킬·암기자료 사용을 중단한다.
2. 실제 과제 루트를 확인하고, 제출 대상 파일의 존재·이름·확장자·형식·상대 경로를 공식 요구와 한 항목씩 대조한다.
3. 작업 트리의 수정·미추적 파일은 기록만 하고, 다른 사람의 변경을 되돌리거나 삭제·stash·재작성하지 않는다.
4. R1 등 요구사항마다 마지막 성공 증거를 연결한다. 결과가 오래되었거나 코드·입력이 바뀌었으면 허용된 재현 명령을 다시 실행한다.
5. 테스트는 종료 코드만 보지 말고 핵심 출력, 스키마, 생성물, 실패 사례가 수용 기준을 뒷받침하는지 확인한다.
6. 재현 명령은 실제 실행 디렉터리·필요 환경·입력·명령·결과를 짧게 남긴다. 실행하지 못했으면 원인과 미검증으로 표시한다.
7. 제출 대상과 설정 파일을 범위 내에서 점검해 자격증명, 토큰, 개인 데이터, 비밀 키의 노출 징후를 찾는다. 의심 내용은 값 자체를 출력하지 말고 경로와 유형만 보고한다.
8. 알려진 버그는 심각도, 영향, 우회 가능성, 제출 판단에 미치는 영향을 분리한다. 실패·경고·누락을 통과로 바꾸지 않는다.
9. 남은 시간이 부족하면 새 기능, 전면 리팩터링, 장식 작업을 중단하고 필수 파일 → 핵심 재현 → 민감정보 점검 → 최종 체크 순서를 지킨다.
10. 모든 필수 항목의 실제 증거가 있고 차단 결함·민감정보 위험이 없을 때만 `GO`로 판정한다. 증거 또는 공식 규칙이 부족하면 `CONDITIONAL`, 차단 결함이면 `NO-GO`로 판정한다.

## 기본 프롬프트
```text
$sk-deliver
실제 과제 루트는 [과제 루트]이고 남은 시간은 [남은 시간: 분]분이다.
공식 제출 안내는 [공식 제출 안내/요구사항]이며, 안내가 없는 내용은 추정하지 마라.
요구사항과 수용 기준은 [요구사항 ID와 수용 기준]이다.
제출 예정 파일은 [제출 예정 파일/산출물]이고, 마지막 검증 증거는 [최종 검증 명령과 결과]이다.
알려진 문제와 승인 범위는 [알려진 문제·사용자 승인 범위]이다.

제출 준비만 수행하라. 실제 과제 루트와 공식 규칙을 먼저 대조하고, 필수 파일·형식·저장 상태·재현 가능성·민감정보 노출·남은 버그를 점검하라.
각 요구사항에 실제 실행 명령과 관찰 결과를 연결하되, 실행하지 않은 항목은 미검증으로 적어라.
외부 push, 배포, 업로드, 제출 버튼 조작, 비밀정보 전송은 수행하지 마라.
다른 사람의 변경을 삭제·되돌리거나 실패를 숨기지 마라.
마지막에 제출 준비 상태를 GO, CONDITIONAL, NO-GO 중 하나로 정하고 근거를 제시하라.
결과는 제출 파일 점검, 재현 명령과 실제 결과, 남은 문제, 제출 전 최종 체크 순으로 간결히 출력하라.
```

## 심화/반증 프롬프트
```text
$sk-deliver
[과제 루트]의 제출 직전 결과물을 반증 관점에서 점검하라.
남은 시간은 [남은 시간: 분]분, 공식 규칙은 [공식 제출 안내/요구사항], 요구사항은 [요구사항 ID와 수용 기준]이다.
후보 증거는 [최종 검증 명령과 결과], 후보 산출물은 [제출 예정 파일/산출물], 알려진 문제는 [알려진 문제·사용자 승인 범위]이다.

먼저 실제 과제 루트인지 확인하고, 공식 규칙이 없는 항목은 확인 질문으로 남겨라.
각 필수 산출물에서 누락·잘못된 이름/형식·생성 실패·재현 불가·요구사항과 다른 출력·민감정보 노출을 찾는 검사를 제안하거나 실행하라.
각 검사는 명령, 기대 결과, 실제 결과, 판정을 분리하고 추측한 통과를 금지하라.
변경된 파일 때문에 기존 증거가 무효가 될 가능성도 확인하라.
차단 조건은 즉시 NO-GO로, 증거 부족은 CONDITIONAL로 분류하고 해결에 필요한 최소 다음 행동 하나만 제안하라.
외부 제출·배포·push·업로드·삭제·reset은 절대 실행하지 마라.
```

## 완료 기준
- 실제 과제 루트와 적용 가능한 공식 규칙의 출처가 명확하다.
- 필수 제출 파일의 존재·이름·형식·저장 상태가 실제로 확인되었거나 미확인 사유가 기록되었다.
- 각 핵심 요구사항이 실제 실행 명령과 결과 또는 명시적 미검증 상태로 연결되었다.
- 민감정보와 차단 결함의 점검 범위·발견 여부·잔여 위험이 숨김없이 정리되었다.
- `GO`·`CONDITIONAL`·`NO-GO` 판정과 외부 행동 전 최종 체크가 근거와 함께 제시되었다.

## 다음 단계
`GO`여도 사용자에게 최종 체크 결과를 제시하고 외부 제출·배포·push·업로드는 별도의 구체적 승인을 받은 뒤에만 진행한다.
`CONDITIONAL`이면 누락된 공식 규칙이나 최소 검증 하나를 해결한 뒤 이 단계로 돌아온다.
`NO-GO`이면 차단 원인 해결을 구현·디버깅·검증 단계로 넘기고, 해결 전 제출을 권하지 않는다.

## 주의
공식 안내 메일의 내용, 마감, 모델, 채점 방식, 허용·금지 규정은 제공되지 않았으므로 만들어 내지 않는다.
제출 문서는 실제 증거로만 작성하며, 사용자가 요청하거나 과제가 요구한 정확한 경로 외에 임의 문서나 패키지를 만들지 않는다.
비밀값을 대화, 로그, 제출 문서에 복사하지 말고 노출 의심 시 값은 마스킹하지도 말고 출력 자체를 피한다.
