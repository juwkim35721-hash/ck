# 7.1 반증 중심 코드 리뷰

> 스킬: `$sk-review` · 단계: 리뷰·준수 감사 · 작업 노트: `sk/work/REVIEW.md`, `sk/work/EVIDENCE.md`, `sk/work/DECISIONS.md` · 사용 자료: `없음`

## 언제 쓰나

- 구현 슬라이스와 검증을 마친 뒤, 제출 전 변경이 실제로 요구사항을 깨지 않는지 독립적으로 볼 때 쓴다.
- 특히 P0 요구사항, 담당자 확정 정책 P#, 공개 API·CLI·데이터 출력, 오류 경로가 바뀌었을 때 쓴다.
- 이 프롬프트는 발견과 승인 요청을 만든다. 자동 수정 프롬프트가 아니다.
- 특정 실패 원인의 수정이 목적이면 먼저 `../6-debug/6.1-debug.md`의 `6.1 debug`($sk-debug)를 쓴다.

## 준비할 입력

- 현재 과제 루트와 검토할 구현 슬라이스 S# 또는 변경 목적.
- `sk/work/SPEC.md`의 R#/C#/P#/T#와 최신 `sk/work/EVIDENCE.md`의 E#.
- 담당자 답변이 반영된 경우 `sk/work/DM_LOG.md`의 관련 M#/P#.
- 가능하면 현재 `git diff --stat`, `git diff --name-only`, 최신 전체 테스트 결과.
- 검토 시간(예: 10분 또는 25분)과 사용자가 수정 승인할지 여부.

## 전략 — 왜 이렇게 하나

리뷰는 “코드가 그럴듯한가”가 아니라 “무슨 입력에서 약속이 깨지는가”를 찾는 일이다.
따라서 새 코드부터 읽고, 각 분기마다 빈 값·경계·중복·오류·호환성 반례를 만든다.
발견은 재현 가능한 F#로 남겨야 구현자·검증자·보고서 작성자가 같은 사실을 본다.
테스트 통과는 근거 중 하나일 뿐이며, P#·C#·스키마·민감정보는 별도로 대조한다.

## 기본 프롬프트

```text
$sk-review

현재 과제 루트에서 제출 전 반증 중심 코드 리뷰를 수행해 주세요.
과제 파일은 수정하지 말고, sk/는 도구이므로 리뷰 대상에서 제외하세요.
먼저 sk/work/SPEC.md의 Top 5 규칙, R/C/P, 데이터 계약, T와 추적표를 읽고,
sk/work/DM_LOG.md의 관련 P#, sk/work/EVIDENCE.md의 최신 E#, sk/work/DECISIONS.md의 관련 DD#를 확인하세요.
읽기 전용 git status --short, git diff --stat, git diff --check, git diff --name-only로 실제 변경 범위를 고정하세요.
변경 파일별로 정상 경로를 믿지 말고 빈 값, 누락, 잘못된 타입, 경계, 중복, 동점, 빈 결과, 오류 응답의 반례를 찾으세요.
P#의 조건→동작, C#의 인터페이스·금지 의존성·수정 금지 제약, 출력 스키마·오류 계약, 테스트 assert의 실효성, 하드코딩·민감정보·성능 위험을 대조하세요.
실제 실행은 안전한 최소 테스트만 하고, 실행한 사실과 결과만 E#로 기록하세요. 실행하지 못했으면 미검증으로 남기세요.
각 발견을 F# | 심각도 | 위치 | 근거·재현 입력 | 관련 R/P/C | 영향 | 제안 | 상태 형식으로 sk/work/REVIEW.md의 ## 리뷰 발견 F에 추가하세요.
차단·높음은 수정하지 말고 최소 수정안과 사용자 승인 필요 여부를 보고하세요.
마지막에 범위, 판정, F# 표, E# 근거, 미점검 범위, 다음 단계 7.2 compliance($sk-compliance)를 순서대로 보고하세요.
```

## 심화 프롬프트 — DM 정책·공개 인터페이스가 바뀐 상황

```text
$sk-review

<변경 목적 또는 S#>에 대해 25분 이내의 제출 전 리뷰를 해 주세요. 자동 수정은 금지합니다.
검토 전에 SPEC.md에서 <관련 R#/P#/C#>와 수용 기준 AC, T를 인용 가능한 수준으로 정리하고,
DM_LOG.md에서 각 P#의 원래 M# 답변을 다시 읽어 코드가 답변 범위를 넘겨 일반화하지 않았는지 확인하세요.
현재 변경 범위는 git diff 기준으로 고정하고 sk/ 하위 파일은 모두 제외하세요.
각 새 조건문·기본값·예외 처리에 대해 다음 반증을 우선 적용하세요:
1) 필수 필드 누락과 빈 값, 2) 문자열/숫자 타입 혼동, 3) 정확히 경계값인 경우,
4) 중복·재시도·동점, 5) 빈 결과, 6) 서버·CLI의 오류 응답, 7) 이전 호출자의 입력과 출력.
API 또는 파일 출력이 있다면 키 이름, 타입, null/빈 표현, 순서, 반올림, 상태 코드를 SPEC 10절과 비교하세요.
테스트는 새 분기·P#·실패 경로를 실제 assert하는지 보고, 구현을 복제한 기대값이면 독립 검산 부족으로 표시하세요.
민감정보는 값 자체를 출력하지 말고 노출 위치와 경로만 검사하세요. 성능은 실제 측정이 없으면 위험 가설로만 쓰세요.
발견마다 F#에 구체 입력 또는 정적 근거, 심각도(차단/높음/중간/낮음), 관련 ID, 최소 제안, 상태를 기록하세요.
실행한 명령은 E#에 종료 코드와 요약을 남기고, 코드 변경 뒤의 오래된 증거는 STALE로 구분하세요.
결론은 수정 필요/조건부 통과/발견 없음(검토 범위 내) 중 하나로 내리고, 차단·높음만 별도 승인 요청 목록으로 제시하세요.
수정이 승인되면 6.1 debug($sk-debug), 준수 행 단위 감사는 7.2 compliance($sk-compliance)로 넘기세요.
```

## 변형 — 남은 시간이 10분 이하인 상황

```text
$sk-review

제출까지 <남은 시간>분입니다. 과제 파일을 수정하지 말고 10분 최소 리뷰만 수행하세요.
현재 git diff에서 sk/를 제외한 변경 파일을 확인한 뒤, P0 R#, 모든 P#, 모든 C#, 필수 제출물 경로,
공개 인터페이스·출력 스키마, 민감정보 노출만 우선 점검하세요.
각 항목은 실제 코드 위치와 T#/E# 연결을 확인하고, 확인할 수 없으면 통과로 추정하지 말고 미검증으로 표시하세요.
반례는 빈 입력, 경계, 오류, 이전 호출자 호환성 중 변경과 가장 가까운 1개씩만 고르세요.
F# 표를 sk/work/REVIEW.md의 ## 리뷰 발견 F에 기록하고, 차단·높음부터 사용자 승인 요청으로 요약하세요.
점검하지 못한 성능·낮은 우선순위 엣지·대규모 리팩터링 범위는 명시적으로 미점검으로 보고하세요.
다음 행동은 승인된 차단 수정이면 6.1 debug($sk-debug), 아니면 7.2 compliance($sk-compliance)로 제안하세요.
```

## 변형 — Git diff가 없는 비Git 과제인 상황

```text
$sk-review

이 과제는 Git diff를 사용할 수 없습니다. 사용자가 제공한 <변경 파일 목록>과 sk/work/PLAN.md의 S# 상태,
그리고 EVIDENCE.md의 최신 E#에 적힌 변경 파일을 근거로 리뷰 범위를 먼저 선언하세요.
sk/는 리뷰 범위에서 제외하고 과제 파일은 수정하지 마세요.
SPEC의 R/C/P/T와 실제 파일·함수·라우트·출력 계약을 대조하며, 각 변경에 대해 깨뜨리는 입력을 한 개 이상 찾으세요.
파일 수정 시각이나 실행 로그만으로 통과를 추정하지 말고 실제 코드와 테스트 assert를 읽으세요.
발견은 F# 표로 REVIEW.md의 ## 리뷰 발견 F에 기록하고, 범위 근거가 약한 부분은 미점검으로 분리하세요.
필요한 최소 재현 실행만 실제 수행해 E#로 남기고, 차단·높음은 수정하지 않은 채 승인 요청으로 보고하세요.
완료 후 7.2 compliance($sk-compliance)에서 명세 행 단위 감사가 필요함을 제안하세요.
```

## 결과물 확인

- `sk/work/REVIEW.md`에 정확한 `## 리뷰 발견 F` 제목과 F# 표가 있으며 기존 행을 덮어쓰지 않았다.
- 모든 F#에 심각도, 위치, 반례 또는 정적 근거, 관련 R#/P#/C#, 상태가 있다.
- “통과” 주장은 실제 실행 E# 또는 코드 대조 근거를 갖고, 미검증은 별도 표기했다.
- 차단·높음 항목은 자동 수정하지 않고 승인 대기 상태다.
- AI 산출물 결함이라면 `sk/work/DECISIONS.md`의 `## AI 교정 기록`에 AI#을 사실만으로 남겼다.

## 주의

- 리뷰는 사용자 승인 없이 과제 코드, 테스트, 설정, 문서를 고치지 않는다.
- 담당자 답변을 새로 만들거나, 명세에 없는 정책으로 결함을 단정하지 않는다.
- 원본 데이터·기존 테스트를 삭제하거나 위험한 Git 복구 명령을 사용하지 않는다.
- 외부 제출, 업로드, push, 배포를 실행하지 않는다.
- 비밀값·토큰·개인정보·민감 원본값을 출력하거나 노트에 남기지 않는다.
