# 7.2 명세·DM 반영 준수 감사

> 스킬: `$sk-compliance` · 단계: 리뷰·준수 감사 · 작업 노트: `sk/work/REVIEW.md`, `sk/work/SPEC.md`, `sk/work/EVIDENCE.md` · 사용 자료: `없음`

## 언제 쓰나

- 코드 리뷰 뒤, 제출 문서 작성 전에 SPEC과 담당자 답변이 실제 코드·테스트·증거로 닫혔는지 감사할 때 쓴다.
- 요구사항은 구현됐다고 보이지만 T# 또는 E# 연결이 비어 있을 수 있을 때 유용하다.
- API·데이터·UI 어느 유형이든 R#/C#/P#/A#와 필수 제출물의 추적이 필요하면 쓴다.
- 코드 한 곳의 버그 원인을 고치는 일은 `../6-debug/6.1-debug.md`의 `6.1 debug`($sk-debug)가 먼저다.

## 준비할 입력

- `sk/work/SPEC.md` 전체, 특히 상태·필수 제출물·R/C/P/A·데이터 계약·T·추적표.
- `sk/work/DM_LOG.md`의 M# 원문과 `## 정책 목록 P`.
- `sk/work/EVIDENCE.md`의 최신 E#, `sk/work/REVIEW.md`의 열려 있는 F#.
- 현재 변경 파일 목록과 최신 전체 테스트 결과 또는 실행하지 못한 이유.
- 감사에 사용할 시간과 현재 제출 마감 기준.

## 전략 — 왜 이렇게 하나

구현 파일이 존재한다고 요구사항이 준수된 것은 아니다.
한 R#은 수용 기준, 테스트, 실행 증거까지 이어져야 하며, 담당자 답변 P#는 답변의 원래 조건 범위 안에서만 코드화돼야 한다.
제약 C#와 필수 제출물은 기능 테스트가 잡아내지 못하므로 별도 행으로 감사한다.
감사 표의 `미검증`은 실패가 아니라 정직한 작업 목록이며, 제출 직전의 위험을 작게 만든다.

## 기본 프롬프트

```text
$sk-compliance

현재 과제의 제출 전 명세·DM 반영 준수 감사를 수행해 주세요. 과제 파일은 수정하지 마세요.
먼저 sk/work/SPEC.md의 상태, 필수 제출물, 모든 R/C/P/A, 데이터 계약, T, 추적표를 읽고,
sk/work/DM_LOG.md의 M# 원문과 정책 목록 P, EVIDENCE.md의 최신 E#, REVIEW.md의 열려 있는 F#를 확인하세요.
읽기 전용 git status --short, git diff --stat, git diff --name-only로 sk/를 제외한 현재 변경 범위와 증거 신선도를 판단하세요.
R#, C#, P#, 구현에 영향을 주는 A#, 필수 제출물을 빠짐없이 행으로 만들고,
각 행에 출처, 구현 위치, 테스트 T#, 실행 증거 E#, 상태, 빈칸·다음 행동을 채우세요.
상태는 충족/부분/미충족/미검증/해당 없음만 사용하고, 구현·T·현재 코드 대응 E# 중 하나라도 없으면 충족으로 쓰지 마세요.
특히 M# 답변의 조건→동작이 코드 분기와 테스트에 실제 반영됐는지, 답변 범위를 넘겨 일반화하지 않았는지 점검하세요.
인터페이스 유지, 바인딩·포트, 금지 의존성, 수정 금지 파일, 제출물 경로·이름·형식도 C# 또는 제출물 행으로 독립 감사하세요.
결과를 sk/work/REVIEW.md의 ## 준수 감사에 표로 기록하고, 기존 ## 리뷰 발견 F는 덮어쓰지 마세요.
차단·높음 불일치는 수정하지 말고 영향도순 최소 다음 행동을 제시하세요.
마지막에 감사 기준선, 결론, 상태 집계, 차단·높음, 남길 한계, 다음 인계를 보고하세요.
```

## 심화 프롬프트 — 담당자 답변·가정이 많은 상황

```text
$sk-compliance

<과제 또는 S#>의 정책 반영을 중심으로 30분 이내 준수 감사를 해 주세요. 자동 수정은 금지합니다.
SPEC.md에서 모든 P#와 A#, 관련 R#/AC/T#, C#를 표로 먼저 수집하고, 각 P#는 DM_LOG.md의 원래 M# 답변과 나란히 읽으세요.
각 정책마다 다음 사슬을 역방향으로 검증하세요: M#의 조건과 선택 범위 → P#의 조건→동작 문장 → 구현 조건문/기본값/오류 처리 → T#의 구체 입력과 기대값 → E#의 실제 결과.
답변이 “이 경우만”인데 코드가 모든 경우에 적용하거나, 예시를 일반 규칙으로 확장한 경우는 부분으로 표시하고 G# 후보와 확인 질문 필요성을 적으세요.
A#는 근거, 위험, 되돌릴 지점, 확인 계획이 남아 있는지 보고 P0 동작을 좌우하면 우선순위를 높이세요.
R#은 구현 위치와 AC를 분리해 확인하고, C#는 인터페이스, 지정 설정, 금지 의존성, 수정 금지 파일, 성능·형식 제약을 독립 행으로 감사하세요.
현재 코드보다 오래된 E#는 STALE로 보고, 실제 재실행이 필요하면 5.1 verify($sk-verify)로 인계할 항목을 구체적으로 적으세요.
감사 표는 대상 | 요약 | 출처 | 구현 위치 | T | E | 상태 | 빈칸·다음 행동 열을 사용해 REVIEW.md의 ## 준수 감사에 남기세요.
코드 결함은 관련 F#와 연결하고, AI 산출물 결함이라면 DECISIONS.md의 ## AI 교정 기록에 AI#을 추가하세요.
결론은 준수 확인/조건부 준수/준수 보류 중 하나로 제한하고, 통과처럼 보이는 추정은 미검증으로 남기세요.
완료 후 수정은 6.1 debug($sk-debug), 증거 보강은 5.1 verify($sk-verify), 질문은 1.3 dm-questions($sk-dm-questions), 문서화는 8.1 report($sk-report)로 분기하세요.
```

## 변형 — 최신 증거가 코드 변경보다 오래된 상황

```text
$sk-compliance

현재 코드가 최신 E# 이후에 바뀌었습니다. 준수 감사를 하되 과거 PASS를 현재 통과로 재사용하지 마세요.
먼저 git status --short와 git diff --name-only로 변경 파일을 확인하고, 각 E#의 코드 상태·대상 R/T·명령·실제 결과를 비교해 STALE 여부를 표시하세요.
SPEC의 R/C/P/A와 필수 제출물 표는 모두 만들되, 현재 코드로 다시 확인되지 않은 행은 미검증 또는 부분으로 기록하세요.
가장 작은 재실행 목록을 P0 R, P#, C#, 공개 인터페이스, 필수 제출물 순으로 우선순위화해 5.1 verify($sk-verify)에 넘기세요.
실제로 실행한 경우에만 새 E#를 기록하고, 실행하지 않은 항목을 충족으로 승격하지 마세요.
REVIEW.md의 ## 준수 감사에는 STALE 근거와 필요한 재검증 명령 또는 T#를 포함하세요.
수정은 수행하지 말고, 결론과 제출 전 반드시 닫아야 할 차단 항목을 보고하세요.
```

## 변형 — 남은 시간이 10분 이하인 상황

```text
$sk-compliance

제출까지 <남은 시간>분입니다. 과제 파일을 수정하지 말고 최소 준수 감사만 해 주세요.
SPEC에서 P0 R#, 모든 C#, 모든 P#, 필수 제출물만 먼저 행으로 만들고, 코드 위치·T#·최신 E#를 대조하세요.
특히 담당자 답변의 핵심 조건, 기존 인터페이스, 금지 의존성, 제출 파일명·경로·형식, 민감정보 노출 가능성을 확인하세요.
확인하지 못한 P1/P2와 성능 세부 항목은 생략하지 말고 미검증으로 남기세요.
차단·높음만 대상 ID | 근거 | 최소 다음 행동 | 관련 F#/G# 형식으로 먼저 보고하고, 수정 승인 없이 코드를 고치지 마세요.
시간이 남으면 5.1 verify($sk-verify)로 가장 위험한 미검증 1개를 재실행하도록 제안하고,
그렇지 않으면 정직한 조건부 준수 또는 준수 보류 결론을 내리세요.
```

## 결과물 확인

- `sk/work/REVIEW.md`의 정확한 `## 준수 감사` 아래에 감사 기준선과 표가 있다.
- 표에는 모든 R#/C#/P#/영향 A#/필수 제출물 행이 있고, 대상 ID가 재사용되지 않았다.
- 각 행은 출처, 구현 위치, T#, E#, 보수적인 상태, 다음 행동 또는 공백 사유를 가진다.
- 현재 코드와 E#의 코드 상태를 비교해 STALE 증거를 구분했다.
- M# 원문에서 P#까지의 범위를 확인했고, 자동 수정 없이 차단·높음 목록을 만들었다.

## 주의

- 공식 문서와 담당자 답변이 충돌하면 임의로 하나를 고르지 말고 G#와 확인 질문으로 남긴다.
- 테스트 통과 하나나 구현 파일 하나만으로 R#/C#/P#를 충족으로 선언하지 않는다.
- 실행하지 않은 검증과 보지 않은 제출물은 반드시 미검증이다.
- 사용자 승인 없이 코드·테스트·설정·보고서·제출물을 수정하지 않는다.
- 외부 제출, 업로드, push, 배포, 자격증명 전송을 실행하지 않는다.
- 비밀값·토큰·개인정보·민감 원본값을 감사 표나 채팅에 기록하지 않는다.
