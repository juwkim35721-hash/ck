# 5.4 API 계약 검증 (smoke_test.py 사용)

> 스킬: `$sk-api-contract` · 단계: 검증·증거 · 작업 노트: `sk/work/EVIDENCE.md#실행 기록`, `sk/work/SPEC.md#12. 추적표` · 사용 자료: `sk/snippets/smoke_test.py`

## 언제 쓰나

HTTP API, 백엔드 서비스, 웹 서버의 엔드포인트가 요구사항에 있을 때 쓴다.
구현 뒤 메서드·경로·상태 코드·응답 스키마·오류 형식이 SPEC 10절 계약과 맞는지 실제 호출로 확인할 때 쓴다.
서버 도달성만 확인하거나 서버를 새로 구성하는 프롬프트가 아니라 계약을 대조하고 증거를 남기는 프롬프트다.
화면의 사용자 흐름은 [5.5 ui-smoke](../5-verify/5.5-ui-smoke.md)를 쓴다.

## 준비할 입력

- `sk/work/SPEC.md`의 5절 P, 10절 API 계약, 11절 T, 12절 추적표.
- `sk/work/BRIEF.md`의 공식 서버 시작 명령, 호스트·포트, 종료 방법.
- P0 엔드포인트별 메서드·경로·안전한 요청 본문·기대 상태·필수 필드.
- 기존 인터페이스를 확인할 수 있는 테스트·문서·코드 지도.
- 인증·외부 네트워크·민감 데이터 관련 대회 규칙과 사용자 허가 여부.

## 전략 — 왜 이렇게 하나

`smoke_test.py`는 URL에 GET 한 번을 보내 2xx인지 보는 빠른 도달성 체크일 뿐 API 계약 전체를 검증하지 않는다.
따라서 스모크 뒤에 정상·오류 경로를 메서드와 요청 본문까지 명시해 호출하고, 상태뿐 아니라 필수 필드·타입·빈 결과·오류 스키마를 비교한다.
기존 인터페이스를 한 번 더 확인하면 새 기능이 이전 호출자를 깨뜨린 사실을 빨리 찾을 수 있다.
서버를 실행한 주체와 종료 책임을 기록하면 다른 팀 프로세스를 실수로 종료하는 일을 막는다.

## 기본 프롬프트

```text
$sk-api-contract
현재 API를 SPEC 10절 계약과 실제 HTTP 호출로 검증해줘.
먼저 sk/work/SPEC.md의 P#, API 계약, T#, 추적표와 sk/work/BRIEF.md의 공식 서버 시작·종료 조건을 읽어줘.
P0 엔드포인트마다 T# | 메서드 | 경로 | 요청 조건 | 기대 상태 | 필수 응답 필드·타입 | 오류 규칙 표를 만들어줘.
과제 안내에 있는 명령으로만 서버를 시작하거나 이미 실행된 서버를 확인해줘. 포트·호스트는 임의로 바꾸지 마.
먼저 아래 명령으로 도달성을 한 번 확인해줘.
python3 sk/snippets/smoke_test.py http://127.0.0.1:<포트>/<경로>
이 스니펫은 GET 1건, 2xx 성공, 5초 제한, 본문 120자 출력, 실패 시 종료 코드 1이라는 한계를 결과에 밝혀줘.
그 뒤 과제 테스트 클라이언트 또는 curl로 각 P0의 정상 요청과 T#의 오류 요청을 실제로 호출해줘.
메서드·경로·상태 코드·필수 필드·타입·빈 결과·오류 응답을 SPEC과 대조하고 기존 인터페이스도 최소 한 건 확인해줘.
각 실제 실행을 E#로 기록하고 추적표에는 실제 E#만 연결해줘.
코드·라우팅·포트·CORS·테스트는 수정하지 말고, 불일치는 6.1 debug으로 넘겨줘.
끝에 도달성, 계약 대조 표, 호환성, E#, 서버 종료 책임, 다음 행동을 보고해줘.
```

## 심화 프롬프트 — 여러 엔드포인트와 오류 계약을 검증하는 상황

```text
$sk-api-contract
제출 전 API 계약 전체를 최신 코드 상태에서 엄격히 검증해줘.
SPEC.md의 R, P, 10절 메서드·경로·상태·본문 계약, 11절 T와 BRIEF.md의 실행 조건을 먼저 읽어줘.
P0 엔드포인트 전부와 P1 중 기존 호출자가 사용하는 엔드포인트를 대상으로 계약 체크 표를 만들어줘.
서버가 이미 실행 중인지 확인해 중복 시작하지 말고, 이 세션에서 시작한 경우만 종료 책임을 명확히 해줘.
공식 시작 명령과 요구된 호스트·포트만 사용한 뒤 health 또는 공식 GET 경로에 smoke_test.py를 실행해 도달성을 확인해줘.
POST·PUT·PATCH·DELETE 전용 엔드포인트는 GET 성공 여부로 판정하지 말고, 공식 GET 경로를 스모크 대상으로 정한 이유를 적어줘.
정상 요청은 안전한 본문으로 호출하여 상태·필수 필드·타입·정렬·null/빈 결과·값 범위를 계약과 대조해줘.
T#에 정의된 누락 필드, 잘못된 타입, 존재하지 않는 리소스만 사용해 오류 요청을 만들고, 4xx/오류 본문 키를 확인해줘.
500이 돌아오면 정상 오류로 합리화하지 말고 FAIL로 기록해줘.
기존 테스트·문서에 나온 인터페이스를 최소 한 건 실제 호출해 메서드·경로·필수 필드가 유지되는지 확인해줘.
인증 값·토큰·개인정보·전체 응답 본문은 노트에 남기지 말고 상태와 안전한 필드 요약만 E#에 적어줘.
EVIDENCE와 SPEC 12절에는 실제 결과만 갱신하고, 코드·설정·서버 바인딩은 수정하지 마.
FAIL은 요청 유형·실제 상태·E#를 묶어 6.1 debug으로, 계약 빈칸은 2.2 io-contract 또는 1.3 dm-questions로 인계해줘.
끝에 P0 API별 PASS/FAIL/미검증, 스모크의 한계, 호환성, 종료 책임, 제출 차단 항목을 보고해줘.
```

## 변형 — 서버가 시작되지 않는 상황

```text
$sk-api-contract
공식 명령으로 서버를 시작했지만 도달성 확인이 실패했어. 추측 수정 없이 검증·증거를 남겨줘.
BRIEF.md의 공식 명령, 지정 포트·호스트, 서버 로그의 실제 오류를 확인하고 서버 소유·중복 실행 여부를 분리해줘.
smoke_test.py를 한 번 실행해 연결 실패인지 HTTP 응답 불일치인지 종료 코드와 출력으로 기록해줘.
포트 변경, 방화벽 변경, 환경변수 추가, 라우팅 수정, 강제 종료는 하지 마.
실패 명령·작업 디렉터리·E#·코드 상태를 EVIDENCE에 기록하고 P0 API는 미검증 또는 FAIL로 정직하게 판정해줘.
최소 재현 정보와 함께 6.1 debug으로 넘기고, 서버가 다른 사람이 시작한 경우 종료하지 말아줘.
```

## 변형 — 인증 또는 외부 서비스가 필요한 상황

```text
$sk-api-contract
API 계약에 인증 또는 외부 서비스가 필요해. 규칙을 지키면서 검증 범위를 결정해줘.
먼저 공식 과제 규칙과 사용자 허가가 있는지 확인하고, 실제 토큰·개인정보·외부 고객 데이터를 채팅이나 노트에 출력하지 마.
공식 테스트 자격 또는 로컬 모의 경로가 있으면 그것만 사용해 메서드·상태·오류 형식을 대조해줘.
허가된 안전한 방법이 없으면 도달 가능한 공개 경로만 확인하고 인증 필요 경로는 미검증과 차단 사유로 남겨줘.
실제 실행한 명령·상태·E#만 기록하고, PASS를 인증 계약 전체로 확대하지 마.
정책이 비어 있으면 1.3 dm-questions으로 질문 초안을 만들고 코드·서버 설정은 변경하지 마.
```

## 결과물 확인

- 스모크 URL의 실제 종료 코드·HTTP 상태와 GET/2xx/5초/120자 한계가 기록되어 있다.
- P0 엔드포인트마다 정상 요청, 적용되는 오류 요청, 메서드·경로·상태·필수 필드·타입 대조가 있다.
- 기존 API가 있으면 최소 한 경로의 호환성 확인 또는 미검증 사유가 있다.
- 서버를 시작한 주체와 정상 종료 책임이 분명하다.
- E#에는 민감 값 없이 실제 호출·결과·코드 상태가 있다.

## 다음 단계

응답 차이·서버 실패의 최소 재현이 있으면 [6.1 debug](../6-debug/6.1-debug.md)의 `$sk-debug`으로 넘긴다.
API 계약 자체가 비어 있거나 충돌하면 [2.2 io-contract](../2-spec/2.2-io-contract.md)의 `$sk-data-contract`을 쓴다.
담당자만 정할 오류 규칙·호환성 정책은 [1.3 dm-questions](../1-discover/1.3-dm-questions.md)의 `$sk-dm-questions`로 질문한다.
검증 E#를 R별 판정에 연결하려면 [5.1 verify](../5-verify/5.1-verify.md)의 `$sk-verify`를 쓴다.

## 주의

GET 2xx 한 번을 POST·오류·스키마·호환성까지 통과했다고 주장하지 않는다.
과제 요구 없이 포트, CORS, 환경변수, 네트워크 설정을 바꾸지 않는다. 바인딩은 하네스 규칙(웹 과제는 지정 포트로 `0.0.0.0`, 과제 문서 우선)을 따르고 요청은 `127.0.0.1`로 보낸다.
토큰·인증 헤더·개인정보·전체 민감 응답을 출력하거나 EVIDENCE에 기록하지 않는다.
다른 세션이 시작한 서버를 종료하지 않고, 실패를 숨기려고 요청·테스트를 약화하지 않는다.
