# 5.2 실행 증거 기록

> 스킬: `$sk-evidence` · 단계: 검증·증거 · 작업 노트: `sk/work/EVIDENCE.md#실행 기록`, `sk/work/SPEC.md#12. 추적표` · 사용 자료: 없음

## 언제 쓰나

테스트, 빌드, API 호출, 데이터 검산, UI 흐름처럼 의미 있는 실행을 끝낸 직후 쓴다.
보고서에 쓸 근거가 흩어져 있거나, 코드 변경 뒤 어떤 통과 기록이 오래됐는지 정리할 때 쓴다.
실행 자체를 대신 수행하거나 실패 원인을 수정하는 프롬프트가 아니라 실제 실행 사실을 정확히 기록하는 프롬프트다.

## 준비할 입력

- 방금 실행한 정확한 명령, 작업 디렉터리, 종료 코드와 핵심 출력.
- 검증한 R#, P#, T#, S# 및 실행 전 기대값의 출처.
- 현재 코드 상태를 확인할 수 있는 Git 정보 또는 변경 파일 목록.
- `sk/work/EVIDENCE.md`의 마지막 E#와 `sk/work/SPEC.md`의 추적표.
- 민감 값이 포함될 수 있는 출력의 마스킹 기준.

## 전략 — 왜 이렇게 하나

나중에 “테스트했다”는 말만으로는 재현·보고·설명이 불가능하다.
E# 한 행은 무엇을 어떤 명령으로 기대했고 실제로 무엇이 나왔는지, 당시 코드가 무엇이었는지 남기는 최소 증거다.
기대와 실제를 분리하면 종료 코드 0인데 값이 틀린 실패도 잡을 수 있다.
코드가 바뀌면 과거 증거는 삭제하지 않고 STALE 처리해 이력과 최신성을 함께 보존한다.

## 기본 프롬프트

```text
$sk-evidence
방금 실행한 검증 결과를 재현 가능한 E# 증거로 기록해줘.
먼저 sk/work/EVIDENCE.md의 ## 실행 기록에서 마지막 E#를 확인하고 다음 번호만 사용해줘.
실행한 명령과 실제 작업 디렉터리, 대상 R#/T#/P#, 실행 전 기대값 근거를 확인해줘.
git rev-parse --short HEAD와 git status --short를 읽기 전용으로 확인하거나 비Git이면 변경 파일 목록을 써줘.
종료 코드, 통과·실패·건너뜀 수 또는 API·데이터의 핵심 수치를 실제 결과와 분리해 적어줘.
sk/work/EVIDENCE.md에 E# | 시각 | 명령·작업 디렉터리 | 대상 R/T | 기대 | 실제 결과 요약 | 판정 | 코드 상태 열로 행을 추가해줘.
기대와 일치하면 PASS, 다르면 FAIL, 실행 또는 판정 근거가 없으면 미검증으로만 판정해줘.
관련 파일이 바뀐 이전 E#가 있으면 삭제하지 말고 STALE로 표시해줘.
확인된 T#만 sk/work/SPEC.md의 ## 12. 추적표에 실제 E#로 연결해줘.
비밀값·개인정보·전체 로그는 기록하지 말고, 끝에 E#, 판정, STALE 여부, 다음 행동을 보고해줘.
```

## 심화 프롬프트 — 제출 근거를 정리하는 상황

```text
$sk-evidence
제출 문서의 근거가 되도록 현재 작업 노트의 실행 증거를 감사하고 보완해줘.
먼저 sk/work/EVIDENCE.md의 ## 실행 기록 전체와 sk/work/SPEC.md의 11절 T, 12절 추적표를 읽어줘.
각 T#에 연결된 E#가 실제 명령·작업 디렉터리·기대·실제·판정·코드 상태를 모두 갖추는지 표로 점검해줘.
E# 이후 관련 코드·테스트·설정이 바뀌었는지 현재 git 짧은 해시와 git status --short로 읽기 전용 비교해줘.
영향 가능성이 있는 이전 PASS는 STALE — PASS로 표시하고, 필요한 명령은 실제로 재실행해 새 E#를 추가해줘.
실행하지 못한 검증은 임의 E#를 만들지 말고 추적표에서 미검증으로 표시해줘.
테스트는 종료 코드와 통과·실패 수, API는 상태·필수 필드, 데이터는 행 수·합계, UI는 관찰 흐름을 최소 사실로 기록해줘.
토큰·인증 헤더·개인정보·원본 데이터 값·장황한 콘솔 로그는 [REDACTED] 또는 요약으로 바꿔줘.
실제 실행 결과가 있는 T#만 SPEC 추적표의 증거 E 열에 연결해줘.
코드나 테스트를 수정하지 말고, FAIL은 6.1 debug, 빠진 T는 2.3 acceptance로 다음 행동을 분리해줘.
끝에 최신 PASS 수, FAIL 수, 미검증 수, STALE 수와 제출 전 재실행 목록을 보고해줘.
```

## 변형 — Git 저장소가 아닌 상황

```text
$sk-evidence
이 과제는 Git 해시를 신뢰할 수 없거나 Git 저장소가 아니야. 실행 증거를 정확히 기록해줘.
방금 실제로 실행한 명령, 작업 디렉터리, R#/T#, 기대와 실제 결과를 먼저 확인해줘.
코드 상태 열에는 해시를 만들지 말고 이번 작업에서 변경된 파일 목록과 확인 시각을 기록해줘.
결과에 영향을 줄 수 있는 파일이 나중에 바뀌면 기존 E#의 판정 앞에 STALE을 붙이고 새 E#로 재실행하도록 표시해줘.
EVIDENCE 표의 열 순서는 유지하고, 실행하지 못한 일은 E# 대신 채팅에서 미검증 사유로 알려줘.
과제 파일을 수정하거나 전체 로그·민감 값을 복사하지 말고, 추적표에는 실제 E#만 연결해줘.
```

## 변형 — 실패 출력이 긴 상황

```text
$sk-evidence
실패 출력이 길고 민감 값이 섞일 수 있어. 증거를 짧고 안전하게 기록해줘.
실제 명령·작업 디렉터리·종료 코드·대상 T#는 그대로 적되, 전체 로그는 복사하지 마.
오류 유형, 첫 실패 위치, 통과·실패 수, 재현에 필요한 안전한 입력 유형만 1~3줄로 요약해줘.
토큰·URL 쿼리·개인정보·원본 행은 [REDACTED]로 바꾸고 E#에 원값을 남기지 마.
기대와 실제가 다른 이유를 추측하지 말고 FAIL로 판정한 관찰 사실만 적어줘.
재현 명령과 새 E#를 6.1 debug로 넘길 수 있게 보고해줘.
```

## 결과물 확인

- E# 번호가 기존 번호와 중복되지 않고 실제 실행 순서를 보존한다.
- 표에 `E# | 시각 | 명령·작업 디렉터리 | 대상 R/T | 기대 | 실제 결과 요약 | 판정 | 코드 상태` 열이 있다.
- 기대값과 실제 관찰이 분리되고, 판정은 PASS·FAIL·미검증 중 하나다.
- 코드 변경의 영향을 받는 과거 증거는 STALE 처리되어 있다.
- `SPEC.md` 추적표에는 실제 E#만 연결되어 있다.

## 다음 단계

증거가 연결됐지만 R별 누락을 찾으려면 [5.1 verify](../5-verify/5.1-verify.md)의 `$sk-verify`를 쓴다.
실패의 최소 재현이 있으면 [6.1 debug](../6-debug/6.1-debug.md)의 `$sk-debug`으로 넘긴다.
데이터 수치의 독립 대사는 [5.3 data-validation](../5-verify/5.3-data-validation.md)의 `$sk-data-validation`으로 수행한다.
제출 보고서는 최신 E#를 근거로 [8.1 report](../8-submit/8.1-report.md)의 `$sk-report`에서 작성한다.

## 주의

실행하지 않은 결과, 담당자 답변, 코드 읽기만 한 일을 E#로 적지 않는다.
과거 FAIL 행을 삭제하거나 E# 번호를 재사용하지 않는다.
성공 종료 코드만으로 PASS를 단정하지 않고 실제 값·스키마·상태를 대조한다.
코드·테스트·설정·원본 데이터는 이 프롬프트로 수정하지 않는다.
`git reset --hard`, `git clean`, `git stash`, 강제 체크아웃으로 상태를 정리하지 않는다.
