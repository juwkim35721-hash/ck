# 5.1 요구사항 추적 검증

> 스킬: `$sk-verify` · 단계: 검증·증거 · 작업 노트: `sk/work/SPEC.md#12. 추적표`, `sk/work/EVIDENCE.md#실행 기록` · 사용 자료: 없음

## 언제 쓰나

P0 구현 슬라이스가 끝났고, 요구사항별로 무엇을 실제 실행해 증명했는지 확인할 때 쓴다.
제출 전 전체 테스트를 다시 실행하고, 오래된 통과 기록과 빠진 수용 테스트를 찾아야 할 때 쓴다.
코드를 수정하는 단계가 아니라 판정·근거·다음 행동을 정하는 단계다.
실패 원인을 고치려면 이 프롬프트 대신 [6.1 debug](../6-debug/6.1-debug.md)를 쓴다.

## 준비할 입력

- `sk/work/SPEC.md`의 R#, P#, AC-R#-n, T#, `## 12. 추적표`.
- `sk/work/BRIEF.md`의 `## 환경`과 실제 테스트·빌드 명령.
- `sk/work/PLAN.md`의 현재 S# 및 축소 결정.
- `sk/work/EVIDENCE.md`의 최신 E#와 코드 변경 뒤 STALE 여부.
- 현재 과제 루트에서 실행할 수 있는 안전한 테스트 환경.

## 전략 — 왜 이렇게 하나

테스트 통과 수만으로는 요구사항 충족을 증명하지 못한다.
R → AC → T → 명령 → 실제 결과 E#의 고리를 행 단위로 연결해야 제출 문서와 후속 설명도 흔들리지 않는다.
기대값은 구현 결과를 다시 호출해 만들지 않고 SPEC, P#, 샘플 또는 별도 계산으로 독립성을 확인한다.
코드가 바뀐 뒤 과거 E#를 PASS로 재사용하지 않고 STALE로 표시해 최신 코드 기준으로 판정한다.

## 기본 프롬프트

```text
$sk-verify
현재 P0 구현을 요구사항 추적으로 검증해줘.
먼저 sk/work/SPEC.md의 R, P, AC, T와 12절 추적표를 읽고,
sk/work/BRIEF.md의 환경에서 실제 테스트·빌드 명령을 확인해줘.
현재 슬라이스 S#의 P0 R부터 R → AC → T → 실행 명령 → E# 연결 표를 만들어 빈칸을 찾아줘.
정상 경로와 T 표에 정의된 경계·실패 경로를 실제로 실행하고, 전체 테스트 스위트도 한 번 실행해줘.
기대값이 구현에 의존하지 않는지 P#, 샘플, 손계산 또는 별도 계산 근거로 확인해줘.
읽기 전용으로 git status --short와 git diff --stat를 확인하되 파일을 정리·수정하지 마.
관련 코드가 바뀐 E#는 STALE로 표시하고 필요한 명령을 재실행해줘.
sk/work/SPEC.md의 ## 12. 추적표와 sk/work/EVIDENCE.md의 ## 실행 기록을 실제 결과만으로 갱신해줘.
각 R은 PASS, FAIL, 미검증 중 하나로만 판정하고 실패를 통과로 바꾸지 마.
끝에 R별 결과, 실행 E#, 빈칸·STALE, 변경 범위, 다음 행동 1개를 보고해줘.
```

## 심화 프롬프트 — 제출 직전 전체 근거 재검증

```text
$sk-verify
제출 직전이므로 최신 코드 기준의 전체 요구사항 추적 검증을 수행해줘.
시작 전에 sk/work/SPEC.md의 0절 상태, 2절 필수 제출물, 3절 R, 4절 C, 5절 P,
10절 계약, 11절 T, 12절 추적표와 sk/work/EVIDENCE.md 전체를 읽어줘.
R별로 R# | AC-R#-n | T# | 테스트/명령 | 독립 기대값 근거 | 최신 E# | 판정을 임시 표로 만들어줘.
P0은 전수, P1/P2는 현재 PLAN의 시간 예산과 축소 결정을 근거로 범위를 명시해줘.
각 P#에 최소 한 T#가 있는지, C#의 인터페이스·포트·수정 금지 제약이 확인됐는지도 점검해줘.
가장 작은 P0 테스트부터 실행한 뒤 정상·경계·실패 입력을 T# 그대로 실행해줘.
BRIEF에 기록된 전체 테스트·빌드·검사 명령도 실제로 실행하고 종료 코드와 통과·실패·건너뜀 수를 기록해줘.
기준선 실패와 현재 실패는 기존 E# 근거가 있을 때만 구분하고, 근거가 없으면 새 실패로 다뤄줘.
실행 전후의 git status --short, git diff --stat는 읽기 전용으로만 확인해 의도 밖 변경·미추적 파일을 알려줘.
관련 파일이 바뀐 과거 증거에는 STALE을 붙이고 재실행한 새 E#만 추적표 PASS 근거로 연결해줘.
sk/work/SPEC.md의 ## 12. 추적표와 sk/work/EVIDENCE.md의 ## 실행 기록을 덮어쓰지 말고 자기 행만 갱신해줘.
코드·테스트·설정·원본 데이터는 수정하지 말고, FAIL은 재현 정보와 함께 6.1 debug로 인계해줘.
끝에는 PASS/FAIL/미검증 수, R별 표, 제출 차단 항목, 다음 행동 딱 1개를 보고해줘.
```

## 변형 — 기준선 실패가 이미 있는 상황

```text
$sk-verify
기존 테스트에 실패가 있을 수 있으니 현재 구현을 함부로 원인으로 단정하지 말고 검증해줘.
sk/work/BRIEF.md의 기준선과 sk/work/EVIDENCE.md의 이전 E#를 먼저 읽어 기존 실패의 명령·오류·코드 상태를 확인해줘.
현재 코드에서 같은 전체 테스트를 한 번 실행하고, 실패마다 기존 E#와 오류 위치·메시지·관련 R/T가 같은지 비교해줘.
기준선 근거가 있는 실패만 기존 실패로 표시하고, 나머지는 현재 FAIL 또는 원인 미분류로 기록해줘.
P0 정상·경계·실패 T#는 기준선과 무관하게 별도로 실행하고 R → AC → T → E# 추적표를 채워줘.
모든 실제 실행은 E#로 남기고 관련 코드가 바뀐 오래된 E#는 STALE 처리해줘.
코드 수정·테스트 삭제·작업 트리 정리는 하지 말고, 실패별로 6.1 debug 또는 2.3 acceptance 중 다음 행동을 제안해줘.
```

## 변형 — 시간이 15분 이하인 상황

```text
$sk-verify
남은 시간이 15분 이하야. 최소 제출 검증 경로만 빠르게 수행해줘.
SPEC의 P0 R만 골라 각 R에 AC, T, 최신 E#가 있는지 먼저 표로 확인해줘.
P0 전체 테스트 스위트를 실제로 한 번 실행하고, 각 P0의 대표 정상 경로와 가장 위험한 경계 또는 실패 경로를 하나씩만 실행해줘.
실행하지 못한 P1/P2와 추가 엣지 케이스는 미검증으로 명시하고 PASS로 확대하지 마.
git status --short와 git diff --stat는 읽기 전용으로 확인해 의도 밖 변경만 알려줘.
EVIDENCE와 추적표에 실제 결과·종료 코드·코드 상태를 남기고, FAIL이면 6.1 debug에 줄 재현 정보를 정리해줘.
코드·테스트·설정·원본 데이터는 수정하지 마.
```

## 결과물 확인

- `sk/work/SPEC.md`의 `## 12. 추적표`에 `R | AC | T | 구현 위치 | 증거 E | 상태` 연결이 있다.
- P0의 PASS는 실제 최신 E#를 가리키고, 빈 AC/T/E는 미검증으로 남아 있다.
- `sk/work/EVIDENCE.md`의 실행 기록에는 명령·작업 디렉터리·종료 코드·실제 결과·코드 상태가 있다.
- 정상·경계·실패 경로 중 적용되는 항목을 실제 실행했다.
- STALE 증거, 기준선 실패, 의도 밖 변경이 구분되어 있다.

## 다음 단계

FAIL의 최소 재현과 E#가 있으면 [6.1 debug](../6-debug/6.1-debug.md)의 `$sk-debug`으로 넘긴다.
데이터 처리 결과의 행 수·합계 대사가 필요하면 [5.3 data-validation](../5-verify/5.3-data-validation.md)의 `$sk-data-validation`을 쓴다.
API 계약은 [5.4 api-contract](../5-verify/5.4-api-contract.md)의 `$sk-api-contract`, UI 흐름은 [5.5 ui-smoke](../5-verify/5.5-ui-smoke.md)의 `$sk-ui-smoke`로 검증한다.
모든 P0가 최신 E#로 PASS이거나 한계가 투명하면 [7.1 review](../7-review/7.1-review.md)의 `$sk-review`로 넘어간다.

## 주의

실행하지 않은 결과를 통과로 적지 않는다.
테스트를 삭제·약화하거나 실패를 숨기지 않는다.
`sk/`는 도구 폴더이므로 테스트·분석·린트 대상에 넣지 않는다.
과제 코드 수정, 새 패키지 설치, 포트 변경, 외부 네트워크 호출은 이 검증 단계의 일이 아니다.
비밀값·개인정보·민감한 원본 값을 채팅과 작업 노트에 기록하지 않는다.
