# 5.5 UI 핵심 흐름 확인 (smoke_test.py 사용)

> 스킬: `$sk-ui-smoke` · 단계: 검증·증거 · 작업 노트: `sk/work/EVIDENCE.md#실행 기록`, `sk/work/SPEC.md#12. 추적표` · 사용 자료: `sk/snippets/smoke_test.py`

## 언제 쓰나

웹·풀스택·화면 기반 과제에서 사용자가 실제로 밟는 P0 흐름이 동작하는지 짧게 확인할 때 쓴다.
정상 입력, 빈값·잘못된 입력, 오류·빈 상태를 최대 세 흐름으로 제한해 제출 전 실사용 관점의 근거를 만들 때 쓴다.
브라우저 도구가 없더라도 HTTP 확인과 사용자가 할 수동 체크리스트를 구분해 만들 수 있다.
코드를 수정하거나 화면 디자인을 전면 변경하는 프롬프트가 아니다.

## 준비할 입력

- `sk/work/SPEC.md`의 R#, P#, UI·API 계약, T#, 추적표.
- `sk/work/BRIEF.md`의 공식 UI 시작 명령, URL, 포트·호스트, 종료 방법.
- 현재 S#의 P0 사용자 흐름과 안전한 테스트 입력.
- 브라우저 도구의 사용 가능 여부와 실제 계정·민감 데이터 사용 제한.
- `sk/work/EVIDENCE.md`의 최신 E# 및 현재 코드 상태.

## 전략 — 왜 이렇게 하나

페이지가 2xx를 반환해도 입력, 결과 표시, 오류 메시지, 빈 상태가 사용자에게 제대로 보인다는 뜻은 아니다.
그래서 먼저 `smoke_test.py`로 도달성을 빠르게 확인한 뒤, 가장 위험한 세 사용자 흐름만 직접 확인한다.
브라우저가 없을 때 화면을 본 것처럼 주장하지 않고 HTTP 결과와 수동 확인 항목을 분리한다.
콘솔 오류·실패 요청은 현재 흐름에서 새로 생긴 것인지 기준선과 비교해 기록해야 불필요한 수정도 막을 수 있다.

## 기본 프롬프트

```text
$sk-ui-smoke
현재 UI의 P0 핵심 흐름을 사용자 관점에서 짧게 검증해줘.
먼저 sk/work/SPEC.md의 R#, P#, UI·API 계약, T#, 추적표와 sk/work/BRIEF.md의 공식 시작·종료 조건을 읽어줘.
정상 입력→기대 결과, 빈값 또는 잘못된 입력→검증 메시지, 오류 또는 빈 결과→안내·복구 중 최대 세 흐름만 T# 기반으로 골라줘.
공식 명령으로 앱을 시작하거나 이미 실행된 URL을 확인하고, 포트는 바꾸지 마. 웹 UI가 지정 포트로 `0.0.0.0`에 바인딩돼 내장 Browser에서 보이는지도 확인해줘(과제 문서가 다르면 과제 문서 우선).
먼저 아래 명령으로 페이지 또는 공식 건강 경로의 도달성을 실제 확인해줘.
python3 sk/snippets/smoke_test.py http://127.0.0.1:<포트>/<페이지_또는_건강경로>
이 스니펫은 GET 1건·2xx·5초 제한·본문 120자·실패 시 종료 코드 1인 1차 확인임을 밝혀줘.
브라우저 도구가 있으면 선택한 흐름을 직접 수행해 입력·결과·검증 메시지·로딩·빈 상태·오류 표시를 T#와 대조해줘.
브라우저가 없으면 HTTP 수준 결과와 사용자가 직접 할 수동 체크리스트를 분리하고 UI PASS로 쓰지 마.
가능한 경우 현재 흐름의 콘솔 오류와 실패 요청을 확인해 새 오류와 기존 경고를 분리해줘.
각 실제 실행을 E#로 기록하고, SPEC 12절에는 실제 E#만 연결해줘.
화면 문구·스타일·코드·테스트는 수정하지 말고 실패는 6.1 debug, API 차이는 5.4 api-contract로 넘겨줘.
끝에 흐름별 기대/실제/판정, 미검증 사유, E#, 프로세스 종료 책임, 다음 행동을 보고해줘.
```

## 심화 프롬프트 — 제출 직전 브라우저 기반 점검

```text
$sk-ui-smoke
제출 직전이므로 현재 코드 기준의 UI P0 흐름을 브라우저로 엄격히 스모크 검증해줘.
SPEC.md의 R, P, 10절 UI·API 계약, 11절 T, 12절 추적표와 BRIEF.md의 실행·종료 조건을 먼저 읽어줘.
P0 중 사용자가 반드시 완료해야 하는 흐름을 우선순위로 골라 정상, 잘못된 입력, 빈 결과 또는 오류 흐름을 최대 세 개 선정해줘.
각 흐름마다 T# | 시작 화면 | 안전한 입력 | 사용자 동작 | 기대 화면·API 신호 | P# 근거 표를 먼저 만들어줘.
서버가 이미 실행 중인지 확인하고, 공식 명령과 공식 포트·호스트만 사용해 URL을 준비해줘.
smoke_test.py로 페이지 또는 건강 경로 도달성을 확인하되 GET 2xx가 UI 전체 PASS가 아님을 명시해줘.
브라우저가 있으면 흐름별로 실제 클릭·입력·제출을 수행하고 결과 값·필수 문구·정렬·빈 상태·로딩·오류 표시를 T#와 비교해줘.
잘못된 입력은 SPEC에 정의된 빈 필수값·형식 오류·범위 오류 중 한 가지만 안전하게 사용하고, 폼이 메시지를 표시하는지와 요청을 막는지 확인해줘.
빈 상태 또는 오류는 안전하게 재현 가능한 빈 검색·빈 목록·공식 오류 경로만 써서 확인하고, 서버를 고의로 망가뜨리지 마.
브라우저 콘솔과 네트워크를 볼 수 있으면 새 오류·실패 요청을 현재 흐름과 연결하고, 볼 수 없으면 콘솔 미검증으로 적어줘.
스크린샷은 증거가 꼭 필요할 때 한 장 이하로 저장하며 계정명·개인정보·민감 값이 보이면 저장하지 마.
모든 실제 도달성·화면 흐름을 EVIDENCE E#로 기록하고, 코드 변경 뒤 STALE인 E#가 있으면 새 실행으로 갱신해줘.
코드·CSS·문구·포트·서버 설정은 수정하지 말고, 기능 실패는 6.1 debug, 응답 차이는 5.4 api-contract로 인계해줘.
끝에 흐름별 PASS/FAIL/미검증, HTTP와 UI의 구분, 콘솔 관찰, E#, 종료 책임, 제출 차단 항목을 보고해줘.
```

## 변형 — 브라우저 도구가 없는 상황

```text
$sk-ui-smoke
브라우저 도구를 사용할 수 없으니 화면을 직접 본 것처럼 주장하지 말고 제한된 UI 검증을 수행해줘.
SPEC의 P0 사용자 흐름과 T#를 읽고 최대 세 흐름의 시작 URL·입력·기대 화면 상태를 수동 체크리스트로 작성해줘.
공식 URL에 smoke_test.py를 실제 실행해 HTTP 도달성의 종료 코드·상태를 E#로 기록해줘.
가능하면 API 계약이 있는 흐름은 안전한 HTTP 호출 결과로 뒷받침하되, 화면 문구·로딩·콘솔·빈 상태는 미검증 또는 수동 확인 필요로 분리해줘.
사용자가 직접 확인할 순서를 정상 입력, 잘못된 입력, 빈/오류 상태별로 3~5단계씩 구체적으로 제시해줘.
수동 확인 결과가 아직 없으면 UI PASS로 판정하지 말고 HTTP 확인 PASS / 화면 수동 확인 필요로 적어줘.
코드·스타일·서버 설정을 수정하지 말고, API 응답 차이는 5.4 api-contract, 기능 실패는 6.1 debug으로 넘겨줘.
```

## 변형 — 빈 상태나 서버 오류를 안전하게 재현할 수 없는 상황

```text
$sk-ui-smoke
빈 상태 또는 서버 오류를 강제로 만들면 위험하니 안전한 범위에서 UI 검증을 해줘.
먼저 SPEC과 T#에 공식 빈 검색·빈 목록·오류 테스트 경로가 있는지 확인하고, 있을 때만 해당 입력을 사용해줘.
공식 재현 수단이 없으면 서버를 중지·변조하거나 데이터·포트·환경변수를 바꾸지 마.
정상 흐름과 잘못된 입력 흐름은 실제로 검증하고, 빈/오류 상태는 미검증 사유와 사용자가 수동으로 확인할 화면 요소를 체크리스트로 남겨줘.
HTTP 도달성과 확인 가능한 API 상태는 E#로 기록하되, 확인하지 못한 오류 표시를 PASS로 쓰지 마.
정책·표시 요구가 불명확하면 1.3 dm-questions으로, 재현 가능한 기능 실패는 6.1 debug으로 인계해줘.
```

## 결과물 확인

- 최대 세 개의 P0 흐름이 R/T/P 근거와 안전한 입력으로 선택되어 있다.
- `smoke_test.py`의 실제 종료 코드·HTTP 상태와 GET/2xx/5초/120자 한계가 기록되어 있다.
- 브라우저 가능 시 정상·잘못된 입력·빈/오류의 적용 흐름을 실제로 수행했다.
- 브라우저 불가 시 HTTP 결과와 수동 화면 확인이 명확히 분리되어 있다.
- E#에는 흐름·안전한 입력 유형·실제 관찰·코드 상태가 있고 민감 값이 없다.

## 다음 단계

재현 가능한 화면 기능 실패가 있으면 [6.1 debug](../6-debug/6.1-debug.md)의 `$sk-debug`으로 넘긴다.
API 상태·응답 스키마 차이면 [5.4 api-contract](../5-verify/5.4-api-contract.md)의 `$sk-api-contract`을 쓴다.
화면 상태·문구의 정책이 비어 있으면 [1.3 dm-questions](../1-discover/1.3-dm-questions.md)의 `$sk-dm-questions`로 확인한다.
UI E#를 요구사항별 PASS/FAIL/미검증에 연결하려면 [5.1 verify](../5-verify/5.1-verify.md)의 `$sk-verify`를 쓴다.

## 주의

GET 2xx 도달성만으로 입력 검증·결과 표시·빈 상태·오류 처리가 통과했다고 쓰지 않는다.
브라우저가 없으면 화면·콘솔을 직접 봤다고 기록하지 않는다.
실제 사용자 계정, 개인정보, 결제·외부 서비스는 허가 없이 시험하지 않는다.
오류 상태를 보기 위해 서버를 강제 종료·변조하거나 포트·호스트를 바꾸지 않는다.
화면 문구·스타일 대규모 변경, 코드 수정, 테스트 삭제는 이 프롬프트의 범위 밖이다.
