# 8.2 제출 전 최종 점검·도구 정리

> 스킬: `$sk-deliver` · 단계: 문서화·제출 · 작업 노트: `sk/work/SPEC.md`, `sk/work/EVIDENCE.md`, `sk/work/REVIEW.md`, `sk/work/PLAN.md` · 사용 자료: 없음

## 언제 쓰나

- 보고서가 준비된 뒤, 사용자가 실제 제출·업로드를 하기 직전에 사용한다.
- 필수 파일·최신 테스트·서버 계약·민감정보·도구 흔적을 한 번에 대조해 GO 여부를 판단할 때 사용한다.
- 남은 시간이 적어 새 기능을 멈추고 최소 제출 경로를 확정할 때 사용한다.
- 코드 구현이나 실패 원인 분석이 목적이면 이 프롬프트 대신 4-build 또는 6-debug 단계로 돌아간다.

## 준비할 입력

- `sk/work/SPEC.md`의 상태, 필수 제출물, C#, T#, 추적표, 게이트 결과
- `sk/work/EVIDENCE.md`의 최신 E# 및 코드 변경 이후 STALE 여부
- `sk/work/REVIEW.md`의 차단/높음 F#와 준수 감사 상태
- `sk/work/PLAN.md`의 시간·축소 결정·상태 캡슐
- 제출 보고서의 실제 경로와 과제 공식 제출 안내
- 서버 요구가 있으면 공식 실행 명령, 포트, 확인할 URL
- 현재 남은 시간과 QA 단계가 AI 허용 시간인지 여부

## 전략 — 왜 이렇게 하나

제출 직전에는 “파일이 있다”는 확인보다 현재 코드로 다시 실행된 증거, 공식 경로·형식, 남은 위험을 함께 봐야 한다.
그래서 필수 제출물 표와 최신 E#을 먼저 대조하고, 실패·STALE·미검증을 GO 판정에서 분리한다.
도구 제거는 제출 규칙과 사용자의 명시적 승인 없이는 되돌릴 수 없는 손실을 만들 수 있으므로 안내와 결정만 한다.
제출·업로드·push는 사용자의 행동으로 남겨 승인 경계를 지킨다.

## 기본 프롬프트

```text
$sk-deliver
제출 직전 최종 점검을 수행하고 GO, CONDITIONAL, NO-GO 중 하나를 근거와 함께 판정해 주세요.
먼저 sk/work/SPEC.md의 2절 필수 제출물·C#·T#·추적표, EVIDENCE.md의 최신 E#,
REVIEW.md의 차단/높음 F#와 준수 감사, PLAN.md의 남은 시간·축소 결정을 읽으세요.
SPEC 2절의 항목별로 “지정 경로·파일명 | 실제 존재 | 형식·이름 | 근거 | 상태” 표를 만드세요.
현재 코드 기준으로 전체 테스트를 실제로 한 번 실행할 수 있으면 과제의 표준 명령만 사용하고 E#을 기록하세요.
실행하지 못하면 이전 E#을 최신 통과로 쓰지 말고 사유와 위험을 미검증으로 표시하세요.
서버 요구가 있으면 공식 실행 방법과 계약을 확인하고, 필요할 때만
python3 sk/snippets/smoke_test.py http://127.0.0.1:<포트>/<경로>
형식으로 GET 도달성을 확인한 후 종료 코드와 한계를 E#에 남기세요.
보고서 존재·형식·근거, 민감정보, git 변경 범위, QA 준비 상태를 점검하되 AI 금지 시간에는 QA 자료를 열거나 만들지 마세요.
공식 규칙에 도구 제거 요구가 있는지 확인하고, 사용자 승인 전에는 uninstall·삭제·제출·업로드·push를 실행하지 마세요.
GO/CONDITIONAL/NO-GO, 필수 제출물 표, 최신 E#, 차단 조건, 도구 흔적 판단, 사용자가 실행할 마지막 행동 순으로 보고하세요.
```

## 심화 프롬프트 — 변경이 많거나 제출 규칙이 엄격한 경우

```text
$sk-deliver
제출 전 감사처럼 최종 점검하되, 실제 근거와 사용자 승인 경계를 엄격히 지켜 주세요.
SPEC.md에서 0·2·4·11·12·14절을, EVIDENCE.md에서 실행 기록을,
REVIEW.md에서 F#·준수 감사를, PLAN.md에서 축소 결정·상태 캡슐을 먼저 읽으세요.
시작 시 git status --short와 git diff --stat을 읽기 전용으로 확인하고, 예상 밖 파일·대용량 로그·민감정보 가능성을 분리해 표시하세요.
SPEC 2절의 각 제출물을 “제출물 | 지정 경로·파일명 | 실제 존재 | 형식·이름 | 내용/근거 | 상태” 표로 대조하세요.
존재 여부와 요구사항 충족 여부를 혼동하지 말고, 보고서는 템플릿의 5절과 실제 T#/E#/DD#/P# 근거가 남아 있는지도 확인하세요.
표준 전체 테스트를 새로 실행할 수 있으면 실행하고, 명령·작업 디렉터리·대상 R/T·기대·실제 결과·종료 코드·판정·코드 상태를 E#으로 기록하세요.
이전 PASS 뒤 코드가 달라졌다면 STALE로 처리하며, 실행하지 않은 것은 통과로 쓰지 마세요.
서버 과제라면 공식 포트·실행 명령을 바꾸지 말고 `0.0.0.0` 바인딩(내장 Browser 미리보기용, 과제 문서 우선)을 확인하며, 도달성 확인과 API/UI 계약 확인을 분리하세요.
smoke_test.py는 GET 1건의 2xx 도달성만 보므로, 실패 시 종료 코드가 0이 아님을 확인하고 계약 전체를 대체하지 않는다고 기록하세요.
차단/높음 F#, 테스트 FAIL, 필수물 누락, 서버 계약 위반, 민감정보는 NO-GO 조건으로 분류하세요.
미검증·낮은 위험·사용자 확인·도구 처리 결정만 남았으면 조건을 문장으로 적어 CONDITIONAL을 고려하세요.
도구 흔적은 공식 규칙이 명시하고 사용자가 승인한 경우에만 정리 절차를 안내하며, sk/work 노트 보존 위치를 먼저 확인하세요.
python3 sk/scripts/install.py --uninstall 명령은 직접 실행하지 말고, 영향과 사용자 결정을 설명하는 용도로만 제시하세요.
제출 버튼·파일 업로드·외부 push·삭제를 실행하지 말고, 끝나면 사용자가 할 정확한 마지막 행동을 제시하세요.
```

## 변형 — 남은 시간이 15분 이하인 경우

```text
$sk-deliver
남은 시간이 15분 이하입니다. 새 기능·리팩터링·추가 패키지 설치는 하지 말고 최소 제출 경로만 점검하세요.
SPEC 2절의 필수 제출물과 보고서 경로를 실제 파일과 대조해 표로 정리하세요.
현재 코드의 전체 테스트를 한 번 실행할 시간이 있으면 표준 명령으로 실행해 E#을 남기고, 없으면 미검증 사유를 숨기지 마세요.
서버 요구가 명시됐고 이미 실행 환경이 있으면 지정 URL의 도달성만 빠르게 확인하되 계약 전체 통과로 과장하지 마세요.
REVIEW의 차단/높음, EVIDENCE의 FAIL/STALE, 민감정보, 필수 파일 누락만 우선 차단 조건으로 보세요.
QA 카드가 이미 준비됐는지 여부만 확인하고, AI 금지 시간이면 만들거나 열지 마세요.
도구 제거는 지금 실행하지 말고 공식 규칙과 사용자 결정이 필요한지 한 줄로 표시하세요.
GO/CONDITIONAL/NO-GO와 사용자가 수행할 마지막 제출 행동을 간결하게 보고하세요.
```

## 변형 — 도구 제거 요구가 불명확한 경우

```text
$sk-deliver
필수 제출물과 최신 검증을 먼저 점검하되, 도구 흔적 제거 요구가 불명확합니다.
과제 공식 안내에서 제출 범위와 제거 요구를 찾아 사실만 인용하고, 요구가 없으면 sk/, AGENTS.md 관리 구역, 설치된 스킬을 변경하지 마세요.
사용자에게 보존할 sk/work 노트, 공식 제출 범위, 정리 승인 여부를 질문 목록으로 제시하세요.
정리 요구와 명시적 승인이 모두 있을 때에만 python3 sk/scripts/install.py --uninstall을 제안하고 직접 실행하지 마세요.
그 전에는 어떤 폴더·노트·설정도 삭제하지 마세요.
테스트·보고서·민감정보·필수물의 GO 조건은 도구 정리와 분리해 판정하세요.
끝나면 제출 판정, 도구 처리의 미결정 이유, 사용자가 결정해야 할 선택지를 순서대로 보고하세요.
```

## 결과물 확인

- [ ] 필수 제출물이 SPEC 2절의 경로·이름·형식과 실제로 대조됐다.
- [ ] 최신 코드 기준 전체 테스트가 새 E#으로 남았거나, 미실행·STALE 이유가 명확하다.
- [ ] 서버 과제라면 지정 포트·`0.0.0.0` 바인딩·계약이 별도로 확인됐다.
- [ ] 보고서가 존재하고 실제 근거·미검증 상태가 최신 실행 결과와 모순되지 않는다.
- [ ] 차단/높음 F#, FAIL, 민감정보, 예상 밖 파일이 숨겨지지 않았다.
- [ ] QA 준비는 AI 사용 가능 시간 내에서만 확인됐다.
- [ ] 도구 정리는 공식 규칙과 사용자 승인 전에는 실행되지 않았다.
- [ ] GO/CONDITIONAL/NO-GO와 사용자의 마지막 행동이 분명하다.

## 다음 단계

GO라면 사용자가 공식 안내에 따라 직접 제출·업로드·push를 수행한다. 이 프롬프트는 그 동작을 실행하지 않는다.
CONDITIONAL이면 조건을 해소한 뒤 이 프롬프트를 다시 사용하며, 최신 검증이 필요하면 [5.1 요구사항 추적 검증](../5-verify/5.1-verify.md)으로 간다.
NO-GO의 실패는 [6.1 가설 기반 디버깅](../6-debug/6.1-debug.md), 보고서 누락·근거 불일치는 [8.1 보고서 작성](../8-submit/8.1-report.md)으로 보낸다.
AI 허용 시간에 QA 카드가 없으면 [9.2 6문항 암기 카드](../9-qa/9.2-qa-card.md)를 권장하되, AI 금지 시간이 시작되면 즉시 사용을 멈춘다.

## 주의

- PASS는 실제 최신 실행 결과로만 쓰고, 이전 E#이나 추정 결과를 대체 근거로 쓰지 않는다.
- `smoke_test.py`의 GET 2xx 확인은 API/UI 계약 전체 테스트가 아니다.
- 보고서와 코드를 제출 준비 상태로 바꾸기 위해 결과를 조작하거나 실패를 숨기지 않는다.
- 사용자 승인 없이 설치 해제·삭제·강제 복구를 하지 않으며, 작업 노트를 먼저 보존하지 않고 정리하지 않는다.
- 제출 버튼·업로드·외부 push·자격증명 전송은 사용자가 직접 한다.
