# 8.1 보고서 작성 (SUBMISSION 템플릿 사용)

> 스킬: `$sk-report` · 단계: 문서화·제출 · 작업 노트: `sk/work/SPEC.md`, `sk/work/DM_LOG.md`, `sk/work/DECISIONS.md`, `sk/work/EVIDENCE.md`, `sk/work/UNDERSTANDING.md` · 사용 자료: `sk/templates/SUBMISSION_DOC_TEMPLATE.md`

## 언제 쓰나

- 7.2 준수 감사 후, 실제 구현과 검증 결과를 제출 보고서로 정리할 때 사용한다.
- 과제가 요구한 보고서 경로·파일명이 `SPEC.md` 2절에 확정됐을 때 가장 적합하다.
- 제출 경로가 불명확하면 공식 파일을 추측해 만들지 않고 `sk/work/REPORT_DRAFT.md`에 초안을 만들 때 사용한다.
- 코드 수정이나 새 테스트 작성이 목적이면 이 프롬프트 대신 해당 단계 스킬을 쓴다.

## 준비할 입력

- `sk/work/SPEC.md`의 2·3·4·5·11·12절과 현재 상태
- `sk/work/DM_LOG.md`의 실제 담당자 답변 및 P#
- `sk/work/DECISIONS.md`의 DD#와 AI#
- `sk/work/EVIDENCE.md`의 최신 E# 및 FAIL/STALE/미검증 항목
- 있으면 `sk/work/UNDERSTANDING.md`, `sk/work/REVIEW.md`
- 과제 공식 제출 경로·파일명·형식, 또는 “미지정”이라는 사실

## 전략 — 왜 이렇게 하나

보고서는 홍보 문구가 아니라 요구사항·결정·코드·실행 증거를 하나로 연결하는 제출물이다.
따라서 템플릿의 5개 절 구조와 2절 4열 표는 고정하고, 모든 주장을 실제 ID·파일·함수·실행 결과로 역추적한다.
확인되지 않은 담당자 답변, 실행하지 않은 테스트, 처리하지 않은 엣지 케이스는 채우지 않는다.
제출 경로가 불명확한 경우 과제 파일을 오염시키지 않고 작업 노트 초안으로 분리한다.

## 기본 프롬프트

```text
$sk-report
현재 과제의 제출 보고서를 증거 기반으로 작성해 주세요.
먼저 sk/work/SPEC.md에서 공식 보고서 경로·파일명·형식과 R/C/P/T 추적 상태를 확인하세요.
sk/work/DM_LOG.md의 실제 M# 답변과 P#, sk/work/DECISIONS.md의 DD#/AI#,
sk/work/EVIDENCE.md의 최신 E#, 필요하면 UNDERSTANDING.md·REVIEW.md를 읽어 근거만 추출하세요.
sk/templates/SUBMISSION_DOC_TEMPLATE.md의 제목, 1~5절 순서, 2절 4열 표를 정확히 유지하세요.
템플릿의 대괄호 플레이스홀더와 과제와 무관한 예시는 남기지 말고 실제 내용으로 교체하세요.
SPEC 2절에 지정 경로가 있으면 그 공식 경로에 저장하고, 없으면 sk/work/REPORT_DRAFT.md에만 저장하세요.
1절은 목표·C#·실제 M#→P# 반영, 2절은 DD# 근거의 선택·대안·트레이드오프,
3절은 실제 파일·함수의 입력→처리→출력 흐름, 4절은 최신 T#/E#/AI#,
5절은 실제 한계·구체 개선안만 작성하세요.
FAIL, STALE, 미검증은 숨기지 말고 해당 절에 사실대로 표시하세요.
코드·테스트·원본 데이터는 수정하지 말고, 비밀값·개인정보·민감 원본값도 보고서에 넣지 마세요.
완료 후 저장 경로, 사용한 근거 ID, 미검증/제외 항목, 템플릿 구조 점검 결과와 다음 단계 8.2를 보고하세요.
```

## 심화 프롬프트 — 근거가 흩어졌거나 검증 상태가 섞인 경우

```text
$sk-report
시간 제한 제출을 위해 보고서를 작성하되, 먼저 증거 완결성을 감사한 뒤 문서를 만드세요.
읽을 범위는 sk/work/SPEC.md의 0·2·3·4·5·11·12·14절, DM_LOG.md의 M#과 정책 목록 P,
DECISIONS.md의 DD# 및 AI 교정 기록, EVIDENCE.md의 실행 기록, UNDERSTANDING.md와 REVIEW.md입니다.
각 보고서 주장에 대해 “절 | 주장 | 근거 ID/파일:함수 | 현재성 | 처리” 내부 점검표를 먼저 만드세요.
코드가 바뀐 뒤의 E#은 최신으로, 이전 결과는 STALE 또는 미검증으로 구분하고 통과 근거로 과장하지 마세요.
공식 문서와 P#가 충돌하거나 보고서 경로가 상충하면 선택하지 말고 사용자 확인 항목으로 표시하세요.
sk/templates/SUBMISSION_DOC_TEMPLATE.md를 기반으로 제목과 1~5절 구조, 2절의 네 열을 보존하세요.
1절에는 R#/C#와 실제 M#→P#만 연결하고, 답변 없는 문의를 확인된 정책으로 쓰지 마세요.
2절에는 실제 DD#가 있는 결정만 행으로 쓰며, 비교하지 않은 대안을 꾸며 내지 마세요.
3절에는 코드에서 재확인한 2~5개 파일·함수와 실제 제어 흐름을 쓰세요.
4절은 T#→E# 연결을 우선하고, 처리·검증한 엣지 케이스만 번호로 기록하며 개수를 맞추지 마세요.
AI#가 있을 때만 초기 제안의 문제·발견·수정 지시·검증을 짧게 적고, 없으면 AI 협업 내역을 만들지 마세요.
5절에는 PLAN의 축소 결정과 REVIEW의 미해결 항목을 반영해 실패 조건과 개선 검증 방법을 구체화하세요.
제출 경로가 확정됐으면 그 경로에 저장하고, 미지정이면 sk/work/REPORT_DRAFT.md에만 저장하세요.
대괄호 플레이스홀더, 예시 문장, 민감정보, “모두 통과” 같은 근거 없는 표현을 제거하세요.
코드·테스트·원본 데이터·제출 설정을 변경하지 마세요.
완료 보고에는 저장 위치, 절별 근거, 최신/STALE/FAIL/미검증 구분, 사용자 확인 필요 사항, 8.2 제출 점검 전제조건을 순서대로 제시하세요.
```

## 변형 — 제출 경로가 아직 확정되지 않은 경우

```text
$sk-report
보고서 제출 위치가 아직 확인되지 않았습니다.
SPEC 2절과 과제 안내를 읽어 경로·파일명·형식이 명시됐는지 먼저 판별하고, 없으면 임의의 과제 파일을 만들지 마세요.
sk/templates/SUBMISSION_DOC_TEMPLATE.md의 5절 구조와 2절 4열 표를 유지한 초안을 sk/work/REPORT_DRAFT.md에 작성하세요.
초안은 SPEC·DM_LOG·DECISIONS·EVIDENCE의 실제 R#/C#/P#/DD#/T#/E#만 근거로 채우세요.
증거가 없거나 STALE인 결과는 “미검증”과 사유로 쓰고, 실제 처리하지 않은 엣지 케이스는 삭제하세요.
플레이스홀더와 템플릿 예시는 남기지 말고 민감정보도 제거하세요.
코드나 제출 디렉터리는 수정하지 마세요.
끝나면 초안 경로, 공식 경로를 확정하기 위해 사용자에게 물을 정확한 질문, 누락 근거, 다음 단계 8.2 전 필요한 검증을 알려주세요.
```

## 변형 — 남은 시간이 10분 미만인 경우

```text
$sk-report
남은 시간이 10분 미만입니다. 제출 보고서의 최소 정합성 경로만 수행하세요.
SPEC 2절에서 공식 경로를 확인한 뒤 템플릿 제목·1~5절·2절 4열 표를 보존해 저장하세요.
우선순위는 1절의 목표·제약·P#, 3절의 실제 파일·함수, 4절의 가장 최신 E#, 5절의 미검증·한계입니다.
DD#가 있는 설계만 2절에 한 행씩 쓰고, 근거가 없는 대안 비교나 배경 설명은 생략하세요.
예시 문구·대괄호 플레이스홀더·만들어 낸 DM 답변·만들어 낸 테스트 결과를 남기지 마세요.
STALE/FAIL/미검증은 짧게라도 사실대로 표시하고 비밀값·개인정보는 제외하세요.
코드·테스트·원본 데이터를 수정하거나 외부 제출을 실행하지 마세요.
끝나면 저장 경로, 가장 큰 제출 위험 3개 이하, 8.2에서 확인할 항목만 간결하게 보고하세요.
```

## 결과물 확인

- [ ] 공식 제출 경로가 `SPEC.md` 2절과 일치하거나, 미지정이면 `sk/work/REPORT_DRAFT.md`만 생성됐다.
- [ ] 제목, 1~5절 순서, 2절 4열 표가 템플릿과 동일하게 유지됐다.
- [ ] 1절은 R#/C#/M#→P#, 2절은 DD#, 4절은 T#/E#/AI#로 실제 근거가 추적된다.
- [ ] 3절의 파일·함수·흐름이 코드와 일치하며, 5절이 실제 제약과 개선 검증 방법을 담는다.
- [ ] 플레이스홀더·예시·민감정보·근거 없는 통과 주장이 없다.
- [ ] FAIL, STALE, 미검증을 통과로 바꾸지 않았다.

## 다음 단계

보고서가 저장되면 [8.2 제출 전 최종 점검·도구 정리](../8-submit/8.2-deliver.md)에서 필수 제출물, 최신 전체 테스트, 서버 요구, 민감정보, 도구 정리 결정을 점검한다.
테스트 근거가 오래됐거나 빈칸이면 먼저 [5.1 요구사항 추적 검증](../5-verify/5.1-verify.md)으로 돌아간다.
실패가 있으면 보고서를 미화하지 말고 [6.1 가설 기반 디버깅](../6-debug/6.1-debug.md)으로 원인을 좁힌다.

## 주의

- 보고서는 템플릿을 참고하는 것이 아니라 5개 절 구조·순서와 2절 표를 보존해 작성한다.
- 보고서 경로를 추측하지 않으며, 경로 미지정 시 작업 노트 초안 외 과제 파일을 만들지 않는다.
- 담당자 DM은 사용자가 직접 보낸 실제 답변만 근거가 된다.
- 작성되지 않은 AI 교정 기록, 실행하지 않은 테스트, 처리하지 않은 엣지 케이스를 추가하지 않는다.
- 제출 버튼·업로드·외부 push는 이 프롬프트의 범위가 아니다.
