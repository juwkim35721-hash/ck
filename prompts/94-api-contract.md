# API 계약·상태 전이 검증

## 사용 시점

API 구현 또는 수정 뒤, 제출 전 실제 요청과 응답이 기존 계약을 지키는지 확인할 때 사용한다.
이 단계는 새 API 설계나 인증 정책 변경이 아니라, 이미 존재하는 표면과 상태 규칙의 검증이다.
공식 안내가 제공되면 그것을 우선하며, AI 사용이 허용된 단계에서만 이 문서를 사용한다.
후속 AI 금지 서술형이 시작되면 즉시 프롬프트·스킬·암기자료 사용을 중단한다.

## 필요 입력

- [과제 루트]: 준비 도구 저장소가 아닌 실제 과제의 절대 경로
- [남은 시간: 분]: 테스트와 수정 여부를 판단할 시간
- [요구사항/파일/답변]: API 명세, 라우트·컨트롤러·모델, 호출자, 기존 테스트, 정책 답변
- [실행 방법]: 서버 또는 테스트 실행 명령, 필요한 로컬 의존성
- [인증/권한 정보]: 제공된 테스트 계정·토큰의 사용 범위(없으면 없음으로 기록)

입력이 없거나 모호하면 코드를 고치지 말고 라우트와 기존 테스트를 읽어 확인한다.
명세와 코드가 충돌하면 어느 쪽이 우선인지 확인할 질문으로 남기고 임의로 계약을 정하지 않는다.

## 전략

1. 실제 과제 루트와 테스트 실행 가능 여부를 확인한다. 준비 도구 저장소를 과제로 취급하지 않는다.
2. 라우트, 핸들러, 스키마, 상태 저장소, API 호출자와 기존 테스트를 읽어 현재 계약의 증거를 모은다.
3. 메서드·경로별로 전제조건, 요청 본문/파라미터, 성공 상태와 본문, 오류 상태와 오류 본문, 부작용을 표로 정리한다.
4. 상태가 있는 자원은 시작 상태, 허용 전이, 금지 전이, 종결 상태를 코드·명세 근거와 함께 분리한다.
5. 각 계약에 정상, 잘못된 입력, 없는 ID, 중복 요청, 적용 가능한 권한 사례를 연결한다. 인증을 임의로 추가·제거하지 않는다.
6. 실제 요청 또는 기존 테스트 러너로 검증한다. 상태 코드만 통과 기준으로 삼지 말고 본문의 필수 필드·값·오류 구조·부작용을 assert한다.
7. 중복 요청은 같은 요청을 두 번 보내 생성 수·최종 상태·응답 의미를 비교한다. 멱등 키나 재시도 정책이 실제로 있을 때만 그 규칙을 검사한다.
8. 실패는 숨기거나 테스트를 삭제하지 않는다. 관찰값, 기대값의 근거, 재현 명령, 영향을 받은 계약을 함께 남긴다.

## 기본 프롬프트

```text
$sk-api-contract
실제 과제 루트는 [과제 루트]이고 남은 시간은 [남은 시간: 분]분이다.
[요구사항/파일/답변]과 현재 라우트·핸들러·호출자·기존 테스트를 먼저 읽어 API 계약을 검증하라.

수정 전에 메서드와 경로별로 다음을 증거 파일/위치와 함께 표로 작성하라.
- 전제조건과 권한
- 요청 파라미터·본문의 필수/선택 필드와 형식
- 성공 상태 코드와 응답 본문의 필수 필드·값
- 오류 상태 코드와 오류 본문 구조
- 저장·전송 등 관찰 가능한 부작용

상태가 있는 자원은 시작 상태, 허용 전이, 금지 전이, 종결 상태를 별도 전이표로 작성하라.
정상·잘못된 입력·없는 ID·중복 요청·적용 가능한 권한 사례를 실제로 실행하라.
각 사례에서 상태 코드뿐 아니라 본문, 오류 구조, 저장된 결과 또는 후속 조회를 assert하라.
중복 요청은 동일 요청을 두 번 실행하여 생성 수·최종 상태·응답 의미를 비교하라.

인증 정책을 바꾸거나 추측하지 말고 제공된 계정/토큰과 기존 동작만 사용하라.
명세, 코드, 실행 환경 중 하나가 없어 기대값을 정할 수 없으면 수정·추정을 멈추고 정확한 부족 정보와 읽기 전용으로 확인한 사실을 보고하라.
출력은 계약 테스트 표, 상태 전이·멱등성 결과, 정확한 실행 명령과 통과/실패, 미검증 항목 순서로 작성하라.
```

## 심화/반증 프롬프트

```text
$sk-api-contract
[과제 루트]의 API에서 이미 통과한 결과를 정답으로 가정하지 말고 반증 검토를 하라.
기존 공개 표면을 읽기 전용으로 추적하여, 각 메서드/경로의 호출자 기대와 실제 응답이 어긋날 수 있는 지점을 찾으라.
특히 다음 반례를 실제 계약에 적용 가능한 경우에만 재현하라.
- 존재하지 않는 ID 또는 다른 자원의 ID
- 필수 필드 누락, 잘못된 타입/형식, 경계값
- 같은 변경 요청의 즉시 재전송과 최종 상태 재조회
- 이미 종결되었거나 현재 상태에서 허용되지 않는 전이
- 제공된 서로 다른 권한 주체의 읽기·변경 시도

모든 재현에는 요청, 기대값 근거, 실제 상태 코드, 응답 본문 assert, 후속 상태 확인을 연결하라.
상태 코드가 성공이어도 본문 필드, 오류 누출, 중복 생성, 잘못된 상태 변경이 있으면 실패로 판정하라.
권한 계정, 상태 모델, 실행 가능한 서버가 없으면 가짜 요청이나 추정 결과를 만들지 말고 미검증으로 분류하라.
수정이 필요하면 원인과 최소 수정 후보만 제안하고, 승인된 범위 밖의 인증 변경·리팩터링·배포는 실행하지 말라.
```

## 완료 기준

- 확인 가능한 모든 메서드/경로에 계약 테스트와 근거가 연결되어 있다.
- 실행한 사례는 상태 코드와 본문 assert, 필요한 경우 후속 상태 확인을 포함한다.
- 상태 전이와 중복 요청 결과가 실제 실행 증거로 기록되어 있다.
- 실행 불가, 정책 미확인, 권한 사례 부재는 성공으로 포장하지 않고 미검증으로 남겼다.

## 다음 단계

실패가 재현되면 최소 원인 가설과 재현 명령을 `90-debug` 또는 승인된 구현 단계로 넘긴다.
계약이 통과했으면 요구사항 전체의 독립 검증은 `08-verify`, 제출 준비는 `10-deliver`에서 수행한다.
시간이 부족하면 새 엔드포인트 검토를 중단하고 P0 경로의 정상·오류·상태 전이 증거를 우선 보존한다.

## 주의

공식 메일의 모델, 일정, 금지 규정, 채점 방식은 제공되지 않았으므로 추정하거나 주장하지 않는다.
기존 API의 메서드·경로·응답 스키마와 인증 동작을 편의상 바꾸지 않는다.
원본 데이터와 기존 테스트를 삭제하거나 실패를 숨기지 않으며, 외부 배포·제출·push는 수행하지 않는다.
