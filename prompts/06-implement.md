# 수직 슬라이스 구현

## 사용 시점

요구사항 ID와 최소 설계가 확인되었고, 허용된 범위에서 실제 코드를 수정할 때 사용한다.
목표는 한 요구사항을 입력부터 관찰 가능한 출력까지 관통시키는 최소 변경이다.
준비 도구 저장소가 아닌 실제 과제 루트에서만 작업한다.
공식 안내가 제공되면 그 규칙을 우선하고, AI 사용 허용 범위에서만 사용한다.
후속 AI 금지 서술형이 시작되면 이 프롬프트와 모든 보조 자료 사용을 중단한다.

## 필요 입력

- [과제 루트]: 실제 구현·실행 대상 절대 경로
- [남은 시간: 분]: 검증과 복구 시간을 뺀 현재 시간
- [요구사항/파일/답변]: 구현할 R1 같은 요구사항 ID와 수용 기준 원문
- [수정 허용 범위]: 수정 가능/금지 파일, 기존 사용자 변경 여부
- [기존 설계]: 선택한 경계, 입력·출력 계약, 되돌릴 지점
- [기준선 명령과 결과]: 변경 전 실행한 테스트·빌드의 실제 결과
- [공식 안내]: 제공된 경우에만 원문 또는 적용 규칙

입력이 없거나 상충하면 파일을 수정하지 말고 실제 과제 루트와 부족한 항목을 먼저 확인한다.
기준선 결과가 없으면 가장 좁은 관련 실행 명령을 찾아 읽기·실행으로 확인한다.

## 전략

한 번에 한 요구사항 ID만 선택한다. 여러 요구사항이 얽히면 입력, 핵심 처리,
출력 중 가장 작은 끝점까지 닫히는 P0 흐름을 먼저 고른다.

수정 전에는 호출자, 공개 API, 데이터 스키마, 관련 테스트와 현재 diff를 읽는다.
기존 이름·경로·필수 키·단위·오류 형식을 바꾸는 변경은 계약 근거 없이 하지 않는다.

재현 가능한 실패 또는 기준선 하나를 확보한 뒤, 그 실패를 통과시키는 최소 파일·함수만
수정한다. 전면 리팩터링, 의존성 교체, 편의 기능 추가는 슬라이스 밖으로 분리한다.

각 반복은 `재현/기준선 → 작은 변경 → 같은 실행 → 결과 기록` 순서로 한다.
정상 경로 한 개와 해당 변경이 깨뜨릴 수 있는 가장 가까운 경계 또는 오류 경로 한 개를
실제 assert로 확인한다. 기존 테스트를 삭제·약화하거나 실패를 건너뛰지 않는다.

기준선 실패는 미구현 요구사항의 예상 실패, 기존 기능 결함, 환경 오류로 구분한다.
담당 요구사항의 예상 실패는 테스트를 보존해 구현 출발점으로 삼는다. 무관한 결함이나
실행 불가 환경은 새 변경과 섞지 말고 명령·출력을 보고한 뒤 먼저 작업을 분리한다.
계약이 모호해 출력 또는 오류 정책을 정할 수 없으면 추정 구현 대신 질문과 되돌릴 지점을
남긴다. 시간이 부족하면 새 슬라이스를 시작하지 말고 현재 P0 흐름의 실행 증거를 확보한다.

## 기본 프롬프트

```text
$sk-implement
[과제 루트]에서 R[번호]만 수직 슬라이스로 구현하라.
수정 전 현재 diff, 호출자, 입력·출력 계약, 관련 테스트를 읽고 [기준선 명령과 결과]를 실제로 확인하라.
수용 기준은 다음과 같다: [요구사항/파일/답변].
[수정 허용 범위] 밖의 파일과 사용자의 관련 없는 변경은 건드리지 말고, 원본 데이터도 덮어쓰지 마라.
입력 → 처리 → 출력이 연결되는 가장 작은 파일·함수 집합을 선언한 뒤 최소 변경만 하라.
변경마다 같은 재현 명령을 실행하고, 정상 경로와 가장 가까운 경계/오류 경로를 assert로 확인하라.
기존 API·스키마·오류 형식 변경이 필요하면 멈추고 근거와 대안을 보고하라.
끝에는 구현한 요구사항 ID, 변경 파일·함수, 실행한 정확한 명령과 실제 결과, 남은 작업·한계를 구분해 보고하라.
실패, 미실행, 미확인 항목을 통과로 표현하지 마라.
```

## 심화/반증 프롬프트

```text
$sk-implement
방금 구현한 R[번호] 수직 슬라이스를 반증하라. [과제 루트]의 실제 diff와 호출자를 기준으로만 판단하라.
(1) 이전 입력이 새 코드에 들어오는 경로, (2) 필수 출력/오류 형식, (3) 빈값·경계값 또는 실패 하나를 각각 추적하라.
기존 API·스키마·순서·원본 데이터 보존을 깨는 반례가 있으면 재현 명령, 기대/실제, 영향 파일을 제시하라.
반례가 현재 범위의 최소 수정으로 해결되면 그 수정과 회귀 assert를 적용하고 같은 명령을 재실행하라.
기준선의 무관한 기능 결함·환경 오류, 계약 미정, 범위 밖 수정, 또는 [남은 시간: 분] 내 검증 불가이면 중단하고 차단 원인을 보고하라. 해당 요구사항의 미구현으로 처음부터 실패한 테스트는 보존한 채 구현·재검증하라.
새 기능, 전면 리팩터링, 테스트 삭제·완화로 문제를 숨기지 마라.
```

## 완료 기준

- 선택한 요구사항 ID의 수용 기준이 입력부터 출력까지 실제로 실행된다.
- 변경 전후에 사용한 정확한 명령과 실제 통과·실패 결과가 남아 있다.
- 정상 경로와 관련 경계 또는 오류 경로에 독립 assert가 있다.
- 변경 파일·함수와 보존한 API·스키마가 명확하다.
- 미구현, 미검증, 기준선 실패, 정책 의존 사항을 숨기지 않았다.

다음 중 하나면 완료로 선언하지 말고 작업을 분리한다: 무관한 기준선 결함·환경 오류, 영향 큰 계약 미확정,
수정 권한 부재, 필요한 실행 환경 부재, 또는 검증 버퍼를 침범하는 새 작업.

## 다음 단계

실행 증거가 있는 슬라이스만 07-harden으로 넘겨 예외·불변식을 방어한다.
요구사항 대비 독립 검증이 더 필요하면 08-verify로 넘긴다.
현재 슬라이스가 닫히지 않았으면 새 기능을 추가하지 말고 04-plan 또는 92-timebox로 돌아간다.

## 주의

공식 안내 메일의 내용, 모델·일정·금지 규정·채점 방식은 제공되지 않았으므로 추정하지 않는다.
외부 push·배포·제출 버튼 조작·민감정보 업로드를 자동으로 하지 않는다.
파괴적 reset, rm, 광범위 재작성으로 사용자의 변경을 지우지 않는다.
테스트 코드 추가·실행은 허용 범위 안에서만 하고, 원본 데이터와 기존 테스트를 삭제하지 않는다.
