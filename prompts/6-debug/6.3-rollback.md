# 6.3 내 변경만 안전하게 되돌리기

> 스킬: `$sk-rollback` · 단계: 6-debug 디버깅·복구·시간 관리 · 작업 노트: `sk/work/PLAN.md`, `sk/work/EVIDENCE.md`, `sk/work/rollback/` · 사용 자료: 없음

## 언제 쓰나
마지막 PASS 이후의 내 변경이 회귀를 만들었고, 계속 디버깅하는 것보다 안전하게 이전 상태로 돌아가는 편이 나을 때 쓴다.
특히 [6.2 AI 반복 루프 탈출](../6-debug/6.2-unstuck.md) (`$sk-unstuck`)이 diff 확산·회복 불명확을 확인했을 때 사용한다.
원인이 확정된 한 줄 수정은 [6.1](../6-debug/6.1-debug.md) (`$sk-debug`)에서 해결하며, 단순히 마음에 들지 않는 코드를 무단 폐기하는 용도가 아니다.

## 준비할 입력
- 복구 사유와 관련 S#/R#/T#, 마지막 PASS E#, 현재 FAIL E#.
- `git status --short`, `git diff --name-only`, 대상 파일별 diff.
- 파일별 소유 판정: 내 변경 / 사용자·기존 변경 / 소유 불명.
- Git 저장소 여부, 마지막 정상 상태의 근거, 복구 뒤 실행할 테스트 명령.
- 사용자의 명시적인 승인 여부. 승인 전에는 과제 파일을 바꾸지 않는다.

## 전략 — 왜 이렇게 하나
되돌리기는 빨라 보여도 사용자 변경·미추적 파일·과제 원본까지 잃을 위험이 있다.
현재 patch와 내 미추적 파일을 먼저 `sk/work/rollback/`에 보관하고, 파일·hunk 단위 계획을 사용자에게 보여 준다.
사용자가 정확한 범위를 승인한 뒤에만 한 파일씩 복구하고 실제 테스트로 성공 여부를 판정한다.

## 기본 프롬프트
```text
$sk-rollback
복구 이유는 <실패/회귀 요약>이며 관련 S#/R#/T#은 <...>이다.
마지막 PASS는 <E#·명령>, 현재 FAIL은 <E#·명령>이다.
현재 git status와 diff 요약은 <...>이고, 복구 후보 파일은 <목록>이다.
각 파일의 소유 판정은 <내 변경/사용자·기존 변경/소유 불명>이다.
복구 후 확인할 기존 테스트 명령은 <명령>이다.

아직 사용자의 명시적 승인이 없다. 과제 파일을 복구·삭제·교체하지 마라.
먼저 파일 또는 hunk 단위로 복구 범위를 식별하고, 소유 불명·사용자 변경은 제외하라.
sk/work/rollback/<시각>.patch에 현재 추적 변경을 백업하고, 내 미추적 파일만 원래 상대 경로로 복사하라.
백업 존재·대상 목록을 확인한 뒤 복구 이유, 대상·제외 파일, 백업 경로, 테스트 계획을 표로 보고하라.
마지막에 “위 범위만 되돌리고 T#를 재실행해도 될까요?”라고 승인 질문을 하라.
승인이 없는 동안에는 분석·백업·계획만 하고 git restore 등 복구 명령을 실행하지 마라.
```

## 심화 프롬프트 — 사용자 변경과 내 변경이 한 파일에 섞임
```text
$sk-rollback
현재 복구를 검토한다. 관련 S#/R#/T#은 <...>, 마지막 PASS E#은 <...>, 현재 FAIL E#은 <...>이다.
파일별 현재 상태:
- <파일 A>: 내 변경 <hunk 설명>, 사용자·기존 변경 <hunk 설명>, 소유 판정 <...>
- <파일 B>: 내 변경 <hunk 설명>, 소유 판정 <...>
- <미추적 파일>: 생성자·용도·소유 판정 <...>
읽기 전용 git 출력은 <status/diff 요약>이고, 복구 후 테스트는 <명령>이다.

1) 파일 전체 복구 가능/불가를 소유 판정과 함께 표로 분류하라.
2) 사용자·기존 변경과 내 변경이 섞인 파일은 전체 복구 대상으로 삼지 말고, hunk 분리가 가능한지와 불가할 때의 확인 질문을 제시하라.
3) 현재 추적 변경 patch와 내 미추적 파일의 복사본을 sk/work/rollback/에 먼저 보관하라.
4) 백업의 상대 경로·포함 범위·제외 범위를 확인하고 PLAN.md의 ## 슬라이스 S에 복구 검토 상태로 기록하라.
5) 복구 대상, 보존할 변경, 복구하지 않을 항목, 테스트 순서를 사용자에게 보여라.
6) 승인 전에는 어떤 과제 파일도 바꾸지 마라. 위험한 전체 되돌리기 명령은 쓰지 마라.
7) 승인 후에는 승인된 파일 또는 hunk 하나씩만 복구하고 매번 diff를 확인하라.
8) 마지막 PASS 재현·대상 회귀·관련 전체 테스트를 실제 실행해 E#으로 기록하고 PASS/FAIL/미검증을 구분하라.
```

## 변형 — Git이 아니거나 정상 사본만 있음
```text
$sk-rollback
이 작업 공간은 Git diff를 신뢰할 수 없거나 Git 저장소가 아니다.
현재 파일은 <파일 목록>, 복구 기준 사본은 <경로·근거>, 실패 근거는 <E# 또는 실제 출력>이다.
사용자 승인 상태는 <없음/있음>이며 복구 후 테스트는 <명령>이다.

현재 파일과 복구 기준 사본을 각각 sk/work/rollback/<시각>/ 아래에 보관하고 출처를 적어라.
파일별로 내 변경인지 사용자·기존 변경인지 판정 근거를 표로 써라.
승인 전에는 파일 교체를 실행하지 말고, 대상·보존 항목·복구 후 테스트를 포함한 승인 질문만 작성하라.
승인 후 파일 하나씩만 교체하고, 전후 파일 상태와 실제 테스트 결과를 E#에 남겨라.
```

## 변형 — 승인받은 뒤 복구를 실행할 때
```text
$sk-rollback
사용자가 다음 범위의 복구를 명시 승인했다: <승인 원문 또는 요약>.
승인 범위는 <파일 또는 hunk>, 제외 범위는 <...>, 백업 경로는 <...>이다.
복구 후 실행할 명령은 <재현/회귀/관련 전체 테스트>다.

승인 범위를 다시 확인한 뒤 대상 하나씩만 복구하라.
각 복구 뒤 git diff로 예상 밖 변경이 없는지 확인하고, 적용 충돌 시 강제로 진행하지 말고 중단하라.
복구가 끝나면 git status/diff stat와 실제 테스트를 실행하라.
PLAN.md의 S# 상태와 EVIDENCE.md의 E#을 갱신하고, 복구됨·부분 복구·복구 실패 중 실제 판정만 보고하라.
다음 행동은 6.1 debug 또는 6.5 timebox 중 근거 있는 하나만 제시하라.
```

## 결과물 확인
- 복구 범위가 “전체 작업”이 아니라 파일·hunk 수준이다.
- 현재 상태가 `sk/work/rollback/`에 patch·사본으로 남아 있다.
- 사용자·기존 변경과 소유 불명 파일은 복구 대상에서 제외되었다.
- 승인 전에는 과제 파일을 바꾸지 않았고, 승인 뒤에도 승인 범위만 처리했다.
- 복구 후 실제 테스트 E#과 PLAN의 S# 상태가 있다.

## 주의
`git reset --hard`, `git clean`, `git stash`, 강제 체크아웃을 사용하지 않는다.
원본 데이터·기존 테스트·사용자 변경·소유 불명 파일을 내 변경으로 간주하지 않는다.
backup만 성공한 상태를 복구 완료라고 말하지 않으며, 테스트하지 않은 결과는 미검증으로 남긴다.
외부 push·배포·제출·업로드를 실행하지 않는다.
