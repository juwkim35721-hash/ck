# 6.2 AI 반복 루프 탈출

> 스킬: `$sk-unstuck` · 단계: 6-debug 디버깅·복구·시간 관리 · 작업 노트: `sk/work/PLAN.md`, `sk/work/EVIDENCE.md` · 사용 자료: 없음

## 언제 쓰나
같은 오류가 두 번 이상 반복되거나, 고치면 다른 부분이 깨지고, 같은 파일을 계속 왕복 수정할 때 쓴다.
현재 diff가 커지거나 AI가 R#/P#·현재 파일 상태를 이전 대화와 혼동할 때도 편집을 멈추기 위해 쓴다.
새 세션 단순 재개는 [6.4](../6-debug/6.4-resume.md) (`$sk-resume`)를, 이미 확정된 단발 오류는 [6.1](../6-debug/6.1-debug.md) (`$sk-debug`)를 우선한다.

## 준비할 입력
- 반복된 시도 2회 이상: 무엇을 바꿨는지, 실행 명령, 실제 오류·결과, E#.
- 마지막 PASS E#와 최근 FAIL E#, 각각의 코드 상태.
- `git status --short`, `git diff --stat`, 반복 수정한 파일의 diff.
- 현재 S#/R#/P#/T#, 남은 시간, 제출 필수물.
- 현재 PLAN 상태 캡슐과 열린 G#/A#.

## 전략 — 왜 이렇게 하나
반복 오류는 AI의 추론 부족보다 문제 범위가 너무 크거나 기준이 섞였다는 신호인 경우가 많다.
따라서 세 번째 수정 전에 사실을 한 장으로 압축하고, 입력·함수·상태·계약 중 하나만 10분 동안 판별한다.
실험이 실패하면 더 큰 수정으로 밀어붙이지 않고 복구·정책 확인·범위 축소 중 하나로 의도적으로 전환한다.

## 기본 프롬프트
```text
$sk-unstuck
같은 문제를 <횟수>회 수정했지만 아직 <오류/실패>가 반복된다.
시도 목록은 <시도1: 변경·결과>, <시도2: 변경·결과>이고 관련 E#은 <...>이다.
마지막 PASS는 <E#·명령·코드 상태>, 현재 FAIL은 <E#·명령·코드 상태>다.
현재 S#/R#/P#/T#은 <...>, 남은 시간은 <분>이며 현재 변경 파일은 <목록>이다.

지금부터 코드를 더 수정하지 말고 편집을 중단하라.
마지막 PASS와 현재 diff를 비교해 추가된 파일·변경 덩어리·미추적 파일을 구분하라.
문제를 “S#에서 R#/P#를 만족하려 했으나 T#가 어떻게 실패한다”는 한 문장으로 재진술하라.
입력/순수 함수/상태/API 계약/UI 중 한 층만 골라 10분 안의 단일 판별 실험을 설계하라.
성공 판정과 중단 조건을 포함하고, PLAN.md의 시간 예산·위험 실험·상태 캡슐을 갱신하라.
실험 결과에 따라 6.1 debug, 6.3 rollback, 6.5 timebox 중 하나만 다음 단계로 권고하라.
실행한 명령은 E#으로 기록하고, 복붙용 리셋 지시문도 제공하라.
```

## 심화 프롬프트 — 큰 diff와 맥락 혼동이 함께 발생함
```text
$sk-unstuck
AI 수정 루프를 중단한다. 현재 문제는 <한 줄 오류>이며 동일 계열 실패가 <횟수>회 있었다.
시도별 사실:
- 1회: <변경 파일·의도·명령·실제 결과·E#>
- 2회: <변경 파일·의도·명령·실제 결과·E#>
- 필요 시 3회: <사실만>
마지막 PASS E#: <...>, 현재 FAIL E#: <...>.
현재 git 상태: <status>, diff 요약: <stat>, 반복 수정 파일: <목록>.
SPEC 기준: R# <...>, P# <...>, A#/G# <...>, T# <...>.
PLAN 기준: 현재 S# <...>, 남은 시간 <분>, 제출 차단 항목 <...>.

1) 코드 편집과 자동 리팩터링을 즉시 멈추고, 시도 | 변경 | 명령 | 결과 | 배운 사실 표를 만들어라.
2) 마지막 PASS와 현재 상태 사이의 차이만 나열하고, 소유 불명 변경은 내 변경으로 단정하지 마라.
3) 문제를 SPEC 언어의 한 문장으로 재진술하고, 아직 모르는 사실을 분리하라.
4) 입력·순수 함수·상태·계약·UI 중 하나의 계층만 골라 가설 2개와 가장 싼 판별 실험을 제시하라.
5) 10분 타임박스의 시작·종료·성공 판정·중단 조건을 정하고 PLAN.md에 기록하라.
6) 정책 답이 없어서 막혔다면 구현하지 말고 1.3 dm-questions ($sk-dm-questions)의 긴급 단일 질문으로 넘겨라.
7) 현재 diff가 위험하면 복구를 실행하지 말고 6.3 rollback ($sk-rollback)의 백업·승인 계획만 제시하라.
8) 남은 시간이 15분 이하면 새 접근을 시작하지 말고 6.5 timebox ($sk-timebox)를 즉시 권고하라.
9) 마지막에 다음 AI에게 줄 리셋 지시문과, 다음 스킬 하나를 보고하라.
```

## 변형 — 담당자 정책 답변이 없어 구현이 막힘
```text
$sk-unstuck
반복 실패의 원인이 코드가 아니라 <정책 모호성>일 가능성이 높다.
관련 문서·P#/A#/G#은 <...>이고, 서로 다른 구현 결과는 <A일 때 결과 / B일 때 결과>이다.
현재 시도 <횟수>회와 E#은 <...>, 남은 시간은 <분>이다.

코드 편집을 멈추고 문서·DM에 이미 답이 있는지 먼저 확인하라.
없다면 H 영향인지 판정하고, H이면 1.3 dm-questions ($sk-dm-questions)용 3문항 이하의 긴급 질문 초안을 작성하라.
답을 기다리는 동안 진행 가능한 독립 S# 또는 되돌릴 수 있는 A# 기반 최소 작업만 구분하라.
PLAN.md 상태 캡슐에 차단 정책·다음 확인 행동을 기록하고, 답을 지어내지 마라.
```

## 변형 — 10분 실험이 실패하고 마감이 임박함
```text
$sk-unstuck
10분 판별 실험 <명령>의 실제 결과는 <결과/E#>이며 원인은 아직 확정되지 않았다.
현재 diff 위험도는 <낮음/중간/높음>, 남은 시간은 <분>, P0 차단 여부는 <예/아니오>다.

새 수정 전략을 추가로 제시하지 말고 먼저 rollback과 timebox의 선택 기준을 비교하라.
내 변경 범위가 명확하고 복구가 필요하면 6.3 rollback ($sk-rollback)의 백업·승인 계획으로 인계하라.
기능 가치보다 제출 위험이 크면 6.5 timebox ($sk-timebox)용 P0·필수물·최소 검증 목록을 만든다.
PLAN.md에 실험 실패 사실과 선택한 다음 행동 하나를 기록하라.
```

## 결과물 확인
- 세 번째 수정 전에 편집을 중단하고 시도 목록이 정리되었다.
- 마지막 PASS와 현재 FAIL·diff의 차이가 실제 E#/git 출력에 근거한다.
- 10분 실험은 한 계층·한 목표이며 성공과 중단 조건이 있다.
- PLAN의 시간 예산, 위험 실험, 상태 캡슐이 갱신되었다.
- 다음 경로는 debug·rollback·timebox 중 하나로 좁혀졌다.

## 주의
반복된 FAIL을 다른 이름으로 바꾼 뒤 같은 수정 세 번째 시도를 하지 않는다.
현재 diff를 확인하지 않고 파일을 덮어쓰지 않으며, 사용자 승인 없이 복구하지 않는다.
대화 기억·AI 추측보다 SPEC·PLAN·EVIDENCE·실제 출력이 우선이다.
