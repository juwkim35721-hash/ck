# 6.5 시간 부족 시 범위 축소

> 스킬: `$sk-timebox` · 단계: 6-debug 디버깅·복구·시간 관리 · 작업 노트: `sk/work/PLAN.md`, `sk/work/EVIDENCE.md`, `sk/work/SPEC.md` · 사용 자료: 없음

## 언제 쓰나
계획이 지연되어 열린 작업을 모두 완료할 수 없거나, 디버깅·복구로 제출물 위험이 생겼을 때 쓴다.
남은 시간이 15분 이하가 되면 반드시 사용해 새 기능·리팩터링을 멈추고 제출 가능한 최소 상태로 전환한다.
정상 검증만 남은 경우에는 [5.1](../5-verify/5.1-verify.md) (`$sk-verify`)와 [8.2](../8-submit/8.2-deliver.md) (`$sk-deliver`)를 우선한다.

## 준비할 입력
- 현재 시각, 공식 안내에서 확인한 마감 시각, 계산한 남은 시간.
- SPEC의 P0 R#/AC/P#, 필수 제출물 경로·형식, 비목표, T# 표.
- PLAN의 시간 예산·열린 S#·기존 축소 결정·상태 캡슐.
- EVIDENCE의 P0별 최신 PASS/FAIL/미검증 E#.
- 보고서·최종 점검·Q1~Q6 카드의 현재 준비 상태.
- 현재 변경 범위 `git status --short`, `git diff --stat`.

## 전략 — 왜 이렇게 하나
마감 압박에서는 “조금만 더 구현”이 검증·문서·제출 버퍼를 소모해 P0도 불안정하게 만든다.
먼저 P0 동작·필수 제출물·최소 증거·보고서·제출 버퍼를 고정하고, P2부터 명시적으로 잘라낸다.
각 cut은 사용자 영향과 보고서의 사실 기반 한계 문구까지 기록해야, 미구현을 숨기지 않고 제출 준비를 끝낼 수 있다.

## 기본 프롬프트
```text
$sk-timebox
현재 시각은 <시각>, 공식 안내에서 확인한 마감은 <시각 또는 미확인>, 남은 시간은 <분>이다.
SPEC 기준 P0은 <R# 목록>, 필수 제출물은 <경로·형식>, 최소 T#/E# 상태는 <...>이다.
열린 슬라이스는 <S#별 예상 시간·상태>, 기존 축소 결정은 <...>이다.
보고서·최종 점검·Q1~Q6 카드 상태는 <...>, 현재 git 변경 범위는 <...>다.

남은 시간을 구현·수정, 검증·증거, 보고서·제출, 최소 10분 버퍼로 먼저 나눠라.
P0 동작·필수 제출물·최소 검증 E#·보고서·제출 버퍼를 필수 고정 목록으로 제시하라.
열린 S#을 P0/P1/P2, 제출 차단 여부, 예상 분, 증거 상태, cut 영향으로 표에 정리하라.
P2 전체 → P1 부가 기능 → 품질 개선·리팩터링 순서로 완료/최소 구현/보류/cut을 결정하라.
각 cut·보류에는 보고서에 쓸 정직한 한계 문구와 재개 조건을 적어라.
남은 시간이 15분 이하라면 새 기능·새 의존성·리팩터링을 즉시 금지하고 제출 점검 순서만 남겨라.
PLAN.md의 시간 예산·슬라이스 S·축소 결정·상태 캡슐을 갱신하고, P0 테스트를 실제 실행해 E#으로 기록하라.
마지막에 지금 즉시 실행할 다음 스킬 하나를 5.1 verify, 8.1 report, 8.2 deliver 중에서 권고하라.
```

## 심화 프롬프트 — P0 실패와 여러 미완료 작업이 공존함
```text
$sk-timebox
마감 위험이 있다. 현재 <시각>, 남은 시간 <분>, 확보할 제출 버퍼 <분>이다.
P0 요구·수용 기준: <R#/AC/P# 목록>.
필수 제출물: <경로·형식·존재 여부>.
현재 S# 목록: <S# | 우선순위 | 예상 분 | 진행률 | 관련 T# | 최신 E#>.
P0 실패 또는 미검증: <T#/E#와 실제 상태>.
P1/P2 후보: <목록>.
보고서 상태: <...>, 최종 점검 상태: <...>, QA 카드 상태: <...>.

1) 공식 마감이 확인되지 않았으면 단정하지 말고, 사용자가 제공한 남은 시간만 기준으로 계획하라.
2) 버퍼 최소 10분을 먼저 제외하고 구현·검증·문서에 남은 분을 배분하라.
3) P0·필수 제출물·최소 E#를 절대 우선으로 하는 고정 목록을 작성하라.
4) 각 S#을 완료/최소 구현/보류/cut으로 한 번만 분류하고 이유·사용자 영향·보고서 한계 문구를 표에 넣어라.
5) P0 실패가 하나의 원인 후보로 10분 안에 좁혀질 수 있으면 6.1 debug ($sk-debug)에 정확히 10분만 배정하라.
6) P0 실패 원인이 모호한 정책이면 답을 지어내지 말고 G#과 긴급 DM 필요성을 표시하라.
7) 새 기능·리팩터링·화면 다듬기 대신 최신 P0 테스트를 실제 실행하고 E# 결과만 사용하라.
8) PLAN.md의 ## 시간 예산, ## 슬라이스 S, ## 축소 결정, ## 상태 캡슐을 같은 기준 시각으로 갱신하라.
9) 구현 시간 종료 후 5.1 verify ($sk-verify) → 8.1 report ($sk-report) → 8.2 deliver ($sk-deliver)의 순서와 종료 시각을 제시하라.
10) AI 허용 시간에만 9.2 qa-card ($sk-qa-card)를 배치하고, 금지 단계 시작 시 즉시 사용 중단을 명시하라.
```

## 변형 — 남은 시간이 15분 이하임
```text
$sk-timebox
남은 시간은 <분>이며 15분 이하이다.
P0 상태는 <PASS/FAIL/미검증>, 필수 제출물 존재 여부는 <...>, 최신 E#은 <...>이다.
보고서·최종 점검·QA 카드 상태는 <...>이다.

새 기능, 리팩터링, 새 패키지, 대규모 UI 변경을 시작하지 마라.
남은 시간을 P0 핵심 테스트, E# 기록, 필수 제출물 확인, 보고서, 최종 점검, 제출 버퍼 순으로 분 단위 배정하라.
미검증·FAIL·누락을 숨기지 않고 CONDITIONAL 또는 NO-GO가 될 조건을 8.2 deliver ($sk-deliver) 기준으로 제시하라.
PLAN.md의 축소 결정과 상태 캡슐을 갱신하고, 지금 실행할 단일 명령 또는 스킬을 하나만 정하라.
```

## 변형 — 보고서에 한계를 정직하게 반영해야 함
```text
$sk-timebox
다음 기능은 시간 때문에 구현하거나 검증할 수 없게 되었다: <R#/S#/기능>.
현재 P0·필수 제출물·최신 E# 상태는 <...>이고, 사용자 영향은 <...>이다.

미구현과 미검증을 구분해 PLAN.md의 ## 축소 결정 표에 기록하라.
각 항목에 “무엇을 하지 않았는지, 현재 어떤 영향이 있는지, 언제 어떤 조건에서 재개할지”가 드러나는 한계 문구를 작성하라.
8.1 report ($sk-report)에서 실제 증거만 사용하도록 인계하고, 구현하지 않은 기능을 완료라고 표현하지 마라.
```

## 결과물 확인
- 남은 시간과 최소 10분 제출 버퍼가 숫자로 고정되었다.
- P0·필수 제출물·최소 E#이 모든 부가 작업보다 먼저 배치되었다.
- 열린 S# 모두가 완료/최소 구현/보류/cut 중 하나이며 이유·영향·재개 조건이 있다.
- cut·미검증 항목은 보고서 한계 문구와 연결된다.
- P0 테스트의 실제 결과가 E#에 있거나 실행 불가 사유가 기록되었다.

## 다음 단계
구현 시간을 닫으면 [5.1 요구사항 추적 검증](../5-verify/5.1-verify.md) (`$sk-verify`)으로 최신 P0 근거를 채운다.
그 다음 [8.1 보고서 작성](../8-submit/8.1-report.md) (`$sk-report`)과 [8.2 제출 전 최종 점검](../8-submit/8.2-deliver.md) (`$sk-deliver`)으로 간다.
AI 사용이 허용된 제출 전 시간이라면 [9.2 6문항 암기 카드](../9-qa/9.2-qa-card.md) (`$sk-qa-card`)를 준비하고, 금지 단계가 시작되면 즉시 중단한다.

## 주의
마감 압박으로 FAIL·미검증·누락을 PASS처럼 쓰지 않는다.
사용자 승인이나 근거 없이 요구사항 우선순위를 바꾸거나 담당자 정책을 무시하지 않는다.
외부 제출·push·배포·업로드는 실행하지 않으며, 제출 버튼은 사용자가 결정한다.
`sk/` 도구 파일은 수정하지 않고 작업 기록은 `sk/work/`에만 남긴다.
