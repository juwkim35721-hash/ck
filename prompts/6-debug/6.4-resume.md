# 6.4 맥락 복구·작업 재개

> 스킬: `$sk-resume` · 단계: 6-debug 디버깅·복구·시간 관리 · 작업 노트: `sk/work/PLAN.md`, `sk/work/EVIDENCE.md`, `sk/work/SPEC.md` · 사용 자료: 없음

## 언제 쓰나
새 세션, 컨텍스트 압축, 긴 중단 뒤에 이전 대화가 보이지 않거나 현재 S#·테스트 상태를 확신할 수 없을 때 쓴다.
담당자 답변을 기다린 뒤 돌아오거나 다른 작업 후 과제를 이어갈 때도 코드 수정 전에 사용한다.
반복 수정이 이미 문제라면 [6.2](../6-debug/6.2-unstuck.md) (`$sk-unstuck`)를, 확정된 실패 원인 분석은 [6.1](../6-debug/6.1-debug.md) (`$sk-debug`)를 쓴다.

## 준비할 입력
- 과제 루트 위치와 현재 시각·남은 시간.
- `sk/work/SPEC.md`, `sk/work/PLAN.md`, `sk/work/EVIDENCE.md`의 존재 여부.
- 있다면 `sk/work/DM_LOG.md`, `sk/work/REVIEW.md`의 최신 기록.
- `git status --short`, `git diff --stat`, 필요 시 관련 파일 diff.
- 마지막으로 알고 있던 목표·현재 작업. 기억일 뿐이며 문서·실행으로 검증해야 한다.

## 전략 — 왜 이렇게 하나
세션이 바뀌면 대화의 설명은 오래된 코드·테스트 결과를 사실처럼 섞기 쉽다.
따라서 SPEC의 규칙, PLAN의 슬라이스, EVIDENCE의 실행 결과, DM·리뷰의 미해결 사항을 정해진 순서로 읽는다.
그 뒤 가장 작은 기존 테스트 한 번으로 현 상태를 검증하고, 10줄 상태 캡슐에 다음 행동 하나만 남긴다.

## 기본 프롬프트
```text
$sk-resume
세션 전환 또는 컨텍스트 압축 뒤 과제 작업을 안전하게 재개하려 한다.
과제 루트는 <경로>, 현재 시각은 <시각>, 남은 시간은 <분>이다.
이전 기억상 목표는 <기억한 목표>이지만, 이를 사실로 가정하지 마라.
현재 git status/diff 요약은 <있으면 붙여넣기, 없으면 직접 읽기>다.

먼저 sk/work/SPEC.md에서 한 장 요약·Top 5·상태·관련 R/P/A/G/T를 읽어라.
다음으로 PLAN.md의 시간 예산·슬라이스 S·위험 실험·축소 결정·상태 캡슐을 읽어라.
EVIDENCE.md의 마지막 PASS/FAIL/STALE E#과 코드 상태를 읽고, DM_LOG와 REVIEW의 최근 미해결 P#/F#도 확인하라.
그 다음 git status --short와 git diff --stat으로 현재 코드가 기록과 일치하는지 읽기 전용으로 확인하라.
가장 작은 기존 핵심 테스트 또는 명령을 실제로 한 번 실행하고 E#으로 기록하라.
결과를 근거로 다음 행동 하나만 선택하고, PLAN.md의 ## 상태 캡슐을 10줄 이내로 갱신하라.
실패면 6.1 debug, 위험한 diff면 6.3 rollback, 시간 부족이면 6.5 timebox로 인계하라.
```

## 심화 프롬프트 — 노트와 실제 코드 상태가 서로 다름
```text
$sk-resume
기록된 상태와 현재 작업 공간이 다를 수 있으므로 코드 수정 없이 사실을 복구하라.
이전 상태 캡슐: <붙여넣기 또는 없음>.
SPEC 상태·관련 기준: <알면 붙여넣기, 모르면 읽기>.
최신 E#의 PASS/FAIL: <알면 붙여넣기>.
현재 git status: <출력>, diff stat: <출력>.
현재 남은 시간: <분>, 제출 필수물: <알면 붙여넣기>.

1) SPEC에서 목표 1줄, P0, 필수 제출물, Top 5 제약을 먼저 확정하라.
2) PLAN에서 마지막 완료 S#, 진행 중 S#, 멈춘 이유, 기존 축소 결정을 분리하라.
3) EVIDENCE에서 마지막 PASS와 최근 FAIL의 명령·코드 상태를 찾고, 현재 변경과 비교하라.
4) DM_LOG의 최근 P#과 REVIEW의 미해결 F#을 확인해 아직 반영하지 않은 기준을 표시하라.
5) git diff의 추가 파일을 내 변경이라고 단정하지 말고, 기록-현실 불일치 표를 작성하라.
6) 기존 핵심 테스트 하나를 실제 실행해 종료 코드·핵심 결과·현재 코드 상태로 새 E#을 남겨라.
7) 테스트 PASS라도 최신 E# 이후 코드가 바뀌었다면 STALE 후보로 표시하라.
8) 테스트 FAIL이면 구현을 재개하지 말고 6.1 debug ($sk-debug)로 최소 재현을 인계하라.
9) 사용자 변경과 섞였거나 복구가 필요하면 파일을 바꾸지 말고 6.3 rollback ($sk-rollback)의 승인 절차로 인계하라.
10) PLAN.md의 상태 캡슐을 정확히 10줄 이내로 갱신하고 다음 행동 하나만 보고하라.
```

## 변형 — 핵심 테스트를 실행할 환경이 아직 없음
```text
$sk-resume
현재 세션에서 <테스트 명령>을 실행하려 했으나 <서버 미실행/권한/환경 변수/의존성> 때문에 실행할 수 없다.
SPEC·PLAN·EVIDENCE의 최신 상태는 <요약>이고, 현재 git 상태는 <요약>이다.

테스트 결과를 추정하지 말고 실행 불가 원인과 미검증 범위를 E#에 기록하라.
공식 과제 안내에 있는 기존 환경 준비 명령만 확인하고, 패키지 설치·네트워크 사용은 사용자 확인 없이 실행하지 마라.
현재 코드 상태에서 독립적으로 확인 가능한 다음 행동 하나를 정하고 PLAN.md 상태 캡슐에 기록하라.
환경이 필수 차단이면 필요한 사용자 확인을 한 문장으로 제시하라.
```

## 변형 — DM 답변을 받은 뒤 재개함
```text
$sk-resume
중단 중 담당자 답변이 추가되었다. 원문은 다음과 같다: <붙여넣은 담당자 답변>.
기존 PLAN 상태 캡슐은 <...>, 현재 S#/R#/T#는 <...>이다.

답변을 임의로 일반화하지 말고 DM_LOG의 M# 원문과 정책 목록 P#을 먼저 확인·갱신할 필요를 판단하라.
답변이 명세를 바꾸면 1.4 dm-answers ($sk-dm-log)와 2.1 spec ($sk-spec)으로 먼저 인계하라.
명세 변경이 없으면 현재 코드·E#·git diff를 검증해 다음 S# 하나를 선택하고 10줄 상태 캡슐을 갱신하라.
```

## 결과물 확인
- SPEC·PLAN·EVIDENCE를 대화 기억보다 먼저 읽었다.
- DM·리뷰의 최신 미해결 정책·발견을 확인했다.
- 현재 git 상태와 마지막 E#의 코드 상태 일치 여부가 있다.
- 핵심 명령을 실제 실행했거나 불가 사유와 미검증 범위를 E#으로 남겼다.
- PLAN 상태 캡슐은 10줄 이내이고 다음 행동이 하나다.

## 다음 단계
핵심 테스트가 PASS이고 P0 S#가 남으면 [4.0 구현 루프](../4-build/4.0-build-loop.md)의 재개 변형(`$sk-build-loop`)으로 멈춘 단계부터 이어 가거나, [4.2 슬라이스 하나 최소 변경 구현](../4-build/4.2-implement.md) (`$sk-implement`)으로 한 슬라이스를 진행한다.
핵심 테스트가 FAIL이면 [6.1 가설 기반 디버깅](../6-debug/6.1-debug.md) (`$sk-debug`)으로 최소 재현부터 한다.
변경 소유가 불명확하면 [6.3 안전 복구](../6-debug/6.3-rollback.md) (`$sk-rollback`), 마감이 임박하면 [6.5 시간 부족 시 범위 축소](../6-debug/6.5-timebox.md) (`$sk-timebox`)로 간다.

## 주의
대화 요약만 믿고 코드를 수정하지 않는다.
현재 diff를 전부 내 변경이라고 가정하거나, 사용자 승인 없이 되돌리지 않는다.
실행하지 않은 테스트를 PASS로 쓰지 않으며, 비밀값·개인정보를 상태 캡슐·E#에 적지 않는다.
`sk/`는 도구 폴더이므로 과제 코드 수정·테스트 대상에 포함하지 않는다.
