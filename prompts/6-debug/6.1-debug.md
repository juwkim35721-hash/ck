# 6.1 가설 기반 디버깅

> 스킬: `$sk-debug` · 단계: 6-debug 디버깅·복구·시간 관리 · 작업 노트: `sk/work/EVIDENCE.md`, `sk/work/DECISIONS.md` · 사용 자료: 없음

## 언제 쓰나
테스트·빌드·서버·데이터 대사·UI 확인이 실제로 실패했거나, 기대 출력과 다른 결과가 나올 때 쓴다.
특히 [5.1 요구사항 추적 검증](../5-verify/5.1-verify.md), [5.3 데이터 정합성 독립 검산](../5-verify/5.3-data-validation.md), [5.4 API 계약 검증](../5-verify/5.4-api-contract.md)의 E# 실패가 있으면 바로 시작한다.
같은 오류를 두 번 고쳤는데 재발했다면 수정부터 반복하지 말고 이 프롬프트로 가설을 좁힌다.

## 준비할 입력
- 실패한 정확한 명령, 실행한 작업 디렉터리, 종료 코드, 오류 전문 또는 응답 본문.
- 실패를 만든 입력 1건 또는 요청값 1건. 비밀값·개인정보는 마스킹한다.
- 관련 R#/P#/A#/T#와 최근 E#(마지막 PASS, 최근 FAIL).
- 현재 변경 파일 목록과 `git diff --stat` 결과.
- 가능한 경우 같은 실패를 다시 낸 최소 명령 하나.

## 전략 — 왜 이렇게 하나
증상만 보고 여러 파일을 고치면 정책 오류·환경 오류·테스트 기대값 오류가 섞여 시간이 늘어난다.
먼저 수정 전 동일 실패를 최소 재현하고, 서로 다른 계층의 가설 2~3개를 가장 싼 실험으로 반증한다.
원인이 확정된 뒤에만 최소 수정하고, 그 입력을 회귀 테스트로 남겨 재발을 막는다.

## 기본 프롬프트
```text
$sk-debug
<실패한 명령>이 종료 코드 <코드>로 실패했다.
오류 전문 또는 응답 핵심은 다음과 같다: <오류 전문/본문>.
실패 입력·요청은 <마스킹한 입력>이고, 기대값은 <기대>, 실제값은 <실제>다.
관련 기준은 R# <...>, P# <...>, T# <...>이며 최근 증거는 PASS <E#>, FAIL <E#>이다.
과제 루트에서 현재 변경 범위는 <파일 목록>이다.

코드를 바로 수정하지 말고 수정 전 최소 재현 명령을 먼저 실행해 같은 실패인지 확인하라.
가설은 입력/정책 분기/상태·호출/테스트 기대값처럼 서로 다른 계층에서 2~3개만 제시하라.
각 가설마다 근거와 가장 싼 판별 실험, 반증 조건을 표로 제시하고 한 번에 한 변수만 바꿔라.
원인이 확정되면 P#/A#와 공개 인터페이스를 보존하는 최소 수정만 수행하라.
실패 사례를 회귀 테스트로 만들고 재현·관련·가능한 전체 테스트를 실제 실행하라.
EVIDENCE.md의 ## 실행 기록에 E#을 추가하고, AI 생성 코드 결함이 확인된 경우만 DECISIONS.md의 ## AI 교정 기록에 AI#을 남겨라.
결과는 실패 정의, 가설 표, 확정 원인, 수정, 실제 검증, 다음 인계 순서로 보고하라.
```

## 심화 프롬프트 — 실패 원인이 코드·정책·환경 중 불명확함
```text
$sk-debug
지금의 실패를 추측으로 고치지 말고 원인을 판별하라.
실패 명령: <명령>, 작업 디렉터리: <경로>, 종료 코드: <코드>.
오류 전문: <전문 또는 핵심 스택 프레임>.
입력/요청: <마스킹한 값>, 기대: <명세 기반 기대>, 실제: <실제 출력>.
관련 R#: <...>, P#: <...>, A#: <...>, T#: <...>.
마지막 PASS: <E#와 명령>, 최근 FAIL: <E#와 명령>.
현재 git 상태와 변경 파일: <요약>.

1) 최소 재현을 수정 전 상태에서 한 번 실행하고 종료 코드와 핵심 출력을 기록하라.
2) 가설을 최대 3개로 제한하되, 입력 경계·정책 분기·상태/순서·기대값 중 다른 층으로 나눠라.
3) 각 가설에 관찰 근거, 단일 변수 판별 실험, 채택·폐기 조건을 표로 써라.
4) 가장 비파괴적이고 싼 실험부터 실제 실행하고, 결과로 다음 가설을 좁혀라.
5) P#/문서와 테스트가 충돌하면 어느 쪽도 임의 선택하지 말고 G#와 1.3 dm-questions 초안을 제안하라.
6) 원인이 확정된 경우에만 관련 파일·함수의 최소 수정안을 구현하라. 무관한 리팩터링은 금지한다.
7) 실패 입력을 기존 규칙에 맞는 회귀 테스트로 추가하거나, 불가하면 sk/work/ 아래 임시 검증의 이유를 기록하라.
8) 재현 테스트 → 관련 테스트 → 가능한 전체 테스트 순으로 실제 실행하고 결과를 PASS/FAIL/미검증으로만 말하라.
9) E#의 표 열을 지키고, AI 생성 코드의 실제 결함이면 AI#에 문제·발견 E#·수정 지시·확인을 남겨라.
마지막에 5.1 verify ($sk-verify)로 넘길 R→AC→T→E 연결 또는 남은 차단 요인을 1개만 제시하라.
```

## 변형 — API가 5xx 또는 계약과 다르게 응답함
```text
$sk-debug
<메서드> <URL> 요청이 HTTP <실제 상태>와 본문 <요약>을 반환했다.
SPEC.md 10절의 기대 상태·응답 스키마는 <기대 계약>이고, 관련 P#/T#은 <...>이다.
서버 실행 명령과 포트 요구는 <...>, smoke 결과 E#은 <...>이다.

먼저 같은 요청을 최소 재현하고, 라우팅·입력 검증·핵심 로직·오류 매핑 중 어느 계층인지 가설 2~3개로 분리하라.
임의로 바인딩·포트·CORS를 바꾸지 말고, 상태 코드와 본문 스키마를 각각 관찰하라.
원인 확정 뒤 최소 수정과 오류 경로 회귀 테스트를 만들고, 5.4 api-contract ($sk-api-contract)로 계약 재검증을 인계하라.
모든 실제 실행은 E#으로 남기고, 해결되지 않으면 차단 조건만 보고하라.
```

## 변형 — 데이터 집계·행 수 대사가 불일치함
```text
$sk-debug
원본과 결과의 대사에서 <행 수/합계/그룹 수>가 기대 <기대값> 대신 실제 <실제값>이다.
관련 데이터 계약·P#·T#은 <...>이고, 최근 data-validation 증거는 <E#>이다.
원본 데이터는 수정하지 마라.

입력 제외·중복 처리·필터 경계·반올림/단위·정렬 중 서로 다른 가설 2~3개를 세워라.
구현과 독립적인 작은 재계산 또는 단일 레코드 추적으로 가장 싼 가설부터 판별하라.
처리 정책이 문서에 없으면 새 규칙을 발명하지 말고 G#와 1.3 dm-questions ($sk-dm-questions) 초안을 제시하라.
원인 확정 후 최소 수정, 회귀 케이스, 5.3 data-validation ($sk-data-validation) 재검산, E# 기록까지 수행하라.
```

## 결과물 확인
- 수정 전 최소 재현의 실제 결과가 있다.
- 가설은 2~3개이고, 각 가설의 실험과 채택·폐기 근거가 있다.
- 원인 확정 전에는 대규모 수정이나 새 정책을 만들지 않았다.
- 수정했다면 실패 입력의 회귀 테스트와 실제 실행 E#이 있다.
- AI 코드 문제는 실제로 확인된 경우에만 AI#으로 남았다.

## 주의
오류 전문·실행 결과 없이 “아마”라는 수정만 반복하지 않는다.
한 실험에서 코드·입력·환경·기대값을 함께 바꾸지 않는다.
기존 테스트·원본 데이터·제출물을 삭제하지 않으며, 실행하지 않은 결과는 PASS라고 쓰지 않는다.
새 패키지·네트워크·외부 제출은 공식 규칙과 사용자 확인 없이 수행하지 않는다.
