# 1.2 모호성·충돌·누락 탐지

> 스킬: `$sk-ambiguity` · 단계: 요구사항 발굴·담당자 DM · 작업 노트: `sk/work/DISCOVERY.md` · 사용 자료: `sk/snippets/data_audit.py`

## 언제 쓰나

- 1.1에서 요구사항·제약·제출물 후보를 적은 뒤, 담당자 DM의 우선순위를 정하기 전에 사용한다.
- 문서에 “유효”, “적절히”, “정렬”, “오류”처럼 해석 가능한 표현이 있거나 테스트와 문서가 다를 때 사용한다.
- CSV/JSON/JSONL 데이터에서 null, 음수, 중복, 범위가 실제로 관찰되는지 근거를 얻고 싶을 때 사용한다.
- 정책을 확정하거나 구현을 시작하려는 용도로는 사용하지 않는다.

## 준비할 입력

- `sk/work/DISCOVERY.md`의 `## 필수 제출물`, `## 요구사항 후보 R`, `## 제약 C`
- `<과제 문서·샘플·테스트 경로>`
- 있다면 `<CSV/JSON/JSONL 데이터 파일 경로>`
- 공식 문서와 담당자 답변 중 이미 확정된 자료
- 민감값을 가리고 기록할 수 있는 데이터 접근 범위

## 전략 — 왜 이렇게 하나

모호성은 “질문 목록”이 아니라 같은 입력에서 결과가 어떻게 달라지는지를 보여 주는 위험 목록이어야 한다.
문서·샘플·테스트로 먼저 해결하면 담당자 DM을 최소화할 수 있고, H 항목만 남기면 빠른 답을 받기 쉽다.
감사 스니펫의 통계는 정책의 정답이 아니라 실제 데이터에서 질문이 발생할 근거로만 쓴다.

## 기본 프롬프트

```text
$sk-ambiguity
sk/work/DISCOVERY.md의 필수 제출물, R 후보, C를 읽고 <과제 문서·샘플·테스트 경로>와 대조하세요.
용어, 결측·빈 값·타입 오류, 이상치·경계, 중복, 정렬·동점, 수치 형식, 시간, 규칙 충돌, 오류, 출력, 성능, 범위, 보안, 제출 형식의 14개 범주를 점검하세요.
각 모호성은 어떤 입력에서 어떤 두 결과가 달라지는지 작은 예시로 쓰세요.
공식 문서, 샘플, 제공 테스트, 관찰 코드 순으로 자체 해결 가능 여부를 먼저 확인하세요.
자체 해결된 항목은 근거와 함께 닫고, 열린 항목만 G#로 기록하세요.
각 G에 영향도 H/M/L, 근거, 기본안, 처리 방식(DM 질문/가정/자체 해결/보류), 결정 필요 시점을 넣으세요.
정책을 확정하거나 과제 코드·테스트·데이터를 수정하지 마세요.
sk/work/DISCOVERY.md의 ## 모호성 G만 기존 행을 보존하며 갱신하세요.
마지막에 H G부터 DM 후보 1~3개와 자체 해결된 항목을 구분해 보고하세요.
```

## 심화 프롬프트 — 실제 데이터 감사와 문서 충돌을 함께 점검

```text
$sk-ambiguity
다음 근거를 읽기 전용으로 비교해 결과를 바꾸는 빈칸과 충돌만 찾으세요.
- 발견 노트: sk/work/DISCOVERY.md
- 문서·샘플: <문서/샘플 경로>
- 제공 테스트: <테스트 경로>
- 데이터: <CSV/JSON/JSONL 파일 경로>
과제 규칙상 허용되면 먼저 python3 sk/snippets/data_audit.py <CSV/JSON/JSONL 파일 경로>를 실행하세요.
감사에서 null, 음수, 0, 중복, 범위, 범주 상위값을 찾되 민감값은 기록·출력하지 마세요.
감사 스크립트가 CSV/JSON/JSONL만 지원하고 파일 전체를 메모리에 읽으며 숫자 판정이 휴리스틱임을 한계로 기록하세요.
14개 범주를 하나씩 점검하되, 억지 G는 만들지 마세요.
각 G에는 문서 또는 테스트의 정확한 출처, `입력 → 해석 A 결과 / 해석 B 결과`, 영향도, 자체 확인 결과를 넣으세요.
문서와 테스트가 충돌하면 우선순위를 임의로 적용하지 말고 H G와 확인 질문 초안을 만드세요.
현재 데이터에 음수가 없더라도 미래 입력 정책이 비어 있으면 관련 문서·테스트 근거를 추가로 확인하세요.
외부 출력·금액·데이터 손실·제출 실패를 바꾸는 항목은 H로, 구현 내부 선택은 설계로 분리하세요.
각 H G에는 답이 없을 때의 최소 기본안과 되돌릴 지점을 적되 P로 확정하지 마세요.
sk/work/DISCOVERY.md의 ## 모호성 G만 갱신하고, 다음 1.3에서 보낼 질문 우선순위를 제안하세요.
```

## 변형 — null·음수·중복 데이터가 발견된 경우

```text
$sk-ambiguity
<데이터 파일 경로>를 규칙상 허용되는 범위에서 감사하고, 문서·샘플·테스트와 비교하세요.
결측값, 빈 문자열, 숫자 문자열, 음수, 0, 중복 식별자 각각에 대해 현재 근거가 정한 처리와 비어 있는 처리를 구분하세요.
예를 들어 quantity=-2, quantity=null, 같은 id가 2회인 경우에 제외·오류·합산·최신값 선택이 어떤 결과 차이를 내는지 쓰세요.
실제 건수는 질문 근거로 쓰되 원본 행·개인정보·식별자는 노출하지 마세요.
집계값 또는 데이터 손실을 바꾸는 항목은 H로 올리고, 답이 문서에 있으면 G 대신 자체 해결로 남기세요.
sk/work/DISCOVERY.md의 ## 모호성 G에 처리 방식과 결정 필요 시점을 기록한 뒤 1.3용 질문 후보를 3개 이하로 보고하세요.
```

## 변형 — 출력 스키마·동점·시간 경계가 불명확한 경우

```text
$sk-ambiguity
<API/출력 문서 경로>, <샘플 응답 경로>, <테스트 경로>를 비교해 외부 결과의 재현성을 점검하세요.
빈 결과가 []/null/오류 중 무엇인지, 필수·선택 필드, 숫자 소수·반올림, 정렬 방향, 동점 2차 키를 확인하세요.
시작·끝 시각의 포함 여부와 시간대가 없으면 자정 레코드 같은 작은 예시로 결과 차이를 쓰세요.
샘플과 테스트가 다르면 현재 구현 선호로 고르지 말고 충돌 G로 기록하세요.
외부 계약을 바꾸는 G는 H 또는 M으로 분류하고 1.3에서 답하기 쉬운 질문으로 만들 수 있게 선택지를 정리하세요.
sk/work/DISCOVERY.md의 ## 모호성 G만 갱신하고, 설계 판단으로 넘길 항목과 DM 항목을 구분해 보고하세요.
```

## 결과물 확인

- `DISCOVERY.md`의 정확한 `## 모호성 G` 섹션에 G#와 영향도·근거·결과 차이·처리 방식이 있다.
- 14개 범주를 확인했고, 문서로 풀린 사실을 불필요한 DM 후보로 남기지 않았다.
- 데이터 감사는 실제 실행 결과 또는 미실행 이유·도구 한계가 남아 있다.
- H G가 정책으로 확정되지 않았고, 과제 파일은 읽기만 했다.

## 다음 단계

H 우선의 질문을 담당자가 빠르게 답할 수 있게 만들려면 [1.3 담당자 DM 질문 설계](../1-discover/1.3-dm-questions.md)의 `$sk-dm-questions`로 간다.
열린 G가 없고 P0의 수용 기준이 충분하면 [2.1 명세 통합](../2-spec/2.1-spec.md)의 `$sk-spec`로 넘긴다.

## 주의

- `python3 sk/snippets/data_audit.py <파일>`은 CSV·JSON·JSONL만 지원하며 실패 시 통과로 쓰지 않는다.
- 데이터에 값이 있다는 사실과 그 값을 어떻게 처리할지는 별개다. 정책은 담당자·문서 근거가 필요하다.
- 공식 문서와 담당자 답변이 충돌하면 어느 쪽도 조용히 선택하지 말고 G와 확인 질문을 남긴다.
- 과제 원본 데이터, 코드, 테스트, 설정을 이 단계에서 수정하지 않는다.
