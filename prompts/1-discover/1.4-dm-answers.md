# 1.4 담당자 답변 기록·해석·후속 질문

> 스킬: `$sk-dm-log` · 단계: 요구사항 발굴·담당자 DM · 작업 노트: `sk/work/DM_LOG.md` · 사용 자료: `없음`

## 언제 쓰나

- 사용자가 업무 담당자에게 직접 DM을 보낸 뒤, 받은 답변 원문을 Codex에 붙여 넣었을 때 사용한다.
- 선택지 답변, 조건부 답변, 사례 답변, “알아서” 같은 위임, 범위 변경 회신을 정책으로 정리할 때 사용한다.
- 담당자 답변과 문서·기존 테스트·이전 답변이 충돌하는지 확인해야 할 때 사용한다.
- 답변 원문이 없거나, 추측만 있는 상태에서는 사용하지 않는다.

## 준비할 입력

- `<붙여넣은 담당자 답변 원문>`
- 관련 `M#` 또는 `M#-n`과 `sk/work/DM_LOG.md`의 질문 블록
- `sk/work/DISCOVERY.md`의 관련 R/C/G
- `<공식 문서·테스트·샘플 근거 경로>`
- 범위 변경이면 현재 `sk/work/SPEC.md`의 관련 P/A/G

## 전략 — 왜 이렇게 하나

답변 원문을 보존해야 나중에 보고서·테스트·설명에서 근거를 되짚을 수 있다.
정책은 “조건 → 동작”과 예시로 바꿔야 구현자가 답의 범위를 넘겨 해석하지 않고 수용 테스트를 만들 수 있다.
“적절히” 같은 위임은 확정 정책이 아니므로 A로 남기고, 문서 충돌은 G로 다시 열어야 한다.

## 기본 프롬프트

```text
$sk-dm-log
다음 담당자 답변 원문을 관련 <M# 또는 M#-n> 질문과 연결해 처리하세요.
<붙여넣은 담당자 답변 원문>
먼저 sk/work/DM_LOG.md의 해당 M 블록에 원문을 줄바꿈과 의미를 바꾸지 않고 보존하세요.
질문별로 명시 확정, 조건부 답, 사례 답, 위임, 무응답을 구분하세요.
확정 답은 조건 → 동작 형태의 P#로 바꾸고, 작은 예시·M# 근거·영향 R/C/T 후보를 함께 적으세요.
사례에 대한 답은 그 사례 범위만 P로 쓰고, 일반화가 필요하면 G로 남기세요.
“알아서/적절히” 같은 표현은 P로 확정하지 말고 기본안·위험·되돌릴 지점이 있는 A 후보로 기록하세요.
공식 문서·테스트·기존 P와 결과가 다르면 임의 선택하지 말고 G로 재등록하고 후속 질문 초안을 제시하세요.
G 상태를 해결/부분 해결/신규/충돌로 갱신하고, H 영향이 남을 때만 1.3 후속 DM을 권하세요.
과제 파일은 수정하지 말고 DM_LOG의 ## M<n> 블록과 ## 정책 목록 P를 갱신하세요.
마지막에 원문 연결, P, A/G, 영향, 다음 단계 2.1 또는 1.3을 순서대로 보고하세요.
```

## 심화 프롬프트 — 조건부 답과 문서 충돌이 있는 경우

```text
$sk-dm-log
다음 자료를 근거 순서대로 검토해 담당자 답변을 안전하게 정책화하세요.
- 질문 원문: sk/work/DM_LOG.md의 <M#>
- 담당자 답변 원문: <붙여넣은 담당자 답변>
- 공식 문서·샘플: <경로>
- 제공 테스트·현재 관찰: <경로>
- 발견 노트: sk/work/DISCOVERY.md의 관련 R/C/G
답변 원문을 먼저 M 블록에 그대로 보존하고, 응답의 문장별 범위를 질문 번호와 연결하세요.
“음수는 오류지만 빈 값은 제외”처럼 조건이 나뉜 답은 조건마다 P#를 분리하세요.
각 P는 주체·입력 조건·동작·외부 결과를 포함한 `조건 → 동작` 문장과 마스킹된 예시를 갖게 하세요.
답변이 특정 파일·기간·사례만 말했으면 전체 데이터·모든 요청으로 넓히지 말고 일반화 범위를 G로 기록하세요.
문서가 빈 배열을 말하고 답변이 null을 말하는 등 결과가 충돌하면 우선순위를 조용히 적용하지 말고 충돌 G와 짧은 확인 질문을 만드세요.
답변의 “알아서/보통”은 담당자 위임이라는 근거의 A로 기록하고, 외부 계약 영향이 크면 H로 표시하세요.
관련 R/C/T 후보와 코드 위치는 영향으로만 기록합니다. 코드는 수정하거나 테스트를 통과로 주장하지 마세요.
sk/work/DM_LOG.md의 해당 M 블록과 ## 정책 목록 P를 갱신하고, DISCOVERY의 G 상태 변경을 제안하세요.
마지막에 확정 P, 아직 열린 A/G, 재질문 필요성, 2.1 명세 통합 준비도를 표로 보고하세요.
```

## 변형 — 담당자가 선택지 밖의 새 정책을 준 경우

```text
$sk-dm-log
<붙여넣은 담당자 답변>은 M 질문의 A/B/C가 아닌 새 정책을 제시합니다.
답변을 기존 선택지 중 하나로 억지 매핑하지 말고 원문을 M 블록에 보존하세요.
새 정책을 조건 → 동작·예시·M# 근거를 갖춘 P#로 만들고, 출력·오류·정렬 중 답변에 없는 부분은 비워 둔 G로 남기세요.
관련 R/C/T 후보와 기존 P·문서의 충돌 여부를 확인하세요.
새 정책이 범위를 넓히면 비목표·제출물 영향도 표시하되 구현하지 마세요.
H 공백이 남는 경우에만 1.3의 단일 후속 질문을 제안하세요.
```

## 변형 — “알아서 처리하세요”처럼 위임한 경우

```text
$sk-dm-log
<붙여넣은 담당자 답변>이 구체 정책 대신 구현자 판단을 위임했는지 확인하세요.
원문은 M 블록에 그대로 보존하고, 이를 확정 P#로 쓰지 마세요.
문서·샘플·테스트에서 가장 보수적이고 되돌리기 쉬운 기본안을 찾되, 근거와 위험을 분리한 A# 후보로 기록하세요.
예를 들어 데이터 손실·외부 API 변경이 생길 기본안이면 H A로 분류하고 재확인 필요 여부를 표시하세요.
A의 영향을 받는 R/C/T 후보와 되돌릴 지점을 적고, SPEC 통합 시 READY-WITH-ASSUMPTIONS 여부를 알려주세요.
코드·테스트·원본 데이터는 바꾸지 마세요.
```

## 변형 — 답변이 일부만 왔거나 답이 없는 경우

```text
$sk-dm-log
<M#>의 답변 원문에서 답한 질문과 답하지 않은 질문을 분리하세요.
답한 부분만 P# 또는 A#로 처리하고, 미답·모호한 부분은 기존 G를 삭제하지 말고 부분 해결 또는 답변 대기로 갱신하세요.
P0·외부 출력·데이터 손실에 영향을 주는 미답 G만 H 후속 질문 후보로 남기세요.
기다리는 동안 진행할 수 있는 문서 정리와, 답 없이 진행할 경우의 기본안·되돌릴 지점을 구분해 보고하세요.
sk/work/DM_LOG.md의 M 블록과 ## 정책 목록 P만 정확한 근거로 갱신하세요.
```

## 결과물 확인

- 담당자 원문이 해당 `## M<n> …` 블록에 보존됐고, 질문별 해석이 있다.
- P#는 조건 → 동작·예시·M# 근거로 테스트 가능한 형태다.
- 사례 답·위임·무응답이 전체 규칙으로 과장되지 않았고, A/G로 분리됐다.
- 충돌은 숨기지 않고 G와 후속 질문으로 남았으며, 코드는 수정하지 않았다.

## 다음 단계

정리된 P/A/G를 단일 기준 문서로 옮기려면 [2.1 명세 통합](../2-spec/2.1-spec.md)의 `$sk-spec`를 사용한다.
H 영향이 남아 확인이 필요하면 [1.3 담당자 DM 질문 설계](../1-discover/1.3-dm-questions.md)의 `$sk-dm-questions`로 단일 후속 질문을 만든다.

## 주의

- 담당자 답이 공식 문서와 충돌하면 정보 우선순위를 조용히 적용하지 말고 G로 기록해 확인한다.
- 실행하지 않은 테스트, 적용하지 않은 코드 변경을 완료 또는 통과라고 쓰지 않는다.
- 원문 데이터·개인정보·비밀값을 답변 로그에 불필요하게 옮기지 않는다.
- 정책으로 충분히 확정되지 않은 내용은 P가 아니라 A 또는 G다.
