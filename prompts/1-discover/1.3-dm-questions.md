# 1.3 담당자 DM 질문 설계 (DM 템플릿 사용)

> 스킬: `$sk-dm-questions` · 단계: 요구사항 발굴·담당자 DM · 작업 노트: `sk/work/DM_LOG.md` · 사용 자료: `sk/templates/DM_QUESTION_TEMPLATES.txt`

## 언제 쓰나

- 1.2에서 문서·테스트로 해결되지 않은 H 또는 중요한 M `G#`가 1개 이상 남았을 때 사용한다.
- 첫 질문 묶음, 답변 후 남은 한 가지 정책, 구현을 막는 긴급 단일 질문, 사례 적용 확인 질문에 사용한다.
- 사용자가 직접 우측 메신저의 업무 담당자에게 DM을 보내기 직전에 복붙 문구를 만들 때 사용한다.
- 담당자 답변을 해석하거나, 구현 방법·채점 방식을 묻는 단계에는 사용하지 않는다.

## 준비할 입력

- `sk/work/DISCOVERY.md`의 `## 모호성 G`와 관련 R/C/제출물 후보
- 이미 보낸 내용이 있다면 `sk/work/DM_LOG.md`의 최근 M 블록
- `sk/templates/DM_QUESTION_TEMPLATES.txt`의 결측·충돌·정렬 패턴
- `<사용자가 확인한 문서·테스트 근거>`와 마스킹한 실제 조건 예시
- `<현재 모드: 첫 질문 배치/후속/긴급 단일/예시 확인>`

## 전략 — 왜 이렇게 하나

담당자는 긴 분석문보다 한 메시지에서 최대 세 개의 독립적인 선택형 질문에 빠르게 답할 수 있다.
질문에는 상황·실제 조건·A/B(/C)·기본 제안이 있어야 답변이 테스트 가능한 정책이 된다.
문서에 있는 답과 평가·채점 질문을 제거하고 H부터 보내면 DM 한 번이 구현 위험을 가장 크게 줄인다.

## 기본 프롬프트

```text
$sk-dm-questions
sk/work/DISCOVERY.md의 ## 모호성 G와 관련 R/C를 읽고 <현재 모드>의 DM 초안을 만드세요.
먼저 공식 문서·샘플·테스트에 이미 답이 있는 G를 제외하세요.
H 영향부터 고르고, 한 메시지에는 서로 독립적으로 답할 수 있는 질문을 최대 3개만 넣으세요.
각 질문은 상황 1줄, 실제 조건 예시 1줄, A/B(/C) 선택지, 제 기본 제안과 이유, “다른 기준이 있으면 알려주세요”를 포함하세요.
선택지는 결과가 다르고 구현 가능한 동작으로 쓰며, 내부 G/R/P ID와 어려운 기술 용어는 메시지에서 빼세요.
마지막에 `1-A, 2-B처럼 답해주셔도 됩니다.` 형식 안내를 넣고 정중한 존댓말·12줄 이내인지 점검하세요.
sk/templates/DM_QUESTION_TEMPLATES.txt의 세 패턴은 현재 상황에 맞게 변형하되 그대로 복사하지 마세요.
복붙용 최종 메시지를 text 코드블록으로 하나만 제시하고, Codex가 보내지 않으며 사용자가 직접 DM을 보내야 함을 명시하세요.
sk/work/DM_LOG.md에 새 ## M<n> 블록, M#-n→G# 매핑, 발송 대기 상태를 기록하세요.
답변 대기 중 독립적으로 할 작업 2~3개와, 답변 수신 뒤 1.4로 갈 경로를 보고하세요.
```

## 심화 프롬프트 — 데이터·규칙 충돌·정렬을 한 번에 확인하는 첫 DM

```text
$sk-dm-questions
구현 전 담당자에게 보낼 첫 DM을 설계하세요. 입력은 sk/work/DISCOVERY.md의 열린 G와 다음 관찰입니다.
- 데이터 사실: <예: null N건, 음수 N건, 중복 가능성. 민감값은 제외>
- 문서·테스트 근거: <경로 또는 요약>
- 현재 구현을 막는 H G: <G 목록 또는 설명>
질문 후보를 H→P0→M 순으로 평가하고, 문서·테스트에서 이미 명시된 항목과 평가·채점 질문은 버리세요.
답 하나가 여러 G를 해소하더라도 한 질문에는 하나의 정책만 묻고, 최대 세 질문으로 제한하세요.
1번은 결측·음수 등 입력 처리, 2번은 동시 충족 규칙의 우선순위, 3번은 동점·빈 결과·출력 형식 중 실제 열린 항목만 선택하세요.
각 질문은 업무 상황, 마스킹한 실제 값·조건, 배타적인 A/B(/C), 추천안과 이유, 대안 허용 문장을 갖게 쓰세요.
추천안은 데이터 손실·API 호환성·재현성 중 현재 근거가 되는 한 가지 이유만 짧게 쓰세요.
“처리해 주세요”, “적절히”, “어떻게 구현할까요?” 같은 모호한 문구를 선택지에 쓰지 마세요.
한글 존댓말, 인사 포함 12줄 이내, 답변 형식 `1-A, 2-B` 안내를 만족하는 복붙용 DM 하나를 만드세요.
DM 본문에는 ID·파일 경로·코드 구현 용어·민감 데이터·추정한 평가 방식을 넣지 마세요.
sk/work/DM_LOG.md에 M 번호, 목적, 관련 G, 질문 매핑, 메시지, 답변 원문 자리, 상태를 추가하세요.
답변을 기다리는 동안 요구사항 재검토·데이터 사실 확인·A 후보 기록 중 가능한 작업을 구분해 보고하세요.
마지막에 사용자가 직접 DM을 보내고 원문 답변을 붙여 넣으면 1.4를 실행한다고 안내하세요.
```

## 변형 — 구현을 멈추게 하는 긴급 단일 질문

```text
$sk-dm-questions
현재 <구현이 멈춘 지점>은 <한 가지 정책 공백> 때문에 P0 결과를 확정할 수 없습니다.
관련 문서·테스트에서 답이 없는지 먼저 다시 확인하고, 없다면 긴급 단일 DM을 만드세요.
질문은 한 번호만 사용하고, <실제 조건 예시>에서 A와 B가 만드는 결과 차이를 명시하세요.
가장 안전하고 되돌릴 수 있는 기본 제안과 이유를 한 줄로 쓰고 다른 기준도 열어 두세요.
메시지는 인사 포함 6줄 이내, 정중한 존댓말, `1-A` 답변 안내를 갖춰야 합니다.
sk/work/DM_LOG.md에 새 M 블록과 G 매핑을 기록하되, 코드 수정·답변 추정은 하지 마세요.
사용자가 직접 보내야 함과 답변 전 병렬로 가능한 작업을 한 줄씩 보고하세요.
```

## 변형 — 담당자가 “상황에 따라”라고 답한 뒤의 후속 질문

```text
$sk-dm-questions
sk/work/DM_LOG.md의 <이전 M# 답변 원문>과 sk/work/DISCOVERY.md의 남은 G를 읽으세요.
이전 답변의 범위를 넘겨 일반화하지 말고, “상황에 따라”를 가르는 입력 조건 하나만 후속 질문으로 만드세요.
예를 들어 고객 등급·상태·시간 조건 중 실제 문서에 있는 구분을 사용하고, 없는 구분은 발명하지 마세요.
A/B 선택지는 각 조건에서 관찰 가능한 결과로 쓰고, 이전 답을 한 줄만 인용해 맥락을 제공하세요.
5~7줄의 단일 DM과 M#-n→G# 매핑을 sk/work/DM_LOG.md에 추가하세요.
이미 답한 정책을 다시 묻거나 여러 새 질문을 묶지 마세요.
```

## 변형 — 동점·출력 스키마 사례 확인 질문

```text
$sk-dm-questions
<문서/샘플 경로>에서 1차 정렬은 보이지만 동점의 2차 기준 또는 빈 결과 표현이 비어 있습니다.
동점 예시(예: 점수 80인 A와 B) 또는 빈 결과 예시를 하나만 골라 사례 확인 DM을 만드세요.
“이 예시에서 결과가 <A안>인가요, <B안>인가요?”처럼 답하기 쉽게 쓰고, 추천안은 재현성 또는 기존 인터페이스 근거로 한 줄만 제시하세요.
새로운 구현·평가 질문을 섞지 말고, 6줄 이내의 단일 질문과 답변 형식을 만드세요.
sk/work/DM_LOG.md에 새 M 블록과 관련 G를 기록하고, 답변 수신 뒤 1.4에서 정책화할 것을 보고하세요.
```

## 결과물 확인

- 복붙용 DM은 H 우선의 최대 3문항이고, 각 문항이 독립적으로 답할 수 있다.
- 각 문항에 상황·조건 예시·선택지·기본 제안·대안 허용 문장·답변 형식이 있다.
- 내부 ID, 코드 구현법, 평가·채점 질문, 민감값, 문서상 답이 있는 질문이 없다.
- `DM_LOG.md`에는 `## M<n> …` 블록과 M#-n→G# 매핑이 있고, 발송은 사용자가 직접 한다.

## 다음 단계

사용자가 받은 답변 원문을 붙여 넣으면 [1.4 담당자 답변 기록·해석](../1-discover/1.4-dm-answers.md)의 `$sk-dm-log`로 원문 보존과 P# 변환을 한다.
H 가정이 남은 채 구현 직전이라면 [1.5 이해 재진술·최종 확인](../1-discover/1.5-dm-confirm.md)의 `$sk-dm-confirm`으로 짧게 확인한다.

## 주의

- Codex는 DM을 전송할 수 없다. 보내기 버튼을 누르는 것은 사용자 역할이다.
- 답변이 올 때까지 구현하지 않더라도, 독립적인 문서 정리와 데이터 사실 확인은 진행할 수 있다.
- 담당자의 답을 추정해 P#로 쓰지 않는다. 원문을 받으면 1.4에서만 확정·가정·후속 질문으로 분기한다.
- 문서와 담당자 답변이 충돌하면 조용히 선택하지 말고 G로 다시 올린다.
