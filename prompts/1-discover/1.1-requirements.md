# 1.1 요구사항·제약·제출물 추출

> 스킬: `$sk-requirements` · 단계: 요구사항 발굴·담당자 DM · 작업 노트: `sk/work/DISCOVERY.md` · 사용 자료: `없음`

## 언제 쓰나

- 0단계에서 실행 환경과 코드 지도를 확인한 뒤, 구현·설계·DM 전에 사용한다.
- 과제 README, 요구사항 문서, API 명세, 샘플 입출력, 설정 또는 기존 테스트가 있을 때 사용한다.
- 담당자에게 무엇을 물을지 막연할 때, 먼저 문서상 사실과 빈칸을 분리하는 데 사용한다.
- 코드 수정, 패키지 설치, 테스트 추가가 필요한 단계에서는 사용하지 않는다.

## 준비할 입력

- `<과제 README 경로>`와 과제 안내·명세의 경로
- `<샘플 입력/출력 또는 API 스펙 경로>`
- `<기존 테스트 또는 설정 경로>`
- 있으면 `sk/work/BRIEF.md`의 환경·유형·코드 지도
- 공식 안내에서 확인한 제출 경로·파일명·형식 정보

## 전략 — 왜 이렇게 하나

요구를 문장 단위로 쪼개고, 명시 요구와 코드·테스트의 관찰을 구분해야 구현 전에 충돌을 발견할 수 있다.
제출물과 인터페이스 제약을 먼저 확정하면 기능이 맞아도 경로·형식 때문에 실패하는 위험을 줄인다.
답이 없는 문장을 억지로 해석하지 않고 G 후보로 넘겨야 DM이 짧고 정확해진다.

## 기본 프롬프트

```text
$sk-requirements
<과제 README 경로>, <과제 문서 경로>, <샘플/API 스펙 경로>, <테스트·설정 경로>를 읽기 전용으로 조사하세요.
과제 루트 기준으로만 경로를 쓰고 sk/ 폴더는 분석 대상에서 제외하세요.
먼저 필수 제출물의 항목·경로·파일명·형식·출처를 찾으세요. 문서에 없으면 미지정으로 기록하세요.
명시 요구와 테스트·코드에서 관찰한 암묵 요구를 구분해 R# 후보로 추출하세요.
인터페이스 유지, 포트·호스트, 수정 금지 파일, 의존성, 성능, 보안, 제출 형식 제약은 C# 후보로 분리하세요.
각 행에는 실제 파일:줄·문단·테스트명 출처와 관찰 가능한 수용 기준 초안을 넣으세요.
P0/P1/P2는 잠정 후보로만 정하고 이유를 쓰세요.
해석이 둘 이상인 문장은 확정하지 말고 G 후보와 결과 차이를 별도로 제시하세요.
sk/work/DISCOVERY.md의 ## 필수 제출물, ## 요구사항 후보 R, ## 제약 C만 갱신하세요.
과제 파일과 sk/ 도구 파일은 수정하지 마세요.
마지막에 읽은 출처, P0 후보, C, G 후보, 다음 단계 1.2를 순서대로 보고하세요.
```

## 심화 프롬프트 — 문서·테스트·기존 코드가 함께 있는 과제

```text
$sk-requirements
이번 목표는 구현이 아니라 요구사항의 증거 기반 추출입니다. 다음 자료를 읽기 전용으로 비교하세요.
- 문서: <README/과제 문서 경로>
- 인터페이스·샘플: <API 스펙 또는 예제 경로>
- 회귀 근거: <테스트 경로>
- 현재 동작·설정: <코드·설정 경로>
먼저 제출물, 실행 방식, 공개 경로·함수, 출력 스키마, 오류 형식을 별도 목록으로 만드세요.
문서의 명시 요구는 R#, 테스트·코드에서만 보이는 사실은 성격을 관찰로 표시한 R# 후보로 기록하세요.
한 문장에 조건과 동작이 여러 개면 각각 분리하고, 모든 R에는 입력→기대 결과 형태의 수용 기준 초안을 쓰세요.
C#에는 인터페이스 호환, 수정 금지 범위, 포트·호스트, 허용되지 않은 의존성, 성능·보안·제출 형식을 포함하세요.
문서와 테스트의 값·정렬·오류 처리·범위가 다르면 어느 쪽도 임의로 채택하지 말고 G 후보로 분리하세요.
현재 코드가 문서와 달라도 현재 관찰로만 기록하고, 공식 문서 요구를 덮어쓰지 마세요.
제출 경로가 미지정이면 추측 경로를 만들지 말고 D 항목과 G 후보로 남기세요.
sk/work/DISCOVERY.md의 세 지정 섹션만 기존 행을 보존하며 갱신하세요.
보고에는 파일:줄 또는 테스트명 근거를 붙이고, 민감값·토큰·개인정보는 노출하지 마세요.
끝에 P0 후보가 왜 P0인지, DM 전에 더 확인할 출처가 있는지, 1.2에서 볼 G를 표로 요약하세요.
```

## 변형 — 데이터 처리 과제에서 출력 요구가 약한 경우

```text
$sk-requirements
<데이터 과제 문서 경로>, <입력 데이터 설명 경로>, <샘플 결과 경로>, <테스트 경로>를 읽어 요구사항을 추출하세요.
입력 레코드 단위, 집계·필터 조건, 출력 필드·정렬·반올림·빈 결과 표현을 R 후보로 분해하세요.
데이터에 실제로 무엇이 있는지는 정책으로 단정하지 말고 관찰 근거로만 기록하세요.
음수·null·중복·동점·시간 경계의 처리 규칙이 문서에 없으면 G 후보로 분리하세요.
필수 결과 파일의 이름·경로·CSV/JSON 형식이 불명확하면 미지정으로 기록하세요.
각 R에는 작은 입력 예시와 기대 결과 초안을 쓰되, 아직 구현하거나 값을 계산하지는 마세요.
sk/work/DISCOVERY.md의 지정 세 섹션을 갱신하고 1.2로 넘길 H G를 우선순위순으로 보고하세요.
```

## 변형 — API·기존 기능 유지 과제인 경우

```text
$sk-requirements
<API 문서 경로>, <라우트 코드 경로>, <기존 테스트 경로>, <서버 설정 경로>를 읽기 전용으로 조사하세요.
각 공개 엔드포인트·메서드·요청 필드·응답 필드·상태 코드를 제출물 또는 R/C로 구분하세요.
기존 호출자가 기대하는 경로·필드명·오류 형식은 C# 인터페이스 제약으로 기록하세요.
문서와 테스트에서 상태 코드나 빈 결과 표현이 다르면 충돌 G 후보로 만들고 출처를 함께 쓰세요.
호스트·포트·환경 변수는 실제 값의 비밀을 적지 말고 요구 여부와 키만 기록하세요.
sk/work/DISCOVERY.md의 지정 세 섹션만 갱신한 뒤, P0 호환성 제약과 다음 1.2 점검 항목을 보고하세요.
```

## 결과물 확인

- `DISCOVERY.md`에 `## 필수 제출물`, `## 요구사항 후보 R`, `## 제약 C`가 정확한 제목으로 있다.
- 각 행에 출처가 있고, R은 명시/관찰이 구분되며 C는 요구와 섞이지 않았다.
- 제출물 미지정, 문서·테스트 충돌, 해석 갈림이 숨지 않고 G 후보로 분리됐다.
- 과제 코드·테스트·설정·원본 데이터와 `sk/` 도구 파일은 수정되지 않았다.

## 주의

- 공식 안내가 최우선이지만, 확인하지 못한 대회 규정을 사실처럼 쓰지 않는다.
- “테스트가 이렇게 한다”는 관찰과 “반드시 이렇게 해야 한다”는 요구를 구별한다.
- 담당자 DM은 다음 단계에서 사용자가 직접 보낸다. 여기서는 질문을 만들거나 전송하지 않는다.
- 불명확한 정책은 기본 동작을 발명하지 말고 G 후보로 남긴다.
