# 1.0 질의 루프 — 전체 스캔·DM·후속 질문 반복

> 스킬: `$sk-clarify-loop` · 단계: 요구사항 발굴·담당자 DM · 작업 노트: `sk/work/DISCOVERY.md`, `sk/work/DM_LOG.md` · 사용 자료: `sk/templates/DM_QUESTION_TEMPLATES.txt`, `sk/snippets/data_audit.py`

## 언제 쓰나

- 0.1 context 직후, 발굴(1.1~1.5)을 한 흐름으로 돌리고 싶을 때 쓴다. 1.1 → 1.2 → 1.3 → 1.4 → 1.5를 하나씩 호출하는 대신 이 프롬프트 하나로 라운드를 반복한다.
- 담당자 답변이 올 때마다 붙여 넣어, 해석 → 영향 재스캔 → 파생 질문 → 다음 DM까지 한 번에 받고 싶을 때 쓴다.
- 명세 동결 뒤 구현 중 결과를 바꾸는 새 모호성이 생겼을 때 질문 1개로 재진입한다.
- 루프가 닫히면 2.1 spec부터는 기존 순서(2.1 → 2.2 → 2.3 → 2.4)를 따른다.

## 준비할 입력

- 현재 시각 또는 시작 후 경과 시간 (첫 DM 목표 10:22, 동결 목표 10:40은 예시)
- `sk/work/BRIEF.md`가 있으면 그대로 (0.1·0.2·0.3 결과)
- 담당자 답변을 받았다면 **원문 그대로** (요약하거나 고치지 않는다)
- 이미 루프를 진행했다면 `sk/work/DM_LOG.md`의 `## 질의 루프 상태판`

## 전략 — 왜 이렇게 하나

한 번에 완벽한 질문 목록을 만들 수는 없다. 담당자의 답 하나가 새 경계(0은?), 새 적용 범위(다른 필드도?), 새 충돌(기존 테스트는 반대 기대)을 만든다. 그래서 질문을 **라운드**로 나누고, 답이 올 때마다 그 규칙의 키워드로 과제 전체를 다시 검색해 파생 모호성을 찾는다.

동시에 담당자 시간과 대회 시간은 한정돼 있다. 라운드당 메시지 1개·질문 3개, 질문 라운드 최대 3회, 확인 1회로 상한을 두고, 새로 나온 모호성이 모두 M/L이면 질문을 멈춘다. 상태판의 "열린 H" 숫자가 0이 되는 것이 목표다. 시간이 다 되면 남은 것을 되돌릴 지점이 있는 가정으로 바꿔 닫는다.

## 기본 프롬프트 — 라운드 0: 전체 스캔과 첫 DM

```text
$sk-clarify-loop
라운드 0을 시작해줘. 현재 시각은 <시각>이야.
과제 루트 전체를 스캔해. sk/, .git, .agents, .codex, 의존성 폴더는 빼고, AGENTS.md는 SK-KIT 관리 구역 밖만 과제 지시로 봐.
1) 파일 인벤토리를 만들고 파일마다 역할(문서/데이터/테스트/진입점/핵심 코드/설정 등)과 읽기 깊이(정독/훑음/목록만/제외+사유)를 정해.
   문서·테스트·진입점·미구현 흔적·실행 설정은 반드시 정독하고, CSV·JSON·JSONL은 python3 sk/snippets/data_audit.py로 수치를 확인해.
2) TODO·미구현 흔적, 요구 표현(반드시·금지·형식·정렬·반올림·null·오류·포트), 테스트 기대값을 검색해.
3) 요구사항 R·제약 C·필수 제출물을 파일:줄 출처와 함께 뽑고, 14개 범주로 모호성 G를 찾아 결과 차이 예시와 H/M/L을 붙여.
4) 문서·샘플·테스트·코드로 스스로 답할 수 있는 G는 먼저 닫아.
5) 남은 G 중 담당자 정책 질문만 골라, H부터 최대 3문항의 첫 DM을 sk/templates/DM_QUESTION_TEMPLATES.txt 패턴을 실제 상황에 맞게 바꿔 만들어.
sk/work/DISCOVERY.md(스캔 커버리지 포함)와 sk/work/DM_LOG.md(질의 루프 상태판, M1 블록)에 기록해.
코드·테스트·데이터는 수정하지 마. DM은 내가 직접 보낼 테니 복붙용 메시지 1개만 줘.
```

## 라운드 프롬프트 — 담당자 답변을 붙여 넣을 때

```text
$sk-clarify-loop
담당자 답변이 왔어. 아래는 원문 그대로야. 현재 시각은 <시각>이야.
---
<담당자 답변 원문>
---
1) 어느 M#에 대한 답인지 확인하고 원문을 DM_LOG의 해당 M 블록에 그대로 보존해.
2) 질문별로 명시/조건부/사례/위임/무응답/선택지 밖/충돌로 분류하고, 확정된 것은 "조건 → 동작" + 예시 + 근거 M#의 P로 바꿔.
3) 새 P마다 필드명·상태값·경로·용어로 과제 전체를 다시 검색해, 같은 규칙이 적용될 다른 위치, 반대로 기대하는 테스트·문서, 바뀌는 출력 필드를 찾아.
4) 답변마다 파생 7점검(경계, 적용 범위, 출력 표현, 집계 영향, 규칙 순서, 예외, 시점)을 하고, 결과가 달라지고 문서에 답이 없는 것만 새 G로 등록해.
5) 상태판을 갱신하고 계속/확인/종료/차단 중 하나로 판정해. 판정 이유를 숫자(열린 H, 예산)로 말해줘.
6) 계속이면 다음 DM(최대 3문항), 확인이면 재진술 확인 DM, 종료면 구현 기준 요약을 줘.
답을 추측하지 말고, 코드는 수정하지 마.
```

## 짧은 라운드 프롬프트 — 답변만 바로 붙여 넣을 때

스킬이 위 절차를 모두 담고 있으므로 다음처럼만 입력해도 같은 라운드가 진행된다. 시험 중에는 이 형식이 가장 빠르다.

```text
$sk-clarify-loop
답변 원문:
<담당자 답변 원문>
```

## 마감 프롬프트 — 루프를 닫고 구현할 것을 정리할 때

```text
$sk-clarify-loop
질의 루프를 마감해줘. 현재 시각은 <시각>이야.
상태판과 DISCOVERY.md의 모든 G를 다시 보고 "닫힘 정의"를 항목별로 점검해: 열린·질문 중·충돌 H 0개, 모든 P에 조건 → 동작·예시·근거, 문서↔P 충돌 0개, P0 R마다 기대 출력을 손계산할 수 있는지.
남은 G는 가정 전환(기본안 + 근거 + 위험 + 되돌릴 지점) 또는 범위 밖·보류로 정리해.
그다음 구현 기준 요약을 만들어: P0 R마다 "입력 → 처리 규칙(P/가정) → 출력" 한 줄, 필수 제출물 목록, 지켜야 할 제약 C, 남은 가정과 되돌릴 지점.
마지막으로 2.1 spec → 2.2 io-contract → 2.3 acceptance → 2.4 spec-gate로 넘길 때 각 단계가 볼 핵심 항목을 알려줘.
코드는 아직 수정하지 마.
```

## 변형 — 답이 늦거나 오지 않을 때

```text
$sk-clarify-loop
M<n>을 보낸 지 <분>분이 지났는데 답이 없어. 현재 시각은 <시각>, 동결 목표는 <시각>이야.
재촉 메시지는 만들지 마.
1) 답에 의존하지 않고 지금 할 수 있는 작업(2.2 데이터 계약, 0.3 코드 지도 보강, R·C 정리)을 골라줘.
2) 질문 중인 G마다 기본안, 그 근거, 틀렸을 때의 위험, 되돌릴 지점(파일·함수·조건)을 미리 적어 둬.
3) 동결 목표까지 답이 없으면 어떤 G를 가정 전환하고, 어떤 G가 차단 사유인지(필수 제출물·P0 출력 형식) 구분해줘.
상태판에 대기 상태와 이 계획을 기록해.
```

## 변형 — 답변이 문서·테스트와 충돌할 때

```text
$sk-clarify-loop
방금 반영한 답변이 <문서 또는 테스트 경로>와 충돌하는 것 같아.
충돌을 조용히 해결하지 말고, 양쪽 원문(답변 인용, 파일:줄)과 각각을 따랐을 때의 결과 차이를 구체 예시로 적어줘.
충돌 G를 H로 재오픈하고, 담당자에게 "문서에는 X라고 되어 있는데 말씀하신 Y가 우선일까요?" 형태의 단일 확인 질문을 만들어줘.
답이 오기 전까지 어떤 쪽을 기본안으로 둘지와 그 이유(공식 문서 우선 원칙, 되돌리기 쉬움)를 기록해.
```

## 변형 — 동결 후 구현 중 새 모호성이 생겼을 때

```text
$sk-clarify-loop
명세 동결 뒤 구현 중에 새 모호성이 생겼어: <상황, 관련 파일·함수, 결과가 달라지는 예시>.
먼저 문서·테스트·데이터·기존 P로 답할 수 있는지 확인하고, 있으면 질문하지 말고 근거를 알려줘.
없으면 영향도를 매겨. H면 단일 질문 1개를 6줄 이내로 만들고 라운드를 R<n>(동결 후)로 기록해. M/L이면 질문하지 말고 가정 전환으로 기록해.
답이 오면 SPEC.md 13절 변경 기록과 영향받는 T#를 먼저 고쳐야 한다는 인계를 남겨줘.
진행 중인 구현 코드는 이 단계에서 고치지 마.
```

## 변형 — 세션이 끊긴 뒤 이어서 진행할 때

```text
$sk-clarify-loop
세션이 바뀌었어. sk/work/DM_LOG.md의 질의 루프 상태판, M 블록, 정책 목록 P와 sk/work/DISCOVERY.md의 G 표를 읽고 현재 라운드와 판정을 복원해줘.
보낸 메시지 중 답변 원문이 비어 있는 M#, 질문 중인 G, 남은 예산(라운드·누적 질문·동결 목표)을 요약해.
상태판과 실제 기록이 어긋나면 기록을 기준으로 상태판을 고치고 무엇을 고쳤는지 알려줘.
다음에 내가 할 일(답변 붙여넣기, DM 전송, 마감)을 한 줄로 알려줘.
```

## 결과물 확인

- `DISCOVERY.md`의 `## 스캔 커버리지`에 제외 대상을 뺀 모든 파일(또는 묶음)의 역할·깊이가 있고, 제외에는 사유가 있다.
- `DM_LOG.md` 맨 위 `## 질의 루프 상태판`에 라운드별 질문 수·새 P·신규 G·열린 H·판정이 있다.
- 모든 답변 원문이 M 블록에 보존됐고, P마다 조건 → 동작·예시·근거 M#가 있다.
- 파생 G에는 어느 답변에서 나왔는지(`파생 M<n>-k`)와 결과 차이 예시가 있다.
- 마감 시 `현재 구현 기준`에 P0 R별 입력 → 규칙 → 출력이 한 줄씩 있다.

## 주의

- Codex는 DM을 보낼 수 없다. 메시지를 보내고 답변 원문을 붙여 넣는 것은 사용자 역할이다.
- 답이 오지 않았는데 예상 답으로 다음 라운드를 진행하지 않는다.
- 라운드당 메시지 1개, 질문 3개, 질문 라운드 3회, 누적 질문 9개가 상한이다. 담당자 시간을 아낀다.
- 루프 중에는 과제 코드·테스트·데이터를 수정하지 않는다. 구현은 2.4에서 READY 계열 판정을 받은 뒤 시작한다.
