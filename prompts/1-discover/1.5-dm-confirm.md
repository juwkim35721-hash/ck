# 1.5 이해 재진술·최종 확인 메시지

> 스킬: `$sk-dm-confirm` · 단계: 요구사항 발굴·담당자 DM · 작업 노트: `sk/work/DM_LOG.md`, `sk/work/SPEC.md` · 사용 자료: `없음`

## 언제 쓰나

- 구현 시작 직전, 담당자 답변이 여러 개이거나 H 영향 가정이 남아 이해를 한 번에 확인하고 싶을 때 사용한다.
- 범위 변경, 출력 형식 변경, 예외 처리 변경이 생겨 기존 이해를 다시 맞춰야 할 때 사용한다.
- 2.4 명세 게이트에서 READY-WITH-ASSUMPTIONS가 될 수 있는 A를 담당자에게 짧게 확인할 때 사용한다.
- 처음 정책을 묻는 DM, 이미 확정된 세부사항을 반복하는 DM에는 사용하지 않는다.

## 준비할 입력

- `sk/work/DM_LOG.md`의 최근 M 블록과 `## 정책 목록 P`
- `sk/work/DISCOVERY.md`의 열린 H G와 기본안
- 존재하면 `sk/work/SPEC.md`의 `## 5. 확정 정책 P`, `## 6. 가정 A`, `## 7. 열린 모호성 G`
- `<구현 범위와 출력 핵심>`
- `<이번 메시지에서 확인할 H 가정 또는 범위 변경>`

## 전략 — 왜 이렇게 하나

첫 질문은 빈칸을 발견하는 용도이고, 최종 확인은 확정된 정책의 공통 이해를 검증하는 용도다.
핵심 규칙 3~5개와 H 가정만 평이하게 재진술하면 담당자가 짧은 메시지로 오해를 잡아 줄 수 있다.
답이 없더라도 A와 되돌릴 지점을 남기면 해커톤 시간을 모두 대기에 쓰지 않고 안전하게 명세 게이트로 갈 수 있다.

## 기본 프롬프트

```text
$sk-dm-confirm
sk/work/DM_LOG.md의 최근 답변과 ## 정책 목록 P, sk/work/DISCOVERY.md의 열린 H G를 읽으세요.
존재하면 sk/work/SPEC.md의 ## 5. 확정 정책 P, ## 6. 가정 A, ## 7. 열린 모호성 G와 대조하세요.
최종 확인이 필요한지 먼저 판단하고, 불필요하면 이미 확정되어 DM 생략 가능하다고 보고하세요.
필요하면 목표 1줄, P0/H 관련 확정 정책 3~5개, 출력 형식 핵심, 비목표 1~2개를 평이한 한국어로 재진술하세요.
아직 열린 H 가정은 `이렇게 진행해도 될까요?`라는 한 문장으로 명시 확인을 요청하세요.
새 정책 질문·내부 ID·파일 경로·구현 기술·평가 질문은 넣지 말고, 인사 포함 10줄 이내로 만드세요.
복붙용 최종 메시지를 text 코드블록으로 하나만 제시하고 Codex가 보내지 않으며 사용자가 직접 DM을 보내야 함을 안내하세요.
sk/work/DM_LOG.md에 새 ## M<n> 블록과 포함 P/A/G 매핑, 답변 원문 자리, 발송 대기 상태를 기록하세요.
답변이 오면 1.4에서 P 승격, 답이 없으면 A와 되돌릴 지점을 유지해 2.4 게이트로 가는 경로를 보고하세요.
과제 파일·테스트·원본 데이터는 수정하지 마세요.
```

## 심화 프롬프트 — 여러 정책과 한 개의 H 가정을 구현 전 동기화

```text
$sk-dm-confirm
구현 착수 전 이해 동기화 DM을 만들되, 새로운 정책을 물어보는 메시지로 바꾸지 마세요.
근거는 sk/work/DM_LOG.md의 P#, 최근 담당자 원문, sk/work/DISCOVERY.md의 열린 G, sk/work/SPEC.md의 P/A/G입니다.
공식 문서와 P가 충돌하면 메시지로 덮지 말고 먼저 G와 1.3 후속 질문이 필요하다고 보고하세요.
목표를 업무 결과로 한 줄 작성하고, P0·외부 결과·데이터 처리와 직접 연결된 정책만 3~5개 선택하세요.
선택한 정책은 “값이 비면 제외”, “취소면 집계 제외”, “동점이면 ID 오름차순”처럼 구현 용어 없이 평이하게 바꾸세요.
출력 형식은 결과 종류·빈 결과·정렬 중 이미 확정된 사실만 한 줄로 씁니다.
이번 범위에서 하지 않는 일 1~2개를 구체화해 추가 범위 오해를 막으세요.
아직 H인 <가정>은 기본안·영향을 한 문장으로 쓰고 `이렇게 진행해도 될까요?`로 확인을 요청하세요.
동일 사실을 재질문하거나 선택지를 새로 만들지 말고, 수정이 필요하면 알려 달라는 열린 문장만 둡니다.
인사 포함 10줄 이하의 정중한 복붙용 DM 하나를 text 코드블록으로 제시하세요.
sk/work/DM_LOG.md에 M 블록, 포함 P/A/G, 발송 대기, 원문 자리와 답변 후 1.4 처리 경로를 기록하세요.
답변이 없을 때의 A·되돌릴 지점·2.4 게이트 영향도 함께 짧게 보고하세요.
```

## 변형 — 시간대·경계 기준만 H 가정으로 남은 경우

```text
$sk-dm-confirm
현재 정책은 대부분 확정됐고, <시간대 또는 기간 경계>만 H 가정으로 남아 있습니다.
확정된 목표와 핵심 정책은 최대 3개만 재진술하고, 결과 형식·비목표를 각 한 줄로 쓰세요.
자정의 <마스킹한 예시>에서 결과가 달라짐을 짧게 설명한 뒤, <기본 시간대/경계안>으로 진행해도 되는지 한 문장으로 확인하세요.
새 A/B 선택지를 만들거나 이미 답한 데이터 처리·정렬을 다시 묻지 마세요.
6~8줄의 정중한 DM과 DM_LOG의 새 M 블록을 만들고, 무응답 시 A를 유지할 되돌릴 지점을 보고하세요.
```

## 변형 — 범위 축소를 공유하며 확인하는 경우

```text
$sk-dm-confirm
남은 시간 때문에 <제외할 P1/P2 기능>을 이번 구현 범위에서 제외해야 하는지 확인하는 DM을 만드세요.
기존 P0 목표와 반드시 제공할 출력은 한 줄씩 명시하고, 제외 대상과 포함하지 않는 이유를 평이하게 쓰세요.
담당자가 이미 확정한 정책을 다시 묻지 말고, 범위 축소가 허용되는지 또는 더 우선할 기능이 있는지만 짧게 확인하세요.
데이터 수정·제출·평가 방식은 추정하지 말고, 8줄 이내 정중한 메시지와 M 블록을 작성하세요.
답변 전에는 변경하지 않으며, 답변 수신 시 1.4·2.4에서 반영할 경로를 보고하세요.
```

## 변형 — 확인 DM이 불필요한 경우

```text
$sk-dm-confirm
sk/work/DM_LOG.md와 sk/work/SPEC.md를 검토해 P0와 H 항목이 모두 확정됐는지 판정하세요.
열린 H G나 외부 결과를 바꾸는 A가 없고 범위 변경도 없다면 담당자에게 중복 DM을 만들지 마세요.
대신 확인 DM 생략 근거, 이미 확인된 M#/P#, 바로 2.4 게이트로 갈 수 있는 이유를 짧게 보고하세요.
낮은 영향의 A가 있으면 A·위험·되돌릴 지점을 남기되 P로 승격하지 마세요.
과제 파일은 수정하지 말고 DM_LOG와 SPEC의 기존 기록을 보존하세요.
```

## 결과물 확인

- 최종 DM에는 목표 1줄, 핵심 정책 3~5개, 출력 핵심, 비목표, H 가정 확인 요청이 있다.
- 메시지는 10줄 이내의 존댓말이고 내부 ID·기술 구현·평가 질문·민감값이 없다.
- 새 정책 질문이 섞이지 않았고, 이미 확정된 사실을 장황하게 반복하지 않았다.
- `DM_LOG.md`에 새 M 블록과 P/A/G 매핑이 있고, 사용자가 직접 발송한다는 점이 명확하다.

## 다음 단계

답변을 받으면 [1.4 담당자 답변 기록·해석](../1-discover/1.4-dm-answers.md)의 `$sk-dm-log`로 원문을 보존하고 A를 P로 승격한다.
확정·가정·열린 G를 구현 기준으로 동결하려면 [2.4 구현 착수 게이트](../2-spec/2.4-spec-gate.md)의 `$sk-spec-gate`를 실행한다.

## 주의

- 담당자가 확인하지 않은 A를 확정 P처럼 말하지 않는다.
- 담당자 답변이 공식 문서와 충돌하면 재진술 메시지로 숨기지 말고 1.3의 확인 질문으로 분리한다.
- 답변을 기다리는 동안에도 독립적인 명세 정리는 할 수 있으나, H 정책을 코드로 구현하지 않는다.
- Codex가 DM을 전송하거나 답변을 만들어 낸 것처럼 기록하지 않는다.
