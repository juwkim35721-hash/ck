# 0.2 과제 유형 판별·공략 경로 선택

> 스킬: `$sk-triage` · 단계: 착수 — 환경·과제 유형·코드 지도 · 작업 노트: `sk/work/BRIEF.md#과제 유형·전략` · 사용 자료: `없음`

## 언제 쓰나
- 0.1에서 과제 루트와 실행 환경을 확인한 뒤, 구현 전에 과제의 중심 유형을 정할 때 쓴다.
- 데이터 처리, API, UI, 기존 코드 수정, CLI·알고리즘이 섞여 있어 무엇을 먼저 할지 판단해야 할 때 쓴다.
- 문서와 코드의 목표가 어긋나 보일 때도 판정을 보류하고 다음 확인 경로를 정하는 데 쓴다.
- R/C를 완전 추출하거나 함수 호출을 상세 추적하는 작업에는 사용하지 않는다.

## 준비할 입력
- 환경 기록: `sk/work/BRIEF.md#환경`
- 과제 문서·README·샘플 입출력: `<경로 또는 없음>`
- 관찰한 디렉터리·실행 스크립트·테스트 위치: `<경로 또는 없음>`
- 남은 시간: `<예: 95분>`
- 이미 보이는 모호성 또는 담당자에게 물을 후보: `<있으면 간단히, 없으면 없음>`

## 전략 — 왜 이렇게 하나
유형을 하나로 단정하면 API 계약, 데이터 정합성, UI 오류 상태, 회귀 위험 중 하나를 놓치기 쉽다.
그래서 A~E 모두를 근거로 판정하고, 주 유형에는 필수 검증 경로를, 보조 유형에는 놓치면 큰 위험을 연결한다.
이 단계의 시간 예산은 확정 계획이 아니라 발견·명세·P0 구현·검증·제출 버퍼를 보호하는 초안이다.
H 영향 모호성은 구현 후가 아니라 발견 단계에서 DM 또는 가정 관리로 넘긴다.

## 기본 프롬프트
```text
$sk-triage
sk/work/BRIEF.md#환경을 읽고, <문서 경로들>과 <관찰한 코드·테스트 경로들>을 읽기 전용으로 확인하라.
과제의 한 문장 목표를 문서의 동사를 유지해 적고, A 데이터 처리·집계, B API·백엔드 규칙, C 풀스택·UI, D 기존 기능 유지, E CLI·알고리즘을 각각 주/보조/해당 없음/보류로 판정하라.
각 판정에는 문서 또는 파일:줄 관찰 근거를 붙이고 파일명만으로 정책·채점 방식을 단정하지 마라.
주 유형 1개와 보조 유형 0~2개를 선택하고, 유형별 핵심 위험을 구체적으로 적어라.
공통 다음 경로인 1.1, 1.2, 2.1, 2.3과 유형별 필수 ID를 정확한 스킬 이름으로 연결하라.
A면 2.2와 5.3, B면 2.2와 5.4, C면 0.3과 5.5, D면 0.3·4.1·5.1, E면 2.3·4.1·5.1을 빠뜨리지 마라.
H 영향 모호성이 보이면 첫 DM을 보낼 시점과 1.3 dm-questions를 제안하고, 평가 방식만 묻는 질문은 만들지 마라.
남은 시간 <시간>을 기준으로 발견·명세, P0 구현, 검증, 보고·QA, 최소 10분 제출 버퍼의 초안 예산을 세워라.
sk/work/BRIEF.md의 ## 과제 유형·전략만 정해진 두 표와 첫 DM 시점·다음 행동 줄로 갱신하라.
코드·테스트·설정·데이터를 수정하지 말고, 마지막에는 판정·위험·필수 경로·시간·다음 행동을 6개 번호로 보고하라.
```

## 심화 프롬프트 — 복합 과제와 시간 압박을 함께 다룰 때
```text
$sk-triage
<과제 루트>에서 환경 기록과 <문서 경로들>, <코드·테스트 경로들>을 근거로 복합 과제 트리아지를 수행하라.
먼저 문서에서 확인되는 목표·제출물·입력·출력·기존 인터페이스 단서를 분리하고, 관찰과 추측에 서로 다른 표시를 하라.
A~E 유형마다 긍정 증거와 반증 또는 미확인 근거를 한 줄씩 수집하라.
데이터 파일·집계·반올림 단서가 있으면 A의 결측·중복·대사 위험을, HTTP·라우트 단서가 있으면 B의 상태 코드·오류 스키마·호환성 위험을 명시하라.
화면·폼·브라우저 상태가 있으면 C의 정상·빈·오류 흐름을, 기존 실패·공개 함수가 있으면 D의 회귀·변경 범위를, 입력 크기·정렬 제한이 있으면 E의 경계·복잡도·결정성을 명시하라.
주 유형은 제출물과 P0 결과에 가장 직접적인 근거로 고르고, 나머지는 보조 또는 보류로 둬라.
공통 필수 경로는 1.1 requirements, 1.2 ambiguity, 2.1 spec, 2.3 acceptance로 잡아라.
유형 전용 경로는 A: 2.2·5.3, B: 2.2·5.4, C: 0.3·5.5, D: 0.3·4.1·5.1, E: 2.3·4.1·5.1을 정확히 연결하라.
문서만으로 해결되지 않는 H 영향 모호성에는 1.3 dm-questions를, 문서와 코드가 충돌하는 경우에는 1.2 ambiguity의 G 등록을 먼저 제안하라.
남은 시간 <시간> 중 제출 버퍼 10분과 검증 약 15%를 먼저 확보하고, P2→P1 일부→품질 개선 순으로 축소 후보를 적어라.
sk/work/BRIEF.md의 ## 과제 유형·전략에서 유형 | 판정 | 근거(문서·파일:줄) | 주요 위험 | 필수 다음 ID | 최소 경로 표와 시간 예산 표만 갱신하라.
코드나 설정을 바꾸지 말고, 마지막 보고에서는 불확실한 항목을 확정처럼 표현하지 마라.
```

## 변형 — 데이터 파일과 API가 함께 있는 경우
```text
$sk-triage
<과제 루트>의 문서·데이터 경로 <데이터 경로들>·API 경로 <API 경로들>을 읽어 A와 B 복합 유형을 판정하라.
각 유형의 근거를 분리하고, 최종 제출물이 배치 결과인지 HTTP 응답인지에 따라 주 유형을 선택하라.
A에는 결측·중복·단위·원본/결과 행 수 대사 위험과 2.2 io-contract·5.3 data-validation을 반드시 연결하라.
B에는 메서드·경로·상태 코드·오류 스키마·기존 인터페이스 위험과 2.2 io-contract·5.4 api-contract를 반드시 연결하라.
두 흐름 사이에서 데이터 정책이 달라질 여지가 있으면 1.2 ambiguity를 먼저 제안하고, H 영향 질문이 있으면 1.3을 제안하라.
sk/work/BRIEF.md의 ## 과제 유형·전략만 갱신하고, 구현·테스트 실행·데이터 수정은 하지 마라.
```

## 변형 — 남은 시간이 30분 이하인 경우
```text
$sk-triage
남은 시간은 <30분 이하 시간>이다. <문서 경로들>과 환경 기록을 근거로 유형을 빠르게 판정하라.
주 유형 하나와 반드시 보존할 보조 위험 하나만 고르고, P0·필수 제출물·최소 검증 증거·10분 제출 버퍼를 먼저 고정하라.
P2, P1 일부, 시각적·구조적 개선의 순서로 축소 후보를 명시하라.
문서로 해결되지 않는 H 영향 모호성은 구현 전 짧은 DM이 필요한지 판단하되, 답을 기다리느라 다른 발견 작업을 멈추지 마라.
sk/work/BRIEF.md의 ## 과제 유형·전략만 갱신하고, 다음 첫 행동을 1.1 requirements 또는 0.3 code-map 중 하나로 정확히 제시하라.
```

## 결과물 확인
- [ ] A~E 모두가 주/보조/해당 없음/보류 중 하나로 판정되었다.
- [ ] 주·보조 판정은 문서·파일:줄 관찰 근거를 갖는다.
- [ ] 주 유형에 맞는 2.x·4.x·5.x 필수 프롬프트 경로가 있다.
- [ ] H 영향 모호성의 첫 DM 시점 또는 DM 불필요 이유가 있다.
- [ ] 시간 예산에 검증과 최소 10분 제출 버퍼가 포함됐다.
- [ ] `sk/work/BRIEF.md#과제 유형·전략`만 갱신했다.

## 주의
공식 문서와 담당자 답변이 없는 상태에서 기본 정책을 확정하지 않는다.
Codex는 담당자에게 DM을 보내지 않으며, 질문 초안만 만들고 사용자가 직접 보낸다.
이 단계의 시간 표는 구현 계획이 아니므로, 실제 슬라이스·실험 계획은 3.1 plan에서 다시 만든다.
