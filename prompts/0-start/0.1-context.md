# 0.1 환경·규칙·기준선 확인

> 스킬: `$sk-context` · 단계: 착수 — 환경·과제 유형·코드 지도 · 작업 노트: `sk/work/BRIEF.md#환경` · 사용 자료: `없음`

## 언제 쓰나
- 과제 루트에서 처음 Codex를 실행했을 때 가장 먼저 사용한다.
- 설치가 끝났는지, 어떤 명령을 안전하게 실행할지, 기존 기준선이 무엇인지 모를 때 사용한다.
- 세션을 재개했는데 실행 환경·Git 변경·기준선 기록이 오래되었을 때도 다시 쓴다.
- 테스트가 이미 실패해 원인 분석이 목적이면 이 프롬프트 대신 `6-debug/6.1-debug.md`를 사용한다.

## 준비할 입력
- 현재 작업 위치와 과제 루트: `<과제 루트>`
- 읽을 공식 안내·README·실행 문서: `<문서 경로들 또는 없음>`
- 제한 시간 또는 남은 시간: `<예: 120분 / 미확인>`
- 이미 알고 있는 금지 조건: `<네트워크·패키지 설치·포트·수정 금지 파일 또는 미확인>`
- 사용자 확인 없이 실행하면 안 되는 명령: `<있으면 목록, 없으면 미확인>`

## 전략 — 왜 이렇게 하나
이 단계의 목적은 기능을 구현하는 것이 아니라, 잘못된 위치·도구·명령으로 시작하는 실패를 5분 안에 막는 것이다.
`sk/`는 과제 코드가 아니라 도구이므로 분석·테스트·린트 대상에서 제외한다.
기준선은 안전성이 확인된 문서상 명령을 한 번 실행한 관찰 결과일 뿐, 요구사항 충족 증거가 아니다.
불명확한 네트워크·설치·마이그레이션은 허용으로 추정하지 않고 `미확인`으로 기록한다.

## 기본 프롬프트
```text
$sk-context
과제 루트는 <과제 루트>이며, 참고할 문서는 <문서 경로들 또는 없음>이다.
지금은 0-start의 환경·규칙·기준선 확인만 수행하라.
과제 루트가 sk/ 폴더의 부모인지, AGENTS.md 관리 구역과 .agents/skills/sk-* 설치 상태가 보이는지 읽기 전용으로 확인하라.
문서와 설정에서 언어·런타임, 실행·테스트·빌드 명령 후보, 포트·호스트, 네트워크·패키지 설치 허용 여부, 수정 금지 파일을 찾아 근거를 남겨라.
sk/는 도구이므로 과제 분석·테스트 대상에서 제외하라.
Git 상태는 읽기 전용으로 확인하되 기존 변경을 되돌리거나 정리하지 마라.
안전한 로컬 기준선 명령이 문서에 명시되고 설치·다운로드·데이터 변경 위험이 없을 때만 한 번 실행하라.
실행하지 못하면 미실행 이유와 확인할 최소 행동을 남기고, 실패를 코드 결함으로 단정하지 마라.
sk/work/BRIEF.md의 ## 환경만 정해진 표 열로 생성 또는 갱신하고 다른 섹션은 건드리지 마라.
코드·테스트·설정·의존성·데이터 파일은 수정하지 마라.
마지막에는 루트·설치 상태, 명령·기준선, 허용 상태, 막힌 점, 다음 단계 0.2와 필요 시 0.3을 번호로 보고하라.
```

## 심화 프롬프트 — 설치·명령·기존 변경을 모두 판별해야 할 때
```text
$sk-context
<과제 루트>에서 착수 전 환경 감사를 수행하라. 공식 문서는 <문서 경로들>이고 남은 시간은 <시간>이다.
먼저 pwd와 sk/의 관계를 확인해 과제 루트를 확정하라. Git 최상위가 다르면 두 경로를 기록하되 과제 루트 판단을 억지로 바꾸지 마라.
AGENTS.md의 SK-KIT 관리 구역과 .agents/skills/sk-*만 읽어 설치 상태를 확인하고, 누락 시 설치를 실행하지 말고 불완전으로 표시하라.
README, 패키지·빌드 설정, 테스트 설정에서 언어·버전과 실행·테스트·빌드 후보를 파일:줄 근거로 수집하라.
각 명령에 대해 로컬 여부, 설치·다운로드 가능성, DB 초기화·데이터 변경 가능성, 외부 서비스 의존성을 판정하라.
공식 안내에서 네트워크, 새 패키지, 포트·호스트, 비밀값, 수정 금지 파일, 제출물 규칙을 찾고 없는 항목은 미확인으로 분리하라.
git status --short와 git diff --stat은 읽기 전용으로만 사용해 기존 변경 파일을 보호 대상으로 요약하라.
안전하다고 입증된 기준선 명령은 하나만 실행하고 종료 코드, 통과·실패 수, 오류 첫 줄을 남겨라.
명령이 안전하지 않거나 불명확하면 실행하지 말고 왜 멈췄는지와 사용자에게 필요한 확인 1개를 적어라.
실제 실행 결과만 PASS/FAIL로 쓰고, 실행하지 않은 것은 미실행으로 쓰며 요구사항 충족으로 확대 해석하지 마라.
sk/work/BRIEF.md의 ## 환경에 항목 | 확인값 | 근거·명령 | 판정·주의 열을 사용해 기록하라.
다른 BRIEF 섹션과 과제 파일은 수정하지 마라.
끝에 6개 번호로 루트·설치, 런타임, 명령 후보, 기준선, 제약·보호 대상, 0.2/0.3 핸드오프를 보고하라.
```

## 변형 — 안전한 기준선 명령을 찾지 못했을 때
```text
$sk-context
<과제 루트>에서 환경만 확인하되, 문서의 테스트 명령이 설치·다운로드·DB 초기화·외부 호출을 할 가능성이 있어 실행하지 마라.
명령 후보별로 안전하지 않은 단서와 문서 근거를 비교하고, 안전성 미확인 때문에 미실행이라고 명확히 기록하라.
루트·설치 상태·언어·Git 상태·포트·호스트·패키지 설치와 네트워크 허용 상태는 읽기 전용으로 확인하라.
사용자에게 확인받을 최소 질문은 하나만 제시하고, 그 전에는 새 패키지 설치나 설정 변경을 제안하지 마라.
sk/work/BRIEF.md의 ## 환경만 갱신하고 표의 기준선 행에는 `미실행`과 이유를 써라.
다음에는 0.2 과제 유형 판별을 진행할 수 있는지, 아니면 어떤 답이 필요한지 보고하라.
```

## 변형 — 기존 기준선이 실패한 상태일 때
```text
$sk-context
<과제 루트>에서 문서상 안전한 기준선 명령을 한 번만 재현해 환경 관찰을 기록하라.
실패하면 종료 코드, 통과·실패 수, 오류 첫 줄, Git 변경 요약을 사실로만 남기고 원인을 추측하거나 코드를 고치지 마라.
환경·의존성·테스트 실패 중 어느 범주인지 확정되지 않으면 `미확정`으로 표기하라.
기준선 통과 여부와 요구사항 충족 여부를 혼동하지 마라.
sk/work/BRIEF.md의 ## 환경만 갱신한 뒤, 재현 가능한 오류가 있으면 6.1 debug와 0.2 triage 중 무엇을 먼저 할지 이유와 함께 제안하라.
```

## 결과물 확인
- [ ] `sk/`의 부모를 과제 루트로 확인하거나 불일치를 기록했다.
- [ ] 설치 상태, 런타임, 명령 후보, Git 상태가 각각 관찰 근거와 함께 있다.
- [ ] 네트워크·설치·포트·호스트·보호 파일을 허용/금지/미확인으로 분리했다.
- [ ] 기준선은 실제 1회 결과 또는 실행하지 않은 구체 이유가 있다.
- [ ] `sk/work/BRIEF.md#환경`만 갱신했고 과제 파일은 수정하지 않았다.

## 주의
공식 안내에 없는 모델명, 시간표, 채점 방식, 금지 규정을 사실처럼 쓰지 않는다.
사용자 승인 없이 새 패키지 설치, 런타임 업데이트, 외부 네트워크 접속, 포트 바인딩 변경을 하지 않는다.
기존 변경은 사용자 작업일 수 있으므로 위험한 Git 초기화·정리 명령으로 없애지 않는다.
