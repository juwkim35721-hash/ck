# 0.3 기존 코드 지도 작성

> 스킬: `$sk-code-map` · 단계: 착수 — 환경·과제 유형·코드 지도 · 작업 노트: `sk/work/BRIEF.md#코드 지도` · 사용 자료: `없음`

## 언제 쓰나
- 제공된 기존 소스·테스트가 있고, 구현 전에 어디를 읽고 어디를 조심해야 할지 파악할 때 쓴다.
- API, UI, 기존 기능 유지, 리팩터링 유형에서 진입점·호출 흐름·공개 경계를 확인할 때 특히 유용하다.
- 데이터·CLI 과제라도 이미 있는 코드와 테스트를 건드려야 할 가능성이 있으면 사용한다.
- 빈 프로젝트에서 코드가 전혀 없으면 최소 지도만 남기고 요구사항 발굴로 이동한다.

## 준비할 입력
- 환경 기록: `sk/work/BRIEF.md#환경`
- 유형 기록(있으면): `sk/work/BRIEF.md#과제 유형·전략`
- 읽을 README·과제 문서: `<경로 또는 없음>`
- 대표 흐름 후보: `<예: 주문 조회 요청 / CSV 집계 명령 / 없으면 README 기준 선택>`
- 제외할 생성물·대용량 디렉터리: `<예: node_modules, venv, build 또는 없음>`

## 전략 — 왜 이렇게 하나
코드 지도의 목적은 모든 파일을 요약하는 것이 아니라, 한 대표 흐름이 실제로 지나가는 경로와 변경 위험을 보이는 것이다.
문서의 요구사항 ID가 아직 없으면 R#을 지어내지 않고 `대표 흐름 후보`로 표시한다.
진입점→검증→핵심 로직→저장·외부 연동→출력을 실제 호출·import·등록 근거로만 연결한다.
지도에서 비어 있는 정책·스키마·경계는 추측으로 채우지 않고 1-discover 단계의 확인 대상으로 넘긴다.

## 기본 프롬프트
```text
$sk-code-map
sk/work/BRIEF.md#환경과, 있으면 #과제 유형·전략을 먼저 읽어라.
<과제 루트>에서 README와 <대표 흐름 후보 또는 README 기준 흐름>을 기준으로 기존 코드를 읽기 전용으로 지도화하라.
sk/, .git, 생성물·의존성 디렉터리는 탐색 대상에서 제외하고, 과제 코드·테스트·설정·데이터를 수정하거나 실행하지 마라.
실제 import·호출·라우팅 등록 근거로 진입점과 핵심 모듈·파일 역할을 확인하라.
대표 흐름 후보 1건을 골라 진입점 → 검증 → 핵심 로직 → 저장/외부 연동 → 출력 순으로 추적하라.
아직 R#이 없다면 대표 흐름 후보로 부르고 요구사항 ID를 만들지 마라.
데이터 모델, 요청·응답 경계, 포트·호스트·환경 변수·기본 경로 설정, 테스트·픽스처 위치를 확인 가능한 범위에서 적어라.
변경 예상 후보와 공개 인터페이스·공용 유틸·공유 모델·설정 기본값 같은 위험 경계를 반드시 분리하라.
미확인 호출 연결은 ?로 표시한 ASCII 흐름도를 만들어라.
sk/work/BRIEF.md의 ## 코드 지도만 정해진 세 표와 흐름도로 갱신하고 다른 섹션은 덮어쓰지 마라.
마지막에는 진입점, 대표 흐름, 위험 경계, 미확인 사항, 1.1/1.2 다음 행동을 6개 번호로 보고하라.
```

## 심화 프롬프트 — 대표 요청 또는 명령 하나를 끝까지 추적할 때
```text
$sk-code-map
<과제 루트>에서 <대표 흐름 후보>의 실행 경로를 읽기 전용으로 추적해 코드 지도를 작성하라.
먼저 환경 기록에서 언어·런타임·보호 파일·포트 요구를 읽고, 유형 기록이 있으면 그 위험을 탐색 우선순위에 반영하라.
상위 디렉터리와 설정 파일을 조사하되 sk/, .git, node_modules, venv와 <추가 제외 경로>는 제외하라.
실제 실행 진입점은 앱 생성, 라우터 등록, 명령 등록, main 함수, 스크립트 설정을 교차 확인해 후보와 확정을 구분하라.
대표 흐름의 입력이 어느 파일:심볼에서 들어오는지, 어느 검증을 거치는지, 어떤 도메인 로직과 모델을 거치는지, 어떤 출력 또는 부작용으로 끝나는지 순서대로 추적하라.
각 화살표는 호출·import·등록·테스트 호출 중 확인된 근거를 붙이고, 자동 등록처럼 간접적인 연결은 간접 연결로 표시하라.
요청 DTO·스키마·타입·CSV 헤더·ORM 모델·직렬화 중 확인된 데이터 계약 단서를 표에 넣고, 미확인 필드는 추측하지 마라.
포트·호스트·환경 변수·기본 경로는 키와 위치만 쓰고 비밀값은 기록하지 마라.
테스트와 픽스처의 위치·검증 대상·미실행 상태를 구분하고, 테스트가 없으면 이를 위험으로 표시하라.
변경 예상 지점은 목표를 충족할 후보로만 적고, 공개 라우트·CLI 옵션·공용 유틸·공유 모델은 보존 위험으로 별도 표에 적어라.
sk/work/BRIEF.md의 ## 코드 지도에 세 표의 열을 정확히 사용하고 ASCII 흐름도, 미확인·다음 확인 줄을 넣어라.
코드 수정·테스트 실행·패키지 설치·서버 실행은 하지 마라.
끝에 1.1 requirements와 필요한 경우 1.2 ambiguity에 넘길 근거를 파일:줄과 함께 보고하라.
```

## 변형 — 코드베이스가 매우 크거나 시간이 10분 미만일 때
```text
$sk-code-map
남은 시간은 <시간>이고 코드베이스가 크다. 모든 파일을 읽지 말고 <대표 흐름 후보> 하나에만 집중하라.
진입점, 직접 호출 모듈, 데이터 모델 또는 경계, 관련 테스트 위치, 공개·공용 위험 경계만 확인하라.
sk/와 생성물·의존성 폴더를 제외하고 rg와 find 같은 읽기 전용 명령으로 탐색 범위를 좁혀라.
확인되지 않은 연결은 ?로 두며, 파일명만으로 역할이나 정책을 단정하지 마라.
sk/work/BRIEF.md의 ## 코드 지도에 최소 세 표와 한 줄 ASCII 흐름도를 남기고, 남은 빈칸은 1.1 또는 1.2로 넘겨라.
과제 파일을 수정하거나 테스트를 실행하지 마라.
```

## 변형 — 테스트 또는 픽스처가 없는 경우
```text
$sk-code-map
<과제 루트>를 읽기 전용으로 탐색해 대표 흐름과 설정·데이터 경계를 지도화하라.
테스트·픽스처 위치를 찾지 못하면 `테스트 부재`를 관찰 사실과 탐색 범위로 기록하고 통과·실패를 추정하지 마라.
대표 흐름에서 회귀 위험이 큰 공개 인터페이스와 공용 유틸을 분리해 적어라.
이 부재가 향후 2.3 acceptance와 4.1 test-first가 필요한 이유임을 연결하되, 이 단계에서는 테스트 파일을 만들지 마라.
sk/work/BRIEF.md의 ## 코드 지도만 갱신하고, 요구사항 R/C 확정은 1.1로 넘겨라.
```

## 결과물 확인
- [ ] 실제 진입점과 그 근거가 있다.
- [ ] 대표 흐름 1건이 확인된 연결과 `?` 연결을 구분한 ASCII 흐름도로 있다.
- [ ] 파일·모듈 역할, 데이터·설정 경계, 테스트·픽스처 위치 또는 부재를 기록했다.
- [ ] 변경 예상 후보와 공개·공용 위험 경계를 별도로 기록했다.
- [ ] `sk/work/BRIEF.md#코드 지도`의 세 표 열을 정확히 사용했다.
- [ ] 코드 수정, 테스트·서버 실행, 패키지 설치를 하지 않았다.

## 다음 단계
문서·테스트·코드에서 R/C와 제출물을 추출하려면 [1.1 요구사항 추출](../1-discover/1.1-requirements.md)을 사용한다.
정책·스키마·경계의 빈칸이나 문서·코드 충돌은 [1.2 모호성 탐지](../1-discover/1.2-ambiguity.md)로 G 후보를 만든다.
유형·시간 경로가 아직 없다면 [0.2 과제 유형 판별](../0-start/0.2-triage.md)로 돌아간다.

## 주의
과제 파일을 읽을 수 있다고 해서 수정 권한이 있는 것은 아니다. 구현 변경은 4-build 단계까지 기다린다.
`sk/`는 도구 폴더이므로 소스·테스트 지도에 넣지 않는다.
테스트를 찾았더라도 이 스킬은 실행하지 않으며, 기준선 실행은 0.1의 안전성 판단을 따른다.
