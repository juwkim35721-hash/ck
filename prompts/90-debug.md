# 가설 기반 디버깅

## 사용 시점

- 이미 실행 가능한 코드에서 오류, 실패 테스트, 예상과 다른 출력이 확인됐을 때 사용한다.
- 기능 추가나 전면 설계 전에, 한 증상을 재현하고 원인을 좁혀야 할 때 사용한다.
- 공식 안내와 현재 과제의 AI 사용 규칙을 먼저 따른다. AI 금지 서술형 평가가 시작되면 이 문서와 모든 AI 보조 사용을 중단한다.
- 준비 도구 저장소가 아니라 실제 과제 루트에서만 조사·실행한다.

## 필요 입력

- [과제 루트]: 실제 소스와 테스트가 있는 절대 경로
- [남은 시간: 분]: 재현·수정·재검증에 쓸 수 있는 시간
- [실패 증상]: 오류 전문, 기대값과 실제값, 영향받는 기능
- [재현 명령]: 현재 알려진 실행 또는 테스트 명령
- [최근 변경/파일]: 의심되는 변경 범위. 모르면 "모름"으로 둔다.
- [수정 승인 범위]: 수정 가능 파일과 수정 금지 파일
- 입력이 비어 있으면 파일을 바꾸지 말고 실제 과제 루트와 오류 전문 또는 재현 명령을 먼저 요청한다.

## 전략

증상 설명을 원인으로 취급하지 않는다. 먼저 읽기 전용으로 호출 경로, 입력, 설정, 로그, 실패한 assert를 확인하고 가장 작은 재현을 만든다. 재현은 같은 명령을 두 번 실행해 결과가 같은지로 확인한다. 결과가 흔들리면 시간·난수·외부 서비스·공유 상태를 별도 가설로 기록한다.

원인 가설은 서로 구별되는 정확히 두 개를 쓴다. 각 가설에는 관찰 가능한 예측 하나와, 통과/실패가 두 가설을 가르는 가장 싼 판별 실험 하나를 연결한다. 로그를 더 찍는 것만으로 충분하지 않으면 작은 assert, 단위 테스트, 고정 입력을 사용한다. 비밀값이나 원본 데이터는 출력·커밋하지 않는다.

판별 결과가 한 가설을 지지해도 관련 코드 전체를 고치지 않는다. 실패를 일으킨 불변식 또는 계약을 복구하는 최소 변경만 제안한다. 수정 권한이 없거나 승인 범위 밖이면 패치하지 말고 파일·위치·근거·제안만 보고한다. 실패 테스트 삭제, 기대값을 실제값에 맞춤, 예외 무시, 데이터 삭제로 녹색 상태를 만들지 않는다.

수정 뒤에는 반드시 같은 재현 명령을 다시 실행한다. 가능하면 실패와 직접 연결된 경계 사례 하나를 추가 확인하되, 시간이 부족하면 그 미실행 항목을 남긴다. 새 실패가 생기거나 원인이 판별되지 않으면 변경을 누적하지 말고 마지막 알려진 기준으로 돌아갈 수 있는 지점과 다음 실험을 기록한다.

### 의사결정·중단 게이트

1. 재현이 안 되면 수정하지 않는다. 정확한 입력·환경·로그·명령을 확보할 때까지 관찰 단계로 돌아간다.
2. 두 가설을 가르는 실험이 없으면 임의 수정 대신 관찰을 추가하거나, 부족한 정보 한 가지를 질문한다.
3. 판별 실험이 승인 범위를 벗어나거나 파괴적이면 실행하지 않는다. 안전한 대체 관찰을 제시한다.
4. 최소 수정 후 원래 재현이 통과하고 새 회귀가 없을 때만 디버깅을 종료한다.
5. [남은 시간: 분]이 부족하면 새 조사·리팩터링을 중단하고, 재현 결과·미확정 가설·안전한 다음 한 작업을 인계한다.

## 기본 프롬프트

```text
$sk-debug
너는 가설 기반 디버거다. 공식 안내와 현재 과제의 AI 사용 규칙을 우선하며, AI 금지 평가가 시작됐다면 즉시 중단하라.

입력:
- 과제 루트: [과제 루트]
- 남은 시간: [남은 시간: 분]분
- 실패 증상/오류 전문: [실패 증상]
- 현재 재현 명령: [재현 명령]
- 최근 변경/관련 파일: [최근 변경/파일]
- 수정 승인 범위: [수정 승인 범위]

실제 과제 루트인지 먼저 확인하고, 입력이 모자라면 파일을 바꾸지 말고 부족한 항목만 질문하라. 읽기 전용으로 실패 위치·호출 경로·입력·기대/실제 결과를 조사하라. 가장 작은 재현 명령을 제시하고 같은 조건에서 재현 여부를 확인하라.

서로 경쟁하는 원인 가설을 정확히 2개 작성하라. 각 가설마다 (a) 근거와 반대 근거, (b) 관찰 가능한 예측, (c) 두 가설을 가르는 가장 작은 판별 실험, (d) 통과/실패 해석을 적어라. 전체 재작성, 데이터 삭제, 실패 테스트 제거, 예외 무시는 금지다.

원인이 충분히 좁혀지고 수정 권한이 있을 때만 최소 수정안을 적용하라. 그 뒤 동일 재현 명령을 재실행하고 결과를 사실 그대로 보고하라. 최종 출력은 다음 순서로 짧게 작성하라: 재현 명령과 결과, 가설 2개와 판별 근거, 최소 수정(파일·위치·의도), 재실행 결과, 미검증/다음 한 작업. 전체 사고과정은 쓰지 말고 판단 근거와 실행 증거만 제시하라.
```

## 심화/반증 프롬프트

```text
$sk-debug
다음 디버깅 결론을 반증 중심으로 검토하라. 아직 해결됐다고 가정하지 말고, 승인 범위 밖의 파일은 수정하지 마라.

- 과제 루트: [과제 루트]
- 남은 시간: [남은 시간: 분]분
- 최소 재현 명령과 실제 결과: [재현 명령/결과]
- 현재 원인 가설 2개: [가설 A, 가설 B]
- 적용했거나 제안한 수정: [수정 내용]
- 관련 요구사항/계약: [요구사항/파일/답변]

먼저 재현이 결정적인지 확인하라. 입력 누락, 환경 차이, 순서 의존, 시간·난수, 캐시·공유 상태, 경계값 중 이 실패를 더 잘 설명할 반례를 하나만 선택해 검사하라. 검사마다 기대 결과와 실제 결과를 분리해 적어라.

수정이 단지 증상을 숨기는지 확인하기 위해 원래 실패와 인접한 경계 사례 하나를 실행하라. 실패 테스트 삭제, 기대값 완화, 무조건 기본값, 예외 무시는 해결책으로 인정하지 마라. 새 실패, 비결정성, 또는 가설 미판별이면 추가 변경을 중단하고 마지막 안전 상태·미확정 원인·가장 싼 다음 실험을 보고하라.

출력 형식: (1) 반증 대상, (2) 실행한 판별/경계 실험과 명령, (3) 기대/실제/판정, (4) 유지 또는 되돌릴 최소 수정, (5) 종료 가능 여부와 잔여 위험. 증거 없는 성공 선언은 하지 마라.
```

## 완료 기준

- 실제 과제 루트에서 가장 작은 재현 명령과 실제 결과를 기록했다.
- 상호 배타적인 가설 2개와 각각의 판별 근거를 제시했다.
- 승인된 범위에서만 최소 수정했거나, 미승인이라면 수정 제안으로 멈췄다.
- 같은 재현 명령을 수정 후 다시 실행했고, 통과·실패·실행 불가를 숨기지 않았다.
- 실패 테스트·원본 데이터·관련 없는 사용자 변경을 삭제하거나 덮어쓰지 않았다.

## 다음 단계

원인이 해결됐으면 `08-verify`에서 요구사항별 정상·경계·실패 검증을 확장한다. 예외·시간·중복·상태 경계가 원인이면 `07-harden`으로 넘어간다. 재현이 계속 불안정하면 수정 대신 환경·입력 계약을 다시 확인한다.

## 주의

오류 메시지 한 줄, 마지막 변경, 단일 성공 실행만으로 원인을 확정하지 않는다. 공식 규정·답변이 없으면 모델, 일정, 채점, 허용 도구를 추정해 쓰지 않는다. 외부 제출·배포·push, 자격증명 노출, 파괴적 초기화는 이 단계의 작업이 아니다.
