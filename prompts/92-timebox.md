# 시간 부족·범위 축소

## 사용 시점

- 마감까지 남은 시간이 짧아졌거나, 계획 대비 구현·검증이 밀렸을 때 사용한다.
- 실제 과제 루트와 공식 마감 시각을 확인한 뒤 사용한다. 준비 도구 저장소를 과제로 오인하지 않는다.
- 공식 안내에서 AI 사용이 허용된 준비·구현 단계에만 사용한다. 후속 AI 금지 서술형이 시작되면 이 문서와 모든 프롬프트 사용을 중단한다.
- 목표는 더 많이 만드는 것이 아니라 필수 수용 기준을 작동·검증 가능한 상태로 남기고 제출 버퍼를 확보하는 것이다.

## 필요 입력

- [과제 루트]
- [남은 시간: 분] 및 [공식 마감 시각]
- [요구사항/수용 기준]: R1처럼 식별 가능한 필수 조건과 선택 조건
- [현재 상태]: 구현됨/부분 구현/미착수, 마지막 실행 명령과 실제 결과
- [제출 형식/필수 파일] 및 [공식 안내/정책]
- [현재 막힌 점]과 이미 진행 중인 변경 사항

입력이 없거나 충돌하면 추측하지 말고, 실제 과제 루트·남은 분·필수 조건부터 짧게 질문한다. 테스트 결과나 담당자 답변은 없는 것으로 꾸며내지 않는다.

## 전략

### 1. 5분 안에 사실만 고정한다

- 시계를 확인해 남은 시간 `T`를 분 단위로 기록하고, 마지막 실행 결과와 작업 트리를 읽기 전용으로 확인한다.
- 제출에 필요한 파일, 실행 진입점, 필수 수용 기준만 목록화한다. 새 설계 토론이나 원인 불명의 재현 작업은 보류한다.
- 이미 동작하는 핵심 흐름을 기준선으로 삼고, 사용자와 관련 없는 변경·원본 데이터·기존 테스트는 보존한다.

### 2. 제출 버퍼를 먼저 떼어 둔다

- `T`가 60분 이상이면 최소 15분 또는 `T`의 20% 중 큰 값을 제출·최종 검증 버퍼로 예약한다.
- `T`가 20~59분이면 10분, 20분 미만이면 5분을 예약한다. `T`보다 큰 버퍼는 잡지 말고 즉시 최소 제출 상태 점검으로 전환한다.
- 남은 작업 시간은 `T - 버퍼`로만 배분한다. 버퍼는 새 기능이나 보기 좋은 정리에 다시 쓰지 않는다.

### 3. 작업을 P0/P1/중단으로 강제 분류한다

- **P0(남김)**: 제출물이 열리거나 실행되는 데 필수이고, 명시된 필수 수용 기준을 직접 충족하며, 짧은 명령으로 검증 가능한 작업이다.
- **P1(미룸)**: P0가 완성된 뒤에만 가치가 있는 성능 개선, 추가 예외, 보조 화면, 선택 요구사항, 설명 다듬기다.
- **중단**: 새 기능, 전면 리팩터링, 라이브러리 교체, 디자인 재작업, 탐색적 최적화, 재현되지 않은 버그 추측 수정이다.
- 한 작업이 P0인지 결정할 수 없으면 필수 조건·제출 형식과의 연결을 확인한다. 연결 증거가 없으면 P1로 내린다.

### 4. 작은 완료 단위만 실행한다

- P0마다 “입력 또는 호출 → 기대 출력 또는 관찰값 → 실제 검증 명령”을 한 줄로 적는다.
- 위험이 가장 큰 P0 하나를 먼저 끝내고 즉시 해당 명령을 실행한다. 여러 P0를 동시에 부분 구현하지 않는다.
- 한 P0가 예상 배정 시간의 절반을 써도 진전 증거가 없으면 원인을 길게 파지 말고, 최소 대체 경로가 있는지 2분 안에 판단한다. 없으면 중단 목록으로 옮기고 다음 P0 또는 제출 준비로 전환한다.

### 5. 시간 점검에서 범위를 더 줄인다

- 각 P0 종료 후와 버퍼 시작 직전에 남은 시간을 다시 확인한다.
- 남은 시간이 예약 버퍼 이하가 되면 코드 변경을 멈추고 필수 파일·실행·최소 검증·민감정보만 점검한다.
- 최소 검증이 실패하면 실패를 숨기거나 테스트를 삭제하지 않는다. 마지막으로 재현 가능한 실패 명령, 영향받는 R-ID, 시도한 최소 조치를 남긴다.

## 기본 프롬프트

```text
$sk-timebox
[과제 루트]에서 시간 부족 상태를 읽기 전용으로 정리하라.
남은 시간은 [남은 시간: 분], 공식 마감은 [공식 마감 시각]이며,
필수 조건과 제출 형식은 [요구사항/수용 기준], [제출 형식/필수 파일]이다.
현재 상태와 마지막 실제 실행 결과는 [현재 상태]이고, 막힌 점은 [현재 막힌 점]이다.

먼저 실제 과제 루트, 공식 정책, 남은 시간을 확인하라. 정보가 없으면 정확히 무엇이
부족한지 질문하고 추측하지 마라. AI 금지 평가 단계라면 즉시 중단하라.

코드를 새로 설계하거나 수정하지 말고, 필수 조건별로 P0(남김)·P1(미룸)·중단으로
분류하라. 각 P0에는 이유, 최대 투입 시간, 가장 짧은 검증 명령을 붙여라.
남은 시간에서 제출·최종 검증 버퍼를 먼저 예약하고, 현재부터 버퍼 시작까지의 순서를
한 작업씩 제시하라. 새 기능·전면 리팩터링·추측성 수정은 중단 목록에 넣어라.

출력은 1) 시간 예산, 2) P0/P1, 3) 중단 목록, 4) 최소 검증·제출 순서,
5) 확인되지 않은 사실과 실패 시 전환 조건으로 제한하라. 실제로 실행하지 않은 결과를
통과라고 쓰지 마라.
```

## 심화/반증 프롬프트

```text
$sk-timebox
다음 시간 절약 계획을 반증 중심으로 점검하라.
[과제 루트], [남은 시간: 분], [요구사항/수용 기준], [제출 형식/필수 파일],
[현재 상태], [P0/P1/중단 초안]은 위와 같다.

각 P0에 대해 “없으면 제출이 실패하는가?”, “명시된 필수 조건에 연결되는가?”,
“남은 시간 안에 독립적으로 검증 가능한가?”를 확인하라. 하나라도 아니면 P1 또는
중단으로 내려라. P1을 생략했을 때 계약·호출자·제출 형식이 깨지는 반례가 있으면
그 항목을 P0으로 올리고 최소 형태만 제안하라.

예약한 제출 버퍼가 침식되는 순서, 검증 없이 완료로 오인할 위험, 실패한 P0를
계속 붙잡을 중단 신호를 찾아라. 기존 변경·원본 데이터·테스트를 삭제하거나 실패를
감추는 해결책은 제외하라. AI 금지 단계라면 분석도 진행하지 말고 중단을 보고하라.

수정된 결과는 “유지할 P0 / 미룰 P1 / 즉시 중단 / 최소 검증 명령 / 버퍼 시작 시각 /
미검증 위험” 여섯 항목만 표로 제시하라. 근거가 없는 완료 주장은 하지 마라.
```

## 완료 기준

- 남은 시간과 예약된 제출 버퍼가 분 단위로 기록되어 있다.
- 모든 남은 작업이 P0/P1/중단 중 하나이며, P0는 필수 조건·최소 검증과 연결되어 있다.
- 새 기능·전면 리팩터링·추측성 수정은 명시적으로 중단되었다.
- 버퍼 시작 시 할 최소 검증과 제출 점검 순서, 미검증 항목과 실패 전환 조건이 분명하다.

## 다음 단계

- P0의 최소 변경이 필요하면 승인된 범위에서 `06-implement`를 한 항목에만 적용하고 즉시 검증한다.
- P0 구현이 끝났거나 버퍼에 도달하면 `08-verify`의 최소 검증 뒤 `10-deliver`로 제출 준비를 한다.
- 재현 가능한 실패 하나가 P0를 막으면 시간 배정을 다시 확인한 뒤 `90-debug`로 최소 재현만 다룬다.

## 주의

- 공식 안내 메일·채점 방식·모델·금지 규정은 제공되지 않았으므로 지어내지 말고 공식 안내를 우선한다.
- 제출 준비는 외부 제출, push, 배포, 업로드 버튼 조작을 뜻하지 않는다. 별도 구체적 승인이 없으면 실행하지 않는다.
- 남은 시간 압박은 기존 테스트 삭제, 원본 데이터 변경, 비밀정보 노출, 실패 은폐의 근거가 될 수 없다.
