# 입출력·데이터 계약 분석

## 사용 시점

- 문제 정의와 정책 확인 뒤, 설계·구현 전에 사용한다.
- API, 함수, 파일, 배치, UI 입력처럼 데이터가 경계를 넘는 과제에 적용한다.
- 공식 안내와 AI 사용 허용 범위가 있으면 그것을 먼저 따른다.
- 공식 안내가 제공되지 않았으므로 모델, 일정, 채점, 금지 규정을 추정하지 않는다.
- 기본 작업은 읽기 전용 분석이며 구현 파일이나 원본 데이터는 바꾸지 않는다.

## 필요 입력

- 실제 과제 루트: [과제 루트]
- 남은 시간: [남은 시간: 분]
- 요구사항·수용 기준·담당자 답변: [요구사항/파일/답변]
- 살필 경계 후보(함수·경로·파일·화면): [대상 경계]
- 실행 가능한 명령과 기존 테스트 결과: [명령/결과 또는 없음]

입력이 비어 있으면 먼저 과제 루트와 경계 후보를 질문한다.
요구사항은 있으나 코드·샘플이 없으면 그 사실만 기록하고 추정 계약을 확정하지 않는다.

## 전략

1. 실제 과제 루트에서 요구사항, 호출자, 타입 선언, 스키마, 테스트, 샘플 순으로 읽는다.
2. 증거마다 파일·위치와 관찰 사실을 남기고, 공식 요구사항을 샘플보다 우선한다.
3. 샘플은 가능한 값의 예일 뿐 전체 스펙이 아니므로 누락·빈 값·큰 값·다른 순서를 허용한다고 단정하지 않는다.
4. 각 경계의 요청, 정상 응답, 오류 응답을 분리해 계약 표로 만든다.
5. 필드마다 이름, 타입, 필수 여부, null/빈 값 의미, 단위, 시각 기준·형식·시간대, 범위, 기본값, 정렬·중복 규칙을 확인한다.
6. 레코드나 요청을 식별하는 고유 키와 복합 키, 키 충돌 시의 처리, 원본 보존·변환 규칙을 확인한다.
7. 오류는 상태/예외 이름만 보지 말고 오류 코드, 메시지, 필드 오류, 재시도 가능성, 부분 성공 여부의 실제 증거를 확인한다.
8. 각 항목을 `확정`, `관찰됨이나 미확정`, `미확인`으로 표시한다. 관찰과 정책 판단을 섞지 않는다.
9. 결과를 바꾸는 미확인 항목만 영향도 순으로 정책 확인 후보로 올린다. 답이 없으면 가정 대신 되돌릴 지점을 적는다.
10. 계약별로 정상·경계·실패 테스트 입력과 기대 관찰을 설계한다. 미확정 필드에는 임의의 기대값을 쓰지 않는다.

## 기본 프롬프트

```text
$sk-data-contract
[과제 루트]에서 [대상 경계]의 입출력·데이터 계약을 읽기 전용으로 분석하라.
남은 시간은 [남은 시간: 분]이고, 요구사항/답변은 [요구사항/파일/답변]이다.
먼저 실제 과제 루트인지 확인하고 요구사항, 호출자, 타입/스키마, 테스트, 샘플을 읽어라.
샘플을 전체 명세로 일반화하지 말고, 증거마다 파일·위치·관찰 사실을 붙여라.

각 경계마다 다음 표를 작성하라.
- 입력: 필드/타입/필수 여부/null·빈 값 의미/단위/시간 형식·시간대/범위/고유 키/정렬·중복 규칙
- 정상 출력: 같은 항목과 원본 보존·변환 규칙
- 오류 출력: 실제 오류 코드·본문 또는 예외·필드 오류·부분 성공 여부
- 상태: 확정 / 관찰됨이나 미확정 / 미확인

그 뒤 데이터 특성 및 검사 한계, 영향도 높은 정책 확인 후보 최대 3개,
계약별 정상·경계·실패 테스트 입력과 기대 관찰을 제시하라.
입력에 없는 정책, 기본값, 오류 형식은 만들지 말고 미확인으로 남겨라.
파일을 수정·생성·삭제하거나 외부 호출을 하지 말라.
결과는 판단 근거와 실행 증거만 간결하게 보고하라.
```

## 심화/반증 프롬프트

```text
$sk-data-contract
아래 계약 분석을 반증하라: [기존 계약 표/분석 결과].
[과제 루트]에서 요구사항, 서로 다른 호출자, 타입 선언, 테스트, 샘플을 대조하되 읽기 전용으로 작업하라.

특히 다음 반례를 찾고 증거 위치와 영향을 기록하라.
1) 샘플에는 없지만 호출자가 보내는 누락·null·빈 배열·0·음수·긴 문자열 값
2) 숫자 단위 또는 시각 형식·시간대·경계 시각의 불일치
3) 고유 키 충돌, 중복 요청/레코드, 정렬 가정, 부분 데이터
4) 정상 응답과 오류 응답의 스키마 차이, 부분 성공, 재시도 가능한 실패
5) 원본 데이터가 변형·손실될 위험과 호출자 호환성 깨짐

확정 증거와 추론을 분리하고, 모순이면 어느 계약 항목을 미확정으로 되돌릴지 제시하라.
계약별 최소 정상·경계·실패 테스트 입력도 갱신하라.
증거가 없으면 '확인 불가'라고 쓰며, 파일 변경·테스트 삭제·임의 기본값 추가를 하지 말라.
```

## 완료 기준

- 대상 경계마다 입력, 정상 출력, 오류 출력이 분리되어 있다.
- 타입·필수 키·단위·시각·고유 키·범위·정렬/중복과 오류 스키마의 확인 상태가 드러난다.
- 모든 확정 항목에 출처가 있고, 샘플만 근거인 항목은 미확정으로 남아 있다.
- 데이터 원본 보존 규칙과 검사 한계가 기록되어 있다.
- 계약별 정상·경계·실패 테스트 입력이 있으며, 정책 확인 후보와 미응답 시 되돌릴 지점이 있다.

## 다음 단계

계약의 미확인 항목이 결과를 바꾸면 `02-clarify`로 돌아가 최소 질문만 한다.
계약이 구현 범위와 위험을 충분히 정하면 `04-plan`으로 넘긴다.
구현 중 계약 위반이 발견되면 이 단계의 표를 증거와 함께 갱신한 뒤 설계·구현을 재검토한다.

## 주의

공식 안내가 우선이며 AI가 허용된 단계에서만 이 문서를 사용한다.
후속 AI 금지 서술형이 시작되면 프롬프트·스킬·암기자료 사용을 즉시 중단한다.
원본 데이터, 기존 테스트, 사용자와 무관한 변경을 삭제·덮어쓰기·숨기지 않는다.
검증이 실행 불가하거나 증거가 부족하면 통과로 표현하지 말고 한계로 보고한다.
