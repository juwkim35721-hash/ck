# UI 핵심 흐름·접근성 점검

## 사용 시점

UI가 구현되어 있고 핵심 기능 구현 뒤, 제출 전 짧은 화면 점검이 필요할 때 사용한다.
브라우저로 실제 앱을 열 수 있는지부터 확인하고, 디자인 개선이나 신규 기능 구현으로 범위를 넓히지 않는다.
공식 안내와 허용된 AI 사용 단계가 있다면 그 규칙을 우선한다.
후속 AI 금지 서술형 평가가 시작되면 이 문서와 모든 프롬프트 사용을 즉시 중단한다.

## 필요 입력

- [과제 루트]와 실제 앱 실행 명령 또는 접속 URL
- [남은 시간: 분] 및 현재 변경 허용 범위
- [요구사항/파일/답변]: 핵심 사용자 목적, 반드시 통과해야 할 흐름, 알려진 제한
- 가능한 경우 테스트 계정·데모 데이터·오류를 재현할 안전한 입력
- 공식 안내의 브라우저·로그인·네트워크·AI 사용 제한

입력이 없으면 추정하지 말고 과제 루트와 실행 방법만 먼저 확인한다.
로그인 정보나 민감 데이터는 요청·출력·업로드하지 않는다.

## 전략

1. 먼저 실제 과제 루트와 변경 허용 범위를 확인하고 준비 도구 저장소를 과제로 착각하지 않는다.
2. Browser 도구의 가용성, 앱 기동 가능 여부, 접속 주소를 먼저 확인한다. 불가하면 소스만 보고 통과를 주장하지 않는다.
3. 요구사항에서 사용자 가치가 큰 P0 흐름을 1~3개 고른다. 예: 진입→입력/선택→실행→결과 확인이다.
4. 각 흐름에 시작 상태, 사용자 행동, 기대 화면/데이터/API 반응, 실제 관찰, 증거를 한 줄로 기록한다.
5. 흐름마다 정상 상태만 보지 말고 로딩, 빈 데이터, 오류, 긴 값/작은 화면 폭 중 적용 가능한 상태를 하나 이상 확인한다.
6. 버튼·링크·입력·모달 등 조작 요소는 마우스만이 아니라 Tab, Shift+Tab, Enter, Space, Escape로 최소 점검한다.
7. 포커스가 보이는지, 순서가 의미 있는지, 키보드로 조작 가능한지, 오류 메시지가 인지 가능한지를 관찰한다.
8. 화면 결과와 실제 API/데이터 반영이 필요한 흐름은 개발자 도구·네트워크 기록 또는 화면의 재조회로 확인한다. 한쪽만 보고 연동 성공이라 하지 않는다.
9. 테스트 데이터가 없거나 위험하면 데이터를 만들거나 삭제하지 말고 관찰 가능한 상태만 점검하고 한계를 남긴다.
10. 발견 사항은 사용자 영향과 재현 가능성으로 P0 차단, P1 중요, P2 개선으로 분류한다. 수정은 별도 승인된 구현 단계에서만 한다.
11. P0 흐름이 막히거나 브라우저/앱이 실행되지 않으면 진단을 길게 확장하지 말고 즉시 중단 기준과 재현 정보를 보고한다.
12. 남은 시간이 부족하면 P0 정상 흐름과 키보드 진입/실행/결과 확인을 보호하고, 꾸밈·전면 반응형 점검은 미검증으로 넘긴다.

## 기본 프롬프트

```text
$sk-ui-smoke
[과제 루트]의 UI를 읽기 전용으로 스모크 점검하라. 남은 시간은 [남은 시간: 분]분이고, 핵심 요구사항/흐름은 [요구사항/파일/답변]이다.

1) Browser 도구 가용성, 앱 실행 명령과 URL을 먼저 확인하라. 불가하면 이유와 미검증 범위를 보고하고 통과 판정을 하지 마라.
2) 사용자 가치 기준 P0 흐름 최대 3개를 고르고, 각 흐름을 시작 상태 → 행동 → 기대 결과 → 실제 관찰 → 증거로 표에 기록하라.
3) 각 흐름에서 적용 가능한 로딩·빈 데이터·오류·긴 값 상태를 확인하라. 화면과 API/데이터 연동이 필요한 경우 양쪽 증거를 구분하라.
4) Tab/Shift+Tab/Enter/Space/Escape로 핵심 조작 요소의 포커스 표시, 순서, 실행, 닫기를 점검하라.
5) 코드·디자인·테스트 데이터는 바꾸지 마라. 실행 불가, 로그인 불가, 데이터 부재는 미검증으로 명시하라.

출력은 (a) 점검 환경, (b) 흐름별 기대/실제/판정/증거, (c) 접근성·실패 상태, (d) P0/P1/P2 발견 사항, (e) 미검증 및 다음 한 작업 순으로 작성하라. 없는 결과는 만들지 마라.
```

## 심화/반증 프롬프트

```text
$sk-ui-smoke
[과제 루트]에서 이미 정상으로 보인 UI 핵심 흐름 [요구사항/파일/답변]을 반증 중심으로 재점검하라. 남은 시간은 [남은 시간: 분]분이다.

먼저 Browser 도구와 대상 URL의 사용 가능 여부를 확인하라. 각 P0 흐름에 대해 다음 중 실제로 가능한 최소 반례를 하나씩 실행하라: 빈 결과, 느린/실패 응답, 매우 긴 텍스트·숫자, 중복 클릭, 키보드만 사용, 모달/오류 후 원래 흐름 복귀.

각 반례마다 사용자 행동, 기대 안전 동작, 실제 화면, 데이터/API 반영 여부, 키보드 포커스 이동, 재현 가능성을 구분해 기록하라. 도구·계정·데이터 제약으로 확인하지 못한 것은 미검증으로 남겨라. 구현이나 디자인을 변경하지 말고, 제출을 막는 P0만 맨 위에 요약하라.
```

## 완료 기준

- Browser 도구와 앱 접속 가능 여부가 실제 결과로 기록되어 있다.
- P0 흐름별 기대와 실제 관찰이 분리되어 있고, 화면과 연동 증거의 한계가 명시되어 있다.
- 적용 가능한 로딩·빈 데이터·오류·긴 값과 키보드 점검 결과가 있다.
- 확인하지 못한 화면·상태·뷰포트·브라우저는 미검증으로 남아 있다.
- 발견 사항은 재현 단계와 사용자 영향으로 우선순위화되어 있으며 임의 수정은 하지 않았다.

## 다음 단계

P0 차단이 있으면 90-debug 또는 승인된 구현 단계로 재현 정보만 넘긴다.
요구사항별 독립 검증이 필요하면 08-verify로 흐름과 증거를 넘긴다.
차단이 없으면 10-deliver에 실행 방법, 점검 범위, 미검증 목록을 전달한다.

## 주의

소스 코드만 읽고 실제 UI가 동작했다고 결론 내리지 않는다.
색상·간격·문구 선호를 기능 결함처럼 과장하거나 전면 디자인 변경을 제안하지 않는다.
보조기기 호환성, 모든 브라우저, 모든 화면 크기는 실제로 검증하지 않았다면 범위 밖으로 표시한다.
실패를 숨기기 위해 오류 화면을 닫거나 테스트를 건너뛰지 않는다.
외부 배포·제출·계정 생성·민감정보 입력은 별도 구체적 승인 없이 수행하지 않는다.
