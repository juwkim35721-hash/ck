## 0. 약속 — 모든 것은 과제 루트에서

| 약속 | 명령 |
| :--- | :--- |
| ① 과제 루트에서 클론한다 | `git clone https://github.com/juwkim35721/sk sk` |
| ② 과제 루트에서 설치한다 | `python3 sk/scripts/install.py` |
| ③ 과제 루트에서 Codex를 실행한다 | `codex` |

**과제 루트**는 시험이 준 실제 과제 폴더(README·소스·데이터가 있는 곳)입니다. 설치 프로그램은 `sk` 폴더의 **부모 폴더를 과제 루트로 간주**하며, 다른 위치에서 실행하면 이동할 경로를 알려 주고 멈춥니다.

```text
<과제 루트>/
├── README.md, src/, data/ …     ← 과제 파일 (Codex가 구현하는 대상)
├── sk/                          ← 이 저장소 (도구. 과제 코드가 아님)
│   ├── prompts/0-start … 9-qa/  ← 단계별 전략 프롬프트
│   ├── skill/sk-*/SKILL.md      ← 스킬 원본 38개
│   ├── templates/  snippets/    ← 템플릿 3종, 스니펫 2종
│   ├── scripts/install.py, help.py
│   └── work/                    ← 작업 노트 (설치 시 생성, git에 안 올라감)
├── AGENTS.md                    ← 설치 시 SK-KIT 관리 구역이 추가됨
└── .agents/skills/sk-*/         ← 설치된 스킬 (Codex가 자동 인식)
```

설치가 하는 일은 네 가지뿐입니다.

1. 과제 루트 `AGENTS.md`에 `SK-KIT:BEGIN/END` 관리 구역을 추가합니다. 기존 내용은 그대로 두고, 바뀌는 파일은 먼저 `sk/.install/backups/`에 백업합니다.
2. `sk/skill/`의 38개 스킬을 `.agents/skills/`로 복사합니다. Codex는 실행 위치의 `.agents/skills`를 읽습니다.
3. 과제 루트가 git 저장소라면 `.git/info/exclude`에 `sk/`, 설치한 스킬, 새로 만든 `AGENTS.md`를 넣어 `git status`를 깨끗하게 유지합니다. 이 설정은 로컬 전용이라 커밋되지 않습니다.
4. 작업 노트 폴더 `sk/work/`를 만듭니다.

네트워크 사용, 패키지 설치, Codex 설정 변경은 하지 않습니다.

### 3.1 ID가 이어지는 방식 — 이 키트의 뼈대

모든 단계는 앞 단계가 만든 ID를 받아 다음 ID를 만듭니다. 그래서 어느 줄의 코드든 "어떤 담당자 답(P#) 때문에, 어떤 테스트(T#)로, 어떤 실행(E#)으로 증명됐는지"를 거슬러 올라갈 수 있고, 이것이 보고서와 6문항의 근거가 됩니다.

```text
과제 전체 스캔 → 요구사항 R · 제약 C · 모호성 G
   → (DM) 보낸 메시지 M# → 답변 → 확정 정책 P# / 가정 A# / 다시 열린 G#
   → SPEC 통합 → 수용 기준 AC-R#-n → 수용 테스트 T#
   → 슬라이스 S# (+ 설계 결정 DD#) → 구현 루프 → 실행 증거 E# → 판정
   → 리뷰 발견 F# · AI 교정 AI# → 보고서 5개 절 · 6문항 카드
```

지켜야 할 원칙은 세 가지입니다.

1. **구현 전에 확정한다.** 모호한 규칙은 추측으로 코딩하지 않고 담당자에게 묻거나, 되돌릴 지점이 있는 가정 A#로 둡니다.
2. **한 번에 한 슬라이스.** "전부 구현해 줘"라고 하지 않습니다. 슬라이스 하나를 테스트로 닫고 다음으로 갑니다.
3. **실행한 것만 증거.** 실제로 돌린 명령과 결과만 E#로 남기고, 코드가 바뀌면 다시 실행합니다.

- **기준선이 왜 중요한가**: 구현 뒤 실패가 보이면 "내가 깨뜨린 것"인지 "원래 실패하던 것"인지 기준선으로 구분합니다. 구현 루프의 착수 점검도 기준선이 없으면 멈춥니다.
- **과제 유형이 쓰이는 곳**: DM 완성 예시(E1~E6) 선택, 검증 단계의 유형별 점검(데이터 5.3 / API 5.4 / UI 5.5), 보고서 서술.
- 코드 지도는 DM 답을 기다리는 동안(5.4절) 보강해도 됩니다.

## 5. 담당자 DM으로 요구사항·제약 확정 — 질의 루프 (1단계, 10:12–10:40)

구현 품질은 코드를 쓰기 전에 거의 정해집니다. 모호한 규칙(결측값 처리, 동점 정렬, 규칙 충돌 우선순위, 출력 형식)을 추측으로 구현하면 테스트·채점 기준과 어긋나고, 나중에 고치려면 여러 파일을 다시 건드려야 합니다. 그래서 **질문 → 답변 기록 → 후속 질문**을 모호함이 닫힐 때까지 반복하고, 그 결과를 6절에서 한 번에 명세로 정리한 뒤 구현에 들어갑니다.

### 5.1 질의 루프 한 사이클 (`$sk-clarify-loop`, 권장)

1.1~1.5를 하나씩 부르는 대신 `$sk-clarify-loop` 하나로 라운드를 돌립니다. 세부 규칙은 1.1~1.5 스킬을 그대로 따르고, 루프는 라운드 진행과 판정만 맡습니다.

```text
R0   help.py 1.0 -p     → 과제 전체 스캔 → R·C·제출물·G 목록 → 첫 DM 초안 (M01, 최대 3문항)
      ↓ [내가 DM 복사·전송]   ── 기다리는 동안: 2.2 데이터 계약, 0.3 보강, SPEC 초안 (5.4절)
Rn   help.py 1.0 -p 2   → 답변 원문 붙여넣기 → 원문 보존 → 답변 유형 분류 → P#/A#/G#
                          → 영향 재스캔 → 파생 7점검 → 판정
      ├─ 계속       → 다음 묶음 DM (M03 등) → 전송 → Rn 반복
      ├─ 확인       → 재진술 확인 DM 1회 (M11) → 동의·수정 반영 → 종료
      ├─ 종료       → help.py 1.0 -p 4 마감 → 6절 (2.1 spec)
      ├─ 병행 전환  → 남은 G를 가정으로 두고 6절 진행, 구현하며 계속 질문 (5.7절)
      └─ 차단       → 긴급 단일 질문 (M09) + 위험 고지
```

### 5.2 라운드 0 — 무엇을 뽑아내나

**전체 스캔**: `sk/`·`.git`·`.agents`·의존성 폴더를 뺀 모든 파일을 역할(문서·명세, 샘플·데이터, 테스트, 코드-진입점·핵심·보조, 설정)과 읽기 깊이(정독·훑음·제외+사유)로 분류해 `DISCOVERY.md`의 `## 스캔 커버리지`에 남깁니다. 문서·테스트·진입점·미구현 흔적·실행 설정은 반드시 정독하고, CSV·JSON·JSONL 데이터는 `python3 sk/snippets/data_audit.py <파일>`로 결측·음수·중복 수치를 얻습니다. `.env`처럼 비밀이 있을 수 있는 파일은 키 이름만 기록합니다.

**뽑아내는 네 가지** (모두 `파일:줄` 출처를 답니다):

- **요구사항 R**: 기능, 출력, 비기능 요구. 기존 테스트가 기대하는 동작(암묵 요구사항)도 포함합니다.
- **제약 C**: 유지할 API·함수 서명·출력 스키마, 지정 포트·`0.0.0.0`, 금지 라이브러리, 수정 금지 파일, 성능, 제출 형식.
- **필수 제출물**: 파일명·경로·형식. 보고서 위치도 여기서 확정합니다.
- **모호성 G**: 아래 14개 범주로 훑습니다. 각 G에는 "A로 하면 결과가 X, B로 하면 Y"라는 구체적 차이, 영향도, 기본안, 결정이 필요한 시점을 적습니다.

**영향도**: 제출 실패·금액/집계·API 호환성·데이터 손실에 걸리면 **H**, 제한된 화면·P1 기능이면 **M**, 문구·비핵심이면 **L**입니다. DM으로 묻는 것은 H부터이고, 문서·테스트·데이터로 스스로 답할 수 있는 G는 묻지 않고 근거를 적어 닫습니다.

| 범주 (1.2 ambiguity 순서) | 이럴 때 G가 됩니다 | DM 템플릿 패턴 |
| :--- | :--- | :--- |
| 용어 정의 | "유효 회원", "활성 주문"의 범위가 문서에 없음 | P01 |
| 결측·빈 값·형식 오류 | 빈 값 12건, `-999` 3건, 날짜 형식이 섞임 | P02 |
| 이상치·경계 등호 | "5만 원 이상"에서 정확히 50,000원, 음수 수량 | P03 |
| 중복·같은 요청 반복 | 같은 주문 ID 2행, 같은 요청 재전송 | P04 |
| 정렬·동점 | 점수가 같을 때 순서, 정렬 방향 | P05 |
| 숫자 형식·반올림·단위 | 반올림 시점, 소수 자리, 원/천 원 | P06 |
| 시간대·기간 경계 | "일별" 기준 시간대, 자정 직전·직후 기록 | P07 |
| 규칙 충돌 우선순위 | 회원 할인과 쿠폰을 함께 받는 주문 | P08 |
| 오류 처리 방식 | 잘못된 입력에 오류 응답 / 건너뜀 / 기본값 | P09 |
| 출력 형식·빈 결과 | 결과가 없을 때 `[]` / `null` / 안내 문구 | P10 |
| 규모·성능 기대 | 데이터 건수, 응답 시간 기대 | P11 |
| 범위·이번에 하지 않을 것·기존 동작 변경 | 기존 리포트 열을 바꿔도 되는지 | P12 |
| 권한·보안·민감정보 | 누가 볼 수 있는지, 가릴 값 | P13 |
| 결과물 형식·전달 방식 | 파일 형식, 저장 위치, 제출 방법 | P14 |

### 5.3 DM 메시지 만들기 — 템플릿 사용법

템플릿 원문은 `python3 sk/scripts/help.py dm`(파일 `sk/templates/DM_QUESTION_TEMPLATES.txt`)로 봅니다. Codex가 아래 순서로 메시지를 만들고, 나는 체크리스트만 확인해서 보냅니다.

1. 열린 G의 범주를 보고 같은 번호의 **질문 패턴**(P01~P14, 템플릿 3절)을 고릅니다.
2. 지금 상황에 맞는 **메시지 형식**(M01~M11, 템플릿 4절)을 고릅니다.
3. 패턴의 '채울 칸'을 실제 대상·값·건수·선택지별 결과로 채웁니다. 패턴 문장을 그대로 보내지 않습니다.
4. 영향이 큰 것(H)부터 최대 3문항을 **메시지 뼈대**(템플릿 2절: 묶음 S1 / 단일 S2)에 넣습니다.
5. **보내기 전 체크리스트**(템플릿 9절)를 통과시킵니다.
6. `DM_LOG.md`에 M 블록(사용한 패턴·형식 번호, 질문 매핑 `M#-k → G#`)을 남기고 복붙용 메시지 1개를 코드블록으로 줍니다.

**상황별 메시지 형식**

| 형식 | 쓰는 때 |
| :--- | :--- |
| M01 첫 질문 묶음 | 구현 전, 영향 큰 의문이 2~3개 |
| M02 단일 질문 | 의문이 하나뿐이거나 시간이 5분 이내 |
| M03 후속 질문 | 답이 일부만 해결함 (이전 답 인용 1줄 + 남은 정책 하나) |
| M04 "상황에 따라 다르다" 뒤 | 나누는 조건을 묻기 |
| M05 예시 확인 | 규칙은 알지만 적용 경계가 불명확 |
| M06 문서와 답변 충돌 | 두 근거를 나란히 보여 주고 어느 쪽인지 확인 |
| M07 "알아서 해 주세요" 뒤 | 기본안 알림 (답을 요구하지 않음) |
| M08 범위 확인 | 질문이 넓어질 때 여러 의문을 한 번에 정리 (수렴 점검) |
| M09 긴급 단일 | 핵심 기능 구현이 막힘 (결정 시점 포함) |
| M10 동결 후 병행 확인 | 가정으로 구현 중인 항목을 확인 |
| M11 구현 직전 재진술 확인 | 1.5 dm-confirm (10줄 이내, 새 질문을 섞지 않음) |

**공통 규칙 12개** (템플릿 1절. 템플릿 안의 R1~R12는 요구사항 R#과 무관한 규칙 번호입니다)

| 규칙 | 내용 |
| :--- | :--- |
| 분량 | 한 메시지 최대 3문항, 인사·마무리 포함 12줄 이내. 단일·긴급은 6줄 이내 (빈 줄 제외) |
| 한 번호 = 정책 하나 | 결측 처리와 정렬 기준을 한 번호에 섞지 않음 |
| 질문 구성 | 상황 한 줄(실제 예시 포함) → 선택지 A/B(/C) → 기본 제안과 이유 한 줄 |
| 열린 대안 | "다른 기준이 있으면 알려주세요"를 질문마다 또는 묶음 마지막에 한 번 |
| 답변 형식 | 묶음이면 "`1-A, 2-B`처럼 답해주셔도 됩니다." |
| 업무 언어 | 내부 ID(R2, G3, P1), 파일 경로, 함수명, 코드 용어(null, parse, throw) 금지. 결과로 말함 |
| 실제 예시 | 판단에 필요한 값·건수는 그대로(수량=-2, 12건), 개인정보·식별자·비밀값은 가림 |
| 선택지 | 서로 겹치지 않고 결과가 보이는 동작, 3개까지. "적절히", "알아서"는 선택지가 아님 |
| 기본 제안 | 답이 없을 때 가장 안전하고 되돌리기 쉬운 안. 이유는 한 가지 |
| 묻지 않음 | 문서·샘플·테스트·데이터로 답이 나오는 것, 구현 방법, 채점·평가 방식, 대회 운영 규칙 |
| 보내는 때 | 앞 메시지의 답이 오기 전에는 다음 묶음을 보내지 않음, 재촉하지 않음 (예외: M09) |
| 말투 | 정중한 존댓말, 한 문장에 한 뜻, 질문은 물음표로 끝냄 |

**나쁜 예와 좋은 예**

```text
나쁜 예: 결측치는 어떻게 처리할까요?

좋은 예: 안녕하세요. 일별 판매 집계 관련해 구현 전에 기준 몇 가지를 확인 부탁드립니다.
        1. 수량이 비어 있는 주문이 12건, 음수(예: 수량=-2)인 주문이 3건 있습니다. 어떻게 처리할까요?
           A) 집계에서 제외  B) 오류 건으로 따로 표시하고 합계에는 제외  C) 0으로 보고 포함
           저는 합계 왜곡을 막기 위해 A를 제안드립니다.
        2. "일별"은 어느 시간 기준인가요? (자정 전후 주문 41건의 날짜가 달라집니다)
           A) 한국 시간  B) 기록된 시각 그대로(UTC)
           저는 담당 업무가 국내 기준이라 A를 제안드립니다.
        다른 기준이 있으면 편하게 알려주세요. `1-A, 2-A`처럼 답해주셔도 됩니다.
```

템플릿에는 이 밖에 과제 유형별 완성 예시 6세트(E1 데이터 집계, E2 API·서버, E3 규칙 판정, E4 기존 기능 수정, E5 화면, E6 답변 뒤 후속 라운드), 나쁜 질문 고쳐 쓰기, 표현 사전이 있습니다.

**보내기 전 체크리스트** (하나라도 아니면 Codex에 고치라고 합니다)

- 문서·샘플·테스트·데이터로 답이 나오지 않는 질문만 남았다.
- 영향이 큰 것(H)부터 최대 3문항이고, 한 번호에 정책 하나만 묻는다.
- 질문마다 실제 예시(값·건수·사례), 겹치지 않는 선택지, 기본 제안과 이유가 있다.
- "다른 기준" 문장과 답변 형식 안내가 있다.
- 내부 ID·파일 경로·함수명·코드 용어가 없고, 개인정보·식별자·비밀값을 가렸다.
- 구현 방법·채점·대회 운영 질문이 없다.
- 인사 포함 12줄(단일·긴급 6줄) 이내, 정중한 존댓말이다.
- 앞 메시지의 답을 기다리는 중이 아니다(M09 제외).
- `DM_LOG.md`에 M 블록, 패턴·형식 번호, 질문 매핑을 남겼다.

### 5.4 보내고 기다리는 동안

DM은 우측 메신저의 `업무 담당자`에게 내가 직접 복사해 보냅니다(Enter 전송, Shift+Enter 줄바꿈). 답을 기다리는 동안에는 **질문한 규칙에 의존하지 않는 일**을 합니다.

- [2.2 io-contract](../prompts/2-spec/2.2-io-contract.md): 입력·출력·오류 계약 작성 (6.2절).
- [0.3 code-map](../prompts/0-start/0.3-code-map.md) 보강: 질문한 규칙이 코드 어디에 들어갈지 미리 찾기.
- SPEC 초안: 질문한 부분은 기본안을 가정 A#로 적고 **되돌릴 지점**(어느 함수·조건을 바꾸면 되는지)을 같이 남깁니다.

답이 늦으면 재촉하지 않고 [1.0 블록 5](../prompts/1-discover/1.0-clarify-loop.md)로 기본안을 가정으로 두고 진행합니다.

### 5.5 답이 오면 — 답변 라운드

담당자 답변을 **원문 그대로**(요약하거나 고치지 말고) Codex에 붙여 넣습니다. 어느 메시지에 대한 답인지 모르면 Codex는 가장 최근에 보낸 M#로 보고 그 가정을 밝힙니다.

```text
$sk-clarify-loop
M1 답변입니다.
<담당자 답변 원문>
```

Codex는 원문을 `DM_LOG.md`에 보존하고, 답변의 유형에 따라 다르게 처리합니다.

| 답변 유형 | 예 | 처리 | 후속 형식 |
| :--- | :--- | :--- | :--- |
| 명시 확정 | "1-A, 2-A" | P# 확정 ("조건 → 동작" + 예시 + 근거 M#) | — |
| 조건부 확정 | "음수만 오류, 빈 값은 제외" | 조건을 나눠 P#, 남은 조건은 G# | M04 |
| 부분 답 | 3문항 중 1개만 답함 | 답한 것만 P#, 나머지 G 유지 | M03 |
| 위임 | "알아서 처리하세요" | 되돌릴 수 있는 기본안 A# (근거: 담당자 위임) | M07 (알림만) |
| 무응답·읽음 | 답 없음 | G 유지, 시간이 되면 A# | — (재촉 금지) |
| 선택지 밖 답 | "B인데 표시는 하지 마세요" | 선택지에 억지로 맞추지 않고 원문대로 P# | 필요하면 M05 |
| 문서와 충돌 | 문서는 `[]`, 답변은 "비워 두세요" | 조용히 고르지 않고 G# 재등록 | M06 |

**P#는 테스트할 수 있는 문장**으로 씁니다. 예: `P1 수량이 비었거나 0 미만인 주문 → 일별 합계·건수에서 제외 (예: 수량=-2 → 제외) · 근거 M1-1`.

**영향 재스캔**: 새 P#의 필드명·상태값·경로로 과제 전체를 다시 검색해, 같은 규칙이 적용될 다른 위치와 반대로 기대하는 테스트·문서를 찾습니다. 찾은 충돌은 G#로 다시 엽니다.

**파생 7점검**: 답변마다 아래 7가지를 확인하고, **결과가 달라지는 것만** 새 질문 후보로 올립니다. 문구는 템플릿 5절 D1~D7에 있습니다.

| 점검 | 확인할 것 | 예시 문구 |
| :--- | :--- | :--- |
| D1 경계 | 값이 정확히 0·기준값·빈 문자열일 때 | "수량이 0인 주문도 같은 기준으로 제외할까요?" |
| D2 적용 범위 | 같은 기준을 다른 항목·기능·파일에도 쓰는지 | "같은 기준을 반품 데이터에도 적용할까요?" |
| D3 결과 표시 | 제외·오류 처리한 건을 결과에 표시하는지 | "제외한 주문이 있다는 사실을 결과에 표시할까요?" |
| D4 집계 영향 | 제외 건이 분모·건수·순위에서도 빠지는지 | "제외한 건은 전체 건수에서도 빠지는 것이 맞을까요?" |
| D5 규칙 순서 | 두 규칙의 적용 순서에 따라 결과가 달라지는지 | "할인과 쿠폰의 적용 순서에 따라 금액이 달라집니다" |
| D6 예외 | 예외로 둘 경우가 있는지 | "테스트 데이터도 같은 기준인가요?" |
| D7 적용 시점 | 과거 데이터에도 적용하는지 | "이미 저장된 지난달 데이터에도 적용할까요?" |

### 5.6 판정 — 언제 다시 묻고 언제 닫나

라운드가 끝날 때마다 Codex가 판정하고 `DM_LOG.md` 맨 위 `## 질의 루프 상태판`을 갱신합니다.

| 판정 | 조건 | 다음 행동 |
| :--- | :--- | :--- |
| 계속 | 질문 가치가 있는 열린 H, 또는 P0 결과를 바꾸는 열린 M이 1개 이상 | 다음 묶음 DM (최대 3문항, H 먼저) |
| 확인 | 열린 H 0개, P0 결과를 바꾸는 열린 M 0개 | 재진술 확인 DM 1회 (M11, 6.4절) |
| 종료 | 확인 DM에 동의·수정 반영 완료, 또는 남은 G가 모두 L·범위 밖 | 남은 G를 가정 전환·보류로 정리하고 마감 → 6절 |
| 병행 전환 | 열린 H·M이 남았지만 동결 목표 시각이 지남 | 남은 G를 되돌릴 지점이 있는 가정으로 두고 6절 진행, 질문은 병행 라운드로 |
| 차단 | 필수 제출물·P0 출력 형식 자체가 미정이고 문서·답변 모두 없음 | 긴급 단일 질문 (M09) + 위험 고지, 2.4에서 BLOCKED 예상 |

**닫힘 기준**: 열린·질문 중·충돌 상태의 H가 0개이고, 모든 P에 "조건 → 동작"·예시·근거가 있고, 문서↔P 충돌이 0개이며, P0 요구마다 기대 출력을 손으로 계산할 수 있을 때 닫힌 것으로 봅니다.

**질문 수**: 총 질문 수·라운드 수 상한은 없습니다. 대신 메시지당 3문항, 앞 답이 오기 전 다음 묶음 금지, 매 라운드 가치 없는 질문(문서로 답이 있거나 결과가 안 바뀌는 것) 제거를 지킵니다. 라운드 5회·질문 15개마다 Codex가 수렴 점검(열림·닫힘 추세, 범위가 넓어지는지)을 보고하고, 계속할지는 내가 정합니다. 범위가 넓어지면 M08로 한 번에 정리합니다.

### 6.2 입출력·데이터 계약 (2.2 io-contract)

경계를 `입력자 → 검증 지점 → 핵심 처리 → 출력 소비자`로 나열하고 표로 고정합니다.

- **입력 계약**: 필드 · 타입 · 필수 · 허용 범위·형식 · 결측 표현 · 단위·시간대 · 예시 · 상태·근거. 키가 있으면 고유성·중복·멱등성 행을 따로 둡니다.
- **정상 출력 계약**: 필드 · 타입 · 계산·변환 · 정렬 · 반올림·단위 · null 표현 · 빈 결과 · 근거.
- **오류 계약**: 조건 · 상태 코드·예외 · 본문/메시지 · 필드 오류 · 부분 성공 · 재시도 · 근거.
- **API 과제**: 메서드 · 경로 · 요청 · 성공 상태·본문 · 오류 상태·본문 · 호환성 제약.
- 데이터 파일은 `python3 sk/snippets/data_audit.py <파일>`의 관찰값(행 수, 결측, min/median/max, 음수·0, 중복)을 옮기고, 근거 없는 처리 방식은 만들지 않고 G 후보로 올립니다. TSV·Excel·Parquet은 지원하지 않으므로 과제의 기존 도구로 확인합니다.

### 6.3 수용 테스트 표 (2.3 acceptance) — 구현과 검증의 기준

각 R의 `AC-R#-n`과 **모든 P#**를 구체적인 테스트 T#로 바꿉니다. 이 표가 구현 루프에서 그대로 테스트 코드가 됩니다.

- 유형은 정상 · 경계 · 실패 · 회귀 중 하나입니다. P0 R부터 만들고, 모든 P#가 적어도 하나의 T#에 연결됐는지 따로 확인합니다.
- 입력은 재현 가능한 구체값(행, 요청 본문, 사전조건)으로, 기대 출력은 정확한 값·상태·정렬·오류 구조로 씁니다. "유효한 입력", "정상 처리" 같은 표현은 쓰지 않습니다.
- **기대값은 구현과 독립적으로 손계산**합니다. 구현할 함수를 실행해서 기대값을 만들지 않습니다.

| T# | 유형 | 대상 | 입력 | 기대 출력 | 기대값 근거 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| T1 | 정상 | R1, AC-R1-1 | 6/1 주문 수량 2·3 | `2026-06-01: 5` | 2+3=5 (손계산) |
| T2 | 경계 | P4 | 6/1 수량 0·3 | `2026-06-01: 3`, 건수 1 | P4: 0 제외 |
| T3 | 실패 | P1 | 6/1 수량 빈 값·-2·4 | `2026-06-01: 4`, 건수 1 | P1: 빈 값·음수 제외 |

### 6.4 재진술 확인 DM (1.5 dm-confirm, 템플릿 M11)

구현 직전에 "제가 이해한 내용"을 10줄 이내로 보내 확인받습니다. 새 질문을 섞지 않습니다. 영향도 H 가정이 남아 있을 때 특히 중요합니다.

```text
안녕하세요. 구현 전에 제가 이해한 기준을 정리해 확인 부탁드립니다.
목표: 유효한 주문만 기준으로 일별 판매 합계를 제공하는 것입니다.
1. 수량이 비어 있거나 0 이하인 주문은 합계와 건수에서 제외합니다.
```

담당자가 한 문장만 고쳐도 나머지가 자동 확정된 것으로 보지 않습니다. 고친 부분은 1.0 라운드로 다시 반영합니다.

### 8.2 구현 원칙

- **한 번에 한 슬라이스.** 연속 모드도 하나씩 판정한 뒤 다음으로 갑니다.
- **테스트를 구현에 맞추지 않는다.** 기대값을 바꾸거나 assertion을 약하게 하거나 기존 테스트를 고치·지우·건너뛰지 않습니다. 그래야 통과한다면 멈추는 것이 맞습니다.
- **결정은 바로 기록**: 구현 중 선택이 생기면 [3.3 decision-log](../prompts/3-plan/3.3-decision-log.md)로 DD#를, AI가 처음 만든 코드의 문제를 내가 발견해 고치게 했다면 **AI 교정 기록 AI#**를 남깁니다. 보고서 4절과 후속 Q4(검증 및 AI 교정)의 핵심 근거입니다.
- **증거는 실행으로만**: 테스트·명령을 실제로 실행한 결과만 E#로 기록합니다(8열: E# · 시각 · 명령·작업 디렉터리 · 대상 R/T · 기대 · 실제 결과 요약 · 판정 · 코드 상태). 코드가 바뀌면 이전 증거는 STALE이 되어 다시 실행합니다.
- **엣지 케이스**(원본 가이드의 7대 범주): 결측·빈 값, 경계값·이상치·0 나누기, 타입·스키마 오염, 중복·멱등성, 동점 정렬, 권한·상태 전이(4xx), 서버 바인딩·경로. 현재 기능과 관련된 범주만, 담당자 정책 P#에 근거해 방어하고 회귀 테스트로 남깁니다. 근거가 없으면 막지 않고 질문 후보로 올립니다.
- **무관한 변경 금지**: 리팩터링·포맷 정리·이름 변경·의존성 추가를 섞지 않습니다. `git reset --hard`, `git clean`, `git stash`, push·배포·제출은 Codex가 실행하지 않습니다.

3. **마무리 순서**: 9.1 understand → 9.4 retrospect → **8.1 report** → 9.2 qa-card → **8.2 deliver** → 9.3 qa-drill. 보고서 3절(구현 흐름)과 5절(한계)의 근거를 먼저 만들기 위한 순서입니다.
4. [8.1 report](../prompts/8-submit/8.1-report.md): `sk/templates/SUBMISSION_DOC_TEMPLATE.md`의 5개 절을 작업 노트로 채웁니다(1절←SPEC·DM, 2절←DECISIONS, 3절←코드·UNDERSTANDING·슬라이스 설명, 4절←테스트·EVIDENCE·AI 교정, 5절←한계). 예시 문구를 그대로 남기지 않고, 실제로 처리·검증한 엣지 케이스만 적습니다. 저장 위치는 과제가 지정한 경로이고, 지정이 없으면 `sk/work/REPORT_DRAFT.md`에 쓴 뒤 위치를 확인합니다.

6. **도구 정리 판단**: 지정 파일만 제출한다면 정리할 필요가 없습니다. 과제 폴더나 저장소 전체를 제출한다면, 필요한 내용이 보고서에 들어갔는지 확인한 뒤 아래 명령을 실행합니다.

```bash
python3 sk/scripts/install.py --uninstall --dry-run
python3 sk/scripts/install.py --uninstall
rm -rf sk
```

`--uninstall`은 AGENTS.md 관리 구역, 설치한 스킬, git 제외 설정만 제거하고 `sk/work` 노트와 백업은 남깁니다. 설치 후 내가 수정한 스킬 파일은 지우지 않고 알려 줍니다. `rm -rf sk`는 노트까지 지우므로 공식 제출 규칙을 확인하고 마지막에 실행합니다.

## 12. 후속 서술형 6문항 대비 (9단계)

후속 서술형은 **AI·복붙 없이 문항당 5분**입니다. 그래서 제출 전, AI 사용이 허용된 시간에 **내가 만든 것을 내 말로 설명할 수 있게** 준비합니다. 남이 쓴 답을 외우는 것이 아니라 내 코드·결정·증거를 이해하는 작업입니다. DM부터 구현까지 남긴 ID가 여기서 그대로 근거가 됩니다.

| 문항 | 알아야 할 것 | 근거가 쌓이는 곳 |
| :--- | :--- | :--- |
| Q1 설계 의도 (Why) | 선택한 구조, 비교한 대안, 선택 이유가 된 요구사항·제약, 포기한 것 | `DECISIONS.md` DD#, `SPEC.md` C# |
| Q2 동작 원리 (How) | 진입 파일·함수, 입력 → 검증 → 핵심 로직 → 출력 흐름, 예시 1건의 값 변화 | `UNDERSTANDING.md` 흐름·예시 추적, 슬라이스 설명 |
| Q3 예외 방어 (Edge Cases) | 정의한 엣지 케이스, 방어 위치(Guard), 정책 근거, 회귀 테스트 | `SPEC.md` T#, `UNDERSTANDING.md` 방어 위치 |
| Q4 검증 및 AI 교정 | 테스트 종류와 수, 독립 검산 방법, AI 초기 코드에서 내가 찾은 문제와 수정 지시 | `EVIDENCE.md` E#, `DECISIONS.md` AI# |
| Q5 업무 맥락 (Business Fit) | 담당자에게 물은 것, 받은 답, 그 답이 코드의 어디에 반영됐는지 | `DM_LOG.md` M#·P#, `REVIEW.md` 준수 감사 |
| Q6 한계·개선안 | 실제 구조에서 나오는 실패 조건, 시간 때문에 택한 단순화, 구체적 개선안 | `UNDERSTANDING.md` 한계·개선안, 남은 A#·G# |

준비 순서는 이렇습니다.

1. [9.1 understand](../prompts/9-qa/9.1-understand.md): 파일·함수 지도, 예시 1건 추적, 정책이 강제되는 위치, 테스트가 증명하는 것과 못하는 것, 핵심 사실 10개를 정리합니다.
2. [9.4 retrospect](../prompts/9-qa/9.4-retrospect.md): 일반론이 아닌, 내 구현에 해당하는 한계와 개선안을 정리합니다.
3. [9.2 qa-card](../prompts/9-qa/9.2-qa-card.md): `sk/templates/POST_QA_6_TEMPLATE.md`의 Q1~Q6 3문장 형식에 실제 파일·함수·DD·P·T·E·AI를 넣어 카드를 만들고, 문항마다 키워드 5개와 예상 꼬리질문 1개를 붙입니다.
4. [9.3 qa-drill](../prompts/9-qa/9.3-qa-drill.md): 카드를 보지 않고 내가 먼저 답을 써 보고, Codex는 근거와 대조해 빠진 점만 짚습니다. 완성 답안을 대신 써 주지 않습니다.

**AI 금지 단계가 시작되면 카드·노트·Codex 사용을 즉시 멈춥니다.** 자료 참조 허용 여부는 공식 규칙을 따릅니다.

## 16. 설치 관리와 문제 해결

```bash
python3 sk/scripts/install.py --dry-run      # 변경 없이 계획만
python3 sk/scripts/install.py --check        # 설치 파일 상태 점검 (읽기 전용)
git -C sk pull && python3 sk/scripts/install.py   # 키트 갱신 후 재설치
python3 sk/scripts/install.py --uninstall    # 설치한 것만 제거
```

| 증상 | 해결 |
| :--- | :--- |
| `과제 루트에서 실행하세요` | 안내된 `cd '<과제 루트>'`를 실행한 뒤 `python3 sk/scripts/install.py` |
| `클론 폴더 이름은 sk여야 합니다` | 과제 루트에서 `git clone https://github.com/juwkim35721/sk sk`로 다시 받기 |
| `/skills`에 `sk-*`가 안 보임 | ① Codex를 과제 루트에서 실행했는지 확인 ② Codex 재시작 ③ 그래도 없으면 구버전 경로로 설치: `python3 sk/scripts/install.py --skills-dir codex` 후 재시작 ④ 스킬 호출 없이 프롬프트 본문만 사용 |
| AGENTS.md 관리 구역 표시가 손상됨 | 설치가 멈춥니다. `SK-KIT:BEGIN`/`END`를 한 쌍만 남기고 다시 설치 |
| 과제 테스트·린트가 `sk/`를 검사함 | `sk/`는 도구이므로 제외 옵션 사용(예: `--exclude sk`) |
| 설치 전 상태로 되돌리고 싶음 | `--uninstall`. 덮어쓴 파일의 원본은 `sk/.install/backups/<시각>/`에 있음 |

## 17. 시험 전 리허설 (권장)
