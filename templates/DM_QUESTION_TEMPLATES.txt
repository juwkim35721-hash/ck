담당자 DM 질문 템플릿 (우측 메신저 '업무 담당자(실무자 에이전트)'용)
====================================================================
이 파일은 Codex가 담당자 DM을 만들 때 읽는 원본 양식이다.
- 쓰는 곳: 1.3 dm-questions($sk-dm-questions), 1.0 clarify-loop($sk-clarify-loop),
           1.4 dm-answers의 후속 질문, 1.5 dm-confirm의 재진술 확인
- 보기   : python3 sk/scripts/help.py dm
- 패턴 문장을 그대로 보내지 않는다. <꺾쇠> 칸을 실제 과제의 대상·값·조건·결과로 바꾼다.
- Codex는 DM을 보내지 않는다. 사용자가 복사해 직접 보내고, 답변 원문을 다시 붙여 넣는다.
- 처음 3개 질문(결측·이상치, 규칙 충돌, 정렬·동점)은 P02·P03, P08, P05로 확장했다.

목차
  0. 빠른 사용 순서
  1. 공통 규칙 (반드시 지킴)
  2. 메시지 뼈대 (묶음 · 단일)
  3. 범주별 질문 패턴 14종 ............ [P01]~[P14]  (1.2 ambiguity의 14개 범주와 같은 순서)
  4. 상황별 메시지 형식 11종 ........... [M01]~[M11]
  5. 답변 뒤 파생 질문 문구 7종 ........ [D1]~[D7]   (1.0 clarify-loop의 파생 7점검)
  6. 과제 유형별 완성 예시 6세트 ....... [E1]~[E6]
  7. 나쁜 질문 → 좋은 질문 고쳐 쓰기
  8. 표현 사전 (인사 · 제안 이유 · 마무리 · 피할 말)
  9. 보내기 전 체크리스트

0. 빠른 사용 순서
====================================================================
1) 열린 G의 범주를 확인하고 3절에서 같은 번호의 패턴을 고른다. (예: 정렬·동점 → P05)
2) 지금 상황에 맞는 4절 형식을 고른다. (첫 묶음 M01, 답변 뒤 후속 M03, 충돌 M06 ...)
3) 패턴의 '채울 칸'을 실제 대상·값·건수·선택지별 결과로 채운다. 민감값은 가린다.
4) 영향이 큰 것(H)부터 최대 3문항을 2절 뼈대에 넣는다.
5) 9절 체크리스트를 통과시킨다.
6) sk/work/DM_LOG.md에 M 블록(사용 패턴·형식 번호, 질문 매핑 M#-k → G#)을 남기고,
   복붙용 메시지 1개를 사용자에게 준다.


====================================================================
1. 공통 규칙 (반드시 지킴)
====================================================================
R1  분량     : 한 메시지 최대 3문항, 인사·마무리 포함 12줄 이내. 단일·긴급 질문은 6줄 이내.
               (빈 줄은 세지 않는다)
R2  한 번호 = 정책 하나 : 결측 처리와 정렬 기준을 한 번호에 섞지 않는다.
R3  질문 구성 : 상황 한 줄(실제 예시 포함) → 선택지 A/B(/C) → 기본 제안과 이유 한 줄.
R4  열린 대안 : "다른 기준이 있으면 알려주세요"를 질문마다, 또는 묶음 마지막 줄에 한 번 넣는다.
R5  답변 형식 : 묶음이면 마지막에 "`1-A, 2-B`처럼 답해주셔도 됩니다."를 넣는다.
R6  업무 언어 : 내부 ID(R2, G3, P1), 파일 경로, 함수명, 코드 용어(null, parse, throw)를 쓰지 않는다.
               "값이 비어 있으면", "형식이 잘못되면", "오류로 응답"처럼 결과로 말한다.
R7  실제 예시 : 판단에 필요한 값·건수는 그대로(수량=-2, 12건), 개인정보·식별자·비밀값은 가린다
               (고객=…, 연락처=010-****-1234).
R8  선택지   : 서로 겹치지 않고, 결과가 눈에 보이는 구현 가능한 동작이어야 한다.
               "적절히", "알아서", "상황에 맞게"는 선택지로 쓰지 않는다. 선택지는 3개까지.
R9  기본 제안 : 답이 없을 때 가장 안전하고 되돌리기 쉬운 안. 이유는 한 가지만 쓴다(8절 이유 목록).
R10 묻지 않음 : 문서·샘플·테스트·데이터로 답이 나오는 것, 구현 방법, 채점·평가 방식,
               대회 운영 규칙(제출 시간·방법은 공식 공지로 확인).
R11 보내는 때 : 앞 메시지의 답이 오기 전에는 다음 묶음을 보내지 않는다. 재촉하지 않는다.
               예외는 구현이 멈춘 긴급 단일 질문(M09)뿐이다.
R12 말투     : 정중한 존댓말, 한 문장에 한 뜻, 질문은 물음표로 끝낸다.

2. 메시지 뼈대
====================================================================
[S1] 묶음 (2~3문항, 12줄 이내)
--------------------------------------------------------------------
안녕하세요. <업무 대상> 관련해 구현 전에 기준 몇 가지를 확인 부탁드립니다.
1. <상황 한 줄, 실제 예시 포함>?
   A) <동작 → 결과>  B) <동작 → 결과>  C) <동작 → 결과>
   저는 <이유>로 <A>를 제안드립니다.
2. <상황 한 줄>?
   A) <동작 → 결과>  B) <동작 → 결과>
   저는 <이유>로 <B>를 제안드립니다.
3. <상황 한 줄>?
   A) ...  B) ...
   저는 <이유>로 <A>를 제안드립니다.
다른 기준이 있으면 편하게 알려주세요. `1-A, 2-B, 3-A`처럼 답해주셔도 됩니다.
--------------------------------------------------------------------

[S2] 단일 (1문항, 6줄 이내)
--------------------------------------------------------------------
안녕하세요. <업무 대상> 관련해 한 가지만 확인 부탁드립니다.
<상황 한 줄, 실제 예시 포함>?
A) <동작 → 결과>  B) <동작 → 결과>
저는 <이유>로 <A>를 제안드립니다. 다른 기준이 있으면 알려주세요.
`A` 또는 `B`로만 답해주셔도 됩니다.
--------------------------------------------------------------------


====================================================================
3. 범주별 질문 패턴 14종  [P01]~[P14]
====================================================================
각 패턴: 언제 / 채울 칸 / 문구 / 제안 예 / 이어질 후속(5절) / 답을 정책으로 옮긴 예
문구는 출발점일 뿐이다. 실제 과제의 대상·값·결과로 바꿔 쓴다.

[P01] 용어 정의
  언제    : "유효", "완료", "최신", "활성", "정상" 같은 말이 정의 없이 쓰이고 상태값이 여러 개일 때
  채울 칸 : <용어> <대상> <상태값 목록> <애매한 상태>
  문구    : "<용어> <대상>"에 상태가 <애매한 상태>인 건도 포함할까요? (현재 상태값: <목록>)
            A) 포함  B) <확정 상태>만 포함  C) <애매한 상태>는 별도 항목으로 분리해 표시
  제안 예 : B — 확정되지 않은 건이 실적에 섞이지 않도록
  후속    : D2(같은 정의를 다른 화면·기능에도 쓰는지)
  정책 예 : status가 PAID 또는 SHIPPED → 유효 주문으로 집계, PENDING → 제외

[P02] 결측 · 빈 값 · 형식 오류                                    (처음 질문 1 확장)
  언제    : 빈 값, 빈 문자열, "N/A", 숫자 자리에 문자, 날짜 형식이 깨진 값
  채울 칸 : <항목> <건수> <값 예>
  문구    : <항목> 값이 비어 있거나 "<N/A>"처럼 숫자가 아닌 기록이 <N>건 있습니다. 어떻게 처리할까요?
            A) 그 기록만 제외하고 계속 처리  B) <0> 같은 기본값으로 채워 포함  C) 오류 상태로 표시해 결과에 포함
  제안 예 : A — 값을 추정해 넣으면 합계·평균이 왜곡될 수 있어서
            (누락 추적이 중요한 업무라면 C — 빠진 건을 확인하실 수 있도록)
  후속    : D3(제외 사실 표시), D4(평균의 분모)
  정책 예 : quantity가 비어 있음·숫자 아님 → 해당 행 제외, 제외 건수는 별도로 셈

[P03] 이상치 · 경계 등호                                           (처음 질문 1 확장)
  언제    : 음수, 0, 센서 오류값(-999 등), 임계값과 정확히 같은 값
  채울 칸 : <항목> <오류값 예> <건수> <기준값> <구간 이름>
  문구 a  : <항목>에 <-999>처럼 측정 오류로 보이는 값이 <N>건, 음수가 <N>건 있습니다. 어떻게 처리할까요?
            A) 집계에서 제외  B) 오류 상태로 분류해 결과에 포함  C) 그대로 집계
  문구 b  : 기준이 "<기준값>"으로만 적혀 있어 확인드립니다. 값이 정확히 <기준값>이면 <구간 A>에 들어가나요?
            A) 들어감(<기준값> 이상)  B) 안 들어감(<기준값> 초과만)
  제안 예 : a는 A — 오류값이 평균을 크게 흔들어서 / b는 문서 예시와 맞는 쪽, 예시가 없으면 고객에게 불리하지 않은 쪽
  후속    : D1(0·빈 문자열도 같은지), D6(예외)
  정책 예 : score >= 80 → 우수 / temperature가 -999 또는 음수 → 집계 제외

[P04] 중복 · 같은 요청 반복
  언제    : 같은 ID·같은 내용이 두 번 이상 들어오거나 같은 요청이 반복될 때
  채울 칸 : <ID 종류> <가린 예시> <건수> <구분 가능한 정보: 시각·버전>
  문구    : 같은 <주문번호>(예: <ORD-…>)가 두 번 이상 들어온 경우가 <N>건 있습니다. 어떻게 처리할까요?
            A) 처음 것만 반영  B) 가장 나중 것으로 덮어쓰기  C) 중복은 오류로 거절
  제안 예 : 시각 정보가 있으면 B — 나중 기록이 정정본일 가능성이 커서 / 없으면 A — 결과가 늘 같아서
  후속    : D2(무엇이 같으면 중복인지: ID만인지, ID+날짜인지), D3(중복 건수 표시)
  정책 예 : 같은 order_id → updated_at이 가장 늦은 행만 반영

[P05] 정렬 · 동점                                                  (처음 질문 3 확장)
  언제    : 정렬 기준은 있지만 같은 값·같은 시각일 때의 순서, 순위 매기는 방식이 없을 때
  채울 칸 : <1차 기준> <방향> <동점 예시> <2차 기준 후보>
  문구 a  : 결과를 <점수> 높은 순으로 보여 드릴 때, 점수가 같으면(예: 80점 2건) 어떤 순서로 둘까요?
            A) <식별자> 오름차순  B) <시각> 최신 우선  C) 들어온 순서 유지
  문구 b  : 순위를 매길 때 동점이면 같은 순위로 둘까요? (예: 1위, 1위, 3위 / 1위, 1위, 2위 / 1위, 2위, 3위)
            A) 같은 순위, 다음 순위 건너뜀  B) 같은 순위, 다음 순위 이어짐  C) 동점 없이 차례대로
  제안 예 : a는 A — 실행할 때마다 같은 순서가 나와서
  후속    : D2(다른 목록·내보내기에도 같은 순서인지)
  정책 예 : score 내림차순, 동점이면 id 오름차순

[P06] 숫자 형식 · 반올림 · 단위
  언제    : 소수 자리, 반올림 방식·시점, 금액·시간 단위가 명시되지 않았을 때
  채울 칸 : <항목> <예시 값> <자리수> <단위 후보>
  문구 a  : <평균 금액>은 소수 몇째 자리까지 어떻게 맞출까요? (예: 1,234.565)
            A) 둘째 자리 반올림(1,234.57)  B) 둘째 자리 버림(1,234.56)  C) 원래 값 그대로
  문구 b  : 합계는 어느 시점에 반올림할까요? (예: 1,234.5 + 2,000.5)
            A) 모두 더한 뒤 한 번(3,235)  B) 건별 반올림 후 합산(3,236)
  문구 c  : <소요시간> 값의 단위는 무엇인가요? (예: 1500)  A) 밀리초  B) 초
  제안 예 : b는 A — 누적 오차가 생기지 않아서
  후속    : D2(화면 표시와 파일 저장의 자리수가 같은지)
  정책 예 : 금액 합계 → 전부 더한 뒤 소수 둘째 자리 반올림, 단위 원

[P07] 시간대 · 기간 경계
  언제    : 날짜 범위의 끝 포함 여부, 기준 시간대, 일·주·월 경계가 불명확할 때
  채울 칸 : <기간 표현> <경계 사례> <건수> <시간대 후보>
  문구 a  : "<10월 1일~10월 31일>"에 10월 31일 23시 59분 기록도 들어가나요?
            A) 들어감(종료일 하루 전체 포함)  B) 안 들어감(종료일 0시까지)
  문구 b  : 날짜 기준 시간은 무엇인가요? (자정 전후 기록 <N>건의 날짜가 달라집니다)
            A) 한국 시간  B) UTC  C) 기록에 적힌 시간 그대로
  제안 예 : a는 A, b는 A — 담당자분이 보시는 달력 날짜와 맞아서
  후속    : D2(주·월 집계에도 같은 경계인지), D7(과거 데이터)
  정책 예 : 기간 = 시작일 00:00 이상 ~ 종료일 다음 날 00:00 미만, 한국 시간 기준

[P08] 규칙 충돌 우선순위                                           (처음 질문 2 확장)
  언제    : 두 규칙이 동시에 참일 때 결과가 달라지는 경우
  채울 칸 : <조건 A> <조건 B> <실제 사례> <각각 우선 시 결과>
  문구    : <마감 시각이 지났지만 이미 취소된 주문>처럼 <조건 A>와 <조건 B>가 동시에 해당하는 경우가 있습니다.
            어느 기준을 먼저 적용할까요?
            A) <조건 A> 우선 → <결과>  B) <조건 B> 우선 → <결과>
  제안 예 : 되돌릴 수 없는 결과를 피하는 쪽 — 예: 취소 우선(취소 건이 실적에 잡히지 않도록)
  후속    : D5(세 규칙 이상이 겹칠 때 순서), D6(예외)
  정책 예 : 취소 상태 → 마감 여부와 관계없이 집계 제외

[P09] 오류 처리 방식
  언제    : 여러 건 중 일부만 잘못됐을 때, 잘못된 요청에 어떻게 응답할지 정해지지 않았을 때
  채울 칸 : <처리 단위> <오류 사례> <건수>
  문구 a  : 한 번에 여러 건을 처리하다 일부만 잘못된 경우(예: 100건 중 2건 형식 오류) 어떻게 할까요?
            A) 잘못된 건만 건너뛰고 나머지 처리, 건너뛴 목록 함께 제공

8. 표현 사전

인사·목적
  - 안녕하세요. <업무 대상> 관련해 구현 전에 기준 몇 가지를 확인 부탁드립니다.
  - 안녕하세요. 진행 중 한 가지 기준을 확인드리고 싶습니다.
  - 답변 감사합니다. 말씀하신 대로 반영하겠습니다. 이어서 한 가지만 더 여쭙겠습니다.
제안 이유 (한 가지만 고른다)
  - 합계·평균이 왜곡되지 않도록          - 데이터가 사라지지 않도록
  - 이미 쓰는 곳이 깨지지 않도록          - 실행할 때마다 같은 결과가 나오도록
  - 문서 예시와 결과가 맞도록            - 나중에 바꾸기 쉽도록
  - 잘못된 결과가 밖으로 나가지 않도록     - 고객에게 불리하지 않도록
  - 민감정보가 노출되지 않도록
마무리
  - 다른 기준이 있으면 편하게 알려주세요.
  - `1-A, 2-B`처럼 짧게 답해주셔도 됩니다.
  - 말씀 주시면 바로 반영하겠습니다.
피할 말 → 바꿀 말
  - 적절히 / 알아서 / 상황에 맞게      → 구체 동작 (제외 / 오류로 응답 / 0으로 채움)
  - null 처리 / 파싱 실패 / 예외 발생  → 값이 비어 있으면 / 형식이 잘못되면 / 오류로 응답하면
  - G3, R2, P1, 파일 경로, 함수명     → 업무 대상 이름 (주문, 센서 기록, 일별 리포트)
  - 제가 잘 몰라서                   → 문서에서 확인되지 않아
  - 급합니다 / 빨리 부탁드려요        → 삭제 (긴급이면 M09로 결정 시점만 밝힘)
